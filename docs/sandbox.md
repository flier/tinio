# `--sandbox`: what an operator has to know

`--sandbox` confines the server to the paths it is given — a private mount namespace, `pivot_root`, and a seccomp filter that denies ten syscalls and the whole x32 ABI. The notes below are Linux's, because Linux's is the mechanism they describe, unless a heading names another platform (Linux is the first of the three to land; macOS and Windows have landed since), and each is a consequence of the confinement working as designed rather than a defect: all three read as bugs the first time they are met without warning.

## macOS: two mechanisms, `sandbox-exec` by default

`TINIO_SANDBOX_MACOS_MECHANISM` selects how the profile reaches the confined child. `sandbox-exec` is the default and wraps the child's `exec` with Apple's deprecated-but-shipped helper. `sandbox-init` invokes no helper at all: the launcher hands the rendered profile to the child on the launch payload and the child applies it to itself with `sandbox_init_with_parameters` before it serves. Either name is accepted and nothing else is — a typo is a usage error (exit 2) naming the variable and its two values, never a silent run under the default.

Two consequences are the operator's. On `sandbox-init` the confinement is **one-shot and irreversible** in the child, and a process confined that way can neither fork nor exec anything afterwards, so a profile that turns out to be wrong costs a restart of the run rather than a repair. And the rendered profile is **one rule shorter** there: the `process-exec` rule exists only for `sandbox-exec`, whose helper cannot exec the child without it, so on the same one-exposure run a `sandbox-init` render's `rules=4` against the helper's `rules=5` is the measurement rather than a missing grant — a serving run counts more, one rule per exposure the launcher adds (design decision 6; design §5 owns the count).

## Windows: a served root behind a junction is granted at its target, and the child resolves the operator's spelling

The Windows launcher grants the **canonical** spelling of every exposure — a path that is, or passes through, a reparse point is refused, and what is left is resolved before the ACE is written — and the served root arrives already canonical, because the CLI canonicalises the root before it builds the exposure set. A root handed in as a directory junction is therefore granted on the directory the junction *names*, and the junction's own spelling appears nowhere in the grant. The child is re-invoked with the operator's argv, so its first act is to canonicalise the junction itself, as a confined process: an AppContainer's access check needs an ACE for a SID of its own, the junction's own directory carries none, and the child cannot resolve its root at all — it refuses before it dispatches, with `resolve_root`'s `— pass an existing DIR` sentence on the stderr it inherits.

The symptom is reported rather than silent: the launcher's own `error` frame reaches the caller, because a child that dies before reporting readiness is the parent's answer to give, and the child's refusal is on the log beside it. macOS does not meet this shape: its profile adds the resolved spelling **beside** the operator's, so a link in the exposure set matches either spelling. Whether Windows should do the same for the served root is an open product question rather than a decided one, recorded in `docs/superpowers/plans/2026-09-25-sandbox-followups.md` §22; until it is settled, serve the directory the junction names.

## The process has no capabilities, even when it runs as root

The confinement drops every capability before the server starts, `CAP_DAC_OVERRIDE` and `CAP_DAC_READ_SEARCH` among them, so the process reads files as the account it runs as rather than as the superuser it still is: under the root model it is uid 0 with an empty capability set apart from the single `CAP_CHOWN` a `local_uid` mapping needs. A file under the served root that the service account does not own and that is not readable by others is therefore refused, and an S3 client sees `AccessDenied` for objects that were readable before the flag was added. The user-namespace model states the same rule from the other side: its namespace maps exactly one uid — the invoking user's — so a file owned by any other host id is as unreadable inside the jail as a stranger's file is outside it. Run the server as the account that owns the data, or `chown -R` the served root to that account.

## Outbound connections are denied, and the filter cannot see the address family

The seccomp filter denies **ten** syscalls by number, not four: `connect`, `sendto`, `sendmsg` and `sendmmsg`, which are the paths out over a socket a dependency could reach; the three `io_uring` ring calls (`io_uring_setup`, `io_uring_enter`, `io_uring_register` — 425/426/427), which submit an `IORING_OP_CONNECT` or an `IORING_OP_SENDMSG` without ever reaching any of those four; and the ptrace family (`ptrace`, `process_vm_readv`, `process_vm_writev`), which is not about the network at all. **The x32 ABI is refused whole, not only those ten**: one `JSET 0x4000_0000` mask on the syscall number sits ahead of every comparison, so an x32 `connect` (`0x4000_002a`) meets `EPERM` like the rest of that ABI, and a reader should not conclude the filter denies ten things and nothing else. No address family can be let through either, so `connect(AF_UNIX)` is denied along with the TCP ones: inside the jail, `/dev/log` (syslog), a Docker socket and a D-Bus connection all fail with `EPERM`. This is deliberate — a filter that could see the family would be a different and larger program — and it is survivable because the server's own logs go to stderr rather than to syslog. There is no allowance to add: a Unix socket inside an exposed directory is unreachable too, because the refusal is at `connect`, not at the path.

**The ptrace half costs the operator their debuggers inside the jail, and that belongs beside the syslog consequence rather than in a footnote.** `gdb`, `perf` and `strace` each attach by calling one of those three syscalls, so none of them works on a confined server: `ptrace` answers `EPERM`, and `process_vm_readv`/`process_vm_writev` are the same read and the same write without the attach. The filter has to deny them because the jail confines the served root and not the rest of the machine — the confined process still runs as the operator's own uid, and a same-uid process outside the jail is otherwise fair game: it could read a neighbour's memory out, write into it, or follow `/proc/<pid>/root` back across the mount view the jail just built, none of which the user namespace stops. **That cost is stated from the syscalls' own semantics and was not measured** — the jail holds the exposure set and four device files, so it has no such tool to try and the host's copies are outside it.

## The host's path namespace does not exist inside the jail

The jail is a private mount namespace with `pivot_root`, and what it contains is the exposure set plus the four device files every `serve` jail binds in — `/dev/null`, `/dev/zero`, `/dev/random` and `/dev/urandom` — each entry at its original absolute path. Everything else is absent rather than refused: `/etc`, `/proc`, the host's `/tmp` and the operator's home do not exist in there, and a path that is neither an exposure nor one of those four fails as "no such file or directory" rather than as a permission error. This is where Linux differs from the other two platforms, which confine by policy — a Windows AppContainer's DACLs, a macOS Seatbelt profile — and in those the host's paths are visible and refused. So a configuration file, a helper binary or a data path the server needs on Linux has to be exposed, and what would have been a permission error at startup is a missing file instead.
