# `tinio-pg` (P5): Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `tinio-pg`, the servable PostgreSQL backend: `Storage`/`VersionOps`/`Cleanup` over the shared ops engine and `tinio-store-pg`, the `[storage] type`/`[storage.pg]` configuration with a synthetic root, TLS, the read-only mode with a restricted role, the writable-ownership guard, doctor checks, the serialized `@pg` cucumber pass, and the CI job that carries the PostgreSQL service.

**Architecture:** `tinio-pg` is a backend crate like `tinio-fs`: it owns a `PgStore` (P3), an `Ops` value over that store and `tinio_blob::Store<PgBlocks>`, a `Hooks` implementation (two methods: a no-op bucket-delete action and a no-op part lock), its `Storage`/`VersionOps`/`Cleanup` implementations calling the engine, and its configuration, ownership and doctor surface.

**Tech Stack:** Rust (edition 2024), `async-trait`, `tinio-core`, `tinio-ops`, `tinio-store-pg`, `tinio-version`, `tokio`, `postgres:18-alpine` in CI.

**Spec:** `docs/superpowers/specs/2026-10-03-pg-design.md` — this plan implements its **§6 The backend surface** and **PG5–PG17, PG25**; the store's halves (§3–§5, PG18–PG24) are P3's.

**Depends on:** `2026-10-03-tinio-store-pg-p3.md` (the store and its schema) and `2026-10-03-tinio-ops-p4.md` (the engine and its `Hooks`).

## Global Constraints

- English only in repo artifacts; no hard-wrapped prose (`docs/compress.md`). Public items carry doc comments; `PgStorage`'s constructor carries an example (`ignore`d if it needs a database, with the reason in the doc). Gate: `RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps`.
- **Feature shape** (PG15/PG16): `tinio-pg`/`tinio-store-pg` carry `pg` (dependencies + code) and `pg-tests` (the DB-backed tests, non-default); `pg` joins `crates/tinio`'s `full` set, so the released binary can serve this backend while the default workspace leg stays database-free; `versioning` is orthogonal and gates only `tinio-pg`'s own version module and its `VersionOps` twin (`tinio-ops`/`tinio-store-pg` carry no `versioning` feature).
- Per-crate `Error` with `impl From<Error> for tinio_core::storage::Error`; the engine's `storage::Error` is `#[from]`-absorbed.
- **The dsn is `tinio_config`'s own `Secret`**; errors and logs render host/database from the **parsed** config's non-secret fields (PG5). Tests read the dsn from `TINIO_PG_DSN`; the only literal dsn lives in the crate's `docker-compose.yml`, which is why the credential grep is scoped to non-test sources.
- Read-only (PG6) is enforced three ways: the operation entry answers `AccessDenied`, the session is `default_transaction_read_only`, and the role has no DML grants. `Cleanup` (PG7) yields the same `ActionStream` shape `tinio-fs` yields.
- `[storage] type` is the selector the config contract already names; this plan updates `specs/001-s3-local-server/contracts/config.md` in the same commit that adds the key.
- Git: every commit step asks the operator first (`docs/git.md`); no AI/agent trailers.
- Gates: `cargo test -p tinio-pg --features pg,pg-tests` (PostgreSQL up), `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt`, the doc gate, `cargo hack check --package tinio-pg --each-feature`, the serialized `@pg` cucumber pass.

## Review Focus

1. **A read-only instance that writes.** Three layers, not one: the entry refusal (the contract's answer), the session's read-only default, and the role's missing DML grants — the last is the only one a helper that bypasses the entry cannot get around.
2. **A credential leaking.** The dsn is a `Secret`; connection errors name host and database only; `status`, `doctor`, logs and the tracing capture are all checked.
3. **A silently lost lock.** Two locks exist (the migration lock, the ownership lock) and both live on dedicated out-of-pool connections with liveness checks; losing the ownership lock terminates the process rather than letting a second writer start.
4. **A cleanup that deletes live data.** Dry run first, `LiveSet` reachability, and a chunk a live row names is never reclaimed; a listing never shows residue (P3's row-backed `scan`).
5. **A CI leg that needs a database.** DB-backed tests stay behind `pg-tests` and in the dedicated job; `cargo test --workspace` and every other leg stay database-free, and the `@pg` pass is serialized because all scenarios share one database.

## Notes for the executor

- The engine is where the S3 semantics live: `tinio-pg`'s operation bodies call it and map errors. A body that grows a branch PostgreSQL alone needs is a finding about the engine (or the contracts), not a local implementation.
- Keep the three read-only guards together: the entry refusal is the contract's answer, the session setting and the role's grants are the database's, and only all three make a missed guard loud.
- The CI job is the phase's proof: a `@pg` pass that only runs locally is the failure mode this task exists to prevent — and it must run **serialized**, because every scenario resets the one shared database.
