# The version slot-write contract (`VersionMeta::restore_slot`): Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the version restore expressible through the persistence contracts — one new `VersionMeta` method that commits, in a single transaction, the backwards slot move to a real identity, the object row it installs, the version row and index entry it consumes, and the cleared retained part list — implemented by every implementor, pinned by the shared contract conformance leg and the reference store's own suite, and adopted by `tinio-fs`, whose `commit_restore` then retires with **zero observable behaviour change**.

**Architecture:** One method on the standalone `VersionMeta` contract (`crates/tinio-core/src/meta/version.rs`), implemented by `RedbMetadata` (the reference; fs's `Rows` adapter and the ops/version doubles delegate to it), by `PgStore`, and by the two in-crate test doubles. The slot's monotonic guard (RC1) is untouched: the backwards move is the new call's own definition, never a parameter on `advance_slot`. `tinio-version`'s state engine is unchanged — the new call decides nothing; it is a store primitive beside `advance_slot` and `expire`.

**Tech Stack:** Rust (edition 2024), `async-trait`, `tinio-core` — Rust only; no new dependency of any kind.

**Spec:** `docs/superpowers/specs/2026-10-10-version-slot-write-contract.md` — this plan implements its **§2** (the capability), **§6** (the implementors), **§7** (the pins) and **§8** items 1-2 (the migration). Where the spec leaves a value open, the step says so and the task records the decision it made.

**Depends on:** the landed P4 tree (`crates/tinio-ops`' engine, the D37 close-out filing) and the landed stores (`crates/tinio-store-redb`, `crates/tinio-store-pg`). **Consumed by:** the ops version group's ninth body (a later wave, `ObjectOps::delete_object_version`) and `tinio-pg` (P5).

## Review Focus

1. **A backwards move that slips past the guard.** The new call must not weaken `advance_slot`: no `backwards` parameter, no shared helper that loosens the comparison, no edit to `crates/tinio-store-redb/src/meta/version.rs:263`'s condition. The store's own suite still refuses a `Some → Some` lower-sequence advance; only the new call lands a lower-sequence real move.
2. **A store that writes the row and forgets one of the five facts.** The parts clear, the index entry, the consumed row, the stamp, the marker bit: each is asserted separately, and a mutation of any one turns a leg red. A leg that asserts only the final identity is not the pin.
3. **A delegating adapter that drifts.** `tinio-fs`'s `Rows` (`crates/tinio-fs/src/version_adapter.rs:724`) and `tinio-ops`' `TestMeta` (`crates/tinio-ops/src/testutil.rs:691`) delegate every `VersionMeta` method to `RedbMetadata`; the new method is delegated like `advance_slot` is, and the delegation is proven by a test that would fail against a hand-rolled copy (the tests in those crates run over the delegated plane).
4. **A silent pg gap.** The `.sqlx` cache is a build input: a statement edit without `cargo xtask sqlx update` fails the database-free build, and a missing marker bit makes a restored marker read back as an object version. Either the pg step lands both or it files both, in the plan's own words.
5. **A behaviour change smuggled into the re-point.** Task 2's acceptance is that **no test text changes**: fs's version suite, the shared storage journey and the fs cucumber versioning pass run unmodified against the re-pointed body. A red suite means the new call does not yet express fs's commit exactly; the fix is the call, not the test.
