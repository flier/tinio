# The shared ops engine (`tinio-ops`, P4): Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Extract the S3 storage semantics shared by the backends into `tinio-ops` — 44 of the 45 `Storage` operations as bodies over the persistence contracts (`list_object_versions` stays backend-side), with a two-method `Hooks` seam and two declared policies — and re-point `tinio-fs` and `tinio-mem` onto it with zero observable behavior change.

**Architecture:** `tinio-ops` holds one module per operation group (`bucket`, `object`, `multipart`, `version`, `listing`, `staged`) plus `hooks`; each backend keeps its `Storage`/`VersionOps`/`Cleanup` implementations and its error enum, calls the operation bodies, and supplies its own `Hooks` and its two policy values. Operations return `storage::Error`.

**Tech Stack:** Rust (edition 2024), `async-trait`, `tinio-core` (contracts), `tinio-version` (the version state engine), `tinio-blob` (the block engine), `tokio`. **No feature of its own.**

**Spec:** `docs/superpowers/specs/2026-10-03-ops-engine-design.md` — this plan implements its **§1 Shape**, **§2 The operation bodies** (its fourteen obligations) and **§3 Acceptance and testing**.

**Depends on:** `2026-10-03-metadata-store-contract-p2-mem-and-conformance.md` (both backends on the persistence contracts). `tinio-store-pg` (P3) is a peer phase; `tinio-pg` (P5) is the engine's third consumer.

**Operator amendment 2026-10-09 (round 41, spec E16):** the engine's handles are **per group** — `versions`/`version_rows`/`blobs` are the *version plane*, a value of its own that only the version-touching bodies take. `mem` has no state engine, no block plane and no `tinio-blob` dependency, and its version-creating writes are single-transaction by the P2 ruling, so it builds no plane: its version group and its version-creating writes stay mem-local, and the bodies it does take (bucket, the version-free object bodies, the version-free multipart bodies, listing) are unchanged. Tasks 1–4 read every "`Ops<M, V, R, C, B, H>`" in their text as "the group receiver(s) the spec's §1 now sketches".

## Global Constraints

- English only in repo artifacts; no hard-wrapped prose (`docs/compress.md`). Public items carry doc comments; each operation group's module carries one runnable example. Gate: `RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps`.
- `tinio-ops` knows the four contracts only: no `redb`, no `tokio::fs`, no `postgres`, no backend crate in its **production** dependency list. Its test base is the in-memory reference implementation (`tinio-store-redb` as a **dev-dependency**: `RedbMetadata::in_memory()` + `RedbContent`) plus one in-memory `BlockStore` double.
- **`tinio-ops` carries no feature** (spec E1): the version group is always compiled because `tinio-version` always is. `Ops` has no `Option` and no `cfg` — the removed `tinio-blob` gate's rule applies.
- `Hooks` has exactly **two** methods (`before_bucket_delete`, `lock_part`); a third is a spec amendment with a named consumer, never a local addition. **Locks are the backend's**: the bucket-mutation lock is acquired by the trait impl around the engine call, and the part lock reaches the engine through `Hooks::lock_part`'s guard.
- The two policies are declared, never inferred: `metadata_failure: MetadataFailure::{Warn, Fail}` and `bucket_row: BucketRow::{Guaranteed, Lazy}`.
- Operations return `storage::Error`; backends absorb it with their existing `Storage(#[from] storage::Error)`.
- Acceptance is **zero observable change** for `tinio-fs` and `tinio-mem`: their suites, `assert_conformance`, both cucumber passes, the fs benchmarks **and a new listing benchmark** pass with adapter-only edits.
- Where fs and mem disagree today on an observable detail, the engine preserves each backend's behavior; the disagreement is filed, not silently unified.
- Git: every commit step asks the operator first (`docs/git.md`); no AI/agent trailers.
- Gates: `cargo test -p tinio-ops -p tinio-fs -p tinio-mem`, `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt`, the doc gate, `cargo hack check --package tinio-ops --each-feature`, both cucumber passes.

## Review Focus

1. **An ordering the audit found reversed.** A version-creating write moves the outgoing content into the block plane **before** the publish overwrites it (spec §2 obligation 1) — the reverse loses the previous version.
2. **A behavior only one backend has.** The cold read/list heal (`stat` + recompute + persist, obligation 7), rename's retained-part move (`move_`), the copy fast path (`ObjectContent::copy`), the folder-marker emptiness (`is_empty`), and the part lock's **commit-phase-only** width (`Hooks::lock_part`). Each has a named call and an existing test that must stay green.
3. **An operation decomposed into several contract calls where one was atomic.** `put_with_parts`, `move_`, the drains, the version row + index write.
4. **A listing that is correct but slow.** The enrichment is one `ObjectMeta::load` per page (never a point read per key), `scan` carries the prefix bound, and fs's `scan` delegates to the walk the scanner shares — the listing benchmark is the pin.
5. **An engine that grew a storage assumption or a third hook.** `rg` over its source is the check; the version group uses both handles (the `tinio-version` engine and `VersionMeta`), and none of the 44 bodies may need a new per-backend callback.

## Notes for the executor

- Migrate one group at a time and finish each group's acceptance before starting the next: the per-group green state is what keeps a 9 000-line extraction reviewable.
- Report a behavioral difference found mid-group before deciding it: preserving each backend's behavior is the rule, and "unifying" two backends is a behavior change this plan does not carry.
- The engine must not learn about a backend. If a group cannot be written against the contracts, that is a finding about the contracts (or about `Hooks`), not a reason to import a backend type — and a third hook needs the operator.
- The read-heal (spec obligation 7) is the one place where fs's `ensure_row` policy moved into shared code; if its tests (`composed_etag_*`, the cold-listing family) cannot be made green, stop and report — the fallback is a per-backend policy field, not a silently weaker heal.

## Carried into P4

Two contract questions were raised while closing the metadata-store P1 wave out and deliberately NOT decided there. Both were put to the operator on 2026-10-07, who carried them here rather than change the contract inside P1. Neither is a defect; both are improvements whose cost lands on contracts P2 is about to extend, so this is the wave that should decide them.

1. **A typed `put_version` conflict.** When a `put_version` meets an existing row naming a different version, the refusal projects as `storage::Error::Io` (via `io::Error::other`). That is HEAD's behaviour, not a P1 regression — P1 dropped only the `tracing::warn!` beside it, and that warn is restored (T169). Adding `storage::Error::VersionConflict` would let a caller distinguish the case by type instead of by string; it needs a decided HTTP mapping at the S3 layer (500 `InternalError` is the safe default, and the wire message must stay generic) plus a conformance leg, so it belongs in a wave already touching the error surface.

2. **`ObjectContent::publish` answering `Published`.** The eleven D23 calls have `publish` returning `()`, while `materialize` already builds a `PublishedBody { etag, size }` from the row it read. Returning that shape would let a staged object answer what it actually left behind without re-reading the row — a D23 correction candidate. It changes a contract both consumers implement, so it wants the wave that already re-treads those bodies.

Also carried, and a scope note rather than a decision: the operator ruled on 2026-10-07 that fs call-site migration stops at the scope P1's Task 9 Step 3 defines. Spec §6 item 6's stronger "no module outside the facades touches a table handle" therefore stays unmet by design (58 `_store_redb::` lines, 99 raw open sites) and is work for whichever wave takes it up.
