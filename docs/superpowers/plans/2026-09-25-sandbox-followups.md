## 1. Read the DACL through Win32 APIs — **LANDED 2026-09-25**

- **Problem**: the skip that makes a standing grant free was silently dead. `icacls` lists a well-known SID **by name** (`APPLICATION PACKAGE AUTHORITY\ALL APPLICATION PACKAGES`), so a check for the literal `S-1-15-2-1` never fired and the program directory was rewritten every run — 10–30 s of `SetNamedSecurityInfoW` full-tree propagation each time. The same rendering appears as the SDDL alias `AC`, so text matching has three spellings to guess.
- **Solution (landed)**: `has_ace` → `acl_names` → `any_ace_in` reads `GetNamedSecurityInfoW` + `GetAclInformation`/`GetAce` + **`EqualSid`**. `already_granted` → `acl_grants` is the same walk plus the mask/flag test. SID text goes through `ConvertStringSidToSidW` once in an RAII `OwnedSid`; a `PackageSid` passes its own `raw()`. Mask constants are measured against the tool: `M = FILE_GENERIC_READ|WRITE|EXECUTE|DELETE` (`0x0013_01BF`), `RX = GENERIC_READ|GENERIC_EXECUTE` (`0x0012_00A9`), containment not equality, `INHERIT_ONLY_ACE` fails every target, `(OI)(CI)` required for `Target::Directory` only. `MapGenericMask` deliberately not called (user mode cannot store generic bits in an ACE).
- **Two findings**: (a) the API **cannot read the `*.dll` batch path** (`123 ERROR_INVALID_NAME`) → `already_granted` returns a 3-state `GrantOutcome { AlreadyGranted, Missing, Unanswerable }`, and a wildcard in the final component is `Unanswerable` ⇒ `grant_to` writes; the sibling skip still cannot fire with a pattern API, but that is ~8–16 ms/run over a few DLLs and the old text search never matched there either. (b) the well-known-SID read went from always-false to correct — one wasted re-grant measured **224 ms / 4 201 objects**.
- **Sites**: `crates/tinio-sandbox-windows/src/acl.rs`.
- **Acceptance (met)**: `tinio-sandbox-windows` suites green (lib 37 + 14 suites, 0 failed); clippy clean; `mentions_sid`/`sid_spellings` kept as the test oracle.
- **Still open from this item**: a one-line "reads are API, writes are `icacls`" note in `specs/2026-09-18-sandbox-design.md`, and the `MapGenericMask` precedent in `docs/superpowers/icacls-vs-win32-acl-research.md`.

## 2. Write the DACL through Win32 APIs — **OPEN** *(same file as §1 and §3)*

- **Problem**: every grant and revoke spawns `icacls` (≈7–10 ms of process launch plus SID name resolution per operation). With §1's read fixed, the spawn is the remaining per-operation cost, and `icacls`'s text output is what §1 had to work around.
- **Solution**: `GetNamedSecurityInfoW` → merge with `SetEntriesInAclW` → `SetNamedSecurityInfoW`. Do it **in two stages**: first the directory/file `grant`/`revoke` (the non-pattern shapes), then decide the batch. The `*.dll` pattern **cannot** go through the API (§1's finding) — either enumerate the directory's DLLs and grant each (a measurable change from one call to N) or keep `icacls` for that shape; the batch is ~8–16 ms/run, so keeping the subprocess is defensible and must be justified with a measurement rather than assumed.
- **Traps**: only the security descriptor may `LocalFree` (never the ACL pointer); a `NULL`-DACL directory can return as an empty deny-all DACL after a grant→revoke round trip; the merge must preserve other ACEs, the owner, the SACL and the control bits exactly as `/grant:r` does (decision 15).
- **Sites**: `crates/tinio-sandbox-windows/src/acl.rs` internals only (public surface unchanged: `grant`, `revoke`, `has_ace`, `Grants`).
- **Acceptance**: the four operations behave identically to the `icacls` implementation on the existing suites; `tests/acl.rs`'s skip/standing assertions keep their meaning; per-operation timing reported against the `icacls` baseline.

## 3. One lock per path around read-merge-write — **OPEN** *(same file as §1 and §2)*

- **Problem**: grants and revokes are paired against the same directory, so two confined runs sharing a root can lose or resurrect each other's ACE (`/grant:r` and `/remove:g` are separate operations).
- **Solution**: a per-path advisory lock around the whole read-merge-write, following DSH: lock file under the system temp dir named `tinio-acl-locks\<sha256(lowercase path)[:16]>.lock`, opened without sharing delete and held with `LockFileEx` (exclusive) for the duration. Take it in `Grants::apply`/`apply_standing`/`revoke` rather than in `icacls`-level helpers, so the write path (§2) inherits it for free.
- **Cost**: one file create plus a lock per operation; the lock files themselves must be documented as intentionally left behind (DSH's choice) or reaped on a best-effort basis.
- **Sites**: `crates/tinio-sandbox-windows/src/acl.rs` (`grant`, `revoke`, `Grants::apply`, `Grants::apply_standing`) and the grant stage in `backend/mod.rs`.
- **Acceptance**: a concurrent test grants two SIDs to one directory from two threads and asserts both ACEs survive; `tinio-sandbox-windows` suites unchanged otherwise.

## 4. Report enforcement and denial as data, not only as log lines — **OPEN**

- **Problem**: a caller cannot tell "the sandbox broke (the command never ran)" from "the command was denied (it ran and was refused)"; today both reach the caller as an `Error`/log line.
- **Design (from the 2026-09-25 read-only pass, no code written)**: new `crates/tinio-sandbox-core/src/enforcement.rs` holding `Enforcement { Full, Partial, Unimplemented, NotReported }`, `RunnerFailureRule { allowed_exit_codes, fatal_signatures, informational_lines }`, `Diagnostics { enforcement, denial_signatures, runner_failure_rules }` with `NOT_REPORTED` and `attribute(platform, status, stderr)`, plus `Refused { Path, Capability, Unnamed }`, `Denial { platform, refused, evidence }` and `Attribution { Broken { platform, detail }, Denied(Denial) }`.
- **Solution, in four steps**: (1) land the core types and re-export them through the facade (`crates/tinio-sandbox/src/lib.rs`) — the CLI only depends on the facade, so without the re-export it cannot see them; (2) give `Backend` a defaulted `fn diagnostics(&self) -> Diagnostics { Diagnostics::NOT_REPORTED }` so all three platforms keep compiling; (3) add the two CLI `Error` variants (`SandboxBroken`, `SandboxDenied`) while **keeping the existing refusal sentences verbatim** (the `serve_sandbox_channels` legs and `cli_lifecycle.feature` assert their wording), and expose `sandbox::diagnostics()` / `sandbox::attribute(status, stderr)` as the only entry points; (4) map the Windows backend's refusals and hand the child's status+stderr to `attribute` at the supervise site.
- **Sites**: new `crates/tinio-sandbox-core/src/enforcement.rs` plus the facade re-export in `crates/tinio-sandbox/src/lib.rs`; `Backend` in `crates/tinio-sandbox-core/src/backend.rs`; `crates/tinio-cli/src/error.rs`, `crates/tinio-cli/src/sandbox/mod.rs`, `crates/tinio-cli/src/commands/start/run.rs`; the refusal mapping in `crates/tinio-sandbox-windows/src/backend/mod.rs`.
- **Wiring caveat**: "which path was refused" lives in `crates/tinio-cli/src/commands/start/run.rs`, where `?` on `create_dir_all`/`FsStorage::new`/`bind` currently turns an io error into a path-less `Error::Io`; the classifier has to be called there, gated on `adopted.is_some()`.
- **Unverified**: the real Windows denial text, the io kind of an AppContainer refusal, and whether the launcher captures (rather than merely inherits) the child's stderr.
- **Acceptance**: three platforms can express it, and **no platform is a stub for this item to hang on any more** — `crates/tinio-cli/src/sandbox/mod.rs`'s `BACKEND_IS_STUB` is `false` on Linux, macOS and Windows (`contracts/cli.md`'s `--sandbox` bullet owns that landed fact), so each platform must name its own strength rather than an `Unimplemented` stub's "unsupported"; a denial names the channel or path; fail-closed strength unchanged; nothing may run unconfined.

## 5. Pipe-pool extremes — **PARTLY LANDED; one test gap**

- **Problem**: (a) concurrent dials beyond the pool return `ERROR_PIPE_BUSY`, which used to be indistinguishable from a dead channel; (b) a client that never closes holds an instance under the drain; (c) whether `INSTANCES` should be configurable.
- **Solution (landed)**: (a) bounded retry (`BUSY_RETRIES = 5`, `BUSY_BACKOFF = 1 ms`, ~31 ms budget) and a spent busy dial now returns **`Error::Busy`** instead of a raw `io::Error`, so `stop` can tell "there is a server and it is full" from "nothing there" while `status` keeps reporting `running: false` with the state file intact (`contracts/cli.md:58`); (b) `wait_for_peer_close` is bounded by **`DRAIN_LIMIT = 250 ms`** and a forced reclaim emits `tracing::warn!(%identity, limit, waited, …)` — justified by measurement, not taste: across 201 sequential dials the drain ends in **80–181 µs** (p50 97 µs, p99 177 µs), i.e. the bound sits ~1 400× above the mean, and nothing is discarded at it (tokio's pipe write is `WriteFile` + `FlushFileBuffers`, which blocks until the client consumes, and `keep_alive(false)` means nothing follows the response); (c) `INSTANCES` **stays a constant** — configurability would create a second source of truth across the launcher handoff plus a matching `Plane::adopt` floor, for zero measured benefit (0 retries over 200 sequential dials).
- **Remaining gap (measured, not suspected)**: neither §5 scenario can be turned into a passing test in-tree, because `#[tokio::test]` runs **current-thread** here and (i) `ClientOptions::open` on an instance that has not reached `ConnectNamedPipe` **blocks the only thread** (spawning the dial does not help — the task inherits the thread), while (ii) a held `SendRequest` does **not** keep a pipe open (measured: the server released the instance ~100 µs after the exchange, because the handle lives in hyper's connection future).
- **Solution for the gap**: add `rt-multi-thread` to `tinio-api`'s dev-dependencies and write the two tests as `#[tokio::test(flavor = "multi_thread", worker_threads = 2)]`; the implementation needs no change for that. Keep the `Error::Busy` mapping pinned by the `error.rs` test that already exists.
- **Sites**: `crates/tinio-api/**` (`client.rs`, `error.rs`, `transport.rs`, `Cargo.toml`).
- **Acceptance**: the two scenarios become passing tests; `tinio-api` suites green; one real confined run (`status` ×2 then `stop`) with no forced-reclaim warning in the log.

## 6. Linux seccomp coverage review — **PARTLY LANDED**

- **Problem**: the filter blocked outbound `connect`/`sendto`/`sendmsg`/`sendmmsg` only; Codex blocks `io_uring_*` unconditionally because a ring can carry traffic without `socket()`.
- **Solution (landed)**: `io_uring_setup`/`enter`/`register` (425/426/427) are denied; `filter_program` is 19 instructions. The bypass was **measured**: before the change `io_uring_setup` returned a descriptor inside the confinement and an `IORING_OP_SENDMSG` SQE delivered a datagram while `sendto` was `EPERM`. `enter`/`register` are denied separately because tinio confines **in place**, so a ring opened before the filter lands would stay usable through `enter`.
- **Solution for what remains**: (a) `ptrace`/`process_vm_readv`/`process_vm_writev` — deny all three (Codex's companion to the user namespace: inject into an unfiltered same-uid process, or follow `/proc/<pid>/root` links across the mount view); the cost is tooling-visible (gdb/perf/strace), so record it and test it; (b) the **x32 ABI** gap — add one rule to the same program: `JSET 0x4000_0000` on the syscall number ⇒ `RET_ERRNO|EPERM` (the current program only compares `nr`, so this is the one addition that fits its shape); (c) keep allowed, deliberately: `recvfrom`/`recvmsg`/`recvmmsg`, `socketpair` (receiving cannot exfiltrate; denying breaks socketpair-based tooling), `sendfile`/`splice` (they copy into an already-connected fd, which no syscall filter can unmake); (d) `connect(AF_UNIX)` stays denied (the filter cannot see the family) and `socketpair` keeps local IPC working.
- **Documentation owed**: `docs/sandbox.md:17` and `plans/2026-09-18-sandbox-p1-linux.md:5247` list the deny set without `io_uring` — still true, no longer complete (see §18).
- **Sites**: `crates/tinio-sandbox-linux/src/seccomp.rs`.
- **Acceptance**: each item is either a rule with its reason in a comment or a documented "not needed"; a test or a measured before/after per addition; the "seccomp outbound denial ≠ netns isolation — loopback and inherited sockets still work" distinction recorded.

## 7. End-to-end coverage of the Linux overlay branch — **OPEN**

- **Problem**: after the remount fix re-asserts the source mount's `nosuid`/`nodev`/`noexec`, every leg takes the remount arm on this kernel, so the overlay arm is no longer exercised end to end (`read-only-arm: remount`, measured).
- **Solution**: reach `EPERM` through a **locked per-mount flag the request does not name** — `nosymfollow` on this kernel (the host's `/run/credentials/*` mounts carry it; `rustix::mount::MountFlags::NOSYMFOLLOW` exists). Constructing that state needs a **nested** user namespace: a wrapper creates the `nosymfollow` tmpfs in userns A, then execs `sandbox-child` so its own `unshare(CLONE_NEWUSER)` becomes B. Put that test behind an explicit opt-in variable (e.g. `TINIO_SANDBOX_TEST_NOSYMFOLLOW=1`) rather than the default gate, because it needs `mount -o nosymfollow` support and would otherwise redden hosts without it.
- **Sites**: `crates/tinio-sandbox-linux/tests/jail.rs` and the "one of the two" assertion.
- **Acceptance**: the arm stays; the gap is documented where the test asserts "one of the two"; the nested-userns test passes under the opt-in variable on this host.

## 8. Windows network isolation — **VERIFIED 2026-09-25, no work left**

- **Problem**: Linux confines outbound traffic with seccomp, while the Windows side had never been checked. An AppContainer *should* be unable to reach the network without a network capability — but "should" is not a measurement.
- **Solution (verified; nothing to implement)**: the capability vocabulary is closed and all three variants are network capabilities (`backend/capability.rs:37-45`; `S-1-15-3-1/2/3`), `Options` derives `Default` over an empty `Vec` (`backend/mod.rs:85-88`), the only operator channel is `TINIO_SANDBOX_CAPABILITIES` (`crates/tinio-cli/src/sandbox/windows.rs:129`; no config-file key exists), and an empty set reaches the kernel as a **null pointer with `CapabilityCount: 0`** (`process.rs:487-512`). WFP enforces the consequence against the token's capability SIDs, so tinio writes no filter, firewall rule or network namespace of its own.
- **Sites**: the threat model in `specs/2026-09-18-sandbox-design.md` §7, where the measurement is recorded.
- **Acceptance (met)**: unconfined the host reaches `1.1.1.1:53`; under `Options::default()` the child's outbound attempt fails with **`WSAEACCES` (10013)**, while the `internetClient` positive control succeeds on the same address with the same binary. Also recorded there: a confined child reaching the **unconfined launcher's** loopback listener is **silently dropped** (`TimedOut`, no raw code) with and without `internetClient` — AppContainer's loopback policy, not the capability filters.
- **Still unmeasured**: a LAN host reaching the inherited listener; non-53 external ports; the container's own loopback.

## 10. Standing-grant hardening — **OPEN**

- **Problem**: `package_name` is a pure function of the canonical root, so any local user can compute the SID and create the same AppContainer profile; the grant is also **permanent** for every root ever served (standing, never revoked), and the program directory's `ALL APPLICATION PACKAGES` grant is readable by *any* AppContainer app on the machine.
- **Solution, in three layers** (any subset is useful): (a) **threat-model text** in `specs/2026-09-18-sandbox-design.md` stating both exposures plainly, so a reader does not discover them from the code; (b) **an optional persisted salt** mixed into `package_name`'s derivation (a random value kept in the state directory, one per user/machine) — this is the only thing in this plan that would justify a state file, and it invalidates existing grants once; (c) **an ACE ledger** recording which roots have been granted, so an operator can audit and revoke (Codex's `deny_read_state` structure is the reference), with the concurrency rule that a SID belonging to a run started after the ledger was read must not be removed.
- **Sites**: `crates/tinio-sandbox-windows/src/sid.rs` (salt), the design spec (threat model), and a new ledger module if (c) is taken.
- **Acceptance**: (a) done as text; (b) and (c) only if the exposure is judged worth closing, each with its migration cost stated.

## 13. Test and script hygiene: server processes leak — **OPEN**

## Verified 2026-09-25: the standing skip works end to end

Same root, second confined run: **both** the program directory and the served root report `written=false`, the ACL phase measures **0 ms**, and readiness falls from **11287.9 ms to 65.2 ms** (~170×). Cross-checked without trusting the program's own `written` field — an NTFS `ChangeTime` probe (validated first: a descriptor write changes it, a read does not) shows the program directory and the root unchanged after the second run, and the ACE counts hold at 25/11. Reproduced on three binary revisions.

The first run's 11.19 s is **99.1%** one `SetNamedSecurityInfoW` on the program directory, whose subtree is 82,184 objects (76,034 files + 6,150 directories) — **0.136 ms/object**, the same order as the 0.16 ms/object the design notes carry. Because `target\debug` had never carried `S-1-15-2-1` on this host (its 13 residue ACEs are all per-root package SIDs), the first run must write it — the expectation that even the first run would skip is **disproved**. Afterwards a new root never rewrites the program directory (`written=false`) and costs 8–11 ms for its own grant.

Two DACL-touching operations still happen every run and are **not** on an exposure path, so neither counts as a grant: the launcher's own `state` file, and `CreateAppContainerProfile` (see §19).

### Windows true in-process apply: **no**

- `CreateRestrictedToken` builds a **new** token from an existing one, and the documented consumption is `CreateProcessAsUser` or `ImpersonateLoggedOnUser` — nothing applies it to the calling process's own primary token ([MS Learn](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken); documentation, **not measured here**).
- `SetTokenInformation` replaces information on a token, and token-*type* information is set only at creation; `TokenRestrictedSids` and `TokenIntegrityLevel` exist as classes ([TOKEN_INFORMATION_CLASS](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ne-winnt-token_information_class)) — "the class exists" is not "a running process is confined". **No file under `crates/**` names `SetTokenInformation`, `NtSetInformationToken`, `SetProcessContainer`, `SetProcessMitigationPolicy`, `CreateRestrictedToken` or `sandbox_init`** (`rg` over `crates/`, 0 hits).
- **Closest thing**: self-lowering to Low IL through `SetTokenInformation(TokenIntegrityLevel)` — in-process, and the one half of DSH's mechanism that is even expressible on a running process. It is a **write** wall; reads of medium-IL objects stay allowed, which is exactly why DSH's read isolation is documented `partial` (prior art §5, §9). Whether the call succeeds on the caller's **own primary token**, and what it does to a server that already opened its listener, state dir and storage, is **unmeasured** (open questions).
- `SetProcessMitigationPolicy` is in-process by definition ("for the calling process") and is **not access control** — DEP, ASLR, dynamic-code, child-process, font and image-load hardening ([MS Learn](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessmitigationpolicy)). Not a substitute for a confinement.
- Job objects: [`AssignProcessToJobObject`](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject) does accept an already-running process, but the job's token-**filtering** security limitations require a suspended creation (`JOB_OBJECT_SECURITY_ONLY_TOKEN`), so the security half is creation-time too; the rest is limits and lifetime, which `windows/src/job.rs` already uses for that and nothing more.
- AppContainer has no attach step in this tree at all: the identity rides `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` into `CreateProcessW` (`windows/src/process.rs:548-557`), which is why `Backend::confine` can only confine a process it creates (`windows/src/lib.rs:4-7`).
- **Answer: no.** Closest = self-lowering to Low IL (in-process, write-only); second closest = a restricted token at creation (Codex/DSH).

### The degraded Windows route, and exactly what it gives up

- **What AppContainer buys that the route surrenders**: read isolation, measured in-tree — a directory carrying `Users` and no package-SID ACE is refused `permission denied` to the confined child (`windows/tests/common/tree.rs:125-142`, `windows/tests/confine.rs:68`; design:413, "a non-granted tree is denied despite carrying `Users` and `Authenticated Users` ACEs"). `WRITE_RESTRICTED` consults its restricting SIDs **only when evaluating write access** (MS Learn), and a token that keeps the caller's own SIDs still reads every tree the caller can read — DSH's documented `partial` (prior art §5).
- **Do not copy the write-only shape.** Prior art §9 says it plainly: DSH confines writes only, and copying its core mechanism wholesale is a security regression against AppContainer's default-deny read. A degraded mode is defensible only if the run **says** which mode it is — §4's "enforcement as data" argument, applied to strength.
- **Saved**: the profile lifecycle (`windows/src/sid.rs:280`, `:399-419`) and with it §19's per-run `%LOCALAPPDATA%\Packages` directory; `package_name`'s derivation and residue takeover (`windows/src/sid.rs:136-153`); the program directory's standing `ALL APPLICATION PACKAGES` RX (`windows/src/sid.rs:58-81`) and the "readable by any AppContainer app on the machine" price that constant states.
- **Not saved, contrary to the obvious reading**: the per-root ACL write. DSH's restricting list carries a per-workspace capability SID, and it must hold an ACE (plus a deny and a Low integrity label) or writes fail the second access check (prior art §5). The cost moves from "profile + per-root ACE" to "per-root ACE + label"; what the operator buys back is the **read** half, not the ACL half.
- **The one shape that does save the ACL half**: Codex's unelevated mode — `CreateRestrictedToken(WRITE_RESTRICTED)` with the caller's own token, no identity and no ACL writes (prior art §2) — but it buys that by making the tree unwritable, so a normal read-write tinio run cannot use it at all. It is the read-**only** degraded mode, not the general one.

### Linux: several directories, each in its own process — **no helper needed**

- **What in-place does, and from where.** `Backend::confine` → `enter` (`linux/src/lib.rs:113-124`, `linux/src/enter.rs:75-98`): validate + plan → jail root in `$TMPDIR` → `unshare(CLONE_NEWUSER)` + the three maps → `unshare(CLONE_NEWNS)` → `make / private` → the mounts → `pivot_root` + `umount2(MNT_DETACH)` → cap drop → seccomp. **Irreversible for the calling process** and every failure fatal (`linux/src/enter.rs:63-66`). Reached as step i: `crates/tinio-cli/src/commands/start/run.rs:276` → `sandbox::confine` (`crates/tinio-cli/src/sandbox/mod.rs:484-491`) → `crates/tinio-cli/src/sandbox/linux.rs:62-129`. Linux answers `Confinement::InPlace` and launches nothing (`linux/src/lib.rs:113-124`).
- **Per-process by construction**: `unshare` applies to *this* process, so each caller gets its own user + mount namespace, its own jail root (`linux/src/jail.rs:27-52`, pid-free, keyed on the served root), its own overlay pair (`linux/src/plan.rs:120-134`) and its own seccomp filter (`linux/src/seccomp.rs:353-357`, per-thread, single-thread precondition). Decision 10 states the concurrency rule — two processes mounting one host directory each do so inside their own mount namespace (design:139).
- **`src/bin/sandbox-child.rs` is test-only.** A plain `fn main` that confines itself, then prints `key: value` probes (`linux/src/bin/sandbox-child.rs:1-27`); its only spawner is `crates/tinio-sandbox-linux/tests/jail.rs:130` (`CARGO_BIN_EXE_sandbox-child`), while `crates/tinio-server/tests/sandbox_e2e.rs:216` mentions it in a doc comment and spawns the `tinio` binary. It exists because libtest runs a test on a worker thread and `unshare(CLONE_NEWUSER)` refuses in a multi-threaded process (`linux/src/bin/sandbox-child.rs:4-7`) — a **test** constraint, not a production one.
- **Answer: no.** A helper is not needed; it is sufficient to call the existing in-place mechanism inside each already-separate server process. The per-process requirement that makes it work is exactly one: **confine before any thread exists** — `unshare(CLONE_NEWUSER)` returns `EINVAL` in a multi-threaded process, and the filter applies per-thread without `TSYNC` (decision 26, design:169; design:473, `:490`; `linux/src/mechanism.rs:193-205`; `linux/src/seccomp.rs:353-357`). Every server process already meets it inside one `fn main`: `crates/tinio-cli/src/run.rs:77-80`, with the runtime built last (`run.rs:184-201`), and the order recorded at `crates/tinio-cli/src/commands/start/run.rs:54-63`.
- **The shape that *would* need a helper, and why it is not this one**: a single supervisor that already built its runtime and then wanted N confined children in place. That process is multi-threaded (`crates/tinio-cli/src/run.rs:197-201`), so its own `unshare` is the `EINVAL` case and its namespace would in any case be shared by every child; confining from there needs a fresh single-threaded re-exec — a helper. N independent servers, each with its own `fn main`, are not that shape.
- **The one place the split is necessary rather than merely sufficient**: `plan` refuses more than one read-only exposure under `Mechanism::UserNamespace`, because one jail has one overlay pair and an overlay upper binds a single lower (`linux/src/plan.rs:172-186`; design §4, design:370). One directory per process is at most one read-only exposure per jail, so the refusal never fires — and a single process exposing N read-only directories is refused today. Under `Mechanism::Root` two are accepted, on the premise that the remount is never refused (`linux/src/plan.rs:332-334`).
- **Also worth recording**: N exposures in **one** process are supported for read-write (`linux/src/plan.rs:188-203` loops the whole set), so "N directories" has two shapes — one process with N exposures, or N processes with one each. The read-only case is the one that wants the second.

### Parameterisation: structural on Linux and Windows, textual only on macOS

- macOS is the only platform whose grant is **text a policy engine parses** — `(param "E0")` in the SBPL plus the value beside it as `-D NAME=VALUE` (`macos/src/profile.rs:1-16`, `:220-263`; `macos/src/launch.rs:400-490`) — and decision 24 makes that a security property: a value is data (design:167).
- Linux needs no equivalent, because nothing parses a path: `mirror_under` composes the target (`linux/src/jail.rs:83-120`), `plan` records source/target/kind (`linux/src/plan.rs:188-203`), and `apply_mount` hands them to `mount` / `mount_bind_recursive` / `mount_remount` (`linux/src/enter.rs:335-341`). No policy language exists, so the channel injection would use does not exist.
- Windows needs no equivalent for the same reason: an exposure becomes an **ACE** whose SID and mask are structured values and whose path is an API argument (`windows/src/acl.rs`; design §6, design:401-407). The `icacls` subprocess is the one text-shaped step in that path (§1/§2), and §2's planned direct-API write removes it.
- **Consequence**: the macOS in-process route's measured cost is not parameterisation — `sandbox_init_with_parameters` takes the same `-D` pairs (measured) — but its being one-shot and its refusal of `fork`/`exec` after the apply, and neither of those transfers to Linux or Windows. A cross-platform "user picks the mechanism" option therefore adds no parameterisation concept to Linux or Windows. The rule that already carries that duty on macOS is decision 24's "path validation, not the profile text, is what bounds the exposure set" (design:167).

### Open questions / not established

- Whether `SetTokenInformation(TokenIntegrityLevel)` succeeds on a process's **own primary token** and tightens the access checks of a server that is already running. Unmeasured: the call's documented existence is not a measurement of the effect, and no experiment was run for this survey.
- Whether an unprivileged user can mint a token carrying an arbitrary `S-1-4-…` capability SID. This decides whether the degraded route **narrows** §10's "any local user can compute the SID" exposure or merely changes its shape.
- Whether design §7's Windows network default-deny (design:430, `:433`) is a property of the **AppContainer SID** or of capability SIDs as such. Every in-tree network measurement is an AppContainer measurement; a non-AppContainer token is unmeasured.
- Whether the macOS in-process route keeps parameterisation. **Answered 2026-09-26**: it does — `sandbox_init_with_parameters` took the real rendered profile text and the real `-D` pairs at `rc=0`, and the record is the design's evidence-table row rather than an out-of-tree note. The retired wording was: `sandbox_init` takes a profile string; whether `sandbox_init_with_parameters` replaces `-D` was **not verified** here. The tree records only that `sandbox_init` FFI is authorized (design:554), and the operator's in-process measurement lives outside it.
- Whether that route can be applied **in place** to an already-serving process at all — before the runtime, in one `fn main`, the way Linux does it. **Answered 2026-09-26**: yes, and it does not care about threads — a thread created before the apply does not block it, every tokio runtime configuration builds and `block_on` returns in under 2 ms, and only `Command::output()` is refused — but the apply is one-shot and forbids `fork`/`exec` unless the profile grants `process-fork`, so a launcher that must still spawn its child cannot use it (design evidence table).
- The degraded route's numbers: what the profile lifecycle and the `package_name` derivation actually cost per run, measured against the ACL phase the tree already times (`windows/src/backend/grant.rs`, `report_grant_phase`). Not measured for a token route.
- Whether a degraded route keeps the control-channel handoff. Today it exists because the child's identity is the package SID and it cannot create a pipe (`crates/tinio-cli/src/sandbox/windows.rs:117-148`); whether a restricted-token child could bind its own is unmeasured, and Codex paid for that with `TokenDefaultDacl` (prior art §2).
- The channel a cross-platform choice should use. Linux already reads `TINIO_SANDBOX_MODEL` (`linux/src/mechanism.rs:82-118`) and Windows already reads `TINIO_SANDBOX_CAPABILITIES` (`crates/tinio-cli/src/sandbox/windows.rs:153-158`); whether one name generalises both, or the choice becomes a flag/config key, is a schema decision nobody has made.
- Whether the exposure cap survives an in-process macOS route. `MAX_EXPOSURES` bounds the **compiled profile** (design:395), so it should persist; not re-checked against `sandbox_init`.

### The dual-mode items this survey implies — **OPEN** *(Windows degraded mode; Linux multi-root)*

- **Problem**: no platform lets the user choose a weaker mechanism; Windows' only mode is AppContainer, so the accepted degraded option is not expressible (`Options` carries `capabilities`, `program`, `args` only — `windows/src/backend/mod.rs:85-101`); and the Linux multi-root question has no written answer.
- **Solution**: (a) Windows — add a mode to `Options` plus a CLI channel beside `TINIO_SANDBOX_CAPABILITIES`, selecting restricted-token confinement. Supervision, payload, listener/control handoff and the job are unchanged; only the creation call differs — `windows/src/process.rs:487-586` builds `SECURITY_CAPABILITIES` + `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` into a `STARTUPINFOEX`, and a token route swaps that attribute for `CreateProcessAsUserW` (`windows/src/process.rs:647-663`). (b) Linux — write "N roots = N processes, each confining itself; no helper" into the design, and keep `sandbox-child` test-only.
- **Sites**: `crates/tinio-sandbox-windows/src/backend/mod.rs`, a restriction module beside `windows/src/process.rs`, `crates/tinio-cli/src/sandbox/windows.rs`; for (b) `specs/2026-09-18-sandbox-design.md` §2/§4 and this plan.
- **Acceptance**: the selected mode is named in the run's own reporting, and a degraded run never claims read isolation (the §4 vocabulary applied to strength); on Linux, two servers on two roots under `--sandbox --read-only` confine themselves one process apiece, with no helper binary in the process tree or on disk. Take (a) only after the open questions above are answered — the read-isolation loss is the whole price.
