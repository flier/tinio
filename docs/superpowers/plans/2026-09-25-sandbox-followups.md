## 1. Read the DACL through Win32 APIs — **LANDED 2026-09-25**

- **Problem**: the skip that makes a standing grant free was silently dead. `icacls` lists a well-known SID **by name** (`APPLICATION PACKAGE AUTHORITY\ALL APPLICATION PACKAGES`), so a check for the literal `S-1-15-2-1` never fired and the program directory was rewritten every run — 10–30 s of `SetNamedSecurityInfoW` full-tree propagation each time. The same rendering appears as the SDDL alias `AC`, so text matching has three spellings to guess.
- **Solution (landed)**: `has_ace` → `acl_names` → `any_ace_in` reads `GetNamedSecurityInfoW` + `GetAclInformation`/`GetAce` + **`EqualSid`**. `already_granted` → `acl_grants` is the same walk plus the mask/flag test. SID text goes through `ConvertStringSidToSidW` once in an RAII `OwnedSid`; a `PackageSid` passes its own `raw()`. Mask constants are measured against the tool: `M = FILE_GENERIC_READ|WRITE|EXECUTE|DELETE` (`0x0013_01BF`), `RX = GENERIC_READ|GENERIC_EXECUTE` (`0x0012_00A9`), containment not equality, `INHERIT_ONLY_ACE` fails every target, `(OI)(CI)` required for `Target::Directory` only. `MapGenericMask` deliberately not called (user mode cannot store generic bits in an ACE).
- **Two findings**: (a) the API **cannot read the `*.dll` batch path** (`123 ERROR_INVALID_NAME`) → `already_granted` returns a 3-state `GrantOutcome { AlreadyGranted, Missing, Unanswerable }`, and a wildcard in the final component is `Unanswerable` ⇒ `grant_to` writes; the sibling skip still cannot fire with a pattern API, but that is ~8–16 ms/run over a few DLLs and the old text search never matched there either. (b) the well-known-SID read went from always-false to correct — one wasted re-grant measured **224 ms / 4 201 objects**.
- **Sites**: `crates/tinio-sandbox-windows/src/acl.rs`.
- **Acceptance (met)**: `tinio-sandbox-windows` suites green (lib 37 + 14 suites, 0 failed); clippy clean; `mentions_sid`/`sid_spellings` kept as the test oracle.
- **Still open from this item**: a one-line "reads are API, writes are `icacls`" note in `specs/2026-09-18-sandbox-design.md`, and the `MapGenericMask` precedent in `docs/superpowers/icacls-vs-win32-acl-research.md`.

## 2. Write the DACL through Win32 APIs — **LANDED 2026-09-27** *(same file as §1 and §3)*

- **Problem**: every grant and revoke spawns `icacls` (≈7–10 ms of process launch plus SID name resolution per operation). With §1's read fixed, the spawn is the remaining per-operation cost, and `icacls`'s text output is what §1 had to work around.
- **Solution**: `GetNamedSecurityInfoW` → merge with `SetEntriesInAclW` → `SetNamedSecurityInfoW`. Do it **in two stages**: first the directory/file `grant`/`revoke` (the non-pattern shapes), then decide the batch. The `*.dll` pattern **cannot** go through the API (§1's finding) — either enumerate the directory's DLLs and grant each (a measurable change from one call to N) or keep `icacls` for that shape; the batch is ~8–16 ms/run, so keeping the subprocess is defensible and must be justified with a measurement rather than assumed.
- **Traps**: only the security descriptor may `LocalFree` (never the ACL pointer); a `NULL`-DACL directory can return as an empty deny-all DACL after a grant→revoke round trip; the merge must preserve other ACEs, the owner, the SACL and the control bits exactly as `/grant:r` does (decision 15).
- **Sites**: `crates/tinio-sandbox-windows/src/acl.rs` internals only (public surface unchanged: `grant`, `revoke`, `has_ace`, `Grants`).
- **Acceptance**: the four operations behave identically to the `icacls` implementation on the existing suites; `tests/acl.rs`'s skip/standing assertions keep their meaning; per-operation timing reported against the `icacls` baseline.
- **Landed 2026-09-27, and two of this item's own clauses were settled the other way.** The write is the Win32 API and the subprocess is gone from it: every grant opens the spelled path with `CreateFileW` (`FILE_FLAG_OPEN_REPARSE_POINT | FILE_FLAG_BACKUP_SEMANTICS`), refuses a reparse point or an object of the wrong kind on that handle, then reads **and** writes the DACL on the same handle — `GetSecurityInfo` → `SetEntriesInAclW` + `SetSecurityInfo` — which is a stronger shape than this item asked for: it closes the check-then-use the tool route left open, where a writer who replaced an exposed directory with a junction inside the grant window had the ACE written somewhere the whitelist's check never saw. **`revoke` still shells out** (`icacls <dir> /remove:g` is the operator's own spelling and the API keeps it), and `icacls` remains the suites' independent oracle. **The `*.dll` batch is gone rather than kept**: the grant is per enumerated file, each opened by its own handle, so the pattern survives only as the enumeration's spelling (`backend::SiblingScan::pattern`) — what decided that is not the one-call-vs-N measurement this item asked for but the linked `x.dll` the batch granted through its target (the sibling enumeration is by name now and a reparse-point sibling is refused). **The per-operation timing half of the Acceptance was not reported**, so the item is met in its behaviour half only; the grant phase's own log line carries `elapsed_ms` and the phase's step name is `grant the ACLs` (a failed read's is `read the DACL`), where the tool-era names were `icacls /grant:r` and the read's own.

## 3. One lock per path around read-merge-write — **LANDED 2026-09-28** *(same file as §1 and §2)*

- **Problem**: grants and revokes are paired against the same directory, so two confined runs sharing a root can lose or resurrect each other's ACE (`/grant:r` and `/remove:g` are separate operations — and **since the standing ruling the launcher issues no revoke at all** (decision 15), so what a shared root can still lose or resurrect today is another run's *grant*; the read-merge-write window this item exists for is unchanged by that).
- **Solution**: a per-path advisory lock around the whole read-merge-write, following DSH: lock file under the system temp dir named `tinio-acl-locks\<sha256(lowercase path)[:16]>.lock`, opened without sharing delete and held with `LockFileEx` (exclusive) for the duration. Take it in `Grants::apply`/`apply_standing`/`revoke` rather than in `icacls`-level helpers, so the write path (§2) inherits it for free.
- **Cost**: one file create plus a lock per operation; the lock files themselves must be documented as intentionally left behind (DSH's choice) or reaped on a best-effort basis.
- **Sites**: `crates/tinio-sandbox-windows/src/acl.rs` (`grant`, `revoke`, `Grants::apply`, `Grants::apply_standing`) and the grant stage in `backend/mod.rs`.
- **Two shape constraints the profile lock's landing puts on this item, before it is planned** (the Windows crate's input, 2026-09-27; `ProfileLock`'s own doc in `crates/tinio-sandbox-windows/src/sid.rs` states the naming rule and nothing in it is profile-specific, so the type can be lifted and its key string changed). **First, reuse `package_name`'s normalisation for the key**: that function is already a 16-hex digest of the *normalised* root — the verbatim prefix stripped, the components collected, the path text and the UTF-16 units folded and hashed together — so a per-path lock with a scheme of its own takes two locks for two spellings of one directory and the guarantee becomes per-spelling; the lock file name above should be built from that same normalised path rather than the raw one. **Second, bound or report the wait**: this item's critical section is one `icacls` read-merge-write, which is seconds on a large tree (**the design's** §6 — `docs/superpowers/specs/2026-09-18-sandbox-design.md`'s inheritance-and-cost paragraph, which owns the numbers — not this plan's own §6, which is Linux seccomp coverage and carries none), and it is worth knowing that the profile lock's own bound is *not* the milliseconds a `CreateProcessW` takes either — it is acquired in `prepare_launch` and released only after `process::launch`, so the ACL grant phase sits **inside** it, and `ProfileLock`'s doc says exactly that ("its bound is that window: the ACL phase, seconds on a large tree"). A per-path lock's holder can therefore be waited on for as long as a whole ACL phase, so the wait has to be bounded or reported rather than silent — which is also why a bare `INFINITE` is defensible for the profile lock and is not a precedent to copy here without saying what a long wait means. The abandonment rule transfers as-is and is the reason a kernel lock is the right primitive: a crashed holder's lock is released by the kernel and its waiter's warning is where an operator learns of it, so a killed run cannot wedge a directory for everyone else.
- **Acceptance**: a concurrent test grants two SIDs to one directory from two threads and asserts both ACEs survive; `tinio-sandbox-windows` suites unchanged otherwise.
- **Landed 2026-09-28**: `acl::AclLock` holds one lock per **normalised path** across the whole read-merge-write — a lock file under the caller's temp directory (`tinio-acl-locks\<16 hex>.lock`, the digest of the same unsalted normalisation `package_name` derives under, so two spellings of one directory take one lock), opened without sharing delete and held with `LockFileEx` across `grant_to`'s read, merge and write and across `revoke`; taken in `grant_to`, so `grant`, `Grants::apply`, `apply_standing` and `apply_siblings` inherit it and `backend/mod.rs` needed no change. **The race is measured, not argued**: with the lock removed from `grant_to`, `two_grants_to_one_path_from_two_threads_keep_both_aces` failed on three consecutive runs (one package-SID entry where two grants had been made); with it, a peer *process* holding the byte range made an acquire wait 18 770 ms, an uncontended acquire took it on its first attempt, and a holder killed with `TerminateProcess` left the range takeable 0 ms later. **The wait is reported, not bounded** — a holder can be inside a whole ACL phase — with one `warn!` at a 1 s threshold, and the lock files are left behind on purpose (the withheld share-delete is what makes unlinking them unsound). The design's §6 paragraph owns the rule; the crate's manifest gained the `Win32_System_IO` feature for `OVERLAPPED`.

## 4. Report enforcement and denial as data — **LANDED 2026-09-28** *(the no-capture variant, per the operator's ruling)*

- **Problem**: a caller cannot tell "the sandbox broke (the command never ran)" from "the command was denied (it ran and was refused)"; today both reach the caller as an `Error`/log line.
- **Design (from the 2026-09-25 read-only pass, no code written)**: new `crates/tinio-sandbox-core/src/enforcement.rs` holding `Enforcement { Full, Partial, Unimplemented, NotReported }`, `RunnerFailureRule { allowed_exit_codes, fatal_signatures, informational_lines }`, `Diagnostics { enforcement, denial_signatures, runner_failure_rules }` with `NOT_REPORTED` and `attribute(platform, status, stderr)`, plus `Refused { Path, Capability, Unnamed }`, `Denial { platform, refused, evidence }` and `Attribution { Broken { platform, detail }, Denied(Denial) }`. **Three of the variants this design reserved and the code never built are deleted** (2026-09-30, `plans/2026-09-29-sandbox-bdd-e2e.md` §8 H2, task A6): `Enforcement::{Partial, Unimplemented}`, `Refused::Unnamed` and `Attribution::Denied` are gone, and each enum keeps only the variants its code produces — `Enforcement::{Full, NotReported}`, `Refused::{Path, Channel}`, `Attribution::{Broken, Ran}` (`crates/tinio-sandbox-core/src/enforcement.rs`).
- **Solution, in four steps**: (1) land the core types and re-export them through the facade (`crates/tinio-sandbox/src/lib.rs`) — the CLI only depends on the facade, so without the re-export it cannot see them; (2) give `Backend` a defaulted `fn diagnostics(&self) -> Diagnostics { Diagnostics::NOT_REPORTED }` so all three platforms keep compiling; (3) add the two CLI `Error` variants (`SandboxBroken`, `SandboxDenied`) while **keeping the existing refusal sentences verbatim** (the `serve_sandbox_channels` legs and `cli_lifecycle.feature` assert their wording), and expose `sandbox::diagnostics()` / `sandbox::attribute(status, stderr)` as the only entry points; (4) map the Windows backend's refusals and hand the child's status+stderr to `attribute` at the supervise site.
- **Sites**: new `crates/tinio-sandbox-core/src/enforcement.rs` plus the facade re-export in `crates/tinio-sandbox/src/lib.rs`; `Backend` in `crates/tinio-sandbox-core/src/backend.rs`; `crates/tinio-cli/src/error.rs`, `crates/tinio-cli/src/sandbox/mod.rs`, `crates/tinio-cli/src/commands/start/run.rs`; the refusal mapping in `crates/tinio-sandbox-windows/src/backend/mod.rs`.
- **Wiring caveat**: "which path was refused" lives in `crates/tinio-cli/src/commands/start/run.rs`, where `?` on `create_dir_all`/`FsStorage::new`/`bind` currently turns an io error into a path-less `Error::Io`; the classifier has to be called there, gated on `adopted.is_some()`.
- **Unverified**: the real Windows denial text, the io kind of an AppContainer refusal, and whether the launcher captures (rather than merely inherits) the child's stderr.
- **Acceptance**: three platforms can express it, and **no platform is a stub for this item to hang on any more** — `tinio_sandbox::backend_available()` answers `true` on Linux, macOS and Windows (`contracts/cli.md`'s `--sandbox` bullet owns that landed fact; the `BACKEND_IS_STUB` constant this line used to name is deleted), so each platform must name its own strength rather than an `Unimplemented` stub's "unsupported"; a denial names the channel or path; fail-closed strength unchanged; nothing may run unconfined.
- **Landed 2026-09-28, in the variant the operator ruled**: `crates/tinio-sandbox-core/src/enforcement.rs` holds the vocabulary (`Enforcement`, `Refused`, `Denial`, `Attribution`, `Diagnostics`), `Backend::diagnostics()` defaults to `Diagnostics::NOT_REPORTED` with each backend overriding it beside its `FACTS` (`DIAGNOSTICS`, `Full` on all three), the facade re-exports the names name-for-name and adds `diagnostics()`, and the CLI carries `Error::SandboxBroken`/`SandboxDenied` with `sandbox::{diagnostics, attribute, describe, classify_io}` as the entry points. **The item's stderr half was dropped by that ruling**: no `RunnerFailureRule`, no denial-signature matching, no stderr capture — decision 19 keeps the child's stderr the operator's, unmediated — so `attribute` takes `(&ExitStatus, reported_ready)` and a child that never reported is `Broken` carrying the sentence that site already emitted, while a confined child's own permission refusal on a named path becomes `SandboxDenied` naming it (`run.rs` calls the classifier at the four io sites, gated on `adopted.is_some()`). No existing refusal sentence changed; the Windows confined e2e and the `@cli and @confinement` pair were run against the rewired path, and `cargo hack check --package tinio --each-feature --no-dev-deps` is green in all 16 feature states. **The one settled limit this item left, recorded 2026-09-28**: `Attribution::Denied` has no producer on the launcher path — the launcher decides on the exit status and the readiness record alone, and a confined child refused *after* readiness is indistinguishable from any other non-zero exit without the child's stderr (decision 19), so `attribute(_, true)` has no caller, no run builds `Denied`, and a post-readiness refusal reaches the caller as the forwarded code; the core enum, the CLI's `sandbox::attribute` and `run.rs`'s `launcher_exit` each state that limit where they decide. The two write-only `platform` fields were deleted in the same pass — `Attribution::Broken`'s and `Error::SandboxBroken`'s — because the sentence an operator reads is the detail's and nothing rendered either spelling (the `SandboxDenied` platform stays: its sentence names it). **And the variant that limit is stated on is deleted with the other unconstructed ones** (2026-09-30, `plans/2026-09-29-sandbox-bdd-e2e.md` §8 H2, task A6): `Attribution::Denied` is gone, so the enum is `Broken | Ran` and the limit reads as `Attribution::Ran`'s — the arm that holds "an exit with nothing to classify" — with a post-readiness refusal still reaching the caller as the forwarded code. **`Denial`, the struct that variant carried, is deleted as dead vocabulary in the same sweep** (2026-09-30, the same `plans/2026-09-29-sandbox-bdd-e2e.md` §8 H2 criterion — a name keeps only what its code produces): `Attribution::Denied` was its only structural user, so once the variant went the struct had no reader and it is gone from `crates/tinio-sandbox-core/src/enforcement.rs`, both `lib.rs` re-exports and `tests/facade.rs`, while `Refused` and `Attribution::Ran` stay live.

## 5. Pipe-pool extremes — **LANDED 2026-09-28; the drain defect its own test found is fixed**

- **Problem**: (a) concurrent dials beyond the pool return `ERROR_PIPE_BUSY`, which used to be indistinguishable from a dead channel; (b) a client that never closes holds an instance under the drain; (c) whether `INSTANCES` should be configurable.
- **Solution (landed)**: (a) bounded retry (`BUSY_RETRIES = 5`, `BUSY_BACKOFF = 1 ms`, ~31 ms budget) and a spent busy dial now returns **`Error::Busy`** instead of a raw `io::Error`, so `stop` can tell "there is a server and it is full" from "nothing there" while `status` keeps reporting `running: false` with the state file intact (`contracts/cli.md:58`); (b) `wait_for_peer_close` is bounded by **`DRAIN_LIMIT = 250 ms`** and a forced reclaim emits `tracing::warn!(%identity, limit, waited, …)` — justified by measurement, not taste: across 201 sequential dials the drain ends in **80–181 µs** (p50 97 µs, p99 177 µs), i.e. the bound sits ~1 400× above the mean, and nothing is discarded at it (tokio's pipe write is `WriteFile` + `FlushFileBuffers`, which blocks until the client consumes, and `keep_alive(false)` means nothing follows the response); (c) `INSTANCES` **stays a constant** — configurability would create a second source of truth across the launcher handoff plus a matching `Plane::adopt` floor, for zero measured benefit (0 retries over 200 sequential dials).
- **Remaining gap (measured, not suspected)**: neither §5 scenario can be turned into a passing test in-tree, because `#[tokio::test]` runs **current-thread** here and (i) `ClientOptions::open` on an instance that has not reached `ConnectNamedPipe` **blocks the only thread** (spawning the dial does not help — the task inherits the thread), while (ii) a held `SendRequest` does **not** keep a pipe open (measured: the server released the instance ~100 µs after the exchange, because the handle lives in hyper's connection future).
- **Solution for the gap**: add `rt-multi-thread` to `tinio-api`'s dev-dependencies and write the two tests as `#[tokio::test(flavor = "multi_thread", worker_threads = 2)]`; the implementation needs no change for that. Keep the `Error::Busy` mapping pinned by the `error.rs` test that already exists.
- **Both landed 2026-09-28** — `a_dial_that_finds_the_whole_pool_busy_is_reported_as_busy` (`client.rs`) and `a_client_that_never_closes_holds_its_instance_only_under_the_bounded_drain` (`transport.rs`) — **and the second one found a defect in what the bound does to the instance it reclaims, now fixed.** The test's own probes measured it: `DisconnectNamedPipe` disarms the pipe but does not clear the runtime's per-handle read state (`mio` reads named pipes through an internal buffer — `mio-1.2.3/src/sys/windows/named_pipe.rs:532`, *"reads are submitted using internal buffers and `NamedPipe::read` reads from this internal buffer"*), and the drain's **one-byte** read is what left a request's tail in it, so the instance went back into service out of step with its connections: over the transcript the test now asserts, the first dial after a forced reclaim ended `Transport("/status: connection error")` and the dials after it were answered **`405 Method Not Allowed`**, the request having reached the router as `ET /status HTTP/1.1` because the drain's read had taken its first byte.
- **The fix is two rules and no new machinery.** The drain takes a **whole chunk** — the runtime's own 4 KiB buffer size — instead of one byte, so the *drain* is never the thing that leaves a request's tail behind; and it answers the loop with whether the client's **close** ended the wait, which the loop carries to the next connection's `Pool`, whose `poll_read` **retries a pre-first-byte read error once** — the error the cancelled read leaves for the connection that follows, and one retry is enough because the runtime schedules its next read as it consumes the stored one. Normal path unchanged: `the_pipe_pool_serves_back_to_back_dials_with_no_gap` still reports `200 sequential dials, 0 retries`, the forced-reclaim warning and `DRAIN_LIMIT` stand, and the new test asserts the property rather than a retry count — every dial that connects after the reclaims is answered `200` (the first three of them, in a row; a dial that *connects* and is then answered nothing is a failure too, which is the pre-fix behaviour verbatim), with the whole transcript in the failure message, and only the dials that cannot connect at all — `ERROR_PIPE_BUSY` while both instances are held — are waited through.
- **Neither retirement mechanism this item's first draft would have reached for is available, and both were measured rather than assumed.** A **successor instance** (close the poisoned one, create the next at the same name) needs `CreateNamedPipeW`, which is refused to the process that serves these instances inside a container — its token is the package SID and the DACL is current-user-only, `ERROR_ACCESS_DENIED` (`dacl.rs`'s `adopted_pipe` note; `bind::INSTANCES` says the same about the name going deaf for good). And **renewing the same instance** (duplicate the handle, drop the association that owns the state, wrap the duplicate into a fresh one) is refused by the kernel: `DuplicateHandle` succeeds, but the fresh association's registration is `CreateIoCompletionPort` on an object already associated with the completion port, and that answers `ERROR_INVALID_PARAMETER (87)` — measured 2026-09-28 with the two steps separated so the failing call was read rather than inferred.
- **What is still open, and now stated where the code lives**: the runtime's buffer can still hold *bytes* a client wrote after its response and never closed — a client that writes more than one chunk — and bytes carry no marker that tells them from a request, so no connection can tell those apart. The whole-chunk drain read keeps the *drain* from being the one that leaves them; nothing else in this crate can.
- **Corrections to the prose above, from the same measurement**: the `(b)` bullet's "nothing is discarded at it (tokio's pipe write is `WriteFile` + `FlushFileBuffers`, which blocks until the client consumes…)" keeps its conclusion and loses its evidence — `tokio`'s write on a pipe is a `WriteFile` into the pipe's buffer and its `poll_flush` is a no-op (`tokio-1.53.1`'s `net/windows/named_pipe.rs:918`), so the answer is *buffered* for the client rather than consumed by it; and "the disarm discards whatever the pipe still holds unread" is true of the **pipe** and false of the **runtime's** read state, which is exactly what the fix above answers.
- **Sites**: `crates/tinio-api/**` (`client.rs`, `error.rs`, `transport.rs`, `Cargo.toml`; the fix is `transport.rs`'s `wait_for_peer_close`/`serve_pipe_connection`/`pipe_instance_loop`/`Pool`).
- **Acceptance**: the two scenarios become passing tests; `tinio-api` suites green; one real confined run (`status` ×2 then `stop`) with no forced-reclaim warning in the log — **the confined run is not part of this pass** (nothing in it changes, and the warning it reads is the event the new test asserts by identity, scoped to its own pipe name).

## 6. Linux seccomp coverage review — **LANDED 2026-09-26; extended 2026-09-27**

- **Problem**: the filter blocked outbound `connect`/`sendto`/`sendmsg`/`sendmmsg` only; Codex blocks `io_uring_*` unconditionally because a ring can carry traffic without `socket()`.
- **Solution (landed)**: `io_uring_setup`/`enter`/`register` (425/426/427) are denied; `filter_program` is **twenty-seven instructions on `x86_64` and twenty-five on `aarch64`** (the pair was nineteen until (a) and (b) below landed on 2026-09-26). The bypass was **measured**: before the change `io_uring_setup` returned a descriptor inside the confinement and an `IORING_OP_SENDMSG` SQE delivered a datagram while `sendto` was `EPERM`. `enter`/`register` are denied separately because tinio confines **in place**, so a ring opened before the filter lands would stay usable through `enter`.
- **The two items left open at this plan's writing are landed too, so nothing here is left to do.** (a) `ptrace`/`process_vm_readv`/`process_vm_writev` are denied beside the network paths — a second guarantee rather than a second spelling of the first, since a confined same-uid process could otherwise read a neighbour outside the jail or inject into it, or follow `/proc/<pid>/root` links across the mount view — and (b) the x32 gap is closed by one `JSET 0x4000_0000` on the syscall number, ahead of every equality test, which refuses **the whole ABI** rather than only the ten numbers the list names: the one-rule shape this item's (b) asked for, and the wider behaviour is the ratified one because the program compares `seccomp_data.nr` once and has no second comparison to key on both the bit and a number.
- **The measurements live here, in the item they belong to, rather than in a scratch report**: they were made inside WSL2 (`Ubuntu-26.04`, kernel `6.18.33.2-microsoft-standard-WSL2`, `CONFIG_X86_X32_ABI=y`) with the crate's own compiled program installed by its test-only dump probe (`crates/tinio-sandbox-linux/src/bin/sandbox-child.rs`'s `TINIO_SANDBOX_TEST_DUMP_FILTER=1`, so the bytes the kernel got were `filter_program`'s and not a second spelling of the policy), read as a before/after pair in one run each: **before**, `x32 connect` was `ALLOWED` and reached a listener (`127.0.0.1:35596`), `ptrace TRACEME` was `ALLOWED` and `process_vm_readv`/`process_vm_writev` against self were `ALLOWED`; **after**, all four answer `EPERM`, the ordinary `connect` is refused in both runs, and `write` is still `ALLOWED` — while the control leg with no filter installed answers `ALLOWED` to every one of the six, so the refusals are the filter's doing rather than a broken probe. The same run's dumped program shows the mask at index 4 (`JSET 0x4000_0000`, `jt=0`, `jf=1`) ahead of every equality test, which is the shape behind the instruction counts this item's opening bullet already carries; the counts themselves are `the_program_length_is_fixed_per_architecture`'s assertion, and the mask's behaviour per number is `the_x32_abi_does_not_reach_the_allow_tail`'s (a four-opcode BPF evaluator over the dumped program, `EPERM` for twelve masked numbers and for the ten unmasked ones and for one past the table it knows, `ALLOW` for a masked number on the `aarch64` program), so both halves are pinned in-tree without a kernel. What is this item's to keep is the tooling cost the ptrace denial buys — no `gdb`, `perf` or `strace` inside the jail — which is **stated from the syscalls' semantics and not measured**, the jail holding no such tool; `docs/sandbox.md` carries it for the operator.
- **Kept as they were, deliberately**: `recvfrom`/`recvmsg`/`recvmmsg`, `socketpair` (receiving cannot exfiltrate; denying breaks socketpair-based tooling) and `sendfile`/`splice` (they copy into an already-connected fd, which no syscall filter can unmake) stay allowed; `connect(AF_UNIX)` stays denied because the filter cannot see the family, and `socketpair` keeps local IPC working.
- **Documentation**: done with the landing (`docs/sandbox.md` names the deny set and the whole-ABI mask, and `plans/2026-09-18-sandbox-p1-linux.md`'s live prose states the landed shape, its fenced record keeping the phase's thirteen-instruction program as written, per §18's rule), and §18 is the entry that records it — **with the set later the same day's eleven: §6's `pidfd_getfd` note owns that count and the twenty-nine/twenty-seven lengths**.

## 7. End-to-end coverage of the Linux overlay branch — **PARTLY LANDED 2026-09-28; the proposed route is measured impossible**

- **Problem**: after the remount fix re-asserts the source mount's `nosuid`/`nodev`/`noexec`, every leg takes the remount arm on this kernel, so the overlay arm is no longer exercised end to end (`read-only-arm: remount`, measured).
- **Solution, as proposed and as landed**: the proposal was to reach `EPERM` through a **locked per-mount flag the request does not name** — `nosymfollow` on this kernel (the host's `/run/credentials/*` mounts carry it; `rustix::mount::MountFlags::NOSYMFOLLOW` exists) — with that state built in a **nested** user namespace: a wrapper creates the `nosymfollow` tmpfs in userns A, then execs `sandbox-child` so its own `unshare(CLONE_NEWUSER)` becomes B, behind an explicit opt-in variable (`TINIO_SANDBOX_TEST_NOSYMFOLLOW=1`) rather than the default gate. The construction is landed, unchanged, as `crates/tinio-sandbox-linux/tests/jail.rs`'s `a_nosymfollow_source_is_served_read_only_under_a_nested_user_namespace`: util-linux's `unshare --user --map-root-user --mount --propagation private sh -c`, which mounts the tmpfs `-o nosymfollow`, seeds the served root, proves the flag took through a symlink that mount refuses to follow, and `exec`s the child with its model pinned to `userns`. The default gate reports and returns without the variable; a host that cannot build the state **fails** the leg rather than skipping (verified with a stub `mount` that refuses the flag).
- **Measured 2026-09-28, and the premise is false: `nosymfollow` is not a locked flag and cannot be one.** `lock_mnt_tree` locks `MNT_LOCK_ATIME` unconditionally and `MNT_LOCK_READONLY`/`NODEV`/`NOSUID`/`NOEXEC` for the flags a mount carries, `can_change_locked_flags` tests exactly those five, and **there is no `MNT_LOCK_NOSYMFOLLOW`** (`fs/namespace.c`, `include/linux/mount.h`); `MNT_NOSYMFOLLOW` is inside `MNT_USER_SETTABLE_MASK`, so a request that does not name it **clears** it instead of being refused. With a bare `mount(2)` from a nested user namespace on kernel `6.18.33.2-microsoft-standard-WSL2`: a bind of a `rw,relatime,nosymfollow` tmpfs, remounted `MS_REMOUNT|MS_BIND|MS_RDONLY` — this crate's request for that source — returns `0` and reads back `ro,relatime`, while the same request naming `MS_NOSYMFOLLOW` reads back `ro,relatime,nosymfollow`; a source carrying `nosuid,nodev` still refuses the bare request with `EPERM`, so the nesting does produce locked flags, just never this one. **The `EPERM` branch therefore has no end-to-end route through a mount flag the code fails to re-assert in a correct run** — which is narrower than "no such flag exists", and the difference is the measurement: the kernel locks **three** of `source_mount_flags_in`'s four flags (`nosuid`/`nodev`/`noexec`, the ones with an `MNT_LOCK_*` behind them; `nosymfollow` has none) plus `RDONLY`, and preserves the atime bits of a remount that names no atime flag — so the request names those three because dropping a locked flag is exactly the `EPERM` this arm catches, while `nosymfollow` rides in the set for the other reason, a request that omits it **silently drops** it. **How wide the route still is, is measured rather than argued**: with the `noexec` parse arm deleted from `source_mount_flags_in`, this leg flips to `read-only-arm: overlay` and the `served-root-exec` probe added beside it tells the two states apart (`PermissionDenied` while the flag survives, the `NotFound` a run without it produces) — so what closes the arm is the request's naming rather than the kernel's locking, and `crates/tinio-sandbox-linux/src/enter.rs`'s `enforce_bind_read_only` carries that counter-measurement in its own paragraph rather than this plan restating it. The overlay arm's in-tree coverage is now two named unit tests — `refused_remount_needs_the_overlay`'s errno pin and `overlay_read_only_flags`'s `the_overlay_carries_the_sources_noexec_and_nosymfollow`, the flag set `apply_overlay_read_only` mounts with — which is also the state design §4 now records. The leg keeps the tolerant "one of the two" arm assertion this item's Acceptance asks for and reports `read-only-arm: remount` like the two default legs; a future kernel that locks a flag the request does not name would make it report `overlay` with no code change, which is why no particular arm is asserted.
- **The same measurement found a second defect in the same flag, and it is fixed (2026-09-28)**: `source_mount_flags_in` named only `nosuid`/`nodev`/`noexec`, so a served root on a `nosymfollow` mount was served **without** that protection — the remount cleared it silently, with no `EPERM` to report, and the overlay arm's fresh mount never carried it either. The set now carries `nosymfollow` when the source does (the overlay included, so both arms serve one root the same way), and the opt-in leg asserts the effect end to end: the child reads a symlink inside the served root and the read is `ELOOP` (`served-root-symlink: refused (FilesystemLoop)`). With the fix reverted in the guest, both halves fail as they should — the flag unit test on the parsed set, and the leg with the child reporting that symlink `followed`.
- **Sites**: `crates/tinio-sandbox-linux/tests/jail.rs` (the opt-in leg and the "one of the two" comment), `crates/tinio-sandbox-linux/src/enter.rs` (`source_mount_flags_in`, `apply_mount`'s inherited-flag argument, `apply_overlay_read_only`, its flag set's definer `overlay_read_only_flags` and the unit tests that pin the arm, `refused_remount_needs_the_overlay`'s and `the_overlay_carries_the_sources_noexec_and_nosymfollow`) and `crates/tinio-sandbox-linux/src/bin/sandbox-child.rs` (the symlink and `served-root-exec` probes).
- **Acceptance**: the arm stays; the gap is documented where the test asserts "one of the two" (done, with these numbers); the nested-userns leg passes under the opt-in variable on this host (`cargo test -p tinio-sandbox-linux --test jail`, 3 passed, the leg green in repeated runs and under `sudo`). **The half that asked for the overlay arm to be reached end to end is not met**, and what closes it is the request rather than the kernel: a correct run names every locked flag the source carries, so no locked flag is left to refuse the `EPERM` — `nosymfollow` cannot be the trigger by construction (the kernel never locks it) and `noexec` can be, which deleting its parse arm shows.

## 10. Standing-grant hardening — **LANDED 2026-09-28** *(all three layers, per the operator's ruling of 2026-09-28; the item's "any subset is useful" was not taken)*

- **Problem**: `package_name` is a pure function of the canonical root, so any local user can compute the SID and create the same AppContainer profile; the grant is also **permanent** for every root ever served (standing, never revoked), and the program directory's `ALL APPLICATION PACKAGES` grant is readable by *any* AppContainer app on the machine.
- **Solution, in three layers** (any subset is useful): (a) **threat-model text** in `specs/2026-09-18-sandbox-design.md` stating both exposures plainly, so a reader does not discover them from the code; (b) **an optional persisted salt** mixed into `package_name`'s derivation (a random value kept in the state directory, one per user/machine) — this is the only thing in this plan that would justify a state file, and it invalidates existing grants once; (c) **an ACE ledger** recording which roots have been granted, so an operator can audit and revoke (Codex's `deny_read_state` structure is the reference), with the concurrency rule that a SID belonging to a run started after the ledger was read must not be removed.
- **Sites**: `crates/tinio-sandbox-windows/src/sid.rs` (salt), the design spec (threat model), and a new ledger module if (c) is taken.
- **Acceptance**: (a) done as text; (b) and (c) only if the exposure is judged worth closing, each with its migration cost stated.
- **Landed (a) — the threat-model text**, as design §6's two new paragraphs ("Two exposures stand where the grants do …" and "The ledger is the record of what was granted …") plus a clause in the Risks table's residue row naming the ledger as the index of the four places: the derived-name exposure stated as the salt's reason to exist, what the salt does **not** close (a reader of the salt file — another standard account cannot read it, an administrator or anything running as this account can), the program directory's machine-wide `ALL APPLICATION PACKAGES` reading with the fact that **no layer of the design narrows it**, and the ledger's own "audit surface and never a control" statement. Nothing was restated from a section that owns it: the grant cost stays §6's, the four residue places stay the Risks table's.
- **Landed (b) — the salt**, in `crates/tinio-sandbox-windows/src/sid.rs`. `Salt::load` reads `%LOCALAPPDATA%\tinio\acl-salt` — one per user, under the same `LOCALAPPDATA` the profile machinery's `Packages` directory sits in — and creates it on first use: 32 CSPRNG bytes (`getrandom`), written into a private temporary file created through `tinio_winsec::create_restricted` and **published by `fs::hard_link`**, so the name never exists without its value, the file is current-user-only with `SE_DACL_PROTECTED` from its first instant, and the loser of a creation race **reads the winner's value** (the failure a create-then-write would have is a loser reading an empty file and silently deriving unsalted). **Derivation**: `package_name(root)` always derives under the salt, `package_name_with(root, &salt)` and `package_name_unsalted(root)` are the pure pair, and **the salt is hashed last** — the normalisation's two readings first, the 32 bytes appended — which is what the design paragraph argues: with the salt in the preimage nothing computes a name without the file, a secret at the end of the preimage is the shape SHA-256's length extension cannot continue, and the unsalted path stays byte-identical to the pre-change derivation so "the degradation" names one historical value rather than a second derivation. The per-path ACL lock's key is deliberately the **unsalted** digest (`root_digest`), so a salted run and a degraded run still take one lock for one path.
- **Landed (b) — the failure policy and the migration cost**. An unreadable, uncreatable, unresolvable-directory or wrong-length salt logs `step="load the ACL salt"` at `warn!` naming the file and saying which derivation ran, and the launch proceeds on the unsalted name: never a failed launch, never silent, and never a name that pretends the salt applied (`ProfileLock`'s precedent). **The migration cost: every ACE and every profile that exists today belongs to an unsalted SID**, so after this change every served root derives a new SID, takes a fresh grant on its first run, and the unsalted ACEs stay standing exactly as decision 15 requires — residue per root ever served, removable only by an operator.
- **Landed (c) — the ACE ledger**, in the new `crates/tinio-sandbox-windows/src/ledger.rs`: `%LOCALAPPDATA%\tinio\acl-ledger.jsonl`, one JSON object per line carrying the root as spelled, the normalised root, the package name, the `S-1-15-2-…` SID, the RFC 3339 UTC instant and the program directory. **The hook is `backend`'s `grant_whitelist`, after its `info!` phase report** — every grant of the launch has returned `Ok` by then, so a line is a claim that a grant happened and a phase that fails halfway records nothing, and the ledger's own file I/O is not counted into the duration that report publishes. **Append-only: no pruning, no rewriting, no removal** — which is how the item's concurrency rule ("a SID belonging to a run started after the ledger was read must not be removed") holds by construction, there being no removal path in the crate to order wrongly — and the append takes `acl::AclLock` keyed on the ledger's own path, so two runs cannot interleave a partial line. **Revocation stays manual**: `acl::revoke`'s `icacls <dir> /remove:g "*<sid>"`, which the launcher never calls — the ledger records, it does not revoke. A ledger that cannot be written warns (`step="record the ACL grants"`) and the run continues, a policy its signature states (`record` has no `Result` to propagate).
- **Manifest**: two dependency edges were added to `crates/tinio-sandbox-windows/Cargo.toml`, both on crates the lock already resolves — `serde_json` (the line; hand-escaping Windows paths into JSON is the class of bug an audit file cannot have) and `time` with `formatting` (the RFC 3339 instant, the spelling `tinio-api`'s state file already publishes) — so this is an edge rather than a crate in the tree, the treatment decision 14's own ledger gives `windows-sys`. **No new `unsafe` site**: the salt's file API is `tinio_winsec`'s safe surface, so decision 14's enumeration is unchanged.

## 22. A served root behind a junction is granted where it points, and the child resolves the spelling it was handed — **RULED 2026-09-28; the resolved spelling alone**

- **Problem**: **the exposure asymmetry this review's own leg proved by building it.** On Windows the launcher grants the **canonical** spelling of an exposure and nothing else — a reparse point in the spelled path is refused outright, and a path that passes is resolved before its ACE is written — while the child is re-invoked with the operator's argv and canonicalises *that* itself, as a confined process. So a served root that is a directory junction whose own directory the container is not granted is granted on the target and unreachable from inside: the child's access check needs an ACE for a SID of its own, the junction's own directory carries none, and `resolve_root` answers the CLI's usage error before the child dispatches. macOS does not meet this shape — `tinio-sandbox-macos`'s `profile::with_canonical_paths` keeps "the resolved spelling beside the operator's", so a link in the exposure set matches either way (`crates/tinio-cli/src/commands/start/run.rs`'s own doc states the two arms' difference). **Whether Windows should do the same is a product question for the crate owner and is not decided here**: granting the operator's spelling beside the canonical one would also mean granting a reparse-point path, which the spelled-path refusal exists to prevent, and the two rules meet on exactly this case. The symptom is honest today rather than silent — the parent emits its own `error` frame for the child that never reported, and the child's own refusal is on the inherited stderr — so this is a coverage question rather than a diagnosis one, and the workaround is to serve the directory the junction names.
- **Sites**: `crates/tinio-sandbox-windows/src/backend/exposures/whitelist.rs` (`canonical_host`'s refusal-then-resolve and `canonical_exposures`; `exposures.rs` is the directory `backend/exposures/{mod,reparse,siblings,whitelist}.rs` since 2026-09-27), `crates/tinio-sandbox-windows/src/backend/mod.rs`'s `confine`; the design's §6 reparse-point paragraph owns the rule, and `docs/sandbox.md`'s Windows section states the operator-visible consequence.
- **Acceptance**: the Windows crate's owner rules on the asymmetry, and whichever way it is ruled the rule has one definer — either `canonical_exposures` grants both spellings (the macOS reading) and design §6's paragraph says so, or it keeps granting the resolved one alone and the paragraph states that a junction root must be spelled as its target. A test pins the ruled behaviour from the launcher's side, and `crates/tinio-server/tests/sandbox_e2e_windows.rs`'s `a_child_that_never_reports_is_the_parents_own_error_frame` is the leg that must be re-induced if the exposure rule ever widens — it is coupled to this behaviour, and its own doc block says so. The fixture is that leg's own and the tree carries its reasoning: the leg builds the junction and seals the tree, `windows_e2e_harness.rs`'s `seal_to_current_user` reads the seal back so a seal that did not take fails the fixture rather than the assertion, and its doc states why omission is the refusal the mechanism honours (an object is hidden from a container by carrying no container ACE at all, because a deny ACE is evaluated against a token's normal groups while the restriction is a second, allow-only pass).
- **Ruled 2026-09-28, and no code changed**: the operator took the first branch — Windows keeps granting the resolved spelling alone, so a served root that is a directory junction is served by the directory the junction names and not by the junction's own spelling; granting both would re-open exactly what the spelled-path refusal exists to prevent (an ACE on a link's own object, or on a target outside the exposure — both measured in the Problem above). The rule now lives in design §6's reparse-point paragraph, with `docs/sandbox.md`'s Windows section stating the operator-visible shape, and the coupled leg the Acceptance names — `crates/tinio-server/tests/sandbox_e2e_windows.rs`'s `a_child_that_never_reports_is_the_parents_own_error_frame` — stands as the ruled behaviour's pin and is to be re-induced if the rule ever widens.

## The mechanism-selection question (three platforms, one choice)

**Nature**: survey + table + open questions, not a todo item. The operator wants the **user** to pick the mechanism, and accepts a **degraded** Windows option beside the Codex/DSH-equivalent ones. Nothing below is decided; the future Windows/Linux dual-mode work cites this section.

**Citations**: `design` = [`docs/superpowers/specs/2026-09-18-sandbox-design.md`](../specs/2026-09-18-sandbox-design.md), `prior art` = [`docs/superpowers/sandbox-prior-art-research.md`](../sandbox-prior-art-research.md); a bare `crate/path:line` for the sandbox crates means `crates/tinio-sandbox-*`, and a bare `NNN` after `design` is a line of that file.

### Windows true in-process apply: **no**

- `CreateRestrictedToken` builds a **new** token from an existing one, and the documented consumption is `CreateProcessAsUser` or `ImpersonateLoggedOnUser` — nothing applies it to the calling process's own primary token ([MS Learn](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken); documentation, **not measured here**).
- `SetTokenInformation` replaces information on a token, and token-*type* information is set only at creation; `TokenRestrictedSids` and `TokenIntegrityLevel` exist as classes ([TOKEN_INFORMATION_CLASS](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ne-winnt-token_information_class)) — "the class exists" is not "a running process is confined". **No file under `crates/**` names `SetTokenInformation`, `NtSetInformationToken`, `SetProcessContainer`, `SetProcessMitigationPolicy`, `CreateRestrictedToken` or `sandbox_init`** (`rg` over `crates/`, 0 hits).
- **Closest thing**: self-lowering to Low IL through `SetTokenInformation(TokenIntegrityLevel)` — in-process, and the one half of DSH's mechanism that is even expressible on a running process. It is a **write** wall; reads of medium-IL objects stay allowed, which is exactly why DSH's read isolation is documented `partial` (prior art §5, §9). Whether the call succeeds on the caller's **own primary token**, and what it does to a server that already opened its listener, state dir and storage, is **unmeasured** (open questions).
- `SetProcessMitigationPolicy` is in-process by definition ("for the calling process") and is **not access control** — DEP, ASLR, dynamic-code, child-process, font and image-load hardening ([MS Learn](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessmitigationpolicy)). Not a substitute for a confinement.
- Job objects: [`AssignProcessToJobObject`](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject) does accept an already-running process, but the job's token-**filtering** security limitations require a suspended creation (`JOB_OBJECT_SECURITY_ONLY_TOKEN`), so the security half is creation-time too; the rest is limits and lifetime, which `windows/src/job.rs` already uses for that and nothing more.
- AppContainer has no attach step in this tree at all: the identity rides `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` into `CreateProcessW` (`windows/src/process.rs:548-557`), which is why `Backend::confine` can only confine a process it creates (`windows/src/lib.rs:4-7`).
- **Answer: no.** Closest = self-lowering to Low IL (in-process, write-only); second closest = a restricted token at creation (Codex/DSH).

### The degraded Windows route, and exactly what it gives up

- **What AppContainer buys that the route surrenders**: read isolation, measured in-tree — a directory carrying `Users` and no package-SID ACE is refused `permission denied` to the confined child (`windows/tests/common/tree.rs:125-142`, `windows/tests/confine.rs:68`; design:413, "a non-granted tree is denied despite carrying `Users` and `Authenticated Users` ACEs"). `WRITE_RESTRICTED` consults its restricting SIDs **only when evaluating write access** (MS Learn), and a token that keeps the caller's own SIDs still reads every tree the caller can read — DSH's documented `partial` (prior art §5).
- **Do not copy the write-only shape.** Prior art §9 says it plainly: DSH confines writes only, and copying its core mechanism wholesale is a security regression against AppContainer's default-deny read. A degraded mode is defensible only if the run **says** which mode it is — §4's "enforcement as data" argument, applied to strength.
- **Saved**: the profile lifecycle (`windows/src/sid.rs:280`, `:399-419`) and with it §19's per-run `%LOCALAPPDATA%\Packages` directory; `package_name`'s derivation and residue takeover (`windows/src/sid.rs:136-153`); the program directory's standing `ALL APPLICATION PACKAGES` RX (`windows/src/sid.rs:58-81`) and the "readable by any AppContainer app on the machine" price that constant states.
- **Not saved, contrary to the obvious reading**: the per-root ACL write. DSH's restricting list carries a per-workspace capability SID, and it must hold an ACE (plus a deny and a Low integrity label) or writes fail the second access check (prior art §5). The cost moves from "profile + per-root ACE" to "per-root ACE + label"; what the operator buys back is the **read** half, not the ACL half.
- **The one shape that does save the ACL half**: Codex's unelevated mode — `CreateRestrictedToken(WRITE_RESTRICTED)` with the caller's own token, no identity and no ACL writes (prior art §2) — but it buys that by making the tree unwritable, so a normal read-write tinio run cannot use it at all. It is the read-**only** degraded mode, not the general one.

### Linux: several directories, each in its own process — **no helper needed**

- **What in-place does, and from where.** `Backend::confine` → `enter` (`linux/src/lib.rs:113-124`, `linux/src/enter.rs:75-98`): validate + plan → jail root in `$TMPDIR` → `unshare(CLONE_NEWUSER)` + the three maps → `unshare(CLONE_NEWNS)` → `make / private` → the mounts → `pivot_root` + `umount2(MNT_DETACH)` → cap drop → seccomp. **Irreversible for the calling process** and every failure fatal (`linux/src/enter.rs:63-66`). Reached as step i: `crates/tinio-cli/src/commands/start/run.rs`'s `sandbox::confine` call → `crates/tinio-cli/src/sandbox/confine.rs`'s `confine` → `tinio-sandbox`'s `serve::Spec::apply` → the Linux backend's `Backend::confine` → `enter` (the chain this bullet used to spell through `sandbox/mod.rs` and `sandbox/linux.rs`, both of which the 2026-09-27 seam moved). Linux answers `Confinement::InPlace` and launches nothing (`linux/src/lib.rs:113-124`).
- **Per-process by construction**: `unshare` applies to *this* process, so each caller gets its own user + mount namespace, its own jail root (`linux/src/jail.rs:27-52`, pid-free, keyed on the served root), its own overlay pair (`linux/src/plan.rs:120-134`) and its own seccomp filter (`linux/src/seccomp.rs:353-357`, per-thread, single-thread precondition). Decision 10 states the concurrency rule — two processes mounting one host directory each do so inside their own mount namespace (design:139).
- **`src/bin/sandbox-child.rs` is test-only.** A plain `fn main` that confines itself, then prints `key: value` probes (`linux/src/bin/sandbox-child.rs:1-27`); its only spawner is `crates/tinio-sandbox-linux/tests/jail.rs:130` (`CARGO_BIN_EXE_sandbox-child`), while `crates/tinio-server/tests/sandbox_e2e.rs:216` mentions it in a doc comment and spawns the `tinio` binary. It exists because libtest runs a test on a worker thread and `unshare(CLONE_NEWUSER)` refuses in a multi-threaded process (`linux/src/bin/sandbox-child.rs:4-7`) — a **test** constraint, not a production one.
- **Answer: no.** A helper is not needed; it is sufficient to call the existing in-place mechanism inside each already-separate server process. The per-process requirement that makes it work is exactly one: **confine before any thread exists** — `unshare(CLONE_NEWUSER)` returns `EINVAL` in a multi-threaded process, and the filter applies per-thread without `TSYNC` (decision 26, design:169; design:473, `:490`; `linux/src/mechanism.rs:193-205`; `linux/src/seccomp.rs:353-357`). Every server process already meets it inside one `fn main`: `crates/tinio-cli/src/run.rs:77-80`, with the runtime built last (`run.rs:184-201`), and the order recorded at `crates/tinio-cli/src/commands/start/run.rs:54-63`.
- **The shape that *would* need a helper, and why it is not this one**: a single supervisor that already built its runtime and then wanted N confined children in place. That process is multi-threaded (`crates/tinio-cli/src/run.rs:197-201`), so its own `unshare` is the `EINVAL` case and its namespace would in any case be shared by every child; confining from there needs a fresh single-threaded re-exec — a helper. N independent servers, each with its own `fn main`, are not that shape.
- **The one place the split is necessary rather than merely sufficient**: `plan` refuses more than one read-only exposure under `Mechanism::UserNamespace`, because one jail has one overlay pair and an overlay upper binds a single lower (`linux/src/plan.rs:172-186`; design §4, design:370). One directory per process is at most one read-only exposure per jail, so the refusal never fires — and a single process exposing N read-only directories is refused today. Under `Mechanism::Root` two are accepted, on the premise that the remount is never refused (`linux/src/plan.rs:332-334`).
- **Also worth recording**: N exposures in **one** process are supported for read-write (`linux/src/plan.rs:188-203` loops the whole set), so "N directories" has two shapes — one process with N exposures, or N processes with one each. The read-only case is the one that wants the second.

### Parameterisation: structural on Linux and Windows, textual only on macOS

- macOS is the only platform whose grant is **text a policy engine parses** — `(param "E0")` in the SBPL plus the value beside it as `-D NAME=VALUE` (`macos/src/profile.rs:1-16`, `:220-263`; `macos/src/launch.rs:400-490`) — and decision 24 makes that a security property: a value is data (design:167).
- Linux needs no equivalent, because nothing parses a path: `mirror_under` composes the target (`linux/src/jail.rs:83-120`), `plan` records source/target/kind (`linux/src/plan.rs:188-203`), and `apply_mount` hands them to `mount` / `mount_bind_recursive` / `mount_remount` (`linux/src/enter.rs:335-341`). No policy language exists, so the channel injection would use does not exist.
- Windows needs no equivalent for the same reason: an exposure becomes an **ACE** whose SID and mask are structured values and whose path is an API argument (`windows/src/acl.rs`; design §6, design:401-407). The `icacls` subprocess is the one text-shaped step in that path (§1/§2), and §2's planned direct-API write removes it.
- **Consequence**: the macOS in-process route's measured cost is not parameterisation — `sandbox_init_with_parameters` takes the same `-D` pairs (measured) — but its being one-shot and its refusal of `fork`/`exec` after the apply, and neither of those transfers to Linux or Windows. A cross-platform "user picks the mechanism" option therefore adds no parameterisation concept to Linux or Windows. The rule that already carries that duty on macOS is decision 24's "path validation, not the profile text, is what bounds the exposure set" (design:167).

### Open questions / not established

- Whether `SetTokenInformation(TokenIntegrityLevel)` succeeds on a process's **own primary token** and tightens the access checks of a server that is already running. Unmeasured: the call's documented existence is not a measurement of the effect, and no experiment was run for this survey.
- Whether an unprivileged user can mint a token carrying an arbitrary `S-1-4-…` capability SID. This decides whether the degraded route **narrows** §10's "any local user can compute the SID" exposure or merely changes its shape.
- Whether design §7's Windows network default-deny (design:430, `:433`) is a property of the **AppContainer SID** or of capability SIDs as such. Every in-tree network measurement is an AppContainer measurement; a non-AppContainer token is unmeasured.
- Whether the macOS in-process route keeps parameterisation. **Answered 2026-09-26**: it does — `sandbox_init_with_parameters` took the real rendered profile text and the real `-D` pairs at `rc=0`, and the record is the design's evidence-table row rather than an out-of-tree note. The retired wording was: `sandbox_init` takes a profile string; whether `sandbox_init_with_parameters` replaces `-D` was **not verified** here. The tree records only that `sandbox_init` FFI is authorized (design:554), and the operator's in-process measurement lives outside it.
- Whether that route can be applied **in place** to an already-serving process at all — before the runtime, in one `fn main`, the way Linux does it. **Answered 2026-09-26**: yes, and it does not care about threads — a thread created before the apply does not block it, every tokio runtime configuration builds and `block_on` returns in under 2 ms, and only `Command::output()` is refused — but the apply is one-shot and forbids `fork`/`exec` unless the profile grants `process-fork`, so a launcher that must still spawn its child cannot use it (design evidence table).
- The degraded route's numbers: what the profile lifecycle and the `package_name` derivation actually cost per run, measured against the ACL phase the tree already times (`windows/src/backend/grant.rs`, `report_grant_phase`). Not measured for a token route.
- Whether a degraded route keeps the control-channel handoff. Today it exists because the child's identity is the package SID and it cannot create a pipe (`crates/tinio-sandbox/src/serve.rs`'s `apply_windows` and the CLI's `sandbox/confine.rs` handoff — the module this line used to cite, `crates/tinio-cli/src/sandbox/windows.rs`, is gone); whether a restricted-token child could bind its own is unmeasured, and Codex paid for that with `TokenDefaultDacl` (prior art §2).
- The channel a cross-platform choice should use. Linux already reads `TINIO_SANDBOX_MODEL` (`linux/src/mechanism.rs:82-118`) and Windows already reads `TINIO_SANDBOX_CAPABILITIES` (`crates/tinio-sandbox/src/serve.rs`'s `apply_windows`, the `env::var` call itself); whether one name generalises both, or the choice becomes a flag/config key, is a schema decision nobody has made.
- Whether the exposure cap survives an in-process macOS route. `MAX_EXPOSURES` bounds the **compiled profile** (design:395), so it should persist; not re-checked against `sandbox_init`.

### The dual-mode items this survey implies — **OPEN** *(Windows degraded mode; Linux multi-root)*

- **Problem**: no platform lets the user choose a weaker mechanism; Windows' only mode is AppContainer, so the accepted degraded option is not expressible (`Options` carries `capabilities`, `program`, `args` only — `windows/src/backend/mod.rs:85-101`); and the Linux multi-root question has no written answer.
- **Solution**: (a) Windows — add a mode to `Options` plus a CLI channel beside `TINIO_SANDBOX_CAPABILITIES`, selecting restricted-token confinement. Supervision, payload, listener/control handoff and the job are unchanged; only the creation call differs — `windows/src/process.rs:487-586` builds `SECURITY_CAPABILITIES` + `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` into a `STARTUPINFOEX`, and a token route swaps that attribute for `CreateProcessAsUserW` (`windows/src/process.rs:647-663`). (b) Linux — write "N roots = N processes, each confining itself; no helper" into the design, and keep `sandbox-child` test-only.
- **Sites**: `crates/tinio-sandbox-windows/src/backend/mod.rs`, a restriction module beside `windows/src/process.rs`, the Windows mode's channel beside `TINIO_SANDBOX_CAPABILITIES` in `crates/tinio-sandbox/src/serve.rs` (`crates/tinio-cli/src/sandbox/windows.rs` is gone since 2026-09-27); for (b) `specs/2026-09-18-sandbox-design.md` §2/§4 and this plan.
- **Acceptance**: the selected mode is named in the run's own reporting, and a degraded run never claims read isolation (the §4 vocabulary applied to strength); on Linux, two servers on two roots under `--sandbox --read-only` confine themselves one process apiece, with no helper binary in the process tree or on disk. Take (a) only after the open questions above are answered — the read-isolation loss is the whole price.
