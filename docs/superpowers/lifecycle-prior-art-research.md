**Direct answer.** AWS replaces the whole configuration on `PUT`, requires a checksum (any supported algorithm, not literally `Content-MD5`), returns `200` with an empty body, and `GET` on a bucket without a configuration is `404 NoSuchLifecycleConfiguration`. `Expiration.Days` rounds *up* to the next midnight UTC; a `Date` in the past is accepted and everything matching becomes immediately eligible; and if the current version is already a delete marker, **S3 takes no action** — which confirms the design's LC2 rather than correcting it. MinIO parses and validates the same XML minus `AbortIncompleteMultipartUpload` (unsupported by design, maintainer-confirmed), evaluates rules in its background scanner with the same midnight-UTC rounding (`ExpectedExpiryTime`), and adds non-AWS extensions plus one real filter deviation (§9.1).

## 1. AWS API surface

### 1.1 `PutBucketLifecycleConfiguration`

- **Replaces the whole configuration.** "Creates a new lifecycle configuration for the bucket or replaces an existing lifecycle configuration. Keep in mind that this will overwrite an existing lifecycle configuration, so if you want to retain any configuration details, they must be included in the new lifecycle configuration." ([PutBucketLifecycleConfiguration](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutBucketLifecycleConfiguration.html)) — direct. Consequence (inference): clients must read-modify-write; MinIO's CLI does exactly that (§7).
- **A checksum is required, but not specifically `Content-MD5`.** The current request syntax carries `x-amz-sdk-checksum-algorithm`, documented as: "When you send this header, there must be a corresponding `x-amz-checksum` or `x-amz-trailer` header sent. Otherwise, Amazon S3 fails the request with the HTTP status code `400 Bad Request`." ([PutBucketLifecycleConfiguration](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutBucketLifecycleConfiguration.html)) — direct for the mechanics. That the *operation* requires a checksum is attested by AWS's SDK maintainer — "`PutBucketLifecycleConfiguration` is one of the operations that [does require](https://github.com/boto/botocore/blob/5eea62f219c61c6b3c81353d00156113151cdb35/botocore/data/s3/2006-03-01/service-2.json#L1087-L1089) a checksum" — while the older note "When making a request using the REST API, you must include the Content-MD5 header." was **removed from AWS's docs** in March 2025: "A colleague of mine let S3 know about the note, and they've actually already removed it." ([botocore#3415](https://github.com/boto/botocore/issues/3415)) — direct. So: required, algorithm-agnostic today; `Content-MD5` is the pre-2025 documented form and is what MinIO enforces (`cmd/bucket-lifecycle-handlers.go:54-57`).
- **Return.** "If the action is successful, the service sends back an HTTP 200 response. The response returns the following HTTP headers." The only documented header is `x-amz-transition-default-minimum-object-size`, and the sample response shows `Content-Length: 0` ([PutBucketLifecycleConfiguration](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutBucketLifecycleConfiguration.html)) — direct.
- **Several actions per rule are legal.** The documented `GET` response for one rule carries two `<Transition>` elements *and* an `<Expiration>` inside the same `<Rule>` ("Archive and then delete rule") ([GetBucketLifecycleConfiguration](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetBucketLifecycleConfiguration.html)) — direct; v1 says it in words: "The rule also specifies two actions (`Transition` and `Expiration`)." ([PutBucketLifecycle](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutBucketLifecycle.html)) — direct. The `PUT` page's own examples happen to use one action per rule; that is a sample shape, not a limit.

### 1.2 `GetBucketLifecycleConfiguration`

- **Response element names** (exact): root `<LifecycleConfiguration>`; repeated `<Rule>`; inside a rule `<ID>`, `<Prefix>`, `<Status>`, `<Filter>` (with `<And>`, `<ObjectSizeGreaterThan>`, `<ObjectSizeLessThan>`, `<Prefix>`, `<Tag><Key>/<Value>`), `<Expiration>` (`<Date>`, `<Days>`, `<ExpiredObjectDeleteMarker>`), `<Transition>` (`<Date>`, `<Days>`, `<StorageClass>`), `<NoncurrentVersionExpiration>` (`<NewerNoncurrentVersions>`, `<NoncurrentDays>`), `<NoncurrentVersionTransition>`, `<AbortIncompleteMultipartUpload><DaysAfterInitiation>` ([GetBucketLifecycleConfiguration response syntax](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetBucketLifecycleConfiguration.html)) — direct.
- **No configuration →** "`GetBucketLifecycleConfiguration` has the following special error: Error code: `NoSuchLifecycleConfiguration`; Description: The lifecycle configuration does not exist.; HTTP Status Code: 404 Not Found" ([same page](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetBucketLifecycleConfiguration.html)) — direct. The design's assertion that GET answers `NoSuchLifecycleConfiguration` is confirmed.
- `x-amz-transition-default-minimum-object-size` is a response *header*, not a body element — direct (same page).

### 1.3 `DeleteBucketLifecycle`

- "If the action is successful, the service sends back an HTTP 204 response with an empty HTTP body." ([DeleteBucketLifecycle](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DeleteBucketLifecycle.html)) — direct.
- **No configuration present:** the page documents **no** special error, unlike its sibling `GetBucketLifecycleConfiguration` — inference: S3 answers `204` regardless. ### 1.4 v1 still exists, and both generations share one subresource

- "For an updated version of this API, see PutBucketLifecycleConfiguration. **This version has been deprecated.** Existing lifecycle configurations will work. For new lifecycle configurations, use the updated API." ([PutBucketLifecycle](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutBucketLifecycle.html)) — direct; "provided for backward compatibility" likewise on [GetBucketLifecycle](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetBucketLifecycle.html) — direct.
- **Shape difference.** v1's rule body has no `<Filter>`: `<Rule>` with `<AbortIncompleteMultipartUpload>`, `<Expiration>`, `<ID>`, `<NoncurrentVersionExpiration>`, `<NoncurrentVersionTransition>`, `<Prefix>`, `<Status>`, `<Transition>` ([PutBucketLifecycle request syntax](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutBucketLifecycle.html)) — direct. v2 keeps a rule-level `<Prefix>` but deprecates it — "The general purpose bucket prefix … *This member has been deprecated.* We recommend using `Filter` instead of `Prefix` for new PUTs" — and adds `<Filter>`, "`Filter` is required if the `LifecycleRule` does not contain a `Prefix` element" ([LifecycleRule](https://docs.aws.amazon.com/AmazonS3/latest/API/API_LifecycleRule.html)) — direct.
- **`?lifecycle` versus `?lifecycle-configuration`.** Every AWS page read addresses both generations as `/?lifecycle`: v2 `PUT /?lifecycle` / `GET /?lifecycle` ([Put](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutBucketLifecycleConfiguration.html), [Get](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetBucketLifecycleConfiguration.html)), v1 `PUT /?lifecycle` ([Put](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutBucketLifecycle.html)) — direct. I found **no** AWS documentation of a `?lifecycle-configuration` query string; AWS distinguishes the generations by request/response *shape*. The premise that `?lifecycle-configuration` is a second subresource is `UNVERIFIED`. MinIO likewise registers only `lifecycle` (`cmd/api-router.go:420-423`).

## 2. Filter grammar

- **An empty `<Filter/>` is valid.** "If the `Filter` element is left empty, the Lifecycle Rule applies to all objects in the bucket." ([LifecycleRuleFilter](https://docs.aws.amazon.com/AmazonS3/latest/API/API_LifecycleRuleFilter.html)); "You can specify an **empty filter**, in which case the rule applies to all objects in the bucket." ([Lifecycle configuration elements](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html)) — direct. An *absent* `<Filter>` is equally "everything" in MinIO: the gate is `if r.Filter.set { return r.Filter.Validate() }; return nil` (`internal/bucket/lifecycle/rule.go:86-105`, gate at `:101-102`), and MinIO's quickstart ships an `ExpiredObjectDeleteMarker` rule with no `Filter` at all ([`docs/bucket/lifecycle/README.md` §3.3](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/docs/bucket/lifecycle/README.md)) — direct.
- **Exactly one predicate at the `Filter` level.** "A `Filter` can have exactly one of `Prefix`, `Tag`, `ObjectSizeGreaterThan`, `ObjectSizeLessThan`, or `And` specified." ([LifecycleRuleFilter](https://docs.aws.amazon.com/AmazonS3/latest/API/API_LifecycleRuleFilter.html)) — direct; `LifecycleRule` repeats "must have exactly one" ([LifecycleRule](https://docs.aws.amazon.com/AmazonS3/latest/API/API_LifecycleRule.html)) — direct.
- **So size predicates are *not* legal siblings of `Prefix`/`Tag`.** Combining any two predicates is refused; the wrapper is `And`: "When using more than one filter, you must wrap the filters in an `<And>` element." ([Adding filters to Lifecycle rules](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-filters.html)) — direct. A single size predicate alone is fine (`<Filter><ObjectSizeGreaterThan>500</ObjectSizeGreaterThan></Filter>`, same page) and a size *range* needs `And` (same page) — direct. MinIO agrees and enforces it: `internal/bucket/lifecycle/filter.go:151` `Validate`, rejecting `predCount > 1` with `errInvalidFilter` at `filter.go:190`, with the comment "Note: S3 supports empty <Filter></Filter>, so predCount == 0 is valid" at `filter.go:188-189`. This contradicts LC8 (§9.1).
- **`And` requires two or more predicates.** "This is used in a Lifecycle Rule Filter to apply a logical AND to **two or more** predicates." ([LifecycleRuleAndOperator](https://docs.aws.amazon.com/AmazonS3/latest/API/API_LifecycleRuleAndOperator.html)) — direct. MinIO copies the sentence into the source and enforces `predCount < 2 → errXMLNotWellFormed` (`internal/bucket/lifecycle/and.go:42-60`, the check at `:58`) — direct.
- **At most one prefix, tags with unique keys.** "A filter can have only one prefix, and zero or more tags." / "When you specify multiple tags in a filter, each tag key must be unique." ([Lifecycle configuration elements](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html)) — direct. Matching is exact on key and value, and an object with extra tags still matches (same page) — direct.
- **Refused combinations (documented):**
  - `AbortIncompleteMultipartUpload` in a rule with a tag filter: "You can't specify this lifecycle action in a rule that has a filter that uses object tags." ([Lifecycle configuration elements](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html)) — direct.
  - `ExpiredObjectDeleteMarker` in a rule with a tag filter: same sentence set, same page — direct.
  - `ExpiredObjectDeleteMarker` with `Days` or `Date`: "This cannot be specified with `Days` or `Date` in a Lifecycle Expiration Policy." ([LifecycleExpiration](https://docs.aws.amazon.com/AmazonS3/latest/API/API_LifecycleExpiration.html)) — direct.
  - `NewerNoncurrentVersions` without a `<Filter>`: "To specify the number of noncurrent versions to retain, you must also provide a `<Filter>` element. If you don't specify a `<Filter>` element, Amazon S3 generates an `InvalidRequest` error" ([Lifecycle configuration elements](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html)) — direct.
  - `ObjectSizeGreaterThan` not below `ObjectSizeLessThan`: "the `ObjectSizeGreaterThan` integer must be less than the `ObjectSizeLessThan` value" ([Adding filters to Lifecycle rules](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-filters.html)) — direct.
  - `Days`+`Date` in one `Expiration`: not documented as refused, only as two members ([LifecycleExpiration](https://docs.aws.amazon.com/AmazonS3/latest/API/API_LifecycleExpiration.html)) — `UNVERIFIED` for AWS; MinIO refuses it (`internal/bucket/lifecycle/expiration.go:186-187`, `errLifecycleInvalidExpiration`).
- **MinIO's filter error text:** "Filter must have exactly one of Prefix, Tag, or And specified" (`internal/bucket/lifecycle/filter.go:27`) — direct.

## 3. Action semantics

### 3.1 `Expiration.Days` / `Expiration.Date`

- **Rounding.** "Amazon S3 calculates the time by adding the number of days specified in the rule to the object creation time and **rounding up the resulting time to the next day at midnight UTC**. For example, if an object was created on 1/15/2014 at 10:30 AM UTC and you specify 3 days in a transition rule, then the transition date of the object would be calculated as 1/19/2014 00:00 UTC." ([Lifecycle rules: Based on an object's age](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html#intro-lifecycle-rules-number-of-days)) — direct. The same section says "Amazon S3 maintains only the last modified date for each object … the creation date is synonymous with the **Last modified** date" — direct, which is what LC10 assumes.
- **`Date` must be midnight UTC.** "The date value must conform to the ISO 8601 format. The time is always midnight UTC." ([Lifecycle rules: Based on a specific date](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html#intro-lifecycle-rules-date)) — direct for the requirement. Whether AWS *rejects* a non-midnight `Date` is `UNVERIFIED`; MinIO rejects it (`internal/bucket/lifecycle/expiration.go:85-87`).
- **A past date is accepted.** "If you specify an S3 Lifecycle action with a date that is in the past, all qualified objects become immediately eligible for that lifecycle action." and "the date-based action is not a one-time action. Amazon S3 continues to apply the date-based action even after the date has passed, as long as the rule status is `Enabled`." (same section) — direct. The design's "expires on the next pass" is a timing deviation, not a validation one.

### 3.2 `ExpiredObjectDeleteMarker`

- **May not coexist with `Days`/`Date`.** "This cannot be specified with `Days` or `Date` in a Lifecycle Expiration Policy." ([LifecycleExpiration](https://docs.aws.amazon.com/AmazonS3/latest/API/API_LifecycleExpiration.html)) — direct. MinIO enforces the same rule first in `Expiration.Validate` (`internal/bucket/lifecycle/expiration.go:171-179`, check at `:177`, `errLifecycleInvalidDeleteMarker`) — direct.
- **What it removes.** "Indicates whether Amazon S3 will remove a delete marker with no noncurrent versions. If set to true, the delete marker will be expired; if set to false the policy takes no action." (same page) — direct. Scoped to versioning-enabled buckets: "In a versioning-enabled bucket, a delete marker with zero noncurrent versions is referred to as an *expired object delete marker*." ([Lifecycle configuration elements](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html)) — direct.
- **Refused on unversioned/suspended buckets?** Not stated anywhere I read — `UNVERIFIED`; the documented failure mode is inert.
- **Tag-filtered rules cannot use it** — §2 (direct).

### 3.3 Overlapping rules

- `Expiration` vs `Expiration`: "if two expiration policies overlap, **the shorter expiration policy is honored** so that data is not stored for longer than expected." ([How Amazon S3 handles conflicts](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-conflicts.html)) — direct. This is the source for LC10's "earliest applicable expiry … wins"; the page's Example 3 (overlapping prefixes, 10-day vs 365-day transition) picks 10 days — direct.
- Across action kinds: "An object is eligible for only one S3 Lifecycle action per day. When multiple rules match, Amazon S3 applies the least costly action." plus "Permanent deletion takes precedence over transition. Transition takes precedence over creation of delete markers." ([Expiring objects](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html), detail on [conflicts](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-conflicts.html)) — direct. AWS's rule is therefore earliest-wins for two expirations and cost-ordered across kinds.
- **Noncurrent and abort actions:** no rule-specific precedence statement exists — `UNVERIFIED`; only the general "least costly" wording applies (inference).

### 3.4 Versioned buckets: does `Expiration` add a second delete marker?

- Positive case: "Versioning-enabled bucket – **If the current object version is not a delete marker**, Amazon S3 adds a delete marker with a unique version ID. This makes the current version noncurrent, and the delete marker the current version." ([Expiring objects](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html)) — direct.
- Decisive negative case, on two pages: "**Amazon S3 doesn't take any action if there are one or more object versions and the delete marker is the current version.**" ([Lifecycle configuration elements](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html), [Expiring objects](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html)) — direct. A marker that is the *only* version is handled as an expired object delete marker: "Amazon S3 removes the expired object delete marker" (same pages) — direct.
- MinIO implements the same shape structurally: the only block that can emit `DeleteAction` is guarded `if obj.IsLatest && !obj.DeleteMarker` (`internal/bucket/lifecycle/lifecycle.go:452`), so a latest marker can never reach the `DeleteObject` path; markers instead fall to `ExpiredObjectDeleteMarker` (`lifecycle.go:365-395`) or to MinIO's own `DelMarkerExpiration`. MinIO docs: "MinIO AIStor does not expire `DeleteMarkers` *even if* no other versions of that object exist." ([Object Lifecycle Management](https://docs.min.io/aistor/administration/object-lifecycle-management/)) — direct.
- **Verdict on LC2:** confirmed. S3 does not stack a second marker on a due key whose current version is already a marker.
- Versioning-suspended: "the lifecycle action creates a delete marker with null version ID, which becomes the current version. If the version ID of the current version of the object is null, the Expiration action permanently deletes this version." ([Lifecycle actions and bucket versioning state](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html#lifecycle-actions-bucket-versioning-state)) — direct.

### 3.5 `NoncurrentVersionExpiration`

- **Basis.** "To determine the number of days an object is noncurrent, Amazon S3 looks at when its successor was created. Amazon S3 uses the number of days since its successor was created as the number of days an object is noncurrent." ([How Amazon S3 calculates how long an object has been noncurrent](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html#non-current-days-calculations)) — direct; the arithmetic is the same midnight-UTC rounding applied to "the time when the new successor version of the object is created" (same page). LC10's `became_noncurrent_at` basis is confirmed.
- **`NewerNoncurrentVersions` range and interaction.** "you can also specify the number of noncurrent versions (`<NewerNoncurrentVersions>`) to retain (**between 1 and 100**) … Amazon S3 will permanently delete any additional noncurrent versions beyond the specified number to retain. **For the deletion to occur, both the `<NoncurrentDays>` and the `<NewerNoncurrentVersions>` values must be exceeded.**" ([Lifecycle configuration elements](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html)) — direct; the versioning table repeats it as "exceeds both" (same page) — direct.
- **Unversioned bucket:** the table cell reads "NoncurrentVersionExpiration **has no effect**." ([same table](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html#lifecycle-actions-bucket-versioning-state)) — direct. So it is **not refused at PUT** (inference, since no refusal is documented); suspended buckets behave "Same behavior as a versioning-enabled bucket".
- MinIO accepts `NewerNoncurrentVersions` **with no `NoncurrentDays`** as a deliberate extension — "This is available only on MinIO as an extension to the NewerNoncurrentVersions feature … Note: This rule has an implicit zero NoncurrentDays, which makes the expiry of those 'extra' noncurrent versions immediate." ([`docs/bucket/lifecycle/README.md` §3.2.a](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/docs/bucket/lifecycle/README.md)) — direct; the validator only refuses *both* being zero (`internal/bucket/lifecycle/noncurrentversion.go:81-96`, check at `:87`) — direct.

### 3.6 `AbortIncompleteMultipartUpload`

- **Basis is initiation.** "Specifies the days since the initiation of an incomplete multipart upload that Amazon S3 will wait before permanently removing all parts of the upload." ([LifecycleRule](https://docs.aws.amazon.com/AmazonS3/latest/API/API_LifecycleRule.html)) — direct. "direct Amazon S3 to stop multipart uploads that aren't completed within a specified number of days **after being initiated** … it becomes eligible for an abort operation." ([Configuring a bucket lifecycle configuration to delete incomplete multipart uploads](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpu-abort-incomplete-mpu-lifecycle-config.html)) — direct.
- **Nothing re-bases the clock on part activity.** Initiation is the only documented clock — so LC10's "counts from `initiated_at`, deliberately not the sweeper's `max(initiated_at, latest part mtime)`" is supported by the documented basis (direct) and by the absence of any part-activity wording (inference).
- **Does S3 abort an upload that is still receiving parts?** Not documented. The rule "applies to both existing multipart uploads and those that you create later" and an upload becomes "eligible" once past the window (same page) — direct; the in-flight case is `UNVERIFIED`.
- It deletes only upload parts: "this action doesn't apply to objects. No objects are deleted by this lifecycle action." (same page) — direct.
- **Tag filter refused** — §2.

## 8. MinIO: why the scanner, and its pacing

- **A MinIO design document states the cycle explicitly.** "MinIO scanner (which runs at one minute intervals, each time scanning one sixteenth of the namespace), picks up the object for tiering." ([`docs/bucket/lifecycle/DESIGN.md:10`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/docs/bucket/lifecycle/DESIGN.md#L10)) — direct.
- **The documented rationale is workload priority, not correctness.** "MinIO AIStor uses a built-in scanner to actively check objects against all configured lifecycle management rules. The scanner is a low-priority process that yields to higher-priority workloads, so that rule timing does not cause performance spikes. **The scanner may therefore not detect an object as eligible for a configured transition or expiration lifecycle rule until after the lifecycle rule period has passed.**" ([Object Lifecycle Management](https://docs.min.io/aistor/administration/object-lifecycle-management/)) — direct. No MinIO document argues against request-path evaluation; for MPUs the maintainer dismissed the AWS action outright — "It's the most useless feature in AWS S3" ([minio#19115](https://github.com/minio/minio/issues/19115)) — direct.
- **Cycle and pacing in the code.** `scannerCycle = uatomic.NewDuration(dataScannerStartDelay)` with `dataScannerStartDelay = 1 * time.Minute // Time to wait on startup and between cycles.`; each pass is `objAPI.NSScanner(...)` after the timer fires, and folders are skipped unless they carry active rules — "A leaf is only scanned once every `dataUsageUpdateDirCycles` [16], rarer if the bloom filter for the path is clean **and no lifecycles are applied**"; per-folder/per-object waits come from `scannerSleeper` (`newDynamicSleeper`) and `dataScannerSleepPerFolder = time.Millisecond` (`cmd/data-scanner.go`, top-of-file constants and `runDataScanner`). Rule applicability per prefix is `f.oldCache.Info.lifeCycle.HasActiveRules(prefix)`, and `HasActiveRules` itself tests `rule.Expiration.Date.Before(time.Now().UTC())` for date rules (`internal/bucket/lifecycle/lifecycle.go`).
- **Consequence for LC12/LC22:** MinIO's design is the trade the design document accepts — a stateless walk whose "due" test is re-derived every pass, with a machine-wide worker ceiling and a dropped-task counter instead of per-object backpressure (§5). Inference.

## 9. Corrections to the design document

### 9.1 Contradicted

1. **LC8, `Filter` shape.** Written: "an **empty** filter (everything), `Prefix`, `Tag`, or `And` — and `ObjectSizeGreaterThan`/`ObjectSizeLessThan` **both as siblings of `Prefix`/`Tag` and inside `And`**." AWS: a `Filter` "can have exactly one of `Prefix`, `Tag`, `ObjectSizeGreaterThan`, `ObjectSizeLessThan`, or `And` specified", and combining predicates requires `And` ([LifecycleRuleFilter](https://docs.aws.amazon.com/AmazonS3/latest/API/API_LifecycleRuleFilter.html), [filters guide](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-filters.html)); MinIO enforces the same (`internal/bucket/lifecycle/filter.go:190`). **Correction:** a size predicate may appear alone at `Filter` level or inside `And`, never beside `Prefix`/`Tag`; size *ranges* require `And`. The design's "the framework's documented one, because `aws s3api` emits all of it" misreads the shape — the SDK's optional members are not co-legal.
2. **LC8, size bounds.** Written: "sizes within `0..=5 TiB`". AWS: "Maximum filter size is 50 TB" ([filters guide](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-filters.html)); the object ceiling is "48.828125 Terabytes" ([quotas](https://docs.aws.amazon.com/general/latest/gr/s3.html)). **Correction:** 50 TB (or the object ceiling), not 5 TiB — 5 TiB is the *old* S3 single-object limit. The matrix also omits AWS's rule that `ObjectSizeGreaterThan` must be below `ObjectSizeLessThan`.
3. **LC8, "exactly one non-empty action set per rule".** AWS allows several actions in one rule — the documented `GET` sample carries two `<Transition>` and one `<Expiration>` in one `<Rule>` ([GetBucketLifecycleConfiguration](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetBucketLifecycleConfiguration.html)) — and MinIO's `Rule::Validate` requires only *at least one*. **Correction:** if the intent is "at least one", say so; if it is literally one action kind per rule, it is stricter than both AWS and MinIO and will reject configurations both accept.
4. **LC8, missing refusals.** The matrix has no entry for either documented refusal: `AbortIncompleteMultipartUpload` and `ExpiredObjectDeleteMarker` "can't [be] specify[ied] … in a rule that has a filter that uses object tags" ([Lifecycle configuration elements](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html)), and `ExpiredObjectDeleteMarker` "cannot be specified with `Days` or `Date`" ([LifecycleExpiration](https://docs.aws.amazon.com/AmazonS3/latest/API/API_LifecycleExpiration.html)). **Correction:** add both to the refusal matrix, or record them as accepted deviations.

### 9.2 Confirmed (one line each)

5. **LC2 — a due key whose current version is a delete marker is skipped.** Confirmed by AWS ("Amazon S3 doesn't take any action if there are one or more object versions and the delete marker is the current version") and structurally by MinIO (`internal/bucket/lifecycle/lifecycle.go:451-452`). The design's *reason* is its own; the *behaviour* is AWS's.
6. **LC8 — empty `<Filter/>` applies to everything.** Confirmed by the API type, the user guide, and MinIO's `filter.go:188-189`/`:197`; an absent `<Filter>` behaves the same (`rule.go:101-102`).
7. **LC8 — `And` needs at least two predicates.** Confirmed verbatim ("two or more predicates"); MinIO's `and.go:58` encodes it.
8. **LC8 — IDs optional on the wire, unique within one configuration.** Confirmed ("Required: No"; "uniquely identifies a rule within a bucket's lifecycle configuration"). The specific `InvalidRequest` code for a duplicate is `UNVERIFIED`.
9. **LC8 — `Days ≥ 1`.** Confirmed ("must be a non-zero positive integer").
10. **LC8 — a `Date` at midnight UTC.** Confirmed ("The time is always midnight UTC"); MinIO enforces it at `expiration.go:85-87`.
11. **LC8 — a past `Date` is accepted.** Confirmed ("all qualified objects become immediately eligible"). "Expires on the next pass" is a timing deviation, not a validation one.
12. **LC8 — 1,000 rules; `Enabled`/`Disabled`.**
13. **LC10 — `Expiration.Days` from last-modified, rounding forward to midnight UTC.** Confirmed by AWS's rounding paragraph and `ExpectedExpiryTime` (`lifecycle.go:531-537`).
14. **LC10 — `NoncurrentDays` from `became_noncurrent_at`.** Confirmed ("looks at when its successor was created"; `SuccessorModTime` in `lifecycle.go:413`).
15. **LC10 — MPU clock from `initiated_at`, not last part activity.** Supported: initiation is the only documented basis.
16. **LC10 — earliest applicable expiry across matching enabled rules.** Confirmed for expirations ("the shorter expiration policy is honored"); across action kinds AWS orders by cost (permanent deletion > transition > delete marker), which MinIO's comparator reproduces.
17. **§The S3 surface — `GET` without a configuration is `NoSuchLifecycleConfiguration`.** Confirmed (404 at AWS; 404 with the same code in MinIO).
18. **LC9 — transitions refused.** Not an AWS or MinIO behaviour: AWS accepts transitions, MinIO accepts them once the tier resolves. No correction needed, but it should be labelled a deliberate local-only deviation rather than something implied by the framework.
19. **`PutBucketLifecycleConfiguration` returns 200 with an empty body.** Confirmed; the design does not state the body, and it is nothing plus one informational header.

### 9.3 Not supported / unverifiable in the design's terms

20. **§A2's premise (`?lifecycle-configuration` as a distinct subresource)** — `UNVERIFIED`; every AWS page read uses `/?lifecycle` for both generations, and MinIO registers only `lifecycle`. If `s3s` 0.17 registers a second query string, that is the framework's choice, not AWS's documented surface.
21. **LC8's "at most 10 tags"** — `UNVERIFIED` as a *filter* limit; 10 is the object tag cap, and a filter with more than 10 tags is unsatisfiable rather than documented-invalid. Neither AWS nor MinIO refuses it (MinIO rejects only duplicate keys).
22. **Error codes generally.** Conditions are documented, codes mostly are not; `NewerNoncurrentVersions`-without-`Filter` is the one documented `InvalidRequest`.
23. **Maximum configuration size** — no AWS-documented limit found; the design's silence is safe, any stated number would be `UNVERIFIED`.
24. **Checksum on tinio's `PUT`.** AWS requires one (algorithm-agnostic today); MinIO requires `Content-MD5` specifically. The design says nothing, and this is an interop decision worth taking explicitly: modern SDKs send `x-amz-sdk-checksum-algorithm` + CRC32 and *not* `Content-MD5` (§1.1, §4).
25. **`ExpiredObjectDeleteMarker` on an unversioned/suspended bucket** — no source states refusal or acceptance; the documented effect on an unversioned bucket is inert.

**Object Lock is a veto, not an action.** `object_lock.rs` only answers "is this object locked" — legal hold `ON`, a `GOVERNANCE`/`COMPLIANCE` retain-until in the future, or a bucket default retention; malformed metadata fails **closed** ("A configured default retention with missing or malformed input is treated as locked so a lifecycle worker cannot turn incomplete metadata into an unsafe delete", `crates/lifecycle/src/object_lock.rs:48-51`). There is no retention-expiry action.

**Port residue is marked with `allow`, not `todo!()`.** Recurring on `TraceFn`, `TimeFn`, `AMZ_TAG_COUNT`, `AMZ_ENCRYPTION_KMS`, `EVENT_LIFECYCLE_TIER_AUDIT`: `#[allow(dead_code, reason = "MinIO-parity tier/lifecycle entry point that this port never wired (backlog#1823)")]` (`crates/ecstore/src/bucket/lifecycle/bucket_lifecycle_ops.rs:141-172`). Three other markers: `// TODO(GA): Remove ENV_ILM_PROCESS_TIME_DEPRECATED compatibility during GA release.` (`crates/lifecycle/src/core.rs:1113`), `RUSTFS_COMPAT_TODO(backlog-2097-tier-delete-journal-v6)` (`…/tier_delete_journal.rs:110`), and a large commented-out MinIO block left in place (`validate_id`/`validate_status`/`get_prefix`, `core.rs:161-215`). ### 10.3 Rule model and parsing

- **The wire types are `s3s::dto`'s, not a hand-rolled model and not MinIO's Go structs**: `BucketLifecycleConfiguration`, `LifecycleRule`, `LifecycleRuleFilter`, `LifecycleExpiration`, `NoncurrentVersionExpiration`, `Transition`, `NoncurrentVersionTransition`, `DelMarkerExpiration` — imported straight from `s3s::dto` (`core.rs:17-20`), with `s3s = { features = ["minio"] }` supplying MinIO's additions. So XML decoding is the framework's (`s3s`'s derive); the serde/quick-xml mechanics are the framework's and `UNVERIFIED` here.
- **Accepted `Filter` shapes.** An empty filter is valid and means everything: "A filter with no predicate at all stays valid: AWS documents an empty `Filter` as 'applies to every object in the bucket', and rejecting it would break the most common way to write an unconditional rule" (`core.rs:355-358`). Top level allows **at most one** of `Prefix`/`Tag`/`ObjectSizeGreaterThan`/`ObjectSizeLessThan`/`And` (`core.rs:361-372`) — so sizes are siblings of `Prefix`/`Tag` only as an alternative, and inside `And` they may combine. `And` needs ≥2 predicates (`core.rs:377-382`). Legacy top-level `Prefix` and `Filter` are mutually exclusive: "S3 standard: Legacy Prefix and Filter cannot both be present. An empty prefix is treated as 'not set' and is allowed with a Filter" (`core.rs:263-266`).
- **Limits encoded** (all as `const ERR_…` strings answered as `io::Error`): 1000 rules (`core.rs:290`), non-empty rule list, `status` ∈ {Enabled, Disabled}, `Expiration.Days ≥ 1`, `Date` must be **exactly midnight UTC** (`core.rs:414-421`), `Days`+`Date` together refused, `NoncurrentDays ≥ 1`, `DaysAfterInitiation ≥ 1`, `NewerNoncurrentVersions ≥ 0` (negative is "corrupt", see below), rule id non-empty and ≤255, ids unique (O(n²) pairwise scan, `core.rs:520-533`), tag key 1..=128 chars / value ≤256, size bounds non-negative with `greater < less`. **No 5 TiB upper bound and no 10-tag cap** are encoded anywhere I read — `ERR_LIFECYCLE_FILTER_TOO_MANY_PREDICATES` is used *only* for the top-level count, not for tag cardinality (`core.rs:361-372`). This is a real gap against LC8.
- **A negative `NewerNoncurrentVersions` is treated as data corruption, not as "keep everything"**, and this is the one comment in the file that reads like a post-mortem: "A negative count must never be read as 'retain everything': that is how an invalid configuration silently stopped deleting versions (backlog#2201)" (`core.rs:136-140`). Two enforcement points: PUT rejects it (`core.rs:270-276`), and evaluation *skips the whole rule* if it arrives from older persistence (`core.rs:838-855`), with `Evaluator::eval` additionally erroring (`evaluator.rs:150-158`).

### 10.4 Validation on the request path

Validation runs on PUT, in ecstore, and is imported by the S3 use-case layer: `use … lifecycle::bucket_lifecycle_ops::{LIFECYCLE_MALFORMED_XML_ERROR_KIND, enqueue_expiry_for_existing_objects, enqueue_transition_for_existing_objects, run_stale_multipart_upload_cleanup_once, validate_lifecycle_config, validate_transition_tier}` (`rustfs/src/app/bucket_usecase.rs:26-30`). Two error kinds are distinguished deliberately: a schema-shape failure is `MalformedXML`, everything else `InvalidArgument` — "A validation failure that the S3 boundary must answer with `MalformedXML` rather than `InvalidArgument`: the document does not match the published schema shape (wrong number of `Filter` predicates, a one-member `And`)" (`core.rs:126-133`), with `LIFECYCLE_MALFORMED_XML_ERROR_KIND = io::ErrorKind::InvalidData` (`core.rs:134`). Test-side confirmation of the mapping: "The PutBucketLifecycleConfiguration path maps this io::Error to s3_error!(InvalidArgument)" (`core.rs:1478-1480`).

**A PUT also enqueues work**: `enqueue_expiry_for_existing_objects` / `enqueue_transition_for_existing_objects` are called from the same layer, so a new rule does not wait for the scanner cycle to reach already-matching objects.

`NoSuchLifecycleConfiguration` on a GET with no stored config is the expected answer but I did not read the handler body — `UNVERIFIED`.

### 10.5 The evaluator's shape

Not a pure function; a thin struct over the policy, evaluated **per key over the whole version chain**:

```rust
pub struct Evaluator { policy: Arc<BucketLifecycleConfiguration>, lock_retention: Option<Arc<ObjectLockConfiguration>> }
pub async fn eval(&self, objs: &[ObjectOpts]) -> Result<Vec<Event>, std::io::Error>
async fn eval_inner(&self, objs: &[ObjectOpts], now: OffsetDateTime) -> Vec<Event>
```
(`crates/lifecycle/src/evaluator.rs:34-38`, `:110-158`.) It returns **actions with a deadline**, not a due time alone: `pub struct Event { action: IlmAction, rule_id: String, due: Option<OffsetDateTime>, noncurrent_days: u32, newer_noncurrent_versions: usize, storage_class: String, expiry_policy: Option<ExpiryPolicySnapshot> }` (`core.rs:1390-1400`). Trap worth knowing: `Event::default()` sets `due = Some(UNIX_EPOCH)` and `action = NoneAction` (`core.rs:1420-1432`), so `due.is_some()` never means "something is due".

Inputs are all in `ObjectOpts` (`core.rs:1207-1240`): `name, user_tags (a `&`-string form), mod_time, size, version_id, is_latest, delete_marker, num_versions, successor_mod_time, transition_status, restore_ongoing, restore_expires, versioned, version_suspended, user_defined, version_purge_status, replication_status`. Two gates run *after* evaluation, in the evaluator, not the rule engine: `expiration_action_has_valid_target(action, version_id, is_latest, delete_marker)` and `lifecycle_action_waits_for_replication(action)` + `is_pending_replication` — a `Pending`/`Failed` replication status voids a delete (`evaluator.rs:59-70`, `:200-218`).

Single-object entry points exist for the request path (`get`/`head` predictions): `predict_expiration(&self, obj) -> Event` picks the **earliest** date across matching rules (`core.rs:612-663`).

### 10.6 Day arithmetic, version facts, delete markers

- **`Days` is `modtime + days`, then rounded up to the next process boundary** — one function, `pub fn expected_expiry_time(mod_time: OffsetDateTime, days: i32) -> OffsetDateTime` (`core.rs:1083`). `days == 0` short-circuits to `UNIX_EPOCH` ("Return epoch time to ensure immediate expiry"); otherwise `t = mod_time + days * ilm_day_secs()`, then `// Round up to the next processing boundary per S3-compatible Days semantics.` (`core.rs:1121`). The boundary is `RUSTFS_ILM_PROCESS_TIME`, defaulting to the day length, so with defaults one "day" is 86400 s and the rounding is epoch-aligned — i.e. **midnight UTC, but reached by modulo on a tunable interval, not by a calendar**. `RUSTFS_ILM_DEBUG_DAY_SECS` shrinks a day to seconds for tests ("modeled on Ceph RGW's `rgw_lc_debug_interval`", `core.rs:1140-1152`). This is materially different from LC10's plain `midnight_utc(anchor + days)`: same result at defaults, different mechanism, plus a production-accessible knob that changes it.
- **The noncurrent basis is `successor_mod_time`, not a stored `became_noncurrent_at`.** The rule's clock starts at the *newer* version's mod time: `let expected_expiry = expected_expiry_time(successor_mod_time, noncurrent_days)` (`core.rs:974`), and a missing successor means skip-with-log `reason = "missing_successor_mod_time"` ("Skipped noncurrent expiration for incomplete version chain", `core.rs:988-996`). A count-only rule treats `noncurrent_days` as 0 ("every version past the retained count is due as soon as it became noncurrent", `core.rs:968-970`).
- **`NewerNoncurrentVersions` is a running counter, not a stored keep count.** `eval_inner` threads `newer_noncurrent_versions: usize` through the newest-first version list and increments it for every noncurrent version it decides to spare (`evaluator.rs:159-175`); a version is expired only when `retain.is_none_or(|retain| newer_noncurrent_versions >= retain)` (`core.rs:958-962`). The single-object path passes 0 on purpose: "A single-object lookup cannot prove how many newer historical versions survive. Count-dependent actions wait for the complete-group evaluator" (`core.rs:600-603`).
- **A delete-marker-only key cannot get a second marker, structurally.** `expired_object_deletemarker()` is `delete_marker && is_latest && num_versions == 1` (`core.rs:1242-1244`), and `expiration_action_has_valid_target` refuses `DeleteAction` unless `is_latest && !delete_marker`, while `DeleteVersionAction` requires `version_id.is_some() && (!is_latest || delete_marker)` (`core.rs:1270-1285`). A current delete marker therefore resolves to `DeleteVersionAction` (remove the marker) or nothing — never to a `DeleteObject` that would stack a marker. RustFS solves LC2's problem by action-type eligibility rather than by a pre-read of the current version.
- **Overlap resolution is priority-then-deadline, not earliest-date:** eligible expiration always beats transition even when the transition deadline is earlier: "Eligible expiration takes precedence over transition, even when a failed transition has an earlier deadline" (`core.rs:1062-1070`), ranked by `ilm_action_priority_rank` (`core.rs:1300-1310`). `predict_expiration` does use earliest-date, so the *advertised* expiry and the *enforced* expiry can disagree when a transition rule coexists.

### 10.7 What drives enforcement

- **The scanner.** `init_scanner_with_recovery(shutdown_token.clone(), store, enable_scanner)` is the only lifecycle driver started at boot (`rustfs/src/startup_lifecycle.rs:186`); cadence comes from `scanner_cycle_interval()` / `ENV_SCANNER_CYCLE`, with a start delay, a `DynamicSleeper` speed knob, a per-cycle object/duration budget (`ScannerCycleBudget`), and `AbortOnDropHandle` + `CancellationToken` for stop (`crates/scanner/src/scanner.rs:24-40`, `:95-100`).
- **The scanner does not delete; it enqueues into an expiry worker pool.** `pub struct ExpiryState { tasks_tx: Vec<Sender<Option<ExpiryOpType>>>, tasks_rx: …, stats: Arc<ExpiryStats>, recovery_notify: Arc<Notify> }` (`bucket_lifecycle_ops.rs:1034`). Work is sharded by hash: `get_worker_ch(h) = tasks_tx[h % len]`, where `h = xxh64(sha256(bucket‖key))` (`:1176-1181`, `:334-341`). Queue depth is `EXPIRY_WORKER_QUEUE_CAPACITY = 1000` per worker (`:124`); pool size comes from `ENV_MAX_EXPIRY_WORKERS` (imported at `:87-90`) and is live-resizable via `resize_workers(n, api)`, which spawns workers up to `n` and drains the tail with a `None` sentinel (`:1219-1245`). Task kinds are downcast in the worker loop: `ExpiryTask`, `NewerNoncurrentTask`, `Jentry` (tier-delete journal entry), `FreeVersionTask` (`:1260-1400`).
- **Stop and saturation are explicit.** The worker `select!`s on `cancel_token.cancelled()` from `ctx.background_cancel_token()` and breaks with `state = "stopped", reason = "shutdown_signal"` (`:1247-1262`). A full queue is counted, not retried: `missed_expiry_tasks` plus `EVENT_LIFECYCLE_NOT_ENQUEUED … reason = "queue_full"` (`:1140-1150`). The observability shape is worth copying: pending/active/workers/missed as gauges, with a comment explaining why the counters must not saturate at zero ("Clamping that transient -1 to 0 turns the later +1 into a phantom task that never drains (rustfs#7921)", `:470-476`).
- **Pacing** is the scanner's own: per-object work is bounded by the cycle budget and the dynamic sleeper, not by a per-object sleep in the lifecycle engine. There is no `delay` knob of the kind LC22 proposes.

### 10.8 Durability: three different things, only one of which is an audit

1. **The configuration is not in a table.** It lives inside the bucket metadata record: `metadata.lifecycle_config: Option<Arc<BucketLifecycleConfiguration>>` plus the raw `lifecycle_config_xml`, read through `BucketMetadata`/`metadata_sys` under a *bucket incarnation* check — "if !metadata.bucket_incarnation_sidecar || metadata.bucket_incarnation_id != bucket_incarnation_id { return Err(…'bucket lifecycle metadata is not authoritative') }" (`crates/ecstore/src/bucket/lifecycle/metadata_boundary.rs:36-46`). A missing parsed config with a non-empty raw XML is a hard error, not a silent `None` ("persisted bucket lifecycle configuration is invalid", `:75-77`). Re-create invalidation is handled by the incarnation id, which is the mechanism that answers LC19's "a new bucket must not inherit stale rules".
2. **`bucket_lifecycle_audit.rs` is not a durable audit ledger — it is the S3 notification emitter.** The whole file maps an action plus the source marker (`LcEventSrc::{Scanner, Heal, Decom, Rebal, S3PutObject, …}`, `:28-40`) onto `EventName::LifecycleExpiration*`/`ObjectTransition*` and calls `send_event(EventArgs{ … })` (`:143-152`). It carries no storage of its own. One comment is a real lesson in "no error is not success": the disk layer "skips an absent version and reports success … so a batch entry for a version that was already gone comes back indistinguishable from a committed delete" (`:96-104`), which is why an event is gated on `deleted.found && !deleted.source_missing` rather than on `Ok(())`.
3. **`durable_namespace.rs` is the real durability layer: 12 namespaces, all under `ilm/` in the meta bucket, each with a prefix and a max record size**, declared as `pub(crate) const DURABLE_ILM_NAMESPACES: [DurableIlmNamespace; 12]` (`…/durable_namespace.rs:140-153`): `tier-delete-journal`, `tier-delete-journal-v6`, `tier-delete-dispatch-manifest`, `transition-transaction`, `tier-probe-intent`, `manual-transition-{job,scope,task,worker-result}`, `recovery-{control,export,disposition}` (`:56-133`). Every record is validated before use — `classify_durable_ilm_record` / `validate_durable_ilm_record`, a `DurableIlmRecordCheckpoint` carrying `content_sha256` + `identity_sha256` + `committed`, and `#[serde(deny_unknown_fields)]` throughout (`:171-220`). **What failure it prevents:** a record that no longer matches its own digest, or that was written by a build with a different schema, cannot be replayed into a destructive action; and a namespace's max size bounds how much a corrupt object can make a recovery pass read.
4. **`legacy_transition_state_reconcile.rs` repairs metadata written before the transition-version-state field existed**, and its header states the invariant: "Exact, generation-conditional reconciliation of legacy transition metadata. Repairs are monotonic and never use metadata rollback or remote deletion." (`…/legacy_transition_state_reconcile.rs:16-18`). It is a *targeted operator call*, keyed by `(bucket, object, version_id)` with `"null"` accepted for the unversioned case, and it fences on a fleet proof (`acquire_legacy_transition_state_reconcile_fleet_proof`, `:30-37`). It exists because a "we do not know if the remote copy is gone" state cannot be resolved by guessing.

**The asymmetry that matters for tinio:** expiry itself is *not* journaled. The expiry queue is in-process only (`ExpiryState`, tokio channels), a restart re-derives work from the listing, and the counters exist to make losses visible rather than to replay them. Journals appear only where an **external side effect** is not re-derivable: remote tier deletes, in-flight transitions, operator batch jobs.

### 10.9 The journal design, quoted

- `// v6 is the first transaction journal whose Committed state is allowed to be the sole remote-cleanup owner. Readers capped at v5 reject this version and therefore cannot bypass the all-pool live-source proof during a rolling upgrade or downgrade.` then `const TIER_DELETE_JOURNAL_SOLE_OWNER_VERSION: u8 = 6;` (`tier_delete_journal.rs:106-112`).
- Shape: `TIER_DELETE_JOURNAL_VERSION: u8 = 2`, then per-generation constants v3 (exact version), v4 (state), v5 (transaction), v6 (sole owner) — the journal format has been extended **four times without a rewrite**, with a version fence per generation and downgrade rules written down (`:101-112`).
- Recovery is a paced loop, not a startup pass: `DEFAULT_TIER_DELETE_JOURNAL_RECOVERY_LIMIT = 8` per page, loop interval 60 s, pass budget 240 s, per-entry 90 s, remote deadline 30 s, concurrency 4 (`:75-90`) — with the reason stated: "Keep one page small enough that slow remote tiers remain bounded by per-entry deadlines and worker concurrency. A production pass may consume multiple successful pages while its wall-clock budget remains." (`:75-77`).
- Two recovery loops are started lazily once per process (`TIER_FREE_VERSION_RECOVERY_STARTED`, `MANUAL_TRANSITION_JOB_RECOVERY_STARTED`, `RECOVERY_DISPOSITION_MAINTENANCE_STARTED`, `bucket_lifecycle_ops.rs:180-184`), take a **leader lock** (`"tier-free-version-recovery/leader.lock"`, `:118`), and back off with jitter between 60 s and 10 min (`:114-117`).
- Additive-only rule: `TIER_DELETE_DISPATCH_*` and the "chunked parent" manifest add a *new* namespace rather than changing the old one, with another `RUSTFS_COMPAT_TODO(backlog-2133-tier-delete-chunk-parent)` recording when the old reader may be deleted (`:113-119`).

### 10.13 Lessons for tinio

**Copy:**
1. **A pure model+evaluator crate with zero storage deps** — `crates/lifecycle`, `Evaluator::eval(&[ObjectOpts]) -> Vec<Event>`. tinio's LC3/LC4 already split this way; RustFS proves the split survives contact with a real implementation, and `object_opts_from_object_info` is the entire cost of the adapter. Take note: pass the **whole version chain** per key (`&[ObjectOpts]`), not one object with a pre-computed keep count — `NewerNoncurrentVersions` needs the scan, and RustFS's "single-object lookup cannot prove how many newer versions survive" is exactly the bug that shape prevents.
2. **Action-type eligibility as the delete-marker guard** (`expiration_action_has_valid_target`): cheaper and more auditable than LC2's "read `current_version` for due keys only", because it removes the read *and* the class of bug.
3. **Distinguish `MalformedXML` from `InvalidArgument` by carrying an `ErrorKind`** (`LIFECYCLE_MALFORMED_XML_ERROR_KIND`): one enum, no string matching at the boundary. tinio's LC8 currently says `InvalidRequest` for everything; the split is one constant.
4. **Fail closed on corrupt persisted rules** — skip the rule, count it, never reinterpret it as "keep forever". Cheap and it is the difference between a stale rule and silent data retention (`retained_noncurrent_versions`).
5. **A queue with visible saturation** (`pending/active/workers/missed` + the "do not clamp the gauge at zero" comment). tinio's LC16 says one log line per pass; the three counters are worth more than the log line and cost three atomics.
6. **Idempotent delete as the only replay mechanism for expiry**, with journals reserved for non-re-derivable side effects. That is the strongest argument for LC12 (stateless pass) and it is what RustFS actually ships: expiry re-derives, remote deletes journal.

**Over-engineering for a single-node local server — do not copy:**
1. **The 12-namespace `ilm/` durable layer, record checkpoints, digest/identity proofs, and four versions of journal format** (`durable_namespace.rs`, `tier_delete_journal.rs`). It exists to make *remote* tier deletes and *fleet* topology changes safe. tinio has no remote archive tier — its cold plane is a database (`docs/superpowers/specs/2026-10-24-tiered-storage-design.md` T1) — and one writer.
2. **Fleet proofs, leader locks, `reserved`/`_diagnostic` namespaces, manual transition job leases** (`recovery_control`, `manual_transition_job`, `rustfs/src/admin/handlers/ilm_transition.rs`): 350 KB of code for an operator-driven data-movement feature tinio does not have.
3. **`ExpiryState`'s sharded worker pool with live resize** (`resize_workers`): an honest single worker with a bounded channel and a stop check is the right size for one root.
4. **A tunable process boundary that changes when a day ends** (`RUSTFS_ILM_PROCESS_TIME`) plus a debug day-length that accelerates deletion. LC10's fixed `midnight_utc` is the better contract; if tests need speed, inject a clock, don't ship an env var that deletes early. RustFS itself can only warn about it.
5. **`Event.due = Some(UNIX_EPOCH)` by default**: an always-present deadline that means "never" is a footgun; return `Option<Event>` or make `due` non-optional.

**Where RustFS disagrees with LC10, and I think RustFS is wrong:** (a) the noncurrent clock is the **successor's mod time**, not a stored `became_noncurrent_at`; a re-write of the current version therefore restarts every older version's clock, which is neither AWS's definition nor tinio's; (b) overlap resolution is **action-priority first, deadline second**, so an eligible transition can beat an earlier expiry; LC10's "earliest applicable expiry wins" is simpler and matches AWS. Keep LC10.

### 10.14 Other notes in the tree

`crates/ecstore/src/bucket/lifecycle/README.md` is a split inventory, and its honest framing is the load-bearing part: "This directory still belongs to ECStore. It is not ready to become a standalone crate because lifecycle workers currently depend on ECStore runtime state, object IO, bucket metadata, replication scheduling, notification/audit sinks, and tier services." It then lists the eight contracts the workers would need (`LifecycleObjectStore`, `LifecycleMetadataStore`, `LifecycleRuntime`, `LifecycleConfigStore`, `LifecycleTagFilter`, `LifecycleObjectLockStore`, `LifecycleReplicationSink`, `LifecycleAuditSink`), forbids the crate move until the imports are gone ("Do not move `bucket/lifecycle` into a new crate while any worker imports `crate::store::ECStore`, `crate::set_disk::SetDisks`, runtime globals, or bucket replication internals directly"), and names the strategy actually used: extract *one* seam at a time while keeping the old call path — which is why `runtime_boundary.rs`, `config_boundary.rs`, `tagging_boundary.rs`, `object_lock_boundary.rs`, `replication_sink.rs` exist ("Current first boundary: `runtime_boundary.rs` centralizes lifecycle access to runtime state while preserving the existing ECStore-backed implementations."). Module-top docs elsewhere state intent the code then keeps: the reconcile file's "Repairs are monotonic and never use metadata rollback or remote deletion", and `tagging.rs`'s "plain re-export: no new crate edge, and no second copy of the parser to drift from the replication contract" (`crates/lifecycle/src/tagging.rs:15-20`) — the same anti-duplication argument tinio makes for reusing its own parsers.
