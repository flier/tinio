## Background

The CLI is the last unimplemented piece of the 001 feature. `crates/tinio-cli/src/lib.rs:52` is a `pub fn run() -> ExitCode { ExitCode::SUCCESS }` placeholder; `crates/tinio-cli/src/commands/mod.rs` is five lines of doc comment; `crates/tinio-api` holds `error.rs` and a ten-line module doc that names the surface it does not have. Everything the CLI must drive already exists, but it exists **inside one example binary**: `crates/tinio-server/examples/serve.rs` hand-parses its own argv, loads the config only when `--config` is passed, resolves the read-only mode by hand, builds `FsStorage`, installs the log subscriber at a hard-coded `Verbosity::Info`, runs the startup repair through `FsCleanup`, spawns the scanner and the sweeper, builds the plane, binds the listener, and prints `listening on <addr>` on stdout.

Three properties of that arrangement are what this design has to replace rather than wrap:

- **It is not reachable by an operator.** The binary that exists is `tinio`, whose `run()` does nothing; the binary that works is an example target that cargo builds only for `--example serve`. The CLI contract's commands (`status`, `stop`, `doctor`), its flags (`--address`, `--daemon`, `--api`, `--log-format`, `--verbosity`, `--no-follow-symlinks`), its exit-code discipline and its storage-root discovery have no implementation at all.
- **It must not be wrapped twice.** The sandbox design fixes the process sequence in its §10 — read the launch payload first, parse arguments, load the configuration, resolve the mode, create the directories, confine or launch, supervise, **then** build the runtime — and `docs/superpowers/plans/2026-09-18-sandbox-p1-linux.md` Task 7 currently owns that restructuring *of the example*. The CLI is the same entry point one step later, so a plan that restructured `serve.rs` first and moved it to the CLI afterwards would write the sequence twice. The operator settled this on 2026-09-20: the CLI takes the entry point now, and P1's task is retargeted at the CLI (decision 1).
- **The management plane does not exist.** `status` and `stop` are thin clients of an API that has no router, no transport, no state file and no client; single-instance enforcement is a property of that same control-channel bind; and the read-only mode's state relocation has an unimplemented half (the api plane's state file, control socket and logs) that `specs/001-s3-local-server/tasks.md:156` (T143) parks here on purpose.

The sandbox work is the other half of the scope. P0 (`tinio-sandbox-core` + the facade + the three platform crates) landed in this worktree on 2026-09-20, and **P1, P2 and P3 have landed since**: `tinio-sandbox-linux`, `-macos` and `-windows` are real backends, the facade's `platform()` resolves each target's own `backend()`, and `tinio_sandbox::backend_available()` answers `true` on all three, so no supported target refuses a confinement request any more. The three request channels (`--sandbox`, `TINIO_SANDBOX`, `[server] sandbox`) are named by the sandbox design's decision 1 and implemented by none of its four plans, and decision 5 requires that until a channel is implemented, a run that uses it **refuses to start** rather than proceeding unconfined. That rule, plus the §10 sequence, plus the exposure set, is exactly the CLI-shaped remainder of the sandbox feature — and it is the part this design finishes, with the confinement itself left to P1/P2/P3.

## Goal

`tinio <command> [DIR]` is the product's entry point, and every channel the contracts promise works through it: `server`/`start` serves a storage root with the flags, precedence and readiness the CLI contract specifies (including a first start that auto-creates a config with generated credentials); `status` and `stop` are thin clients of a real management plane with single-instance semantics; `doctor` diagnoses a directory offline and can repair the private state it may repair; `--read-only` and `--sandbox` compose, with the sandbox resolved through all three of its channels and **failing closed on every channel this build or this platform cannot honour**.

## Non-goals

- **The confinement itself.** P1/P2/P3 fill `tinio-sandbox-linux`/`-macos`/`-windows`. This design wires the channels, the sequence and the exposure set; a target with no backend crate refuses the request (decision 10) exactly as decision 5 of the sandbox design requires — and since the three backends landed (Background), no supported platform is in that class.
- **New S3 behaviour.** The data plane is `DataPlane` as it exists; the CLI changes who drives it, not what it serves.
- **The FR-023 read-only semantics themselves.** They landed in `a46a1d1`. This design implements the three clauses that work deliberately deferred (T143) and nothing else.
- **Repository layout changes to the sandbox crates.** No new sandbox crate, no change to the P0 surface.
- **A `tinio init` command, credential rotation, or any CLI data command.** The contract's "no CLI data commands are provided" stands.
- **`--anonymous` (US3's T087).** `contracts/cli.md:28` lists the flag and `config.md:134` fixes its semantics, but `tasks.md:181` is where the wiring lives and it is still open; this feature declares neither the flag nor `TINIO_ANONYMOUS`, so nothing inert ships. T087 owns the whole of it, including the server side if "no credentials" turns out to need more than the CLI's defaulting helper.
- **The `mem` backend as a CLI default.** `specs/001-s3-local-server/plan.md:186` has one older sentence about "in-memory backend when no directory argument"; `contracts/cli.md:17` — the CLI's own contract — specifies the positional `DIR` **or a walk-up to the nearest ancestor containing `.tinio/`**, with no in-memory fallback. The contract wins: a missing root is a usage error naming the remedy. The `mem` feature stays declared and unused by the CLI (decision 18).

## Decisions

1. **The CLI owns the process entry point, and `examples/serve.rs` retires.** The §10 sequence of the sandbox design lands in `crates/tinio-cli/src/commands/start.rs` (**landed as the directory `crates/tinio-cli/src/commands/start/` — `start/serve.rs` and `start/run.rs` carry the sequence**), `crates/tinio-server/examples/serve.rs` is deleted once the harness drives the `tinio` binary (**since happened: the example is gone and the suites drive `tinio`**), and `docs/superpowers/plans/2026-09-18-sandbox-p1-linux.md`'s Task 7 is retargeted from "restructure the example" to "the CLI's start command consumes the sandbox backend" — a document edit the sandbox set's own Bookkeeping already anticipates ("It disappears when the CLI owns the flag and the example retires"). **Why not keep both**: the §10 sequence orders confinement *before* the runtime exists and therefore lives at a process entry point; two entry points means two copies of that order, and the copy that drifts is the one nobody runs.
2. **`run()` stays synchronous and builds its own runtime.** `pub fn run() -> ExitCode` keeps its signature (the facade binary calls it). Inside, the sequence is: scan `args_os()` for the listener-descriptor element and, if present, read the launch payload from stdin (`adopt`) — **before** any parser sees the argv, because `tinio-sandbox-fd=<n>` is not a flag and clap would reject it; then parse the remaining argv; then dispatch. Step 8 of §10 (`Builder::new_multi_thread().build()?.block_on(...)`) is the only place a runtime is created. **Every command shares that one** *(grilling round 3, over the plans: plan B's sketch had `status`/`stop` building "a small runtime of their own" and `commands/start.rs` building the multi-thread one locally — both are the second runtime this decision exists to forbid, and plan C's "in `lib.rs`" was the same sentence pointing at the wrong function. The runtime is built in `run()`, and `server`, `status`, `stop` and `doctor` all run on it.)*
3. **Argument parsing is `clap` derive with `env` attributes, and the four-level chain is resolved from clap's own provenance.** clap supplies levels 1 and 2 (a flag beats the process environment, and `clap::parser::ValueSource` says which of the two produced each value); level 3 is the `.env` load; level 4 is the config file. `resolve.rs` therefore fills a value from `.env` only when clap reports `DefaultValue` or no value at all, and from the config file only when `.env` did not supply it — which is FR-016's chain expressed once, in one place, instead of a load order that has to be kept in step with the parser. **This is why the `.env` load happens after parsing rather than before it** (§1 step e): the state directory decides where the file is, and the state directory is not known until the mode is resolved, which is not known until the config file is read. Exit codes stay 0/1/2 through the existing `Error::exit_code`; usage errors are clap's, mapped to 2.
    **Amendment, 2026-09-22 (operator ruling): every environment variable is clap's, and the parse is therefore two-pass.** The three exceptions this decision left to `tinio-config::sources` are gone. The boolean switches `--read-only` and `--sandbox` now carry their variable directly (`env = "TINIO_READ_ONLY"` / `"TINIO_SANDBOX"`) with a **custom `value_parser`** plus `num_args(0..=1)` and `default_missing_value("true")`: the action is `Set` rather than `SetTrue`, because `SetTrue` parses through `ValueParser::bool()`, which rejects the `1` the contract documents and the harnesses set, while the custom parser accepts `1`/`true`/`0`/`false` and refuses everything else — the tolerant spelling the old `sources::parse_switch` implemented, now the flag's own. `TINIO_STATE_DIR` and `TINIO_ACCESS_KEY`/`TINIO_SECRET_KEY` became environment-only arguments too (hidden `--state-dir`/`--access-key`/`--secret-key`, `hide = true`: the environment is the documented channel, and a secret typed on a command line is visible in the process table), which supersedes "credentials are not clap arguments" — the credential *pair rule* (both halves or neither, refused by name) survives unchanged and now lives in `resolve`'s fold. `tinio-config` keeps the `.env` loader and the state-dir parser and reads no variable at all.
    The mechanism follows from clap reading the environment **at parse time**: with `.env` living in a directory the mode decides, one parse cannot both answer the mode and see the file. So `lib.rs` parses argv twice — the **discovery** pass answers `DIR`, `--config`, the mode's two channels and `TINIO_STATE_DIR` (the values `.env`'s own location is a function of, and nothing else), `<state dir>/.env` is loaded into the process environment between the passes (dotenvy never overrides an already-set variable, which is what keeps the process environment above the file), and the second pass is the authoritative one whose values and `ValueSource`s the resolution folds. Consequences: `resolve::{Locate, server, for_doctor}` split at that boundary, `locate` runs on the discovery answers alone; `sandbox::plan` names its channel from the second parse's `Provenance::sandbox`; and levels 2 and 3 are **indistinguishable** in that provenance — a `.env` value arrives as an ordinary `EnvVariable` answer, so the file is the third level by when it was read, which `pick`'s doc and `contracts/config.md` now say instead of the old comment claiming the two could be told apart. `service` is the one command the second pass does not serve: it reads no configuration file, so `.env` is not part of its chain and it is dispatched from the discovery parse — a value from a file the served state dir holds must not decide the argv a unit records. A feature-off build keeps `TINIO_SANDBOX` readable under a hidden argument name, because decision 10's fail-closed rule for the variable is a runtime refusal that must not become a silence.
4. **`.env` never selects the read-only mode** *(operator ruling, 2026-09-20)*. The mode is resolved from `--read-only`, the process environment's `TINIO_READ_ONLY` and the root configuration file **only**, because the `.env` file's own path is a function of the mode (`<root>/.tinio/.env` in normal mode, the relocated state dir in read-only mode) and letting it decide the mode closes a cycle. Every other key keeps the full four-level chain — **credentials included** *(round 3, over plan B)*: `TINIO_ACCESS_KEY`/`TINIO_SECRET_KEY` override the config file's `[auth]`, because FR-016 says credentials are configurable through flags, environment, `.env` and the file, and because a first start generates a random pair that nothing else can know. **The `MINIO_*` names are not part of this chain** *(plan-audit round)*: `contracts/config.md:110` lists them as the **data plane's** fallback, and T084 parks their CLI-side wiring, so an earlier draft of this decision that folded them into the overlay was wrong — the CLI reads the `TINIO_*` pair and nothing else. Plan B applies that overlay in its resolution and its harness sets the two variables for the child. This is recorded in `contracts/config.md` beside the read-only section, and it is tested (a `.env` carrying `TINIO_READ_ONLY=1` must not put the run in read-only mode, and must not be loaded from a state dir the mode did not select).
    **Amendment, 2026-09-22 (decision 3's mechanism change): "only" is now enforced by the parse, not by a signature.** The mode is resolved from the **discovery** parse — `--read-only`/`TINIO_READ_ONLY` as clap answered them before the load, with `Provenance::read_only` saying whether it answered at all — plus the root-side config file, and `resolve_mode`'s inputs are exactly that pair. A `.env` line therefore cannot select the mode even in principle: the file it lives in was located from a value that resolution had already produced. The credential half of this decision is unchanged in effect: `TINIO_ACCESS_KEY`/`TINIO_SECRET_KEY` (and `.env`, one level lower) replace the file's `[auth]` pair, still over `MINIO_*`, and the pair is still folded onto the resolved config — only the reading moved, to the two hidden arguments decision 3's amendment records.
5. **`--config PATH` is part of the CLI surface** *(operator ruling, 2026-09-20)*. It overrides config discovery entirely. The contracts' flag list does not have it today, but three consumers already assume it: the example's own parser, the interop harness's fixture injection (`clients.rs:163-171`), and the sandbox design's launcher, whose §3 step 2 does a **targeted single-key probe of the configuration bytes** it must forward without retaining a parse (decision 18 there, `probe_read_only` in P2's plan). Adding it is one line in `contracts/cli.md` and removes a discovery step from the launcher. **The search order when the flag is absent**, first hit wins: `<root>/.tinio/.tinio.toml` → `<root>/.tinio/config.toml` → the state dir's own `.tinio.toml` → the state dir's `config.toml` → auto-create. The third and fourth steps are what make read-only mode coherent rather than special-cased: the state dir *is* `<root>/.tinio` in read-write mode (so they are the first two steps there), and in read-only mode they are the relocated `<home>/.tinio/roots/<hash>/`, which is where an earlier read-only run auto-created the file (`contracts/config.md:9`'s alias rule, `:120`'s creation rule). Auto-create writes `<writable state dir>/.tinio.toml`, never over an existing file, and in read-only mode it never touches `<root>/.tinio/`. **A `--config` that names a file which does not exist is a usage error (exit 2)** — an explicit path is a statement about which file to read, and silently creating one there (credentials included) is the failure mode hardest to notice; auto-create is a property of the discovery path only. Read-only mode adds a hard guard rather than a consequence: `load_or_create` never writes **anything** under the served root in that mode, the explicit path included.
6. **The state directory is a parameter of the management plane, never a derivation inside it.** Read-only mode relocates everything — `state`, socket, `access.log`, `meta.redb` — to `TINIO_STATE_DIR` or `<home>/.tinio/roots/<sha256(canonical root)16>/` (FR-023), so `tinio-api` receives the resolved state dir from its caller and joins its own file names to it. That is what makes T143's third clause ("relocate tinio-api's state file, control socket and logs") a wiring change rather than a second resolver.
7. **The management plane's transport is three-choose-one, enforced after resolution.** `[api.unix]`/`[api.pipe]` (local channel), `[api.http]`, `[api.https]`: exactly one may be enabled, and `--api <URL>` (repeatable, per scheme) replaces the matching subsection, and the presence of **any** `--api` flag disables every transport that flag does not name — so `tinio server /srv/data --api http://127.0.0.1:9001` on a root whose auto-created config enables the local channel yields one transport, not two *(round 2 ruling: the local channel is the tool's default, not the operator's choice, and "HTTP only" is the common intent)*; `--no-api-unix` remains for the case no `--api` flag is given at all, where the config file is the only thing selecting transports. More than one is a startup error; none is a startup error (`contracts/config.md:161-162`). Token rules follow the matrix: on the local channel only `/status` and `/stop` require `X-Tinio-Token`; over TCP **all** endpoints do (`contracts/management-api.md:9-15`).
8. **`/metrics` belongs to the management plane only** *(operator ruling, 2026-09-20: "`/metrics` on localhost, not on the S3 data plane")*. The interim unauthenticated `GET /metrics` on the data-plane listener (F10, `contracts/config.md:160`) is **removed** in the same task that serves it from the management plane, and every artifact that named or scraped it moves with it: the cucumber scenario `crates/tinio-e2e/tests/features/metrics.feature` (tagged `@T075 @SC-008`, which hits the data-plane path today) and `contracts/s3-surface.md`'s data-plane `/metrics` paragraphs. **Authentication follows the bind address** *(round 2 operator ruling)*: the local channel keeps `/metrics` and `/openapi.json` open; a **loopback-bound** TCP transport keeps `/metrics` — and only `/metrics` — open too, while `/status`, `/stop` and `/openapi.json` still require the token there (the scraper's inability to send a custom header is the whole reason, and it does not extend to the API schema; a loopback TCP port is also reachable by every local user, which a mode-0600 unix socket is not); a non-loopback bind requires the token on every endpoint. Because a standard scraper can send only `Authorization: Bearer` and never a custom header, the middleware accepts **`Authorization: Bearer <token>` as an alias for `X-Tinio-Token` on every transport** — that is what makes `contracts/management-api.md:15`'s rationale true instead of aspirational. A plane whose gauges were never attached answers **`404 "metrics are not attached"`** rather than an empty 200 *(round 2 ruling)*: the endpoint's absence is then something a scraper can see, and the contract says so. The contract's token matrix gains the bind-address dimension and its rationale sentence is rewritten in the same task.
9. **Daemon mode is `daemonize` on unix and a detached child on Windows** *(operator ruling, 2026-09-20)*. `daemonize 0.5` is declared under `[target.'cfg(unix)'.dependencies]` so the Windows build never compiles it. Read out of the crate's own source (0.5.0, `src/lib.rs`): `start()` forks twice (`perform_fork` at `:353` and `:377`), the intermediate child exits, the final process calls `setsid` (`:450`), applies `umask` (`:375`), changes the working directory and redirects the three standard streams (`process_stdio`, `:460-482`) — and the **original process exits inside `start()`** with the intermediate child's exit code (`:343`). Because that intermediate child exits `0` unconditionally (`:377-378`), **the operator's exit code is always 0 whenever daemonization itself works**, whatever the daemon does afterwards — and the design's round-1 reading ("the parent exits 0; `state` is how a daemon is found") accepted that. Round 2 changes it, using the fact that `execute()` is the same machinery **without** the exit (`pub enum Outcome { Parent, Child }`, `:186`): it returns the parent its own branch, so the parent can run code and choose its exit code. Three consequences, all settled:

- The three **static** sandbox determinations (feature off / channel not honoured / platform backend still a stub) are evaluated **before** daemonization. They are lookups on the build and the resolved config and need no fork, so the refusal reaches the operator's shell — exit 2, or a startup error naming the platform — instead of being written to a log the operator has not been told to read.
- Daemonization goes through `execute()`, and **the parent stays alive to report**: it waits, bounded at ~10 s, for the `state` file it already knows the location of plus a successful control-channel probe, then prints the readiness event on the operator's stdout and exits 0 — or exits 1 with a message naming the daemon's log file and `tinio status`. `--daemon` therefore means "start in the background and wait for ready", and `contracts/cli.md` says so.
- The daemon runs the real `confine`; a failure there (P1 and later) is logged, which is the only place it *can* be reported once the parent has exited.

So the daemon is fully detached (double fork means it is not even a session leader that could reacquire a controlling terminal), and `--daemon` is handled **after** argument parsing and the root's canonicalisation but **before** confinement and **before** the runtime exists — forking a multi-threaded process is the hazard this ordering avoids. The working directory is set to `/` after the root and state dir have been resolved to absolute paths. Windows uses `std::os::windows::process::CommandExt::creation_flags(DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP)` and re-execs `current_exe()` with `--daemon` stripped, stdio pointed at the log file. Both arms redirect the operational log to `[log] server_log_file`, defaulting to `server.log` (`server.json` under `format = "json"`) **in the state dir**, and the readiness event reaches the operator through the parent's stdout as well as the log file. **The log file is the daemon's own record, and the event stream is the same frames there**; `state` remains the record either way, and this is why daemon mode and systemd are alternatives rather than layers (decision 21).
10. **All three sandbox channels resolve here, and every unhonourable one fails closed.** `--sandbox`, `TINIO_SANDBOX` and `[server] sandbox` are parsed with FR-016 precedence and collapse into one decision whose refusal **names the channel it came from**; a platform whose backend is still `Unsupported` answers a startup error naming the platform — never an accepted-but-inert flag (sandbox design decisions 1 and 5) — **though no supported target is in that class any more**: all three backends have landed, so the refusal is reached only by a target whose `tinio_sandbox::backend_available()` answers `false` (Background's note). **Which of the three the flag is decides what a feature-off build does** *(round 2 operator ruling)*: the `--sandbox` **flag** is compiled out of the clap surface with the feature (an unknown flag is clap's own usage error, exit 2), while `TINIO_SANDBOX` and `[server] sandbox` **still exist and still refuse** at runtime with `Error::Usage` naming the build — they cannot be compiled away, and ignoring them would leave a server running unconfined because of a setting the operator did write. The rule behind the asymmetry, and the reason `[api]`'s keys may be silently ignored in an `api`-off build while these may not: **ignoring a channel is allowed only when ignoring it makes the run smaller (fewer listeners, fewer commands) and forbidden when it makes the run weaker (fewer restrictions).** The exposure set, the launcher/child split and the platform options follow `commands/start.rs`'s reading of §10; the confinement's own behaviour is P1/P2/P3's.
11. **Readiness is an SSE event on stdout, and the contract records it** *(landed; the original text of this decision — the printed line kept "until P1 changes it", and a stdout that is "not yet a protocol channel" — is superseded)*. The serving path writes exactly one frame — `event: listening`, the bound address as a typed field, closed by a blank line — through `crates/tinio-cli/src/events.rs` (`emit`, `ready`, `emit_error`), which is the **only** stdout writer on that path; a startup refusal arrives as an `Error` frame beside the `tinio: …` line stderr carries, so a consumer decoding the stream reports the cause instead of timing out (sandbox design decision 19). `state` and the frame are **ordered, not simultaneous** — decision 12's sequence writes the file before the event, and a launcher platform writes it only once the relay reports readiness, so the frame can precede the file by a few syscalls; `contracts/cli.md`'s "on ready" bullet owns that ordering and the bounded poll a reader owes it — and `--port 0` reports the bound port in both. Every consumer decodes frames: `crates/tinio-e2e/tests/steps/{clients.rs,cli.rs}`, `crates/tinio-server/tests/serve_read_only.rs` (retired on 2026-10-01 — `docs/superpowers/plans/2026-10-01-test-placement-cleanup.md` — its legs are `crates/tinio-e2e`'s `@cli` scenarios), `crates/tinio/tests/lifecycle.rs`, and the sandbox e2e suites read them through `crates/tinio-server/tests/common/mod.rs`. The printed `listening on <addr>` line and the `serve` example that produced it are gone; `contracts/cli.md`'s "on ready" bullet names the frame. Consequence that remains: stdout **is** a protocol channel, so a stray write to it breaks readiness rather than being ignored — which is why one writer is a rule of `events.rs` rather than a convention.
12. **`state` is written after both planes are up and removed on every clean exit path.** Order in `start`: single-instance bind (which is the control-channel bind itself) → startup repair through `Cleanup` → data plane bound → api plane bound → `state` written → readiness event → `READY=1` (decision 21's notification, absent unless systemd asked for it). Graceful shutdown (signal or `POST /stop`) sends `STOPPING=1`, ceases accepting, drains ≤ 10 s, removes the socket and `state`, and exits 0; a second signal exits immediately without draining. This is the CLI contract's text, not a new policy. **One owner for both artifacts** *(round 2)*: `tinio-api` creates the socket (`bind.rs`) and owns the `state` file (`state.rs`), so it is the plane that writes and removes them — exposed to the CLI as `publish(port)` (write `state` at the readiness point) and `shutdown()` (drain, remove socket and `state`); the CLI never joins those file names itself, and the plane's `Drop` is a best-effort backstop for the paths that do not go through `shutdown()`. Both plans had assumed different owners for this, which is why it is written down here. **On a launcher platform the write waits for the child's readiness through the relay, and that wait is bounded with a refusal at the bound** (2026-09-27) — `contracts/cli.md`'s "on ready" bullet owns the bound and the two shapes it distinguishes from a silent child.
13. **`status` and `stop` are thin clients, and `status` answers "stopped" without a server.** Both read `state` from the resolved state dir and speak HTTP to the channel it names; `status` reports `stopped` (exit 1, per the contract) when the file is absent or the probe fails, and `stop` polls until the probe fails or `state` disappears, bounded at ~15 s, reporting unconfirmed exit on timeout.
14. **The doctor reports through three owners and owns no inventory of its own.** `RepairKind::Full` is the private-state half of `doctor --fix`'s scope — the startup items plus meta-orphan reclamation (`tinio-core/src/cleanup.rs:121-145`) — but **not** the stale home root-state-dir GC its own doc promises: that stage is unimplemented and now has its own task, **T144** (`crates/tinio-fs/src/cleanup.rs:14-15`, re-pointed from T076, which is delivered and does not include it), so the CLI keeps the `Full` call and gains the stage for free when it arrives. The meta store's integrity check and fragmentation report are `tinio_fs::database`'s (`check_integrity`; `open`'s `Stats`; `compact_if_needed`, evaluated against `[storage.fs] compact_threshold_percent`), and the stale `state`/control socket are `tinio-api`'s (`bind::reclaim_stale` and `State::remove` — the one probe-then-reclaim implementation `bind_unix` itself calls, in `api` builds only). What the CLI adds is the report type, the human and `--json` renderings, the exit-code mapping, and the checks none of the three performs (root readability/writability unless read-only, config validity, on-disk name validity, symlinks-present-while-disabled, free space, the socket path's length). `--fix` requires a stopped server — the refusal is an `error` finding in the report rather than a bare `Err`, so `--json` still emits a whole document — and never touches user data; `--dry-run` renders exactly what `--fix` would change by running the same plan with `dry_run: true`, and what each mode renders differs (decision 27). Six things round 2 and the doctor-plan grilling fixed in this decision:
- **The exit code is FR-007's, not the contract parenthetical's** *(round 2 ruling)*: `0` = no problems, `1` = warn/error found (with or without `--dry-run`/`--fix`; with `--fix`, findings that remain), `2` = usage error. FR-007's own words are "exit 0 clean / 1 problems", `tasks.md:131` and §10 of this design agree, and a diagnostic that reports a problem while exiting 0 cannot gate anything; `contracts/cli.md:87`'s parenthetical is rewritten in the same task rather than being read as "plain `doctor` always exits 0".
- **The on-disk name checks walk the whole tree.** `contracts/cli.md:83` and T073 both say "including any-depth `.tinio` segments", which is exactly the case a bounded walk misses (the deep `.tinio` is what FR-020 reserves); the report caps how many findings it *lists* per check (the first ~20 plus a count of the rest) in both renderings, so a pathological root cannot produce a huge report while the severity and the exit code stay honest.
- **`--dry-run` and `--fix` are mutually exclusive in the parser** (a usage error), instead of one silently winning.
- **The config check has three outcomes and never creates anything** *(round 2, corrected in the doctor-plan grilling)*: missing → warn (a first `start` would auto-create it), unknown keys or schema-invalid — **half a credential pair included** — → error (`config.md:138` makes a bad key a startup error), and **no credentials at all → warn**, because `config.md:141`'s rule is that a start generates session credentials and prints them once; the earlier "credentials unresolvable → error" read a rule the config reference does not state. `doctor` is offline diagnostics and does not call `load_or_create`. The socket-path-length check joins the state dir with the **root-derived** name (decision 24) and is `#[cfg(unix)]`, since `sun_path` is.
- **The severity mapping is the report's, and the engine only ever says `warn`** *(doctor-plan grilling)*: `FsCleanup`'s single action constructor emits `RepairActionLevel::Warn` for every stage — `Lint`/`Info` exist for other backends — and a stage that *fails* rides the action stream's `Err` side, which the report renders as `error`. Two shapes follow and they are not interchangeable: a leg that **cannot run** (the store is held by another process, the root is unreadable) reports `warn` with `not inspected: <reason>`, because a partial diagnosis must never read as a clean bill; a leg that **does not apply** (no `meta.redb` yet, read-only skipping the writability check) reports `ok` with the reason.
- **`--json`'s shape is a contract, so it has a schema file** *(doctor-plan grilling)*: `contracts/doctor-report.schema.json` pins `{"severity": "ok|warn|error", "findings": [{"check", "severity", "detail"}]}` with `additionalProperties: false`, and an empty report still carries a concrete `"ok"` rather than `null`. The rendering's own test asserts that key set, which is what keeps the implementation and the schema from drifting.
15. **Config discovery, credentials and auto-create live in `tinio-config`, not the CLI.** A new `discover` module resolves the config path (decision 5's order) and loads-or-creates it; `credentials.rs` generates the pair (access key ≥ 16 bytes, secret ≥ 32 bytes, CSPRNG) and the file is written 0600 on unix and ACL-restricted on Windows. The CLI calls one function. This keeps the launcher's targeted probe and the child's re-derivation reading the same code (sandbox design decision 18).
16. **The CSPRNG is `getrandom`, already in the tree.** The lock carries `getrandom` at 0.2/0.3/0.4 (transitively, through rustls-adjacent crates); a direct dependency adds a workspace pin and no new crate. `rand` would work too and is also in the lock, but pulls its own feature surface for one call site.
17. **`tinio-api` gains the features the spec already names.** `openapi` (utoipa with `axum_extras`) and `tls` (tokio-rustls + rustls-pemfile) are crate-internal features per `plan.md:186`, and the facade's `api` feature forwards them; `crates/tinio/Cargo.toml` gains `openapi` and `tls` to its `default` list. Without `tls`, an `https://` `--api` value is a usage error, exactly as `contracts/cli.md` requires.
18. **A missing storage root is a usage error, not an in-memory server.** `tinio server` with no `DIR` walks up to the nearest ancestor containing `.tinio/`; finding none is exit 2 with a message naming the remedy (pass `DIR`). The `mem` feature stays declared; nothing selects it. See Non-goals for why the contract's rule beats `plan.md`'s older sentence.
19. **`status`, `stop` and `doctor` resolve read-only mode the same way the server does, and they look in both places.** They carry the same `--read-only` flag (the contract's own doctor section already says "With `--read-only` (or `[server] read_only = true`), the root-writability check is skipped … and state-dir checks target the home state dir" — the flag table simply omitted it), resolve the mode through decision 4's rule, and `doctor` skips the writability check in that mode. *(Round 2)* The resolution alone is not enough, because the mode is not always derivable: decision 5's auto-create records `[server] read_only` only in a config it **creates**, and it never overwrites an existing file, so a root with a hand-written config that was started with `--read-only` has its server in the relocated state dir while the client's resolution says `<root>/.tinio` — and the client would report "stopped" about a running server, which is the worst failure this command has. So a client that finds no live server in the resolved state dir probes the other candidate (`<root>/.tinio` ↔ `~/.tinio/roots/<hash>/`), reports the one that answered, and names the state dir it read. One consequence to state in the contract: a read-only root has no `.tinio/` of its own (it cannot create one), so the walk-up finds nothing and `tinio server`/`status`/`stop`/`doctor` for such a root require an explicit `DIR`.
20. **Signals are `signal-hook` on unix and `windows-sys` on Windows, with `nix` as the syscall layer underneath** *(operator ruling, 2026-09-20)*. `signal-hook` (0.4.4) registers the handlers and owns the self-pipe; it is the same crate the sandbox design already approved for the macOS launcher's relay, so the tree has one signal mechanism rather than two. `nix` is the **supplement**, not a second signal layer: it carries only the calls `signal-hook` deliberately does not expose (delivering a signal with `kill`, and the process/credential calls the daemon and relay arms need), declared under `[target.'cfg(unix)'.dependencies]` with the smallest feature set that covers them (`signal` + `process`). Windows keeps `SetConsoleCtrlHandler` through `windows-sys` — the spec's ledger already names it for exactly this — because `signal-hook`'s Windows support is CRT-`signal`-based and clears the handler after the first signal, which cannot express the console-close event the CLI contract requires. **Amendment, 2026-09-22: the `nix` supplement was dropped.** Its whole payload in the implemented phase was one line of unit-test code (`raise(SIGTERM)`); the two further calls this decision and the ledger row anticipated — the second-signal fast exit and the daemon/relay process calls — are `std::process::exit` and the `daemonize` crate respectively, so they never existed. `rustix` (already this workspace's syscall crate, already built for `tinio-cli` on unix) expresses the test's call as `kill_process(getpid(), Signal::TERM)` from a `cfg(unix)` **dev**-row; `research.md`'s dependency table carries the replaced row and the behaviour note. `signal-hook`'s half of this decision was unchanged **as of this amendment** — the 2026-09-30 one below is what later moved it. **Amendment, 2026-09-30: the self-pipe is `tinio-cli`'s own, and that is a fix rather than a preference.** `signal-hook`'s iterator wakes it with `libc::send`, which on Linux *is* the `sendto` syscall — the number the confinement's seccomp filter denies outright, with the error the library drops on purpose — so no wake byte ever landed inside a confined run and a confined server ignored `SIGTERM`, `SIGINT` and `SIGHUP` alike (`docs/tests.md`'s WSL2 section recorded the finding). `signal.rs` now registers through `signal_hook::low_level` and wakes a socketpair of its own with a single `write(2)`, which the filter permits — and that registration is this crate's fourth enumerated `#[allow(unsafe_code)]` site, named with its safety argument in `signal.rs`'s own list, where this decision puts the enumeration (a later site is named there rather than exempted); the leg is `confinement.feature`'s `A confined server stops on SIGTERM`. Neither crate is used to *block* on a signal: the handlers flip the same `watch::Sender<bool>` the management plane's `/stop` sends on (decision 12), so there is one shutdown path with three entry points (SIGINT/SIGTERM, Ctrl+C/console-close, `POST /stop`), and a second signal exits immediately without draining.
    **This costs `tinio-cli` its `unsafe_code = "forbid"`, and the exception is enumerated here.** A console handler must be an `unsafe extern "system" fn`, and `windows-sys` is raw bindings, so the crate becomes `unsafe_code = "deny"` with its exceptions enumerated one by one rather than counted — `signal.rs`'s handler and its registration call today, and any later site named in that same list rather than exempted — following the pattern the sandbox design's decision 14 established for the three platform backends and `docs/cargo.md`'s lint rule records. The invariant is the one Windows imposes rather than one this design chooses: the handler runs on a system thread, may not allocate or lock, and does nothing but `send` on a channel that was created before it was registered. If a future reviewer prefers to keep the crate `forbid`, the alternative is the `ctrlc` crate wrapping the same API — a fifth signal dependency against one enumerated unsafe site, and this design takes the site.
21. **systemd integration is `sd-notify`, with a watchdog, and the unit is one text with one author** *(operator ruling, 2026-09-20)*. The unit is `Type=notify` and carries `WatchdogSec=`, and the CLI emits: `READY=1` at the moment it prints the readiness line and writes `state`; `STOPPING=1` when a graceful shutdown begins (the drain window systemd would otherwise not see); `WATCHDOG=1` on a timer at half of `WATCHDOG_USEC` while the run is healthy. **All of it is conditional on the environment systemd provides**: `NOTIFY_SOCKET` absent means every notify call is a silent no-op (the crate's error is ignored, never surfaced as a startup failure), and `WATCHDOG_USEC` absent means no watchdog task exists. The watchdog's honest semantics are stated rather than implied: the timer runs on the serving runtime, so it detects a wedged **runtime** (blocked worker threads stop the timer) and a process that has stopped draining, but a data plane wedged while the runtime is healthy still beats. `--daemon` and systemd are alternatives, not layers — a unit runs the foreground process, so daemon mode sends no notifications (it has no `NOTIFY_SOCKET` from systemd by construction).
    **The unit text is authored once, in this repository, and `tinio service install` passes it through `ServiceInstallCtx::contents`** (decision 22) rather than letting the crate's template write it: that template emits `Type=simple` and no `WatchdogSec=`, under which every notification above would be inert. The same rendered text is what `packaging/tinio.service` shows, and a test asserts the checked-in file equals the template's rendering at the canonical values, so an operator reading the file and a machine installing the service cannot be told different things.
22. **A cross-platform `tinio service` subcommand manages the supervisor** *(operator ruling, 2026-09-20)*: `install`, `uninstall`, `start`, `stop`, `query`, backed by `service-manager` (0.11) and its per-platform backends — systemd on Linux, launchd on macOS, the SCM (`ServiceManagerKind::Sc`) on Windows. `winsw` is rejected on the ground that it needs a wrapper executable we would have to ship. **The label is derived from the root** — `tinio-<sha256(canonical root)[..16]>`, overridable with `--name` — because one machine may serve several roots as several services, which is the same reason the Windows control pipe is name-derived. `--user` selects `ServiceLevel::User` on the unix backends (a systemd user unit or a launchd agent, no elevation) against the default system level (root/Administrator). Platform asymmetry stated rather than flattened: on unix the operator *may* also write a unit by hand — `packaging/tinio.service` is exactly that example — while on Windows the SCM has no file form, so `install` is the only route and there is nothing to keep in step.
    **`--daemon` keeps its own meaning on every platform, including Windows** *(operator ruling, 2026-09-20: both routes coexist)*: it is "run in the background without a supervisor", needs no elevation, and does not survive a reboot. A Windows operator without Administrator rights has no other route, which is why the detached-child arm stays (decision 9). What the two do share is the log redirection — both write the operational log to `[log] server_log_file` in the state dir, because neither has a console.
    **`service` is a new surface and gets the same treatment `--sandbox` gets** *(round 2 ruling)*: the command appears in no contract and no FR today, and three documents actively say the opposite — `contracts/cli.md:42` and `research.md:143` say "no service manager integration in v1", and `research.md:210` lists "a Windows service" as a **rejected** alternative. So `contracts/cli.md` gains a `service` section and flag table (the five verbs, `--name`, `--user`, the derived label, the elevation refusals naming their remedy), the spec gains the corresponding FR, and Bookkeeping records the four text corrections below — the rejected-ledger row gets a dated note rather than a rewrite, because the ledger is a historical record of what was decided and why. The elevation refusals are part of the surface, not an afterthought: `install`/`start`/`stop`/`uninstall` at the system level need root or Administrator, and each failure names the remedy (`--user` on unix, "run as Administrator" on Windows) instead of passing `EACCES` through.
    **The service's in-process half is `windows-service` on Windows and nothing at all on unix.** An SCM-launched process must hand control to the service dispatcher before anything else, report `StartPending` → `Running` at the readiness point (the same instant as `READY=1`), map the STOP/SHUTDOWN/PRESHUTDOWN controls onto the one shutdown channel (decision 12), report `StopPending` for the drain and `Stopped` at the end. On unix the process stays a foreground process and the supervisor does the rest, which is why the service's arguments are the same `server <root> …` argv the operator would type.
23. **`tinio-api` gains no dependency on `tinio-server`; the gauge source is injected.** Plan A's Task 7 proposed exactly that edge (so `tinio-api` could call `tinio_server::metrics`'s setters), and it cannot exist: measured on 2026-09-20 against a minimal two-crate workspace, cargo rejects the cycle at **resolution** time — `error: cyclic package dependency` — even when the optional feature that would activate the reverse edge is off, because `tinio-server` already carries `tinio-api = { optional = true }` (`crates/tinio-server/Cargo.toml:56,105`). So `tinio-api`'s `metrics.rs` defines the **injection point** (the gauge source is supplied by whoever builds the plane — a trait object or a boxed closure), the CLI passes the data plane's source in, and the dependency graph keeps its single direction. §3's phrase "the registry injection point" already meant this; the plan had read it as a call into the other crate. **The shape is `tinio_api::metrics::MetricsSource { fn refresh(&self); fn counts(&self); }` — two side-effecting methods, returning nothing** *(settled while auditing the plan: the first drafts tried to move the counts across the boundary in both directions, and neither can work — the three gauges the scan feeds are `tinio-server` statics that `tinio-api` cannot name, and `tinio-api` has no storage access of its own, so the numbers have nowhere to go but into the gauges, at the caller)* — consumed through `Options::gauges`: `Gauges` refreshes the cheap families on every scrape, and **the storage scan runs in a reader task at `DEFAULT_TTL` and never on a scrape** *(corrected in the plan-audit round)* — a scrape that ran the scan parks one runtime worker per concurrent request until the scan finishes, and `/metrics` is token-free on the local channel and on a loopback bind, so a local flood would take `/stop` and the readiness probe down with it. `counts()` is therefore the reader's call and the handler only reads the registry, which also retires the TTL cache: the cadence and a cache would be one rule with two owners. **`tinio-api` never names `Storage` at all**, because the trait is deliberately dyn-incompatible (`crates/tinio-core/src/storage/mod.rs:23-25`: an associated `Error` plus the `where Self: Storage` category bounds), so the `Arc<dyn Storage>` the plan's first draft carried could not have compiled. The concrete storage type lives in the CLI's adapter, which is also where `tinio_server::metrics::refresh(io: Stats, db: Stats, write_lock: WriteLockStats)` (`Stats` = `tinio_core::pipeline::Stats`) and the three public gauge statics are called.
24. **The unix control socket is named from the root, like the Windows pipe.** `management-api.md:5` derives the pipe name from the root (`tinio-<sha1(canonicalize(root))[..16]>`) and records it in `state` as the source of truth; the unix socket was a fixed `tinio.sock` in the state dir (`config.md:89`). That asymmetry has one consequence and no benefit: two roots sharing a `TINIO_STATE_DIR` — the deployment `config.md:118` exists to allow, since service accounts and containers have no writable home — collide on the socket path, so the second server fails its single-instance bind while serving a *different* root. The unix default becomes `tinio-<sha1(canonicalize(root))[..16]>.sock` in the state dir; `[api.unix] path` still overrides it (relative or absolute), and the resolved absolute path is what `state.control_name` records — clients read the name, they never re-derive it. No automatic fallback for the 108-byte `sun_path` limit: `research.md:56`'s "documented limitation, no workaround" stands (abstract sockets are not portable to macOS), but the bind failure must name the remedy (`[api.unix] path` may be absolute, so it can point at a short directory), and `doctor` reports the resolved path and its length (decision 14).
25. **The TLS test fixtures are committed, and marked test-only.** A self-signed localhost pair under `crates/tinio-api/tests/fixtures/`, with a note beside it that it is test material which must never be used for a deployment. The alternatives buy nothing: `rcgen` is a new dev-dependency whose own generated material then needs tests, and shelling out to `openssl` makes the suite depend on a tool that is not reliably present on Windows. A committed test key is a key with no trust attached to it, and it keeps the TLS legs runnable on every platform.
26. **`doctor` never creates the store it inspects.** The rule is about **creation**, and the probe is what enforces it: the diagnostics pass answers about an *absent* `meta.redb` without opening anything — it stats the file, and stats only — while a store that **is** there is opened by that pass, once, because the integrity check and the fragmentation report it owes cannot be answered without it (`open_store`'s one handle, and `2026-09-20-cli-doctor.md`'s Global Constraints sanction that single open). `--fix` opens it once per pass and hands the handle on to `FsStorage::new_from_db`. (2026-09-23 correction, code-review round: this decision used to read "answers about `meta.redb` without opening it — it stats the file", which is true of the absent case alone and contradicted the plan's own "at most once" clause; what the code never does is open a *missing* store, since that is the open that would create it.) The reason is measured rather than stylistic: `FsStorage::new` and `database::open` both *create* `<root>/.tinio/meta.redb` when it is absent, and an offline diagnostic that writes the root it was asked to inspect is the one behaviour `doctor` must not have (decision 14's "never creates anything" rule, applied to the store). A missing store is therefore `ok` with the reason, never a finding.
27. **`--dry-run` has a job.** A plain `doctor` reports defects only: the proposals the private-state leg would apply render as informational `ok` rows, so a root whose only problem is reclaimable residue still exits 0. `--dry-run` promotes each proposal to a finding, which is why the two modes differ in the exit code and not only in wording, and it is what makes the pair worth having (decision 14's private-state leg is one call one flag apart).

## Design

### §1 The process sequence (one entry point)

```
fn run() -> ExitCode
 1. filter argv: drop a `tinio-sandbox-fd=<n>` element if present; if it was there, `adopt` reads the launch payload from stdin
    -> a confined child: jump to (k) with the adopted listener
 2. parse the remaining argv (clap)                     usage errors -> exit 2
 3. dispatch on the subcommand
    server/start:
      a. resolve the storage root (DIR or walk-up) and canonicalise it
      b. load or create the config (decision 5's order)
      c. resolve the mode: config -> TINIO_READ_ONLY -> --read-only (decision 4)
      d. resolve the state dir (read-only relocates; TINIO_STATE_DIR overrides)
      e. load `<state dir>/.env` and resolve the four-level chain from it (decision 3: clap's
         ValueSource for flags-over-env, `.env` third, the config file last)
      f. sandbox, statically: resolve the three channels and evaluate the refusals that need no
         fork (feature off / channel not honoured / platform backend still a stub) - BEFORE
         daemonize, so the refusal reaches the operator's shell (decisions 10, 23)
      g. `--daemon`: daemonize through `execute()` (decision 9) - after (a)-(f), before any
         thread. The daemon half continues below; the PARENT half stays and does (k)'s probe
         instead: wait for `state` + a control-channel probe, bounded ~10 s, print the
         readiness line, exit 0 - or exit 1 naming the log file and `tinio status`
      h. create the state dir and, in read-write mode, the root (the bind sources must exist)
      i. sandbox, dynamically: build the exposure set and run `confine` (§8)
         - Linux: `Confinement::InPlace`, carry on in this process
         - macOS/Windows: `Confinement::Supervise(child)`, and the launcher stops here
      j. register the signal handlers (decision 20) - before the runtime, so a signal that
         arrives during startup reaches the same shutdown path as one that arrives later
      k. `Builder::new_multi_thread().build()?.block_on(serve(...))`   the only runtime
 4. status | stop | doctor: their own sequences, no confinement, no daemon
```

**Step (f)'s third determination has no supported target left to fire on**: all three backends have landed (Background), so `tinio_sandbox::backend_available()` answers `true` on Linux, macOS and Windows and the refusal guards only a target with no backend crate — the sequence above is otherwise unchanged.

The handler's own body is async-signal-safe by construction: the handler records the signal (one `write(2)` into the socketpair `signal.rs` now owns — decision 20's 2026-09-30 amendment) and the `watch::Sender<bool>` is flipped from ordinary code outside the handler, because the one shutdown path decision 12 describes must not be built on a handler that allocates or locks. `SIGHUP` is registered to a handler that logs and returns (the contract's "ignored and logged"); `SIGPIPE` needs nothing, the Rust runtime already ignores it.

The launcher's own steps are the ones that must **not** run in the child: constructing `FsStorage`, installing the subscriber, and binding anything other than the handed-in listener (sandbox design decision 18 and the shared plan's §4). The child re-derives the same answers from the payload's config bytes, its environment and its filtered argv.

One dependency *feature* is named rather than left to a crate feature, and the distinction is the ruling: `tinio-server = { workspace = true, features = ["acl"] }`, because the serving half's plane selection (`commands::start::plane_for`) needs that crate's identity-backed constructor and its `Identity`/`IdentityFromConfig` names, so a build without them does not compile. The workspace pins `tinio-server` `default-features = false` and a consumer forwards features by name, so a *crate* feature row would leave the branch dead in every graph that does not cooperate — which is exactly what the shipped binary did until the requirement was moved onto the dependency edge. The runtime `caps.acl` check still decides which plane a run gets.

| File | Responsibility |
|---|---|

| `src/router.rs` | `/status`, `/stop`, `/metrics`, `/openapi.json`, the `X-Tinio-Token` middleware, and the transport-aware auth rule (local channel: status/stop only; TCP: all) |

The plane is built around a `watch::Receiver<bool>` shutdown channel that it *sends* on (via `/stop`) and the CLI *listens to*; `DataPlane::serve` already takes the same channel, so "cease accepting, drain ≤ 10 s" is one signal fanning out to two consumers rather than two shutdown mechanisms. The plane also owns the two artifacts decision 12 names — it writes and removes `state` and removes the socket, through `publish(port)` and `shutdown()` — so no other crate joins those file names. `metrics.rs` is an injection point in the sense decision 23 fixes: the gauge source arrives as a parameter, and this crate never names `tinio-server`.

Two facts the contracts fix and the plan must not re-derive: the pipe name is `\\.\pipe\tinio-<sha1(canonicalize(root))[..16]>` (management-api.md:5 — `sha1`, unlike the state dir's `sha256`), and the unix socket's default is `tinio-<sha1(canonicalize(root))[..16]>.sock` in the state dir (decision 24), subject to the 108-byte `sun_path` limit (research.md §8, a documented limitation whose remedy is an absolute `[api.unix] path`, not an automatic fallback). Both names are recorded in `state.control_name`, which is what a client reads.

### §4 The commands and their surfaces

The flag lists, defaults, exit codes and output lines are `contracts/cli.md`'s and are not restated here; what this design adds is where each resolves:

- `server`/`start`: `Args` → the resolution of §1; `--address HOST:PORT` is the Minio-style alias for `--host`/`--port` (host defaulting to `127.0.0.1`); `--port 0` is an ephemeral port whose actual value is printed on the readiness line **and** recorded in `state`; a non-loopback bind prints the startup warning (the `--anonymous` escalation of it belongs to T087, see Non-goals); `--verbosity`/`--log-format`/`--log-file` feed `build_subscriber`, which today is called with hard-coded `Info`/`Text` and gains the `[log]` config plus the flags.
- `status`: reads `state`, probes, prints `running|stopped`, endpoint, root, pid, started time; exit 1 when the root is uninitialised or the probe fails. It resolves its state dir by decision 19 — the mode from `--read-only`/`TINIO_READ_ONLY`/config, then both candidates probed — and names the one that answered.
- `stop`: `POST /stop`, then poll to a ~15 s bound; the same state-dir resolution.
- `doctor`: decision 14; `--json` is a rendering of the same report the human form prints, not a second check pass.

`--read-only`, `--no-follow-symlinks` and `--sandbox` all reach the config's `[server]`/`[storage.fs]`/`[s3]` layer through the same defaulting helper in `resolve.rs`, so a flag and its config key can never be honoured by different code paths; `--read-only` reaches the three client commands too (decision 19). `--anonymous` is **not** part of this feature *(round 2)*: it stays T087's whole — flag, `TINIO_ANONYMOUS` wiring and semantics — because a flag that parses and does nothing is worse than a flag that is not there yet, and `contracts/cli.md` describes the finished product, which T087 completes.

### §5 Config discovery, credentials and auto-create (decision 15)

`tinio-config` gains a `discover` module and a `credentials` module:

```rust
pub fn resolve_path(root: &Path, state_dir: &Path, explicit: Option<&Path>) -> Result<PathBuf, Error>;
pub fn load_or_create(root: &Path, path: &Path, mode: AccessMode) -> Result<(Config, bool /* created */), Error>;
pub fn generate() -> Credentials; // access >= 16 bytes, secret >= 32 bytes, getrandom
```

`load_or_create` takes the root as well as the path, because decision 5's read-only guard is about *where* the file is rather than what it is called: in read-only mode it refuses to write anything under the served root, the caller's explicit path included. The **missing explicit path** is a different failure and is raised one level up, in the CLI's `resolve.rs` — `tinio-config`'s `Error` has no usage variant and §9 keeps the numeric code in exactly one place — so `load_or_create` never sees that case at all.

`load_or_create` writes `version = 1`, the generated `[auth]`, `[server]` with `host`/`port`/`read_only`, `[scanner]` (presence = on), the local channel's platform form — `[api.unix]` on unix, `[api.pipe]` on Windows — and `[storage.fs]`: the shape `contracts/config.md`'s example shows, minus the keys whose absence is the default. Its `[server] read_only` records the mode the run resolved, so a read-only root keeps its mode on the next start and an operator does not have to pass `--read-only` twice. It writes atomically (create-new, 0600) and never overwrites an existing file; a created config's credentials are the ones the run then uses, so a first start is one pass with no restart. In read-only mode it creates under the state dir and logs the path.

### §6 Read-only mode's three deferred clauses (T143)

1. **The root-side config read**: `<root>/.tinio/.tinio.toml` (else `config.toml`) is read in read-only mode when present, never written; `.tinio.toml` wins when both exist; other contents of the root's `.tinio/` are ignored (the metadata store there is not opened).
2. **The `.env` load**: from the state dir, which in read-only mode is the relocated one — after decision 4's mode resolution, never before it.
3. **The api plane's relocation**: `state`, the socket and the logs join `state_dir` in every mode, which decision 6 makes structural rather than conditional.

### §7 The sandbox seam (decision 10)

```rust
// src/sandbox/{mod,plan,confine,product,child}.rs — compiled in every build; the feature gates behaviour, not linkage (decision 10)
pub fn filter_argv(argv: Vec<OsString>) -> Result<(Vec<OsString>, Option<Adopted>), Error>;          // child
pub(crate) fn sandbox_request(resolution: &Resolution, access: AccessMode) -> Result<Sandbox, Error>; // product
pub fn resolve_flag(source: ValueSource, requested: bool, file: bool) -> bool;   // the three channels, collapsed (plan)
```
`plan`, `confine` and `adopted_listener` complete the module: `plan` resolves the three channels and raises every static refusal (the feature-off build's `Error::Usage`, the channel this build does not honour, the target whose `tinio_sandbox::backend_available()` answers `false`), `confine` answers `None` for `Confinement::InPlace` and `Some(child)` for `Confinement::Supervise` — the launcher then drives the facade's `supervise` — and `adopted_listener` turns the adopted payload into the listener the child serves on (its own home is `child.rs` since 2026-09-27; the name is re-exported, which is what this paragraph is about). None of the six is behind `#[cfg(feature = "sandbox")]`: a channel the operator can reach by variable or config key cannot be compiled away, and code that does not exist cannot refuse.

- **Fail-closed, three ways**: feature off → `Error::Usage` (exit 2) naming the build; the channel not honoured → a startup error naming the channel (this is what `TINIO_SANDBOX`/`[server] sandbox` stop being once this lands — decision 10 makes them real channels); the target with no backend crate (`tinio_sandbox::backend_available()` false) → a startup error naming the platform, a class no supported target is in now that the three backends have landed (Background).
- **The exposure set** is the served root at the mode's access, plus the state dir at read-write when it lies outside the root, plus the executable's own directory read-only on Windows only (sandbox design decision 22 — macOS deliberately spends no grant there), plus the device files on Linux. Paths are canonicalised, and a path whose canonical form is a reparse point is refused (the Windows rule the sandbox design settled).
- **The OTLP conflict** (sandbox design decision 25) is a `warn!` on stderr naming both the endpoint and the flag, emitted by the CLI since the CLI owns the subscriber; the confinement proceeds. **Landed 2026-09-27**: `sandbox/confine.rs`'s `lost_export` answers the pair (the asking channel, the configured endpoint) and `commands/start/run.rs` emits the one event on the line both arms reach with the log live — a launcher after its subscriber, the in-place arm after its own.
- **Tracing** follows the shared plan's §7 — `info!` for the resolved mode and exposure set, `debug!` for the per-item detail — and the CLI's subscriber is the sink, so nothing needs its own `try_init`. **Its position is around the confinement rather than beside it**: installed **before** `confine` on a launcher arm (or the backend's own launch events would never reach it) and **after** it on the in-place arm, where `build_subscriber`'s OTLP batch-exporter thread would otherwise stay outside the namespaces, the dropped capabilities and the filter — sandbox design decision 26 owns the rule and states what the in-place arm pays for it.
- **What P1/P2/P3 owed, and have since delivered**: the backends. They have landed (Background), so every supported platform confines rather than refuses and the seam this design delivered is backed by real confinements; the refusal path remains for a target with no backend crate, and that path's test is what asserts it (a `--sandbox` run there exits non-zero with the platform named, and never starts a server).

### §9 Errors, exit codes and the operator's message

One `Error` per crate, as `docs/style.md` requires, with the CLI's mapping to 0/1/2 as the only place a numeric code exists. Every refusal this design introduces names three things: what was asked for, which channel or platform it came from, and what would make it work — the sandbox refusals are the pattern (`--sandbox` on a target with no backend names the platform; in a feature-off build it names the build), and `doctor`'s severities reuse the same discipline at ok/warn/error granularity.

### §10 Testing and verification

- **Unit**: the resolution orders (root discovery, mode, state dir, config path, transport exclusivity) as pure functions; clap's parse of every documented flag and its env alias; the exposure set; the daemon arms' argument construction; the doctor report's renderings.
- **Integration, per crate**: T055's lifecycle round-trip (start → status → stop < 1 s, SC-007; readiness ≤ 1 s, SC-005; single-instance; `--port 0` recorded in `state`; daemon detach; signal shutdown; feature-off builds omitting `status`/`stop`), T056's management plane (token rules per transport, `/stop`'s bounded drain, the pipe's first-instance semantics, stale-socket reclaim), T057's doctor (clean root exit 0; each repairable defect exit 1; `--dry-run` touches nothing; `--fix` requires a stopped server; `--json`). *T055's legs are `@cli` scenarios in `crates/tinio-e2e/tests/features/cli_lifecycle.feature` as of 2026-09-22 — they spawn the real binary, which is the cucumber suite's shape, so `crates/tinio/tests/` keeps only the console-handler leg; `docs/tests.md`'s "CLI (tinio)" section holds the leg-by-leg mapping.*
- **End to end**: the existing cucumber suite runs against the `tinio` binary with no scenario edits beyond the spawn helper — the one scenario that does change is the data-plane `/metrics` scrape plan A retires with the route, and it moves in phase A, not here; `serve_read_only.rs`'s legs ran against the same binary until the file retired on 2026-10-01 (`docs/superpowers/plans/2026-10-01-test-placement-cleanup.md`) into `crates/tinio-e2e`'s `read_only.feature` / `@cli` scenarios; the sandbox legs assert the refusals of §7 until P1 lands.

- **The pre-push bar** is `docs/tests.md`'s Standard acceptance block in full; this feature adds legs to `docs/tests.md` (a CLI section) rather than substituting a shorter list.

## Risks

| Risk | Assessment |
|---|---|
| **The CLI can be read as delivering the sandbox.** It delivered the channels, the sequence and the exposures, and the backends have landed since (Background), so the reading is no longer a gap to close: every supported platform confines, and the refusal remains the behaviour of a target with no backend crate. | Mitigated in the documents and in the tests: the refusal path is asserted (§7), and the design says so in its Status line and its Non-goals. |
| **The harness switch touches every scenario's startup path.** | The readiness line and the `--port 0`/`--config` contract are held identical across the switch (§8), so the spawn helper is the only file that changes; the suite is the regression test. |
| **`daemonize` forks in place, which is a hazard anywhere after the first thread.** | The ordering (§1 step f) is the mitigation and a test spawns the binary to prove the daemon arm works when the runtime does not exist yet. |
| **The Windows named-pipe transport cannot configure keep-alive through `axum::serve`.** | The manual `serve_connection` loop with `http1_keep_alive(false)` is the verified answer (`research.md:99`), and the pipe leg of T056 exercises it. |
| **`.env` and the mode could still be read in the wrong order by a future change.** | Decision 4 is one rule with one owner and a test that fails if a `.env`-supplied `TINIO_READ_ONLY` takes effect. |
| **The dependency graph grows** (`axum`'s graph, `utoipa`, `tokio-rustls`+`rustls`+`rustls-pemfile`, `clap`, `daemonize`, `signal-hook`). | All but `daemonize` and `signal-hook` are in the spec's dependency ledger (`research.md:164-176`) with the alternatives it rejected; both additions are recorded in Bookkeeping with this design's reasoning — `daemonize` has one dependency (`libc`), `signal-hook` two (`libc`, `signal-hook-registry`, the latter already in the lock), and the alternative to each is `unsafe` code this workspace forbids. `nix` (dropped 2026-09-22 — decision 20's amendment) and `sd-notify` added **no** new crates at all: `bitflags` 2.13.1, `cfg-if` 1.0.4 and `libc` 0.2.189 are all already in `Cargo.lock`, and neither crate's optional extras are enabled. |
| **The watchdog can be over-trusted.** Its timer shares the serving runtime, so it proves the runtime is still scheduling, not that the data plane is answering. | Stated in decision 21 rather than implied, and the unit's `WatchdogSec=` is the operator's to size; a full liveness probe of the data plane is not what `WATCHDOG=1` means anywhere else either. |
| **The systemd notification path is invisible off systemd**, which is most machines that run the tests. | The no-op is deliberate and asserted: a run without `NOTIFY_SOCKET` must start, serve and stop with no notification error surfaced, and the notify test binds its own socket and drives the child. |
| **The unix socket's 108-byte path limit can make a deep root unbindable.** | Pre-existing and documented (`research.md:56`); read-only mode's home state dir is deep by construction, so `doctor` reports the resolved socket path and its length as a check. |
| **`service-manager`'s default systemd template would silently un-arm decision 21.** Its template writes `Type=simple` and no `WatchdogSec=`, so a unit generated from it makes every `READY=1`/`WATCHDOG=1` inert without any error. | Answered by `ServiceInstallCtx::contents` (decision 22): the unit text is authored in this repository, and a test keeps `packaging/tinio.service` equal to its rendering, so the file an operator reads and the file a machine installs cannot diverge. A future version changing `contents`' semantics fails that test rather than the deployment. |
| **`service-manager` adds a second `dirs` major to the lock** (`dirs ^4.0` against this workspace's `dirs 7`) plus `plist`, `xml-rs`, `which` and `log` on every platform. | Recorded in the ledger rather than waved through (Bookkeeping). The crate is what keeps the SCM/systemd/launchd plumbing out of our own `unsafe`-forbidding crates — the same trade the sandbox design made when it chose `signal-hook` over a hand-written `sigaction` — and the `dirs` duplicate is the one measurable cost. A build that never installs a service still links it, because the subcommand is always present; if that becomes a problem the answer is a cargo feature, not a rewrite. |
| **The service verbs need elevation and will fail for the operator who forgets.** `install`/`start`/`stop`/`uninstall` at the system level need root or Administrator, and the underlying failures are `EACCES`/`Access is denied` from three different systems. | Each refusal names the remedy (`--user` on unix, "run as Administrator" on Windows) rather than passing the raw error through — the same discipline §9 sets for every other refusal this design introduces. |
| **The `api`-off build has no single-instance enforcement** (there is no control-channel bind without the plane). | Contractual (`plan.md`'s Constraints), and the CLI's `status`/`stop`/`--api` are compiled out with it, so the build cannot promise what it does not have — the allowed half of decision 10's rule, because ignoring them makes the build smaller and never weaker. **`doctor` is deliberately not among them** *(doctor-plan grilling)*: it diagnoses the always-present layers (root, config, names, symlinks, free space, the `Cleanup` trait's private-state legs, the meta store), which need no plane — `research.md:132` says so, and `contracts/cli.md` marks `status`/`stop` api-only while leaving the doctor section unmarked. What compiles out with `api` is `--dry-run`, `--fix` and the stale state/socket leg, because without a control channel the command cannot prove a server is stopped and must not offer an unguarded repair. The forbidden half is a channel the operator can still set without the binary: an environment variable or a config key must refuse, never be ignored. |
| **A dependency edge can make the workspace unresolvable, not merely larger.** Plan A's Task 7 proposed `tinio-api` → `tinio-server`, which cycles with `tinio-server`'s optional `tinio-api` (`crates/tinio-server/Cargo.toml:56,105`). | Measured on 2026-09-20 against a minimal two-crate workspace: cargo refuses to resolve, `error: cyclic package dependency`, even with the optional feature off — so the plan set contained a step that could not build, and only an experiment found it. Decision 23 removes the edge in favour of an injected gauge source, and the task that lands it says why it must not come back. |
| **A wide-open control pipe would let every local user drive the control channel.** | The Windows named pipe is created with a **current-user-only DACL**, via `create_with_security_attributes_raw` (measured), the same posture as the unix socket's mode 0600 and the `state` file's ACL. A platform default would not give this, which is why it is recorded as a property of the transport rather than assumed. |
| **`--sandbox`'s FR does not exist yet.** | This design writes it (§8 plus Bookkeeping), which is the sandbox design's own instruction ("the FR and the contract prose land with the CLI feature, not here"). |
