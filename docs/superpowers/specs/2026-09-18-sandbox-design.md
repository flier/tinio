# Design: `--sandbox` — process confinement on Linux, macOS and Windows

**Date**: 2026-09-18
**Status**: draft — grilling complete, and planned across four phase documents (`2026-09-18-sandbox-p0-core.md`, `-p1-linux.md`, `-p2-windows.md`, `-p3-macos.md`) plus `2026-09-18-sandbox-shared.md`, which owns the conventions and the cross-plan facts the four of them share. **FR-023 (read-only mode) has landed** — commit `a46a1d1` — so this design confines it rather than waiting on it. The macOS rows of §5 and §7 are measured rather than predicted; the Windows rows of §6 and §7 still carry the gaps listed in §12

**Reviewed 2026-09-19**, against the working tree and against all three platforms (this Windows host, a macOS 15.8 VM, WSL2). Three things this document asserted are corrected in place rather than silently: the `remount,bind,ro` rule §4's overlay variant rested on is **false** for the filesystems a served root lives on (§4 and the evidence table), §8's capability-drop order was inverted relative to its own evidence, and `log show` does not report refusals on macOS 15.8 — only `log stream` does. The rest of the pass changed the plans rather than this document, and its findings are recorded against the plans themselves.
**Scope**: new crate `tinio-sandbox`; a default-on `sandbox` cargo feature on the consuming crates; `[server] sandbox` config key; the `serve` example's entry-point restructuring; WSL2 verification. Not touched: the real CLI (`tinio-cli` is still a placeholder — the flag lands there with T066/T067), the management plane, `doctor`, credentials, config auto-create.
**Spec**: no spec text exists for this requirement yet. Unlike read-only mode (FR-023), `--sandbox` has no FR to implement — this document *introduces* the requirement, and the FR/normalization work lands with the CLI feature. Everything here is therefore design-first, not contract-first.

## Background

tinio serves an S3 API over a directory tree and holds credentials in its private state. Two existing properties motivate confinement:

- **FR-020 / FR-023**: all private state lives in a reserved directory, and in read-only mode the storage root is never written at all. Both are currently *application-level* promises — a path-traversal bug, a symlink-following bug, or a bug in the `.tinio` reservation is all that stands between a request and the wrong file. `piolium/findings-draft/p4-005-follow-symlinks-skips-containment-proof.md` is an instance of exactly this class.
- **FR-033**: with a `local_uid` mapping configured the server runs privileged (root or CAP_CHOWN), so a bug in that configuration has the privileges to reach anything the process can.

`--sandbox` moves both promises down to the kernel: the process is confined to the paths the operator exposes, and anything else is unreachable no matter what the code does.

Nothing of this exists today. `crates/tinio-cli/src/commands/mod.rs` is a doc comment and `tinio_cli::run()` returns `ExitCode::SUCCESS`; the only runnable entry point is `crates/tinio-server/examples/serve.rs`, which hand-parses its own arguments — today `serve <root> [--port N] [--address HOST:PORT] [--config <config.toml>] [--read-only]` — rather than going through a CLI parser. The flag therefore lands on `serve` in this design, with the CLI wiring deferred. **`--read-only` is the worked example of that deferral**: it was designed the same way, landed on `serve` alone, and its CLI flag still waits with T066/T067.

## Goal

One flag, one interface, and **two guarantees on the three supported platforms**: (1) the confined process reaches exactly the directories the operator exposed, with exactly the access each was given, and nothing else; (2) the confined process cannot initiate an outbound connection. Plus a third property that follows from the first: `--read-only` becomes kernel-enforced rather than an application-level promise.

The guarantees are uniform across Linux, macOS and Windows. They are **not** uniform across every unix: a fourth platform gets a best-effort fallback that delivers only the first guarantee's directory boundary, and says so at startup (decision 23).

## Non-goals

- **PID / NET / IPC / UTS namespaces and cgroups.** v1 is the mount namespace, capabilities and a single-purpose seccomp filter on Linux. No network namespace, no resource limits, and no *general* syscall filtering — seccomp is used for exactly one thing, blocking outbound connection setup (decision 13).
- **Cross-platform equivalence of *mechanism* or of *visible-path behaviour*.** The three platforms enforce the guarantees differently and Linux alone hides the path namespace. §2 states each one plainly instead of implying more than it delivers; the guarantee is that the paths are *unreachable*, not that they are *unnameable*.
- **Wiring into the real CLI.** `serve` only; `tinio server --sandbox` lands with T066/T067 alongside `--read-only`.
- **Read-only mode itself (FR-023).** That work has **landed** (commit `a46a1d1`): `serve` resolves the mode from `[server] read_only`, the `TINIO_READ_ONLY` overlay and the `--read-only` flag, refuses every mutating operation, and relocates the tool's state out of the served root to `TINIO_STATE_DIR` or `<home>/.tinio/roots/<hash>/`. This design provides the *seam* it plugs into (§9), confines it, and does not re-implement it.
- **Protecting the state directory's contents from the S3 surface.** `.tinio` reservation is FR-020's job; the sandbox only guarantees the state directory is reachable, not that it is unservable.
- **A strong path on platforms outside the three.** Covered by decision 23 as an explicit, documented downgrade rather than a silent one.

## Verified evidence

Every claim below was measured, not assumed. Each row names how to reproduce it; nothing in this document rests on recall where a probe was possible. Rows marked **(unverified)** are the gaps — they are collected in §Risks and assigned to a phase.

| Claim | Evidence |
|---|---|
| `unshare(CLONE_NEWUSER)` fails in a multi-threaded process | `EINVAL(22)` with 11 live threads; `rc=0` single-threaded |
| `unshare(CLONE_NEWNS)` alone needs CAP_SYS_ADMIN | `EPERM` single-threaded, before the user namespace exists |
| **`remount,bind,ro` is decided by the filesystem, not by who owns the superblock** — and the earlier rule stated here was **wrong** | re-measured 2026-09-19 on WSL2, kernel `6.18.33.2-microsoft-standard-WSL2`, Ubuntu 26.04, uid 1000, unprivileged: an ext4 bind and a drvfs (`/mnt/e`) bind both remount read-only `rc=0`, `findmnt` reports `ro`, and a write through them then fails `EROFS`. The previous row claimed this returns `EPERM` because "the superblock belongs to the initial user namespace" — that explanation cannot be right, since those superblocks **are** host-owned and the remount succeeds |
| The filesystems a user namespace may mount itself **refuse** the remount | measured 2026-09-19: `MS_REMOUNT\|MS_BIND\|MS_RDONLY` returns `EPERM(1)` on tmpfs, devtmpfs, procfs and sysfs — and on a **subdirectory of a tmpfs**, so "the source is a mount point" is not the discriminator either |
| A mount whose superblock the user namespace owns **can** be remounted read-only | tmpfs mounted inside the namespace: `OK`, writes then refused |
| overlayfs with `lowerdir` = the served root, `upperdir` on a namespace-owned tmpfs, mounted `MS_RDONLY` | mount `OK`; writes refused with EROFS; **the lower is byte-for-byte untouched** |
| The overlay path holds when the lower is on drvfs (`/mnt/e`) | `OK`, lower visible, write refused |
| `pivot_root` + `umount2(MNT_DETACH)` | `OK` on ext4 and on drvfs |
| WSL2 provides the prerequisites | Ubuntu-26.04, kernel `6.18.33.2-microsoft-standard-WSL2`, `user.max_user_namespaces=47783`, unprivileged `unshare -Urm` works, `sudo -n` works |
| An AppContainer package SID is derivable without elevation | `DeriveAppContainerSidFromAppContainerName` → `S-1-15-2-207154238-…`, `elevated: False` |
| **A Rust binary runs inside an AppContainer** | `serve.exe` exits 2 and prints its own `usage:` banner |
| Only the exposed directory's own ACE is required — **as to ancestors** | leaf-ACEs-only case (ancestors untouched) ran the binary |
| **An inheritable ACE on the exposed directory reaches its pre-existing children** | measured 2026-09-19 on this machine, NTFS (`C:`) and ReFS (`E:`) alike: `icacls <dir> /grant:r "*<sid>:(OI)(CI)M" /q` — **no `/t`** — put the SID on a file seeded *before* the grant at depth 1 and at depth 2 of the tree, rendered as an inherited `(I)(M)` entry, and on the intermediate directory as `(I)(OI)(CI)(M)`; `icacls` reported "Successfully processed 1 files" (the directory alone), and `.NET Set-Acl` reproduced the propagation with `IsInherited: True`, so it is the filesystem's inheritance and not a tool walk. A file created after the grant carries it too, and a directory-only `icacls /remove:g` removed every inherited copy at every depth |
| An inheritance-flagged grant on a **file** is a silent no-op | measured 2026-09-19: `icacls <file> /grant:r "*<sid>:(OI)(CI)M" /q` exits 0 with "Successfully processed 1 files; Failed processing 0 files" and writes nothing — `Get-Acl` lists no entry for that SID. The same command with `:(M)` writes an explicit, non-inherited ACE. `(OI)(CI)` is meaningful on a directory only |
| An **explicit** ACE on a file survives a directory-level `/remove:g` | measured 2026-09-19: the file's own ACE is untouched by `icacls <dir> /remove:g "*<sid>"` and needs its own removal. Inherited copies go with the directory's |
| **A console-wide Ctrl+C does not reach a child created with `CREATE_NEW_PROCESS_GROUP`** | measured 2026-09-19 on this machine's host console: `GenerateConsoleCtrlEvent(CTRL_C_EVENT, 0)` fired the launcher's own handler in the same millisecond and **never** fired the child's — its handler log stayed at the start line and it kept beating for the whole 5 s window. The identical call reached a child created *without* the flag at the same tick, so the flag is the cause and not the call. The flag changes event routing, not console attachment: both processes reported the same console HWND and each listed the other in `GetConsoleProcessList` |
| **A targeted `CTRL_BREAK_EVENT` reaches the new process group** | `GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, <child pid>)`, the child being its own group leader: return 1, `GetLastError` 0, the child's handler fired ~0 ms later with exactly one event, and the child survived because its handler returned TRUE |
| **A launcher-side forward closes the gap** | measured: on receiving the console-wide Ctrl+C, the launcher's handler calling `GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, child_pid)` delivered the event into the child's handler, which logged `CTRL_BREAK_EVENT`. The child did **not** die, because a handler returning TRUE consumes the event — the forward delivers, the child's hook decides |
| **`GenerateConsoleCtrlEvent`'s return value is not evidence of delivery** | `GenerateConsoleCtrlEvent(CTRL_C_EVENT, <pid>)` returned 1 with `GetLastError` 0 and delivered nothing at all — no handler fired in either process, ever. Addressed at a non-leader pid in group 0 the delivery was erratic instead: in four of five runs nothing until the target was killed, in one a delivery to both group-0 processes ~938 ms later. `CTRL_C_EVENT` cannot be limited to a process group; only `CTRL_BREAK_EVENT` can |
| A directory with no package-SID ACE is denied despite `Users` / `Authenticated Users` ACEs | `Access is denied` |
| **ReFS behaves identically to NTFS** for every row above | the same matrix run on `E:` (ReFS) and `C:` (NTFS) produced identical results |
| An `RX`-only grant enforces read-only | write denied |
| Loopback bind + connect needs no capability | `BIND-OK` / `LOOPBACK-CONNECT-OK` with an empty capability set |
| `SID_AND_ATTRIBUTES` is 16 bytes on x64, not 8 | re-measured 2026-09-19 on this host: with a 16-byte stride the confined child is created and runs; with an 8-byte stride `CreateProcessW` returns `err=998 (ERROR_NOACCESS)`. The `87` this row used to quote comes from a different cause — a **truncated `cbSize`** passed to `UpdateProcThreadAttribute` — so the conclusion holds and the cited code did not |
| **A derived package SID is not by itself launchable** | measured 2026-09-19: `CreateProcessW` with `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` for a merely-derived name fails `err=2 (ERROR_FILE_NOT_FOUND)` — for our own binary and for `cmd.exe` alike, with the SID's ACE already on the tree. `CreateAppContainerProfile` (userenv.dll, unelevated, returns the same SID as the derivation, `DeleteAppContainerProfile` removes it) makes the identical call succeed. §6 and decision 21 must carry the profile as a created-and-rolled-back artifact alongside the ACEs |
| **A failed `UpdateProcThreadAttribute` that is not checked produces an unconfined child** | measured 2026-09-19: a truncated `cbSize` makes the call return `err=87` and set no attribute, yet `CreateProcessW` still succeeds and the child runs with no container at all. Every attribute-set call must be checked and fatal — §11's table names `CreateProcess` and the Job object but not the attribute calls |
| `/grant:r` on a file that already carries a same-SID **inherited** ACE leaves two entries for that SID | measured 2026-09-19: the explicit entry and the `(I)` copy coexist, and a directory-level `/remove:g` removes only the inherited one. A `has_ace`-style predicate and the rollback path must accept either form |
| **An AppContainer process can serve on a socket it never created** | parent bound `127.0.0.1:2547` outside the container, passed the handle through `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`; the confined child called `accept`, `recv`, `send` on it and the parent read back `pong-from-inside-the-container` |
| Handle values survive inheritance with their values preserved | parent handle 1040, child saw 1040 |
| Windows 8+ sockets are non-inheritable by default | `SetHandleInformation(h, HANDLE_FLAG_INHERIT, …)` is required before the handle is passable |
| `move_mount` / `open_tree` **cannot** eliminate the jail mountpoint directory | the "anonymous" part removes the requirement for a *source* path; the *target* must still be a real directory, so one must be created |
| The serve path makes no outbound connections | the only outbound code path in the runtime crates is OTLP-gRPC (`crates/tinio-server/src/log.rs:349-352`), gated by `#[cfg(feature = "otel")]` and requiring `otel_endpoint = Some`, which `serve` never passes |
| The serve path reads exactly one file outside root and state | `Config::load(path)` (`crates/tinio-config/src/schema/config.rs:128-132`), the arbitrary `--config` argument. No timezone, `/proc`, TLS-cert or `.env` reads on that path |
| The serve path spawns no child processes | no `Command` / `fork` / `exec` outside `#[cfg(test)]` and the e2e harness |
| **`sandbox-exec -p <profile> <cmd>` works on macOS 15.8 (24H23, x86_64, SIP on)** | measured in a macOS VM on 2026-09-19; the man page marks the tool DEPRECATED, and it still is, but it functions |
| **A `(deny default)` process aborts with SIGABRT unless it may read `/` itself** | the sole violation logged is `file-read-data /`; `(allow file-read* (literal "/"))` is enough to start. Granting `/usr`, `/System`, `/System/Library` or `/usr/lib/dyld` instead does **not** substitute — the denial is on the root directory, not on any file under it |
| **`process-exec` is mandatory** | without it nothing runs at all: `rc=71 sandbox-exec: execvp() of '<path>' failed: Operation not permitted` |
| **Three distinct macOS failure modes, each with its own exit code** | profile will not compile → `rc=65` with the compiler's diagnostic on stderr; profile compiles but denies the exec → `rc=71`; exec allowed but the image cannot start → the **child** dies SIGABRT and `sandbox-exec` prints nothing (`rc=134`) |
| **`network-outbound` also gates AF_UNIX connects** | the resolver's socket to `/private/var/run/mDNSResponder` and the log socket to `/private/var/run/syslog` are both logged as `deny(1) network-outbound`; consequently an external `getaddrinfo` fails under `(deny default)`. DNS does **not** escape a sandbox that withholds `network-outbound` |
| **`accept()` on an inherited listener is not gated by any network rule** | with a profile granting **zero** network operations, a listener created outside the sandbox was passed in and the confined process took a completed connection from its backlog: `accepted-a-connection`, and the violation log records no `accept` denial — only `network-bind` and `network-outbound` |
| **Only `bind()` and `listen()` are gated, and by different rules** | `bind()` succeeds if *either* `network-bind` *or* `network-inbound` permits the local address (a profile with no `network-bind` rule at all still bound `localhost:8080` when `network-inbound` allowed it); `listen()` requires `network-inbound` (`bind:8080` with no inbound rule bound successfully and then failed to listen) |
| **`(local ip "localhost:*")` is not a restriction** | it admits any port and the wildcard address, i.e. it behaves like an unfiltered allow. `(local ip "localhost:8080")` is the effective form: it admits port 8080 and refuses both 9090 and a wildcard-address bind |
| **`(local ip "127.0.0.1:8080")` does not compile** | `rc=65`, profile compilation error; the filter takes a host-name form, not a literal address |
| **`sysctl-read` is load-bearing, as the design claimed and had not measured** | with it removed, `sysconf(_SC_NPROCESSORS_ONLN)` returns **-1** and `sysctl(KERN_OSRELEASE)` fails — so `std::thread::available_parallelism` cannot size the runtime |
| **`mach-lookup` is not needed by anything the probe does except `getpwuid`** | with `(allow mach-lookup)` removed, every check still passes but `getpwuid` fails; the denials name `com.apple.system.opendirectoryd.libinfo`. The design's `com.apple.system.logger` allowance was a guess and is not required |
| **Symlinked path traversal needs `file-read-metadata`** | `cat /tmp/macprobe-alias.txt` is refused under `(subpath "/private/tmp")` **and** under the literal full path, because `/tmp` is a symlink at the root and reading its target is a metadata operation outside the grant; adding `(allow file-read-metadata)` makes both work. `/var` and `/etc` are symlinks too |
| **`-D key=value` with `(subpath (param "KEY"))` works, under `-f` and inline `-p`, with `-D` on either side of the profile flag** | a profile whose served root and state directory are parameters ran the full check set, so paths need not be interpolated into profile text. An **undefined** parameter is a compile error — `invalid data type of path filter; expected pattern, got boolean` — so a missing `-D` fails loudly at startup rather than silently granting nothing |
| **A `-D` value is data, not SBPL — measured against a deliberate injection** | a value that closes the literal and opens a rule, `/srv/x") (allow network-outbound) (subpath "/`, compiles and grants nothing: the outbound connect stays denied, and so it does for a newline, a bare quote and a trailing backslash. A directory whose name genuinely contains `"` reads correctly through `(param …)`. An empty value fails closed (`empty subpath pattern`, rc=65) |
| **Signalling one's own child needs no grant; signalling an unrelated process needs `(allow signal)`** | `kill(child, SIGTERM)` succeeds with no `signal` rule at all and under `(target self)`; `kill(unrelated, 0)` is refused under every rule except blanket `(allow signal)` |
| **A sandboxed process cannot apply a second sandbox** | `sandbox-exec` run inside a profile fails with `sandbox_apply: Operation not permitted` (`rc=71`), so the launcher must stay outside |
| **The compiled profile is capped near 64 KiB** | 10000 small rules compile; 12000 fail with `data object length 72301 exceeds maximum (65535)`; a *single* operation carrying 9000 path literals fails earlier with `profile compilation failed`. Separate `allow` operations scale better than one long filter list |
| **An unbounded `waitpid` after a fallback `kill` is a harness hazard** | the first probe hung there and had to be killed; the cause was not isolated, and every wait in the rewritten probe is bounded by an `alarm` in the child and a `WNOHANG` loop in the parent. A supervisor that reaps a child it may not be able to signal must bound that wait |
| **`log stream` with `--predicate 'sender == "Sandbox"'` needs no `sudo`, and is the only working reader — `log show` is not** | re-measured 2026-09-19 on macOS 15.8: `log stream` reports `<process>(<pid>) deny(1) <operation> <target>` per violation, while `log show` returns **no refusal records at all** over a window in which dozens of denials demonstrably occurred — not with `--last 1m`, not with `--info --debug`, not with `--last 1h`. Error-level kernel records do persist in general, so the Sandbox violation records are specifically live-only on this build. Earlier text here named `log show`, which is why the correction is recorded rather than silently applied. It reports `<process>(<pid>) deny(1) <operation> <target>` per violation, which is what turned "the profile is missing something" into the exact operation and path. This is the tool for minimizing a profile |
| **The real server builds and serves under §5's profile, with not one refusal** | the workspace was copied into the guest and `cargo build -p tinio-server --example serve` finished in 1m22s with zero errors (rustc 1.98.1, crates fetched through a mirror). Run under §5's profile — the four load-bearing allowances, the measured system read set, the exposed root, `network-bind`/`network-inbound` for the port it binds itself, and **no `mach-lookup`, no `system-socket`, no `ipc-posix-shm`** — it prints `listening on 127.0.0.1:19099` and answers `curl` with a real S3 `AccessDenied` XML body. `log show --predicate 'sender == "Sandbox"'` filtered to the server's own process name returns **zero** violations. This is the row the whole macOS section existed to earn: the profile is not merely one a probe survives, it is the one the product runs under |
| **SBPL comments are `;`, and a commented-out rule grants nothing** | measured with a working control: a trailing `; tinio:exposure` on a rule compiles and changes nothing, a `;` line on its own compiles, and commenting the granting rule out removes the grant (the read is refused). `#` is **not** a comment — it is a different construct and fails to compile with `illegal sharp expression ""`. This is what makes the profile's `; tinio:<id>` provenance markers work, and therefore what makes the phase's rule-by-rule pruning experiment possible: removal is `;`-prefixing a line, and a rule that survives pruning is one whose removal broke something |
| **A `(subpath …)` rule must be spelled the way the kernel resolves it** | with the blanket metadata allowance present, a grant written on `/tmp/grill` does **not** match a file at `/private/tmp/grill/real/inner.txt`: Seatbelt matches the rule's literal spelling against the resolved path, so the symlinked spelling granted nothing and both command spellings were refused. The canonical spelling `(subpath "/private/tmp/grill")` plus metadata serves both spellings. So canonicalising an exposure and granting metadata are **both** required, for different reasons — metadata to let the path be walked at all, the canonical spelling to match what it resolves to |
| **On macOS the confined child needs no grant on its own directory** | measured: a dynamically-linked binary runs under a profile that grants `/usr`, `/System`, `/bin`, `/sbin`, `/Library`, `/dev` and `(literal "/")` and **nothing** for its own location, even when that location is a directory no rule mentions. `process-exec` is what gates execution; `file-read-data` on the executable image and on its directory is refused and logged and the program runs anyway. The 81 MB Rust server binary behaves the same way, so this is not an artefact of a small C program. Design decision 22 claimed this requirement for both launcher platforms on the strength of a Windows measurement; it is **Windows-only** |
| **`(subpath X)` includes X itself** | measured directly: `(allow file-read* (subpath "/Library"))` with **no** blanket metadata still permits `stat("/Library")`, and so does `(literal "/Library")`. So an exposure needs no companion `literal` rule for its own directory, and the generator emitting one rule per exposure is correct as written |
| **A denial read from `log stream` must be attributed to a process before it is believed** | the first read of the server's run appeared to show one refusal, `file-read-metadata /Library`, under a profile that plainly grants both that operation and that path. Filtering by process name showed it came from `mobileassetd(214)`, a system daemon, and that the server's own count was zero. `log stream` is system-wide and asynchronous, so a run boundary drawn by line count will attribute a stranger's refusal to your own process — the process name in the record is the only thing that makes it yours |
| **A real Rust binary runs under the profile and serves on a handed-in listener with zero network grants** | a std-only Rust probe built with rustc 1.98.1 in the guest, run under §5's profile: `available_parallelism()` → 6 (so `sysctl-read` reaches std), eight threads spawn and join, `sleep`/`Instant` behave, `TcpListener::bind` inside is refused (`permission denied` — the launcher binds outside, as decision 16 requires), `TcpListener::from(OwnedFd)` on the inherited descriptor accepts a real peer, reads inside the grant and writes inside it, is refused a write outside it, is refused an outbound `connect`, and receives its stdin payload |
| **`network-outbound` covers datagram sends, not only `connect`** | `sendto` on an unconnected `AF_INET`/`SOCK_DGRAM` socket is refused under a profile with zero network rules and permitted once `network-outbound` is granted — so the guarantee is not "no connect" but "no outbound traffic" |
| **`AF_SYSTEM` kernel-control sockets are gated by `system-socket`, not by any network rule** | `socket(PF_SYSTEM, SOCK_DGRAM, SYSPROTO_CONTROL)` succeeds with `(allow system-socket)` and is refused without it, under identical network rules. Nothing else measured needs the allowance, so it is dropped from §5's profile: it is a privilege with no caller |
| **Raw sockets are refused regardless of the network rules** | `socket(AF_INET, SOCK_RAW, IPPROTO_ICMP)` fails whether or not `network-outbound` is granted, so no profile can be talked into opening one by accident |
| **`sandbox-exec` propagates the child's exit status faithfully** | `exit 42` → 42, `exit 1` → 1, and a child killed by SIGTERM is reported as signalled, not as a code. Exit-status forwarding on this platform is therefore a pass-through, not a reconstruction |
| **Rebuilding a listener from an inherited descriptor is `unsafe`, and rustix does not make it safe either** | `rustc` refuses both `std` routes with `E0133`: `BorrowedFd::borrow_raw` and `OwnedFd::from_raw_fd` are `unsafe fn`. The claim that the child's rebuild is safe via `BorrowedFd::try_clone_to_owned` holds only *after* a `BorrowedFd` exists, and obtaining one from an argv integer is the unsafe step. `rustix` is not an escape: its `net::socket` module is free functions over `OwnedFd` (`socket(…) -> io::Result<OwnedFd>`, `accept<Fd: AsFd>`), with no raw-descriptor constructor, so a `rustix` route would still begin at `OwnedFd::from_raw_fd`. This is what makes decision 14's macOS entry a real one rather than an assumption that the platform needs nothing |
| Whether an absent AppContainer capability blocks outbound traffic | **(unverified)** — the probe could not separate container isolation from this host's firewall policy |
| Whether an inherited listener reaches the LAN | **(unverified)** — the probe used loopback, which works without a capability regardless |
| **The `/proc/<pid>/uid_map` descriptor must be opened *after* `unshare(CLONE_NEWUSER)`, never before** | a descriptor opened before the unshare is bound to the **initial** namespace: reading it back after the unshare returns `[0 0 4294967295]` (the init map) and writing returns `EPERM(1)`. A fresh descriptor after the unshare writes `"0 <euid> 1"` with `rc=9`. `/proc/self/setgroups` cannot even be *opened* before the unshare: `EACCES(13)` |
| An unmapped process fails on **file creation**, not on mounting | with no map at all, `mount("tmpfs", …)` returns `rc=0` and `pivot_root` succeeds; `mkdir`/`open(O_CREAT)` inside the new namespace then fail with `EOVERFLOW(75)`, driven by the unmapped **gid** (the namespace's tmpfs root reads `gid=65534`). Writing both maps makes the same calls succeed |
| **`PR_CAPBSET_DROP` needs `CAP_SETPCAP` in the *effective* set at the moment of the call** — so the bounding-set sweep has to run **before** the `capset` that narrows the set, not after it | with the full set intact the drop returns `0` and `PR_CAPBSET_READ` flips to `0`; after a `capset` clearing effective+permitted it returns `EPERM(1)` and the bounding set is untouched. Swept that way, all 41 drop and the bounding set ends empty; `41..63` return `EINVAL(22)`, which is `CAP_LAST_CAP = 40` doing its job. `PR_SET_NO_NEW_PRIVS` is not a substitute — it is what lets the seccomp filter install later, not what permits the drop. Dropping from the bounding set does not clear the effective bit, so the sweep may drop `CAP_SETPCAP` itself and continue |
| Inside a user namespace, a bare `MS_BIND` of a **mount point** source is refused | `mount("/tmp", …, MS_BIND)` and `mount("/", …, MS_BIND)` → `EINVAL(22)`; the same two with `MS_BIND\|MS_REC` → `rc=0`. A subdirectory source (`/etc`, `/bin`) works with a bare `MS_BIND`. `rustix::mount::mount_bind` passes only `MS_BIND`; `mount_bind_recursive` adds `MS_REC` |
| Mount propagation on WSL2 is already private | `findmnt -no TARGET,PROPAGATION /` → `/ private`; `/tmp` and `/mnt/e` likewise. Making `/` private is therefore defensive rather than a fix for a shared-root failure |
| `mount(NULL, "/", MS_REC\|MS_PRIVATE)` succeeds inside the user namespace | `rc=0`, so locking propagation costs one syscall and needs no capability the confinement does not already have |

## Decisions

1. **The flag is `--sandbox`, the key is `[server] sandbox`, the variable is `TINIO_SANDBOX`.** "chroot" was the working name and is wrong on two of three platforms: there the process *can* see paths outside the confinement and is merely refused access, and `chroot(2)` is not what any of the three runs. `sandbox` is the umbrella term that does not promise a mechanism.
2. **One trait, one method, and a return value that names the shape.** `expose(path, access)` is how the caller states what must remain reachable; the builder stays pure data in the core, and turning it into mounts, SBPL rules or DACLs is the platform's job. That job is `Backend::confine(&mut self, sandbox: &Sandbox, plan: &LaunchPlan) -> Result<Confinement>` — `&mut self` because the call changes the caller: on Linux irreversibly, and on a launcher backend by recording what it set up, and `Confinement` is what keeps the call site free of `#[cfg]`: `InPlace` means the calling process is confined and should carry on, `Supervise(child)` means a confined child is running and the parent must wait, forward its exit status and undo what it set up. Linux always answers `InPlace`; macOS and Windows always answer `Supervise`. A trait carrying both an `enter()` and a `launch()` would hang a permanently-failing method off every implementation, and two separate traits would push the platform split into `main()` — the one place it must not appear. **What that freedom does not extend to is a platform's own configuration.** `Confinement` makes the *confinement call* cfg-free, but a backend's settings and its platform-specific status are not part of the shared surface and the facade does not re-export them: `LinuxOptions` — which carries `Mechanism` and the capability policy — and the `seccomp()` state a Linux run must report are reached by importing `tinio-sandbox-linux` directly, inside a `#[cfg(target_os = "linux")]` block. That is the boundary rather than a leak in it: the facade shares what every platform needs in order to *drive* a confinement, and a platform's own vocabulary stays in its own crate, where a caller that wants it is unambiguously writing platform-specific code. Widening the facade with per-platform options and statuses would grow the shared surface into the union of three platforms instead of their intersection.
3. **Five crates: a core holding the contract, three platform implementations, and a facade.** `tinio-sandbox-core` owns the trait, the shared vocabulary (`Exposure`, `Sandbox`, `Error`, `Confinement` — and `AccessMode`, which it **re-exports from `tinio-core` rather than redeclaring**, because FR-023's read-only resolution already produces one at the `serve` call site and a second enum for the same fact would put a conversion between them) and the launcher machinery both child-launching platforms share. `tinio-sandbox-linux` / `-macos` / `-windows` each implement the trait for their platform. `tinio-sandbox` is a thin facade that re-exports the core and, behind `[target.'cfg(…)'​.dependencies]`, the one platform implementation that applies. **The layering is forced, not stylistic**: the platform crates implement the core's trait, so they depend on the core, which means the crate that *selects* a platform cannot also *define* the trait — a two-crate split would be a dependency cycle. The facade follows the existing `crates/tinio` precedent. Per-platform *cargo features* are still rejected: the platform code is already `cfg`-gated, and a feature would add a combination that compiles with no implementation behind it.
   The feature gate stays on the consumers. `tinio-server` (whose only consumer today is the `serve` example, via `required-features`) and the future `tinio-cli` each carry a **default-on** `sandbox` feature. (The alternative home `tinio-util::sandbox` was rejected because `tinio-util` is backend-agnostic runtime helpers and this is a process-level concern with a platform matrix.)
4. **Default-on means compiled in, not enabled.** The sandbox code is in the default build; whether it runs is decided by `--sandbox` / `TINIO_SANDBOX` / `[server] sandbox`, exactly as `--read-only` will be. Enabling it by default as *behaviour* would be a breaking change to every existing deployment and is not what this design does.
5. **A build without the feature refuses the request rather than ignoring it.** With the feature off, any of the three channels that asks for a sandbox is a usage error (exit 2) naming the build as the cause. The project's stripped-capability precedent is "schema-known key silently ignored", and that precedent does not apply here: silently running unconfined is precisely the failure mode §11 exists to prevent. **The same rule covers a platform whose backend has not landed**: `--sandbox` on a target whose crate is still a stub is a usage error naming that, not a flag that is accepted and then ignored — an accepted flag that confines nothing is the same silent failure wearing a different hat.

**And it covers a channel this design names but no phase implements.** Decision 1 fixes three channels; the four phase plans wire only `--sandbox`, and defer the other two to the CLI. Until a phase implements them, a run in which **either** `[server] sandbox` or `TINIO_SANDBOX` is set must **refuse to start**, with an error naming the channel and saying it is not honoured yet — never proceed unconfined. The reason is this decision's own: an operator who sets `TINIO_SANDBOX=1`, believes they are confined, and is not, has been failed by precisely the mechanism §11 exists to provide, and "the channel is not implemented yet" is not a defence when the design named the channel and the operator used it in good faith. `--sandbox` remains the only channel that confines anything, and the error says so.
6. **Linux confines in place; macOS and Windows launch a child.** `sandbox-exec` applies a profile to a process it execs, and AppContainer can only be entered at process creation, so neither can confine a running server in place. Linux can — `unshare` plus `pivot_root` apply to the calling process — and it therefore does, with no second process, no payload, no exit-code forwarding and no signal relay. The asymmetry is stated rather than flattened to the lowest common denominator, and **it was re-examined on 2026-09-18 against the argument that uniformity would be worth a fork on Linux too**. It is not: the call site is already uniform because `Confinement` exists (decision 2), and the difference the fork would buy is implementation-side only. What the fork would cost is the property that matters most here — after `enter()` returns there is **no unconfined code running at all** on Linux, whereas the launcher platforms are forced to keep a supervisor that never enters the jail and therefore keeps a parser, a descriptor table and a signal handler outside it. Trading a guarantee for symmetry, in the direction the other two platforms cannot go, is the wrong trade. The one functional thing the fork would buy is the listener handoff of decision 16, which Linux does not get; that consequence is recorded in decision 19.
7. **Linux adapts: user namespace first, then root, then fail closed.** Verified working unprivileged in WSL2; a hardened host that forbids unprivileged user namespaces still works when started as root; when neither is available the process exits with a clear message. It never continues without the sandbox. **The adaptation needs a probe, because the parent cannot try and then back out**: `unshare(CLONE_NEWUSER)` changes the calling process for good, so a failed attempt is not something a fallback can undo. `Mechanism::Auto` therefore **forks a child that attempts the unshare and reports through a pipe** — the child is discarded, the parent is untouched, and the answer decides the model. The syscall remains the authority (no sysctl proxy, which disagrees with the kernel in containers); the fork is only how the question gets asked without committing. A probe failure with `euid != 0` is the fail-closed case, and its message names both remedies.
8. **Read-only is the absence of a write permission, on all three platforms.** Linux `remount,bind,ro` — which **both** models can do for the filesystems a served root realistically lives on, ext4 and drvfs among them (§4) — or an `MS_RDONLY` overlay where the served root's filesystem refuses the remount, which the kernel-managed families (tmpfs, devtmpfs, procfs, sysfs) do; macOS omits `file-write*` for the served root and the profile's `(deny default)` does the rest; Windows grants `RX` instead of `M`. This is why §9 needs no new mechanism — read-only mode is a different value passed to the same `expose` call.
9. **The Linux path mirrors host paths instead of translating them.** The new root is a tmpfs, and each exposed path is re-created inside it at its **original absolute path** and bind-mounted there. Every path string is then identical before and after the pivot: `dirs::home_dir()`, `state_dir()`, `<root>/.tinio`'s `prove_contained`, and `strict-path`'s containment proofs all keep working unchanged. A fixed-mountpoint design (`/data`, `/state`) would need a translation layer in every one of them.
10. **The Linux jail mountpoint is a fixed, root-derived name that the next run takes over.** `$TMPDIR/.tinio-jail-<hash(root)>`, not a pid-suffixed path: a hard kill leaves at most one directory per root instead of one per run, and startup reuses it (rmdir is safe — every mount inside it lives in a per-process mount namespace, so the host always sees an empty directory). `open_tree`/`move_mount` cannot remove the directory (see the evidence table), so bounding the residue is the available answer. Concurrency is not a concern: two processes mounting the same host directory each do so inside their own mount namespace.
11. **Linux keeps the uid and drops capabilities.** Dropping to a different uid is the conventional move and is wrong here: FR-033 lands object files `0600` owned by the service account, so a uid change makes previously-written objects unreadable. "Dropping privileges" therefore means `PR_SET_NO_NEW_PRIVS` plus a capability set reduced to what the mode needs — never a change to *which host user the process is*.
    **The user-namespace model maps the process to root *inside* the namespace, and that is not an identity change in the sense this decision forbids.** `uid_map` is written as `0 <euid> 1`, so namespace-root is the invoking user as far as the host is concerned: every syscall that crosses the boundary carries the same host euid as before, and files created through it are owned by the service account exactly as an unconfined run would own them. The namespace's root is what makes `mount` and `pivot_root` reachable at all (decision 7), and it is the reason `local_uid` must be refused under this model rather than supported (§8): an unmapped uid is not a uid the confined process can chown *to*. The property to preserve is who owns the files, and no mapping changes that.
12. **No `/proc` in the Linux jail, and no PID namespace in v1.** Mounting the host's `/proc` would leak the host process table into a jail that has no PID namespace of its own, which is worse than having no `/proc` at all. Rust's `getrandom` is a syscall and does not need `/dev`; the four device files in §4 are defensive, not load-bearing.
    **The uid/gid maps are an exception that costs nothing, because it happens before the jail exists.** Their only writable entry point is `/proc/<pid>/{uid_map,gid_map,setgroups}`, and a descriptor to it must be opened *after* `unshare(CLONE_NEWUSER)` (see the evidence table). The confinement therefore unshares in two steps — the user namespace first, while the host's `/proc` is still reachable and no mount namespace has been created yet — writes the three files there, and only then creates the mount namespace and builds the jail. Nothing is ever mounted into the jail, and no `/proc` survives in it: the window closes before the jail is built. The three descriptors are closed explicitly once the maps are written, because this design does not `exec` and so never gets `CLOEXEC`'s protection.
13. **Linux network isolation is a seccomp-BPF filter, not a network namespace.** A network namespace is the obvious answer and it is wrong here: `CLONE_NEWNET` gives the confined process its own loopback, which means **the host can no longer reach the server** — a server nobody can talk to is not a sandbox, it is an outage. Reconnecting the two ends needs a veth pair with addresses, which needs the privileges this design exists to avoid. The filter instead denies the *outbound* syscalls — `connect`, `sendto`, `sendmsg` and `sendmmsg` — and leaves accepting and answering untouched. `sendmmsg` is the batch form of `sendmsg` and an equally direct route out, so it is denied for the same reason; and the family is wider than "the datagram sends" suggests, because glibc's `send(2)` **is** the `sendto` syscall. What still answers is `write`/`writev`, which is what Rust and tokio use; what does not is `send`/`sendto`/`sendmsg`/`sendmmsg`. **The filter cannot see the address family** — seccomp cannot dereference the `sockaddr` pointer — so a `connect` on an `AF_UNIX` socket is denied along with the rest: `/dev/log`, a Docker socket or a D-Bus connection inside the jail fail with `EPERM`. That is the policy, not a defect, and it is the price of not being able to inspect the address. Two boundaries the filter cannot close are recorded in the Risks rather than papered over: `io_uring`'s `IORING_OP_CONNECT`/`IORING_OP_SENDMSG` never reach a filtered syscall at all. This is the only syscall filtering in the design and the reason the Non-goals wording was narrowed rather than the filter dropped.
14. **The unsafe exception is narrow, and the constitution's conditions are answered explicitly.** Constitution II permits `unsafe` when no safe alternative exists, in the smallest possible scope, with documented invariants and explicit review justification. (a) Alternative: `libseccomp` or the `seccompiler` crate would remove the FFI and add a dependency for a filter of six instructions; the operator authorized FFI on 2026-09-18 and the smaller dependency surface was preferred. (b) Scope: **small, enumerated and per-capability, not a fixed count.** Linux needs **three** — the seccomp `prctl`, the `unshare` call, and the user-namespace probe's `fork`. **The third is the correction the compiler asked for**, and it is the reason this subsection does not promise a number: an earlier draft said two, on the belief that `rustix::process` exports a safe `fork`. It exports none. The only one in the crate is `rustix::runtime::kernel_fork`, which is `pub unsafe fn` and sits behind the `runtime` feature and the `linux_raw` backend, so the probe cannot avoid the block — and its invariant is decision 26's rather than the call's own: no thread exists yet, so the child is a copy of a single-threaded process and touches nothing but its own pipe end and `exit`. The `unshare` call is worth stating precisely for the opposite reason — the obvious reading of it is wrong: rustix *does* export a safe `thread::unshare`, and marked it **deprecated** in 1.1 with "this function should be unsafe", pointing at `unshare_unsafe`, whose safety comment is about `CLONE_FILES` — a flag this design never passes. Taking the safe-looking path would trade the `unsafe` block for a deprecation warning, and this workspace builds with `-D warnings`, so the unsafe variant is what the crate itself asks for. **There is a second deprecation trap of the same shape and it is easy to miss**: `rustix::thread::Capability` is deprecated since 1.1 ("Use `CapabilitySet` with a single bit instead") and it **is** re-exported from `rustix::thread` — the module is `mod prctl;` plus `#[cfg(linux_kernel)] pub use prctl::*;`, so the short path compiles and only the deep `rustix::thread::prctl::Capability` fails to resolve. The deprecation alone disqualifies it under `-D warnings`; the capability policy uses `CapabilitySet` throughout. Everything else the Linux backend calls is a safe wrapper: `process::pivot_root`, `thread::set_no_new_privs`, `thread::set_capabilities` and `thread::remove_capability_from_bounding_set`. Windows needs more, and writing P2 showed the earlier three-site count here was an underestimate: the package-SID derivation, the handle plumbing, the Job object, the process launch and the socket rebuild all reach Win32 directly, and Rust 2024 makes each `extern` block `unsafe` in its own right. The boundary that matters is not the number but that each site is one module, one target, and that everything around it is safe — and the count is established by the implementation, corrected here rather than asserted ahead of it. macOS needs exactly **one**, and finding it is the point: an earlier draft of P3 asserted this crate had no `unsafe` at all, and the claim did not survive contact with `rustc`. The child rebuilds its listener from the descriptor number in argv, and both `std` routes — `BorrowedFd::borrow_raw` and `OwnedFd::from_raw_fd` — are `unsafe fn`; asking the compiler returns `E0133` for each. `rustix` is not an escape, because its `net::socket` module is free functions over `OwnedFd` (`socket(…) -> io::Result<OwnedFd>`, `accept<Fd: AsFd>`) with no raw-descriptor constructor, so a `rustix` route would still begin at `OwnedFd::from_raw_fd`. The alternative — letting the child bind inside the confinement — was considered and rejected: it costs the property that makes macOS's guarantee the strongest of the three, since the profile would have to grant `network-bind` and `network-inbound` again, and a port-filtered rule cannot express an ephemeral port. (c) Invariants: the `sock_fprog` and its filter array are `'static` and outlive the `prctl` call; `PR_SET_NO_NEW_PRIVS` is already set before the filter is installed (§7), so the filter cannot be installed with more privilege than the process retains; the filter is installed exactly once and is irreversible; the rebuilt socket takes ownership of an inherited descriptor that the parent keeps alive for the child's lifetime. (d) The lint follows the implementation, not the interface: `tinio-sandbox-linux`, `tinio-sandbox-macos` — and later `-windows` — are `unsafe_code = "deny"` with `#[allow(unsafe_code)]` on the enumerated functions alone, while `tinio-sandbox-core` and the facade keep `forbid`. Every platform backend now carries at least one site, which is worth saying plainly: the shared layer is the one that stays clean, and a backend is the layer where a kernel interface has to be met on its own terms. **The enumerated list of sites lives here, and this is the only place it lives.** `docs/cargo.md` states the rule — which crates are `deny` — and points at this decision for the sites, because that file is a convention and this one is the design the three phases all read. Each phase keeps the list current as its own sites land: Linux's three (`seccomp`, `linux`, and `model`'s `kernel_fork`) and macOS's one (`launch`, the listener rebuild) are known, and Windows' are established by the implementation rather than asserted now, which is the same stance part (b) takes on the count. A second copy of the list anywhere else is the thing that drifts. `forbid` cannot be overridden at all, so `deny` is what makes the exception expressible where it is needed and nowhere else. The exception is inside the **default** build because the feature is default-on; `--no-default-features` strips it.
15. **Grant-only, never revoke-then-grant, and roll back on every exit path.** The Windows launcher adds its ACEs and removes exactly those on exit — including the failure path where the launch itself failed, not only the clean path. It never rewrites a directory's existing DACL, and the POSIX permission bits and existing ACEs are left alone, so a sandbox run cannot lock an operator out of their own data.
16. **On macOS and Windows the parent binds the listener and hands the socket to the child.** No `network-bind` is needed inside the confinement, which is what lets the macOS profile drop its bind rule entirely, and the parent becomes the authority on the port. On macOS the measurement goes further than the design expected: `accept` on an inherited listener is not gated by any network rule, so the profile needs **no** network operation at all and the confined server still serves — which is why the macOS row of §7 reads as it does. **On Windows it is still not a network-isolation mechanism and the design does not rely on it as one**: AppContainer's network policy is enforced by WFP against the process's AppContainer SID, not against whoever created the socket, and the probe that proved the Windows handoff used loopback — which works without a capability anyway. The macOS result does not transfer to Windows, because there the policy attaches to the process, whereas on macOS the check that would have applied simply does not exist.
17. **The launch payload travels on the child's stdin as one JSON line, and there is no environment-variable marker.** The parent writes `{"config":"…"}` to the child's standard input and closes it; a child that reads it and the argv element that names the inherited listener knows it is the confined child. **The pipe is still there, and the earlier draft was wrong to claim otherwise**: a payload that flows parent → child on stdin needs a pipe the parent writes and closes, and both launcher platforms create one — `Stdio::piped()` on macOS, an anonymous pipe whose child end becomes `hStdInput` on Windows. What the stdin form buys is that the child reads a stream it already knows by convention instead of a numbered descriptor it must reconstruct, so the payload's *descriptor argument* and the rebuild-from-raw-descriptor both go away, and stdout is left as the only stream the protocol has to name. The child consumes stdin and never needs it again; `serve` has no other use for it.
    **There is no nonce, and the earlier draft was wrong to want one.** It was described as the child's discriminator, but the parent writes the nonce to the same stream it writes everything else to, so anything able to forge a payload already knows the value — it defended against nothing that the payload's own shape did not already defend against. What actually identifies a confined child is the **argv element naming the listener descriptor** plus a payload that decodes; a process that finds no element treats itself as the launcher, and a launcher inside a confinement fails closed because it can neither grant ACLs nor bind. Removing it also removed the format: the frame was a magic constant, a nonce, a length prefix and raw bytes, and is now one JSON line that `serde` reads and writes on both sides, with trailing bytes rejected by the deserializer's own end check. `config` travels as text because `Config::load` already requires UTF-8.
   An environment-variable marker would have been forgeable — setting it would make a process believe it was already confined and skip the sandbox entirely, which is a bypass of the whole feature. The payload cannot be forged by anything that did not inherit stdin. A child that finds no valid payload treats itself as the launcher, and a launcher inside a confinement fails closed because it can neither grant ACLs nor bind.
   **Reading stdin is conditional, and the condition is the argv element.** A process started from a shell owns its stdin — the operator's terminal — so a blind read-to-end would block a launcher that nothing launched, waiting for input that is never coming, and look like a hang rather than a refusal. The child therefore reads stdin only when argv carries the listener descriptor, which only a parent puts there; anything else is a launcher, and the payload check still runs on top of that once the bytes are read. Writing the rule as "the child reads stdin and validates" without the precondition would have made the design's own discriminator unreachable.
   **The argv element survives, carrying something else.** `tinio-sandbox-fd=<n>` names the inherited **listener** descriptor, because a socket cannot travel on a stream — the descriptor-passing half of decision 16 is irreducible whatever the payload does. It stays in the core, shared by both launcher platforms: they never interoperate, so a per-platform spelling would work perfectly while drifting unnoticed, which is the failure the core exists to prevent.
18. **The parent never builds a `Config`.** It forwards the configuration's *bytes* without constructing a parsed structure, so the unconfined process retains no credential-bearing object. The one exception is a targeted lookup of `server.read_only`, because the served root's access mode depends on it and FR-023 allows read-only to be set in the configuration file; that lookup reads the single key and drops the document. The parent still has the bytes transiently — it must, in order to forward them — so the property this decision buys is *no retained parse*, not *no contact*.
19. **stdout carries a structured event stream and nothing else; every log goes to stderr.** The endpoint is no longer a human line to be scraped but an event to be decoded: **SSE**, an `event:` line naming the event and a `data:` line carrying its JSON object, closed by a blank line. SSE rather than bare JSONL because an error message containing a newline would otherwise split one record into two and neither half would parse, because the standard already defines how a `data:` value carries newlines, and because the framing is a published standard rather than something this project invents. The name and the payload travel in **different fields** — `sse-core` hands them over as one `MessageEvent { event, data }` — so nothing is stored twice and there is no tie-breaker to need. The child's **stderr is inherited, never piped**: it is the log channel, there is no second stream to drain, and no deadlock to design around.

   Today's contract is `wait_for_ready` reading the child's stdout until it finds `listening on `, and it is brittle in a way that has nothing to do with sandboxes: **any stray write to stdout — ours, or a dependency's — breaks readiness detection**, and it breaks it as a timeout rather than as an error. Reserving stdout for the protocol removes that failure class permanently.

   **Who writes the event differs by platform; what the consumer sees does not.** Linux confines in place, so the process writes its own `Listening` event once the jail is built and the listener is bound. On the launcher platforms the child writes to a stdout that is a pipe to the parent, and **the parent re-emits** — decoding each frame and writing it on rather than forwarding bytes, so a corrupted or foreign line cannot reach the operator. The relay is shared by both launcher platforms and lives in the core, for the same reason the payload does.

   **The parent also owns the answer for a child that never reported at all.** It re-emits what the child sent and emits nothing on its own behalf, so a child that dies before its first frame would otherwise be indistinguishable from one that is still starting — and the consumer would wait for an endpoint that is never coming. The relay therefore records the terminal event it saw, the platform keeps that record beside the child, and the parent reads it **after** the wait: `supervise` borrows the child rather than consuming it, and `Child::wait` joins the relay thread before returning, because the process being reaped and the relay noticing end-of-stream are two events with no ordering between them. Reading the record earlier — the only thing a by-value `supervise` allows — is reading a snapshot, and on a healthy child it usually reads nothing at all.

   Two consequences that were asymmetry under the old contract stop being observable: a consumer no longer cares which process wrote the endpoint, and a startup failure is an event rather than an absence. **One asymmetry remains, and it is about *when* rather than *who*.** The event is always the child's, because only the process serving the data plane can say it is serving. But on the launcher platforms the parent has already bound the port before the child exists, so it *knows* the endpoint well before the stream carries it — and a caller that needs the endpoint before the child comes up is asking for something the event deliberately does not promise yet. The answer is to ask for a fixed port rather than port 0, which such a caller should be doing anyway. Linux is not different in kind: there the process binds after confinement, so `Listening` necessarily follows it.
20. **The child's lifetime is tied to the parent's by a Job object, and the parent forwards termination signals to it.** `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` means killing the launcher takes the confined server with it, instead of leaving an orphaned confined process holding a listener; the residual ACEs that a hard kill leaves are the deterministic SID's problem (decision 21), not this one's. Signal forwarding is the other half of the same obligation and is spelled out in §3 step 9 — **required on Windows**, where a container signals only its main process and nothing else, and defensive on macOS, which has no native container runtime and whose `launchd` reaches the job's process group by default. The two together are what makes "the parent is only a supervisor" true rather than hopeful.
21. **The Windows package SID is derived, not generated.** `DeriveAppContainerSidFromAppContainerName` is deterministic for a given name, so a crash that leaves ACEs behind leaves *identifiable, reusable* ACEs rather than orphans — the launcher takes over its own residue on the next run instead of accumulating new ones. **The same name also creates a container profile** (`CreateAppContainerProfile`), which the measurement of 2026-09-19 shows is required before anything can be launched under that SID at all; it is created on the same pass, taken over on the same `ERROR_ALREADY_EXISTS` path, and removed on the same exit paths, so the residue is two artifacts with one name and one lifetime rather than one.
22. **On Windows the executable's own directory is exposed read-only automatically — and the rule is Windows's alone.** Measured there: without an ACE on the directory holding the binary, the confined child cannot load at all. That is not a policy choice but the difference between working and not, and the directory belongs to the tool rather than to the operator's data, so where it applies the exposure is whole-directory (a Rust binary may load siblings) and the confined process can read its own install directory; that consequence is documented rather than hidden. **An earlier draft generalised this to "launcher platforms", which the macOS measurement does not support**: there a confined binary runs with no grant of any kind on its own location, `process-exec` being the only gate — `file-read-data` on its own image and on its directory is refused and logged, and the program proceeds regardless, for an 81 MB Rust server as much as for a small C tool. Linux never needed it either, the image being already mapped and the jail confining in place. So this is the one platform where the tool's own location has to be granted, and macOS deliberately does not spend a grant on it.
23. **Outside Linux, macOS and Windows, `--sandbox` is a best-effort `chroot(2)` with a startup warning.** No mount namespaces, no capability model and no network isolation are available there; `chroot(2)` delivers the directory boundary and nothing else. The warning enumerates exactly what this platform cannot deliver, every time the flag is used, so the gap can never be inferred as covered. The alternative — refusing to start — was considered and rejected by the operator on 2026-09-18 in favour of "partial and loudly labelled"; this is the one place where the design knowingly delivers one of the three guarantees instead of all three, and it is the reason the Goal scopes itself to three platforms. **No phase of the four delivers it, and since 2026-09-19 the documents say that plainly rather than leaving it to be inferred from the phasing**: an earlier draft presented it as a fourth phase that merely had not been written, but no plan implements it, and P0's facade has no `platform()` outside the three targets — so on a fourth platform the code does not compile and the promised startup warning can never fire. What such a platform gets today is a compile error naming the missing crate, which is the honest outcome and is what §2, §11 and §13 now say. When P4 is written it re-enters this decision as an implemented guarantee with its own evidence, not as a promise.
24. **`sandbox-exec -p` carries the profile inline, with exposed paths passed as `-D` parameters.** The macOS profile is passed as an argv element, so no profile file is created and nothing needs cleaning up. The consequence is that the profile is visible in the process list; its contents are paths, not credentials. `sandbox-exec` has no fd or stdin form, so the alternative was a `0600` temp file with an exit-path cleanup. The two were measured equivalent on macOS 15.8, and the inline form is never the tighter limit: a profile that compiles is bounded by the ~64 KiB compiled-object cap of §5, while argv is bounded by `ARG_MAX`, which is an order of magnitude larger. Exposed paths travel as `-D` parameters referenced by `(param "…")` rather than being interpolated into the profile text, which removes profile injection from path handling entirely: a value is data, and a deliberate attempt to close the literal and open a rule was measured granting nothing. What a parameter *can* do is grant a great deal legitimately — a value of `/` is a valid grant of everything — so **path validation, not the profile text, is what bounds the exposure set**, and the generator validates as it did before. The gain is that escaping and its failure modes disappear from the profile builder.
25. **A configured OTLP endpoint and `--sandbox` are mutually exclusive, and the combination is reported on stderr rather than refused.** The only outbound code path in the runtime is the OTLP-gRPC exporter, and a seccomp filter that blocks outbound necessarily breaks it, so the two cannot both be honoured. **The operator's ruling of 2026-09-19 is that the conflict is a `warn!` on stderr through the sandbox's own tracing, not a startup failure** — an earlier version of this decision made it fatal. The confinement is what was asked for and it is applied; what is lost is the export, and losing an observer is not grounds for refusing to serve. **This is a deliberate exception to the fail-closed posture the rest of this design keeps, and it is only defensible because the warning is unmissable**: it is emitted at startup on the same stderr channel every other sandbox log uses, naming both the endpoint and the flag, rather than logged once and forgotten. The check fires only when both are genuinely active (sandbox requested *and* an endpoint configured), so it costs nothing today: `serve` never passes an endpoint and `otel` is not a default feature.
26. **The confinement is one-way and is entered before the runtime exists.** On Linux `enter()` is irreversible by construction; on all three platforms it must run before any thread is spawned, which §10 orders explicitly and which is what makes the seccomp filter correct without cross-thread synchronisation and what keeps `unshare` from returning `EINVAL`.

## Design

### §1 The crates, the feature gate, and the API

Five crates, layered so no edge points back up (decision 3):

```
tinio-sandbox            facade — target-gated re-export of core + the one platform crate
   ├── tinio-sandbox-core          trait, vocabulary, launcher machinery  (no platform FFI)
   ├── tinio-sandbox-linux         implements Backend: plan, jail, caps, seccomp
   ├── tinio-sandbox-macos         implements Backend
   └── tinio-sandbox-windows       implements Backend
```

**The sketch below is indicative, not normative.** The exact signatures — parameter and return types, owned versus borrowed, which constructor generates what — are fixed in `docs/superpowers/plans/2026-09-18-sandbox-p0-core.md`, which is the plan that builds `tinio-sandbox-core` and the document the platform plans consume. This section states the *shape* and why it is that shape; P0 states the spelling. Keeping a second copy here would recreate the drift that splitting P0 out was meant to end — three documents defining one API is how the platform plans came to disagree about it in the first place.

The core's public surface, in outline:

```rust
/// Whether an exposed path is writable inside the confinement.
/// Not declared here: `tinio-sandbox-core` re-exports `tinio_core::AccessMode`
/// (`ReadWrite` — its `Default` —, `ReadOnly`, `is_read_only()`, `From<bool>`),
/// so an exposure takes the same value the read-only work already resolved.
pub enum AccessMode { ReadOnly, ReadWrite } // stands for `tinio_core::AccessMode`, re-exported

/// The set of host paths the confined process may reach. Pure data.
pub struct Sandbox { /* … */ }

impl Sandbox {
    pub fn new() -> Self;
    pub fn expose(self, host_path: impl Into<PathBuf>, access: AccessMode) -> Self;
    pub fn device_files(self) -> Self;
    pub fn exposures(&self) -> &[Exposure];
}

/// What the call site must do once `confine` returns.
pub enum Confinement {
    /// The calling process is confined; carry on. (Linux.)
    InPlace,
    /// A confined child is running; wait, forward its status, undo the setup.
    Supervise(Child),
}

/// What the launcher needs that is not a path: the child's argv, the payload,
/// the inherited listener descriptor.
pub struct LaunchPlan { /* … */ }

/// What the confined process reports on stdout (decision 19).
pub enum Event {
    /// The listener is bound and the data plane is serving.
    Listening { addr: SocketAddr },
    /// A fatal startup failure, already rendered for the operator.
    Error { message: String },
}

impl Event {
    /// One SSE frame: an `event:` line, a `data:` line and a blank line.
    /// ```text
    /// event: listening
    /// data: {"addr":"127.0.0.1:9000"}
    /// ```
    pub fn encode(&self) -> String;
    /// Decode from a whole frame, or from its two field values; `None` for a
    /// name this protocol does not define, a payload that does not parse, or
    /// anything that is not one of ours. The two-field form is `pub(crate)` —
    /// it is the relay's internal seam, and every outside consumer holds a
    /// whole frame.
    pub fn decode(frame: &str) -> Option<Self>;
    pub(crate) fn decode_fields(name: &str, data: &str) -> Option<Self>;
}

/// The child's parsed stdout, one frame at a time. `sse-core` is the state
/// machine that assembles a frame split across reads — **one decoder for the
/// whole stream**, because the half-parsed event lives in the decoder rather
/// than in the buffer — and `Observer` feeds it and records whether the child
/// ever became ready. **`record` is pure and `observe` is async**: the frame
/// logic is tested without a runtime, and the I/O is async because a launched
/// child's streams are pipes the runtime owns. `reemit` — the one-line relay
/// with no record — is `pub(crate)`, for the reason every launcher-platform
/// decision in this document keeps running into: publishing it would offer the
/// relay without the answer.
pub struct Observer<W> { /* … */ }
impl<W> Observer<W> {
    pub fn new(inner: W) -> Self;
    pub fn record(&mut self, name: &str, data: &str) -> Option<Event>;
    pub fn terminal(&self) -> Option<&Terminal>;
}
impl<W: AsyncWrite + Unpin> Observer<W> {
    pub async fn observe(self, reader: impl AsyncBufRead + Unpin) -> Result<Self>;
}

/// A child a launcher platform started: the platform's wait, the relay's thread,
/// and the relay thread whose **join carries the answer back** — there is no
/// shared cell, because nothing has to be read before the join happens.
pub struct Child { /* … */ }
impl Child {
    pub fn new(wait: …) -> Self;
    pub fn with_relay(self, relay: JoinHandle<Option<Terminal>>) -> Self;
    /// Waits for the child, **then joins the relay** — which is what makes
    /// `terminal` a result rather than a snapshot.
    pub fn wait(&mut self) -> Result<ExitStatus>;
    pub fn terminal(&self) -> Option<&Terminal>;
}
/// Borrows the child rather than consuming it, so the caller can ask
/// `Child::terminal` what happened once the wait is over (decision 19).
pub fn supervise(child: &mut Child, teardown: impl FnOnce()) -> Result<ExitStatus>;
```

The **event name and the payload travel in different SSE fields**, which is the standard's own shape and what `sse-core` hands back as one `MessageEvent { event, data }`:

```text
event: listening
data: {"addr":"127.0.0.1:9000"}
```

Repeating the name as a member of the payload would be one fact stored twice with no tie-breaker when the copies disagreed. `addr` is a `SocketAddr` rather than a string or a bare `IpAddr`: it is exactly what `TcpListener::local_addr` returns, and it is the only form that carries the port, which is what `--port 0` exists to discover. The framing is `sse-core`'s resumable state machine rather than a line reader because a child's stdout is a pipe and a frame can arrive in pieces; that crate is also the reason no async-runtime baggage enters the dependency graph (`sse-stream` would have brought `futures-util` and `http-body` unconditionally, and depends on `sse-core` itself). **The child's stderr is inherited, never piped** — so there is no second stream to drain and no deadlock to design around (decision 19).

```rust
pub trait Backend {
    fn confine(&mut self, sandbox: &Sandbox, plan: &LaunchPlan) -> Result<Confinement>;
}
```

A `Sandbox` is pure data. The mount table, the mirrored jail paths, the SBPL profile text, the ACL grant list and the capability policy are all pure functions of builder state — but they belong to the platform crates, not the core, because each is a function of one mechanism. What the core keeps is what more than one platform needs: the exposure vocabulary, and the launcher machinery both child-launching platforms share (decision 17's payload and the supervision loop).

The core holds the launcher machinery rather than the facade because the platform crates need it and depend on the core — putting it in the facade would recreate the cycle decision 3 exists to avoid.

Consumers gate on it: `tinio-server` gains an optional `tinio-sandbox` dependency behind a default-on `sandbox` feature, referenced by the `serve` example through `required-features`; `tinio-cli` will do the same. With the feature off, all three request channels are a usage error (decision 5). A consumer that wants a specific platform's options instead of the facade's default selection depends on that platform crate directly — which is what the facade's own tests do.

### §2 The platform matrix, and the guarantees

| Platform | Mechanism | Enforces | Path namespace |
|---|---|---|---|
| Linux | mount namespace + `pivot_root` | both guarantees | **hidden** — paths outside the jail do not exist |
| macOS | Seatbelt, SBPL via `sandbox-exec -p` | both guarantees | visible, access denied |
| Windows | AppContainer + DACL | both guarantees | visible, access denied |
| other unix | `chroot(2)` (decision 23) — **not delivered by any of the four phases**; such a target fails to compile rather than warning | directory boundary only | visible, access denied |

On Linux `ls /` inside the jail shows the tmpfs and the exposed paths and nothing else. On the other three the path namespace remains enumerable and a non-exposed path is refused rather than absent — **but the refusal is not always distinguishable from absence**, and an earlier version of this paragraph promised that it was. Measured on macOS 15.8 on 2026-09-19: a read outside every grant returns `EPERM(1)`, while a read under a directory whose traversal is refused can return `ENOENT(2)`, which a caller cannot tell from a genuinely missing file. Add that the macOS allowance set legitimately grants read on directories the operator never exposed (§5), and "this path is not there" is a weaker inference on that platform than on Linux. The guarantee is identical on all three; what a caller can infer from the errno is not. The guarantee is identical; what the caller can *observe* about the filesystem layout is not, and the documentation says so rather than implying parity.

`expose` maps onto each mechanism directly:

| | Linux | macOS | Windows |
|---|---|---|---|
| `ReadWrite` | `bind` | `(allow file-read* file-write* (subpath …))` | DACL `M` |
| `ReadOnly` | `bind` + `remount,bind,ro`, under either model, or overlay `MS_RDONLY` where the filesystem refuses it | `(allow file-read* (subpath …))` | DACL `RX` |
| state dir | `bind`, always `rw` | `file-read*` + `file-write*`, always | DACL `M`, always |

### §3 The launch contract (macOS and Windows)

Steps 6–8 below are the **core's** launcher machinery (`tinio-sandbox-core`, built by P0), not either platform's: the stdin payload, the supervision loop and the exit-status forwarding are identical whether the child is an AppContainer or a Seatbelt profile, and only steps 2, 4, 5 and the `CreateProcess`/`sandbox-exec` call in step 6 differ. That shared half is built and tested in P0 even though both child-launching backends are stubs there — the platform crates cannot be written before the trait they implement has been exercised from both shapes, and a trait with one implementor is a guess.

The parent performs the privileged setup and then supervises:

1. Parse `argv`; compute the served root and the state-directory candidates from `argv` and the environment.
2. Targeted-lookup `server.read_only` from the configuration bytes (decision 18) and overlay `TINIO_READ_ONLY` and `--read-only` on the result to fix the served root's `AccessMode`, then drop the document. Only the file channel needs the probe: the other two the launcher reads directly, and the child re-derives the same answer from the same three sources.
3. Bind the listener, mark it inheritable, and keep it alive for the whole run.
4. Compute the exposure set: the served root (per step 2), the state directory if it lies outside the root, the executable's directory as `ReadOnly` (decision 22), and the device files.
5. Apply it — DACLs on Windows (before `CreateProcess`, or the child cannot load), the `-p` profile on macOS.
6. Create the process: `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` plus `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` in a `STARTUPINFOEX` with `EXTENDED_STARTUPINFO_PRESENT` on Windows; `sandbox-exec -p … <self> <args>` on macOS. Assign the child to a Job object (decision 20).
7. Write `{"config":"…"}` — one JSON line — to the child's **stdin** and close it (decision 17); the inherited listener's descriptor number travels in argv, because a socket cannot ride on a stream.
8. Supervise: **relay the child's stdout events** — the `Listening` frame among them — wait for the child, roll back the ACLs, and forward the exit code. **The parent does not emit a `Listening` event of its own**, even though it is the process that bound the port: the event means the data plane is serving, only the child knows that, and a parent that printed the endpoint it had bound would be announcing a server that may never accept. What the parent does emit is its own `Event::Error` when the child exits without ever having reported — read from `Child::terminal()` **after** the wait, which is what `supervise`'s borrowed child and `Child::wait`'s join of the relay thread exist to make possible (decision 19).
9. **On Windows, forward termination signals to the child while waiting** (decision 20). On a console the whole process group receives Ctrl+C, and a Unix supervisor usually reaches the child anyway, so it is easy to conclude forwarding is unnecessary. **Measured on this machine's host console on 2026-09-19, and the conclusion is the opposite of that intuition**: the reason is not container behaviour but `CREATE_NEW_PROCESS_GROUP` — the flag the launcher itself passes so the relay has a group to address — because a console-wide `CTRL_C_EVENT` (group 0, what a Ctrl+C keypress produces) fires the launcher's own handler in the same millisecond and **never** reaches the child's, which keeps serving; the identical call reaches a child created *without* the flag. A launcher that forwards nothing therefore leaves the confined server to be terminated at the end of the grace period instead of draining, silently trading away the graceful shutdown the CLI contract promises — ≤10 s of in-flight drain and a removed state file — for whatever a hard stop leaves behind. The container half of the original claim remains unmeasured here (this machine has no Windows container engine), and it is no longer load-bearing: the host-console measurement alone makes the relay mandatory.

**The obligation is Windows-only, and it is worth being precise about why.** Linux confines in place (decision 6), so under a Linux container the server *is* PID 1 and receives the signal directly — the hazard cannot arise. macOS has no native container runtime, and the containers that do run on a Mac are Linux VMs whose tinio takes the Linux path; `launchd`, the only supervisor that matters there, signals the job's whole process group by default. macOS should still relay defensively, because the cost is a few lines and the failure is silent, but Windows is where leaving it out is a defect rather than a polish item.

Forwarding is a platform obligation, not core machinery: the handler must be async-signal-safe, and it needs the child's identity, which the platform crate that created the child already holds. `tinio-sandbox-core` therefore does not change — the platform backends install the handler and relay before calling `supervise`.

The child is identified by step 7's payload, never by an environment variable (decision 17). Its argv carries the inherited listener's descriptor number and nothing else that is security-relevant; a child that cannot obtain a valid payload treats itself as a launcher, which inside a confinement fails closed.

The relay in step 8 is what makes stdout trustworthy on the launcher platforms: the parent decodes each frame and writes on only what parses as one of our events, so anything else the child or its dependencies print to stdout is dropped rather than passed to an operator who would have no way to tell it apart from a real event. The child's **stderr is inherited untouched** — that is where every log goes, and the parent does not mediate it.

### §4 The Linux mount table

The new root is a tmpfs mounted on `$TMPDIR/.tinio-jail-<hash(root)>` (decision 10), mounted `size=1m,mode=0755`. The jail's own writable space is deliberately small: what lives in it is mount points, the `put_old` directory, and — for a read-only exposure under the user namespace — the overlay's `upper` and `work` directories under `<jail>/.overlay/`. **That directory is reachable by the confined process** and shares the same 1 MiB. **An earlier version of this sentence said a write aimed at a read-only exposure's upper fails with `ENOSPC`, and that path is unreachable**: the overlay is mounted `MS_RDONLY` from the start, so such a write is refused by the mount with `EROFS` and never reaches the tmpfs quota. The `size=1m` is therefore a bound on what the *jail itself* costs rather than a second wall behind the read-only mount — and it is worth doing the arithmetic the constant implies, because otherwise it reads as a guess: what lands in it is mount-point directories, the mirrored path prefixes, `put_old` and `.overlay/{upper,work}` — directories and dentries, which `size=` does not bound the way it bounds file data. The one thing the constant does *not* bound is the host `$TMPDIR` space the jail occupies. For each exposed path the jail creates the **original absolute path** inside the tmpfs and mounts there:

| Path inside the new root | Contents |
|---|---|
| `/` | the tmpfs |
| `<served root>` | `ReadWrite`: `bind`. `ReadOnly`: `bind` then `remount,bind,ro` — available under either model for ext4, drvfs and the like, per the re-measurement recorded above. Where the served root's filesystem refuses the remount, the fallback is `overlay(lowerdir=<served root>, upperdir/workdir on the tmpfs)` mounted `MS_RDONLY`, which is read-only by construction |
| `<state dir>` — only when it lies outside the served root | `bind`, always `rw` |
| `/dev/{null,zero,random,urandom}` | file-level bind |

then `pivot_root(jail, jail/.oldroot)` followed by `umount2("/.oldroot", MNT_DETACH)`.

Two mount details the table cannot show. **Every bind is recursive** (`MS_BIND|MS_REC`): inside a user namespace a bare `MS_BIND` of a mount-point source is refused with `EINVAL` (measured), and the difference between the two forms is invisible for a source with no submounts — so the recursive form is the one to write everywhere rather than the one to special-case. And **`/` is made private** (`mount(NULL, "/", MS_REC|MS_PRIVATE)`) before anything is mounted, because `pivot_root` requires it; on the host measured this is already the case, so the call is defensive, one syscall, and the reason it is unconditional is that the hosts where it is not already private are exactly the ones where the failure would be a confusing `EINVAL` at the pivot.

The `/dev` mount points are created as empty files inside the tmpfs, so nothing is ever created inside the served root — not even a mount point. That property is what makes a genuinely read-only root survivable: `pivot_root` needs `put_old` to already exist *inside the new root*, and a compose-in-tmpfs design satisfies that without writing a byte to the data.

The executable's directory is **not** in this table: Linux confines the process it is already running in, so the image is mapped and needs no exposure (decision 22).

**The overlay variant was justified by a rule that re-measurement has since falsified, and what is left is a choice rather than a constraint.** The earlier text here said the overlay "exists only because" an unprivileged user namespace cannot remount a bind of a host-owned superblock read-only. Re-measured on 2026-09-19, that is not true of the filesystems a served root lives on: an ext4 bind and a drvfs (`/mnt/e`) bind both take `MS_REMOUNT|MS_BIND|MS_RDONLY` under an unprivileged user namespace, and the write through them then fails `EROFS`. What refuses is the family a user namespace may mount itself — tmpfs, devtmpfs, procfs, sysfs, and a tmpfs subdirectory with them — which a served root is not.

So the old argument is gone and the rule it left behind is a different one: **the mechanism follows the filesystem, not the model.** Every `ReadOnly` exposure is planned as a plain bind under either model, and what makes it read-only is the mount step — `mount_remount(target, RDONLY | BIND, "")` first, and on `EPERM` from a kernel-managed filesystem the same target is re-mounted as an `MS_RDONLY` overlay. The overlay is therefore the fallback rather than the default, and the condition that selects it is one errno in one place, which is what keeps a `plan`-time decision out of a code path that performs no syscall and cannot know. **An earlier version of this paragraph made the choice P1's to state; the table and decision 8 have since settled it, and P1 implements it as written here.**

**One overlay pair serves one read-only exposure, so the user-namespace model admits exactly one of them.** An upper directory is bound to a single lower for the lifetime of the mount, and every read-only exposure would otherwise share the one pair the jail creates. The served root is the only read-only exposure any caller produces today, so the composition **refuses a second one explicitly** rather than letting two mounts race for the same upper and surface as an overlayfs error nobody can read. Giving each exposure its own pair is the change to make when a second one actually appears.

### §5 The macOS SBPL profile

Measured text — this is the profile that was run on macOS 15.8 and made a confined process take a connection it had been handed. One `(allow …)` per exposed path, over a `(deny default)` base:

```
(version 1)
(deny default)
(allow process-exec)
(allow process-fork)
(allow signal (target self))
(allow sysctl-read)
(allow file-read-metadata)
(allow file-read* (literal "/"))
(allow file-read* (subpath "/usr") (subpath "/System") (subpath "/Library"))
(allow file-read* (subpath "/bin") (subpath "/sbin") (subpath "/etc"))
(allow file-read* (subpath "/private") (subpath "/dev"))
(allow file-read* (subpath "<served root>"))
(allow file-read* file-write* (subpath "<state dir>"))
(allow file-write* (literal "/dev/null") (literal "/dev/stdout") (literal "/dev/stderr"))
```

Four of these are load-bearing in ways that cannot be guessed, and each was measured by removing it and watching what broke:

- **`(literal "/")` is what lets the process start at all.** A `(deny default)` process whose profile omits it dies of SIGABRT, and the only violation logged is `file-read-data /`. Granting every prefix *under* the root does not substitute — the refused read is of the root directory itself. This is the first thing P3 must get right, because its failure mode is a bare abort with no message.
- **`process-exec` is not optional.** Without it `sandbox-exec` cannot exec the target at all and exits 71 before any other rule is consulted. **The rule is emitted filtered rather than blanket** — `(allow process-exec (literal <the child's own path>))`, the path coming from the same value the argv's program element is built from, so the rule and the exec cannot drift. The reason is that the measurement above establishes only that *an* exec must be permitted; an unfiltered rule, over a profile that also grants read on `/bin`, `/usr` and `/private`, lets the confined process execute any readable binary it likes. This narrowing is **not** among the measurements — it is a change of the emitted text away from the text measured here — so its failure mode is recorded instead of assumed: a refused exec is `rc=71` with `execvp()`'s diagnostic, and a spelling `sandbox-exec` will not compile is `rc=65`, which the pre-flight catches. If a second exec turns out to be required, the blanket rule returns **with the over-grant written down beside it**, never quietly.
- **`sysctl-read` sizes the runtime.** Removing it makes `sysconf(_SC_NPROCESSORS_ONLN)` return -1, so `available_parallelism` fails and tokio cannot size its pool. The design asserted this before measuring it; it holds.
- **`file-read-metadata` is one of two things symlinked paths need, and neither substitutes for the other.** `/tmp`, `/var` and `/etc` are symlinks at the root, and walking a path spelled through one of them is itself a metadata operation: `(subpath "/private/tmp")` — and even the literal full path — is refused without the blanket allowance. But metadata alone does not make a rule *match*: Seatbelt compares the rule's literal spelling against the kernel-resolved path, so a grant written on `/tmp/grill` grants nothing for a file at `/private/tmp/grill/real/inner.txt`, and both command spellings are refused. Each is needed for its own reason — metadata to walk the link, and the canonical spelling to match what it resolves to — which is why the profile carries both the blanket allowance and `with_canonical_paths`. The cost of the allowance is stated rather than hidden: existence and timestamps can be probed outside the grants, contents cannot.

The `ReadOnly` / `ReadWrite` distinction is exactly the presence or absence of `file-write*` on the served root, which is why decision 8 needs no macOS-specific concept — and it was measured: with only a read grant, create, append, truncate, unlink and chmod all fail inside the served root while reads succeed, and no write grant anywhere else refuses every write outside the exposure set.

**The allowance set is a target rather than a finished list, and this platform is where the Goal and the profile are furthest apart.** Two of the rules above are blanket grants over trees the operator did not expose — `/private` recursively and `/etc` — and `(allow file-read-metadata)` is blanket by construction. The Goal says the confined process reaches "exactly the directories the operator exposed, and nothing else"; on this platform a path under any of those trees returns **data** rather than a permission error, so a path-traversal or symlink bug in the server can serve `/private/etc/*` to a remote client — which is the failure class the Background names. The emitted set is therefore required to be pruned to the subpaths the crate actually needs, rule by rule, with the observation that keeps each one (P3 Task 5's experiment is the method and it is a required step, not a follow-up); `/private` is the largest and the plan already flags it as reducible. What cannot be pruned away — `(literal "/")`, `process-exec`, `sysctl-read`, `file-read-metadata` — is the measured price of the process starting at all, and is recorded as such rather than as a grant the design chose.

**Network: the profile grants nothing at all, and the server still serves.** The parent binds the listener (decision 16), and `bind()` and `listen()` turn out to be the only operations the sandbox gates — `accept()`, `recv()` and `send()` on an inherited listener are not checked at all. A profile carrying **zero** network rules was measured taking a real connection out of an inherited listener's backlog, with no `accept` violation in the kernel log. So the macOS row of §7 is not "never grants `network-outbound`"; it is **no network capability of any kind**. That is a stronger statement than Linux's seccomp filter makes (which cannot see a `sockaddr` and so cannot restrict inbound) and stronger than Windows's absent capability makes (which the design has not verified blocks outbound, and which on that platform also constrains inbound). macOS is the one platform where the network guarantee is absolute in both directions, and it comes from the handoff the design already specified.

Three allowances the design had guessed at are **not** needed and are dropped. `mach-lookup`: with it removed every check still passes except `getpwuid`, whose failure names `com.apple.system.opendirectoryd.libinfo` — and the serve path does not resolve users. The allowance for `com.apple.system.logger` in particular was invented and is not required. `system-socket`: it is a genuine privilege rather than a no-op — removing it turns `socket(PF_SYSTEM, SOCK_DGRAM, SYSPROTO_CONTROL)` from accepted to refused — and nothing measured has a caller for one, so carrying it would be granting a capability for no reason. `ipc-posix-shm` was tested beside it and is likewise needed by nothing. A profile is a list of privileges, and one carried without a caller is exactly what this section exists to remove; the way to keep it honest is the tool that produced the list, `log show --predicate 'sender == "Sandbox"'`, which names the refused operation rather than leaving it to be discovered at runtime.

Two operational limits belong here because they are the profile's, not the crate's. The compiled profile is capped near 64 KiB: 10000 small rules compile and 12000 fail with `data object length … exceeds maximum (65535)`, while a *single* operation carrying 9000 path literals fails earlier with `profile compilation failed` — so a large exposure set must be emitted as separate `allow` operations, and the generator **refuses above 4096 exposures** rather than letting `sandbox-exec` report it: 2.4× below the measured cliff and far past any operator's exposure set. The refusal names the exposure that crossed the line and reports it as `Error::BadPath` — the variant whose own definition is "a path handed to `Sandbox::expose` cannot be expressed inside the confinement", which is precisely what the 4097th one is. Refusing rather than truncating matters: a profile that silently dropped exposures would be a confinement that silently granted less than the operator asked for, and the server would serve a subset of its data with no explanation. **This refusal is macOS's alone, and the asymmetry is the platform's rather than an omission in the other two plans**: the cap it guards is the *compiled profile's*, which only Seatbelt has — Linux's mount table and Windows' ACL list are bounded by what the operator asked for and by nothing else in the mechanism, so a library consumer can hand either of them an exposure set that makes a diagnostic string or an argv arbitrarily long. A shared bound would be a number the other two platforms have no reason to defend. And the way to keep this set minimal is the tool that produced it: `log show --predicate 'sender == "Sandbox"'` prints every refused operation with its path and needs no elevation.

The text is passed to `sandbox-exec -p` (decision 24), which applies it to the child before exec; exposed paths travel as `-D` parameters rather than interpolated into the text, which was also measured working. The profile is `(deny default)`, so a path or a network operation not named in it is refused — the same default-deny posture AppContainer gives on Windows, reached through a different kernel facility.

### §6 The Windows ACL whitelist

`DeriveAppContainerSidFromAppContainerName("<name>")` yields a deterministic package SID without elevation. The launcher grants, per exposed path:

- `ReadWrite` → `(OI)(CI)M`
- `ReadOnly` → `(OI)(CI)RX`
- ancestors → nothing (verified: AppContainer tokens carry bypass-traverse, so only the exposed directory's own ACE matters)

**The `(OI)(CI)` form is sufficient, and P2 settled it by measurement on 2026-09-19.** The open question was whether inheritance reaches children that already existed when the ACE was set; it does, on both filesystems in use here. A directory-only `icacls /grant:r "*<sid>:(OI)(CI)M" /q` — no `/t` — put an inherited `(I)(M)` entry on a pre-existing file at depth 1 and at depth 2 of the served tree, and on the intermediate directory as `(I)(OI)(CI)(M)`, identically on NTFS (`C:`) and ReFS (`E:`); `.NET Set-Acl` reproduced it through a different API with `IsInherited: True`, so the propagation is the filesystem's rather than the tool's. The grant list is therefore **one ACE per exposed directory** and the rollback is **one `/remove:g` per directory**: the launcher issues `2N` `icacls` invocations for `N` exposures, and neither it nor the tool walks the tree — the per-file `/t` walk and its per-file rollback story are not needed and are not used. **The filesystem does the walking, though, and an earlier version of this paragraph read that as the absence of a cost rather than as one.** Inheritance is exactly what the measurement above demonstrates: the `(OI)(CI)` ACE reaches every pre-existing descendant of each exposed directory, so both the grant pass (before `CreateProcessW`) and the rollback pass (after the child exits) touch as many objects as the served tree contains — twice per run, proportional to the whole corpus. **Nothing measures it**: no `icacls` timing, no per-object cost and no tree-size assumption appears in any of these documents, while the readiness budget the feature has to fit inside is 30 s (the e2e harness's start timeout) and the CLI contract's graceful-shutdown drain is ≤10 s. P2 establishes the number rather than assuming it, and the Risks table below records what an operator with a very large tree should expect. Two measured consequences bound that answer: an inheritance-flagged grant applied to a *file* reports success and writes nothing, so a per-file grant would have to drop the `(OI)(CI)`; and an ACE written *explicitly* on a file does not go away when the directory's copy is removed, which is why the rollback removes from exactly the paths it granted on and never assumes a directory-level removal reached further.

and launches itself with `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` in a `STARTUPINFOEX`, `EXTENDED_STARTUPINFO_PRESENT`, with the capability list from configuration (empty by default; §7 states the network policy and why the default is what it is).

Verified end to end on both filesystems an operator is likely to use: a Rust binary loads, a granted tree is readable, a non-granted tree is denied despite carrying `Users` and `Authenticated Users` ACEs, and an `RX`-only grant rejects writes. ReFS and NTFS produced identical results for every case.

**What the grant follows is part of the exposure decision rather than an implementation detail.** `icacls` resolves the path it is handed and `(OI)(CI)` is inheritable, so a reparse point — a junction or a symlink — inside the operator's tree redirects the grant to whatever it names, and the confined process then holds `M` on a tree nobody exposed. That is the same class as the symlink-following bug the Background cites, and it is the Windows half of what macOS meets with `with_canonical_paths` (decision 24). **An exposure is canonicalised before it is used, and a path whose canonical form is a reparse point is refused rather than followed**, so the outcome is a startup error naming the path instead of a silently wider grant. Linux does not need the rule: the jail mirrors host paths, so a link inside the tree resolves within the jail to a path that was never mounted, and it fails closed.

**The derived SID is not by itself enough to launch: the container profile has to exist.** Measured on 2026-09-19, `CreateProcessW` with `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` for a merely-derived name fails `err=2 (ERROR_FILE_NOT_FOUND)` — for the test binary and for `cmd.exe` alike, with the SID's ACE already on the tree — and `CreateAppContainerProfile` (userenv.dll, unelevated, returning the same SID as the derivation) makes the identical call succeed. So the launcher creates the profile as well as the ACEs, `ERROR_ALREADY_EXISTS` is the takeover path rather than an error, and the profile joins the ACEs as **a second artifact decisions 15 and 21 have to roll back**: `DeleteAppContainerProfile` on the same exit paths, and the same deterministic-name property, since the profile's SID is the derivation's.

The residual cost, which cannot be designed away: **the launcher writes ACEs onto the operator's directories**, and a hard kill between grant and rollback leaves them. Decision 21 bounds the damage to identifiable, reusable ACEs; the launcher takes over its own residue on the next run and removes it on every exit path it survives (decision 15).

### §7 Dropping privileges and cutting the network

**The uniform network rule, on the three supported platforms: the confined process cannot initiate an outbound connection.** Inbound is untouched and follows the bind address the operator configured — the sandbox never widens it and never silently narrows it beyond what the platform's confinement enforces.

| Platform | Mechanism | Notes |
|---|---|---|
| Linux | seccomp-BPF filter denying `connect`, `sendto`, `sendmsg` and `sendmmsg` | Decision 13. The filter sees no address family, so an `AF_UNIX` connect is denied with the rest. Degrades on an architecture with no syscall table (the filter is skipped and reported, §11); a refusal to *install* on a covered architecture stays fatal |
| macOS | the profile grants **no network operation of any kind**; base is `(deny default)` | measured: with zero network rules the confined process still accepted a real connection from a listener the parent had bound and handed in. `bind()` and `listen()` are the only gated operations — `accept` is not checked — so the profile needs no `network-bind` and no `network-inbound`. Outbound is refused absolutely, and the refusal covers more than `connect`: a `sendto` on an unconnected datagram socket is refused too, a unix-socket connect to `mDNSResponder` is logged as `network-outbound` so even name resolution does not escape, and raw sockets cannot be opened under any profile tested. The one egress-adjacent thing that is *not* a network rule is `system-socket`, which admits an `AF_SYSTEM` kernel-control socket; it is a separate allowance, nothing needs it, and §5 drops it |
| Windows | AppContainer with no network capability | loopback verified; the outbound claim is not (see the verification gap) |
| other unix | **nothing** | decision 23; the startup warning says so |

One asymmetry is inherent and must be documented rather than papered over: on Windows the container's own network isolation also constrains *inbound* — a process with no network capability cannot accept from the LAN — so `--sandbox` plus a non-loopback bind needs `privateNetworkClientServer`, and without it the listener is loopback-only whatever the bind address says. **Handing the listener in does not change this** (decision 16): the policy is applied to the process, not to the socket's origin, which is exactly why the design does not lean on the handoff for isolation. On Linux the filter cannot see a `sockaddr` (seccomp cannot dereference pointers), so a non-loopback bind still accepts from the network. A Linux deployment that wants Windows's stricter posture has to get it from the bind address, which is where it belongs.

macOS lands on the same posture as Linux — inbound governed by the bind address and nothing else — but reaches it by not checking `accept` at all rather than by failing to see the address, and its outbound refusal is the strongest of the three. So the three platforms agree that outbound is cut, and differ in what they do about inbound: Windows narrows it whether the operator wants that or not, Linux and macOS leave it to the bind address. That is the honest shape of the guarantee — "cannot initiate outbound" is uniform, "inbound follows the bind address" is uniform in intent and enforced by different means.

**Verification gap.** The Windows outbound row is not verified. Probe results on this host showed loopback bind and connect succeeding with an empty capability set (solid), but every non-loopback TCP connect refused identically with *and* without `internetClient`, including a refusal of `1.1.1.1:53` that reads as this host's own firewall or routing policy rather than as container isolation. The claim that an absent capability blocks outbound is Microsoft's documented behaviour, not something this document measured. P2 must establish it on a host where the baseline is known to work.

### §8 Capability dropping (Linux)

**The prefix, before any of this: write the maps.** The user-namespace model is entered in two steps — `unshare(CLONE_NEWUSER)`, then `/proc/self/{setgroups,uid_map,gid_map}` written with `deny` and `0 <euid> 1`, then `unshare(CLONE_NEWNS)` and the jail (decision 12). The order is forced from both sides: the map descriptors cannot be opened before the user namespace exists (measured: `EPERM` on a pre-opened descriptor, `EACCES` opening `setgroups`), and the host's `/proc` is gone once the mount namespace is created. Skipping the maps is not survivable either — **on a superblock the namespace itself owns** an unmapped gid makes `mkdir` and file creation fail with `EOVERFLOW(75)`, so `local_uid` and the `CAP_CHOWN` row below are not the only things that need a mapped identity. Re-measured 2026-09-19, the qualifier matters: with no maps at all, `mount("tmpfs", …)` still succeeds and creating a file on the **host's** ext4 succeeds too (the host sees it owned by the real uid), while `mkdir` and `open(O_CREAT)` inside the namespace-owned tmpfs fail `EOVERFLOW`. The jail is built inside that tmpfs, which is why the maps are load-bearing here.

Fixed order, after the jail is built: `prctl(PR_SET_NO_NEW_PRIVS, 1)`, then `PR_CAPBSET_DROP` for every capability not retained, **then** `capset` to clear effective/permitted/inheritable, and last the seccomp filter — all mounts are done by then, and `PR_SET_NO_NEW_PRIVS` must already be set for a filter to be installable without `CAP_SYS_ADMIN`.

**The sweep comes before the `capset`, and an earlier version of this paragraph had it the other way round.** `PR_CAPBSET_DROP` needs `CAP_SETPCAP` in the **effective** set at the moment of the call: re-measured 2026-09-19 on WSL2, with caps intact the drop returns `0` and `PR_CAPBSET_READ` flips to `0`, while after a `capset` clearing effective and permitted it returns `EPERM(1)` and the bounding set is left untouched — with or without `PR_SET_NO_NEW_PRIVS` set first, so `no_new_privs` is not a substitute. An implementer following the old order would get a bounding set that silently stayed populated. `CAP_SYS_ADMIN` goes with the rest — once the mount table is built there is nothing left to mount.

Installing the filter before any thread exists is what makes it correct: a seccomp filter applies per-thread unless `SECCOMP_FILTER_FLAG_TSYNC` is used, and there is nothing to sync when the process is still single-threaded. It is the same reason `unshare` must run early, and §10's ordering covers both.

| Mode | Retained capabilities |
|---|---|
| Read-only | none |
| Read-write | none, **except** `CAP_CHOWN` when a `local_uid` mapping is configured (FR-033 chowns landed objects) |

Two consequences to document rather than discover:

- **Running as root, `--sandbox` makes root capability-less.** Files under the served root that are not owned by the service account lose DAC override and become unreadable, surfacing as `AccessDenied`. The served root is expected to belong to the service account; this is a behaviour change for root-run deployments and belongs in the flag's documentation.
- **A user namespace cannot chown to an unmapped uid.** `local_uid` mapping plus the user-namespace model fails at startup with a configuration error pointing at the root model, rather than failing later on the first object write. The check is explicit and runs **before the availability probe**, so an operator who asked for an impossible combination is told so without a namespace ever being created.

### §9 Read-only mode is a value, not a mechanism

The sandbox takes a set of `(path, AccessMode)` pairs and does not know how they were derived. In normal mode the state directory is `<root>/.tinio`, inside the served root, so it needs no entry of its own. **FR-023 has landed**, so in read-only mode the state directory is `TINIO_STATE_DIR` or `<home>/.tinio/roots/<hash>/` — outside the served root — and the same `expose` call gains one `rw` entry and the mount table gains one row. **No code in this design changed when read-only mode landed**, which is the property this section was written to have; what it cost was one line at the call site and one row in the table, and both were already written.

**The mode's precedence is the configuration's, then the environment's, then the flag's** — `[server] read_only` → `TINIO_READ_ONLY` → `--read-only`, in `serve.rs` — and `AccessMode` is the value that carries the result. A launcher platform reaches the same answer through decision 18's targeted probe, because it must not retain a parsed `Config`; the two processes therefore agree on the mode without either of them parsing the document.

The read-only *mode* and the read-only *mount* are separate: `--read-only` decides where state lives and refuses writes at the API layer (FR-023); `--sandbox` makes the served root unwritable at the kernel layer. They compose, and each works without the other. On the three supported platforms the second is real enforcement; on the fallback path of decision 23 only the first exists, and the startup warning says so.

One combination is refused deliberately: read-only mode with a state directory inside the served root. The confinement would make that directory unwritable and the server could not start. It now takes an explicit `TINIO_STATE_DIR` pointing under the root to reach, since read-only mode relocates state by default — and it is refused twice over, rather than once: `FsStorage::new` rejects it (`crates/tinio-fs/src/backend/mod.rs:398-418`), and the two launcher platforms reject it one process earlier, before anything is granted or launched, because a failure inside the confinement is the more expensive way to learn it. Failing closed with a clear message is better than a server that dies on its first log write.

### §10 Entry-point wiring

`unshare(CLONE_NEWUSER)` returns `EINVAL` in a multi-threaded process (verified), and `#[tokio::main]` builds its multi-threaded runtime inside `main`. The entry point therefore stops being `#[tokio::main]` and becomes a plain `fn main` that confines first:

```
fn main()
 1. read the launch payload if one was inherited   -> confined child: jump to 8
 2. parse arguments
 3. load configuration (host paths, read before the pivot)
 4. ensure_chown_privilege, and resolve the mode  config -> TINIO_READ_ONLY -> --read-only
 5. create_dir_all(root) and the state dir        the bind sources must exist first;
                                                  read-only creates no root and keeps
                                                  no state inside it
 6. macOS / Windows: bind the listener, apply the exposure set, launch the child
    Linux:           the Linux backend confines in place
 7. macOS / Windows: supervise — relaying the child's events, and turning a child that never reported into an `Error` — roll back, forward the exit code
 8. Builder::new_multi_thread().build()?.block_on(serve(...))
```

Step 1 is the discriminator of decision 17 and comes first, before anything else, so a confined child does no privileged work on its way in. Step 6 is skipped on Linux, where the process binds its own listener after `enter()` and prints the endpoint itself (decision 19). The bind sources must exist before step 6, and no thread may exist before it either — both of which the sequence satisfies.

**One precondition the sequence does not express is that `$TMPDIR` must be writable.** The jail is a tmpfs mounted under `std::env::temp_dir()`, so on Linux it is the one host resource the confinement itself consumes — and a read-only or full `$TMPDIR` makes the confinement fail before any later step does. The failure is a startup error that names `$TMPDIR` and its errno rather than the bare `create jail root` step, because the resource that ran out is not the served root and an operator told only "create jail root" looks there first.

**Steps 4 and 5 are FR-023's, and they are guards rather than additions.** The chown probe writes a scratch directory *inside the served root*, and creating the root writes the one thing read-only mode promises to leave alone, so both are skipped when the mode is read-only; and the state directory is resolved to the relocated path rather than to `<root>/.tinio`, because it is one of the paths a launcher platform has to expose. On Linux the sequence is the whole of `main`, in place; on the two launcher platforms the same steps run in the parent, and the child re-derives the identical answer from the payload's configuration bytes, the environment and its inherited argv.

Because the Linux jail mirrors host paths (decision 9), step 8 is **byte-identical with and without `--sandbox`**: same root path, same state-dir path, same relative-path resolution.

**Step 6 is where the two shapes differ, and the difference is configuration rather than dispatch.** A Linux run has settings the other two do not — `LinuxOptions`, carrying `Mechanism` (decision 7) and the capability policy — and a status to report back, the `seccomp()` answer that says whether the filter was installed or skipped for an architecture with no syscall table (§7, §11). Those live in `tinio-sandbox-linux` and are reached from the example through a `#[cfg(all(feature = "sandbox", target_os = "linux"))]` block that names the crate directly; a macOS or Windows run reaches its backend through the facade's `platform()` and needs nothing more, because neither has an equivalent setting. The cfg block is therefore the visible edge of decision 2's boundary, not a failure of it: the shared surface is what drives a confinement, and a platform's own vocabulary stays with the platform.

**Step 1's jump, the confined child's own entry point, is per-launcher-platform and gated as such.** Each of macOS and Windows writes its own `confined`, gated by the feature *and* its own `target_os` — not by the feature alone, because what it calls is platform-specific and a feature-only gate would name functions that do not exist on the other two targets. Linux writes none: it confines in place and never re-invokes itself, so the entry is never reachable there and `adopt` returns `None`. The two bodies differ — Windows installs a stop hook the child side owns and macOS does not — but they agree on the one thing shared code must agree on: **the listener is rebuilt through a single platform-neutral facade name**, `adopted_listener`, rather than by a method on core's `Adopted` or by naming the platform crate. That name is decision 2's rule applied to the child side, and it is why `Adopted` carries the descriptor number rather than a socket: the rebuild is each platform's own, and the facade is where shared code finds it.

### §11 Errors and failure handling

`enter` and `launch` return `Result`. Failure is always fatal: the process never continues unconfined, because a server that silently runs without the confinement its operator asked for is worse than one that refuses to start. **The one row below that is not fatal is not silent either** — a skipped filter is reported through the return value, not logged and forgotten, so the caller can warn without the confinement being the thing that failed.

| Condition | Response |
|---|---|
| Sandbox requested in a build without the feature | usage error (exit 2) naming the build (decision 5) |
| Sandbox requested through a channel this phase does not implement (`[server] sandbox`, `TINIO_SANDBOX`) | startup error naming the channel and saying `--sandbox` is the only one honoured today (decision 5). Never a silent unconfined run — the operator used a channel this document names |
| Sandbox requested with an OTLP endpoint configured | startup **warning** on stderr naming both, and the confinement proceeds; the export is what is lost, not the confinement (decision 25). The one row here that neither refuses nor degrades the sandbox itself |
| `sandbox-exec` missing or refusing the profile (macOS) | startup error carrying the binary's own diagnostic |
| Linux without a usable user namespace and not root | startup error naming the remedy by host: `kernel.apparmor_restrict_unprivileged_userns=0` (or an AppArmor profile for the binary) on Ubuntu 24.04+, where that restriction is the default and the refusal is `EPERM`; `kernel.unprivileged_userns_clone` on Debian-family kernels; or run as root |
| Linux on an architecture the seccomp table does not cover | **not** a startup error: the filter is skipped, the directory boundary stands, and the caller is told so it can warn — the one place in the Linux backend where a guarantee is downgraded rather than the process refusing to start. **The warning is a `warn!` on stderr through the same tracing channel as every other sandbox log, and deliberately not an event on stdout**: decision 19's vocabulary is two events, and a third would make every consumer decide what to do about something that is not a startup failure. A machine consumer that needs to know reads stderr, which is where this design puts every log (shared §7) |
| Launch payload absent or malformed | the process treats itself as the launcher; inside a confinement that fails closed |
| Any syscall refusal (`EPERM`, `EINVAL`, …) | error naming the step that failed and its errno |
| Read-only mode with an in-root state directory | configuration error (§9) |
| `local_uid` mapping with the user-namespace model | configuration error (§8) |
| A `UpdateProcThreadAttribute` call fails | startup error, **fatal**: measured 2026-09-19, a failed attribute set leaves the attribute unset and `CreateProcessW` still succeeds, so the child would run with no container at all. Every attribute-set call is checked before the launch is attempted |
| Windows ACL grant, `CreateProcess`, or Job-object failure | error naming the directory and the underlying failure, **after rolling back whatever was already granted**. It is not always a Win32 error: where a grant goes through a tool rather than a direct API, what arrives is that tool's exit status and text, and the error type carries both forms rather than pretending the second does not exist |
| Platform outside the three | startup warning enumerating what cannot be delivered, then best-effort `chroot(2)` (decision 23) |

### §12 Testing and verification

- **Unit, every platform.** Mount-table composition, mirrored jail paths, SBPL profile text, ACL grant list, the launch payload's one-line JSON encoding, the event framing including a frame split across reads, and the capability policy per (mode, `local_uid`) — all pure functions of the builder state.
- **Integration, Linux.** `assert_cmd` (already a workspace dev-dependency) drives `serve --sandbox` against a temporary root and asserts the properties that matter: a write to the served root fails with `EROFS` under `--read-only`; the state directory outside the root is written; a path outside the jail (`/etc/passwd`, `$HOME`) is unreachable; the server binds and serves. `TINIO_SANDBOX_MODEL=userns|root` selects the model so both branches run rather than whichever the host happens to allow.
- **Integration, Windows.** The same shape against `serve.exe`, asserting the whitelist (granted tree readable, sibling denied, `RX` rejects writes), that ACLs are rolled back on exit **and on a failed launch**, and that killing the launcher takes the child with it. Must run on both an NTFS and an ReFS volume — the verified rows show they agree, and a regression that broke one would otherwise be invisible. It must also settle the network row of §7 on a host whose baseline connectivity is known.
- **The event contract, every platform.** Round-trip `Event::encode`/`decode` as pure functions, pin the exact wire text rather than only round-tripping it (a consumer in another language reads it, and a symmetric mistake would round-trip perfectly against itself); assert that a consumer meeting a non-frame line, an unknown event name or a payload that does not fit its name skips it rather than failing; assert that a frame **split across several reads** is assembled — and assembled *whole*, since a relay holding one decoder per call would still emit a frame per surviving event while losing the bytes of a half-read one; and assert that a confined server emits `Listening` with the address it actually bound. On the launcher platforms, additionally assert that text the child writes to stdout which is *not* a frame does **not** reach the parent's stdout — that is the relay's whole job, and a relay that forwards bytes would pass every other assertion in this list — and that a child which exits without ever reporting becomes the parent's own `Event::Error`, read from the terminal record **after** the wait rather than before it.
- **Network isolation, every platform.** The assertion is the same everywhere: loopback bind and accept still work, and an outbound connection to a known-good address fails. **An earlier version of this sentence said the assertion "belongs in the shared suite", and there is no shared suite** — each crate owns its own test, because what makes a connection fail is that platform's mechanism and a shared helper would be parameterised straight back into three platform tests. What is shared is the *shape* of the assertion, and each crate's test states it. A test that only checks "connect failed" proves nothing — a machine with no route fails it too — so the harness must first prove the address is reachable from outside the confinement and then assert it is unreachable inside.
- **The feature gate.** A build with `--no-default-features` must reject `--sandbox` with exit 2 rather than starting unconfined (decision 5), and must still pass the workspace's existing no-default-features leg.
- **WSL2.** `crates/tinio-sandbox-linux/scripts/wsl-chroot.sh`, modelled on `crates/tinio-e2e/scripts/wsl-interop.sh`: point `CARGO_TARGET_DIR` at ext4, run once as the normal user (user-namespace model) and once under `sudo` (root model). Commands recorded in `docs/tests.md` under the existing WSL2 section. It lives in the Linux crate, not the facade, because everything it runs is Linux-only — the same reason `verify-windows.ps1` and the macOS scripts live in their own platform crates.
- **CI.** The Linux leg runs the integration suite on both models. The macOS leg is the only place the SBPL profile is ever exercised on real hardware, so P3 is not done until that leg runs a confined server and serves a request through it — a profile that merely fails to crash the process proves nothing.
- **Established on a real Mac, from this Windows host.** macOS 15.8 (24H23, x86_64, SIP on) runs in a QEMU VM reachable over SSH, and the whole of §5's profile and §7's macOS row were measured there on 2026-09-19 with a purpose-built probe plus `log show` for the refusals. The probe and its drivers are throwaway, so the *results* are cited above rather than a script; if the profile is ever doubted, the two commands that produced every macOS row here are `sandbox-exec -f <profile> <binary>` and `log show --predicate 'sender == "Sandbox"'`.
- **And with the real binary, not only a probe.** The workspace was copied into the VM, built there, and run under §5's profile with zero refusals (evidence table). So the read set is no longer an open question on this platform, and P3's first task is a test rather than a discovery.
- **Still not verifiable here.** The fallback path of decision 23 (no such host exists in CI), and anything on the CI macOS leg — the VM proves the *mechanism*, and CI is where it has to keep being true on a machine nobody is watching. The read set being application-specific remains a live hazard for future changes: `python3 -V` ran under the measured profile while `import socket` did not, because the interpreter then scans its own installation tree. tinio does not, today; a dependency that starts to would show up as a refusal in the leg's own log, which is why the leg records them.

Four independently shippable phases. Each has its own verification and its own reason to stop.

P1 is the original request, the only phase with a complete evidence base, and the phase that settles the layer boundaries: the three platform crates and both stub backends exist after it, so P2 and P3 fill in an implementation rather than discovering a shape. P2's design is fully evidenced too, but its implementation cannot be tested from WSL2 and belongs on a Windows host. P3 no longer waits on a Mac for its *mechanism*: the VM run of 2026-09-19 measured the profile and the network row, so what P3 has left is the crate and the CI leg — the same "fill in a shape that is already evidenced" position P2 is in, rather than the research question this sentence originally described. P4 is last because it is the weakest and the least likely to be used; it is kept rather than dropped because the operator asked for it, and it is kept separate so that its weakness cannot be mistaken for the other three. P4's home is undecided on purpose — it is the one backend with no evidence, so deciding where it lives now would be deciding it on the weakest grounds.

## Risks

| Risk | Assessment |
|---|---|
| **The macOS profile `tinio` itself needs is no longer unmeasured.** The workspace was built in the VM and run under §5's profile: it served an S3 request and the kernel logged no refusal for its process. What remains is that the read set is application-specific, so a *future* dependency could need an allowance §5 does not carry — `python3` demonstrated the shape of that failure by running under the profile and then failing to `import socket`. | **Closed.** The risk that remains is drift, not the current profile: it is detected by the CI macOS leg's own startup and by the refusals its log records, both of which fail loudly rather than silently degrading the confinement. |
| **`sandbox-exec` is deprecated by Apple.** Still shipped and still how Chrome's helpers and CI sandboxes work, but unsupported and unversioned. | Accepted for P3. If Apple removes it the macOS path degrades to "no sandbox available, fail closed", which the error table already covers, and `sandbox_init` FFI remains authorized as the fallback. |
| **P4 delivers one guarantee of three and can never be tested here.** `chroot(2)` gives no network isolation and no kernel-level read-only. | The operator chose this over refusing to start. Its only mitigation is the startup warning, which is why the warning is mandatory on every invocation rather than logged once, and why the Goal scopes itself to three platforms. |
| **On Windows the ACL grant and its rollback are proportional to the served tree, twice per run.** The `(OI)(CI)` ACE propagates by filesystem inheritance to every descendant, so a corpus of millions of objects pays two metadata passes over all of it — on a path whose budget is the harness's 30 s start timeout. | **Unquantified, and that is the risk rather than the cost itself.** No document gives an `icacls` timing, a per-object cost or a tree-size assumption; P2 establishes the number instead of assuming it (§6). The residue bound of decision 21 is unaffected — this is startup latency, not correctness. |
| **The Windows outbound-blocking claim is unverified here.** The probe could not separate AppContainer isolation from this host's firewall policy. | Assigned to P2, which must establish it where the baseline is known. |
| **Whether an inherited listener reaches the LAN is unknown.** The handoff is verified for loopback, and loopback works without a capability regardless, so the probe does not answer it. | **Nothing in the design depends on the answer** (decision 16). If the AppContainer's policy blocks it, a non-loopback bind under `--sandbox` needs `privateNetworkClientServer`; P2 establishes which, and the documentation states the outcome either way. |
| **`unsafe` in a workspace that forbids it, now in the default build.** Three sites on Linux — the seccomp `prctl`, the `unshare` call (which is `unshare_unsafe`, because rustix deprecated its safe-looking `unshare`), and the probe's `kernel_fork`, which rustix has no safe equivalent for at all (decision 14). One on macOS, the listener rebuild, which an earlier draft of P3 denied existed. Windows needs one module per Win32 capability, and the earlier three-site estimate for that platform was wrong. | Contained by decision 14: the lint follows the implementation crate, sites are enumerated per capability, `deny` plus targeted `allow`, invariants written down, `--no-default-features` strips it entirely. Only `tinio-sandbox-core` and the facade stay `forbid` — every backend now carries at least one site — and no count is promised ahead of the implementation. |
| **Five crates for one feature.** A consumer compiles four of them for one flag. | Accepted as the cost of the layering decision 3 proves is forced, not chosen. The platform crates are small and three of the five are `cfg`-excluded on any given build; the facade is a re-export list. The alternative — one crate with three `cfg` arms — was rejected by the operator on 2026-09-18 in favour of the seam. |
| **stdout is now a protocol channel, so a stray write is a protocol violation.** | Bounded by the framing rather than by discipline: a consumer that meets a line which is not a valid frame ignores it, and on the launcher platforms the parent drops it before anyone sees it. Linux has no such filter, which is exactly why the framing — not a promise to keep stdout clean — is the mitigation. |
| **The launcher's wait joins the relay thread, so it returns only once the child's stdout has actually closed** (decision 19). A descendant left holding that pipe keeps the wait, and the launcher, alive. | Narrow and checked: `serve` spawns no child processes, so the confined server cannot leave one behind (see the evidence table), and a launcher that could must deal with it before its wait closure returns. The alternative is worse than the hazard — reading the relay's record without joining it reports a healthy child as never having become ready, on every clean shutdown. |
| **A seccomp filter is irreversible and denies a syscall family.** If the filter is wrong the server cannot be repaired at runtime, only restarted without `--sandbox`. | Inherent. The filter is deliberately the last step, after every mount, so a mistake cannot corrupt the jail; and it denies the outbound family only (`connect`, `sendto`, `sendmsg`, `sendmmsg`), leaving `write`/`writev` and the accept path the server actually needs. |
| **`io_uring` bypasses syscall-level filtering entirely.** `IORING_OP_CONNECT` and `IORING_OP_SENDMSG` are submitted through `io_uring_enter`, which the filter allows, so a process that sets up a ring could still reach the network. | Accepted, and recorded here rather than papered over: seccomp cannot see inside a ring, the only alternative is denying `io_uring_setup` outright (which breaks any dependency that uses it), and what this filter answers is a *bug in the confined server*, not an adversary who can already execute syscalls at will. P1 names it beside the filter so the boundary is visible to whoever reads the policy. |
| **Ubuntu 24.04+ may refuse an unprivileged user namespace before this code runs at all.** `kernel.apparmor_restrict_unprivileged_userns` defaults to `1` there, so the first `unshare` fails with `EPERM` unless the binary carries an AppArmor profile. | **(unverified here)**: the WSL2 host has no such sysctl and its AppArmor filesystem is unmounted, so the probe could not see the restriction. The startup error names the remedy (see the error table) and the root model remains the fallback, but a real Ubuntu desktop is where this needs its first honest run. |
| **Windows leaves ACEs behind on a hard kill.** Grant and rollback are not atomic. | Bounded by decision 21 (deterministic SID) and by startup takeover; documented with a cleanup command. Not eliminable. |
| **The launcher is unconfined and holds the listener for the child's lifetime.** | It no longer parses the configuration (decision 18) and does no request work, so its attack surface is the argument parser and the Win32 setup calls. It must outlive the child, which is what makes it a supervisor rather than a transient. |
| **Where the tool's own directory is granted, the confined process can read it whole** (decision 22). | Accepted, and now **Windows-only**: it is the tool's own directory, and the alternative is a hand-maintained list of shared-library paths that breaks on the next dependency. macOS does not pay this cost, because measurement showed its confined child needs no grant on its own location at all — the row stands where the grant is actually spent, and nowhere else. |
| **A user namespace plus `local_uid` is refused.** Unmapped uids cannot be chowned to. | Fail-closed configuration error at startup with a named remedy. |
| **Root-run servers lose DAC override under `--sandbox`.** | Documented behaviour change; the served root is expected to belong to the service account. |
| **`serve` is the only entry point.** The flag reaches operators only through an example binary until T066/T067. | Same deferral the read-only design makes; recorded, not smoothed over. |
| **`tinio-server` gains a hard dependency on `tinio-sandbox` for one example.** | A wart: the dependency is explicitly **not** optional, because decision 19 has `serve` emit the readiness frame in *every* build — the feature gates behaviour, not linkage, so a `--no-default-features` build must still link the event type. It disappears when the CLI owns the flag and the example retires; recorded in Bookkeeping rather than solved now. |
| **drvfs specifics.** The repository and many WSL2 workflows live on `/mnt/e`. | Verified working for `pivot_root` and for the overlay read-only path. |

## Bookkeeping

- Five new crates (`publish = false`): `crates/tinio-sandbox-{core,linux,macos,windows}` and the `crates/tinio-sandbox` facade. The workspace glob picks them up, and `Cargo.toml`, CI, `README.md` and `docs/` gain a row where the other crates are listed. The facade is the only one a consumer names.
- `unsafe_code = "deny"` follows the implementation: `tinio-sandbox-linux` and `tinio-sandbox-macos`, with `tinio-sandbox-windows` at P2. `tinio-sandbox-core` and the facade keep `forbid`, as does every pre-existing crate. The `#[allow(unsafe_code)]` sites are enumerated and nowhere else — on Linux the seccomp `prctl`, the `unshare` call — `unshare_unsafe`, because rustix deprecated the safe-looking `thread::unshare` in 1.1 and names the unsafe one as its replacement — and the probe's `kernel_fork`, which has no safe counterpart in rustix at all; on macOS the single listener rebuild from the inherited descriptor, which is `OwnedFd::from_raw_fd` because `std` offers no safe route and rustix offers none either. The Windows `SetHandleInformation` / `CreateProcess` plumbing and the socket rebuild (`from_raw_socket` / `from_raw_fd`) join them at P2. `docs/cargo.md`'s lint rule gains the exception in the same commit as the first of them.
- `tinio-server` gains the `tinio-sandbox` dependency — **not** optional, since decision 19 emits the readiness frame in every build — a default-on `sandbox` feature, `required-features` on the `serve` example target, and a `[target.'cfg(target_os = "linux")'.dependencies]` entry for `tinio-sandbox-linux`, which is where the platform options live (the facade exports none: it re-exports the backend, not a platform's options type). `tinio-cli` gains the same feature when it implements the flag.
- `rustix` gains the `fs`, `mount`, `process` and `thread` features in `tinio-sandbox-linux` only (§4, §8); `tinio-fs` keeps `fs`. Every other new crate is dependency-light on purpose: core needs `thiserror`, `serde`, `serde_json`, `tokio` and the workspace's own `tinio-core` (`AccessMode`'s owner, §1) on top of the `sse-core` line below, the stub backends need nothing but the core, and Windows needs no new dependency at all because its platform calls are FFI the crate already carries.
- **Two new third-party dependencies, and the ledger is two lines rather than the one an earlier draft claimed.** Constitution I requires any addition to be justified against its lifetime maintenance cost, so:
  - **`sse-core`, in `tinio-sandbox-core`.** Decision 19 makes stdout a protocol channel, and the framing is SSE — a published standard with a nontrivial state machine behind it, because a frame can arrive split across reads from a pipe. Writing that by hand is the kind of parser that passes every test until a chunk boundary lands mid-escape. `sse-core` is the zero-I/O half of that lineage: synchronous `SseDecoder`, `no_std`, and — **with its default features off, which is how it is depended on** — `bytes`, `memchr` and `thiserror`, all of which are already in the tree. **Every clause of that was checked against the sparse index on 2026-09-19 rather than recalled**: 0.2.3 is the newest published version, `default = ["fastrand", "std", "stream"]`, `stream = ["dep:futures-core", "dep:pin-project-lite"]`, and the non-optional normal dependencies are exactly `bytes`, `memchr` and `thiserror`. Its defaults are not off by nature: they turn on `stream`, which pulls `futures-core` and `pin-project-lite`, exactly the async baggage this crate was chosen *over* `sse-stream` to avoid. Nothing the design uses is behind them — `SseDecoder` is unconditional and only `SseStream` is gated — so the smaller feature set is also the complete one. Its sibling `sse-stream` was rejected outright — it lists `futures-util`, `http-body` and `http-body-util` as *non-optional* dependencies, decodes from a `TryStream` rather than a reader (so an adapter is needed either way), and depends on `sse-core` itself.
  - **`signal-hook`, target-gated to `tinio-sandbox-macos`.** It buys the §3 step 9 signal relay on a platform where the requirement is defensive rather than mandatory, and it buys it *safely* — the alternative is a hand-written `sigaction`, which would be a second `unsafe` site in a crate that now has exactly one, for a requirement no standard macOS deployment can reach. Rustix is not an option: its `signal` module is signal *numbers* only, and `sigaction` sits in its `not_implemented` list by design. The marginal cost is small because `signal-hook-registry` — the crate that actually owns the handler and the self-pipe — is already in the tree transitively. **This argument was stronger before the listener rebuild was found**, when the crate could still have been `forbid`; what remains is a preference for one enumeration over two rather than a lint that forces the choice, and decision 14 (d) is where the count is actually settled.
  The seccomp filter, by contrast, is hand-built rather than pulling `seccompiler` or `libseccomp` (decision 14). `serde` and `serde_json` are not on this list: both were already in `[workspace.dependencies]`, so the core referencing them adds no dependency to the tree. **`tokio` is not on it either**, for a subtler reason worth stating: it is already a non-optional dependency of `tinio-server`, and the core asks for it with `io-util` alone — no `rt`, no `macros`, no `net`. The relay is async functions the caller's runtime polls, not a runtime of its own; the `rt`/`macros` features the tests need live in `[dev-dependencies]` so that a consumer pays for what it already has and nothing more.
- `[server] sandbox` joins `host` / `port` / `read_only` in `crates/tinio-config/src/schema/server.rs`, and the flag follows FR-016's `flags > env > .env > file` precedence. Until a phase implements it, setting it **or** `TINIO_SANDBOX` is a startup error rather than an ignored key (decision 5).
- **Every sandbox crate gains a `tracing` dependency**, and `tracing-subscriber` joins the dev-dependencies of a crate whose tests assert on events. `tracing` is already pinned in `[workspace.dependencies]`, so the ledger of *new* third-party dependencies is unchanged — this adds a dependency edge inside the workspace, not a crate to the tree. The requirement itself — which operations are traced, at what level, with which fields, and why the sink is never stdout — is stated once in `docs/superpowers/plans/2026-09-18-sandbox-shared.md` §7, and each phase names the operations it owns.
- `crates/tinio-server/examples/serve.rs` stops being `#[tokio::main]` and follows §10's sequence.
- **`crates/tinio-e2e/tests/steps/clients.rs` changes, and it is not part of the sandbox work.** Its `READY` constant and `wait_for_ready` implement today's `listening on ` scrape; decision 19 replaces that with the event stream. **There is a second reader of the same line, and it arrived with FR-023**: `crates/tinio-server/tests/serve_read_only.rs` carries its own `const READY` and its own `Serve::ready()`, and it is an auto-discovered test target the CI `test-port` leg runs. Both change together, because the endpoint change breaks both. The change lands in P1 because it is the first phase to emit events, but it belongs to the e2e harness's own history and must be made with the cucumber features that assert readiness — not smuggled in as a side effect of a sandbox task.
- No spec text exists for `--sandbox`; the FR and the contract prose land with the CLI feature, not here.
- The `--chroot` name appears nowhere in the tree and is not introduced.
