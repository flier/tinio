## Background

tinio serves an S3 API over a directory tree and holds credentials in its private state. Two existing properties motivate confinement:

- **FR-020 / FR-023**: all private state lives in a reserved directory, and in read-only mode the storage root is never written at all. Both are currently *application-level* promises — a path-traversal bug, a symlink-following bug, or a bug in the `.tinio` reservation is all that stands between a request and the wrong file. `piolium/findings-draft/p4-005-follow-symlinks-skips-containment-proof.md` is an instance of exactly this class.
- **FR-033**: with a `local_uid` mapping configured the server runs privileged (root or CAP_CHOWN), so a bug in that configuration has the privileges to reach anything the process can.

`--sandbox` moves both promises down to the kernel: the process is confined to the paths the operator exposes, and anything else is unreachable no matter what the code does.

Nothing of this existed when this design was written. `crates/tinio-cli/src/commands/mod.rs` was a doc comment and `tinio_cli::run()` returned `ExitCode::SUCCESS`; the only runnable entry point was the `serve` example (`crates/tinio-server/examples/serve/`), which hand-parsed its own arguments rather than going through a CLI parser — so the flag landed on `serve` in this design, with the CLI wiring deferred. **Both halves have since reversed**: `crates/tinio-cli` is the serving process, `tinio server <root> --sandbox` is the invocation, and the example is retired. **`--read-only` is the worked example of that deferral**: it was designed the same way, landed on `serve` alone, and its CLI flag landed with T066/T067 on the same terms as `--sandbox`.

## Goal

One flag, one interface, and **two guarantees on the three supported platforms**: (1) the confined process reaches exactly the directories the operator exposed, with exactly the access each was given, and nothing else; (2) the confined process cannot initiate an outbound connection. Plus a third property that follows from the first: `--read-only` becomes kernel-enforced rather than an application-level promise.

The guarantees are uniform across Linux, macOS and Windows. They are **not** uniform across every unix: a fourth platform gets a best-effort fallback that delivers only the first guarantee's directory boundary, and says so at startup (decision 23).

## Non-goals

- **PID / NET / IPC / UTS namespaces and cgroups.** v1 is the mount namespace, capabilities and a single-purpose seccomp filter on Linux. No network namespace, no resource limits, and no *general* syscall filtering — seccomp is used for exactly one thing, blocking outbound connection setup (decision 13).
- **Cross-platform equivalence of *mechanism* or of *visible-path behaviour*.** The three platforms enforce the guarantees differently and Linux alone hides the path namespace. §2 states each one plainly instead of implying more than it delivers; the guarantee is that the paths are *unreachable*, not that they are *unnameable*.
- **Wiring into the real CLI.** Landed: `tinio server --sandbox` is the invocation, in `crates/tinio-cli`, alongside `--read-only`.
- **Read-only mode itself (FR-023).** That work has **landed** (commit `a46a1d1`): the serving path resolves the mode from `[server] read_only`, the `TINIO_READ_ONLY` overlay and the `--read-only` flag, refuses every mutating operation, and relocates the tool's state out of the served root to `TINIO_STATE_DIR` or `<home>/.tinio/roots/<hash>/`. This design provides the *seam* it plugs into (§9), confines it, and does not re-implement it.
- **Protecting the state directory's contents from the S3 surface.** `.tinio` reservation is FR-020's job; the sandbox only guarantees the state directory is reachable, not that it is unservable.
- **A strong path on platforms outside the three.** Covered by decision 23 as an explicit, documented downgrade rather than a silent one.

Swept that way, all 41 drop and the bounding set ends empty; `41..63` return `EINVAL(22)`, which is `CAP_LAST_CAP = 40` doing its job. `PR_SET_NO_NEW_PRIVS` is not a substitute — it is what lets the seccomp filter install later, not what permits the drop. Dropping from the bounding set does not clear the effective bit, so the sweep may drop `CAP_SETPCAP` itself and continue |
| Inside a user namespace, a bare `MS_BIND` of a **mount point** source is refused | `mount("/tmp", …, MS_BIND)` and `mount("/", …, MS_BIND)` → `EINVAL(22)`; the same two with `MS_BIND\|MS_REC` → `rc=0`. A subdirectory source (`/etc`, `/bin`) works with a bare `MS_BIND`. `rustix::mount::mount_bind` passes only `MS_BIND`; `mount_bind_recursive` adds `MS_REC` |
| Mount propagation on WSL2 is already private | `findmnt -no TARGET,PROPAGATION /` → `/ private`; `/tmp` and `/mnt/e` likewise. Making `/` private is therefore defensive rather than a fix for a shared-root failure |
| `mount(NULL, "/", MS_REC\|MS_PRIVATE)` succeeds inside the user namespace | `rc=0`, so locking propagation costs one syscall and needs no capability the confinement does not already have |

## Decisions

1. **The flag is `--sandbox`, the key is `[server] sandbox`, the variable is `TINIO_SANDBOX`.** "chroot" was the working name and is wrong on two of three platforms: there the process *can* see paths outside the confinement and is merely refused access, and `chroot(2)` is not what any of the three runs. `sandbox` is the umbrella term that does not promise a mechanism.
2. **One trait, one method, and a return value that names the shape.** `expose(path, access)` is how the caller states what must remain reachable; the builder stays pure data in the core, and turning it into mounts, SBPL rules or DACLs is the platform's job. That job is `Backend::confine(&mut self, sandbox: &Sandbox, plan: &LaunchPlan) -> Result<Confinement>` — `&mut self` because the call changes the caller: on Linux irreversibly, and on a launcher backend by recording what it set up, and `Confinement` is what keeps the call site free of `#[cfg]`: `InPlace` means the calling process is confined and should carry on, `Supervise(child)` means a confined child is running and the parent must wait, forward its exit status and undo what it set up. Linux always answers `InPlace`; macOS and Windows always answer `Supervise`. A trait carrying both an `enter()` and a `launch()` would hang a permanently-failing method off every implementation, and two separate traits would push the platform split into `main()` — the one place it must not appear. **What that freedom does not extend to is a platform's own configuration.** `Confinement` makes the *confinement call* cfg-free, but a backend's settings and its platform-specific status are not part of the shared surface and the facade does not restate them as types of its own: `Options` — which carries `Mechanism` and the capability policy — and the `seccomp()` state a Linux run must report are reached through the facade's cfg-gated alias for the platform's own crate, `pub use crate::_linux as linux;`, so that a consumer writes `tinio_sandbox::linux::Options` inside a `#[cfg(target_os = "linux")]` block and depends on **one** crate rather than one per platform. That is the boundary rather than a leak in it: the facade shares what every platform needs in order to *drive* a confinement, and a platform's own vocabulary stays in its own crate, where a caller that wants it is unambiguously writing platform-specific code — **the alias is a path to that crate, not a type the facade owns**, which is why the arrangement is still the intersection and not the union. Widening the facade with per-platform options and statuses would grow the shared surface into the union of three platforms instead of their intersection.
3. **Five crates: a core holding the contract, three platform implementations, and a facade.** `tinio-sandbox-core` owns the trait, the shared vocabulary (`Exposure`, `Sandbox`, `Error`, `Confinement` — and `AccessMode`, which it **re-exports from `tinio-core` rather than redeclaring**, because FR-023's read-only resolution already produces one at the `serve` call site and a second enum for the same fact would put a conversion between them) and the launcher machinery both child-launching platforms share. `tinio-sandbox-linux` / `-macos` / `-windows` each implement the trait for their platform. `tinio-sandbox` is a thin facade that re-exports the core and, behind `[target.'cfg(…)'.dependencies]`, the one platform implementation that applies. **The layering is forced, not stylistic**: the platform crates implement the core's trait, so they depend on the core, which means the crate that *selects* a platform cannot also *define* the trait — a two-crate split would be a dependency cycle. The facade follows the existing `crates/tinio` precedent. Per-platform *cargo features* are still rejected: the platform code is already `cfg`-gated, and a feature would add a combination that compiles with no implementation behind it.
   The feature gate stays on the consumers. `crates/tinio-cli` — the serving process — carries a **default-on** `sandbox` feature, and `tinio-server` carries the same gate on its two confined-e2e test targets. (The alternative home `tinio-util::sandbox` was rejected because `tinio-util` is backend-agnostic runtime helpers and this is a process-level concern with a platform matrix.)
4. **Default-on means compiled in, not enabled.** The sandbox code is in the default build; whether it runs is decided by `--sandbox` / `TINIO_SANDBOX` / `[server] sandbox`, exactly as `--read-only` will be. Enabling it by default as *behaviour* would be a breaking change to every existing deployment and is not what this design does.
5. **A build without the feature refuses the request rather than ignoring it.** With the feature off, any of the three channels that asks for a sandbox is a usage error (exit 2) naming the build as the cause. The project's stripped-capability precedent is "schema-known key silently ignored", and that precedent does not apply here: silently running unconfined is precisely the failure mode §11 exists to prevent. **The same rule covers a platform whose backend has not landed**: `--sandbox` on a target whose crate is still a stub is a usage error naming that, not a flag that is accepted and then ignored — an accepted flag that confines nothing is the same silent failure wearing a different hat.

**And it covers a channel this design names but no phase implements.** Decision 1 fixes three channels; the four phase plans wire only `--sandbox`, and defer the other two to the CLI. Until a phase implements them, a run in which **either** `[server] sandbox` or `TINIO_SANDBOX` is set must **refuse to start**, with an error naming the channel and saying it is not honoured yet — never proceed unconfined. The reason is this decision's own: an operator who sets `TINIO_SANDBOX=1`, believes they are confined, and is not, has been failed by precisely the mechanism §11 exists to provide, and "the channel is not implemented yet" is not a defence when the design named the channel and the operator used it in good faith. `--sandbox` remains the only channel that confines anything, and the error says so.
6. **Linux confines in place; macOS and Windows launch a child.** `sandbox-exec` applies a profile to a process it execs, and AppContainer can only be entered at process creation, so neither can confine a running server in place. Linux can — `unshare` plus `pivot_root` apply to the calling process — and it therefore does, with no second process, no payload, no exit-code forwarding and no signal relay. The asymmetry is stated rather than flattened to the lowest common denominator, and **it was re-examined on 2026-09-18 against the argument that uniformity would be worth a fork on Linux too**. It is not: the call site is already uniform because `Confinement` exists (decision 2), and the difference the fork would buy is implementation-side only. What the fork would cost is the property that matters most here — after `enter()` returns there is **no unconfined code running at all** on Linux, whereas the launcher platforms are forced to keep a supervisor that never enters the jail and therefore keeps a parser, a descriptor table and a signal handler outside it. Trading a guarantee for symmetry, in the direction the other two platforms cannot go, is the wrong trade. The one functional thing the fork would buy is the listener handoff of decision 16, which Linux does not get; that consequence is recorded in decision 19. **The macOS half of the premise is now measured and holds for a different reason than the one given here.** An in-process apply exists and works — `sandbox_init_with_parameters`, with the real rendered text and the real `-D` pairs, returns `rc=0` on macOS 15.8 — so "neither can confine a running server in place" is false for macOS; what rejects the route is its measured cost, not a premise about what Seatbelt can attach to: the apply is one-shot and irreversible (`rc=-1 err="Operation not permitted"`, `deny(1) forbidden-sandbox-reinit` on a second apply) and the process it is applied to can then neither `fork` nor `exec` outside the profile's `P` (`deny(1) process-fork`, `process-exec*`) unless the profile grants `process-fork`, so **it cannot be applied by the launcher, which must still spawn the child**. The `sandbox-exec` helper therefore stays the **default**, and there is no hang to weigh against the cost: a thread created before the apply does not block it and every tokio runtime configuration builds and `block_on` returns in under 2 ms — the in-process multi-thread/tokio hang is **falsified**, not merely unobserved (evidence table). **The in-process route is nevertheless implemented, as a second mechanism an operator selects** (2026-09-26): `TINIO_SANDBOX_MACOS_MECHANISM=sandbox-init` renders the same profile and hands it to the child on the launch payload, the child applies it to itself before it serves, and nothing on that route invokes `sandbox-exec` — which is what makes it the answer on a host where the deprecated helper is missing or unwelcome. The cost this decision measured is what the *launcher* does about it rather than the operator: because the launcher cannot apply the profile to itself, the **validator** forks an unconfined child that applies it and exits (a non-zero result refuses the launch and surfaces the kernel's diagnostic), and because the child cannot fork after applying, the route renders **without the `process-exec` rule** — the exec and the dynamic loader have already happened by the time the text lands, so that allowance would be a dead grant (`Mechanism::wraps_the_exec`, the profile table's one conditional entry; measured on the VM, and the reason the product's `sandbox-init` run renders `rules=4` where `sandbox-exec` renders `rules=5` **on the same one-exposure run** — a serving run renders more, one rule per exposure the launcher adds (§5's `rule_count` paragraph owns the derivation)). The mechanism is macOS's own vocabulary in macOS's own crate, reached through the facade's `macos` alias, and a value that is neither name is a **usage error** naming the variable and both of its values — never a silent fallback to the default.
7. **Linux adapts: user namespace first, then root, then fail closed.** Verified working unprivileged in WSL2; a hardened host that forbids unprivileged user namespaces still works when started as root; when neither is available the process exits with a clear message. It never continues without the sandbox. **The adaptation needs a probe, because the parent cannot try and then back out**: `unshare(CLONE_NEWUSER)` changes the calling process for good, so a failed attempt is not something a fallback can undo. `Mechanism::Auto` therefore **forks a child that attempts the unshare and reports through a pipe** — the child is discarded, the parent is untouched, and the answer decides the model. The syscall remains the authority (no sysctl proxy, which disagrees with the kernel in containers); the fork is only how the question gets asked without committing. A probe failure with `euid != 0` is the fail-closed case, and its message names both remedies.
8. **Read-only is the absence of a write permission, on all three platforms.** Linux `remount,bind,ro` — which **both** models can do for a source whose locked per-mount flags are the ones the request re-asserts, ext4 and drvfs binds among them (§4) — or an `MS_RDONLY` overlay where that remount is refused, the refusal being what a source carrying a locked per-mount flag the request drops produces; macOS omits `file-write*` for the served root and the profile's `(deny default)` does the rest; Windows grants `RX` instead of `M`. This is why §9 needs no new mechanism — read-only mode is a different value passed to the same `expose` call.
9. **The Linux path mirrors host paths instead of translating them.** The new root is a tmpfs, and each exposed path is re-created inside it at its **original absolute path** and bind-mounted there. Every path string is then identical before and after the pivot: `dirs::home_dir()`, `state_dir()`, `<root>/.tinio`'s `prove_contained`, and `strict-path`'s containment proofs all keep working unchanged. A fixed-mountpoint design (`/data`, `/state`) would need a translation layer in every one of them.
10. **The Linux jail mountpoint is a fixed, root-derived name that the next run takes over.** `$TMPDIR/.tinio-jail-<hash(root)>`, not a pid-suffixed path: a hard kill leaves at most one directory per root instead of one per run, and startup reuses it (rmdir is safe — every mount inside it lives in a per-process mount namespace, so the host always sees an empty directory). `open_tree`/`move_mount` cannot remove the directory (see the evidence table), so bounding the residue is the available answer. Concurrency is not a concern: two processes mounting the same host directory each do so inside their own mount namespace.
11. **Linux keeps the uid and drops capabilities.** Dropping to a different uid is the conventional move and is wrong here: FR-033 lands object files `0600` owned by the service account, so a uid change makes previously-written objects unreadable. "Dropping privileges" therefore means `PR_SET_NO_NEW_PRIVS` plus a capability set reduced to what the mode needs — never a change to *which host user the process is*.
    **The user-namespace model maps the process to root *inside* the namespace, and that is not an identity change in the sense this decision forbids.** `uid_map` is written as `0 <euid> 1`, so namespace-root is the invoking user as far as the host is concerned: every syscall that crosses the boundary carries the same host euid as before, and files created through it are owned by the service account exactly as an unconfined run would own them. The namespace's root is what makes `mount` and `pivot_root` reachable at all (decision 7), and it is the reason `local_uid` must be refused under this model rather than supported (§8): an unmapped uid is not a uid the confined process can chown *to*. The property to preserve is who owns the files, and no mapping changes that.
12. **No `/proc` in the Linux jail, and no PID namespace in v1.** Mounting the host's `/proc` would leak the host process table into a jail that has no PID namespace of its own, which is worse than having no `/proc` at all. Rust's `getrandom` is a syscall and does not need `/dev`; the four device files in §4 are defensive, not load-bearing.
    **The uid/gid maps are an exception that costs nothing, because it happens before the jail exists.** Their only writable entry point is `/proc/<pid>/{uid_map,gid_map,setgroups}`, and a descriptor to it must be opened *after* `unshare(CLONE_NEWUSER)` (see the evidence table). The confinement therefore unshares in two steps — the user namespace first, while the host's `/proc` is still reachable and no mount namespace has been created yet — writes the three files there, and only then creates the mount namespace and builds the jail. Nothing is ever mounted into the jail, and no `/proc` survives in it: the window closes before the jail is built. The three descriptors are closed explicitly once the maps are written, because this design does not `exec` and so never gets `CLOEXEC`'s protection.
13. **Linux network isolation is a seccomp-BPF filter, not a network namespace.** A network namespace is the obvious answer and it is wrong here: `CLONE_NEWNET` gives the confined process its own loopback, which means **the host can no longer reach the server** — a server nobody can talk to is not a sandbox, it is an outage. Reconnecting the two ends needs a veth pair with addresses, which needs the privileges this design exists to avoid. The filter instead denies the *outbound* syscalls — `connect`, `sendto`, `sendmsg` and `sendmmsg`, the three `io_uring` ring calls that would otherwise carry the same traffic past them, and the cross-process family (`ptrace`, `process_vm_readv`, `process_vm_writev`, `pidfd_getfd`) that is a second guarantee rather than a second spelling of the first: a confined same-uid process could otherwise read or inject a neighbour outside the jail, follow `/proc/<pid>/root` across the mount view this design just built, or — `pidfd_getfd`, the fourth member and a 2026-09-27 addition — copy one of that neighbour's descriptors out and walk a host directory through the copy — and leaves accepting and answering untouched. `sendmmsg` is the batch form of `sendmsg` and an equally direct route out, so it is denied for the same reason; and the family is wider than "the datagram sends" suggests, because glibc's `send(2)` **is** the `sendto` syscall. What still answers is `write`/`writev`, which is what Rust and tokio use; what does not is `send`/`sendto`/`sendmsg`/`sendmmsg`. **The filter cannot see the address family** — seccomp cannot dereference the `sockaddr` pointer — so a `connect` on an `AF_UNIX` socket is denied along with the rest: `/dev/log`, a Docker socket or a D-Bus connection inside the jail fail with `EPERM`. That is the policy, not a defect, and it is the price of not being able to inspect the address. **One** boundary the filter cannot close is recorded in the Risks rather than papered over — the address family, invisible to it by construction — and the other two were closed rather than recorded. **`io_uring` went first (2026-09-25)**: its opcodes never reach a filtered syscall, so what the filter refuses is the ring calls themselves (425/426/427) — the only closure available to a program that cannot see inside a ring. **The x32 ABI went second (2026-09-26)**: one `JSET 0x4000_0000` on the syscall number, ahead of every equality test, refuses any number with `__X32_SYSCALL_BIT` set, so the whole ABI is refused and not only the eleven numbers the list names — the ratified shape, because the program compares `seccomp_data.nr` once and has no second comparison to key on both the bit and a number. **`pidfd_getfd` went third (2026-09-27)**, and it is the one member that reached a *descriptor* rather than a memory range: the permission it wants is `PTRACE_MODE_ATTACH_REALCREDS`, a check inside the kernel rather than a call to the `ptrace` syscall, so denying `ptrace` closed nothing there — measured with the ten-entry program installed, `pidfd_getfd(pidfd_open(peer), dirfd)` returned a descriptor and `openat` read the host's `/etc/hostname` through it (the follow-ups plan's §6 owns the measurement and the program's length counts). Eleven syscalls and one ABI is the filter's whole deny set, and this is the only syscall filtering in the design and the reason the Non-goals wording was narrowed rather than the filter dropped.
14. **The unsafe exception is narrow, and the constitution's conditions are answered explicitly.** Constitution II permits `unsafe` when no safe alternative exists, in the smallest possible scope, with documented invariants and explicit review justification. (a) Alternative: `libseccomp` or the `seccompiler` crate would remove the FFI and add a dependency for a filter of **twenty-nine instructions on `x86_64` and twenty-seven on `aarch64`** — a load, an architecture compare, a kill, a load, the `x86_64`-only `JSET` mask pair, then eleven compare/deny pairs and an allow (the `aarch64` program lacks the mask pair, which is why it is two instructions shorter) — and not the six an earlier version of this decision quoted, which counted the denial policy without its guard and its dispatch; nor the **twenty-seven**/**twenty-five** shape this decision carried until 2026-09-27, before `pidfd_getfd` joined the list; nor the **nineteen-instruction** shape with seven compare/deny pairs it carried until 2026-09-26, which is what the program looked like before the ptrace family and the x32 mask landed. The operator authorized FFI on 2026-09-18 and the smaller dependency surface was preferred. (b) Scope: **small, enumerated and per-capability, not a fixed count.** Linux needs **three** — the seccomp `prctl`, the `unshare` call, and the user-namespace probe's `fork`. **The third is the correction the compiler asked for**, and it is the reason this subsection does not promise a number: an earlier draft said two, on the belief that `rustix::process` exports a safe `fork`. It exports none. The only one in the crate is `rustix::runtime::kernel_fork`, which is `pub unsafe fn` and sits behind the `runtime` feature and the `linux_raw` backend, so the probe cannot avoid the block — and its invariant is decision 26's rather than the call's own: no thread exists yet, so the child is a copy of a single-threaded process and touches nothing but its own pipe end and `exit`. The `unshare` call is worth stating precisely for the opposite reason — the obvious reading of it is wrong: rustix *does* export a safe `thread::unshare`, and marked it **deprecated** in 1.1 with "this function should be unsafe", pointing at `unshare_unsafe`, whose safety comment is about `CLONE_FILES` — a flag this design never passes. Taking the safe-looking path would trade the `unsafe` block for a deprecation warning, and this workspace builds with `-D warnings`, so the unsafe variant is what the crate itself asks for. **There is a second deprecation trap of the same shape and it is easy to miss**: `rustix::thread::Capability` is deprecated since 1.1 ("Use `CapabilitySet` with a single bit instead") and it **is** re-exported from `rustix::thread` — the module is `mod prctl;` plus `#[cfg(linux_kernel)] pub use prctl::*;`, so the short path compiles and only the deep `rustix::thread::prctl::Capability` fails to resolve. The deprecation alone disqualifies it under `-D warnings`; the capability policy uses `CapabilitySet` throughout. Everything else the Linux backend calls is a safe wrapper: `process::pivot_root`, `thread::set_no_new_privs`, `thread::set_capabilities` and `thread::remove_capability_from_bounding_set`. Windows needs more, and writing P2 showed the earlier three-site count here was an underestimate: the package-SID derivation, the handle plumbing, the process launch and the socket rebuild all reach Win32 directly — the Job object was a fifth when that count was being written, and since 2026-09-29 its calls are `tinio-util`'s `job_object` with this crate's `job` module as policy over them — — through the `windows-sys` bindings rather than through declarations of this crate's own, which is the ruling the Bookkeeping ledger records — and each of them does so from a module part (d) enumerates. The boundary that matters is not the number but that each site is one module, one target, and that everything around it is safe — and the count is established by the implementation, corrected here rather than asserted ahead of it. macOS needed exactly **one** until the in-process mechanism landed and now needs **three** — the count follows the implementation here as everywhere in this subsection, and two of them arrived 2026-09-26 with `sandbox-init`. The first, and the one finding it is the point of, is that an earlier draft of P3 asserted this crate had no `unsafe` at all, and the claim did not survive contact with `rustc`: the child rebuilds its listener from the descriptor number in argv, both `std` routes — `BorrowedFd::borrow_raw` and `OwnedFd::from_raw_fd` — are `unsafe fn`, and asking the compiler returns `E0133` for each (`launch::inherited_fd`). The other two are the in-process route's: **`apply::libsystem`** declares `sandbox_init_with_parameters` and `sandbox_free_error` through `libSystem`, because neither `rustix` nor `libc` 0.2.189 ships a `sandbox_*` binding (measured) and an `unsafe extern "C"` block needs its own allow under Rust 2024; and **`apply::validator`** calls `fork(2)`, which is `unsafe` for a reason of its own — a child of a threaded process is not something a signature can promise. **The count is three because a fourth site was removed rather than because it never existed** (2026-09-27): `launch::duplicate_control` — the rebuild-from-an-integer macOS needed while the facade's `control_handles` took `&[i64]` on every platform — is gone, now that the facade's signature is `#[cfg]`-split (`&[BorrowedFd<'_>]` on unix, `&[i64]` on Windows) and core's `ControlHandle::duplicate(impl AsFd)` is the safe route from a borrow; the facade's `lib.rs` doc owns that argument, and this enumeration's count is unchanged at three. The first's invariant is that the caller's strings outlive the call and the callee's error string is freed exactly once by the only deallocator libSystem publishes for it; the second's is the validator's stated precondition that the launcher has no thread at that point, discharged by the ordering in §10. `rustix` is still no escape from the descriptor rebuild: its `net::socket` module is free functions over `OwnedFd` (`socket(…) -> io::Result<OwnedFd>`, `accept<Fd: AsFd>`) with no raw-descriptor constructor, so a `rustix` route would still begin at `OwnedFd::from_raw_fd`. It is no escape from the fork either, which is why this crate names `libc` at all: `rustix`'s only `fork` is `runtime::kernel_fork`, and that module exists on the `linux_raw` backend alone (measured — it does not resolve for `x86_64-apple-darwin`). The alternative — letting the child bind inside the confinement — was considered and rejected: it costs the property that makes macOS's guarantee the strongest of the three, since the profile would have to grant `network-bind` and `network-inbound` again, and a port-filtered rule cannot express an ephemeral port. (c) Invariants: the `sock_fprog` and its filter array are `'static` and outlive the `prctl` call; `PR_SET_NO_NEW_PRIVS` is already set before the filter is installed (§7), so the filter cannot be installed with more privilege than the process retains; the filter is installed exactly once and is irreversible; the rebuilt socket takes ownership of an inherited descriptor that the parent keeps alive for the child's lifetime. (d) The lint follows the implementation, not the interface: `tinio-sandbox-linux` and `tinio-sandbox-windows` are `unsafe_code = "deny"` today, because both backends have landed and each carries sites, while `tinio-sandbox-macos` is `deny` too, P3 having landed its first site (`launch::inherited_fd`, the helper that turns the inherited descriptor number into an `OwnedFd`, which both safe rebuilds `launch::listener` and `launch::control` call) and the in-process mechanism its other two (`apply::libsystem`, the `unsafe extern "C"` block that declares the two `libSystem` symbols — this crate's declarations because neither `rustix` nor `libc` 0.2.189 ships a `sandbox_*` binding — and `apply::validator`'s `fork`) — the same rule the other two followed — and `tinio-sandbox-core` and the facade keep `forbid` throughout. The exception is `#[allow(unsafe_code)]` on the enumerated sites alone. Every platform backend now carries at least one site, which is worth saying plainly: the shared layer is the one that stays clean, and a backend is the layer where a kernel interface has to be met on its own terms. **The enumerated list of sites lives here, and this is the only place it lives.** `docs/cargo.md` states the rule — which crates are `deny` — and points at this decision for the sites, because that file is a convention and this one is the design the three phases all read. Each phase keeps the list current as its own sites land: Linux's three — `seccomp`'s filter install in `crates/tinio-sandbox-linux/src/seccomp.rs`, and `mechanism.rs`'s `unshare` and `mechanism.rs`'s `kernel_fork`, each a function-scoped attribute in that file (module and symbol rather than line, because both files move; the count of three is part (b)'s, and an earlier wording here named a `linux` and a `model` module the crate does not have) — and macOS's **three** (`launch::inherited_fd`, reached by both safe rebuilds `launch::listener` and `launch::control`; `apply::libsystem`'s `unsafe extern "C"` block, whose two `libSystem` declarations only that module's safe `init` calls; and `apply::validator`'s `fork`) are known, and Windows' are established by the implementation rather than asserted now, which is the same stance part (b) takes on the count — **as the P2 phase closed the Windows entry was **eight**, and it is **nine** today — `acl`, the DACL layer, and `sweep`, the launch path's stale-profile reaper, are the two sites that arrived after the phase did** — the seven file-level sites are `handles`, the handle plumbing; `sid`, the package SID and the capability SIDs; `socket`, the listener rebuild that turns an inherited handle value back into a `TcpListener`; `process`, the AppContainer launch that builds the attribute list and creates the child; `control`, the signal relay's console control handler and the event its hook thread waits on; and **`acl`**, the DACL layer — the read that answers whether a SID is already granted, added on 2026-09-25 when that read moved off `icacls`'s text and onto the API, and the grant's own open, read and write since 2026-09-27 (`CreateFileW` with `FILE_FLAG_OPEN_REPARSE_POINT`, `GetSecurityInfo`, `GetAce`, `EqualSid`, `SetEntriesInAclW`, `SetSecurityInfo`, `ConvertStringSidToSidW`, `LocalFree`); and **`sweep`**, the stale-profile reaper decision 21 states — a Toolhelp process snapshot (`CreateToolhelp32Snapshot`, `Process32FirstW`, `Process32NextW`, `GetCurrentProcessId`), the `Storage` key listing (`RegOpenKeyExW`, `RegEnumKeyExW`) and the key's removal (`RegDeleteTreeW`, `RegDeleteKeyW`) — each of the seven carrying one file-level `#[allow(unsafe_code)]` — plus **two function-scoped sites in `lib.rs`**, the crate root's, which is the form a site that is a single function takes: `from_wide`, reading a NUL-terminated kernel answer into a `String`, and `from_wide_units`, the same read handed back as units so that a *path* can be built from it without the lossy text conversion `from_wide` performs. The second is the one this pair gained last (2026-09-23, before `acl`): `handles::system_directory` resolves the kernel's answer and a system directory is a path, so routing it through the `String` form was the `to_string_lossy`-on-a-path mistake the crate's own UTF-16 rule forbids (`crates/tinio-sandbox-windows/src/lib.rs`; the `wide_os` helper this sentence used to name is gone, the writer being `tinio_winsec::to_wide` now and `from_wide_units` the reader that avoids the lossy form). **Two function-scoped sites are still one enumeration's worth of scope** — both are the same read, one conversion apart, in the crate root — but a reader counting them should count both, because that is what the lint sees. **One crate outside this feature's five is also `deny` with an allow, and it is enumerated here because this list is the one the lint rule points at**: `tinio-winsec`, the current-user-only file-DACL writer the config file and the management plane's state file share, carries one module-level `#![allow(unsafe_code)]` in `crates/tinio-winsec/src/dacl.rs` — the module-level form the operator accepted for it, matching `tinio-sandbox-windows`'s `acl.rs` — with a `// SAFETY:` argument on each raw block and `descriptor_is_current_user_only` a `pub unsafe fn` with its own `# Safety` contract; the crate-level allow this file used to carry is gone, so the manifest's `deny` binds every other module it has (2026-09-27). **A second crate outside those five joined it on 2026-09-28, and its shape changed on 2026-09-29 when the job-object sequence moved down into it**: `tinio-util` is `deny` for **two** module-level `#![allow(unsafe_code)]`s. `crates/tinio-util/src/job_object.rs` is the Win32 job-object call sequence itself — `CreateJobObjectW`, `SetInformationJobObject`, `AssignProcessToJobObject`, `IsProcessInJob`, `QueryInformationJobObject`, `TerminateJobObject` and `CloseHandle`, plus a `Send`/`Sync` wrapper for the handle, because a job handle is not thread-affine and the guard holds one in a `static` — and it is **the one part of that crate a production build compiles**: the per-launch job `tinio-sandbox-windows` creates is created by the launcher's own build, so the module is `#[cfg(windows)]` and **not** feature-gated, and `windows-sys` under `[target.'cfg(windows)'.dependencies]` stopped being optional on that date. The sandbox crate's own `job` module is expressed on that primitive now and **is no longer one of its sites** — it lost its file-level allow with the calls, which is why the Windows count above is one lower — while `crates/tinio-util/src/job.rs` is the spawn guard that makes a test-spawned server die with the test process and stays where it was: `#[cfg(any(test, feature = "testing"))]`, so no production build compiles it, keeping the two calls that are its own — `GetCurrentProcess`, the adoption of the test process, and, on Linux, **the Linux arm's site, `#[cfg(target_os = "linux")]`**: the `pre_exec` registration in `arm_parent_death_signal` that sets the child's `PR_SET_PDEATHSIG` to `SIGKILL` — `unsafe` because `Command::pre_exec` is an `unsafe fn` and not because the call inside it is, the closure running `rustix::process::set_parent_process_death_signal`, a safe wrapper, since only async-signal-safe work is permitted between `fork` and `exec` — which the two test harnesses reach through `tinio_util::testing::job::spawn` (§13 of the follow-ups plan is the incident it answers to, and the module doc owns the mechanism, the fallback and the limits it does not close). **The count is the code's rather than an enumeration's, and the sentence that had drifted was this one**: it used to read that `acl.rs` "carries no allow and makes no raw call", which was the plan's first recorded decision about the DACL **writes** — every grant and revoke still goes through `icacls.exe` as a child process — carried over to the module as a whole after the 2026-09-25 landing moved the DACL **read** onto the API. **The writes stopped shelling out too on 2026-09-27** — every grant is FFI on the handle the module opened, and `icacls` remains `revoke`'s path and the tests' oracle — which is why `acl.rs` carries the file-level allow its own header calls "the exception ... on the module that needs it, as decision 14 asks" and why the module is enumerated here rather than described as clean. What a reader should count is `rg -n 'allow\(unsafe_code\)' crates/tinio-sandbox-windows/src`: **seven file-level attributes and two function-scoped ones**, and the doc comments that mention an allow are not sites — `backend`'s module doc says the module carries none, and it carries none, because the AppContainer rule and the reparse-point check it composes reach Win32 through this crate's other modules and through `icacls.exe` rather than through `unsafe` of its own. Every further module joins the list as it lands, and the count follows the implementation rather than being fixed in advance. A second copy of the list anywhere else is the thing that drifts. `forbid` cannot be overridden at all, so `deny` is what makes the exception expressible where it is needed and nowhere else. The exception is inside the **default** build because the feature is default-on; `--no-default-features` strips it.
15. **Grant-only, never revoke-then-grant — and standing, granted once and kept.** The Windows launcher adds its ACEs and keeps them: a grant is written once for a root, the next run on that root finds it already there and skips the write, and **the launcher removes nothing on the way out** — not on the clean path, not on the failure path. It never rewrites a directory's existing DACL, and the POSIX permission bits and existing ACEs are left alone, so a sandbox run cannot lock an operator out of their own data. **This paragraph used to require the opposite — "roll back on every exit path", including the failure path — and the operator's ruling replaced it after measurement rather than preference**: the rollback was a second full-tree pass per run, and the skip that replaced it takes readiness on a served root down by **~170×**. **The raw figures, the `ChangeTime` cross-check and the per-object write rate of the first run are `plans/2026-09-25-sandbox-followups.md`'s "Verified 2026-09-25" section, which owns them** — this decision states the contract they justify and does not restate the measurement. **The exposure this buys is stated rather than implied: every root ever served keeps its package-SID ACE until an operator revokes it**, with `icacls <dir> /remove:g "*<sid>"`, because nothing in the launcher does. **The ACE ledger that lets an operator list what stands has landed** (`crates/tinio-sandbox-windows/src/ledger.rs`, one appended line per granted path, the root and every other path the caller exposed — §6's ledger paragraph owns the file, the fields and why it appends and never revokes, and `plans/2026-09-25-sandbox-followups.md` §10 is the item it answers, landed 2026-09-28); taking a grant back is still an operator's own `icacls … /remove:g` and nothing in the launcher's. The profile half of the same artifact is still removed on a clean exit (decision 21), and the four places residue can be found are the Risks table's.
16. **On macOS and Windows the parent binds the listener and hands the socket to the child.** No `network-bind` is needed **for the serving path**, which is what lets the macOS profile spend no bind rule on the data plane, and the parent becomes the authority on the port. On macOS the measurement goes further than the design expected: `accept` on an inherited listener is not gated by any network rule, so a profile granting no network operation at all still serves — which is why the macOS row of §7 reads as it does. **The child's own local management control socket is a second handoff, and the 2026-09-25 run of the product through `tinio server … --sandbox` is what separated it from the data plane's**: a unix socket `bind()` **is** gated, and the confined child then bound `…/.tinio/tinio-<hash>.sock` itself and died without a rule with `management error: transport: could not bind …: Operation not permitted (os error 1)`. The launcher now binds that socket outside the sandbox and the child adopts the descriptor, exactly as for the listener, so **the emitted profile carries no network rule at all** — see §5 and §7. A narrower spelling of the bind was tried and did not compile, which is why the bind moved instead of the rule being narrowed. **On Windows it is still not a network-isolation mechanism and the design does not rely on it as one**: AppContainer's network policy is enforced by WFP against the process's AppContainer SID, not against whoever created the socket, and the probe that proved the Windows handoff used loopback — which works without a capability anyway. The macOS result does not transfer to Windows, because there the policy attaches to the process, whereas on macOS the check that would have applied simply does not exist.
17. **The launch payload travels on the child's stdin as one JSON line, and there is no environment-variable marker.** The parent writes `{"config":"…"}` to the child's standard input and closes it; a child that reads it and the argv element that names the inherited listener knows it is the confined child. **The pipe is still there, and the earlier draft was wrong to claim otherwise**: a payload that flows parent → child on stdin needs a pipe the parent writes and closes, and both launcher platforms create one — `Stdio::piped()` on macOS, an anonymous pipe whose child end becomes `hStdInput` on Windows. What the stdin form buys is that the child reads a stream it already knows by convention instead of a numbered descriptor it must reconstruct, so the payload's *descriptor argument* and the rebuild-from-raw-descriptor both go away, and stdout is left as the only stream the protocol has to name. The child consumes stdin and never needs it again; `serve` has no other use for it.
    **There is no nonce, and the earlier draft was wrong to want one.** It was described as the child's discriminator, but the parent writes the nonce to the same stream it writes everything else to, so anything able to forge a payload already knows the value — it defended against nothing that the payload's own shape did not already defend against. What actually identifies a confined child is the **argv element naming the listener descriptor** plus a payload that decodes; a process that finds no element treats itself as the launcher, and a launcher inside a confinement fails closed because it can neither grant ACLs nor bind. Removing it also removed the format: the frame was a magic constant, a nonce, a length prefix and raw bytes, and is now one JSON line that `serde` reads and writes on both sides, with trailing bytes rejected by the deserializer's own end check. `config` travels as text because `Config::load` already requires UTF-8.
   An environment-variable marker would have been forgeable — setting it would make a process believe it was already confined and skip the sandbox entirely, which is a bypass of the whole feature. The payload cannot be forged by anything that did not inherit stdin. A child that finds no valid payload treats itself as the launcher, and a launcher inside a confinement fails closed because it can neither grant ACLs nor bind.
   **Reading stdin is conditional, and the condition is the argv element.** A process started from a shell owns its stdin — the operator's terminal — so a blind read-to-end would block a launcher that nothing launched, waiting for input that is never coming, and look like a hang rather than a refusal. The child therefore reads stdin only when argv carries the listener descriptor, which only a parent puts there; anything else is a launcher, and the payload check still runs on top of that once the bytes are read. Writing the rule as "the child reads stdin and validates" without the precondition would have made the design's own discriminator unreachable.
   **The argv element survives, carrying something else.** `tinio-sandbox-fd=<n>` names the inherited **listener** descriptor, because a socket cannot travel on a stream — the descriptor-passing half of decision 16 is irreducible whatever the payload does. It stays in the core, shared by both launcher platforms: they never interoperate, so a per-platform spelling would work perfectly while drifting unnoticed, which is the failure the core exists to prevent.
18. **The parent never builds a `Config`.** It forwards the configuration's *bytes* without constructing a parsed structure, so the unconfined process retains no credential-bearing object. The one exception is a targeted lookup of `server.read_only`, because the served root's access mode depends on it and FR-023 allows read-only to be set in the configuration file; that lookup reads the single key and drops the document. The parent still has the bytes transiently — it must, in order to forward them — so the property this decision buys is *no retained parse*, not *no contact*.
19. **stdout carries a structured event stream and nothing else; every log goes to stderr.** The endpoint is no longer a human line to be scraped but an event to be decoded: **SSE**, an `event:` line naming the event and a `data:` line carrying its JSON object, closed by a blank line. SSE rather than bare JSONL because an error message containing a newline would otherwise split one record into two and neither half would parse, because the standard already defines how a `data:` value carries newlines, and because the framing is a published standard rather than something this project invents. The name and the payload travel in **different fields** — `sse-core` hands them over as one `MessageEvent { event, data }` — so nothing is stored twice and there is no tie-breaker to need. The child's **stderr is inherited, never piped**: it is the log channel, there is no second stream to drain, and no deadlock to design around.

   The contract this decision replaced was `wait_for_ready` reading the child's stdout until it found `listening on `, and it was brittle in a way that has nothing to do with sandboxes: **any stray write to stdout — ours, or a dependency's — broke readiness detection**, and it broke it as a timeout rather than as an error. Reserving stdout for the protocol removed that failure class permanently; **P1 landed the replacement** — `crates/tinio-e2e/tests/steps/clients.rs`'s `READY` constant is gone and `wait_for_ready` decodes frames — and the section's Bookkeeping records the two readers it moved.

   **Who writes the event differs by platform; what the consumer sees does not.** Linux confines in place, so the process writes its own `Listening` event once the jail is built and the listener is bound. On the launcher platforms the child writes to a stdout that is a pipe to the parent, and **the parent re-emits** — decoding each frame and writing it on rather than forwarding bytes, so a corrupted or foreign line cannot reach the operator. The relay is shared by both launcher platforms and lives in the core, for the same reason the payload does.

   **The parent also owns the answer for a child that never reported at all.** It re-emits what the child sent and emits nothing on its own behalf, so a child that dies before its first frame would otherwise be indistinguishable from one that is still starting — and the consumer would wait for an endpoint that is never coming. The relay therefore records the terminal event it saw, the platform keeps that record beside the child, and the parent reads it **after** the wait: `supervise` borrows the child rather than consuming it, and `Child::wait` joins the relay thread before returning, because the process being reaped and the relay noticing end-of-stream are two events with no ordering between them. Reading the record earlier — the only thing a by-value `supervise` allows — is reading a snapshot, and on a healthy child it usually reads nothing at all.

   Two consequences that were asymmetry under the old contract stop being observable: a consumer no longer cares which process wrote the endpoint, and a startup failure is an event rather than an absence. **One asymmetry remains, and it is about *when* rather than *who*.** The event is always the child's, because only the process serving the data plane can say it is serving. But on the launcher platforms the parent has already bound the port before the child exists, so it *knows* the endpoint well before the stream carries it — and a caller that needs the endpoint before the child comes up is asking for something the event deliberately does not promise yet. The answer is to ask for a fixed port rather than port 0, which such a caller should be doing anyway. Linux is not different in kind: there the process binds after confinement, so `Listening` necessarily follows it.
20. **The child's lifetime is tied to the parent's by a Job object, and the parent forwards termination signals to it.** `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` means killing the launcher takes the confined server with it, instead of leaving an orphaned confined process holding a listener; the residual ACEs that a hard kill leaves are the deterministic SID's problem (decision 21), not this one's. Signal forwarding is the other half of the same obligation and is spelled out in §3 step 9 — **required on Windows**, where a container signals only its main process and nothing else, and defensive on macOS, which has no native container runtime and whose `launchd` reaches the job's process group by default. The two together are what makes "the parent is only a supervisor" true rather than hopeful. **The job object is Windows's, and macOS's launch-failure path does not pretend to it (correction, 2026-09-26):** a macOS launcher that fails *while it is running* — the `state` publish after the child reports listening — ends and reaps the child it started through `Child::kill`/`Child::wait` (`crates/tinio-sandbox-core/src/launcher/supervise.rs`, supplied by `tinio-sandbox-macos`'s `confine`), because a dropped `Child` is not an ended one where no job object exists. That is this decision's second obligation applied to a running launcher, and it leaves the first one's accepted gap as the only gap: a launcher killed outright still leaves the confined server.
21. **The Windows package SID is derived, not generated.** `DeriveAppContainerSidFromAppContainerName` is deterministic for a given name, so a crash that leaves ACEs behind leaves *identifiable, reusable* ACEs rather than orphans — the launcher takes over its own residue on the next run instead of accumulating new ones. **The same name also creates a container profile** (`CreateAppContainerProfile`), which the measurement of 2026-09-19 shows is required before anything can be launched under that SID at all; it is created on the same pass, taken over on the same `ERROR_ALREADY_EXISTS` path — where the SID comes from `DeriveAppContainerSidFromAppContainerName`, because the collision reports that code with the SID out-parameter left null (measured 2026-09-21, and the Windows SDK's own sample answers the code the same way) — and removed on every exit path that runs a destructor, so the two artifacts share one name, one derivation and one takeover, but not one lifetime: the profile is deleted while the ACEs stand (decision 15, amended to standing; the Risks table's residue row owns what the delete does and does not take with it, the profile's own `%LOCALAPPDATA%\Packages\<name>` directory among them — **and what that directory's own DACL says while it exists is measured there too: the parent `Packages` descriptor, inherited entry for entry, with no package SID and no capability SID in it, so it is "nothing to do" rather than a hole** — measured 2026-09-28), and **what that descriptor cannot hide is the name itself: it is the derivation's spelling, `%LOCALAPPDATA%\Packages\<name>`, and an account that can list `Packages` reads it there — which is why §6's salt paragraph states pre-computation as the salt's scope rather than "the name is hidden"**. **One root's launch window and one root's profile deletion exclude each other through a per-root cross-process mutex** (`crates/tinio-sandbox-windows/src/sid.rs`'s `ProfileLock`): the object is named `Global\tinio.profile.<package_name>` — keyed on the same derivation `package_name` makes, so the lock's name and the profile's name cannot describe different roots — and it is held from before the profile is derived until `CreateProcessW` has returned, with `PackageSid`'s `Drop` taking it around the delete. **The window it closes is the launch arm of the sharing, and it is measured on this host rather than reasoned** (non-elevated, 2026-09-26; the lock's own half 2026-09-27): two launchers on one root share one profile — the second `CreateAppContainerProfile` collides and the takeover above returns the first run's SID — so a delete landing between a peer's derive and its `CreateProcessW` makes that peer's launch fail with the `err=2 ERROR_FILE_NOT_FOUND` the evidence table records for a SID with no profile behind it, which is the whole harm. **What the window's two halves were measured as, rather than the race being observed**: `DeleteAppContainerProfile` answered `hr=0` while a live confined child held the SID, and a `CreateProcessW` for that SID with the profile gone failed `err=2` in all three shapes tried (the launcher's own attribute list, a plain launch, and `ping.exe`); **a running confined child is unharmed by a peer's delete** (that child stayed alive, still `isAppContainer=true` with the same package SID, and it still wrote through its ACE after the delete) **and a later launch heals itself** (a re-create yields the same SID, after which the launch succeeds). **The lock itself is usable where it is needed**: measured on the same host and the same non-elevated user, the `Global\` object is created, a second process opens it by name, and a peer's bounded wait times out while the holder owns it. **Acquisition never fails a launch.** A holder killed inside its window leaves the kernel to release the object, so the waiter's `WAIT_ABANDONED` takes the lock over and warns rather than hanging or failing; and a host that refuses the machine-wide namespace outright degrades to the pre-lock behaviour — a **warned no-lock path**, which the operator ruled to accept rather than fail closed, because what a launcher would trade for refusing is a total failure in place of a rare misdiagnosis. **What the delete cannot reach is the exit that runs no destructor, and the launch path reaps it.** A launcher killed, a test aborted, the `STATUS_STACK_OVERFLOW` abort of 2026-09-28: no `Drop` runs, so the profile's directory and its `Storage` key both stay — 815 of each measured on this host 2026-09-28 — and the operator ruled that they are reaped at launch rather than accumulated. The definer is `crates/tinio-sandbox-windows/src/sweep.rs`: `stale_profiles` runs **once per process**, called from `backend::prepare_launch` **before the served root's own name is derived**, so the profile the run about to start will create can never be a candidate. Four rules bound it, each one a way a sweep could delete a live server's profile instead of stale residue: it touches only names spelled with `PACKAGE_PREFIX` (`tinio.sandbox.`), in `%LOCALAPPDATA%\Packages` and under `HKCU\Software\Classes\Local Settings\Software\Microsoft\Windows\CurrentVersion\AppContainer\Storage`, and nothing else in either listing; it skips the whole sweep while any *other* process named `tinio` is alive — a confined server **is** a `tinio` process, because the launcher re-invokes its own image, and the per-root `ProfileLock` is no evidence against one since the launcher releases it at `CreateProcessW` — and it skips as well when the process list cannot be walked; it takes each candidate's `ProfileLock` non-blocking and leaves any name a peer is mid-window on; and a name is reaped as `DeleteAppContainerProfile(name)` **plus** its `Storage` key, each half attempted whether or not the other is there. **It can never fail a launch**: every failure warns at `step = "sweep the stale profiles"` and the launch proceeds, and one `info!` line per sweep reports the counts (reaped, locked, failed, the gate's process count). **What the rule does not guarantee is stated with it**: the gate keys on the launcher's image name, so a launcher renamed away from `tinio` is invisible to it and would be swept while serving, and a machine that never launches this launcher again keeps its residue.
22. **On Windows the executable's own directory is exposed read-only automatically — and the rule is Windows's alone.** **The rule is the safe side of two measurements that disagreed, and a third has settled them.** The disagreement is stated where it started, because the losing half of it used to live here: **this decision said that without an ACE on the directory holding the binary the confined child cannot load at all, measured 2026-09-19 in this paragraph rather than as a table row**, and the 2026-09-21 probes reproduce that **only** for a binary that imports something beside it, so what that sentence measured was a child that died, not a launch that was refused. What reconciles the two is the mechanism, and it is what the rule now rests on: `CreateProcessW` opens the image with the **launcher's** access, so a confined child whose dependencies all live in `System32` starts and runs with **no** ACE on the directory holding it — and a binary that imports a DLL beside it starts and then **dies**, `0xC0000135 (STATUS_DLL_NOT_FOUND)` with nothing printed, while the identical launch with the directory granted read-only exits `0` (both 2026-09-21; the evidence table's row carries the reproduction). What the grant therefore buys is the child's **own** loader rather than the launch, and it is kept because the failure it prevents is a confined process that dies on startup with no diagnostic — neither a `CreateProcessW` error nor a line in the log. The directory belongs to the tool rather than to the operator's data, and the grant it is given on Windows is the one **Ruling 78 (2026-09-22) set on measured numbers**: one **non-inherited** `RX` ACE on the program's own directory and **non-inherited** `RX` ACEs on the `*.dll` files **directly beside** the program, granted **one handle-opened ACE per enumerated file** since 2026-09-27 — the enumeration is by name and a sibling that is a reparse point is refused (its `symlink_metadata` failing is a refusal too, not an `Ok`), because the single `*.dll` pattern the tool accepts (`<the program's directory>\*.dll` — a *list* of paths is not a form `icacls` takes, measured 2026-09-21) was the batch that granted a linked `x.dll` through its **target**, outside the program's directory. What that buys and what it deliberately does not reach are both the rule rather than an implementation detail: the loader searches the executable's own directory for the modules an image imports statically, **a DLL in a subdirectory of that directory or one loaded from elsewhere at runtime is not granted**, and the confined process can read the files the loader itself reads — not the tool's whole install tree. The whole-directory alternative was refused because the ACE it writes propagates to every descendant: in this workspace the program directory is `target\debug\deps` with **5 129 objects of which 68 are `*.dll`**, and the phase's measured rate put that at **about 1.6–1.9 s per launch walked twice** (§6 carries the rate and the Risks table the guidance). The boundary the rule draws is the loader's search path **as measured rather than assumed**, and a binary that needs a DLL from a subdirectory or from elsewhere at runtime is a case this rule does not grant. **An earlier draft generalised this to "launcher platforms", which the macOS measurement does not support**: there a confined binary runs with no grant of any kind on its own location, `process-exec` being the only gate — `file-read-data` on its own image and on its directory is refused and logged, and the program proceeds regardless, for an 81 MB Rust server as much as for a small C tool. Linux never needed it either, the image being already mapped and the jail confining in place. So this is the one platform where the tool's own location has to be granted, and macOS deliberately does not spend a grant on it.
23. **Outside Linux, macOS and Windows, `--sandbox` is a best-effort `chroot(2)` with a startup warning.** No mount namespaces, no capability model and no network isolation are available there; `chroot(2)` delivers the directory boundary and nothing else. The warning enumerates exactly what this platform cannot deliver, every time the flag is used, so the gap can never be inferred as covered. The alternative — refusing to start — was considered and rejected by the operator on 2026-09-18 in favour of "partial and loudly labelled"; this is the one place where the design knowingly delivers one of the three guarantees instead of all three, and it is the reason the Goal scopes itself to three platforms. **No phase of the four delivers it, and since 2026-09-19 the documents say that plainly rather than leaving it to be inferred from the phasing**: an earlier draft presented it as a fourth phase that merely had not been written, but no plan implements it, and P0's facade has no `platform()` outside the three targets — so on a fourth platform the code does not compile and the promised startup warning can never fire. What such a platform gets today is a compile error naming the missing crate, which is the honest outcome and is what §2, §11 and §13 now say. When P4 is written it re-enters this decision as an implemented guarantee with its own evidence, not as a promise.
24. **`sandbox-exec -p` carries the profile inline, with exposed paths passed as `-D` parameters.** The macOS profile is passed as an argv element, so no profile file is created and nothing needs cleaning up. The consequence is that the profile is visible in the process list; its contents are paths, not credentials. `sandbox-exec` has no fd or stdin form, so the alternative was a `0600` temp file with an exit-path cleanup. The two were measured equivalent on macOS 15.8, and the inline form is never the tighter limit: a profile that compiles is bounded by the ~64 KiB compiled-object cap of §5, while argv is bounded by `ARG_MAX`, which is an order of magnitude larger. Exposed paths travel as `-D` parameters referenced by `(param "…")` rather than being interpolated into the profile text, which removes profile injection from path handling entirely: a value is data, and a deliberate attempt to close the literal and open a rule was measured granting nothing. What a parameter *can* do is grant a great deal legitimately — a value of `/` is a valid grant of everything — so **path validation, not the profile text, is what bounds the exposure set**, and the generator validates as it did before. The gain is that escaping and its failure modes disappear from the profile builder.
25. **A configured OTLP endpoint and `--sandbox` are mutually exclusive, and the combination is reported on stderr rather than refused.** The only outbound code path in the runtime is the OTLP-gRPC exporter, and a seccomp filter that blocks outbound necessarily breaks it, so the two cannot both be honoured. **The operator's ruling of 2026-09-19 is that the conflict is a `warn!` on stderr through the sandbox's own tracing, not a startup failure** — an earlier version of this decision made it fatal. The confinement is what was asked for and it is applied; what is lost is the export, and losing an observer is not grounds for refusing to serve. **This is a deliberate exception to the fail-closed posture the rest of this design keeps, and it is only defensible because the warning is unmissable**: it is emitted at startup on the same stderr channel every other sandbox log uses, naming both the endpoint and the flag, rather than logged once and forgotten. The check fires only when both are genuinely active (sandbox requested *and* an endpoint configured), so it costs nothing until an operator configures `[telemetry] otlp_endpoint` and `otel` is not a default feature. **It is implemented now, and the CLI is where** (2026-09-27): `crates/tinio-cli/src/sandbox/confine.rs`'s `lost_export` answers the two facts — the channel that asked and the endpoint the confinement costs — from the resolved `Request` and the resolved config, and `crates/tinio-cli/src/commands/start/run.rs` emits the one `warn!`, on the single line both the launcher and the in-place arm reach with the log live. It is a `warn!` and never an `Error` frame: stdout carries the event protocol and nothing else (decision 19). The confined child asks for nothing, so the warning is the launcher's alone and the child inherits the stderr it is written on.
26. **The confinement is one-way and is entered before the runtime exists.** On Linux `enter()` is irreversible by construction; on all three platforms it must run before any thread is spawned, which §10 orders explicitly and which is what makes the seccomp filter correct without cross-thread synchronisation and what keeps `unshare` from returning `EINVAL`. **The macOS in-process apply is the one measured exception, and it is not adopted**: a thread created before the apply does not block it (evidence table), so on a launcher platform this order is the shape of the launch — the profile lands by an exec, before the child's runtime exists — rather than a constraint Seatbelt imposes.
    **Linux now refuses the state instead of trusting the order** (2026-09-27): `enter` runs `refuse_when_threaded` before the `unshare`, the capability drop and the filter, and fails closed — `Error::Step` with step `confine single-threaded` — when `/proc/self/task` cannot be read at all or holds more than one entry. Every operation of the sequence is per-thread, so a sibling would keep the host mount namespace, the full credentials and an unfiltered network while the run reported `Confinement::InPlace`; `SECCOMP_FILTER_FLAG_TSYNC` was rejected as the half measure, because it synchronises the *filter* alone. **The CLI's subscriber is the other half of the same fact, and its position is now part of the order**: on the in-place arm it is installed **after** `confine`, because `tinio_server::log::build_subscriber` starts `opentelemetry_sdk`'s batch-exporter thread at construction when an OTLP endpoint is configured, and a thread created before the confinement stays outside it; on a launcher arm it is installed **before**, because a launcher's confinement is its child's and a subscriber built after the call would never see the backend's own launch events. **What the in-place order costs is stated rather than glossed: the Linux confinement's own events are no longer logged on a production run** — the backend emits them inside `confine`, where the process has no subscriber yet — and only the returned `Error` survives; the operator accepted that trade, and it is why the refusal's failure must read legibly through the error alone.

## Design

### §1 The crates, the feature gate, and the API

Five crates, layered so no edge points back up (decision 3):

```
tinio-sandbox            facade — target-gated re-export of core + the one platform crate
   ├── tinio-sandbox-core          trait, vocabulary, launcher machinery  (no platform FFI)
   ├── tinio-sandbox-linux         implements Backend: plan, jail, caps, seccomp
   ├── tinio-sandbox-macos         implements Backend
   └── tinio-sandbox-windows       implements Backend
```

**The sketch below is indicative, not normative.** The exact signatures — parameter and return types, owned versus borrowed, which constructor generates what — are fixed in `docs/superpowers/plans/2026-09-18-sandbox-p0-core.md`, which is the plan that builds `tinio-sandbox-core` and the document the platform plans consume. This section states the *shape* and why it is that shape; P0 states the spelling. Keeping a second copy here would recreate the drift that splitting P0 out was meant to end — three documents defining one API is how the platform plans came to disagree about it in the first place.

The core's public surface, in outline:

```rust
/// Whether an exposed path is writable inside the confinement.
/// Not declared here: `tinio-sandbox-core` re-exports `tinio_core::AccessMode`
/// (`ReadWrite` — its `Default` —, `ReadOnly`, `is_read_only()`, `From<bool>`),
/// so an exposure takes the same value the read-only work already resolved.
pub enum AccessMode { ReadOnly, ReadWrite } // stands for `tinio_core::AccessMode`, re-exported

/// The set of host paths the confined process may reach. Pure data.
pub struct Sandbox { /* … */ }

impl Sandbox {
    pub fn new() -> Self;
    pub fn expose(self, host_path: impl Into<PathBuf>, access: AccessMode) -> Self;
    pub fn exposures(&self) -> &[Exposure];
    /// The first exposure, refused when the set is empty (the served root's one home).
    pub fn served_root(&self) -> Result<&Exposure>;
}

/// What the call site must do once `confine` returns.
pub enum Confinement {
    /// The calling process is confined; carry on. (Linux.)
    InPlace,
    /// A confined child is running; wait, forward its status, undo the setup.
    Supervise(Child),
}

/// What the launcher needs that is not a path: the child's argv, the payload,
/// the inherited listener descriptor.
pub struct LaunchPlan { /* … */ }

/// What the confined process reports on stdout (decision 19).
pub enum Event {
    /// The listener is bound and the data plane is serving.
    Listening { addr: SocketAddr },
    /// A fatal startup failure, already rendered for the operator.
    Error { message: String },
}

impl Event {
    /// One SSE frame: an `event:` line, a `data:` line and a blank line.
    /// ```text
    /// event: listening
    /// data: {"addr":"127.0.0.1:9000"}
    /// ```
    pub fn encode(&self) -> String;
    /// Decode from a whole frame, or from its two field values; `None` for a
    /// name this protocol does not define, a payload that does not parse, or
    /// anything that is not one of ours. The two-field form is `pub(crate)` —
    /// it is the relay's internal seam, and every outside consumer holds a
    /// whole frame.
    pub fn decode(frame: &str) -> Option<Self>;
    pub(crate) fn decode_fields(name: &str, data: &str) -> Option<Self>;
}

/// The child's parsed stdout, one frame at a time. `sse-core` is the state
/// machine that assembles a frame split across reads — **one decoder for the
/// whole stream**, because the half-parsed event lives in the decoder rather
/// than in the buffer — and `Observer` feeds it and records whether the child
/// ever became ready. **`record` is pure and `observe` is async**: the frame
/// logic is tested without a runtime, and the I/O is async because a launched
/// child's streams are pipes the runtime owns. `reemit` — the one-line relay
/// with no record — is `pub(crate)`, for the reason every launcher-platform
/// decision in this document keeps running into: publishing it would offer the
/// relay without the answer.
pub struct Observer<W> { /* … */ }
impl<W> Observer<W> {
    pub fn new(inner: W) -> Self;
    pub fn record(&mut self, name: &str, data: &str) -> Option<Event>;
    pub fn terminal(&self) -> Option<&Terminal>;
}
impl<W: AsyncWrite + Unpin> Observer<W> {
    pub async fn observe(self, reader: impl AsyncBufRead + Unpin) -> Result<Self>;
}

/// A child a launcher platform started: the platform's wait, the relay's thread,
/// and the relay thread whose **join carries the answer back** — there is no
/// shared cell, because nothing has to be read before the join happens.
pub struct Child { /* … */ }
impl Child {
    pub fn new(wait: …) -> Self;
    pub fn with_relay(self, relay: JoinHandle<Option<Terminal>>) -> Self;
    /// Waits for the child, **then joins the relay** — which is what makes
    /// `terminal` a result rather than a snapshot.
    pub fn wait(&mut self) -> Result<ExitStatus>;
    pub fn terminal(&self) -> Option<&Terminal>;
}
/// Borrows the child rather than consuming it, so the caller can ask
/// `Child::terminal` what happened once the wait is over (decision 19).
pub fn supervise(child: &mut Child, teardown: impl FnOnce()) -> Result<ExitStatus>;
```

The **event name and the payload travel in different SSE fields**, which is the standard's own shape and what `sse-core` hands back as one `MessageEvent { event, data }`:

```text
event: listening
data: {"addr":"127.0.0.1:9000"}
```

Repeating the name as a member of the payload would be one fact stored twice with no tie-breaker when the copies disagreed. `addr` is a `SocketAddr` rather than a string or a bare `IpAddr`: it is exactly what `TcpListener::local_addr` returns, and it is the only form that carries the port, which is what `--port 0` exists to discover. The framing is `sse-core`'s resumable state machine rather than a line reader because a child's stdout is a pipe and a frame can arrive in pieces; that crate is also the reason no async-runtime baggage enters the dependency graph (`sse-stream` would have brought `futures-util` and `http-body` unconditionally, and depends on `sse-core` itself). **The child's stderr is inherited, never piped** — so there is no second stream to drain and no deadlock to design around (decision 19).

```rust
pub trait Backend {
    fn confine(&mut self, sandbox: &Sandbox, plan: &LaunchPlan) -> Result<Confinement>;
}
```

A `Sandbox` is pure data. The mount table, the mirrored jail paths, the SBPL profile text, the ACL grant list and the capability policy are all pure functions of builder state — but they belong to the platform crates, not the core, because each is a function of one mechanism. What the core keeps is what more than one platform needs: the exposure vocabulary, and the launcher machinery both child-launching platforms share (decision 17's payload and the supervision loop).

The core holds the launcher machinery rather than the facade because the platform crates need it and depend on the core — putting it in the facade would recreate the cycle decision 3 exists to avoid.

Consumers gate on it: `crates/tinio-cli` carries a default-on `sandbox` feature and is the only serving process; `tinio-server` carries the same feature to gate its two confined-e2e test targets through `required-features`. With the feature off, all three request channels are a usage error (decision 5). A consumer that wants a specific platform's options instead of the facade's default selection reaches them through the facade's cfg-gated alias for that crate — `tinio_sandbox::linux::Options` — rather than through a dependency of its own on the platform crate, which is what the facade's own tests do.

### §2 The platform matrix, and the guarantees

| Platform | Mechanism | Enforces | Path namespace |
|---|---|---|---|
| Linux | mount namespace + `pivot_root` | both guarantees | **hidden** — paths outside the jail do not exist |
| macOS | Seatbelt, SBPL via `sandbox-exec -p` | both guarantees | visible, access denied |
| Windows | AppContainer + DACL | both guarantees | visible, access denied |
| other unix | `chroot(2)` (decision 23) — **not delivered by any of the four phases**; such a target fails to compile rather than warning | directory boundary only | visible, access denied |

On Linux `ls /` inside the jail shows the tmpfs and the exposed paths and nothing else. On the other three the path namespace remains enumerable and a non-exposed path is refused rather than absent — **but the refusal is not always distinguishable from absence**, and an earlier version of this paragraph promised that it was. Measured on macOS 15.8 on 2026-09-19: a read outside every grant returns `EPERM(1)`, while a read under a directory whose traversal is refused can return `ENOENT(2)`, which a caller cannot tell from a genuinely missing file. Add that the macOS allowance set legitimately grants read on directories the operator never exposed (§5), and "this path is not there" is a weaker inference on that platform than on Linux. The guarantee is identical on all three; what a caller can infer from the errno is not. The guarantee is identical; what the caller can *observe* about the filesystem layout is not, and the documentation says so rather than implying parity.

`expose` maps onto each mechanism directly:

| | Linux | macOS | Windows |
|---|---|---|---|
| `ReadWrite` | `bind` | `(allow file-read* file-write* (subpath …))` | DACL `M` |
| `ReadOnly` | `bind` + `remount,bind,ro`, under either model, or overlay `MS_RDONLY` where the source mount's locked per-mount flags refuse the remount | `(allow file-read* (subpath …))` | DACL `RX` |
| state dir | `bind`, always `rw` | `file-read*` + `file-write*`, always | DACL `M`, always |

### §3 The launch contract (macOS and Windows)

Steps 6–8 below are the **core's** launcher machinery (`tinio-sandbox-core`, built by P0), not either platform's: the stdin payload, the supervision loop and the exit-status forwarding are identical whether the child is an AppContainer or a Seatbelt profile, and only step 5's application and the `CreateProcess`/`sandbox-exec` call in step 6 differ — steps 2 and 4 are one shared spine in both arms (`tinio-cli`'s `sandbox::launch::prepare`). That shared half is built and tested in P0 even though both child-launching backends are stubs there — the platform crates cannot be written before the trait they implement has been exercised from both shapes, and a trait with one implementor is a guess.

The parent performs the privileged setup and then supervises:

1. Parse `argv`; compute the served root and the state-directory candidates from `argv` and the environment.
2. Targeted-lookup `server.read_only` from the configuration bytes (decision 18) and overlay `TINIO_READ_ONLY` and `--read-only` on the result to fix the served root's `AccessMode`, then drop the document. Only the file channel needs the probe: the other two the launcher reads directly, and the child re-derives the same answer from the same three sources.
3. Bind the listener, mark it inheritable, and keep it alive for the whole run.
4. Compute the exposure set: the served root (per step 2), the state directory if it lies outside the root, the executable's directory as `ReadOnly` together with the `*.dll` files directly beside it (decision 22), and the device files.
5. Apply it — DACLs on Windows **before `CreateProcess`**, because every load the child's own loader performs after creation is checked against its token while the image itself is opened with the launcher's (decision 22), the `-p` profile on macOS.
6. Create the process: `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` plus `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` in a `STARTUPINFOEX` with `EXTENDED_STARTUPINFO_PRESENT` on Windows; `sandbox-exec -p … <self> <args>` on macOS. Assign the child to a Job object (decision 20).
7. Write `{"config":"…"}` — one JSON line — to the child's **stdin** and close it (decision 17); the inherited listener's descriptor number travels in argv, because a socket cannot ride on a stream.
8. Supervise: **relay the child's stdout events** — the `Listening` frame among them — wait for the child, and forward the exit code. **The ACLs are not rolled back (decision 15)**: every grant this crate makes is standing, so the teardown has no ACEs to undo and a failed launch leaves what it managed to write. **The parent does not emit a `Listening` event of its own**, even though it is the process that bound the port: the event means the data plane is serving, only the child knows that, and a parent that printed the endpoint it had bound would be announcing a server that may never accept. What the parent does emit is its own `Event::Error` when the child exits without ever having reported — read from `Child::terminal()` **after** the wait, which is what `supervise`'s borrowed child and `Child::wait`'s join of the relay thread exist to make possible (decision 19).
9. **On Windows, forward termination signals to the child while waiting** (decision 20). On a console the whole process group receives Ctrl+C, and a Unix supervisor usually reaches the child anyway, so it is easy to conclude forwarding is unnecessary. **Measured on this machine's host console on 2026-09-19, and the conclusion is the opposite of that intuition**: the reason is not container behaviour but `CREATE_NEW_PROCESS_GROUP` — the flag the launcher itself passes so the relay has a group to address — because a console-wide `CTRL_C_EVENT` (group 0, what a Ctrl+C keypress produces) fires the launcher's own handler in the same millisecond and **never** reaches the child's, which keeps serving; the identical call reaches a child created *without* the flag. A launcher that forwards nothing therefore leaves the confined server to be terminated at the end of the grace period instead of draining, silently trading away the graceful shutdown the CLI contract promises — ≤10 s of in-flight drain and a removed state file — for whatever a hard stop leaves behind. The container half of the original claim remains unmeasured here (this machine has no Windows container engine), and it is no longer load-bearing: the host-console measurement alone makes the relay mandatory.

**The obligation is Windows-only, and it is worth being precise about why.** Linux confines in place (decision 6), so under a Linux container the server *is* PID 1 and receives the signal directly — the hazard cannot arise. macOS has no native container runtime, and the containers that do run on a Mac are Linux VMs whose tinio takes the Linux path; `launchd`, the only supervisor that matters there, signals the job's whole process group by default. macOS should still relay defensively, because the cost is a few lines and the failure is silent, but Windows is where leaving it out is a defect rather than a polish item.

Forwarding is a platform obligation, not core machinery: the handler must be async-signal-safe, and it needs the child's identity, which the platform crate that created the child already holds. `tinio-sandbox-core` therefore does not change — the platform backends install the handler and relay before calling `supervise`.

The child is identified by step 7's payload, never by an environment variable (decision 17). Its argv carries the inherited listener's descriptor number and nothing else that is security-relevant; a child that cannot obtain a valid payload treats itself as a launcher, which inside a confinement fails closed.

The relay in step 8 is what makes stdout trustworthy on the launcher platforms: the parent decodes each frame and writes on only what parses as one of our events, so anything else the child or its dependencies print to stdout is dropped rather than passed to an operator who would have no way to tell it apart from a real event. The child's **stderr is inherited untouched** — that is where every log goes, and the parent does not mediate it.

### §4 The Linux mount table

The new root is a tmpfs mounted on `$TMPDIR/.tinio-jail-<hash(root)>` (decision 10), mounted `size=1m,mode=0755`. The jail's own writable space is deliberately small: what lives in it is mount points, the `put_old` directory, and — for a read-only exposure under the user namespace — the overlay's `upper` and `work` directories under `<jail>/.overlay/`. **That directory is reachable by the confined process** and shares the same 1 MiB. **An earlier version of this sentence said a write aimed at a read-only exposure's upper fails with `ENOSPC`, and that path is unreachable**: the overlay is mounted `MS_RDONLY` from the start, so such a write is refused by the mount with `EROFS` and never reaches the tmpfs quota. The `size=1m` is therefore a bound on what the *jail itself* costs rather than a second wall behind the read-only mount — and it is worth doing the arithmetic the constant implies, because otherwise it reads as a guess: what lands in it is mount-point directories, the mirrored path prefixes, `put_old` and `.overlay/{upper,work}` — directories and dentries, which `size=` does not bound the way it bounds file data. The one thing the constant does *not* bound is the host `$TMPDIR` space the jail occupies. For each exposed path the jail creates the **original absolute path** inside the tmpfs and mounts there:

| Path inside the new root | Contents |
|---|---|
| `/` | the tmpfs |
| `<served root>` | `ReadWrite`: `bind`. `ReadOnly`: `bind` then `remount,bind,ro`, which succeeds where the source's locked per-mount flags are the ones the request re-asserts — a bind of a flagless ext4, 9p or drvfs source among them, per the re-measurement recorded above — and returns `EPERM` where they are not. On that `EPERM` the fallback is `overlay(lowerdir=<served root>, upperdir/workdir on the tmpfs)` mounted `MS_RDONLY`, which is read-only by construction |
| `<state dir>` — only when it lies outside the served root **and holds none of it**; a state directory that holds the served root is refused in the launcher **on either run**, because its `rw` bind would cover the served root and everything beside it | `bind`, always `rw` |
| `/dev/{null,zero,random,urandom}` | file-level bind |

then `pivot_root(jail, jail/.oldroot)` followed by `umount2("/.oldroot", MNT_DETACH)`.

Two mount details the table cannot show. **Every bind is recursive** (`MS_BIND|MS_REC`): inside a user namespace a bare `MS_BIND` of a mount-point source is refused with `EINVAL` (measured), and the difference between the two forms is invisible for a source with no submounts — so the recursive form is the one to write everywhere rather than the one to special-case. And **`/` is made private** (`mount(NULL, "/", MS_REC|MS_PRIVATE)`) before anything is mounted, because `pivot_root` requires it; on the host measured this is already the case, so the call is defensive, one syscall, and the reason it is unconditional is that the hosts where it is not already private are exactly the ones where the failure would be a confusing `EINVAL` at the pivot.

The `/dev` mount points are created as empty files inside the tmpfs, so nothing is ever created inside the served root — not even a mount point. That property is what makes a genuinely read-only root survivable: `pivot_root` needs `put_old` to already exist *inside the new root*, and a compose-in-tmpfs design satisfies that without writing a byte to the data.

The executable's directory is **not** in this table: Linux confines the process it is already running in, so the image is mapped and needs no exposure (decision 22).

**The overlay variant was justified by a rule that re-measurement has falsified twice, and what selects it is now stated at the grain the kernel decides it.** The earlier text here said the overlay "exists only because" an unprivileged user namespace cannot remount a bind of a host-owned superblock read-only; the paragraph that replaced it said the mechanism follows the filesystem, with an ext4 bind and a drvfs (`/mnt/e`) bind taking `MS_REMOUNT|MS_BIND|MS_RDONLY` unprivileged while the kernel-managed families refused it. **That replacement is as wrong as the text it replaced.** `lock_mnt_tree()` runs in `copy_mnt_ns()` whenever the new mount namespace is owned by a *different user namespace*, so every host mount is copied in with its per-mount flags — nosuid, nodev, noexec, ro, atime — **locked**, and an `MS_REMOUNT|MS_BIND` request must re-assert every one of them; a single locked flag the request drops is `EPERM` from `can_change_locked_flags()` in `do_reconfigure_mnt()` (evidence table). What decides is the source mount's flag set and not its filesystem: a flagless host tmpfs (`/mnt/wsl`) remounts read-only, a host ext4 that is already read-only returns `EPERM` when the request clears `RDONLY`, and the "subdirectory of a tmpfs" the old row named was an artefact of `/tmp` being a `nosuid,nodev` tmpfs rather than a property of subdirectories.

So the rule the code implements is unchanged in shape and corrected in reason: **every `ReadOnly` exposure is planned as a plain bind under either model, and what makes it read-only is the mount step — `mount_remount(target, RDONLY | BIND, "")` first, and on `EPERM` the same target is re-mounted as an `MS_RDONLY` overlay.** The overlay is the fallback rather than the default, and the condition that selects it is one errno in one place, which is what keeps a `plan`-time decision out of a code path that performs no syscall and cannot know. **An earlier version of this paragraph made the choice P1's to state; the table and decision 8 have since settled it, and P1 implements it as written here.**

**Which of the two mechanisms a run actually takes is a property of the host's mount flags, and the two verification legs are evidence of that rather than a difference the models force.** Measured 2026-09-20 by tracing the real confined binary with `strace`: the unprivileged leg gets `mount(NULL, <target>, NULL, MS_RDONLY|MS_REMOUNT|MS_BIND, "") = -1 EPERM` followed by `mount("overlay", …, MS_RDONLY|MS_NOSUID|MS_NODEV, "lowerdir=…") = 0`, while the privileged leg — root in the initial namespace, where `lock_mnt_tree()` never runs because the new namespace is not owned by a different user namespace — remounts the identical served root with `= 0` and mounts no overlay. So the two legs do exercise the two implementations on this host, and the qualification is that this is the host's flag set rather than something the model guarantees: on a host whose `/tmp` is a flagless filesystem the unprivileged leg's bare request is accepted too, both legs take the remount, and the overlay never runs. A verification may therefore assert that a read-only exposure is enforced, and may report which arm ran, but it must not require a particular arm of a particular leg. **The 2026-09-24 fix moves the unprivileged leg onto the privileged leg's arm, and the trace above is the pre-fix state**: the remount now re-asserts the source mount's own nosuid/nodev/noexec — and, since 2026-09-28, `nosymfollow` — (see the paragraph below), which is what the locked mount was refusing `EPERM` for, so the user-namespace leg's remount returns `0` as well and both legs land on `remount,bind,ro`. The overlay arm therefore runs on neither verification leg any more — it is reached only by a locked mount that is remounted *without* re-asserting its flags, which is the hazard the Risks row on the partial remount records.

**A measured simplification exists, was deliberately not adopted during P1, and its flag half has since been adopted; both states are recorded here so the trade stays visible rather than lost.** Passing the source mount's own nosuid/nodev/noexec bits to the remount as well as `RDONLY` makes it succeed on **every** filesystem measured, not only the flagless ones — which would make read-only enforcement single-mechanism and would let `MountKind::OverlayReadOnly`, `OverlayDirs`, the `$TMPDIR/.overlay` pair and the tmpfs-quota reasoning above all be deleted. It was not adopted during P1 because both mechanisms were measured working, so this was a simplification rather than a bug fix, and making it would have deleted a working implementation late in a phase; it was recorded as available, with its evidence in the table above, for whoever owned the mechanism next. **The flag half was adopted 2026-09-24**, for the reason the Risks row on the partial remount gives: on the root leg the request lands on an *unlocked* mount and silently clears every flag it does not name, so the remount now re-asserts the source mount's own nosuid/nodev/noexec — and, since 2026-09-28, `nosymfollow` — alongside `RDONLY`. **The deletion half was not taken** — `MountKind::OverlayReadOnly`, `OverlayDirs` and the overlay path stay in the tree — so both mechanisms remain and the overlay arm is now reached only by a locked mount that is remounted without re-asserting its flags. **What that costs is the overlay's end-to-end coverage, and the candidate this sentence used to name for closing it is falsified.** With both verification legs on the remount arm, `apply_mount`'s `EPERM` branch is exercised by its own errno unit test alone, and a leg that reached it again needs a mount whose locked per-mount flags are *not* re-asserted — where an earlier form of this sentence offered "a host mount carrying a flag this design does not name, such as `nosymfollow` (some `/run/credentials/*` mounts carry it), or an explicitly locked mount", and **no flag the design leaves unnamed is one whose lock can refuse the request**: `lock_mnt_tree` locks `MNT_LOCK_ATIME` unconditionally and `MNT_LOCK_READONLY`/`NODEV`/`NOSUID`/`NOEXEC` for the flags a mount carries, `can_change_locked_flags` tests exactly those five, and there is **no `MNT_LOCK_NOSYMFOLLOW`** (`fs/namespace.c`, `include/linux/mount.h`). `MNT_NOSYMFOLLOW` is instead inside `MNT_USER_SETTABLE_MASK`, so a remount that does not name it **clears** it with no `EPERM` to report — which is why the re-asserted set gained the flag on 2026-09-28 instead of the arm gaining a second route to it. The branch's coverage is therefore two named unit tests — that errno pin and `overlay_read_only_flags`'s `the_overlay_carries_the_sources_noexec_and_nosymfollow` — and nothing else on this kernel, and `docs/superpowers/plans/2026-09-25-sandbox-followups.md` §7 carries the measurement (a nested-user-namespace leg that mounts a `nosymfollow` source and still reports `read-only-arm: remount`), the opt-in leg itself, and what that leg asserts instead. **The route is one parse arm wide rather than absent, and that is measured rather than argued**: deleting `noexec` — a flag whose lock is real — from `source_mount_flags_in`'s match flips that leg to `read-only-arm: overlay`, so the arm is closed by what the request names and not by the kernel, and `crates/tinio-sandbox-linux/src/enter.rs`'s `enforce_bind_read_only` owns that counter-measurement. **What the overlay arm's own mount carries is a rule too, and its definer is `crates/tinio-sandbox-linux/src/enter.rs`'s `overlay_read_only_flags`**: `RDONLY|NOSUID|NODEV` unconditionally, plus the source's `NOEXEC` and `NOSYMFOLLOW` when it carries them — a fresh mount inherits nothing, so the request *is* its flag set, and naming either narrow flag for a source that lacks it would make the two arms serve one root differently, while following the source costs a legitimate run nothing because nothing in this jail executes from a served root (the image is mapped before `pivot_root`, which is why the executable's directory is not in the table above).

**One overlay pair serves one read-only exposure, so the user-namespace model admits exactly one of them.** An upper directory is bound to a single lower for the lifetime of the mount, and every read-only exposure would otherwise share the one pair the jail creates. The served root is the only read-only exposure any caller produces today, so the composition **refuses a second one explicitly** rather than letting two mounts race for the same upper and surface as an overlayfs error nobody can read. Giving each exposure its own pair is the change to make when a second one actually appears.

### §5 The macOS SBPL profile

**The emitted profile — what `crates/tinio-sandbox-macos/src/profile.rs` writes today, and no longer the older measured text.** One `(allow …)` per exposed path, over a `(deny default)` base, then the runtime baseline — and nothing else: no conditional rule survives, so the render is `header → exposures → baseline` in both access modes. **The rules themselves have one home — `RUNTIME_BASELINE`, four entries, in that file** — so this section does not re-list them; what it owns is the policy behind the set: why the base is default-deny, why each part of the set is what it is, which rules are load-bearing and what breaks without each, and the network posture.

Exposure rules come first, in exposure order — the served root is `E0` and the state directory `E1` when a caller exposes them in that order — and every exposed path travels as a `-D` value rather than in the text (decision 24); `P`, the child's own resolved program path, travels the same way, and it is the only parameter that is not an exposure — there is no `H`: the launcher's `$HOME` is not a value this profile names. **There is no `/dev` grant either.** The four device literals and the two standard streams the earlier text listed were measured unnecessary on both the startup probe and the real binary and were deleted with the `DEVICE_RULES` table that held them; the device-file flag is Linux's own knob now (`tinio_sandbox_linux::Options::with_device_files`/`device_files`) and the shared `Sandbox` carries none, so nothing travels through this text and no rule in it names a device node.

Four of these are load-bearing in ways that cannot be guessed, and each was measured by removing it and watching what broke:

- **`(literal "/")` is what lets the process start at all, and it is `root-traversal`'s operation.** A `(deny default)` process whose profile omits it dies of SIGABRT, and the only violation logged is `file-read-data /`. Granting every prefix *under* the root does not substitute — the refused read is of the root directory itself. This is the first thing P3 must get right, because its failure mode is a bare abort with no message. **Measured on macOS 15.8: with the rule removed the process exits `rc=134` with `Sandbox: deny(1) file-read-data /` on `log stream`.** **Re-measured on the real product path, 2026-09-25: what dies is the pre-flight's own `/bin/echo`, not the confined child** — the launcher never reaches the real child at all, reporting `sandbox-exec refused the profile … exit=None diagnostic=` and exiting 1, while `log stream --predicate 'sender == "Sandbox"'` carries `Sandbox: echo(<pid>) deny(1) file-read-data /` beside the sysctl names that probe also hits; the earlier framing ("`sandbox-exec` died with no diagnostic") is the same event described wrongly, because the abort is diagnostic-free on the process side and the kernel line **is** the diagnostic. The mechanism is dyld: **`ktrace` shows it resolving its shared cache through relative paths** (`../../System/Volumes/Preboot/Cryptexes/OS/…`), which walks to `/`, and the kernel refuses the read of the root directory itself — measured with the `metadata` confound removed, which is why `(allow file-read-metadata)` in this same table does not cover it. **The rule also grants enumerating `/`, which this bullet never stated**: measured on macOS 15.8, 2026-09-25, under the real baseline a confined `/bin/ls /` lists **16 entries**; with this rule removed it dies `rc=134` and lists **0**; with `(allow file-read-metadata)` removed instead and this rule kept it still lists **16** — so listing the root is this rule's own capability, carried by `file-read*` on the directory, not by the metadata rule. **And a denied `file-read-data /` is what tells this rule from `sysctl-read` when both abort the process the same way**: with `root-traversal` removed the pre-flight's `echo` dies, with `sysctl-read` removed the real child dies before `main`, and the kernel line names which refused operation ran.
- **`process-exec` is not optional.** Without it `sandbox-exec` cannot exec the target at all and exits 71 before any other rule is consulted. **The rule is emitted filtered rather than blanket** — `(allow process-exec (literal <the child's own path>))`, the path coming from the same value the argv's program element is built from, so the rule and the exec cannot drift. The reason is that the measurement above establishes only that *an* exec must be permitted; an unfiltered rule, over a profile that also grants read on `/bin`, `/usr` and `/private/etc`, lets the confined process execute any readable binary it likes. This narrowing is **not** among the measurements — it is a change of the emitted text away from the text measured here — so its failure mode is recorded instead of assumed: a refused exec is `rc=71` with `execvp()`'s diagnostic, **and a literal that is not the canonical resolved program path is refused the same way — measured: `rc=71` with `sandbox-exec: execvp() of '<path>' failed: Operation not permitted`, which is why the launcher canonicalises it** — and a spelling `sandbox-exec` will not compile is `rc=65`, which the pre-flight catches when it runs (a release build skips it and meets the refusal at the real spawn). If a second exec turns out to be required, the blanket rule returns **with the over-grant written down beside it**, never quietly.
- **`sysctl-read` is load-bearing before `main`, and it is not there for the runtime's sizing.** The rule's `hw.pagesize_compat` filter is what std's pre-`main` stack-guard setup needs: `stack_overflow::init()` reads the page size (`sysconf(_SC_PAGESIZE)`), a refused read becomes a `-1` no profile can fix, the main thread's guard-page `mmap` then fails and the process aborts before `main` runs. **Measured on macOS 15.8, 2026-09-25, on the real product path, three builds identical but for the `sysctl` rule** (`cargo build -p tinio`; `NO_COLOR=1 ./target/debug/tinio server /tmp/t1{a,b,c} --port 0 --sandbox`, with `root-traversal` present in all three): build (a), **no `sysctl` rule at all**, and build (b), `(allow sysctl-read (sysctl-name "hw.ncpu"))`, fail identically and verbatim — `thread 'main' (<tid>) panicked at /rustc/<hash>/library/std/src/sys/pal/unix/stack_overflow.rs:539:13:`, `failed to allocate a guard page: Invalid argument (os error 22)`, `fatal runtime error: initialization or cleanup bug, aborting`, `status=signal: 6 (SIGABRT)` — and each leaves `deny(1) sysctl-read hw.pagesize_compat` as the kernel line naming the refused read, while build (c), the page-size filter alone, reaches `event: listening`, answers `403`, writes one access-log line, publishes `state` with `tinio status` answering `running`, and forwards SIGTERM to `exit 0`. **A one-filter rule is the narrowest spelling that runs, and the earlier attribution was measured on a name that does not work**: `hw.pagesize`, `kern.version`, `kern.osvariant_status`, `security.mac.lockdown_mode_state`, `kern.bootargs`, and every combination of those without `pagesize_compat` exit `rc=134`, while `(sysctl-name "hw.pagesize_compat")` exits 0. The rule's **second** filter, `hw.ncpu`, is **not load-bearing and is not claimed to be** — the run is green without it, and the kernel logs `deny(1) sysctl-read hw.ncpu` three times — and it is granted only as the count the confined child genuinely wants: the tokio builder reads `available_parallelism()`, which the filter answers rather than refuses, so its worker pool sizes from the machine instead of from one thread (the child reports `available_parallelism=ok:6` under the two-filter rule and `available_parallelism=error(PermissionDenied)` — `ErrorKind::PermissionDenied` — under the page-size filter alone, while serving normally either way). The attribution this bullet used to carry — `sysconf(_SC_NPROCESSORS_ONLN)` failing, so tokio cannot size its pool — was **wrong**, and pinning `worker_threads(n)`, or deleting the probe's own `available_parallelism()` call, cannot remove the rule, because the abort precedes `main`. **The two rules are separately required, and one build settles it rather than the shared symptom**: with `root-traversal` and `metadata` present, the root read granted through a separate `(allow file-read-data (literal "/"))` and the `sysctl` entry removed, the confined child still dies the guard-page abort while that run's kernel log carries `deny(1) sysctl-read hw.pagesize_compat` and **zero** `deny(1) file-read-data /` lines anywhere in it (counted, not eyeballed: `grep -cE 'file-read-data /$'` → `0`); with `root-traversal` removed instead the launcher never reaches the real child, because the pre-flight's own `/bin/echo` dies (`Sandbox: echo(<pid>) deny(1) file-read-data /`). **The two filters ride on one rule and one `id`, and that is measured rather than assumed**: `(allow sysctl-read (sysctl-name "hw.pagesize_compat"))` leaves the child's `available_parallelism()` at `error(PermissionDenied)`, while the multi-filter form, two separate `allow sysctl-read` lines, and the unfiltered `(allow sysctl-read)` control all answer `ok:6` — so one entry carrying every filter is valid SBPL, and the two-entry fallback was not needed. **The rule carries eight filters as of 2026-09-26**: the page-size name and `hw.ncpu` above, plus the six names the loader's own startup probes are refused (`hw.ephemeral_storage`, `kern.bootargs`, `kern.osvariant_status`, `kern.secure_kernel`, `kern.version`, `security.mac.lockdown_mode_state`), measured as the union over 19 product-path runs under `sandbox-exec` (16 e2e runs plus 3 plain runs) with six more e2e runs under `sandbox-init` seeing only `kern.secure_kernel`. The enumerated shape was chosen over the unfiltered `(allow sysctl-read)` because the set is bounded on every path measured and the widening's whole cost is those six facts — kernel version and boot args, OS-variant status, lockdown mode, secure-kernel and ephemeral-storage flags — while `kern.boottime`, `kern.ostype` and `net.inet.ip.forwarding` are measured still refused. A compiled `sysctlbyname` probe settles it: under the old rule all six answer `ERR Operation not permitted`, under the new one they answer (`hw.ephemeral_storage` → `Invalid argument`, matching the unconfined control) and the three outsiders stay refused. The identical refusal set for the pre-flight's `/bin/echo` is what identifies them as the loader's startup probes rather than the product's requests, and a refusal outside the set reddens the gate by design — a re-audit, not a relaxation. `scripts/prune-profile.sh` keys on `id: "…"` and `tests/harness/mod.rs`'s `remove_rule` on the `; tinio:<id> ` marker, both of which one entry keeps working, so a second entry would add an `id` and an `evidence` string for nothing. **Re-measured on the product path with both filters shipped** (VM, 2026-09-25, root `/tmp/tinio-ncpu`): `rules=7 params=1` as that field then counted it — 2 header lines + 1 exposure + `RUNTIME_BASELINE`'s 4 entries; under today's derivation, `profile.rs`'s `rule_count`, which filters the rendered text for `(allow …)` lines and excludes the header, the same one-exposure run reports `rules=5 params=1` — then `event: listening`, `curl` `403`, `<root>/.tinio/access.log` written, `<root>/.tinio/state` naming the socket and the launcher's pid, `tinio status` → `running`, SIGTERM → `exit status: 0`, `pgrep -fl 'tinio|sandbox-exec'` empty after the sweep — and a `log stream` capture beside that run carries **zero** `deny(1) sysctl-read hw.ncpu` and **zero** `deny(1) sysctl-read hw.pagesize_compat` lines. **The leg that pins the rule was vacuous and the negative control is what found it**: it asserted `contains` over the whole rendered line, and a rendered line is `<rule> ; tinio:<id> — <evidence>` whose evidence quotes both filters by design, so reverting the rule to the single-filter form and leaving the evidence alone still passed; the assertion now drops everything after the `; tinio:` marker and the same control fails for the right reason, while both filters present passes.
- **`file-read-metadata` is one of two things symlinked paths need, and neither substitutes for the other.** `/tmp`, `/var` and `/etc` are symlinks at the root, and walking a path spelled through one of them is itself a metadata operation: `(subpath "/private/tmp")` — and even the literal full path — is refused without the blanket allowance. But metadata alone does not make a rule *match*: Seatbelt compares the rule's literal spelling against the kernel-resolved path, so a grant written on `/tmp/grill` grants nothing for a file at `/private/tmp/grill/real/inner.txt`, and both command spellings are refused. Each is needed for its own reason — metadata to walk the link, and the canonical spelling to match what it resolves to — which is why the profile carries both the blanket allowance and `with_canonical_paths`. **Measured on macOS 15.8, with the rule removed the *exposed* read itself fails `permission denied`**, and on the real product path (2026-09-26, frozen revision) the child reaches `main` and then exits `2` with `tinio: the storage root … is not usable: Operation not permitted (os error 1) — pass an existing DIR`, the kernel naming `deny(1) file-read-metadata /tmp` — the cost lands on the operator's own exposure rather than somewhere peripheral. The cost of the allowance is stated rather than hidden: existence and timestamps can be probed outside the grants, contents cannot.

**The pruning run this paragraph once said was outstanding has been performed, and the set it left is four entries.** `RUNTIME_BASELINE` holds `process-exec`, `sysctl`, `metadata` and `root-traversal` (`crates/tinio-sandbox-macos/src/profile.rs`, the set's one home), and each is there because a run without it broke: `process-exec` refuses the exec (`rc=71`), `sysctl` is the pre-`main` guard-page abort, `root-traversal` kills the pre-flight's own `/bin/echo` before the real child is spawned, and `metadata` stops the operator's own read. Two are narrowed past the form first measured — `process-exec` to the child's own `(literal (param "P"))`, `sysctl` to the **eight** `sysctl-name` filters the `sysctl` bullet above enumerates — and `metadata` is the one allowance with no filter at all. The rules the earlier text carried as unpruned are gone rather than kept: `process-fork`, `signal-self` and the `/System`+`/usr`+`/Library`, `/bin`+`/sbin` and `/private/etc` subpaths were measured unnecessary and deleted, and `network-bind` and the `H` grant went with the control-socket handoff and the home measurement. The audit that removed the rest, and the product-path A/B behind each surviving entry, are the audit paragraph below — this section is where that record lives, and no second document holds it.

**The allowance audit was run twice per id, because the probing script is not the product.** `scripts/prune-profile.sh` decides necessity by running the startup probe, and that probe never binds a control socket and never calls `prepare_home_derived`; re-measuring every id against the real binary (`cargo build -p tinio`, then `tinio server <short root> --port 0 --sandbox`) found the two disagreeing on two rules, and the product path is the authority. The measured verdicts, probe column beside product-path column: `process-exec` required / required (the probe's `execvp() of '/bin/echo' failed: Operation not permitted`, `rc=71`; on the product path the pre-flight dies `sandbox-exec refused the profile … exit=Some(71) diagnostic=sandbox-exec: execvp() of '/bin/echo' failed: Operation not permitted`, kernel `deny(1) process-exec* /bin/echo`); `sysctl` required / required (the A/B above: the child aborts before `main` with `status=signal: 6 (SIGABRT)` and `deny(1) sysctl-read hw.pagesize_compat`); `metadata` required / required (the probe's `permission denied`; on the product path the child reaches `main`, then exits 2 with `tinio: the storage root … is not usable: Operation not permitted (os error 1) — pass an existing DIR` and `deny(1) file-read-metadata /tmp`); `root-traversal` required / required (the pre-flight's own `/bin/echo` dies of `deny(1) file-read-data /` — a diagnostic-free SIGABRT, `exit=None` — and the launch never reaches the real child, `sandbox-exec refused the profile … diagnostic=`, exit 1); `home` not needed / **not needed — deleted** (the four-run measurement below); `network-bind` not needed / **required** — `could not bind …/.tinio/tinio-<hash>.sock: Operation not permitted` — resolved by the handoff rather than by a rule (below); `process-fork`, `signal-self`, `system`, `bin`, `private-etc`, `dev-null`, `dev-zero`, `dev-random`, `dev-urandom` and `dev-stdio` not needed / not needed — **deleted**, with decision 12 already recording the device literals as defensive rather than load-bearing. The probe's two false negatives are the audit's whole point: a probe that does not exercise a capability reports that nothing needs it, so the script's table is a floor and never the authority — do not read it without the product-path column beside it. **Re-run end to end on 2026-09-26 at a frozen revision, and it agrees, one removal per run** — the evidence table's product-path row carries that run's five arms, their exit statuses and their kernel lines, and the provenance that makes the frozen text re-renderable.

**The `home` grant is deleted, and four runs plus a control are the measurement.** `(allow file-read* (subpath (param "H")))` was kept for read-only runs as a conservative guess, and the profile now carries no `HOME_GRANT`, no `H` parameter, no `home_directory()` and no `validate_home()`, so both modes render `header → exposures → baseline` and a read-only run's parameters are its exposures alone. The question was asked four ways on the real product path with a short root under `/tmp` and an `H`-less profile, everything else the launch renders untouched: read-only with `TINIO_STATE_DIR=/tmp/<dir>` and cwd `/tmp` → `event: listening`, `curl` `403`, access log written in the state directory (a read-only run relocates state), `state` published, `tinio status` → `running`, SIGTERM → `exit 0`; the same run with cwd **inside** `$HOME` (`~/tinio-ro-run/sub`) → identical; read-only with no `TINIO_STATE_DIR`, i.e. the home-derived default → reaches no event at all, with `configuration error: failed to resolve the state directory at '/Users/flier/.tinio': Operation not permitted (os error 1)`, exit `1`, and the kernel's only non-sysctl denial `deny(1) file-write-mode /Users/flier/.tinio`; and that same default-state-dir run **with** `H` = `/Users/flier` present → **byte-identical failure and the same `deny(1) file-write-mode /Users/flier/.tinio`**, so the grant is inert there. **The one failure that survives is a write, and no read rule can fix it**: the read-only run's default state directory is the home-derived `<home>/.tinio`, and Seatbelt gates the metadata write that resolving it performs. The remedy is an explicit writable `TINIO_STATE_DIR` — the state directory is always exposed read-write by `sandbox_request`, so any path outside the read-only root works — and `crates/tinio-cli` now **refuses** that request in the launcher rather than letting the child die on its own `EPERM` (`sandbox/product.rs`'s `refuse_underived_state_dir` names the missing channel; the child's own message named the path and the operation but not that a grant was the missing thing). The `$HOME=/` defect that stood beside this one is refused the way an exposure is: `home_directory()` routes the value through the same validation and answers `Error::BadPath` rather than rendering `(subpath "/")` — a silent whole-filesystem read grant no event field reported. **The caller the grant was first attributed to was mis-attributed, and the correction is part of this measurement**: `dirs-sys` 0.5's unix `home_dir` answers from `$HOME` with no I/O when it is set, and suppressing that call alone left the run failing with the same `tinio: I/O error: Operation not permitted (os error 1)`; the real caller was `crates/tinio-cli/src/resolve/locate.rs`'s `locate_with` calling `env::current_dir()` unconditionally — on macOS `getcwd()` is `fcntl(F_GETPATH)`, which Seatbelt refuses `EPERM` for a working directory under a directory the profile does not grant, so a run from `~/…` died before it emitted any event — and `locate_with` now resolves the walk-up's starting point only when no `DIR` was given.

**The spelling this measured paragraph uses is the pre-refactor one, and the contract it states is unchanged**: `LaunchPlan` no longer carries a whole payload — it carries `config: Option<String>`, read through `config()` and `has_config()` — and the frame's one writer is `LaunchPayload::encode_frame(config, token, confinement)`; `payload()`, `with_payload` and the owned `encode` are gone. What the paragraph measures, and the fix it narrates, stand as written.

**The launcher publishes `state` from the relay, and the gap that hid it is measured.** `confine` once built the relay with `Child::with_relay` alone and never `Child::with_ready(rx)`, so `Child::wait_for_ready(PUBLISH_BOUND)` answered `None` at once and `publish_state` returned without writing: after `listening`, `<root>/.tinio/` held `.tinio.toml`, `access.log`, `meta.redb` and `tinio-<hash>.sock` and **no `state`**, and `tinio status <root>` answered `stopped` with "no server has run for this root" (measured on macOS 15.8, 2026-09-25). Wiring `with_ready` was not the whole fix, and the second half is why the file and the token must travel together: `confine` serialized `plan.payload()`, which `for_launch` builds with `token: None`, so the child never received the launcher's token and minted its own — `state` landed and `tinio status` still answered `stopped`, "it is stale", with the socket refusing `401` for the token the file carried. `hand_over` now builds the frame from the plan's two halves (`config` + `token`), the pairing the Windows backend already made. Verified: `state` names the socket the child bound and the launcher's pid, `tinio status <root>` answers `running`, the published token answers `200` on the socket (`401` without it), and the launcher removes the file again on exit. **The ordering a consumer must assume is `contracts/cli.md`'s readiness bullet, not simultaneity**: the launcher learns readiness through the relay and *then* writes `state`, so the `listening` frame can precede the file by a few syscalls — measured 2026-09-25, `published=false, serving=true` once in two runs — and the e2e harness polls for the artifact with a bounded settle (`crates/tinio-e2e/tests/steps/cli.rs`'s `PUBLISH_SETTLE`).

The `ReadOnly` / `ReadWrite` distinction is exactly the presence or absence of `file-write*` on the served root, which is why decision 8 needs no macOS-specific concept — and it was measured: with only a read grant, create, append, truncate, unlink and chmod all fail inside the served root while reads succeed, and no write grant anywhere else refuses every write outside the exposure set.

**The allowance set is now the audited one, and what is left is where this platform still sits furthest from the Goal.** `(allow file-read-metadata)` is blanket by construction, and it is the one grant that remains wider than the exposure set: existence and timestamps can be probed outside the exposures, contents cannot. The Goal says the confined process reaches "exactly the directories the operator exposed, and nothing else", and on this platform the read trees that stood between the two are gone rather than kept. **Every read tree the earlier text carried beyond the metadata blanket is gone**: `(subpath "/private")` reached `/private/var`, which nothing needs; `(subpath "/etc")` matched nothing at all, because `/etc` is a symlink into `/private` and Seatbelt compares the rule's spelling against the kernel-resolved path; and the `/System`+`/usr`+`/Library`, `/bin`+`/sbin` and `/private/etc` subpaths were measured unnecessary on the real binary and deleted (`RUNTIME_BASELINE` above, and the audit paragraph above for the two-column verdicts). **A fourth went by a measurement of its own**: `(subpath "/private/var/folders")` — the narrowing that replaced part of the `/private` blanket — was the only rule that widened the read surface, and with it gone a read through a symlink pointing out of the exposed tree is refused (`ERR(PermissionDenied)`) while `available_parallelism=6`, `threads=4`, the report write and the marker read are all unaffected. It could not be narrowed instead of deleted, because Seatbelt compares the rule's spelling against the kernel-resolved path: the same rule spelled `/private/var/folders/…` left the escape read permitted, and `/var/folders/…` refused it. **The pruning run this paragraph once said was required has been performed** — P3 Task 5's experiment, re-measured against the real binary and recorded in the audit paragraph above — and the four entries named above are what it left. What cannot be pruned away — `(literal "/")`, `process-exec`, `sysctl-read`, `file-read-metadata` — is the measured price of the process starting at all, and is recorded as such rather than as a grant the design chose.

**Network: no rule at all, and neither channel needs one.** The parent binds both channels (decision 16), and `bind()` and `listen()` turn out to be the only operations the sandbox gates — `accept()`, `recv()` and `send()` on an inherited listener are not checked at all. A profile granting **no** network operation was measured taking a real connection out of an inherited listener's backlog, with no `accept` violation in the kernel log. The **control channel** was the exception, and the handoff is what resolved it rather than a rule: a unix socket `bind()` **is** gated — the confined child once bound its own local management control socket (`<state dir>/tinio-<16 hex>.sock`) and without a rule died with `management error: transport: could not bind …: Operation not permitted (os error 1)` — and the narrower spelling `(allow network-bind (local (subpath (param "S"))))` **did not compile** (`sandbox-exec` refused the profile), so the grant could not be made a filter. The launcher binds that socket outside the sandbox and hands the descriptor over, exactly as it does for the data plane's listener, so **the emitted profile carries zero network rules** — `crates/tinio-sandbox-macos/tests/network.rs` asserts the absence. **Measured on macOS 15.8, 2026-09-25: the launcher binds both channels — the data plane's TCP listener and this control socket — and the rendered profile then contained zero lines matching `network`, with the property unchanged as `RUNTIME_BASELINE` was pruned to its four entries.** The handoff is also what the `network-bind` rule's removal left behind rather than a relaxation of the profile's posture, which is why the audit above records that id as `required` on the product path and `NOT NEEDED` on the probe: the probe never binds a control socket, so it never met the refusal the product path did. So the macOS row of §7 is not "never grants `network-outbound`"; it is **no network operation at all**, both binds being the launcher's. That is still a stronger statement than Linux's seccomp filter makes (which cannot see a `sockaddr` and so cannot restrict inbound) and stronger than Windows's absent capability makes (measured as of 2026-09-22 to block outbound, §7's Windows row; and on that platform the capability set bears on inbound too, where §7's note records what is measured and what is not). macOS is the one platform where the outbound refusal is absolute, and it comes from the handoff the design already specified.

Three allowances the design had guessed at are **not** needed and are dropped. `mach-lookup`: with it removed every check still passes except `getpwuid`, whose failure names `com.apple.system.opendirectoryd.libinfo` — and the serve path does not resolve users. The allowance for `com.apple.system.logger` in particular was invented and is not required. `system-socket`: it is a genuine privilege rather than a no-op — removing it turns `socket(PF_SYSTEM, SOCK_DGRAM, SYSPROTO_CONTROL)` from accepted to refused — and nothing measured has a caller for one, so carrying it would be granting a capability for no reason. `ipc-posix-shm` was tested beside it and is likewise needed by nothing. A profile is a list of privileges, and one carried without a caller is exactly what this section exists to remove; the way to keep it honest is the tool that produced the list, `log stream --predicate 'sender == "Sandbox"'`, which names the refused operation rather than leaving it to be discovered at runtime.

Two operational limits belong here because they are the profile's, not the crate's. The compiled profile is capped near 64 KiB: 10000 small rules compile and 12000 fail with `data object length … exceeds maximum (65535)`, while a *single* operation carrying 9000 path literals fails earlier with `profile compilation failed` — so a large exposure set must be emitted as separate `allow` operations, and the generator **refuses above 4096 exposures** rather than letting `sandbox-exec` report it: 2.4× below the measured cliff and far past any operator's exposure set. The refusal names the exposure that crossed the line and reports it as `Error::BadPath` — the variant whose own definition is "a path handed to `Sandbox::expose` cannot be expressed inside the confinement", which is precisely what the 4097th one is. Refusing rather than truncating matters: a profile that silently dropped exposures would be a confinement that silently granted less than the operator asked for, and the server would serve a subset of its data with no explanation. **This refusal is macOS's alone, and the asymmetry is the platform's rather than an omission in the other two plans**: the cap it guards is the *compiled profile's*, which only Seatbelt has — Linux's mount table and Windows' ACL list are bounded by what the operator asked for and by nothing else in the mechanism, so a library consumer can hand either of them an exposure set that makes a diagnostic string or an argv arbitrarily long. A shared bound would be a number the other two platforms have no reason to defend. And the way to keep this set minimal is the tool that produced it: `log stream --predicate 'sender == "Sandbox"'` prints every refused operation with its path and needs no elevation. **The other limit is argv, and it is measured at its failure string but not bounded.** The profile text is one argv element and it is not small — every rule is written with a `; tinio:<id> — <evidence>` provenance comment — so a set at the count guard can approach `ARG_MAX`, and `MAX_EXPOSURES` bounds the count rather than the bytes. The failure is legible rather than silent: measured on macOS 15.8, oversize argv makes `Command::spawn` fail with `display="Argument list too long (os error 7)"`, `kind=ArgumentListTooLong` and `raw=Some(7)`, which `launch.rs`'s `spawn_error` renders as ``sandbox could not spawn `/usr/bin/sandbox-exec`: Argument list too long (os error 7)``. **A byte budget for the rendered text is not added, and that is the operator's ruling of 2026-09-28 rather than a question left open** — settled in the negative because the failure is legible at the measured string the sentence above carries, so a budget would pre-empt a failure an operator can already read and act on, and because a number this section has not measured is not one it writes. **This paragraph is the ruling's home**: the plan records that report it (`plans/2026-09-25-sandbox-followups.md` §12's traps bullet and that file's Cleanup record, and `plans/2026-09-25-sandbox-p3-macos-followups.md`) point here rather than at one another.

The text is passed to `sandbox-exec -p` (decision 24), which applies it to the child before exec; exposed paths travel as `-D` parameters rather than interpolated into the text, which was also measured working. The profile is `(deny default)`, so a path or a network operation not named in it is refused — the same default-deny posture AppContainer gives on Windows, reached through a different kernel facility.

**The crate is macOS-only and its platform gate is taken once, at the crate root — the operator's ruling rather than a preference.** Every file in `crates/tinio-sandbox-macos` is macOS-only, so `crates/tinio-sandbox-macos/src/lib.rs` carries `#![cfg(target_os = "macos")]` and the per-item `#[cfg(target_os = "macos")]` the crate used to carry is gone; accepted knowingly, because it also moves every verification of the crate to a Mac (`bash crates/tinio-sandbox-macos/scripts/macos-sandbox-verify.sh`). **The sharp edge the ruling leaves is that a build which is not macOS sees an empty library**, so anything that must still compile on those targets has to be gated itself — the crate-level example in that `lib.rs`'s module docs among them, its body behind `#[cfg(target_os = "macos")]` and an empty `main` where the crate is empty — and a reader who adds an ungated item or an ungated `//!` doctest meets a compile error on a non-macOS build rather than a silent omission (measured: `cargo test -p tinio-sandbox-macos` on Windows, 2026-09-25, fails `E0432`, and that command is a leg of `cargo test --workspace`). The per-crate `deny`/`forbid` allocation — this crate's `unsafe_code = "deny"` among it — is decision 14's and is not enumerated here.

### §6 The Windows ACL whitelist

**The mechanism is a created package profile, and the SID it returns is the deterministic one**: `CreateAppContainerProfile("<name>", …)` creates the AppContainer profile and hands back the package SID the confined process will run under, without elevation, while `DeriveAppContainerSidFromAppContainerName("<name>")` computes that same SID from the same name — so the derivation is the way to *compute* the SID, and the creation is what makes it usable (decision 21). The launcher grants, per exposed path:

- `ReadWrite` → `(OI)(CI)M`
- `ReadOnly` → `(OI)(CI)RX`
- ancestors → nothing (verified: AppContainer tokens carry bypass-traverse, so only the exposed directory's own ACE matters)

**The list above is the inherited shape, and Ruling 78 (2026-09-22) narrowed where it applies: it is what the *caller's* exposed directories take, and the program's own directory no longer does** (decision 22 — one non-inherited `RX` ACE there, plus the sibling DLLs in the file shape). The inheritance measurement and its cost below are about the caller's exposures.

**The `(OI)(CI)` form is sufficient, and P2 settled it by measurement on 2026-09-19.** The open question was whether inheritance reaches children that already existed when the ACE was set; it does, on both filesystems in use here. A directory-only `icacls /grant:r "*<sid>:(OI)(CI)M" /q` — no `/t` — put an inherited `(I)(M)` entry on a pre-existing file at depth 1 and at depth 2 of the served tree, and on the intermediate directory as `(I)(OI)(CI)(M)`, identically on NTFS (`C:`) and ReFS (`E:`); `.NET Set-Acl` reproduced it through a different API with `IsInherited: True`, so the propagation is the filesystem's rather than the tool's. The grant list is therefore **one ACE per exposed directory**, and a revoke would be **one `/remove:g` per directory** — a capability the launcher no longer exercises at all (decision 15, standing grants): it makes one descriptor write per exposure it has to write and none for one the DACL read finds already granted, and neither it nor the write walks the tree — the per-file `/t` walk and its per-file revoke story are not needed and are not used. **The filesystem does the walking, though, and an earlier version of this paragraph read that as the absence of a cost rather than as one.** Inheritance is exactly what the measurement above demonstrates: the `(OI)(CI)` ACE reaches every pre-existing descendant of each exposed directory, so the grant pass (before `CreateProcessW`) touches as many objects as the served tree contains, proportional to the whole corpus — and the rollback pass that used to follow the child's exit doubled it until the standing ruling dropped that pass (decision 15 for the ratio, and for where the measurement of a root that has already been served lives). **P2 measured it on 2026-09-22, and the number is large enough to have changed the guidance** (Risks table below, and `README.md`'s operator note): on a synthetic corpus of 200 directories × 1000 files — **200,200 objects** — the grant took **32.3 s, 35.5 s and 37.8 s in three runs** on NTFS (`D:\`), with the `-AclCost` script's own second pass — the rollback the launcher used to make and no longer does (decision 15) — at **27.5 s, 47.1 s and 38.2 s**, against **8.81 s** for the grant and **8.56 s** for that second pass on ReFS (`E:\`): on the order of 0.3–0.4 ms per object for the two passes together on NTFS and 0.087 ms on ReFS, so **the filesystem is as much a factor as the object count**, and the spread between two runs of the same tree is wide enough that these are magnitudes rather than constants. The readiness budget the feature has to fit inside is 30 s (the e2e harness's start timeout) and the CLI contract's graceful-shutdown drain is ≤10 s — **so on NTFS a served tree of this size spends the whole readiness budget on the grant alone, on the run that first serves it** (the standing skip is what keeps every later run off that bill — decision 15), while on ReFS the same tree spends under a third of it. The measurement is repeatable rather than quoted: `pwsh crates/tinio-sandbox-windows/scripts/verify-windows.ps1 -AclCost [<dirs> <files>]` builds the corpus, times both passes, and **asserts `icacls`'s own exit status and that the ACE reached a pre-existing descendant before and after the removal** — a refused grant still returns a duration, so a run without those checks measures nothing. Two measured consequences bound that answer: an inheritance-flagged grant applied to a *file* reports success and writes nothing, so a per-file grant would have to drop the `(OI)(CI)`; and an ACE written *explicitly* on a file does not go away when the directory's copy is removed, which is why a revoke — `acl::revoke`, the API an operator or the ledger would use (decision 15) — removes from exactly the paths it granted on and never assumes a directory-level removal reached further. **Ruling 78 (2026-09-22) then stopped the exposure set from paying that cost where the launcher itself owns the directory**: decision 22's entry is a **non-inherited** `RX` ACE on the program's directory plus non-inherited `RX` ACEs on the `*.dll` files directly beside the program, **one handle-opened grant per file** (the `*.dll` pattern is the enumeration's spelling and the tests' oracle, not the route — 2026-09-27), so the propagation the paragraph above prices is the *caller's* exposures' and no longer the tool's own directory. The ACL layer gained the file shape for the same ruling, because an inheritance-flagged grant on a file is the no-op the sentence before this one records — `acl::ace_spec` takes a target for exactly that reason — and the target has **two dimensions rather than one**, which is the correction a full gate run forced: `Directory` is the caller's exposed directory (the list at the top of this section, and the variant a call site with a directory in hand reaches for), `ProgramDirectory` is decision 22's non-inherited exception, and `File` is everything that is a file. `tests/acl.rs` pins the file-shaped grant that lands and the inherited form that writes nothing; the shape the launcher picks for each directory is pinned DACL-free in `backend`'s own tests.

and launches itself with `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` in a `STARTUPINFOEX`, `EXTENDED_STARTUPINFO_PRESENT`, with the capability list from configuration (empty by default; §7 states the network policy and why the default is what it is).

Verified end to end on both filesystems an operator is likely to use: a Rust binary loads, a granted tree is readable, a non-granted tree is denied despite carrying `Users` and `Authenticated Users` ACEs, and an `RX`-only grant rejects writes. ReFS and NTFS produced identical results for every case.

**What the grant follows is part of the exposure decision rather than an implementation detail.** A reparse point — a junction or a symlink — inside the operator's tree moves a name-based grant to somewhere the check never saw, and the confined process then holds `M` on a tree nobody exposed. **What a grant does through one is not a single thing, and the measurement is why this paragraph no longer says "its target"** (this host, 2026-09-27): a link **above** the last component resolves and the ACE lands on the target, outside the exposed tree (`…\hop\tinio` wrote `…\real\tinio`'s descriptor, and the pre-existing file beneath it inherited the ACE); a **junction as the last component** keeps the ACE on the link's own object; a **file symlink as the last component** sends it to the target — the sibling-DLL escape the name-based enumeration closes. Two of the three are outside the exposure and none is the ACE the caller named, which is the rule `crates/tinio-sandbox-windows/src/acl.rs`'s `REPARSE_POINT` sentence states and what its `reparse_refusal` serves three sites with. **And the grant no longer goes through a name at all** (same measurement): `crates/tinio-sandbox-windows/src/acl.rs`'s `Object` opens the spelled path with `FILE_FLAG_OPEN_REPARSE_POINT`, refuses a reparse point or an object of the wrong kind on that handle, and reads and writes the DACL **on the same handle** — `GetSecurityInfo` for the skip, `SetEntriesInAclW` + `SetSecurityInfo` for the write — so the object the check approved is the object granted; `icacls` survives as `revoke`'s path and as the tests' independent oracle, and no grant shells out. The reparse-point rule is the same class as the symlink-following bug the Background cites, and it is the Windows half of what macOS meets with `with_canonical_paths` (decision 24). **An exposure is checked for reparse points before it is resolved, and canonicalised only once it passes**, so the outcome is a startup error naming the path instead of a silently wider grant. **The refusal is wider than "the path itself is a link", and this is what the implementation does** (P2's `backend::canonical_exposures`): every component of the *spelled* path — the directory and each of its ancestors, up to the volume root — is examined with `symlink_metadata`, which reports on the link rather than on its target, and the first one that is a reparse point refuses the whole exposure with `Error::BadPath` naming **that component**. So an operator whose served root sits under a junction anywhere above it is refused at startup, with the offending component printed and logged (`step = "resolve an exposed path"`), and the remedy is to expose the directory the link lands on — the resolved spelling — rather than the link: a grant through one is never the ACE the caller named, and an inherited one on a target can reach a tree nobody exposed (the three measured cases above). What the resolution then produces is the verbatim `\\?\`-prefixed form — accepted by the tool (measured 2026-09-19) and the spelling the grant's own open takes now — so the granted spelling *is* the resolved one. **That remedy is the ruled behaviour rather than an operator's workaround: Windows keeps the resolved spelling alone, so a served root that is a directory junction is served by the directory the junction names and never by the junction's own spelling** — the operator's, whose record and whose coupling of the leg it is pinned by (`crates/tinio-server/tests/sandbox_e2e_windows.rs`'s `a_child_that_never_reports_is_the_parents_own_error_frame`, to be re-induced if the rule ever widens) are `docs/superpowers/plans/2026-09-25-sandbox-followups.md` §22's, and whose operator-visible shape `docs/sandbox.md`'s Windows section states. Granting the operator's spelling beside the canonical one — the macOS reading, where `with_canonical_paths` keeps both — would re-open exactly what the spelled-path refusal exists to prevent: an ACE on the link's own object (the last-component junction above) or on a target outside the exposure (the link-above case). The consequence worth stating for an operator: a workstation with a junction on a path above `%TEMP%` or above the served root has those paths refused, which is why this was measured here (no ancestor of `%TEMP%`, of the worktree or of the cargo target directory is a reparse point) rather than assumed. Linux does not need the rule: the jail mirrors host paths, so a link inside the tree resolves within the jail to a path that was never mounted, and it fails closed.
**A caller's exposed path must be a directory, and a file among the caller's exposures is refused at startup rather than granted nothing.** The caller's paths are granted through the per-path loop, and the only shape that loop applies is the directory form: `(OI)(CI)` for a caller's exposure (the list above) and the plain form for decision 22's program-directory entry — while an inheritance-flagged ACE on a **file** is a silent no-op, so `icacls` would exit 0 having written nothing. A caller that exposed a file would therefore start a server whose confinement cannot read the path the operator named, with no error anywhere. The refusal is `Error::BadPath` naming the file, the same variant and the same startup diagnosis the reparse-point refusal above uses, and it is made by the code that builds the caller's own canonical set (`backend`'s `canonical_caller`, which is the one place that knows an entry is the caller's) **before a single ACE is written**. **The launcher's own file entries are exempt, and that is the whole reason the check is on the caller's set**: the sibling `*.dll` entries decision 22 adds are files too, and they are enumerated **by name** and granted **one file at a time, each opened by its own handle**, through the file shape — never through the per-path loop — so a check that read the granted set instead would refuse the launcher's own launch. The `*.dll` pattern survives as the enumeration's own spelling and the tests' oracle; it is not the batch any more, because a wildcard names objects no handle can be opened on and it was the route that granted a linked `x.dll` through its target (2026-09-27). A sibling that is a reparse point is refused, and so is one whose `symlink_metadata` fails — a stat that cannot answer is not an answer that grants.

**The derived SID is not by itself enough to launch: the container profile has to exist.** Measured on 2026-09-19, `CreateProcessW` with `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` for a merely-derived name fails `err=2 (ERROR_FILE_NOT_FOUND)` — for the test binary and for `cmd.exe` alike, with the SID's ACE already on the tree — and `CreateAppContainerProfile` (userenv.dll, unelevated, returning the same SID as the derivation) makes the identical call succeed. So the launcher creates the profile as well as the ACEs, `ERROR_ALREADY_EXISTS` is the takeover path rather than an error, and the profile joins the ACEs as **a second artifact with its own removal**: `DeleteAppContainerProfile` on every exit path that runs a destructor — the ACEs stay, because they are standing (decision 15) — and the same deterministic-name property, since the profile's SID is the derivation's. **The takeover's SID is read from the derivation, not from the failed creation**: measured on 2026-09-21, `CreateAppContainerProfile` answers an existing profile with `HRESULT_FROM_WIN32(ERROR_ALREADY_EXISTS)` and leaves the SID out-parameter **null**, so a takeover that trusted the creation's own output would fail on exactly the run decision 21 exists for, and the Windows SDK's own sample falls back the same way.

The residual cost, which cannot be designed away: **the launcher writes ACEs onto the operator's directories, and they stand — nothing in the launcher removes them, on a clean exit or a hard kill alike** (decision 15, which carries the exposure the standing form accepts and points at the measurement that chose it). Decision 21 bounds the damage to identifiable, reusable ACEs: the next run for the same root takes its own over rather than adding another, so the residue is one ACE per distinct served root until an operator revokes it — and the ledger that lists what was granted has landed (`crates/tinio-sandbox-windows/src/ledger.rs`; the paragraph below owns the file, what a line carries and why it is not a revoker).

**Two exposures stand where the grants do, and a reader should meet them here rather than infer them from the code.** (1) **The package name is derived from the served root and this user's salt, and the salt is the whole of what keeps that derivation from being public knowledge**: without it a name — and so a SID, and so a profile a local user can create for themselves — is a pure function of the canonical root, which any local account can compute, after which that account reads everything the standing grants expose through the profile it made and leaves ACEs of its own on the way (the exposure `plans/2026-09-25-sandbox-followups.md` §10 was opened on). What the salt does not close is a reader of the salt file: it is `%LOCALAPPDATA%\tinio\acl-salt`, 32 CSPRNG bytes (`crates/tinio-sandbox-windows/src/sid.rs`), created current-user-only through `tinio_winsec::create_restricted` and **measured** that way on this host 2026-09-28 — one access-allowed entry, the current user's own SID at `0x001F01FF` and no inherited copy, control word `0x9004` (`SE_DACL_PRESENT | SE_DACL_PROTECTED | SE_SELF_RELATIVE`), read with `crates/tinio-sandbox-windows/src/acl.rs`'s own ACE walk by its `the_salt_file_is_current_user_only_and_inherits_nothing` — so another standard account on the machine cannot read it, while an administrator or anything running as this account can, and the exposure above stands against those. **The directory the two per-user files live in is repaired rather than merely created, and its definer is `crates/tinio-sandbox-windows/src/sid.rs`'s `create_state_directory`**: an existing `%LOCALAPPDATA%\tinio` whose DACL `tinio_winsec::acl_is_current_user_only` reports as not the current user's alone is re-described, because every machine that has already run a launcher carries `%LOCALAPPDATA%`'s inherited grants there and an account those grants reach could plant a file in it — and the two facts measured on this host 2026-09-28 are that the repair reaches the files already inside (a third-party file placed there loses its inherited entries) while a protected child keeps its own (the salt's `SE_DACL_PROTECTED` descriptor survives it). **What the salt closes is pre-computation, and that is a narrower statement than "the name is hidden":** nobody derives a name for a root they do not serve, but a profile that exists publishes its own — `%LOCALAPPDATA%\Packages\<name>` is that name in plain sight for as long as the profile lasts, and an account with access to `Packages` (the descriptor that directory carries is measured to be the parent's inherited one, decision 21) can read it there and call `CreateAppContainerProfile` with it. The windows left are the profile's own lifetime — a clean exit deletes it (decision 21) — and the ledger's lines, which are this user's alone since the fix of 2026-09-28 recorded in the paragraph below. **A salt that cannot be read, created or trusted does not fail a launch**: it is warned about and the run derives the *unsalted* name, which is the exposure again for that run and for the ACEs it leaves standing, and that warning is the only thing distinguishing the two. **The salt costs the migration as well as closing the exposure**: every ACE and every profile that exists today belongs to an unsalted SID, so the first run after it lands derives a new SID for every served root, writes a fresh grant there, and leaves the unsalted ACEs standing — decision 15 takes nothing back, so they are residue until an operator removes them. (2) **The program directory's `ALL APPLICATION PACKAGES` grant is readable by any AppContainer application on the machine**, not only by this server's container: the SID is the one every package token already carries (decision 22 and Ruling 78 own the shape and the per-root cost it removes), and **no layer of this design narrows it** — the salt changes which per-root SID is derived and not which SID that directory carries, and the ledger below records the directory rather than narrowing it. Its price is stated where the constant is (`crates/tinio-sandbox-windows/src/sid.rs`'s `ALL_APPLICATION_PACKAGES`), and an operator who wants it gone takes it back the way every standing grant goes: `icacls <dir> /remove:g "*S-1-15-2-1"`, after which a confined child that imports a DLL beside its binary dies on startup with no diagnostic, which is the failure decision 22 measured the grant prevents.

**The ledger is the record of what was granted, and it is an audit surface rather than a control.** `crates/tinio-sandbox-windows/src/ledger.rs` appends one JSON object per line to `%LOCALAPPDATA%\tinio\acl-ledger.jsonl` — what the path is to the run (`kind`: `served-root` for the root, `exposure` for the paths beside it — the field without which a reader counting served roots would count the state directory as one), the path as the caller spelled it, its normalisation, the package name, the `S-1-15-2-…` SID every ACE of the run names, the UTC instant as RFC 3339, and the program directory whose `ALL APPLICATION PACKAGES` grant is the machine-wide one — once per launch and once more for every other path the caller exposed (the state directory, `TINIO_STATE_DIR`, which is granted read-write when it lies outside the root), so the file is the index of **every** standing ACE this crate writes and not of the root's alone, **after the grant phase has returned and never from inside a per-path grant**, so a line is a claim that a grant happened rather than an echo of an attempt and a phase that fails halfway records nothing. **It appends and never removes, edits or rewrites**, which is how it keeps the rule it was opened on — a SID belonging to a run started after the ledger was read must not be removed — by construction: the crate has no removal path for a reader to order wrongly, and **revocation stays an operator's manual `icacls … /remove:g`** (`acl::revoke`'s own call), which is the removal the launcher deliberately never makes (decision 15). Two runs appending at once are a sequence rather than an interleaving: the append takes the same per-path kernel lock a grant does, keyed on the ledger's own path rather than on a served root. **A ledger that cannot be written warns and the run continues** — the record is not worth failing a confinement for, and `ledger::record_run` has no failure to propagate. **A run's lines are one transaction** (the shape of 2026-09-29): the lock, the descriptor read-back and the open are taken once for the whole run rather than once per line, so the read-back precedes the run's first appended byte and the file is the same record it was when the lines were written one at a time. **The file carries exactly what the salt hides, so it is protected the way the salt is**, and that is the fix of 2026-09-28: a line names the package name and the full SID, and a reader of one line can call `CreateAppContainerProfile` with that name — so the ledger is *published*, not merely opened: `tinio_winsec::create_restricted` makes a private object, the first line is written into it, and `fs::hard_link` puts that object under the ledger's name, so the name never exists without both its value and its descriptor; a ledger that already exists is read back before the run's lines and put right when it is not the current user's alone, which repairs what an earlier revision created under the directory's inherited grants (measured on this host 2026-09-28: `FLIER-WIN11\CodexSandboxUsers:(I)(M)` beside an unresolved SID on the file before the fix, one current-user entry at `mask=0x001F01FF` with no inherited copy and control word `0x9004` afterwards — the same reading the salt carries, and `crates/tinio-sandbox-windows/src/acl.rs`'s `the_ledger_file_is_current_user_only_and_inherits_nothing` is the leg) and which refuses to publish a line into a file another account planted at that name when it cannot be put right; and the state directory `%LOCALAPPDATA%\tinio` itself is put back to the current user by `sid`'s `create_state_directory` on the next run, because a directory that inherited `%LOCALAPPDATA%`'s grants is one another account can create a file in — with the children that carry a *protected* descriptor, the salt's among them, surviving that repair (measured rather than assumed, and the leg is `sid.rs`'s `the_state_directory_is_put_back_to_the_current_user`). **What the ledger does not protect is a name that is already public and a reader that is already inside**: the profile directory's own name (the paragraph above), and a file another account planted *and opened* before the repair, since a DACL change does not revoke access a handle was granted at open time. And a line is a claim about a past grant and never about the present: nothing in the file says the SID it names is still standing.

**Every read-merge-write of one path's descriptor is taken under one per-path kernel lock, and that lock is what stops two runs sharing a served root from losing each other's ACE.** A grant reads the object's DACL, merges its own package SID's entry into what it read and writes the whole descriptor back, so two grants that overlap on one path end with the later write replacing the earlier's entry with a copy that never carried it — silently, because each run's *own* grant is present and `SET_ACCESS` replaces only the same SID's entry, while two roots are two SIDs. `crates/tinio-sandbox-windows/src/acl.rs`'s `AclLock` is a lock file under the caller's temp directory — `tinio-acl-locks\<16 hex>.lock`, the digest taken over the *same* normalisation `package_name` derives under and **its unsalted reading** (`sid.rs`'s `root_digest`), so two spellings of one directory take one lock rather than one each and a salted run and a degraded one still take **one** lock for one path — opened without sharing delete and held exclusively with `LockFileEx` across the read, the merge and the write, and across `revoke` as well (its one production caller is an operator, since the launcher revokes nothing — decision 15). A ledger append is the lock's second writer, keyed on the ledger's own path (§6's ledger paragraph owns it). **The wait is reported rather than bounded**: a holder is inside a whole-tree descriptor write, the seconds-per-phase case measured above, so a bounded wait would fail a grant that was about to succeed; a waiter that crosses **1 s** says so at `warn!`, naming the path and the time waited, and the kernel releases a killed holder's lock — which is why the primitive is a kernel lock rather than a marker, and why no stale-lock rule exists. The lock files are left behind on purpose: one zero-byte file per distinct path ever granted, and the withheld share-delete is what makes unlinking them unsound rather than merely pointless, since a second waiter would create a new file at the same name and lock that instead of the holder's. **Measured on this host, 2026-09-28**: with the lock removed from the grant, `two_grants_to_one_path_from_two_threads_keep_both_aces` failed on three consecutive runs with a directory listing that carried one package SID where two had been granted; with it, a peer *process* holding the byte range made a same-path acquire wait 18 770 ms until the holder exited, an uncontended acquire took the lock on its first attempt with no sleep at all, and a holder killed with `TerminateProcess` left the range takeable 0 ms later.

### §7 Dropping privileges and cutting the network

**The uniform network rule, on the three supported platforms: the confined process cannot initiate an outbound connection.** Inbound is untouched and follows the bind address the operator configured — the sandbox never widens it and never silently narrows it beyond what the platform's confinement enforces.

| Platform | Mechanism | Notes |
|---|---|---|
| Linux | seccomp-BPF filter denying eleven syscalls — `connect`, `sendto`, `sendmsg`, `sendmmsg`, the `io_uring` ring calls (425/426/427) and the ptrace family (`ptrace`, `process_vm_readv`, `process_vm_writev`, `pidfd_getfd`) — plus the whole x32 ABI by mask | Decision 13, which owns the set and the mask. The filter sees no address family, so an `AF_UNIX` connect is denied with the rest. Degrades on an architecture with no syscall table (the filter is skipped and reported, §11); a refusal to *install* on a covered architecture stays fatal |
| macOS | **no network rule at all** — the launcher binds both channels; base is `(deny default)` | measured: with no network rule on the serving path the confined process still accepted a real connection from a listener the parent had bound and handed in. `bind()` and `listen()` are the only gated operations — `accept` is not checked — and `bind()` *is* gated for a unix socket, which is why the confined child never binds one: the launcher binds the data plane's TCP listener and the control socket (`<state dir>/tinio-<16 hex>.sock`) outside the sandbox and hands both descriptors over, and `crates/tinio-sandbox-macos/tests/network.rs` asserts the rendered profile names no network operation. The rule the profile used to carry, `(allow network-bind)`, was removed by that handoff rather than narrowed — the narrower `(local (subpath (param "S")))` spelling did not compile. Outbound is refused absolutely, and the refusal covers more than `connect`: a `sendto` on an unconnected datagram socket is refused too, a unix-socket connect to `mDNSResponder` is logged as `network-outbound` so even name resolution does not escape, and raw sockets cannot be opened under any profile tested. | Windows | AppContainer with no network capability | **measured 2026-09-22** on a host whose unconfined baseline reaches `1.1.1.1:53`: refused `permission denied` with an empty capability set, `SUCCEEDED` with `internetClient`, refused again with `privateNetworkClientServer` instead. Verifying it cost a defect in this crate — see the verification note below and the evidence table's attribute row |
| other unix | **nothing** | decision 23; the startup warning says so |

**The Windows confined child's network is one closed vocabulary of network capabilities, and it holds none of them — the platform's own AppContainer default, with no mechanism added.** `Capability` has exactly three variants and all three are network capabilities (`crates/tinio-sandbox-windows/src/backend/capability.rs:37-45`): `internetClient` = `S-1-15-3-1`, `internetClientServer` = `S-1-15-3-2` and `privateNetworkClientServer` = `S-1-15-3-3` (`:62-68` the SID table, `:84-90` the names, `:111-120` the parser, `:143-152` the comma list). **No non-network capability exists in it** — no `registryRead`, nothing outside the `S-1-15-3-N` range — so there is nothing an operator can grant that leaves the network policy untouched, none is granted implicitly, and `backend/exposures.rs` carries no capability entry at all: its whole content is the path whitelist. Empty is the default on both sides — `Options` derives `Default` over `capabilities: Vec<Capability>` (`backend/mod.rs:85-88`), and the only operator channel today is `TINIO_SANDBOX_CAPABILITIES`, where absent and empty both mean none (`crates/tinio-cli/src/sandbox/windows.rs:132`, the `env::var` call itself — **that file and that spelling are the pre-2026-09-27 ones: the call is `crates/tinio-sandbox/src/serve.rs`'s `apply_windows` now, the CLI naming no platform `Options`**; no configuration-file key exists). A granted list reaches the kernel as `SID_AND_ATTRIBUTES { Attributes: SE_GROUP_ENABLED }` (`sid.rs:498-501`) and the default reaches it as a **null** pointer with `CapabilityCount: 0` (`process.rs:487-512`), and what enforces the consequence is WFP against the token's capability SIDs: a container holding no network capability initiates nothing outbound, tinio adds no filter, firewall rule or network namespace of its own, and **the Windows arm's outbound cut is therefore the mechanism's default rather than a rule this design writes.** **Re-measured 2026-09-25 on this host, and the raw socket code was not on record before**: the unconfined baseline reaches `1.1.1.1:53` (`Test-NetConnection -ComputerName 1.1.1.1 -Port 53 -InformationLevel Quiet` → `True`); `cargo test -p tinio-sandbox-windows --test network -- --nocapture` answers `6 passed; 0 failed`, printing the control's `measured: with internetClient the confined child reported 'outbound: SUCCEEDED'`; and a throwaway probe in `D:\Temp`, deleted after the run, under `Options::default()` reported `outbound: refused raw_os_error=Some(10013) kind=PermissionDenied` — `WSAEACCES` — against `outbound: SUCCEEDED (1.1.1.1:53)` under `internetClient`, same binary, same address, so the refusal is the capability set's rather than a missing route. **One case the evidence table does not hold** was measured in both arms of that probe: a confined child connecting to a listener owned by the *unconfined* launcher on `127.0.0.1` is dropped silently (`kind=TimedOut`, no `raw_os_error`) with the empty set and with `internetClient` alike — AppContainer's loopback policy rather than the capability filters, and a different case from the `BIND-OK`/`LOOPBACK-CONNECT-OK` row, which is the container's own stack with both ends inside it.

One asymmetry was asserted here and **its Windows half is now partly measured, with the measurement not supporting it as written**. On Windows the container's own network isolation also constrains *inbound* — a process with no network capability cannot accept from the LAN — so `--sandbox` plus a non-loopback bind needs `privateNetworkClientServer`, and without it the listener is loopback-only whatever the bind address says. What was measured on 2026-09-22 (this host's own interface address `192.168.1.10`, an Ethernet DHCP address on a `Private` profile with internet connectivity; the listener bound outside the container and handed in) is that a confined child with an **empty** capability set answered a connection addressed to that non-loopback interface, `pong` read back, and that `privateNetworkClientServer` made no difference — so on this host the policy does not gate a delivery addressed to a non-loopback interface. **What the measurement does not reach is the claim itself**, which is about a client on the *LAN*: both ends of it are this machine and the packet never leaves it, so whether a remote client gets through is still unmeasured, and the requirement above stays a precaution rather than a measured necessity until a second host answers it (the evidence table has the row, with its limit written into it). **Handing the listener in does not change this** (decision 16): the policy is applied to the process, not to the socket's origin, which is exactly why the design does not lean on the handoff for isolation. On Linux the filter cannot see a `sockaddr` (seccomp cannot dereference pointers), so a non-loopback bind still accepts from the network. A Linux deployment that wants Windows's stricter posture has to get it from the bind address, which is where it belongs.

macOS lands on the same posture as Linux — inbound governed by the bind address and nothing else — but reaches it by not checking `accept` at all rather than by failing to see the address, and its outbound refusal is the strongest of the three. So the three platforms agree that outbound is cut, and differ in what they do about inbound: Windows narrows it whether the operator wants that or not, Linux and macOS leave it to the bind address. That is the honest shape of the guarantee — "cannot initiate outbound" is uniform, "inbound follows the bind address" is uniform in intent and enforced by different means.

**Verification gap, closed 2026-09-22 — and what closed it was a defect in this workspace rather than a property of the authoring host.** The row is measured now: on a machine whose unconfined baseline reaches `1.1.1.1:53`, a container with an empty capability set is refused it `permission denied`, the same container granted `internetClient` completes the connection, and one granted `privateNetworkClientServer` instead is refused again — so the refusal is the capability set's and the capability's *name* is what decides it (the evidence table carries the transcript and the reproduction). **The "refused identically with and without `internetClient`" the gap was opened on was this crate's bug.** The capability SIDs were handed to `CreateProcessW` as `SID_AND_ATTRIBUTES { …, Attributes: 0 }`, and an AppContainer token carries such a SID without honouring it — not in the WFP filters that enforce this row, and not in an access check against a resource whose ACL names it. Every capability the option could grant was therefore inert, which made a container granted `internetClient` and a container granted nothing the same container, and made the earlier probe's two identical refusals read as a host policy when they were the attribute's absence. One attribute — `SE_GROUP_ENABLED`, in `sid::CapabilitySids::resolve` — is the whole fix, and the row above it in the evidence table is its before-and-after. **One half of §7 is still not measured on any host used here**: what a client *on another machine* sees when a confined container's inherited listener is bound to a non-loopback address. The note above the platform table states what was measured instead and why it falls short; neither the guarantee nor the documentation depends on the answer (decision 16), and a second host is what would settle it.

### §8 Capability dropping (Linux)

**The prefix, before any of this: write the maps.** The user-namespace model is entered in two steps — `unshare(CLONE_NEWUSER)`, then `/proc/self/{setgroups,uid_map,gid_map}` written with `deny` and `0 <euid> 1`, then `unshare(CLONE_NEWNS)` and the jail (decision 12). The order is forced from both sides: the map descriptors cannot be opened before the user namespace exists (measured: `EPERM` on a pre-opened descriptor, `EACCES` opening `setgroups`), and the host's `/proc` is gone once the mount namespace is created. Skipping the maps is not survivable either — **on a superblock the namespace itself owns** an unmapped gid makes `mkdir` and file creation fail with `EOVERFLOW(75)`, so `local_uid` and the `CAP_CHOWN` row below are not the only things that need a mapped identity. Re-measured 2026-09-19, the qualifier matters: with no maps at all, `mount("tmpfs", …)` still succeeds and creating a file on the **host's** ext4 succeeds too (the host sees it owned by the real uid), while `mkdir` and `open(O_CREAT)` inside the namespace-owned tmpfs fail `EOVERFLOW`. The jail is built inside that tmpfs, which is why the maps are load-bearing here.

Fixed order, after the jail is built: `prctl(PR_SET_NO_NEW_PRIVS, 1)`, then `PR_CAPBSET_DROP` for every capability not retained, **then** `capset` to clear effective/permitted/inheritable, and last the seccomp filter — all mounts are done by then, and `PR_SET_NO_NEW_PRIVS` must already be set for a filter to be installable without `CAP_SYS_ADMIN`.

**The sweep comes before the `capset`, and an earlier version of this paragraph had it the other way round.** `PR_CAPBSET_DROP` needs `CAP_SETPCAP` in the **effective** set at the moment of the call: re-measured 2026-09-19 on WSL2, with caps intact the drop returns `0` and `PR_CAPBSET_READ` flips to `0`, while after a `capset` clearing effective and permitted it returns `EPERM(1)` and the bounding set is left untouched — with or without `PR_SET_NO_NEW_PRIVS` set first, so `no_new_privs` is not a substitute. An implementer following the old order would get a bounding set that silently stayed populated. `CAP_SYS_ADMIN` goes with the rest — once the mount table is built there is nothing left to mount.

Installing the filter before any thread exists is what makes it correct: a seccomp filter applies per-thread unless `SECCOMP_FILTER_FLAG_TSYNC` is used, and there is nothing to sync when the process is still single-threaded. It is the same reason `unshare` must run early, and §10's ordering covers both.

| Mode | Retained capabilities |
|---|---|
| Read-only | none |
| Read-write | none, **except** `CAP_CHOWN` when a `local_uid` mapping is configured (FR-033 chowns landed objects) |

Two consequences to document rather than discover:

- **Running as root, `--sandbox` makes root capability-less.** Files under the served root that are not owned by the service account lose DAC override and become unreadable, surfacing as `AccessDenied`. The served root is expected to belong to the service account; this is a behaviour change for root-run deployments and belongs in the flag's documentation.
- **A user namespace cannot chown to an unmapped uid.** `local_uid` mapping plus the user-namespace model fails at startup with a configuration error pointing at the root model, rather than failing later on the first object write. The check is explicit and runs **before the availability probe**, so an operator who asked for an impossible combination is told so without a namespace ever being created.

### §9 Read-only mode is a value, not a mechanism

The sandbox takes a set of `(path, AccessMode)` pairs and does not know how they were derived. In normal mode the state directory is `<root>/.tinio`, inside the served root, so it needs no entry of its own. **FR-023 has landed**, so in read-only mode the state directory is `TINIO_STATE_DIR` or `<home>/.tinio/roots/<hash>/` — outside the served root — and the same `expose` call gains one `rw` entry and the mount table gains one row. **The entry is added only when the two are disjoint**, because it is the entry that carries the hole in the opposite case: a state directory that **holds** the served root substitutes `rw` for the root's own access over the root — and, on a read-write run, grants over the root's **siblings** under that ancestor, which no mode asked for — so the launcher refuses that pair on **either** run rather than exposing it. **No code in this design changed when read-only mode landed**, which is the property this section was written to have; what it cost was one line at the call site and one row in the table, and both were already written.

**The mode's precedence is the configuration's, then the environment's, then the flag's** — `[server] read_only` → `TINIO_READ_ONLY` → `--read-only`, in `serve.rs` — and `AccessMode` is the value that carries the result. A launcher platform reaches the same answer through decision 18's targeted probe, because it must not retain a parsed `Config`; the two processes therefore agree on the mode without either of them parsing the document.

The read-only *mode* and the read-only *mount* are separate: `--read-only` decides where state lives and refuses writes at the API layer (FR-023); `--sandbox` makes the served root unwritable at the kernel layer. They compose, and each works without the other. On the three supported platforms the second is real enforcement; on the fallback path of decision 23 only the first exists, and the startup warning says so. **Read-only governs the data plane, and the state directory stays legitimately writable**: the mode's promise is about the served root, so the access log (appended — `crates/tinio-cli/src/commands/start/run.rs`), `meta.redb`, the staging areas and `state` are written in the resolved state directory, which in this mode is outside the root, and the confinement does not narrow that. `crates/tinio-cli/src/commands/start/run.rs`'s `a_read_only_run_appends_its_access_log_in_the_state_directory` pins the pair.

One combination is refused deliberately: read-only mode with a state directory inside the served root. The confinement would make that directory unwritable and the server could not start. It now takes an explicit `TINIO_STATE_DIR` pointing under the root to reach, since read-only mode relocates state by default — and it is refused three times over, rather than once, in the order a run meets them: `discover::load_or_create` refuses a first start whose derived config path lies inside the root (so on that shape the sentence an operator reads is discovery's, and it names `server.read_only`), the two launcher platforms reject it one process before the storage layer does, before anything is granted or launched, because a failure inside the confinement is the more expensive way to learn it, and `FsStorage::new` rejects it last (`crates/tinio-fs/src/backend/mod.rs:398-418`). Failing closed with a clear message is better than a server that dies on its first log write. **The mirror is refused by the same guard rather than a second one, and on either run**: a state directory that **holds** the served root — equal to it, or an ancestor of it — would take the state directory's `rw` entry across the root — on a read-only run the same promise broken from the other side, and on a read-write run a write over the root's siblings under that ancestor that no part of the run asked for. The mode narrows the in-root clause alone, as the guard's own doc states, and the equal pair is answered by the in-root sentence, a strict ancestor by the guard's own.

**A second, macOS-only combination is refused the same way, and it is the default shape of the first**: read-only mode with **no** `TINIO_STATE_DIR`, whose state directory is therefore the derived `<home>/.tinio/roots/<hash>/`. Seatbelt refuses `file-write-mode` on `<home>/.tinio` — the directory the derivation must create, one level above the only entry the exposure set carries (the state directory itself, read-write) — and `$HOME` is the grant that would cover it, which this project deleted. No path can grant the parent, so the launcher refuses in `sandbox::plan`, beside the in-root refusal and by the same reasoning ("the launcher is what would have granted the wider access"), rather than let the child die with an EPERM that names a path and no remedy. The refusal names an explicit writable `TINIO_STATE_DIR`; **the platforms whose mechanisms do not refuse are not refused**: Linux confines in place after `start::run` created the state tree, and on Windows the launcher creates it as the user before the container child runs, so on both the derived directory is the documented working shape where a refusal would reject a run that works.

### §10 Entry-point wiring

`unshare(CLONE_NEWUSER)` returns `EINVAL` in a multi-threaded process (verified), and `#[tokio::main]` builds its multi-threaded runtime inside `main`. The entry point therefore stops being `#[tokio::main]` and becomes a plain `fn main` that confines first:

```
fn main()
 1. read the launch payload if one was inherited   -> confined child: jump to 8
 2. parse arguments
 3. load configuration (host paths, read before the pivot)
 4. ensure_chown_privilege, and resolve the mode  config -> TINIO_READ_ONLY -> --read-only
 5. create_dir_all(root) and the state dir        the bind sources must exist first;
                                                  read-only creates no root and keeps
                                                  no state inside it
 6. macOS / Windows: bind the listener, apply the exposure set, launch the child
    Linux:           the Linux backend confines in place
 7. macOS / Windows: supervise — relaying the child's events, and turning a child that never reported into an `Error` — forward the exit code; the ACLs stay (decision 15)
 8. Builder::new_multi_thread().build()?.block_on(serve(...))
```

Step 1 is the discriminator of decision 17 and comes first, before anything else, so a confined child does no privileged work on its way in. Step 6 is skipped on Linux, where the process binds its own listener after `enter()` and prints the endpoint itself (decision 19). The bind sources must exist before step 6, and no thread may exist before it either — both of which the sequence satisfies, and the CLI's tracing subscriber is installed around that step rather than beside it for the reason decision 26 states.

**One precondition the sequence does not express is that `$TMPDIR` must be writable.** The jail is a tmpfs mounted under `std::env::temp_dir()`, so on Linux it is the one host resource the confinement itself consumes — and a read-only or full `$TMPDIR` makes the confinement fail before any later step does. The failure is a startup error that names `$TMPDIR` and its errno rather than the bare `create jail root` step, because the resource that ran out is not the served root and an operator told only "create jail root" looks there first.

**A second precondition is macOS's, and the sequence does not express it either: the state directory must take a new entry.** `macos::confine_or_launch` calls `refuse_unwritable_state_dir` (`crates/tinio-cli/src/sandbox/product.rs`, its own doc the definer; re-exported through `sandbox/mod.rs`, which is a pointer rather than the definition — the CLI's product refusals moved to `product.rs` with the `serve::Spec` seam, 2026-09-27) ahead of `backend.confine`, so a `state` publish that would fail after the child is listening — on a platform with no job object to end it — is refused while no child exists; the probe takes and gives back one entry rather than reserving one, so the window between it and the publish stays a TOCTOU residual.

**Steps 4 and 5 are FR-023's, and they are guards rather than additions.** The chown probe writes a scratch directory *inside the served root*, and creating the root writes the one thing read-only mode promises to leave alone, so both are skipped when the mode is read-only; and the state directory is resolved to the relocated path rather than to `<root>/.tinio`, because it is one of the paths a launcher platform has to expose. On Linux the sequence is the whole of `main`, in place; on the two launcher platforms the same steps run in the parent, and the child re-derives the identical answer from the payload's configuration bytes, the environment and its inherited argv.

Because the Linux jail mirrors host paths (decision 9), step 8 is **byte-identical with and without `--sandbox`**: same root path, same state-dir path, same relative-path resolution.

**Step 6 is where the two shapes differ, and the difference is configuration rather than dispatch.** A Linux run has settings the other two do not — `Options`, carrying `Mechanism` (decision 7) and the capability policy — and a status to report back, the `seccomp()` answer that says whether the filter was installed or skipped for an architecture with no syscall table (§7, §11). Those live in `tinio-sandbox-linux` and are reached from the example through the facade's cfg-gated alias for it — `use tinio_sandbox::linux;` inside a `#[cfg(all(feature = "sandbox", target_os = "linux"))]` block, so the example names the facade and nothing else; a macOS or Windows run reaches its backend through the facade's `platform()` and needs nothing more, because neither has an equivalent setting. The cfg block is therefore the visible edge of decision 2's boundary, not a failure of it: the shared surface is what drives a confinement, and a platform's own vocabulary stays with the platform.

**Step 1's jump, the confined child's own entry point, is per-launcher-platform and gated as such.** Each of macOS and Windows writes its own `confined`, gated by the feature *and* its own `target_os` — not by the feature alone, because what it calls is platform-specific and a feature-only gate would name functions that do not exist on the other two targets. Linux writes none: it confines in place and never re-invokes itself, so the entry is never reachable there and `adopt` returns `None`. The two bodies differ — Windows installs a stop hook the child side owns and macOS does not — but they agree on the one thing shared code must agree on: **the listener is rebuilt through a single platform-neutral facade name**, `adopted_listener`, rather than by a method on core's `Adopted` or by naming the platform crate. That name is decision 2's rule applied to the child side, and it is why `Adopted` carries the descriptor number rather than a socket: the rebuild is each platform's own, and the facade is where shared code finds it.

### §11 Errors and failure handling

`enter` and `launch` return `Result`. Failure is always fatal: the process never continues unconfined, because a server that silently runs without the confinement its operator asked for is worse than one that refuses to start. **The one row below that is not fatal is not silent either** — a skipped filter is reported through the return value, not logged and forgotten, so the caller can warn without the confinement being the thing that failed.

| Condition | Response |
|---|---|
| Sandbox requested in a build without the feature | usage error (exit 2) naming the build (decision 5) |
| Sandbox requested through a channel this phase does not implement (`[server] sandbox`, `TINIO_SANDBOX`) | startup error naming the channel and saying `--sandbox` is the only one honoured today (decision 5). Never a silent unconfined run — the operator used a channel this document names |
| Sandbox requested with an OTLP endpoint configured | startup **warning** on stderr naming both, and the confinement proceeds; the export is what is lost, not the confinement (decision 25). The one row here that neither refuses nor degrades the sandbox itself |
| `sandbox-exec` missing or refusing the profile (macOS) | startup error carrying the binary's own diagnostic |
| Linux without a usable user namespace and not root | startup error naming the remedy by host: `kernel.apparmor_restrict_unprivileged_userns=0` (or an AppArmor profile for the binary) on Ubuntu 24.04+, where that restriction is the default and the refusal is `EPERM`; `kernel.unprivileged_userns_clone` on Debian-family kernels; or run as root |
| Linux on an architecture the seccomp table does not cover | **not** a startup error: the filter is skipped, the directory boundary stands, and the caller is told so it can warn — the one place in the Linux backend where a guarantee is downgraded rather than the process refusing to start. **The warning is a `warn!` on stderr through the same tracing channel as every other sandbox log, and deliberately not an event on stdout**: decision 19's vocabulary is two events, and a third would make every consumer decide what to do about something that is not a startup failure. A machine consumer that needs to know reads stderr, which is where this design puts every log (shared §7) |
| Launch payload absent or malformed | the process treats itself as the launcher; inside a confinement that fails closed |
| Any syscall refusal (`EPERM`, `EINVAL`, …) | error naming the step that failed and its errno |
| Read-only mode with an in-root state directory | configuration error (§9) |
| Read-only mode with the state directory **derived** (no explicit `TINIO_STATE_DIR`), macOS | startup error (§9) from the launcher, naming the derived path and the remedy: the parent is a write Seatbelt refuses and no exposure can grant |
| `local_uid` mapping with the user-namespace model | configuration error (§8) |
| A `UpdateProcThreadAttribute` call fails | startup error, **fatal**: measured 2026-09-19, a failed attribute set leaves the attribute unset and `CreateProcessW` still succeeds, so the child would run with no container at all. Every attribute-set call is checked before the launch is attempted. **A value the attribute accepts and the launch then refuses is fatal in the same place, and the one this phase hit is the default configuration**: measured 2026-09-21, `SECURITY_CAPABILITIES.Capabilities` carrying the empty slice's own dangling pointer beside `CapabilityCount: 0` makes `CreateProcessW` fail `err=87` (`ERROR_INVALID_PARAMETER`), so a container with **no** capability — the configuration §7's outbound guarantee rests on — is the one that could not launch. Null is the value for no capabilities, and the kernel reads the pointer even when the count is zero |
| Windows ACL grant, `CreateProcess`, or Job-object failure | error naming the directory and the underlying failure. **Nothing is rolled back**: every grant this crate makes is standing (decision 15), so a failed launch leaves the ACEs it had already written, and the next run on the same root finds them and skips the write rather than being handed a clean tree. It is not always a Win32 error: where a grant goes through a tool rather than a direct API, what arrives is that tool's exit status and text, and the error type carries both forms rather than pretending the second does not exist |
| Platform outside the three | startup warning enumerating what cannot be delivered, then best-effort `chroot(2)` (decision 23) |

### §12 Testing and verification

- **Unit, every platform.** Mount-table composition, mirrored jail paths, SBPL profile text, ACL grant list, the launch payload's one-line JSON encoding, the event framing including a frame split across reads, and the capability policy per (mode, `local_uid`) — all pure functions of the builder state.
- **Integration, Linux.** `assert_cmd` (already a workspace dev-dependency) drives `serve --sandbox` against a temporary root and asserts the properties that matter: a write to the served root fails with `EROFS` under `--read-only`; the state directory outside the root is written; a path outside the jail (`/etc/passwd`, `$HOME`) is unreachable; the server binds and serves. `TINIO_SANDBOX_MODEL=userns|root` selects the model so both branches run rather than whichever the host happens to allow — **and which read-only mechanism a branch takes is reported by the run, never required of it**, because the arm follows the host's locked mount flags rather than the model (§4).
- **Integration, Windows.** The same shape against `serve.exe`, asserting the whitelist (granted tree readable, sibling denied, `RX` rejects writes), that the grants stand (nothing rolls them back on a clean exit or a failed launch — decision 15) and that a second run on the same root finds them rather than writing them again, and that killing the launcher takes the child with it. Must run on both an NTFS and an ReFS volume — the verified rows show they agree, and a regression that broke one would otherwise be invisible. **What discharges that clause is `crates/tinio-sandbox-windows/scripts/verify-windows.ps1`**, whose volume list defaults to `C:\;E:\` and which prints the filesystem each run actually covered rather than assuming it (a machine with only one of the two is a fact about the machine, which the script reports and does not fail). It must also settle the network row of §7 on a host whose baseline connectivity is known. **That last clause is discharged elsewhere as of 2026-09-22**: the row is measured by `crates/tinio-sandbox-windows/tests/network.rs`, which is the crate's own suite rather than the `serve.exe` integration leg, because the measurement belongs beside the backend it falsifies — and `serve.exe` takes no capability by default, so the integration leg exercises the empty set that `an_address_that_works_outside_is_refused_inside` already covers.
- **The event contract, every platform.** Round-trip `Event::encode`/`decode` as pure functions, pin the exact wire text rather than only round-tripping it (a consumer in another language reads it, and a symmetric mistake would round-trip perfectly against itself); assert that a consumer meeting a non-frame line, an unknown event name or a payload that does not fit its name skips it rather than failing; assert that a frame **split across several reads** is assembled — and assembled *whole*, since a relay holding one decoder per call would still emit a frame per surviving event while losing the bytes of a half-read one; and assert that a confined server emits `Listening` with the address it actually bound. On the launcher platforms, additionally assert that text the child writes to stdout which is *not* a frame does **not** reach the parent's stdout — that is the relay's whole job, and a relay that forwards bytes would pass every other assertion in this list — and that a child which exits without ever reporting becomes the parent's own `Event::Error`, read from the terminal record **after** the wait rather than before it. **That last clause's coverage state, as of 2026-09-27**: **Windows is discharged** by `crates/tinio-server/tests/sandbox_e2e_windows.rs`'s `a_child_that_never_reports_is_the_parents_own_error_frame` — the induction is a served root whose own directory the container is not granted (a directory junction), so the child dies pre-dispatch with nothing on stdout; the assertions are that stream against the encoder's own bytes, the child's exit code, and three witnesses that a child ran — and **the macOS arm of the same assertion still has no leg**, that crate's e2e having the spawn-and-read shape without an induction (`docs/tests.md`'s Windows section carries the leg for the gate). **The ordering the sentence names is not what the leg observes, and that is a property rather than a gap**: "after the wait" belongs to `supervise`'s borrowed child and `Child::wait`'s join of the relay, so a parent that read the record early would compile, run and answer the same frame on this fixture; what the leg pins is the call site's two effects, which is the half the design sentence is about.
- **Network isolation, every platform.** The assertion is the same everywhere: loopback bind and accept still work, and an outbound connection to a known-good address fails. **An earlier version of this sentence said the assertion "belongs in the shared suite", and there is no shared suite** — each crate owns its own test, because what makes a connection fail is that platform's mechanism and a shared helper would be parameterised straight back into three platform tests. What is shared is the *shape* of the assertion, and each crate's test states it. A test that only checks "connect failed" proves nothing — a machine with no route fails it too — so the harness must first prove the address is reachable from outside the confinement and then assert it is unreachable inside.
- **The feature gate.** A build with `--no-default-features` must reject `--sandbox` with exit 2 rather than starting unconfined (decision 5), and must still pass the workspace's existing no-default-features leg.
- **WSL2.** `crates/tinio-sandbox-linux/scripts/wsl-chroot.sh`, modelled on `crates/tinio-e2e/scripts/wsl-interop.sh`: point `CARGO_TARGET_DIR` at ext4, run once as the normal user (user-namespace model) and once under `sudo` (root model). Commands recorded in `docs/tests.md` under the existing WSL2 section. It lives in the Linux crate, not the facade, because everything it runs is Linux-only — the same reason `verify-windows.ps1` and the macOS scripts live in their own platform crates.
- **CI.** The Linux leg runs the integration suite on both models. The macOS leg is the only place the SBPL profile is ever exercised on real hardware, so P3 is not done until that leg runs a confined server and serves a request through it — a profile that merely fails to crash the process proves nothing. **It lints the workspace as well as testing it**: the `macos-latest` leg of `test-port` runs `cargo clippy --profile ci --workspace --all-targets -- -D warnings`, because macOS-only code never compiles in the ubuntu clippy job.
- **Established on a real Mac, from this Windows host.** macOS 15.8 (24H23, x86_64, SIP on) runs in a QEMU VM reachable over SSH, and the whole of §5's then-profile and §7's macOS row were measured there on 2026-09-19 with a purpose-built probe plus `log stream` for the refusals. The probe and its drivers are throwaway, so the *results* are cited above rather than a script; if the profile is ever doubted, the two commands that produced every macOS row here are `sandbox-exec -f <profile> <binary>` and `log stream --predicate 'sender == "Sandbox"'`.
- **And with the real binary, not only a probe.** The workspace was copied into the VM, built there, and run under §5's profile with no refusal outside the launcher's noise floor (evidence table). So the read set is no longer an open question on this platform, and P3's first task is a test rather than a discovery.
- **Still not verifiable here.** The fallback path of decision 23 (no such host exists in CI), and anything on the CI macOS leg — the VM proves the *mechanism*, and CI is where it has to keep being true on a machine nobody is watching. The read set being application-specific remains a live hazard for future changes: `python3 -V` ran under the measured profile while `import socket` did not, because the interpreter then scans its own installation tree. tinio does not, today; a dependency that starts to would show up as a refusal in the leg's own log, which is why the leg records them.

### §13 Phasing

Four independently shippable phases. Each has its own verification and its own reason to stop.

| Phase | Crates it fills | Content | Verified by |
|---|---|---|---|
| **P1 — Linux** | all five | `tinio-sandbox-core` (trait, vocabulary, launcher machinery), `tinio-sandbox` facade, `tinio-sandbox-linux` complete, macOS/Windows backends as `Unsupported` stubs, the consumer feature gate, tmpfs path-mirroring jail, `pivot_root`, adaptive userns/root, capability dropping, the seccomp network filter, read-only via remount-ro and overlay-ro, `serve` restructuring, `TINIO_SANDBOX_MODEL` | measured end to end in WSL2 on this machine; CI Linux leg |
| **P2 — Windows** | `tinio-sandbox-windows` | AppContainer launch, DACL whitelist, deterministic SID, standing grants (the "rollback on every exit path" this cell used to name was dropped — decision 15), Job object, listener handoff, ReFS coverage, and settling the open network question | measured end to end on this machine on **both volumes the suite requires — `C:\` NTFS and `E:\` ReFS** — by `pwsh crates/tinio-sandbox-windows/scripts/verify-windows.ps1`, which runs the AppContainer/DACL suite, the event and signal relays and the confined `serve` e2e over every volume present and prints the filesystem each run actually covered; the ACL pass's cost was measured on both filesystems as well (§6, Risks). **The container half of the stop relay's claim was not measurable here** — this machine has no Windows container engine — and it is not load-bearing: the host-console measurement is what makes the relay mandatory (§3 step 9). §7's LAN half is still open for the same kind of reason (both ends of that measurement are this host). CI: the Windows `test-port` leg (`.github/actions/run-test-leg`) picks the crate's suite up the moment it is a workspace member — NTFS only, with whatever console the runner has |
| **P3 — macOS** | `tinio-sandbox-macos` | SBPL profile generation, `sandbox-exec -p` launch, inline profile lifecycle, network rules | **the mechanism *and* the profile are measured**, on macOS 15.8 in a VM: the profile in §5 starts a process, confines its writes, serves a handed-in connection with no network grant on the serving path, and takes the real server — built in the VM and run under it — to a served S3 request with no refusal outside the launcher's noise floor (evidence table). What is left is the crate, and the CI leg |
| **P4 — fallback path** | a fourth platform crate, or a documented hole in the facade | best-effort `chroot(2)` and its startup warning (decision 23) | **not written, and now recorded as not written** rather than as a phase that is merely later: no plan implements it and the facade has no selection outside the three targets, so a fourth platform fails to compile and the promised warning cannot fire (§2, decision 23). **Unverifiable in this workspace** when it is written — no such host exists in CI; it would ship with the warning as its only guarantee |

P1 is the original request, the only phase with a complete evidence base, and the phase that settles the layer boundaries: the three platform crates and both stub backends exist after it, so P2 and P3 fill in an implementation rather than discovering a shape. P2's design is fully evidenced too, but its implementation cannot be tested from WSL2 and belongs on a Windows host. P3 no longer waits on a Mac for its *mechanism*: the VM run of 2026-09-19 measured the profile and the network row, so what P3 has left is the crate and the CI leg — the same "fill in a shape that is already evidenced" position P2 is in, rather than the research question this sentence originally described. P4 is last because it is the weakest and the least likely to be used; it is kept rather than dropped because the operator asked for it, and it is kept separate so that its weakness cannot be mistaken for the other three. P4's home is undecided on purpose — it is the one backend with no evidence, so deciding where it lives now would be deciding it on the weakest grounds.

## Bookkeeping

- Five new crates (`publish = false`): `crates/tinio-sandbox-{core,linux,macos,windows}` and the `crates/tinio-sandbox` facade. The workspace glob picks them up, and `Cargo.toml`, CI, `README.md` and `docs/` gain a row where the other crates are listed. The facade is the only one a consumer names.
- `unsafe_code = "deny"` follows the implementation: `tinio-sandbox-linux` and `tinio-sandbox-windows` are `deny` today, because those backends have landed and each carries sites; `tinio-sandbox-macos` is `deny` too, P3 having landed its first site (`launch::inherited_fd`, the descriptor rebuild both `launch::listener` and `launch::control` call) and the in-process mechanism its other two (`apply::libsystem`, the `unsafe extern "C"` block declaring the two `libSystem` symbols, and `apply::validator`'s `fork`), which is the same rule the other two followed; `tinio-sandbox-core`, the facade and every pre-existing crate keep `forbid`. **The `#[allow(unsafe_code)]` sites themselves are enumerated in decision 14 and nowhere else**, which is why this bullet restates no list — `docs/cargo.md`'s lint rule states the rule and points there, and a second copy of the sites is the thing that drifts. The copy that was here had already undercounted Windows.
- `tinio-server` gains the `tinio-sandbox` dependency — **not** optional, since decision 19 emits the readiness frame in every build — a default-on `sandbox` feature, and `required-features` on the `serve` example target. **The landed shape is narrower than this sentence: nothing under `tinio-server/src/` names `tinio-sandbox` at all** — the edge is a `[dev-dependencies]` entry the confinement e2e targets read their events with, and the `sandbox` feature switches those three `[[test]]` targets' `required-features` rather than shipping code (`docs/superpowers/specs/2026-09-20-cli-integration-design.md` §2/§8 own that shape; this bullet is the sandbox phase's own plan for the crate, superseded there). Linux's own settings are reached through the facade's cfg-gated `linux` alias rather than through a `[target.'cfg(target_os = "linux")'.dependencies]` entry of its own, which is what keeps a consumer on **one** crate while the platform's types stay in the platform's crate (decision 2). `tinio-cli` gains the same feature when it implements the flag.
- `rustix` gains the `fs`, `mount`, `process` and `thread` features in `tinio-sandbox-linux` only (§4, §8); `tinio-fs` keeps `fs`. **Three further `rustix` edges arrived with the fork probe's handshake (2026-09-27), and this bullet is their home** — `crates/tinio-sandbox-core/src/launcher/probe.rs` owns the parent's half of the pipe a forked probe reports its verdict through, one handshake shared by the Linux user-namespace probe and the macOS profile validator: `tinio-sandbox-core` gains a `[target.'cfg(unix)'.dependencies]` edge with `fs`, `pipe` and `process` — exactly the calls the handshake makes (`fcntl_setfl`, the pipe, `Pid`, `Signal`, `kill_process`, `waitpid`) and **no `runtime`**, because the crate neither forks nor exits, the `pipe()` call and the `fork` staying with the platform crates whose unsafe sites they are; `tinio-sandbox-macos`'s existing edge **loses `fs`** and keeps `pipe` and `process`, because the one `rustix::fs` item it had — the probe pipe's `fcntl_setfl` in `apply` — went with the handshake, and in `rustix` the `fs` feature gates `pub mod fs` and nothing else (the `io` items it keeps asking for, `fcntl_setfd`/`fcntl_getfd`, are not feature-gated); and `tinio-sandbox` gains a `[target.'cfg(unix)'.dev-dependencies]` edge with `process` alone, because its facade test binds **every** re-exported name and the probe's `await_verdict` takes a pid as `rustix::process::Pid`, the one foreign type on that surface. None is a new third-party crate — rustix is already in the lock — so the ledger of *new* dependencies is unchanged, which is why these three live here rather than in their own row. `tinio-sandbox-linux` also names `linux-raw-sys` (`ptrace`, `prctl`, `errno`) for the seccomp-BPF UAPI constants — rustix already depends on it, so the tree does not grow. Every other new crate is dependency-light on purpose: core needs `thiserror`, `serde`, `serde_json`, `tokio` and the workspace's own `tinio-core` (`AccessMode`'s owner, §1) on top of the `sse-core` line below, the stub backends need nothing but the core, and Windows names `windows-sys` for its Win32 calls — a crate the lock already resolves, so it adds an edge rather than a crate to the tree (the third ledger line below).
- **Three new third-party dependencies, and the ledger is three lines rather than the one an earlier draft claimed.** Two are crates and the third is an edge on a crate the lock already resolves — a distinction constitution I's maintenance-cost accounting cares about, and one the `windows-sys` line states rather than assumes. Constitution I requires any addition to be justified against its lifetime maintenance cost, so:
  - **`sse-core`, in `tinio-sandbox-core`.** Decision 19 makes stdout a protocol channel, and the framing is SSE — a published standard with a nontrivial state machine behind it, because a frame can arrive split across reads from a pipe. Writing that by hand is the kind of parser that passes every test until a chunk boundary lands mid-escape. `sse-core` is the zero-I/O half of that lineage: synchronous `SseDecoder`, `no_std`, and — **with its default features off, which is how it is depended on** — `bytes`, `memchr` and `thiserror`, all of which are already in the tree. **Every clause of that was checked against the sparse index on 2026-09-19 rather than recalled**: 0.2.3 is the newest published version, `default = ["fastrand", "std", "stream"]`, `stream = ["dep:futures-core", "dep:pin-project-lite"]`, and the non-optional normal dependencies are exactly `bytes`, `memchr` and `thiserror`. Its defaults are not off by nature: they turn on `stream`, which pulls `futures-core` and `pin-project-lite`, exactly the async baggage this crate was chosen *over* `sse-stream` to avoid. Nothing the design uses is behind them — `SseDecoder` is unconditional and only `SseStream` is gated — so the smaller feature set is also the complete one. Its sibling `sse-stream` was rejected outright — it lists `futures-util`, `http-body` and `http-body-util` as *non-optional* dependencies, decodes from a `TryStream` rather than a reader (so an adapter is needed either way), and depends on `sse-core` itself.
  - **`signal-hook`, target-gated to `tinio-sandbox-macos`.** It buys the §3 step 9 signal relay on a platform where the requirement is defensive rather than mandatory, and it buys it *safely* — the alternative is a hand-written `sigaction`, which would be another `unsafe` site in a crate that keeps its sites enumerated and had exactly one when this argument was made (it has two since the in-process mechanism landed, and a hand-rolled handler would make three), for a requirement no standard macOS deployment can reach. Rustix is not an option: its `signal` module is signal *numbers* only, and `sigaction` sits in its `not_implemented` list by design. The marginal cost is small because `signal-hook-registry` — the crate that actually owns the handler and the self-pipe — is already in the tree transitively. **This argument was stronger before the listener rebuild was found**, when the crate could still have been `forbid`; what remains is a preference for one enumeration over two rather than a lint that forces the choice, and decision 14 (d) is where the count is actually settled.
  - **`libc`, target-gated to `tinio-sandbox-macos` — an edge, not a crate, and it is the `fork` the in-process mechanism's validator needs.** The validator is a forked child that applies the profile and exits, so this crate must call `fork(2)`; `rustix` cannot, because its `runtime` module — the only one with `kernel_fork` — exists on the `linux_raw` backend alone and this crate is the `libc` backend's (measured: an earlier draft reached for `rustix::runtime::kernel_fork` and it does not resolve on `x86_64-apple-darwin`). `libc` is already in the lock through the tree, so the *new third-party* ledger is unchanged; what it adds is an edge and one `unsafe` site. It is used for `fork` and `_exit` only — the two `libSystem` symbols the apply needs are declared by this crate, because `libc` 0.2.189's `apple` module carries no `sandbox_*` binding at all.
  - **`windows-sys`, in `tinio-sandbox-windows` — an edge, not a crate.** The Win32 ABI this crate meets is not its own to maintain, and the version that maintained it by hand had already cost a probe: the evidence table's `SID_AND_ATTRIBUTES` row is a hand-written `repr(C)` layout that returns `ERROR_NOACCESS (998)` at an 8-byte stride and works at 16. The operator ruled on 2026-09-21 that a security boundary is the wrong place to re-derive an ABI by hand, so the declarations module is gone and every module names the `windows_sys::…` item it calls — `use windows_sys::Win32::System::Threading::CreateProcessW;`, which is what the imports rule already prescribes for a 3+ segment path. The crate is **already resolved in the lock**, so this is a dependency edge inside the tree rather than a third crate in it, the same treatment `tracing` gets below and for the same reason; the workspace pins the version and `tinio-sandbox-windows` names a curated feature list rather than pulling `Win32` wholesale. The layout tests that pinned the hand-written structs went with them: with no transcription of this crate's own there is nothing local to pin, and a `windows-sys` bump that moved a layout would not compile against this crate's code anyway.
  The seccomp filter, by contrast, is hand-built rather than pulling `seccompiler` or `libseccomp` (decision 14); the UAPI constants it is assembled from are `linux-raw-sys`'s, named on the rustix line above rather than transcribed. `serde` and `serde_json` are not on this list: both were already in `[workspace.dependencies]`, so the core referencing them adds no dependency to the tree. **`tokio` is not on it either**, for a subtler reason worth stating: it is already a non-optional dependency of `tinio-server`, and the core asks for it with `io-util` alone — no `rt`, no `macros`, no `net`. The relay is async functions the caller's runtime polls, not a runtime of its own; the `rt`/`macros` features the tests need live in `[dev-dependencies]` so that a consumer pays for what it already has and nothing more.
- **A patched dependency rather than a new one: `soft-canonicalize` 0.5.6, vendored under `vendor/`.** It is already in the tree through `strict-path`, which is what `tinio-fs` proves containment with, so the ledger of *new* third-party dependencies is unchanged — this adds a source copy, a `[patch.crates-io]` entry and an `exclude` entry, and no crate. The patch relaxes **four arms, in two pairs — one in each of `soft_canonicalize`'s two std fast paths, and both sites of its existing-prefix walk**. The fast-path pair lets an `io::ErrorKind::PermissionDenied` from the platform canonicalizer fall through to the crate's own `read_link`/`symlink_metadata` machinery instead of being propagated; **both of that pair, not just the first**, because `simple_normalize_path` rewrites a plain `E:\…` into its `\\?\E:\…` form — which routes every plain absolute path, the operator's normal input and the shape `serve`'s child hands `FsStorage`, into the second one, so relaxing only the first leaves the drive-letter case denied. **The second pair is what makes that fall-through resolve rather than merely answer**: the crate's own machinery walks each component with `symlink_metadata` from the volume root, and inside the container every ancestor above the granted root is refused `PermissionDenied` — which `compute_existing_prefix` read as a component that does not exist, bailing at the first one and leaving Stage 7 to append the rest of the path **lexically**. That is an `Ok` that names no directory, and `strict-path`'s containment proof runs on that answer: inside the container the proof stopped resolving reparse points and **accepted** an in-root junction that leaves the served root, where the unconfined control on the same tree refuses it with `Path escapes boundary`, the failure class this feature exists to prevent (measured three runs of three). Two arms of `vendor/soft-canonicalize/src/prefix.rs` answer it — the second pair of the patch, whose mechanism, its measurement and its own drop check are the source header's at the top of that file rather than a second copy here. **The behaviour this ledger line is about does not move outside the container**: the escaping junction is refused again with the control's own message, and the unconfined comparison finds the two builds' behaviour identical. The platform fact it answers is the verified-evidence row above, the vendored crate's source header is the definer of that change, and `tinio-fs` gains a **direct** dependency on it for exactly one call: `FsStorage::resolve`'s root canonicalization falls back to it where the platform canonicalizer is refused. **The patch is engine-level rather than scoped to that one caller, and that is a correction rather than a nuance**: a `[patch.crates-io]` replaces the crate's source for every dependent, and Cargo offers no mechanism that scopes one to a single caller — so the second consumer is `strict-path` itself, the crate `tinio-fs` proves containment with, which resolves its paths through `soft_canonicalize` — `PathBoundary::try_new` canonicalizes the boundary, the boundary check every `join` runs goes through the same call, and the virtual forms use `anchored_canonicalize`, all reached from `validator/path_history.rs` in 0.2.3 — and therefore takes all four patched arms too, the prefix pair as much as the fast-path pair, which is the wider effect rather than the narrower. Inside an AppContainer it is refused by the same `GetFinalPathNameByHandleW(…, VOLUME_NAME_DOS)` denial the verified-evidence row records. Drop the patch when **no consumer still needs any of the arms** — `tinio-fs`'s call and `strict-path`'s containment proofs, both pairs of them, the per-arm check being the header's; the removal is the directory plus its two manifest entries.
- `[server] sandbox` joins `host` / `port` / `read_only` in `crates/tinio-config/src/schema/server.rs`, and the flag follows FR-016's `flags > env > .env > file` precedence. Until a phase implements it, setting it **or** `TINIO_SANDBOX` is a startup error rather than an ignored key (decision 5).
- **The macOS mechanism is a second operator-facing channel, and it is deliberately an environment variable rather than a config key.** `TINIO_SANDBOX_MACOS_MECHANISM` takes `sandbox-exec` (the default, and what every allowance in §5 was measured against) or `sandbox-init`; any other value is a **usage error** (exit 2) naming the variable and both values, which is decision 5's rule applied one level down — an operator who asked for a mechanism and silently got the other has been confined by something they did not choose. It is the platform crate's own vocabulary (`tinio-sandbox-macos`'s `Mechanism` and `Options`), reached through the facade's `macos` alias exactly as Linux's model is reached through `linux` (decision 2), and **the resolved value travels to the child on the launch payload** so neither process can resolve a different one. The launcher logs `step="mechanism"` with the value; on the same one-exposure run a run under `sandbox-init` renders `rules=4` (no `process-exec`) where `sandbox-exec` renders `rules=5` — a serving run renders more, one rule per exposure (§5's `rule_count` paragraph) — and its check logs `step="sandbox-init validator"` where the helper's logs `step="preflight"` — the helper logging that same step with `verdict="skipped"` when it does not run (a release build, or a level below `debug`).
- **Every sandbox crate gains a `tracing` dependency**, and `tracing-subscriber` joins the dev-dependencies of a crate whose tests assert on events. `tracing` is already pinned in `[workspace.dependencies]`, so the ledger of *new* third-party dependencies is unchanged — this adds a dependency edge inside the workspace, not a crate to the tree. Every other mention of `examples/serve.rs` or `examples/serve/` in this document and the plans is that retired target under its old name, and every consumer that named it now resolves the `tinio` binary.
