## Background

- **s3s 0.15 has no CORS operation handling, but has the seam.** The gap analysis stated "s3s 0.15 does not route OPTIONS at all (route.rs has no OPTIONS/preflight handling) — the tinio server HTTP layer must answer preflight itself." Verified against s3s 0.15.0 source: true that there is **no OPTIONS operation** (an unmatched OPTIONS falls through to `501 NotImplemented "Unknown operation"`), but s3s 0.15 *does* ship a **custom-route seam**: `s3s::route::S3Route` (`is_match(method, uri, headers, extensions)` → `check_access(req)` → `call(req)`), registered via `S3ServiceBuilder::set_route` (single slot; tinio uses none today). The route is matched in `ops::prepare` **after** signature extraction but **before** op dispatch; the default `check_access` requires credentials, but routes may override it to allow anonymous requests — exactly what a browser's unsigned preflight needs. This is the sanctioned preflight insertion point; the plan's correction is recorded here so the gap analysis's HTTP-layer assumption is not repeated.
- **The three trait methods already default to 501** in s3s 0.15: `get_bucket_cors(S3Request<GetBucketCorsInput>)`, `put_bucket_cors(S3Request<PutBucketCorsInput>)`, `delete_bucket_cors(S3Request<DeleteBucketCorsInput>)`. dto shapes (all in `s3s::dto`, `List<T> = Vec<T>`):
  - `GetBucketCorsInput { bucket, expected_bucket_owner }`; `GetBucketCorsOutput { cors_rules: Option<CORSRules> }`
  - `PutBucketCorsInput { bucket, cors_configuration: CORSConfiguration, checksum_algorithm, content_md5: Option<ContentMD5> (String), expected_bucket_owner }`; `CORSConfiguration { cors_rules: CORSRules }`
  - `DeleteBucketCorsInput { bucket, expected_bucket_owner }`
  - `CORSRule { allowed_headers: Option<AllowedHeaders> (Vec<String>), allowed_methods: AllowedMethods (Vec<String>), allowed_origins: AllowedOrigins (Vec<String>), expose_headers: Option<ExposeHeaders>, id: Option<ID> (String), max_age_seconds: Option<MaxAgeSeconds> (i32) }`
  - The XML body is deserialized by the framework (`ops/generated.rs` `deserialize_http`); responses are framework-serialized. `NoSuchCORSConfiguration`, `InvalidRequest`, `InvalidDigest`, `BadDigest` error codes all exist; `AccessForbidden` does **not** (AWS's preflight-denial code — see Decisions/grilling Q10).
- **CORS rule semantics are order-preserving and first-match**: AWS selects the *first* rule whose origin matches (then validates method/headers within it). The wire codec therefore must never sort or dedupe rules.
- **Storage rows** (shared table layer, post-tagging shapes): `BUCKETS` `name → (created_at_nanos, tags_wire)`. Extension mechanism: tuple-arity extension appending the new element **last** + canonical wire-string elements, no schema version bump (user ruling 2026-09-02 — additive changes carry no bump; `STATE_VERSION` stays 1) and self-healing decode (invalid element → default). **Correction 2026-09-06 (final review F1; user ruling — NO migration):** "no bump" covers only the `STATE_VERSION` number — it does NOT mean pre-existing row shapes keep decoding. A redb table's key/value type names are bound at the `TableDefinition`: changing the tuple arity makes `check_match` fail with `TableError::TableTypeMismatch` **on open**, so a state dir (`meta.redb`) written by an older row shape will NOT open — the server refuses to start (loud failure, no silent data loss). There is no migration mechanism and no historical-version support — the documented recovery is deleting the state dir (dev-local derived metadata; the scanner recomputes it).
- **Context**: the 2026-09-05 ACL plan is in-flight (owner/ACL elements on BUCKETS/OBJECT_META/UPLOADS). This design targets the current 2-tuple BUCKETS row; the CORS element appends **after the last existing element** regardless of whether the ACL plan merges first (reconcile note in the plan, not here).

## Goal

1. **The three CORS ops are real.** Bucket CORS configuration is stored per bucket (fs + mem via the shared layer), echoed by `get_bucket_cors` (rules in stored order), replaced by `put_bucket_cors` (replace-all, no merge), removed by `delete_bucket_cors` (idempotent 204; subsequent get → 404 `NoSuchCORSConfiguration`).
2. **Preflight works.** An anonymous browser OPTIONS (with `Origin` + `Access-Control-Request-Method`) is answered from the bucket's stored configuration: 200 with the `Access-Control-*` header set when a rule allows the origin/method/requested headers, 403 `AccessDenied` otherwise — without ever revealing bucket existence.
3. **Actual responses are decorated.** Non-OPTIONS requests carrying a matching `Origin` get `Access-Control-Allow-Origin` (+ `-Allow-Methods`, `-Expose-Headers`, `-Allow-Credentials`) on their responses (4xx XML error responses included), so browsers can actually read results after the preflight — without this half, browser clients remain blocked and the feature is inert (user Q1).
4. **Double gated.** A `cors` cargo feature (default on, added to `default`) plus the `Capabilities.cors` runtime toggle (default true) — the `multipart`/`acl` pattern, **not** the compile-always tagging pattern (user grilling Q2). Feature off → the three ops answer s3s's own trait defaults (501 `NotImplemented "{name} is not implemented yet"`) and no preflight/decoration code exists (OPTIONS falls through to s3s 501 as today); capability off (feature on) → `NotImplemented "{name} is disabled"` via `require_cap` (**review correction C3** — the two gates answer different messages; §8 splits them).
5. **Legacy behavior preserved** on all other paths: `DataPlane::new`/`new_with_auth` constructors unchanged in behavior for non-Origin requests; bare OPTIONS probes (no Origin) keep the s3s 501. ("No schema bump" is scoped to the `STATE_VERSION` number — see the Background row-shape correction: an older-arity state dir refuses to open; it never loads under the new shape.)

## Non-goals

- **Other per-bucket config APIs** (lifecycle/policy/notification/encryption/ownership): the same BUCKETS-wire mechanism generalizes later; this design lands only CORS.
- **Prefetch/browser-cache coordination, credentialed-request theory** — out of scope for a dev-local S3 server; the only caching coordination done is the (AWS-exact) `Vary` header trio (Non-goals → grilling Q4).
- **Multi-origin credential negotiation beyond the bare-`*` rule split** — a bare-`*` origin rule answers `Access-Control-Allow-Origin: *` and omits `Allow-Credentials` (grilling Q11); concrete rules echo the origin with `Allow-Credentials: true`; no other negotiation modes.
- **CORS on the management plane** (`/metrics`) — stays outside the S3 service path / decoration.
- **Object-level CORS, CORS for ListBuckets** — S3 has none.
- **Optimistic caching of preflight decisions** (e.g. ETag'd config) — one row read per Origin-bearing request is accepted (see Risks).

## Decisions (locked 2026-09-05)

- **Preflight seam = s3s 0.15 custom route** (user Q2 = A): `CorsPreflightRoute` implementing `s3s::route::S3Route`, registered through `S3ServiceBuilder::set_route`. The alternative (intercepting in the tinio HTTP layer before the S3Service, like `/metrics`) was rejected: it would bypass s3s's path parsing/error serialization and the `/metrics` precedent is a fixed literal path, not a parsed S3 resource.
- **`is_match` gate**: OPTIONS **and** `Origin` present **and** `Access-Control-Request-Method` present. A bare OPTIONS (non-browser probe) is not a preflight and falls through to s3s's 501 — old behavior preserved (verified: signature extraction returns `Ok(None)` for unsigned requests; the auth *enforcement* happens per-operation, which custom routes bypass). Note: signature verification runs **before** route matching in `prepare`, so a signed OPTIONS with a bad signature fails before reaching the route — browsers never sign preflights, so no practical impact.
- **Preflight is always anonymous**: `check_access` overridden to `Ok(())` — browsers cannot sign preflights; the bucket's CORS config is the only authorization (matching AWS: CORS preflight is unauthenticated).
- **Bucket resolution = path-style only.** `s3s::path::parse_path_style(uri.path())` — the tinio data plane configures no virtual-hosted `S3Host`, so s3s op routing is path-style already; the preflight route is consistent with it. A parse failure → 403 (no reveal).
- **First-match semantics.** Both preflight and decoration select the **first** rule in stored order whose **origin** matches; method (and for preflight, headers) are validated **within that rule only** — a later rule is never consulted (AWS semantics; see §1). The wire codec preserves order exactly, never sorts or dedupes.
- **Preflight matching** (grilling Q6/Q11): the **first rule whose `origin` matches** (allowed-origin pattern: exact, bare `*`, or a **single** `*` wildcard — `https://*.example.net` matches `https://a.example.net` but **not** the apex `https://example.net`; pinned tinio choice — AWS docs are silent on the apex, MinIO's wildcard also excludes it); within that rule only, method must be allowed (case-insensitive exact per AWS's five values) **and** **all** requested `Access-Control-Request-Headers` must match an allowed-header pattern (case-insensitive — AWS docs silent, community-observed real S3 matches case-insensitively; `*`-wildcards; no `allowed_headers` set ⇒ no headers allowed — AWS semantics). The method/header validation is confined to the selected rule — a rule that matches origin but fails method/headers is NOT skipped for a later rule.
- **Preflight response** (allowed; grilling Q9/Q11): status 200, empty body (`Content-Length: 0`); `Access-Control-Allow-Origin: <requested origin>` echoed — **or the literal `*`** when the matched rule's origin is the bare `*` (AWS doc-confirmed) — and in the bare-`*` case `Access-Control-Allow-Credentials` is **omitted** (spec-illegal `*`+`true` combination; AWS avoids it). Otherwise: `Access-Control-Allow-Methods: <the matched rule's full method list, comma-joined>` (grilling Q9 — per AWS's current Testing-CORS samples, **not** the requested method; the old OPTIONS-object doc page saying "the method sent in the original request" is stale), `Access-Control-Allow-Headers: <requested headers, comma-joined>` (rule-filtered echo **in the request's own case/spelling** — pinned, op-review G4; omitted when the request sent none), `Access-Control-Expose-Headers: <rule's>` (when set), `Access-Control-Max-Age` (when set), `Access-Control-Allow-Credentials: true`, `Vary: Origin, Access-Control-Request-Headers, Access-Control-Request-Method` (grilling Q4; **append semantics** — an existing `Vary` from the inner response is merged, never replaced — same rule for the decorator, op-review G3). The route sets `Content-Length: 0` itself — s3s copies custom-route headers verbatim and sets nothing (op-review G4). **Header construction is fallible** (op-review S1): every value derived from request or config data (`Origin`, rule lists, echoed/exposed headers) is built via `HeaderValue::from_str`/`from_bytes` and a failure **skips that header** (the route's own inputs may instead map to a 500; the decorator just omits) — never `unwrap`/panic; combined with the put-layer control-byte rejection this is two layers against header-value injection.
- **Preflight denial** (grilling Q10): 403 with an XML error body; code **`AccessDenied`** — recorded deviation: AWS sends `AccessForbidden`, but s3s 0.15's error enum has no such code (only `AccessDenied`; same 403 status); messages **verbatim from AWS** (both variants): no CORS configuration → `"CORS is not enabled for this bucket."`; rule mismatch (disallowed origin/method/header) → `"CORSResponse: This CORS request is not allowed. This is usually because the evalution of Origin, request method / Access-Control-Request-Method or Access-Control-Request-Headers are not whitelisted by the resource's CORS spec."` (the "evalution" typo is AWS's own; emulators copy it verbatim). The response carries **no** `Access-Control-*` headers and **no** `Vary` (pinned; AWS sends `Vary: Origin` on denials — recorded deviation of the same "no CORS headers" posture). A well-formed but missing/invalid bucket → 403 with the **same message as the no-CORS-config case** — `"CORS is not enabled for this bucket."` (semantically true: a missing bucket has no CORS configuration; AWS fidelity for existing buckets preserved; the existence oracle is closed — a probe cannot distinguish "bucket exists, no CORS" from "bucket missing"); a **syntactically invalid** bucket name (bad chars, too long, malformed URI) is answered **by s3s itself with 400 `InvalidBucketName`/`InvalidURI` before the route ever matches** (op-review C1 — `ops::prepare` runs URL-decode + `AwsNameValidation` ahead of the route check; §8's 403 row is scoped to well-formed names only). The rule-mismatch message stays distinct (it can only be produced for a bucket that exists AND has CORS config — no leak). A malformed `Access-Control-Request-Method` (empty, comma-separated multi-value, non-token bytes) degrades to the 403 mismatch message — pinned, not an error of its own.
- **Decorating actual responses** (grilling Q3): in the tinio data-plane middleware (`data.rs`, after the inner S3Service call returns `Ok(resp)` — s3s encodes op errors as `Ok(Response)` bodies, so 4xx/5xx XML answers are decorated too, matching AWS). Only when the request carries an `Origin` **and** the request's method is allowed by the first origin-matching rule (`CorsConfig::rule_for` — origin **and** method; this is AWS's own documented semantics — its API doc states the method must match an `AllowedMethod` for both preflight and actual requests — earlier drafts labeling this "MinIO-style" were wrong; MinIO has no per-bucket CORS at all). Headers: `Access-Control-Allow-Origin: <origin>` (or literal `*` for a bare-`*` rule; `Allow-Credentials` omitted then), `Access-Control-Allow-Methods: <the rule's allowed methods, comma-joined>`, `Access-Control-Expose-Headers: <rule's>` (when set), `Access-Control-Allow-Credentials: true`, `Vary: Origin, Access-Control-Request-Headers, Access-Control-Request-Method`. No `Access-Control-Allow-Headers` on actual responses (AWS does not send it there — only on preflight).
- **Storage wire**: one canonical, order-preserving, percent-encoded string per configuration: `rules := rule ('&' rule)*`; `rule := methods ',' origins ',' headers ',' expose ',' id ',' max_age`; a list field's items are joined by `,` **first** and the **whole field** is then percent-encoded with **every byte outside the RFC 3986 unreserved set `[A-Za-z0-9-._~]` escaped** (`%`, `&`, `,`, and all C0/DEL bytes included), so the item-joining commas are escaped and a raw `,` in the wire is **always** the six-field separator; decode = split on raw `,` into six fields, percent-decode each, then split list fields on `,` — **review correction**: the tags `object.rs` codec escapes only `% = & + space` and thus cannot back this wire; the codec uses the full unreserved-set rule, which is also the property the ACL plan's `percent.rs` extraction must preserve — `,` inside a field item would otherwise split the 6-field record and self-heal the whole config away, op-review C2); optional fields are `''`; `max_age` is bare digits. Decode self-heals: any parse failure → empty config. **`''` = no configuration** → `get_bucket_cors` answers 404 `NoSuchCORSConfiguration`; a config with zero rules is rejected at the request layer (400), and the **storage layer additionally normalizes an empty rule set to the `''` wire** so a zero-rule config can never be stored as a non-empty-but-no-rules row (op-review G2 — the contract's "caller guarantees ≥1 rule" is defense-in-depth, not the only guard).
- **Content-MD5 on `put_bucket_cors`** (grilling Q8): required; three states per AWS — missing → 400 `InvalidRequest` `"Missing required header for this request: Content-MD5"` (verified AWS wire behavior); malformed (not 16-byte base64) → 400 `InvalidDigest`; digest *equality* against the XML body → AWS answers `BadDigest` but is **not verifiable** here (s3s's deserializer consumes the body; `S3Request` retains no raw bytes — recorded deviation, same as the ACL plan). `x-amz-sdk-checksum-algorithm`/`x-amz-checksum-*` **not** honored as an MD5 substitute (headers ignored; Content-MD5 presence still required — tinio validates nothing else). **Coordination**: the ACL plan's A7 ruling said "missing OR malformed → 400 InvalidDigest" for the put-ACL ops; when CORS lands (after ACL per grilling Q5) the shared `require_content_md5` helper takes the AWS three-state behavior and ACL's put-ACL path is aligned to it (one-line change at that merge).
- **Request validation** (400 `InvalidRequest`): ≥1 rule; ≤100 rules (`CORS_RULES_MAX`); rule ID ≤255 chars; every rule must have **≥1 `AllowedMethod` and ≥1 `AllowedOrigin`** (the dto `Vec`s are non-Option but can be EMPTY from an XML body with zero such elements — an empty method/origin list → 400; aligning with AWS); `AllowedMethod` ∈ the five values (accepted case-insensitively, stored uppercased); every allowed-origin/header pattern must contain **at most one `*`** (grilling Q6 = (b): exactly that, and nothing more — empty/odd patterns are stored and simply never match; no other format validation; AWS accepts opaque strings... **review correction 2026-09-05** — with additions: (1) every pattern/ID/**expose** value must contain **no C0 control bytes (<0x20) and no DEL (0x7f)** → 400 when violated — config values flow into response headers (`Access-Control-Expose-Headers`, `-Allow-Headers` echo), and `HeaderValue` construction rejects such bytes with `Err` — a stored poison would otherwise panic the per-connection task on every matching request (op-review S1); (2) **no list item (origin/header/expose pattern) and no rule ID may contain `,`** → 400 (`InvalidRequest`) — belt-and-braces: the wire splits list items and the six fields on raw `,`, so an unescaped `,` inside an item would split the record; origins and header names structurally cannot contain commas (F1); (3) `max_age_seconds` must be **≥ 0** → 400 when negative — a negative value breaks the digit-only wire and self-heals the *entire* config away (op-review G1; AWS rejects negatives too); (4) the **decoded config must fit a 64 KB cap** (total decoded length; `CORS_CONFIG_BYTES_MAX`) → 400 when exceeded — bounds the per-Origin-request decode/scan amplification: the put body is otherwise limited only by s3s's 20 MB XML cap and an unauthenticated writer (default plane) could store multi-MB configs scanned on every decorated/preflighted request (op-review P1).
- **No write lock** (grilling Q7): `put_bucket_cors` takes no per-bucket lock — last-writer-wins, exactly the tagging spec decision (AWS gives no config-write atomicity guarantee; `S3Backend::conditional_put_locks` is for If-Match conditional writes, unrelated).
- **Gating (double)** (grilling Q2): `cors = []` cargo feature on tinio-server (added to `default`) **and** `Capabilities.cors: bool` (config `[s3] capabilities`, default **true**, next to `tagging`). `#[cfg(feature = "cors")]` gates the three trait overrides, the preflight route registration, the decorator, and the `MetricS3` wrappers; serverside ops additionally use `Self::require_cap(self.caps.cors, "GetBucketCors")` etc. (feature off → s3s's 501 defaults; capability off → `NotImplemented "{name} is disabled"`). The e2e matrix includes a `--no-default-features` compile check.
- **Sequencing** (grilling Q5): this plan **lands after the ACL plan merges**. `expected_bucket_owner` on the three CORS inputs is **not** validated here — the ACL plan's `S3Access`/access layer becomes the single enforcement point for it once merged (CORS ops fall under its op mapping); handlers stay ignorant of it. BUCKETS baseline = ACL's post-merge 4-tuple; the CORS element appends 5th. **Interplay once the ACL plan is merged:** the three CORS config ops are resolved-but-unmapped in the ACL authorization matrix → owner-only (the matrix's default B): non-owners get 403 from the `S3Access` check, the bucket owner proceeds to the handler. The preflight route bypasses `S3Access` entirely (custom route, anonymous `check_access`) in all modes — AWS-consistent (preflight is unauthenticated).
- **Shared lookup**: `CorsConfigs<S>` over `Arc<S>` — `S3Backend` already owns `Arc<S>` internally; a `new_shared(Arc<S>)` constructor exposes the sharing so the route, the decorator, and the backend share one storage handle. The decorator's stored reference is the erased `Arc<dyn CorsLookup>`, so `DataPlaneService` stays non-generic — `CorsLookup` therefore uses **`#[async_trait]`** (the workspace's established pattern — the storage/pipeline traits and `async-trait` 0.1 already in the root Cargo.toml); a native async-fn-in-trait is NOT dyn-compatible on stable Rust (E0038) and `Arc<dyn TraitWithNativeAsyncFn>` would not compile.
- **`S3Backend::new(S, caps)` is unchanged** for existing callers (delegates to `new_shared`).
- **No CORS behavior when the capability is off**: route not registered (OPTIONS → s3s 501), decorator absent (no headers added), ops 501.

## Design

### §1 tinio-core CORS types and codec (`crates/tinio-core/src/cors.rs`)

Domain types (tinio-core stays s3s-free):

```rust
pub const CORS_RULES_MAX: usize = 100;
pub const CORS_RULE_ID_MAX: usize = 255;
pub const CORS_CONFIG_BYTES_MAX: usize = 64 * 1024; // decoded config cap (op-review P1)
pub const CORS_METHODS: [&str; 5] = ["GET", "PUT", "HEAD", "POST", "DELETE"];

pub struct CorsRule {
    pub id: Option<String>,
    pub allowed_methods: Vec<String>,
    pub allowed_origins: Vec<String>,      // pattern list: exact | "*" | "https://*.x" (single-`*`)
    pub allowed_headers: Option<Vec<String>>, // None = no headers allowed
    pub expose_headers: Option<Vec<String>>,
    pub max_age_seconds: Option<i32>,
}
impl CorsRule {
    pub fn origin_matches(&self, origin: &str) -> bool;
    pub fn method_allows(&self, method: &str) -> bool;                 // case-insensitive
    pub fn headers_allow(&self, requested: &[String]) -> bool;         // case-insensitive, `*`-patterns
}

pub struct CorsConfig { pub rules: Vec<CorsRule> }                     // Default/Clone/Debug/PartialEq/Eq
impl CorsConfig {
    pub fn to_wire(&self) -> String;                                   // order-preserving canonical wire
    pub fn from_wire(s: &str) -> Self;                               // self-heals to default
    pub fn preflight(&self, origin: &str, method: &str, requested_headers: &[String]) -> Option<PreflightMatch>;
    pub fn rule_for(&self, origin: &str, method: &str) -> Option<&CorsRule>; // decoration lookup
}
pub struct PreflightMatch { pub rule: CorsRule, pub origin: String, pub method: String, pub requested_headers: Vec<String> }
```

Matching rules: origin pattern = exact | `*` | one `*` wildcard splitting into prefix+suffix (the suffix must be non-empty and the value must exceed the two segments' length — a `https://*.example.net` pattern does not match the apex; a bare `*` matches everything). Origin match is **exact, case-sensitive string comparison** (AWS behavior — origins are compared literally; pinned). Header patterns: same single-`*` wildcard, compared case-insensitively. Methods: case-insensitive exact against the rule's list. `preflight` and `rule_for` both apply **first-origin-match semantics**: iterate rules in stored order, select the **first** rule whose `origin` matches, then validate method (and for preflight, headers) **within that rule only** — a rule that matches origin but not the method/headers does NOT fall through to a later rule (AWS: rule 1 origin-match/method-mismatch + rule 2 full-match → denied). `preflight` additionally requires all requested `Access-Control-Request-Headers` to match an allowed-header pattern within the selected rule; `rule_for` requires only origin+method (for decoration).

Wire: per Decisions — `methods ',' origins ',' headers ',' expose ',' id ',' max_age`, rules joined by `&`; a list field's items are joined by `,` **first** and the **whole field** is then percent-encoded with the unreserved-only escape set (everything outside `[A-Za-z0-9-._~]` escaped — NOT the tags five-char set), so the item-joining commas are escaped and a raw `,`/`&` in the wire is always a separator; optional fields as `''`; `max_age` as bare digits. Fields are **never** reordered, rules **never** sorted/deduped. The percent encode/decode helpers are **not** verbatim tags-wire copies — they use the unreserved-only escape set; the codec either shares the ACL plan's extracted `crate::percent` helpers if those use the same set or keeps local ones here (per the locked rule structure: six `,`-separated fields, each list's items `,`-joined and whole-field-encoded, decode = raw-`,` split → per-field percent-decode → `,`-split list fields).

### §2 tinio-store BUCKETS row extension (`crates/tinio-store/src/bucket.rs`)

- Value becomes a **5-tuple: `(created_at_nanos, tags_wire, owner_wire, acl_wire, cors_wire)`** — element appended **last**, per the sequencing decision (grilling Q5: the ACL plan lands first; the 3-tuple form is NOT a variant of this design — **review correction D1**, the earlier "3-tuple" wording contradicted the locked sequencing). Pre-existing decode paths unchanged; `STATE_VERSION` stays 1. **Correction 2026-09-06 (F1):** "decode paths unchanged" holds WITHIN the 5-tuple (element order fixed, per-wire decoders as before) — it does not extend across arities. The BUCKETS value type name is bound at the `TableDefinition`; a `meta.redb` written under the pre-CORS arity will NOT open under this definition (`TableTypeMismatch` at open — loud refusal; no migration, no historical-version support; documented recovery: delete the state dir). Rationale mirrored in the plan's Task-2 reconcile step (if the tree is somehow still the shared-store 2-tuple, that step reconciles [the code shape] before extending).
- Accessor arities adapt: `row(name)` → `Option<(SystemTime, String, String, String, String)>`; `put_full(name, created_at, tags_wire, owner_wire, acl_wire, cors_wire)`; `put(name, created_at)` writes the 5-tuple with `("", "", "", "")` for the config elements (a fresh bucket has no tags, owner, ACL, or CORS).
- `pub(crate) fn decode_cors_wire(wire: &str) -> CorsConfig` — empty/self-heal per Decisions.

### §3 Storage contract and backends

Contract (`crates/tinio-core/src/storage/bucket.rs`, next to the tagging trio):

```rust
async fn get_bucket_cors(&self, name: &bucket::Name) -> Result<Option<cors::CorsConfig>, <Self as Storage>::Error>;
async fn put_bucket_cors(&self, name: &bucket::Name, cors: &cors::CorsConfig) -> Result<(), <Self as Storage>::Error>;
async fn delete_bucket_cors(&self, name: &bucket::Name) -> Result<(), <Self as Storage>::Error>;
```

`get` → `Ok(None)` when no configuration (the `''` wire), `NoSuchBucket` for a missing bucket; `put`/`delete` → `NoSuchBucket` for a missing bucket, replace-all/clear otherwise (delete idempotent). The caller (server) guarantees ≥1 rule before `put`.

Backends: tinio-fs `bucket::Store` gains `cors(&self, name) -> Result<Option<CorsConfig>>`, `set_cors(&self, name, &CorsConfig)`, `clear_cors(&self, name)` (tag accessor pattern: read-modify-write via `put_full` — same created/tags, new/cleared CORS wire); the `BucketOps` impl methods pass through. tinio-mem mirrors with `rewrite_bucket_cors_element`. `tinio-util` conformance gains a bucket-CORS block run by both backends.

### §4 tinio-server: the three ops (`crates/tinio-server/src/backend/cors.rs`)

`op_get_bucket_cors` / `op_put_bucket_cors` / `op_delete_bucket_cors` on `S3Backend`, the tagging-ops pattern (`require_cap` → `self.bucket(req.input.bucket)` → contract call → dto out). `backend/s3.rs` adds the three thin trait forwards; `metrics.rs` adds the three `MetricS3` wrappers (`GetBucketCors`/`PutBucketCors`/`DeleteBucketCors` labels).

- `get`: `Some(config)` → `GetBucketCorsOutput { cors_rules: Some(rules_in_stored_order) }`; `None` → `s3_error!(NoSuchCORSConfiguration, "The CORS configuration does not exist")`.
- `put`: `require_content_md5` (per Decisions — missing → 400 `InvalidRequest` with the AWS message, malformed → 400 `InvalidDigest`) → `cors_config_from_dto` (validation per Decisions, 400 `InvalidRequest`) → contract `put_bucket_cors` → `PutBucketCorsOutput::default` (200).
- `delete`: contract `delete_bucket_cors` → `DeleteBucketCorsOutput::default` (204).
- dto↔core conversion helpers live here: `cors_config_from_dto(dto::CORSConfiguration) -> S3Result<CorsConfig>` (validation + uppercase-method normalization) and `cors_rules_to_dto(&CorsConfig) -> dto::CORSRules` (stored order preserved).

### §5 tinio-server: preflight route + environment wiring

`crates/tinio-server/src/backend/cors.rs` additionally hosts (the whole module is `#[cfg(feature = "cors")]`-gated):

- `CorsConfigs<S: Storage> { storage: Arc<S> }` — `get(&self, bucket: &str) -> Option<CorsConfig>` (invalid/missing bucket → `None`); implements the erased `CorsLookup` trait — `#[async_trait]` (`async fn get(&self, bucket: &str) -> Option<CorsConfig>`; native async-fn-in-trait is not dyn-compatible on stable Rust, E0038) so `DataPlaneService` stays non-generic.
- `CorsPreflightRoute<S: Storage> { configs: Arc<CorsConfigs<S>> }` implementing `s3s::route::S3Route`: `is_match` per Decisions; `check_access` → `Ok(())`; `call` parses the bucket (`s3s::path::parse_path_style`), fetches the config, runs `CorsConfig::preflight`, and builds the `S3Response<Body>` with the header set — or the 403 XML error (the two AWS-verbatim messages, `AccessDenied`).
- `bucket_from_uri(uri) -> Option<&str>` — shared by the route and the decorator.

`data.rs`: `new`/`new_with_auth` wrap the storage in `Arc<S>` once, build `S3Backend::new_shared(Arc::clone(&storage), caps)`, register `CorsPreflightRoute` only when `cfg!(feature = "cors") && caps.cors`, and thread the erased `Arc<dyn CorsLookup>` (a `#[cfg(feature = "cors")]` field on `DataPlaneService`, supplied via its `new`) through `DataPlane::from_service` (which gains a cors-gated parameter). `S3Backend::new(storage, caps)` (by value) stays as today **and delegates to `new_shared`** — `new_shared` is **UNGATED** (it exists in every build, wrapping the storage in the shared `Arc<S>` so the route, decorator, and backend share one handle); only the `CorsLookup` parameter and the cors wiring (route registration, decorator, lookup field) are `#[cfg(feature = "cors")]`, so feature-off builds keep the `DataPlane::new`/tests constructors.

### §6 tinio-server: response decoration (`data.rs`)

In `DataPlaneService::call_with_peer`: capture the request's `Origin` header and path before the inner call; on `Ok(resp)`, if `Origin` present ∧ `CorsLookup` armed ∧ the bucket parses ∧ `CorsConfig::rule_for(origin, request_method)` matches (origin AND method — AWS's own documented rule-match semantics) → insert `Access-Control-Allow-Origin` (echo, or literal `*` for a bare-`*` rule) / `-Allow-Methods` (the rule's list) / `-Expose-Headers` (when set) / `-Allow-Credentials: true` (**omitted** for the bare-`*` rule) / `Vary: Origin, Access-Control-Request-Headers, Access-Control-Request-Method` into `resp.headers_mut()`. No headers added otherwise (non-matching origin, no Origin, capability off). Decoration applies before the body wrap (CountingBody), on `Ok` responses only.

## Risks

- **Per-request row read**: every Origin-bearing request (preflight or decorated GET/PUT) reads the bucket row once — accepted at dev-local scale (tags/ACL reads are already per-request); no cache (Non-goals). The decode+scan cost is now **bounded** by the 64 KB config cap and the 100-rule limit (op-review P1 resolved at the validation layer, no cache needed).
- **Decoration is not atomic with authorization**: the decorator runs after the inner call; a config change between preflight and the actual request can make the actual response's headers stale (the preflight result is browser-cached by max-age anyway). Accepted — no new mechanism.
- **Content-MD5 digest equality unverifiable at the op** (s3s consumes the body): presence+format only; AWS's `BadDigest` path is unreachable — recorded deviation (same class as the ACL plan's).
- **`AccessForbidden` unavailable in s3s 0.15**: the preflight-denial code is `AccessDenied` (AWS sends `AccessForbidden`; same 403 status, harmless for browsers/clients that only read the status). Recorded deviation; revisit if s3s ever adds the code.
- **Wildcard semantics**: AWS documents `*`-in-origin/header patterns loosely; this design pins a concrete rule (single `*`, non-empty segments, apex excluded) and records it as tinio's to avoid silent divergence; the LocalStack-observed S3 behavior (subdomain matches) is honored, the apex case is a documented tinio choice.
- **Preflight-vs-storage race**: a preflight answered against rule N, followed by a config rewrite before the browser's actual request, decorates against newer rules — browser behavior (caches preflight by max-age) already tolerates this; accepted.
- **`set_route` is a SINGLE slot**: `S3ServiceBuilder::set_route` holds one route; any future custom route (e.g. another protocol feature) must be composed inside the same `S3Route` implementation, not registered alongside — a second feature would need to share or wrap this route. Accepted; revisited if a second custom route emerges.
