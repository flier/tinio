# Design: the shared ops engine (`tinio-ops`)

**Date**: 2026-10-03
**Status**: **landed** (2026-10-10; P4 executed on 2026-10-09/10). The crate is written and both backends are re-pointed; what the extraction found and did not close is filed in "Filed at close-out" below, and the differences from this document's own shape are these: the engine writes **43** of the inventory's 44 bodies (E2) — only the multipart completion has no engine body, its reason at the group's module doc — and the object group's two version-creating shapes are bodies of their own; the version-addressed delete is now a version-group body (`ObjectOps::delete_object_version`) and the version-creating delete's ordering (`ObjectOps::create_delete_marker`) landed beside it after close-out, leaving `tinio-pg` — its only consumer — the marker's slot write as a `tinio_version::MarkerWrite` port; `fs` takes 11 of the 12 bucket bodies, the object group's fourteen implemented bodies (`put_object` is the core trait's default over the engine's stage and commit), all 7 landed multipart bodies and 8 of the 9 version bodies, with adapter steps documented at each site; `mem` takes no version plane and no version-touching body (E16), keeps its own staged body (E8, as amended) and four documented mem-local steps; and the engine's production dependency list is `tinio-core`, `tinio-version`, `tinio-blob`, `async-trait`, `futures`, `md-5`, `tracing` and `uuid` — no backend crate. Decisions taken with the operator on 2026-10-03 (rounds 21–38 of the metadata-store contract design's question set; each is tagged). Round 38 is post-audit: an independent six-lane review found that the engine could not be written against the contracts as they stood, and its rulings — eleven added contract calls, two policy fields, a second `Hooks` method and the read-heal's home — are folded in. Round 41 (2026-10-09) amends §1: P4's first wave found that the one-value shape was unbuildable — mem has no `tinio-version` engine handle, no `BlockStore` and no `tinio-blob` dependency, and its version-creating writes are single-transaction by the P2 ruling, so a sequence of contract calls cannot express them — and the operator ruled the handles per group (E16).
**Scope**: a new workspace crate `tinio-ops` holding the S3 storage semantics shared by the backends — the operation bodies behind the `tinio-core` `Storage` categories — the `Hooks` seam a backend implements for the steps only it can take, the two per-backend policies, and the migration of `tinio-fs` and `tinio-mem` onto it with zero observable behavior change. Not touched: the `Storage` contract and its signatures, the persistence contracts (`tinio-core::meta`/`content`/`blob`), the version state machine (`tinio-version`), `list_object_versions` (backend-side, E14), the server and CLI surfaces, the sandbox crates. `tinio-pg` is the engine's third consumer and is designed separately.

## Background

Three backends are now in view — `tinio-fs`, `tinio-mem` and `tinio-pg` — and each implements the same `Storage` categories over its own persistence. Today that means the same operations are written twice (~6 200 lines under `crates/tinio-fs/src/backend/`, ~3 200 lines in `tinio-mem`'s modules) and would be written a third time. The persistence contracts remove the *storage* duplication; they do not remove the *semantics* duplication: how a `put_object` sequences a staged write, a publish, the metadata row and the version supersede; how a conditional write is evaluated; how a listing page is assembled; how a copy differs from a read-then-write.

`tinio-ops` is that second extraction. It is deliberately **not** a `Storage` implementation and **not** a framework: it is a set of operation bodies over the contracts that each backend calls from its own `Storage` implementation, plus a two-method `Hooks` seam and two policy fields.

**The audit's finding** (round 38) is the reason this spec is longer than the first draft: the phrase "the whole surface over the four contracts" was false for eleven operations. Each needed a contract call the persistence spec did not have (`stat` for cold reads and listings, `copy` for fs's zero-copy fast path, the bucket-scoped content calls, `is_empty` that sees folder-marker directories, a `prefix`-bounded `scan`, the metadata `move_` with retained parts, the retained-parts row) — those calls are now in `2026-10-03-metadata-store-contract-design.md` D23/§1, and this document assumes them.

## Goal

1. **One home for the shared operation bodies.** 44 of the 45 `Storage` operations — everything except `list_object_versions` (E14) — are written once over `Metadata`, `VersionMeta`, `ObjectContent`, `BlockStore` and the version engine.
2. **A small, honest seam for the rest.** `Hooks` has two methods: the bucket-delete action and the part-write lock guard.
3. **Two per-backend policies, declared not inferred**: what a failed metadata-row write means (E11) and whether object rows require a bucket row (E12).
4. **Backends keep their own surface.** `tinio-fs`, `tinio-mem` and `tinio-pg` keep their `Storage`, `VersionOps` and `Cleanup` implementations, their error enums and their crate APIs.
5. **Zero observable change in P4.** The migration of `tinio-fs` and `tinio-mem` onto the engine changes no S3 behavior, and the rewritten listing path is covered by a benchmark of its own.

## Non-goals

- **No `Storage` signature change.** The engine fills in the categories; it does not reshape them.
- **No `Cleanup` extraction.** The repair pipeline is backend policy over backend storage.
- **No persistence abstraction.** The engine knows the four contracts only; it never sees a table, a path or SQL.
- **No `Hooks` growth beyond two methods.** A third needs a named consumer, a spec amendment and the operator's ruling.
- **No version state machine move.** The engine calls `tinio-version`; it does not absorb it.
- **No `list_object_versions`.** It needs the backend's "what is the current object" truth plus the F01/F04 gate, which `Metadata::get` deliberately does not apply (E14).
- **No behavior redesign.** Where fs and mem disagree today on an observable detail, the migration preserves each backend's behavior; the disagreement is filed, not silently unified.

## Design

### §1 Shape

```rust
/// The two steps the engine cannot take itself.
#[async_trait]
pub trait Hooks: Send + Sync + 'static {
    /// The backend's action before a bucket's row and metadata are removed
    /// (fs: the tombstone move; mem and pg: nothing).
    async fn before_bucket_delete(&self, bucket: &bucket::Name) -> Result<(), storage::Error>;
    /// A guard held across one part's commit phase (fs: the per-upload
    /// part lock; mem and pg: a no-op guard).
    async fn lock_part(&self, bucket: &bucket::Name, upload_id: &str) -> Box<dyn Guard>;
}

/// What an operation body needs: the contracts, the hooks and the policies
/// — one receiver per group, carrying only the handles that group uses (E16).
pub struct BucketOps<M, C, H> {
    pub meta: Arc<M>,      // BucketMeta + ObjectMeta + UploadMeta
    pub content: Arc<C>,   // ObjectContent
    pub hooks: H,
    pub metadata_failure: MetadataFailure, // E11
    pub bucket_row: BucketRow,             // E12
}

/// The version plane (E16): the handles only the version-touching bodies take.
/// `mem` never builds one (no state engine, no block plane, single-transaction
/// versioned writes); `fs` and `pg` carry it.
pub struct VersionPlane<V, R, B> {
    pub versions: Arc<V>,      // tinio-version's state engine
    pub version_rows: Arc<R>,  // VersionMeta (E14)
    pub blobs: tinio_blob::Store<B>,
}

/// A body staged by `stage_body` for a later `commit_object`.
pub struct StagedBody { /* ObjectContent::Staged + key, tags, len, the running hash */ }
```

The receiver's name and field set are per group; the sketch above shows the shape, not a frozen spelling. Operation bodies are methods on their group's receiver, e.g. `buckets.create_bucket(bucket, owner, acl) -> Result<..>`; the version-touching bodies take the version plane beside it (as a second parameter or on a receiver that carries it — the group's choice). They take a `Storage` method's parameters and return its success type, minus `&self` — the `tinio-core` category signatures are the contract for every op's shape. **Every handle is a concrete type**, e.g. `VersionPlane<Versions<…>, RedbMetadata, LocalBlocks>` for fs and no plane at all for mem; a `dyn` form is impossible by construction — the category methods carry a `where Self: Metadata` clause and return `<Self as Metadata>::Error`, which makes `Metadata` non-dyn-compatible (probe A, round 40: E0038, plus E0191 for `ObjectContent::Staged`). This is the workspace's own style: `Storage` is never used as `dyn` either, so the same method pattern is safe here.

**What stays with the backend** (E5): the `Storage`/`VersionOps`/`Cleanup` trait impls; every backend-specific error variant and its projection; the `Hooks` implementation; **the locks** — the bucket-mutation lock acquired by the trait impl around the engine call, the part lock through `Hooks::lock_part` (E15); `tinio-fs`'s path mapping, atomic writer, tombstones, scanner, sweep, the streaming batch accumulator it shares with the scanner, and `list_object_versions`; `tinio-mem`'s byte limits (in its `CountingContent` decorator) and content tables; `tinio-pg`'s SQL, `list_object_versions` and `Cleanup`.

### §2 The operation bodies

| Group | Operations |
|---|---|
| bucket (12) | `create_bucket`, `delete_bucket`, `head_bucket`, `list_buckets`, the tag/CORS/ACL reads and writes |
| object (15) | `put_object`, `stage_body`, `commit_object`, `get_object`, `copy_object`, `rename_object`, `head_object`, `delete_object`, the tag/ACL pairs, `list_objects`, `list_object_parts` |
| multipart (8) | `create_multipart_upload`, `get_multipart_upload`, `upload_part`, `copy_part`, `list_parts`, `complete_multipart_upload`, `abort_multipart_upload`, `list_multipart_uploads` |
| version (9) | the versioning-state reads/writes, the version-addressed reads and deletes, the version tag/ACL pairs (`list_object_versions` is the backend's, E14) |

Which groups a backend takes is E16's: `fs` and `pg` take all four; `mem` takes the bucket group, the version-free object bodies, the multipart bodies that create no version row, and the listing — its version group and its version-creating writes stay mem-local.

The engine's obligations, each a rule the migration must not lose:

1. **Supersede before publish, row last**: when a write creates a version, the outgoing content is moved into the block plane **before** the content publish overwrites it; then the content is published, then the metadata row is written, then the current slot advances. (The first draft had the order reversed — the audit's blocker: publishing first destroys the bytes the supersede needs.) This binds the version plane's holders (fs, pg); mem's versioned write reads the outgoing bytes and writes the history row in its own single transaction, which is why it takes no version plane (E16).
2. **One contract call per atomic step**; the engine never decomposes a contract method's atomicity into several calls. The object row and its retained parts are written by `put_with_parts`; a rename moves them by `move_`.
3. **Ranges and the compare-before-remove forms** are evaluated by the engine over the rows and content (byte ranges, `list_object_parts`, `remove_if_matches`/`remove_if_tagged`). The `Storage` categories carry **no precondition parameter**, so `If-Match`/`If-None-Match` evaluation stays in the surface layer above the category — an operation body cannot answer 412 and does not try to (round 41, P4 Wave 2a: the first draft of this obligation implied a conditional-write seam the categories do not have).
4. **Streaming** (constitution V): streams pass through; the engine buffers only where the S3 semantics require it.
5. **Feature boundary**: the version group is always compiled (E1); a backend without versioning refuses through its own `#[cfg]` twin, so the engine never answers for it.
6. **Listings are content-side, enriched in one batch**: `list_objects` enumerates keys through `ObjectContent::scan(bucket, prefix, after, limit)` (the prefix bound is what keeps a prefixed page from rescanning the bucket), enriches them through **`ObjectMeta::load`** — one call per page, never a point read per key — and paginates with `tinio_core::storage::UnorderedPager`. A key whose row is absent or stale is **healed** (E13) — that is what preserves fs's cold-listing behavior, where a file the scanner has not recorded still appears with its content ETag.
7. **Reads heal, they do not refuse**: `get_object`/`head_object` compare the row against `ObjectContent::stat`; an absent or stale row is recomputed from the content and persisted (E13), so a hand-dropped file keeps being served. A conditional write never heals: it compares against the row it reads.
8. **Moves stay moves, copies stay copies**: `rename_object` calls `ObjectContent::rename` **and** `ObjectMeta::move_` (one contract call each, so the bytes and the metadata move together); `copy_object` calls `ObjectContent::copy` (fs's `copy_file_range` fast path) and writes the destination row.
9. **Buckets are content-side**: `create_bucket` calls `ObjectContent::create_bucket` then `BucketMeta::put`; `delete_bucket` checks emptiness with **`ObjectContent::is_empty` + `UploadMeta::has_uploads`** (a folder-marker directory is content, so a key-only scan would wrongly report empty), then runs `before_bucket_delete`, then drains and removes.
10. **The destructive step is the commit point**: once `before_bucket_delete` returns, the operation has happened — the drains and the row removal that follow are best-effort (a failure is logged, the operation still answers success), exactly as fs behaves today.
11. **Multipart bytes cross the content seam** through `ContentKey::Part`; the completion assembles through the content plane (read the parts, publish the object) unless the implementation's own layout offers a cheaper path, and its transaction/visibility rule is stated per backend (the pg design owns pg's).
12. **The staged body is the engine's** (E8), and `stage` is keyed (the persistence spec's D38) so a chunked store can insert before publish.
13. **The part lock spans the commit phase only** (E15): the engine streams the body into the staged value, takes `Hooks::lock_part`'s guard, publishes, writes the part row, drops the guard.
14. **The policies are read, not inferred**: a metadata-row failure follows `metadata_failure` (E11), and an object row is written guarded or not per `bucket_row` (E12).

### §3 Acceptance and testing

- **P4's acceptance is zero observable change** for `tinio-fs` and `tinio-mem`: their suites, `assert_conformance` (both legs), the `@fs` and `@mem` cucumber passes, the fs benchmarks **and a new listing benchmark** (paginated full listing over 10⁴–10⁶ entries) pass with adapter-only edits — the listing path is rewritten here, so it needs a cost pin of its own (round 38, finding on benchmarks).
- **The engine's own tests** run per operation group on the in-memory reference base (E7) plus the port-level tests for the version group.
- **`tinio-pg` is the engine's third consumer** (P5) and what validates the `Hooks` seam beyond two points; a third hook needs the operator's ruling (a non-goal).
- **Gates**: the workspace gates plus `cargo hack check --package tinio-ops --each-feature` (which, with no feature, is the default graph) and both cucumber passes.

## Risks

| Risk | Mitigation |
|---|---|
| The extraction changes fs behavior somewhere the suites do not pin | P4's acceptance is the existing suites plus both cucumber passes plus `assert_conformance` plus the listing benchmark; each subtle behavior the audit named (cold read/list heal, rename's part move, the copy fast path, the part lock's width, the folder-marker emptiness) now has a named contract call and an existing test |
| The read-heal (E13) moved fs's `ensure_row` policy into the engine and gets the composed-ETag rule subtly wrong | The rule's inputs are contract data only (the stored row + `stat`), the jitter constant moves with it, and the fs tests that pin the composed-ETag cases must stay green; if they cannot, the alternative is a per-backend policy field and a spec amendment |
| `Hooks` grows a third method | E4's non-goal makes it a ruling, and P5 is where a need would surface |
| The engine becomes a `Storage` framework by accretion | Its non-goals are explicit; the operation inventory in §2 is closed and a new operation is a `Storage` contract change first |
| The listing path's cost regresses without any test noticing | The listing benchmark is part of P4's acceptance; the engine's enrichment is a batch call (obligation 6), and `scan` carries the prefix bound (obligation 6 + the persistence spec's D23) |

### Contract gaps found and not closed

- **D2 — no bucket-existence probe on the content plane.** `ObjectContent` carries `create_bucket`/`remove_bucket`/`is_empty` and no "does this bucket exist"; `is_empty` conflates a missing namespace with an empty one (fs's maps an absent namespace to `Ok(true)`, `crates/tinio-fs/src/content.rs`), so every fs body that needs the probe keeps a one-line `ensure_bucket` pre-step of its own. A content-plane probe would retire the pre-step without touching a body's semantics.
- **D3 — no content-side bucket enumeration.** The row plane's `load_all` enumerates rows, and a bucket the API has never sighted has none (fs's pre-existing directories), so fs's `list_buckets` stayed backend-side — pinned by `pre_existing_directories_are_buckets_with_lazy_creation_time` — and only the engine's row-fed body serves `mem` and `pg`. An enumeration over the content plane is what would make the body shareable for fs.
- **D6 — no row-based emptiness call.** The contract's emptiness is content-side (`ObjectContent::is_empty`), while mem's emptiness authority is its row planes (the row IS the object): a bucket whose rows are gone while byte rows linger — the residue a failed `remove_many` leaves, the state `deleting_a_bucket_with_history_retires_every_plane` pins — would be undeletable and strand the bytes it meters, so `MemoryStorage::delete_bucket` re-asks its own rows (`rows_are_empty`) on that one refusal path and runs the hook directly (`crates/tinio-mem/src/bucket.rs`). A row-based emptiness call would retire the duplicate probe.
- **D37 — fs's row-slot writes are not expressible through the contract's `put_with_parts` + `advance_slot` pair.** This is one class with five landed instances, not five anecdotes — one of them, the restore, is now closed; the other four stand:
  - the **suspended PUT** — fixed store-side by RC1: the redb guard now admits the null identity's in-place move (`id.is_some() && seq < row.version_seq`, `crates/tinio-store-redb/src/meta/version.rs`), pinned wire-level by the suspended-PUT test in `crates/tinio-fs/src/version/tests.rs`;
  - the **suspended DELETE** — **a model decision, not a missing call** (the 2026-10-10 design's §5): fs keeps its own body (`crates/tinio-fs/src/backend/version.rs`), because the marker row it writes is a null-id **version** row that the store's one-null rule uses to displace the superseded null version's history row, and the shared conformance leg requires that history row to survive. No call closes it: the suspended DELETE's marker carries the **null identity**, and under `put_version`'s one-null rule a null-identity marker can never be a version row, so no store could accept one; and fs's model puts the marker in the object row, while the contract's `current_slot` derives the marker bit from the version row at the slot's sequence. Closing it needs a ruled model — a marker bit on the written row (every store's object-row codec), a `current_slot` read-rule change, or a marker version row for **non-null** identities only — so it is filed as the third capability ("the object-row marker"), with fs's `delete_versioned` keeping its private path.
  - the **version restore** (`delete_object_version`) — **closed**: the restore writer this filing asked for landed as `VersionMeta::restore_slot` (`crates/tinio-core/src/meta/version.rs`), whose commit is one transaction moving the slot **backwards to a real identity** — the move `advance_slot` refuses by its absolute guard, which stays untouched — together with the object row it installs, the version row and index entry it consumes and the cleared retained part list. Every implementor carries it (redb, pg — with its `is_delete_marker` slot column, folded into `sql/migrations/0001_init.sql` — and the two doubles, delegated by both adapters), it is pinned by `assert_version_conformance`'s restore leg and by redb's and pg's own suites, and fs's `restore` moved onto it with `commit_restore` and `marker_row` deleted and no test text changed (`docs/superpowers/plans/2026-10-10-version-slot-write-contract.md`, binding on `docs/superpowers/specs/2026-10-10-version-slot-write-contract.md`); the ops engine's ninth body has since **landed** as `ObjectOps::delete_object_version` (`crates/tinio-ops/src/version.rs`; consumed by `tinio-pg`, while `fs` and `mem` keep their own delete bodies, the reasons at their sites).
  - the **multipart completion** (`complete_multipart_upload`, absent from `crates/tinio-ops/src/multipart.rs`) — **the named second capability, deliberately not landed**: fs assembles file-to-file and commits the assembled object, the version branch and the consumed upload in **one** state transaction under the bucket mutation lock; mem decides the write's version outcome inside one transaction and forgives the consumed parts' bytes in the publish that lands the object. Its irreducible core is a **slot-carrying parts write** — `VersionMeta::restore_slot`'s row half with the retained parts kept instead of cleared and no version row consumed (`commit_completion`, the 2026-10-10 design's §4 sketch) — deferred because no landed site needs it (both completions are correct today) and because its home is the multipart wave's to rule with its own evidence.
  - **The engine's version-creating delete now exists — as `ObjectOps::create_delete_marker`, not the name this filing first used for it (`ObjectOps::delete_object_versioned`, not in the tree)**: the ordering (supersede, remove the bytes and the row, write the marker's slot, materialize the marker's object row) is the version group's, and the one step the engine cannot take is the slot write, because a marker is a recorded slot with **no** version row — no contract write expresses it (`put_version` writes a row, and a null-identity one displaces the key's other null row; `advance_slot` derives the bit from a row). That step is the `tinio_version::MarkerWrite` port, implemented by `tinio-pg`, the shape's only consumer. The null-id marker shape is why fs stepped back from the delete half and keeps its own `delete_versioned`.

### Accepted residuals

- **The bucket create's hardening race and its lost-update window** (RF2/RF4). The plan's "the bucket-mutation lock is held around the engine call" is unimplementable — the engine's content side takes the same non-re-entrant mutex (a deadlock, verified in Wave 1) — so the guard spans `harden_created_bucket` and its rollback only, while the create's row write is an unconditional full-row upsert **outside** it. Two consequences, both accepted: a concurrent same-name create is not serialized against the hardening, and a concurrent bucket tag/ACL element write can be lost to the upsert. Tags/ACL only, no corruption; stated at the sites (`crates/tinio-fs/src/backend/buckets.rs`). This is the one **known exception** to §3's zero-observable-change acceptance, and the run accepted it rather than restructure fs's create out of the engine.
- **The versioned record path's two-transaction split** (RI3). fs's versioned put writes `put_with_parts` (the object row and its cleared retained part list) and then `advance_slot`, because no contract call writes the object row and moves the slot; the `became_noncurrent` stamp itself is atomic with the slot move (G1: redb stamps in the slot-moving commit). Accepted cost: a crash between the two leaves a superseded version's parts uncleared — a stale retained list, never a lost object, and the repair pipeline's territory. Stated in `commit_object`'s doc (`crates/tinio-fs/src/backend/objects.rs`).
- **The copy path's `Fail` residual — served, not stranded.** The content contract carries no tagged `copy`, so a copy whose destination row write is refused under `MetadataFailure::Fail` leaves the copied bytes in place. They are **served**: the read-heal recomputes and records their row through `put_preserving`, so the object answers (the intermediate report's "an object the row plane cannot describe" overstated it). Closing the window wants a tagged copy form — or a copy answering the destination's publish identity — or a stated pg-side answer (pg's design calls the residue `Cleanup`'s).
- **The version-read cost stack.** A version-addressed read now resolves the address up to six times where the pre-engine fs read resolved once — the pre-step's `slot()`, `resolve_object_slot`, the engine's state read, the engine's `Versions::current`, `ObjectMeta::get` and the plain read's own re-resolution — plus, since F2's ruling, a label re-check after the content is served. The "never resolved twice" property fs's old doc carried is knowingly gone: part of the stack is structural (E13 gives the read-heal one home, and the version group labels what the plain read served) and part avoidable (the read arms ignore `Found::Current`'s row yet share `resolve` with the metadata bodies). Cost only, no behaviour — and **no bench covers version reads**, so a regression here would be invisible to §3's acceptance as it stands.
- **The put path's small-write cost — the filed ~2.7× was host flush latency, and the engine's own cost is ≈ +0.17 ms/put (+8–13%).** `small_write/put_1KiB` against the `pre-wave2` criterion baseline (mean 2.9015 ms, `D:\Temp\tinio-p4\bench-pre-wave2.log`) read 7.3682–8.8173 ms (**+148% … +204%** in four reproductions, all `p = 0.00`, "Performance has regressed": `D:\Temp\tinio-p4\{g3-bench,final-bench-repro,final-bench-repro-controller}.log` plus one ledger-only run). **Those readings are not a code effect.** The **pre-engine tree** (`8c491239`, extracted to `D:\Temp\base-tree`) runs the same bench, in the same target directory and TMP, at **2.4980 ms** and again at **7.0869 ms** minutes apart — criterion answering **+183.70%, p = 0.00, for a binary built from the baseline's own code** (`D:\Temp\tinio-put-profile\logs\save-basetree.log`) — and a bench this extraction cannot affect (`streaming_write/atomic_write_64MiB`, which drives `AtomicWriter` and touches no engine body) was filed at +10.8%/+21.261% while reading +4.3% in a controlled pair. A 1 KiB put performs two durable flushes (the staged content's `sync_all` and the redb `Durability::Immediate` commit) plus a directory sync, so the reading tracks the host's flush latency, which moves ~3× on a minutes timescale: the baseline and the four readings are two regimes of one host. Interleaved A/B against that same pre-engine tree puts the **engine's own added cost at ≈ +0.17 ms/put (+8–13%)**, and it is **one call** — `publish_and_record` re-stats the landed content through `ObjectContent::stat` (157–165 µs: `ensure_bucket` + `resolve_key` + `metadata` + `file_identity`) where the pre-engine path reused the `fs::metadata` its own publish had already run, plus the versioning-state point read and the per-operation plane construction (≈ 15 µs). **The mechanism first filed here was wrong on the facts**: the supersede-before-publish ordering sits behind `state.records_versions()`, this bench's bucket is unversioned, so no supersede and no `advance_slot` run, and the durable-commit count is exactly **1 per put in both trees** (counted through `FsStorage::write_lock_stats()`, not inferred); RI3's two-transaction split is not on this path either — for a version-recording bucket it would add ≈ 0.5 ms, an order of magnitude below the filed figure. Home for the real cost: `ObjectContent::publish` cannot answer the landed facts, so the write tail pays a second stat — the same gap the plan carried into P4 as "`publish` answering `Published`" (see `### Carried in from the plan, still open`), which this measurement now prices at ≈ 150 µs/put. Separate and still unbenched: the read path's own stack (a single unverified `head_object` sighting at +50%, 163 → 245 µs). Withdrawn with its correction: the plan's Task 2 Step 5 note's "+8.9% / host memory pressure" reading, and the ~2.7× framing that replaced it (`docs/superpowers/plans/2026-10-03-tinio-ops-p4.md`).
- **A criterion baseline is only comparable within its flush regime.** The benches' data root follows the shell's `TMP`/`TEMP` (`tempfile::tempdir()` in `crates/tinio-fs/benches/streaming.rs`), which on this host is `E:\Temp\tinio-tmp` — a file-backed virtual disk — so a stored baseline and a fresh run can land in different latency regimes and produce a 2–3× "regression" or "improvement" out of nothing, as the `pre-wave2` baseline did (above). The rule for the next bench-touching wave: pin the bench's data root to an explicit directory on a fixed volume, and record a flush-cost control beside each baseline (one `sync_all` micro-measurement in the same log) so a stored baseline's regime is checkable after the fact. Cost of not doing it: a false regression gets filed, argued and re-measured for a day — this run's own experience.

### Per-backend arms the engine does not unify

- **`upload_part` has two documented shapes.** The engine's body takes a refused part-row write back with `content.remove` while the guard is held (no other writer of that number can publish inside the window, so the removal is this call's own publish). mem keeps its own body because it can express what the contract cannot: a refused `PARTS` row is **restored** to the bytes the number held before this call's publish (the surviving row still describes them) — only an in-memory store can capture those bytes before publishing. The difference is the previous bytes' capture, not the refusal rule.
- **mem's four mem-local object steps** (E16's consequence, each stated in `crates/tinio-mem/src/object.rs`): `stage_body` (a version-creating commit must write the staged bytes raw inside mem's one transaction), `copy_object`'s read-then-write shape (the object cap, the marker destination and the version-creating destination), `delete_object_tags`'s clear (the identity follows the clear's own write answer, which the engine's lenient body discards) and the version-creating arms of `put_object`/`delete_object`.
- **fs's adapter steps stay fs's**, documented at their sites: the marker branch (the directory's mtime, never the engine's wall clock, D2), the unix ownership hardening around the publish, `retire_degraded_identity` ahead of the version bodies (the heal's identity rule below), and the mutation locks the trait impl holds around engine calls.
- **`FsListing`'s public surface shrank — the one deviation from Goal 4's "the backends keep … their crate APIs" (E5's "what stays with the backend" itemizes the trait impls, the error variants, the `Hooks` impl and the locks; it does not claim this surface).** The run removed `FsListing::list(params: &ListObjectsParams, records_versions: bool) -> Result<ObjectListing, Error>` — the page is the engine's `ObjectOps::list_objects`, reached through `FsStorage::list_objects` — and dropped the `meta::Store` parameter from `FsListing::new`, because the row plane is no longer the listing value's business (`crates/tinio-fs/src/listing.rs`). No consumer outside the crate used either — the workspace's only other mentions of `FsListing::list` are docs and specs — so the break is compile-visible and downstream-free; the struct's doc and the plan's Task 2 Step 4 note carry it today (`docs/superpowers/plans/2026-10-03-tinio-ops-p4.md`).

### P5 and the third consumer

- **pg's `advance_slot` carries neither of the two store rules that landed on redb**: it does not stamp `became_noncurrent` (G1) and does not admit the null identity's in-place move (RC1) — `crates/tinio-store-pg/src/meta/version.rs` still refuses `seq_value < current` unconditionally and its `advance_slot.sql` selects only the sequence. The identical wire defect (a suspended-bucket PUT that errors after taking effect) therefore exists on the pg plane: latent today (no production ops caller), real the day ops runs on pg.
- **The shared conformance leg can pin neither rule as it stands** — its suspended writes are over **fresh** keys (0 == 0) and it is shared with pg, so a leg pinning the null-identity admission or the stamping would redden pg for a rule the contract text does not require. Both rules are pinned at the redb suite only (for RC1, plus the fs wire-level test) — an intentionally unpinned contract-wide requirement, recorded as such rather than as a coverage gap.
- **pg is the version group's consumer** (P5): the ninth `VersionOps` body **landed** as `ObjectOps::delete_object_version` (its commit `VersionMeta::restore_slot`, as the 2026-10-10 plan called), and the version-creating delete's ordering landed with it as `ObjectOps::create_delete_marker`; pg implements `tinio_version::MarkerWrite` for the one step the engine cannot take (the bullet above).
- **The heal's identity obligation reaches pg.** The obligation is stated in `crates/tinio-ops/src/version.rs` ("the heal's identity rule, and what a backend owes it"): a backend whose F01/F04 gate **clears** a degraded identity must clear it **before** the engine body, or the engine's preserving heal perpetuates the retired identity into the refreshed row. fs's `retire_degraded_identity` is the worked case; **pg has no such pre-step today** and will meet the same trap on its version-addressed reads.

### Pin gaps

- **The chown success path is unpinned on Linux.** Three root-only chown tests self-skip under a uid-1000 WSL user (only the failure and unmapped paths run there), so the mapped-owner success path needs a root-side run — the leg this run did not have.
- **No end-to-end pin that an ops versioned write leaves the superseded row stamped.** The mechanism is pinned store-side (redb's suite) only; the ordering assertion that an engine-level write stamps belongs in `tinio-ops` and does not exist.
- **The both-ends copy-order discriminator is unpinned.** fs's Windows copy arm reads the source first so that a request invalid at both ends answers the source's error (`crates/tinio-fs/src/backend/multipart.rs`), but no test has both ends invalid — and the nearest test's comment still says the refusal happens "before the source is read", which its own revert made false.
- **`TestMeta::current` is a hand-rolled `CurrentRows` gate** (`crates/tinio-ops/src/testutil.rs`), so the engine's versioned bodies are never exercised against the real gate implementations (fs's and mem's); the double answers for itself and can drift from them.

### The platform lesson (a rule for the next wave)

**The WSL2 leg caught four defects every Windows gate passed** — the run's strongest evidence for `docs/tests.md`'s "the Linux leg is load-bearing" — and the final review found a fifth hole in the gate design beside them:

- a unix-gated **test left uncompilable** after the helper it called was deleted with `FsListing::list` (`crates/tinio-fs/src/listing.rs`) — a silent coverage loss on every platform until the leg failed;
- a **real regression**: the unix ownership hardening no longer reached the put path (`fs_chown_failure_after_rename_removes_file_and_errors`), fixed with an fs-side adapter step after the engine's commit — D1's sibling, found only here;
- a **clippy `-D warnings` failure on unix**: an unused `ETag` import whose only user was a `#[cfg(not(unix))]` test (`crates/tinio-fs/src/backend/multipart.rs`), invisible to `cargo check`;
- a **stripped + unix cfg hole** visible only to `cargo hack check -p tinio-fs --each-feature` **on Linux** (`crates/tinio-fs/src/backend/objects.rs`'s `object_meta` import was gated `versioning` while the unix-only record tail uses it), because `--all-targets` unifies `versioning` back on through `tinio-fs`'s self dev-dependency.
- the **`not(unix)` + stripped cell** (`versioning` off) is compiled by **no gate in the run**: `--each-feature` on Linux compiles the stripped cell with `unix`, and Windows compiles `not(unix)` with `versioning` on (every Windows leg is `--all-targets`-shaped, where `tinio-fs`'s self dev-dependency unifies the feature back on), so the `#[cfg(not(unix))]` bodies inside a stripped build (`crates/tinio-fs/src/backend/objects.rs`, `crates/tinio-fs/src/backend/multipart.rs`) went unguarded until the final reviewer compiled the cell by hand — green today (the reviewer's `cargo check -p tinio-fs --no-default-features` `--lib` and `--all-targets` plus the clippy `-D warnings` `--lib` form, log `D:\Temp\tinio-p4\final-win-stripped.log`), unguarded tomorrow.

**The rule:** run the Linux leg as the **clippy** form (`cargo clippy --all-targets -- -D warnings`) plus `cargo hack check --each-feature`, never plain `cargo check` — the third class is invisible to `check`, and the fourth is invisible to `--all-targets` on either platform. The fifth names the symmetric Windows gap: no leg builds the stripped `not(unix)` cell, so the Windows side needs a `--no-default-features` check of its own.

- **The cucumber legs are not reproducible from a clean target dir** (a precondition of the acceptance, not a defect): `tinio-e2e` owns no binary, so cargo never sets `CARGO_BIN_EXE_tinio` for it and a fresh target dir turns ~89 scenarios spuriously red — the mechanism, the fix and the counts live in `docs/tests.md`'s cross-platform gate notes.

- `fs::bucket::Store::get_or_record` is production-dead (`crates/tinio-fs/src/bucket.rs`): only its own unit test calls it; `not_recorded` stays live through `get_or_insert`, which `list_buckets` uses. Left in place as public API.
- `create_bucket_dir`'s doc warns about a caller-held-lock path (`create_bucket_dir_locked`) whose only caller is now itself (`crates/tinio-fs/src/backend/buckets.rs`).
- The engine's `list_buckets` test does not exercise the owner filter / `lazy_default` comparison it ports (`crates/tinio-ops/src/bucket.rs`); mem's level covers the rule.
- `before_bucket_delete`'s "the caller holds the bucket's mutation guard" invariant is comment-enforced only (`crates/tinio-fs/src/backend/mod.rs`, `FsHooks`).
- `VersionPlane` and `NoGuard` were published before their consumers existed — the Wave-1 freeze's deliberate cost; the consumers landed in Waves 2–3, so the surface now stands on its own.
- `mint_publish_id`'s mix is not injective (`crates/tinio-ops/src/object.rs`): `PublishId::from(sequence ^ clock)` collides for e.g. `(0, 1000)`/`(1, 1001)` and the doc over-claims uniqueness; the compensation's ETag pre-check bounds the blast radius to byte-identical content, and a plain sequence would be exact.
- The delimited bench leg's denominator understates the walked count by ~2× (`crates/tinio-ops/benches/listing.rs`: the fixture puts half the indices under `big/`, not the quarter the comment says); the pin's shape survives.
- The `Warn`/`Fail` row-write rule lives in two homes (`record_row` and the inlined copy in `publish_and_record`, `crates/tinio-ops/src/object.rs`) — the same arms today, a drift risk tomorrow.
- The multipart test comment at `crates/tinio-fs/src/backend/multipart.rs` ("A reserved destination is refused … before the source is read") contradicts the code after the guard-order revert — the source is read first.
- fs now has **two part-write paths**: the engine's body (the S3 `upload_part`) and the store's public `put_part`/`publish_part` primitives (~31 test call sites, plus `put_part_copy`'s shared commit). They take the same lock and never nest, and the store's docs say so; retiring the store-level primitive would change `tinio-fs`'s public store surface (it carries a doctest).
- The store's `advance_slot` guard wording ("within one identity") is looser than the code, which tests only the **incoming** side — unreachable through the plan's arithmetic, so the wording stands with this note.
- The version read's F2 label re-check puts a resolution on the answer path: a failure there turns a served read into an error (reachable only under a concurrent bucket/key change), and `crates/tinio-ops/src/version.rs`'s module doc is looser than the `served_identity` rule stated below it (not false in the non-racing case).
- mem serves an `Info.acl.owner` where fs does not — a documented, in-repo-unobservable served-field difference (`crates/tinio-mem/src/object.rs`).
- The four element **reads** (`get_object_tags`, `get_object_acl`, `put_object_acl`, `list_object_parts`) still discard what the version pre-step resolved, so they re-open the file and re-read the row the step already had (the write side's share of that cost was recovered on 2026-10-10); connecting them wants a `*_resolved` twin per element body, which is new public engine surface. **Operator ruling 2026-10-10: it rides P5**, which already owns the two contract-surface bundles this would land beside.

### Carried in from the plan, still open

The plan's own "Carried into P4" section handed this wave three items; the extraction did not take any of them, and they are recorded here so the hand-off is not silent.

- **A typed `put_version` conflict.** When a `put_version` meets an existing row naming a different version, the refusal still projects as `storage::Error::Io` (via `io::Error::other`) — HEAD's behaviour, with the `tracing::warn!` beside it restored in P1. Adding `storage::Error::VersionConflict` would let a caller distinguish the case by type; it needs a decided HTTP mapping at the S3 layer (500 `InternalError` is the safe default, the wire message staying generic) plus a conformance leg, so it wants a wave already touching the error surface. The pg store carries its own `VersionConflict` type (`crates/tinio-store-pg/src/error.rs`), so the two planes disagree by construction today. Nothing in the engine depends on the current projection.
- **`ObjectContent::publish` answering `Published`.** The eleven D23 calls have `publish` returning `()` (`crates/tinio-core/src/content.rs:191`), while `materialize` already builds a `PublishedBody { etag, size }` from the row it read; returning that shape would let a staged object answer what it actually left behind without re-reading the row. It changes a contract all three consumers implement, so it wants the wave that already re-treads those bodies — P5 touches pg's publish, which makes it P5's candidate. The close-out's profile round has now **priced** it: the engine's write tail re-stats the landed content through `ObjectContent::stat` **≈ 150–170 µs per put** on the fs small-write path precisely because publish cannot answer what it left behind (`D:\Temp\tinio-p4\put-profile-report.md`).
- **The fs call-site scope note.** The operator ruled on 2026-10-07 that fs's call-site migration stops at the scope P1's Task 9 Step 3 defines, so §6 item 6's stronger "no module outside the facades touches a table handle" stays unmet by design (58 `_store_redb::` lines, 99 raw open sites) — work for whichever wave takes it up, not for this one.
