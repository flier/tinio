**Date**: 2026-09-10
**Status**: draft — brainstorming + grilling 2026-09-10. ## Background

The AWS conformance review of 2026-09-10 (implementation vs the [SELECT command](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-select-sql-reference-select.html) page and its linked reference pages, plus [selecting content from objects](https://docs.aws.amazon.com/AmazonS3/latest/userguide/selecting-content-from-objects.html)) found the implemented surface faithful inside its declared scope, and four divergences. Three are defects fixed here; the fourth is a divergence the user ruled to keep. Every factual claim below was verified against the pinned `sqlparser-0.62.0` source or by probe on 2026-09-10; the ones that corrected an earlier draft of this document are marked **(corrected)**.

**A1 — the stock FROM path silently accepts clauses the engine never reads.** The validator (`sql.rs:136-286`) is a denylist over an enumerated set. Every *other* clause sqlparser 0.62 accepts is parsed and then discarded, because `QueryPlan` (`sql.rs:71-78`) carries exactly six fields — `from`, `projections`, `where_expr`, `limit`, `aggregates`, `missing` — so a clause with no field cannot reach the engine. Probe-verified as **accepted** on the stock path and rejected on the custom path: `SELECT TOP 1 s.a FROM S3Object s`, `… INTO t`, `… FETCH FIRST 1 ROWS ONLY`, `… QUALIFY s.a > 1`, `… WINDOW w AS (…)`, `… FOR UPDATE`, `… SETTINGS x = 1`, `… FORMAT CSV`. Four of them return wrong data rather than merely less data:

- `SELECT TOP 1 …` returns **every row**.
- `SELECT * EXCLUDE (a) FROM S3Object s` returns **column `a`**, the column the user asked to withhold. **(corrected)** The earlier draft placed this in `Select.exclude`; that field is in fact **always `None` under `GenericDialect`** (only `RedshiftDialect` opens `supports_select_exclude()`). The real site is `SelectItem::Wildcard(WildcardAdditionalOptions)` — the validator maps `SelectItem::Wildcard` to `Projection::Wild` (`sql.rs:241-244`) and drops the options. The behaviour claim stands; the location was wrong, and the corrected location is what the fix targets.
- `SELECT * ILIKE '%a%' FROM S3Object s` is accepted and the filter dropped.
- `FROM S3Object s SELECT s.a` (`SelectFlavor::FromFirst`) and `SELECT FROM S3Object s` (empty projection) are both accepted; the second yields a zero-column `QueryPlan`.

The two FROM paths disagreeing about one language is its own defect.

**A2 — the AWS reserved-keyword rule is not implemented.** AWS documents that an unquoted reserved keyword used as an attribute name is a 400 parse error (`SELECT s.CAST` — `s."CAST"` required). `tinio-select` has no reserved-keyword table (verified by grep). **Ruled (Q2): not implemented.** The AWS list is ~230 words including ordinary attribute names (`date`, `year`, `month`, `day`, `hour`, `minute`, `second`, `value`, `key`, `size`, `level`, `user`, `names`, `list`, `space`, `string`); enforcing it would reject queries that work today (`SELECT s.date FROM S3Object s`) for error-code parity alone. MinIO, the reference OSS implementation, documents the same non-compliance ("AWS S3's reserved keywords list is not yet respected"), so this is a shared divergence rather than a compatibility liability.

**A3 — an unknown function parses, then fails per row with a misleading message.** `SELECT LOWER(s.a) FROM S3Object s`, `COALESCE(…)`, `CAST(…)`, `CASE … END` all parse; at evaluation they hit `Error::Value("internal: unexpected aggregate call")` (`engine.rs:978`) — the text names "aggregate" for a scalar call, and it surfaces in-stream as `Custom("S3QueryError")` rather than as a request-level 400. **(corrected)** The earlier draft proposed catching these with a walk over `Expr::Function`. That cannot work for the ones that matter most: `CASE` is `Expr::Case`, `CAST` is `Expr::Cast`, `SUBSTRING`/`TRIM`/`EXTRACT`/`CEIL`/`FLOOR`/`POSITION`/`INTERVAL`/`TYPED STRING` are their own variants — none is a `Function` node. The check must therefore be an eager walk over **expression forms**, not function names.

**A4 — the parquet type mapping is not pinned to the AWS table.** `parquet.rs:239-243` ends in `other => Error::Format(…)`. AWS's Parquet table lists `DATE`, `DECIMAL`, `ENUM`, `INT(8|16|32|64)`, `LIST`, `STRING`, `TIMESTAMP`; of those, `DATE` lands in the catch-all (`arrow::Date32`/`Date64`). **(corrected)** ENUM cannot be tested, and the earlier draft's "add a test" was not implementable: arrow has no ENUM data type, so `ArrowWriter` — which is how every existing parquet test builds its input (`one_column`/`write_parquet`, `parquet.rs:516-528`) — cannot produce a Parquet `ENUM` logical type. `DECIMAL`/`LIST`/`STRING`/`TIMESTAMP` are already covered by `reads_mapped_types` (`parquet.rs:538-590`).

## Goal

1. **One acceptance surface.** Every construct the engine does not implement is rejected at request level, identically on both FROM paths, so a query can never parse and then silently do less than it says.
2. **A named rejection.** Each refused clause reports its own name through `Error::Unsupported(kind)` → 400 `S3QueryParsingError`, matching `ORDER BY`/`GROUP BY`/`HAVING` today; malformed queries use `Error::Parse`.
3. **One definition of "what we support"**, owned by the evaluator, consulted by both the parse-time walk and `eval` — drift is a single-point mistake, not a two-list divergence.
4. **The parquet type table pinned to the AWS list**, with `DATE` implemented. (`ENUM` was recorded here as unverifiable; **superseded 2026-09-11** — it is implemented for top-level columns, see A4.)
5. **A2 recorded** as a documented divergence in the FR-034 contract.

## Non-goals

- **No scalar functions.** `CAST`, `CASE`, `COALESCE`, `NULLIF`, the string functions and the date functions stay unimplemented — spec 2. This spec changes only *how their absence fails*: from a per-row internal-looking stream error to a request-level 400 naming the form.
- **No new `Value` variants.** `timestamp` and `float` are spec 2's; `Date32`/`Date64` ride the existing `Value::String` convention.
- **No ZSTD** (its own spec) and no other MinIO compression superset.
- **No reserved-keyword enforcement** (Q2), and no keyword table. In particular the expression check is **form-based**: an identifier whose *text* happens to be a keyword (`s.CAST`) stays accepted, and Q6's eval-layer pin is the guard that keeps it so.
- **No change to the custom path's factor grammar or its error text.** The custom path keeps failing closed by clause ordering; both paths end at 400.
- **No exhaustive `match` over `Expr` variants.** Q16 took the same trade-off Q6 took for the clause fields: explicit arms, a documented rule, and a per-bump audit.
- **No new FR number.** FR-034 is tightened in place.

## Design

### A1 — the acceptance surface

Three checks in the validator, all shared by both FROM paths. The checks run after the existing body/`DISTINCT`/`GROUP BY`/`HAVING` checks, so clause-shape errors report before FROM errors.

**(1) Clause fields.** Rule: **every `Select`/`Query` field the engine does not read must be at its empty/default value**, except the named exception below. Verified against `sqlparser-0.62.0/src/ast/query.rs` (`Select`: 24 fields, query.rs:446-509; `Query`: 10 fields, query.rs:40-69 — the table below plus this paragraph is the complete inventory); the ones the engine *does* read are `Select.projection`/`from`/`selection`/`distinct`/`group_by`/`having` (the last three already rejected above this check) and `Query.with`/`body`/`order_by`/`limit_clause` (the first and third already rejected).

| Where | Field | Reported as |
|---|---|---|
| `Select` | `top`, `top_before_distinct` | `TOP` |
| `Select` | `into` | `INTO` |
| `Select` | `qualify` | `QUALIFY` |
| `Select` | `named_window` | `WINDOW` |
| `Select` | `lateral_views` | `LATERAL VIEW` |
| `Select` | `prewhere` | `PREWHERE` |
| `Select` | `connect_by`, `cluster_by`, `distribute_by`, `sort_by` | `CONNECT BY`, `CLUSTER BY`, `DISTRIBUTE BY`, `SORT BY` |
| `Query` | `fetch` | `FETCH` |
| `Query` | `locks` | `FOR UPDATE` |
| `Query` | `for_clause` | `FOR` **(amended 2026-09-11)** — MSSQL's `FOR XML`/`FOR JSON`/`FOR BROWSE` are not the lock clause, so each field reports its own name |
| `Query` | `settings` | `SETTINGS` |
| `Query` | `format_clause` | `FORMAT` |
| `Query` | `pipe_operators` | `PIPE` |

**The two remaining fields complete the 24-field `Select` inventory (added in review).** The table above covers 11, the engine reads 6, three are dead (below), plus `optimizer_hints` and `flavor` — 22. The last two:

- `window_before_qualify: bool` (query.rs:504) is asserted **`== false`**, reported as `WINDOW`. **(corrected in review)** It is set to `true` whenever a `WINDOW` clause is parsed — with or without a following `QUALIFY` (parser/mod.rs:14848-14869, a block with no dialect gate at all, which is also why the QUALIFY probe parses under `GenericDialect`) — i.e. exactly when `named_window` is non-empty, which the table rejects on its own row above. So this arm is unreachable today and exists as defence-in-depth: if a future spec ever admits `WINDOW`/`QUALIFY`, the field is already accounted for rather than silently dropped.
- `select_token: AttachedToken` (query.rs:448) is pure token bookkeeping with no semantic content — **exempt** from the empty/default rule, and listed here so the per-bump audit does not rediscover it.

**`flavor` is not on that list because it is not an `Option`.** **(corrected)** It is a plain enum, always set, and an "is empty" test would reject every query. It is instead asserted **`== SelectFlavor::Standard`**, and the assertion is load-bearing in two ways: it rejects `SelectFlavor::FromFirst` (`FROM S3Object s SELECT s.a`) and `SelectFlavor::FromFirstNoSelect` (a bare `FROM S3Object s`, which parses to a `Select` with an empty projection) — both reachable because `GenericDialect::supports_from_first_select()` is `true` (`generic.rs:148-150`). Reported as `FROM-first SELECT`.

**Named exception — `optimizer_hints` (Q12).** `GenericDialect::supports_comment_optimizer_hint()` is `true` (`generic.rs:288-290`), so `SELECT /*+ hint */ * FROM S3Object s` populates the field. It is **accepted and ignored**: a hint is advisory by definition, so dropping it *is* the correct semantic, and rejecting would 400 a semantically ordinary query. This is the one field in the table that is deliberately not read.

Three more fields are **checked** but **dead under `GenericDialect`** — kept in the check as future-proofing, documented as such: `Select.exclude` (Redshift-only gate), `select_modifiers` (trait default `false`), `value_table_mode` (BigQuery-only gate).

**(2) Wildcard additional options (Q10).** `SelectItem::Wildcard` carries a `WildcardAdditionalOptions` (`query.rs:924-949`) that the projection mapping drops. **(corrected)** The struct has **seven** fields, not six: the first is `wildcard_token: AttachedToken` (query.rs:930), token bookkeeping; and its `Default` is a **manual impl** (query.rs:951-963), not a derive, whose `wildcard_token` defaults to a `Mul` token — so whole-struct equality against `Default` never holds for a parsed wildcard, and no test may rely on it. The rejection is instead **per option, by name**, for the five options `GenericDialect` can actually produce (`generic.rs`: `supports_select_wildcard_ilike` :244, `_exclude` :224, `_except` :100, `_replace` :240, `_rename` :248 — all `true`):

| Option | Syntax | Reported as |
|---|---|---|
| `opt_ilike` | `SELECT * ILIKE '%x%'` | `ILIKE` |
| `opt_exclude` | `SELECT * EXCLUDE (a)` | `EXCLUDE` |
| `opt_except` | `SELECT * EXCEPT (a)` | `EXCEPT` |
| `opt_replace` | `SELECT * REPLACE (x AS y)` | `REPLACE` |
| `opt_rename` | `SELECT * RENAME (x AS y)` | `RENAME` |

`opt_alias` is **not** listed: `GenericDialect` does not override `supports_select_wildcard_with_alias`, so it is always `None` — a dead field. `QualifiedWildcard` carries the same struct but `s.*` is already rejected wholesale as `qualified wildcard`, so its options need no names.

**(checked, not assumed)** The options can also appear in a *function argument* (`FunctionArgExpr::WildcardWithOptions`, constructed at `parser/mod.rs:18312` from the block at `18302-18316`; `WildcardWithOptions` occurs nowhere else in that file), which would have been a third silent-drop site. Probe: `SELECT count(* EXCLUDE (a)) FROM S3Object s` → rejected by `validate_aggregate_item` ("non-aggregate expression in aggregate select list"), and every non-aggregate function is rejected by A3's allowlist. The position is closed by existing checks; **no third site is added**.

**(3) Empty projection (Q17).** `GenericDialect::supports_empty_projections()` is `true` (`generic.rs:184-186`), so `SELECT FROM S3Object s` parses with `flavor: Standard` and `projection: vec![]` — the flavor assertion does not catch it. Probe-verified as accepted today, yielding a zero-column `QueryPlan`. Rejected as **`Error::Parse("empty projection")`**, not `Unsupported`: this is a query that does not say what it wants, not a clause we have declined to implement, and `Unsupported` already carries the latter meaning in this design.

Channel for (1) and (2): `Error::Unsupported("<NAME>")`, unchanged — the server already maps both `Error::Parse` and `Error::Unsupported` to 400 `S3QueryParsingError` in `query_parsing_error` (`crates/tinio-server/src/backend/select.rs:228-236`, called at `select.rs:416`), by destructuring the inner message — which drops the `"S3 select: "` Display prefix for these two variants (other variants keep it; there is no strip step). No new error variant, no server change.

Both paths: the custom skeleton constructs its `Select` with these fields at their defaults and its projection through the same stock `parse_projection`, so the clause-field check is a no-op there **while the wildcard check is not** — **(corrected)** the earlier draft called the whole check a no-op on the custom path; probe shows `SELECT * EXCLUDE (a) FROM S3Object[*] s` is accepted there too, because the skeleton ingests the options with the projection. Both paths reject after this change.

### A3 — the function allowlist and the shared support predicate

**Two tables, not one (Q1).** `is_aggregate_name` (`sql.rs:367-374`) is the *aggregate* predicate — `contains_aggregate` uses it to decide aggregate mode, which governs whether `*` is allowed and whether the scan-accumulate path runs. It must never grow scalar names, or `SELECT LOWER(s.a) FROM S3Object s` would be classified as an aggregate query and take the wrong execution path. The allowlist is a separate `is_allowed_function` — **(Q8, grilling 2026-09-10)** it lives in `engine.rs` beside the predicate that consults it, not in `sql.rs`: two functions with two purposes, but one file, so the walk cannot end up checking a different list than the predicate does. In this spec it is exactly the aggregate set; the library spec appends scalar names to it alone, and never touches the aggregate predicate. `is_aggregate_name` keeps its `&ObjectName` signature (`sql.rs:367`) and is called with the `ObjectName` directly — no `&str` round trip.

**The shared predicate (Q7, Q14, Q15, Q16).** A new item in `engine.rs`, `unsupported_form(&Expr, missing_name: &str) -> Option<UnsupportedForm>` — `Some(..)` when the evaluator cannot evaluate that expression form, `None` when it can. (The sentinel name is a parameter — the predicate admits the request's own sentinel without reaching into `sql.rs`.) **(corrected)** The return type is an enum, not `&'static str` as the earlier draft had it: function names are dynamic and do not fit a static string, which contradicted the draft's own diagnostics.

```rust
enum UnsupportedForm {
    /// A dedicated Expr variant the evaluator does not implement. `Cow`
    /// borrows for a form with a fixed name ("CASE") and owns the rendered
    /// text otherwise.
    Expression(Cow<'static, str>),
    /// An Expr::Function whose name is not on the allowlist (dynamic name).
    Function(String),
    /// A literal whose *kind* the converter has no mapping for (`X'…'`,
    /// `N'…'`, `$$…$$`) — the converter's rendered text, `Unsupported`.
    Literal(String),
    /// A statically decidable operand defect: a numeric literal outside the
    /// decimal model (`1e999`, a 29-digit literal) or a bad `ESCAPE`.
    /// `Parse`, the "LIMIT must be a positive integer" precedent.
    Malformed(String),
}
```

`Literal`/`Malformed` are the **(added in review)** conformance pass: the walk had judged the *shape* of `Value`/`Like` supported and left the payload to the evaluator, so `SELECT X'41' …`, `SELECT 1e999 …` and `… LIKE 'x%' ESCAPE 'ab'` all parsed, streamed, and failed per row in-stream — the A3 hole in miniature. The predicate now runs the evaluator's own `literal`/`like_escape` and keeps their verdict and text; only the channel is the walk's.

Two 0.62 shape notes the implementer needs: `TRY_CAST`/`SAFE_CAST` are not their own `Expr` variants — they are `CastKind`s, matched inside the `Cast` arm (`CastKind` has exactly four variants and no `Display`, so match it exhaustively); and an unnamed-variant fallback returns `Expression(Cow::Owned(rendered))`, where `rendered` bounds the text and replaces the request's sentinel name with `IS MISSING` (see Diagnostics).

Its `Display` produces the two diagnostic shapes below (`unsupported expression: CASE` / `unsupported function: LOWER`, plus the operand verdicts' own messages verbatim), so parse-time and runtime messages cannot drift apart. It is the single definition of what we support:

- `eval`'s catch-all arms (`engine.rs:988` and the operator catch-alls) stop formatting `other.to_string()` and call it instead, so the runtime diagnostic and the parse-time rejection come from one place. **(added in review)** If a catch-all ever meets a form the predicate calls *supported* (`None`) — the drift case — it keeps a generic internal error; that path is a bug the parity corpus exists to catch, not a user-facing diagnostic.
- The validator's eager walk consults the same predicate: a declined form becomes request-level `Unsupported`, a malformed operand request-level `Parse`. **Walk entry points (added in review): every `Expr` the plan carries** — each projection expression, `where_expr`, and every aggregate argument expression — so nothing the engine can later evaluate goes unwalked.
- The two traversals genuinely differ and cannot be merged: `eval` is **lazy** (`AND`/`OR` short-circuit, only evaluated rows are walked) while the validator must walk the whole tree eagerly. What is shared is the per-node classification, not the traversal.

Q16 chose this over an exhaustive `match` over `Expr` variants on the same grounds Q6 chose explicit arms for the clause fields: the residual failure mode is a *single-point* mistake that fails closed (a form the predicate rejects but `eval` supports → we refuse a query we could run) rather than the A1 failure mode (accept and silently drop).

**Form-based, never text-based (Q8).** The predicate switches on the `Expr` **variant**; identifiers are never judged by their text. `SELECT s.CAST FROM S3Object s` must stay accepted — the identifier's value is `CAST`, but the expression form is a compound identifier, which is supported. A2's eval-layer pin is the guard.

**The sentinel exception.** The dialect's `parse_infix` hook rewrites every `X IS [NOT] MISSING` into a `Function` node named `__s3_is_missing_<uuid>` (`dialect.rs:522-577`), minted per request and carried on `QueryPlan.missing`. The walk sees those nodes; failing to admit the request's own sentinel name turns every `IS MISSING` query into a 400. The check admits `plan.missing.is_missing()` explicitly, by the same single-part-unquoted shape test the engine already uses (`is_sentinel_call`).

**Diagnostics.** Rejections report the form, not the expression text: `Unsupported("unsupported expression: CASE")`, `Unsupported("unsupported function: LOWER")`; the operand classes report the evaluator's own message (`X'41'`, `invalid numeric value: 1e999`, `ESCAPE must be a single character`). Note this changes the **runtime** in-stream `S3QueryError` detail for named forms — including the deleted `ILIKE` arm and `eval_like`'s `LIKE ANY` refusal, which route through the predicate. **(added in review)** An unnamed variant echoes its rendered SQL, so that echo is bounded to 256 chars (an appended `...` marks the cut) and the request's sentinel name is replaced by the `IS MISSING` the user wrote: a rendered subtree can contain the sentinel (the dialect rewrites `X IS MISSING` wherever it appears), and the client has no business seeing the evaluator's per-request synthetic name. Accepted as part of Q16.

### A4 — the parquet type table

Add `DataType::Date32` and `DataType::Date64` arms to `arrow_value` (`parquet.rs:187-245`; the catch-all is 239-243), producing an **RFC 3339 midnight-UTC string** (`2010-01-01T00:00:00Z`) — not `YYYY-MM-DD` (Q4). Rationale: AWS maps Parquet `DATE` to the `timestamp` type, so "midnight of that day" is the honest reading; and the existing `Timestamp` arm already emits RFC 3339 via `timestamp_string` (`parquet.rs:226-234`), so one shape keeps DATE and TIMESTAMP comparable on the service's string spine until spec 2 introduces a real timestamp type. `Date32` is days since the Unix epoch, `Date64` milliseconds. Conversion reuses the `time`-crate path `timestamp_string` already uses (`parquet.rs:369-380`; `time` is already a direct dependency with the `formatting` feature) — no new dependency. **(added in review)** `Date64`'s "time-of-day bits are ignored" is a rule the arm must enforce, not a property it may assume: the milliseconds are **floored to the day** before conversion, so a non-midnight value still yields that day's midnight rather than leaking a time-of-day the type disclaims. Tests cover a pre-epoch negative `Date32` and a non-midnight `Date64`. **(corrected in review)** Out-of-range values surface as `Error::Format`, never a panic or wrap — one such case is pinned in the test table — and the binding bound is `time`'s own date span (±9999 years), not a narrower one: the day count is converted to a **whole-day offset in seconds**, because an i64 *nanosecond* intermediate caps the range at ±292 years of the epoch and would fail a legal DATE past 2262-04-11. `Date64`'s millisecond count divides to days before scaling, so it cannot overflow the second conversion; a date RFC 3339 cannot spell at all (a negative year) is a `Format` error too. **(added in review)** `dates_past_2262_still_read` pins the widened range with calendar-derived day counts.

**(corrected 2026-09-11 — this supersedes the 2026-09-10 ruling) `ENUM` is mapped at the top level, refused elsewhere.** Two corrections landed on this one fact. The 2026-09-10 review rightly killed the original claim (here and in the plan's Task 5/6 notes) that arrow-rs reads a Parquet `ENUM` as `Utf8`: `parquet` 59.3.0 maps `LogicalType::Enum` and `ConvertedType::ENUM` alike to `DataType::Binary` (`src/arrow/schema/primitive.rs:281`, `:288`), the same type it gives an unannotated `BYTE_ARRAY`, so the annotation is unrecoverable from the *decoded arrow array* and the catch-all refusal as `Format("parquet type not supported: Binary")` — the fact `unsupported_type_errors` already pinned for a `Binary` array — was the honest reading of that fact at that time. It is not the whole fact: the annotation survives in the *parquet schema*, which the reader still holds while building. `ParquetReader::new` therefore captures the annotated top-level root field names there (`enum_columns`) and reads those columns as strings, which is AWS's own mapping. The hint is per *name* and only when every top-level root field of that name is annotated — a duplicate name pairing an ENUM with an unannotated `Binary` drops the hint for both, so neither is silently re-typed. Two boundaries stay refusals: a nested `ENUM` (under a list or struct) has no top-level root field to resolve a hint against and keeps the `Binary` catch-all, and an ENUM cell that is not valid UTF-8 answers `Format("parquet enum is not valid UTF-8: …")` rather than a lossily repaired string. `Dictionary` keeps the catch-all, with a test asserting `Error::Format` — it is a different thing from a Parquet ENUM, no evidence suggests real load hits it, and a `Format` error is a safe failure.

New test table, one case per AWS-listed type: `DATE` (new), `INT(8|16)` (new — `Int8`/`Int16` are already mapped but untested), and the existing `DECIMAL`/`LIST`/`STRING`/`TIMESTAMP` cases folded in so the AWS table reads as one list, plus the `Dictionary`/unsupported-type assertions and (2026-09-11) the `ENUM` cases. **(fact)** These tests live behind `#[cfg(feature = "parquet")]`, so they only compile under `cargo test -p tinio-select --features parquet` — the plan's verification steps must pass the feature explicitly, or the new tests silently never run. **(closed 2026-09-11)** That exposure is gone: `select-parquet` is off in every default graph and the feature-matrix job only cargo-hack *checks* tinio-server, so nothing ran the reader — there is now a `test-parquet` CI leg (`cargo nextest run -p tinio-select --features parquet` and `-p tinio-server --features select-parquet`, plus `cargo test -p tinio-e2e --features parquet --test cucumber -- --tags '@parquet'`). The same leg runs the committed-fixture integration test (`crates/tinio-select/tests/parquet.rs`: one plain-table `.parquet` file, `include_bytes!`-ed by tinio-select's integration test, tinio-server's parquet select test and the `@parquet` cucumber step, regenerated by the ignored test in that file) — the `@parquet` tag is excluded by the runner's default filter, so the default cucumber passes are untouched.

## Conformance-review follow-up (2026-09-10, second pass)

A review of the shipped implementation against this design and the plan found the acceptance surface still open in one direction — the operand-carrying forms (`Value`, `Like`) were judged by *shape*, so their payloads stayed a per-row failure — plus one stale fact and one range bug. Rulings taken with the user and implemented with the review:

- **The operand classes are closed at request level, not parked.** The literal-kind residue this design had parked (`X'…'`, `N'…'`, `$$…$$`) is closed together with the two classes the design had not named at all: an `ESCAPE` operand that is not exactly one character, and a numeric literal outside the decimal model (`1e999`, a 29-digit literal). All three now answer 400 before streaming, on the channels above, carrying the evaluator's own message — the walk runs the evaluator's own `literal`/`like_escape` instead of a second implementation, which is what keeps the layers in step. The runtime arms stay as backstops and are driven by hand-built plans, because `parse` can no longer reach them.
- **Diagnostics are scrubbed and bounded** — see Diagnostics above.
- **`Date32`/`Date64` convert through a whole-day offset in seconds**, so the bound is `time`'s ±9999 years rather than ±292 — see A4.
- **The ENUM fact is corrected** — see A4. `parquet` 59.3.0 maps it to `Binary`, so it is refused; the plan's Task 5 Step 4 / Task 6 Step 3 instruction and this document's earlier text are corrected in place rather than left to mislead the next reader. **(superseded 2026-09-11)** The refusal was the right ruling while the annotation was believed unrecoverable, and it is not: the parquet schema carries it, so a top-level `ENUM` now reads as a string (see A4), while a nested ENUM, a non-UTF-8 ENUM cell and a duplicate name mixing ENUM with an unannotated `Binary` stay refused. ## Risks

- **Over-rejection.** The rule is safe only because every listed field is non-AWS syntax; the failure mode is listing a field a *supported* construct also sets. The verified 0.62 field list makes the dangerous pairs separable and they were checked: `ORDER BY` lives on `Query.order_by` while `Select.sort_by` is Spark `SORT BY`; `Select.distinct` is separate from `select_modifiers`. The cross-path corpus and the untouched existing corpus are the standing guard.
- **The `flavor` assertion** would reject every query if written as an emptiness test — the single highest-consequence line in A1. It gets its own acceptances (ordinary `SELECT … FROM S3Object s` shapes) alongside the `FROM`-first rejections.
- **The sentinel exception** is the most likely line to be written wrong in A3, and its failure mode is every `IS MISSING` query 400ing. Dedicated acceptances, not incidental coverage.
- **`engine.rs` is now in scope**, and `eval`'s catch-alls are edited in the one place where correctness is currently guaranteed. The edit is narrow (the arms delegate to a predicate instead of formatting text), and the 284-test corpus plus the parity corpus cover it — but this is the riskiest hunk in the spec, and it is a direct consequence of Q14/Q15.
- **Runtime message change.** The in-stream `S3QueryError` detail for unsupported forms changes to the predicate's shapes (`unsupported expression: CASE`, `unsupported function: LOWER`), and **(added in review)** an unnamed variant's rendered echo is bounded to 256 chars (an appended `...` marks the cut) with the request's sentinel name replaced by `IS MISSING`. This covers the dedicated `ILIKE` arm (deleted) and `eval_like`'s `LIKE ANY` refusal (pre-empted by a predicate-routed arm), so parse time and runtime name a form identically. No test pins the old texts; callers that matched on them would notice.
- **(added in review) The one residue the walk cannot close: `B'…'` / `R'…'`.** They are not literals in this grammar at all — `GenericDialect`'s lexer does not recognize the byte/raw string prefixes, so `SELECT B'1' FROM S3Object s` parses as the identifier `B` with the alias `1` and evaluates to MISSING, silently. Closing that means teaching the lexer, i.e. `dialect.rs`, which this spec keeps out of scope; it is recorded in the FR-034 contract as a silent divergence instead. **(closed 2026-09-11)** — not by teaching the lexer a new token: `S3SelectDialect::dialect()` now reports `GenericDialect`'s `TypeId`, so the tokenizer's own `dialect_of!` gates read true and `B'…'`/`R'…'` tokenize as the literals they are, which the operand check refuses by name (`unsupported: B'1'`). The same flip closed `b'…'`, `B"…"`/`R"…"`, `R'''…'''` and the `CURRENT_USER`/`CURRENT_CATALOG`/`SESSION_USER` bare keywords — all previously accepted and evaluated to MISSING — and the FR-034 contract records the closure. The `LIKE` DP cell cap is the other in-stream `Value` error on this surface and is deliberately data-dependent (pattern × record size), not an operand defect.
- **sqlparser 0.62 field drift.** The tables name fields of a pinned version (Q6/Q16 chose explicit arms over compiler-enforced exhaustiveness, accepting a per-bump audit). The rule is the contract; the tables are its 0.62 instantiation.
- **The e2e leg is shared-both-backends.** `select.feature` deliberately carries no backend tags, so the new scenario runs on both legs or neither — no new tag.
