# Design: S3 object versioning on a content-addressed history store

**Date**: 2026-10-03
**Status**: draft — the design tree was grilled to an empty frontier on 2026-10-03; every decision below is the operator's, and the last open fact (the `Allow` header on the delete-marker `405`) was settled the same day by implementation evidence: **none is sent**. This document owns the new facts none of them has: the storage model, the version state machine, the block-store contract, and the gating model.

## Background

tinio's fs backend is a **mirror**: one object is one plain file at its key path, and the served directory is the system of record in both directions — an object written through the API appears as a file, and a file dropped into the tree out of band is served (SC-006). The metadata row for an object lives in the `object_meta` table keyed `(bucket, key)` (`crates/tinio-store/src/meta.rs:42-43`), carrying `(etag, size, mtime, file identity, tags, checksum, owner, acl)` (`:54-79`); its staleness gate exists precisely because the file can change without the API's involvement.

S3 versioning requires the opposite guarantee for everything except the newest version: once superseded, a version's bytes must remain retrievable and immutable. The mirror's atomic rename (`crates/tinio-fs/src/write.rs:208-213`) overwrites the previous content, so today a superseded version is simply gone. Nothing in the workspace models a version: there is no `version_id` field anywhere, no version tables, no delete markers, and the only `version_id` occurrences in `tinio-server` are DTO response fields hard-coded to `None` (`crates/tinio-server/src/backend/objects.rs:176`, `:880`). The project's own coverage gap analysis records versioning as "the only original Tier-A row still open" (`docs/superpowers/specs/2026-09-04-s3s-api-coverage-gap-analysis.md:22`).

The protocol layer is ready. `s3s` 0.17 already generates the whole surface — `get_bucket_versioning` / `put_bucket_versioning` (`src/access/generated.rs:424`, `:770`) and `list_object_versions` (`:590`) among the operations, and `version_id` on the `GetObject`/`HeadObject`/`DeleteObject`/`CopyObject`/`UploadPartCopy`/`ListObjectVersions` DTOs — and a `S3` implementation that does not override them answers `NotImplemented` through the trait defaults, which is what tinio does today.

## Goal

1. **S3 versioning semantics, per AWS**: the three bucket states (unversioned, versioning-enabled, versioning-suspended), unique version IDs, `null` versions, delete markers with their status-code rules, `ListObjectVersions`, and the `x-amz-version-id` / `x-amz-delete-marker` response headers.
2. **A content-addressed history store under the mirror**: the current version stays a plain file at the key path (the mirror contract and the fast read path are untouched); each superseded version is stored as a version record pointing at a blob hash, and the blob is stored as content-addressed blocks, deduplicated within the bucket — behind a **backend-agnostic block-store contract**, so a future WebDAV or FTP backend implements block I/O for its transport and inherits the identical versioning, dedup and GC behavior instead of re-inventing it. The history is readable in **read-only mode** too.
3. **Three levels of control**: a compile-time cargo feature, a runtime `[s3] versioning` capability toggle, and the per-bucket S3 state — so a build that does not need versioning does not carry it, a server that does not enable it refuses its operations the way every other disabled capability is refused, and a bucket that does not enable it keeps today's behavior exactly.
4. **Bounded disk**: explicit version deletion (`DeleteObject?versionId`, `DeleteObjects`) plus a configurable retention policy for noncurrent versions; unreferenced blocks are reclaimed by a sweep.

## Non-goals

- **MFA delete's protection.** A local server has no MFA device, so a request that asks for it is refused outright (see **The version model**) rather than accepted-and-ignored — a false protection is worse than an error.
- **Object Lock, retention modes, legal holds.** Out of scope; a later design may layer them on the version model.
- **The S3 Lifecycle API** (`PutBucketLifecycleConfiguration` and its rule engine). Retention is a config key applied by the existing sweep, not a new protocol subsystem; a later design can translate lifecycle rules into it.
- **Cross-bucket deduplication.** Block stores are per-bucket (see **The storage model**), so no cross-bucket content inference exists and a bucket deletion is self-contained.
- **Versioning the unversioned path.** A bucket that has never enabled versioning keeps the mirror's semantics byte for byte, including the out-of-band behaviors.
- **Versioning of folder markers** (keys ending in `/`), decided 2026-10-03: they are directories in the mirror, stay outside the version model, and the limitation is documented rather than papered over (see **The version model**).
- **A versioning backend.** The versioning lives in `tinio-fs`; `crates/tinio-blob` is a library the fs backend consumes, not a `Storage` implementation. The block-store contract is deliberately shaped for other backends (see **The block store**), but no WebDAV, FTP or S3 backend is written or changed here.

## The storage model

**The current version is a file; the history is content-addressed.** For a bucket in the enabled or suspended state:

- The **current version** is the plain file at `<root>/<bucket>/<key>`, written by the existing temp + atomic-rename path, with the existing `object_meta` row extended by the version identity (see **Metadata schema**). Reads of the current version do not change.
- Every **superseded version** is a row in a new version index keyed by `(bucket, key, version_id)` — or by the equivalent ordered key — carrying the version's `blob hash`, size, ETag, timestamps, and its per-version metadata; plus a `kind` discriminator for object versions and delete markers.
- A **blob** is identified by the hash of its content and described by an ordered **block list** stored beside the version row. In v1 the list holds exactly one block — the abstraction is kept so that splitting a blob into chunks later is a policy change rather than a format migration (see **The block store**). A blob is never stored as a bare file with no record of what it is.
- **Blocks** live in the bucket's own store under the state dir, `<state-dir>/blobs/<bucket>/<prefix>/<block-hash>` — decided with the operator on 2026-10-03 — so that a bucket deletion drops the subtree the way it drops `multipart/<bucket>/` today (`specs/001-s3-local-server/fs-backend.md` §8.1) and nothing outside the bucket is ever referenced. The alternative (a reserved `.tinio/` segment inside each bucket directory) was rejected because it collides with the existing rule that any-depth bucket `.tinio/` content is private residue to be cleared, and because it mixes payload into the served tree.

**The move, and the materialize.** Two symmetric operations carry content between the two representations:

- **Move (supersede)**: when a write publishes a new current version over an existing one, the outgoing file's content enters the block store as a blob — hashed and deduplicated against the blobs already present in that bucket (in v1 a blob is one block, so this is a whole-content lookup) — and the version row is committed before the new content is published at the key path. The published file is not itself in the block store: the current version is stored exactly once.
- **Materialize (restore)**: when a version must become current again — a delete marker is deleted, or the current version itself is permanently deleted — its blocks are reassembled into the key path through the existing temp + rename path. This is the only path that turns history back into a file.

Both operations are I/O-bound and streaming; neither buffers an object whole (constitution V).

**The supersede race.** The outgoing file is read, hashed and stored while an out-of-band writer could be rewriting it. If the content no longer matches the file identity the metadata row recorded (size / mtime / file identity — the same staleness gate reads use), the write **fails** (one retry, then an error naming the concurrent modification) rather than committing bytes whose provenance is unknown: what lands in history must be the version that was actually current, not a half-written stranger.

**What is deliberately not stored.** The current version is not duplicated into the block store, so a never-superseded object costs exactly what it costs today. The price is that the current version participates in no deduplication, and an out-of-band edit to it has no version history to fall back on; both are consequences of keeping the mirror authoritative and are recorded under **Risks**.

## The version model (S3 semantics)

**Bucket states.** `Unversioned` (the default; today's behavior), `VersioningEnabled`, `VersioningSuspended`, set and read by `PutBucketVersioning` / `GetBucketVersioning` and persisted per bucket. The state applies to all objects in a bucket; a versioning-enabled bucket can be suspended but never returns to unversioned.

**Version IDs.** Every version of an object in an enabled bucket gets a unique, opaque, URL-safe ID. Ordering for `ListObjectVersions` (newest first) comes from a monotonic per-object sequence carried by the version row, never from the ID's own shape — and the prior art shows why this split is the cheaper one long-term: MinIO's random UUID is free to change format because its ordering key is a stored `ModTime`, whereas the systems that made the ID sortable (Swift, SeaweedFS) did so because it doubles as the on-disk name and the listing key, and SeaweedFS has already had to change its format once for that reason (`docs/superpowers/versioning-storage-prior-art-research.md` §5, §6). Decided with the operator on 2026-10-03: an opaque random ID (UUIDv4-shaped) plus the stored sequence. AWS documents only uniqueness and "most recently stored first" ordering (`ListObjectVersions` examples), never ID ordering — so nothing is lost by not making IDs sortable.

**Null versions.** The `null` version is a real, addressable version while it exists: it is the version of an object written before versioning was enabled or while the bucket was suspended, `?versionId=null` resolves to it, and a request for it when none exists answers `NoSuchVersion`. On a suspended bucket a PUT always writes the null version: it replaces an existing null version **in place** (same version ID, new content — no new version is created and nothing enters the history store), and when no null version exists it creates one that **becomes the current version** while the previous current version turns noncurrent and is moved into the history store, exactly as AWS documents. Enabling versioning on a non-empty bucket changes nothing about the existing objects: the plain file at the key path *is* its `null` version, and its first modification under versioning moves it into the history store with a fresh real ID.

**Delete markers.** `DELETE` without a version ID on a versioned bucket does not remove content: the current version is moved into the history store and the key path file is removed, and a marker row becomes the current version. The observable rules follow AWS: `GET`/`HEAD` without a version ID on a key whose current version is a marker answers `404` with `x-amz-delete-marker: true`; `GET`/`HEAD` **with** that marker's version ID answers `405 Method Not Allowed` with `Last-Modified` and `x-amz-delete-marker: true`; `DELETE` with the marker's version ID removes the marker and **materializes** the version that becomes current again. Two documented details are carried: a `DELETE` of a specific version answers `204` with `x-amz-version-id` (the deleted version's ID) and `x-amz-delete-marker` when it was a marker, and repeated simple `DELETE`s against a key whose current version is already a marker keep inserting further markers rather than removing the existing one.

**Suspended buckets.** A write to a suspended bucket behaves as **Null versions** states. A `DELETE` without a version ID removes the object's null version if one exists and inserts a delete marker carrying the `null` version ID; if no null version exists it removes nothing and only inserts the marker — non-null versions are untouched by both, as AWS documents.

**Per-version metadata.** Decided with the operator on 2026-10-03: **full parity** — tags, checksum, owner and ACL are stored per version (the version row reuses the existing wire encodings), so `GetObjectTagging?versionId` and its ACL siblings answer for history exactly as they do for the current version. The alternative (content-core only) was rejected because S3 clients address history with those operations and the row cost is a few bytes.

**Out-of-band edits.** The mirror stays authoritative for the current version: a detected out-of-band modification (the existing size/mtime/file-identity staleness gate) degrades the object's version identity to `null` — the recorded current version ID stops resolving (`NoSuchVersion`, because the content it named no longer exists), history versions are untouched, and the next API write treats the file as the null version it now is. Serving the old ID with the new content was rejected as a lie no client can detect. This is the one place where the two contracts (mirror, versioning) genuinely conflict, and the mirror wins.

**Conditional writes.** The existing conditionals implementation gains the versioning arms AWS documents: `If-None-Match: *` applies to the **current version only** and succeeds when there is no current version or the current version is a delete marker; `If-Match` fails with `404 Not Found` (not `412`) when there is no current version or the current version is a marker. Conditional *reads* are evaluated against the version the request addresses.

**Folder markers.** Decided 2026-10-03: **not versioned**. `dir/` keeps today's idempotent directory semantics, does not enter the version index, and `ListObjectVersions` does not list it; the S3-fidelity loss is documented as a limitation rather than bought with a second, directory-shaped version chain.

**MFA delete.** A `PutBucketVersioning` request carrying `MfaDelete=Enabled` is refused with `NotImplemented` — decided with the operator on 2026-10-03. The `Status` field is handled normally, and `GetBucketVersioning` never reports MFA delete, because the protection it names cannot be provided. AWS documents no failure mode for a server that cannot honour MFA delete, so this refusal is this design's own contract and is recorded as such.

## Metadata schema (`tinio-store`)

- A **bucket versioning table**: bucket name → versioning state (and the suspension flag), mirroring the `buckets` table's wire conventions.
- A **version index table**: the superseded versions, keyed for the two access patterns the API has — point lookup by `(bucket, key, version_id)` and a per-key range scan ordered newest-first for `ListObjectVersions` pagination (`key-marker` / `version-id-marker`).
- The **existing `object_meta` row** gains the current version identity for versioned buckets — **a nullable version ID, the monotonic sequence, and the recorded delete-marker flag** (decided 2026-10-03; the `null` version is the null value, with no sentinel UUID to remember) — so a read never needs a second table for the common case; for unversioned buckets the row is unchanged. The flag was added by the operator's 2026-10-04 ruling (**a marker row must be marked, not inferred**): a delete marker is a state the simple-DELETE path records (`true`) and every object write clears (`false`), because the row's content shape cannot tell a genuinely zero-byte object — size `0`, the empty-content ETag, identity `0` on a filesystem without a file identity — from a marker's row, and inferring produced a marker where the API never created one. The row-format ruling of the first bullet applies: `FORMAT_VERSION` stays `1`, an older database errors at decode, and the remedy is delete-and-rebuild.
- The **version row** carries a `became_noncurrent_at` timestamp: it is the retention clock (a version's age is measured from when it stopped being current, not from when it was written). A row is written with the timestamp `0` — the supersede commits it before the current slot moves off it, so the crash window's adopted row is not history yet — and the transaction that moves the current slot stamps it, so a row that is history says so and readers ask the row (`tinio_store::version::Row::is_history`) instead of inferring the state from sequences. The stamp is the authority for the row **at** the current slot's sequence (the crash window's adopted row); a row the slot has moved off — or one at a key with no current version at all — is history whatever its stamp says, so the residue of a publish that aborted before its state transaction is listed and retirable rather than stranded.
- **Delete markers are rows too** — with the marker kind and no blob — so `ListObjectVersions` and retention treat them uniformly, as AWS does.
- New tables are **additive**: `FORMAT_VERSION` stays `1` per the 2026-09-02 ruling recorded in `crates/tinio-store/src/state.rs:12-20`, and a stale database written in an older row format keeps its existing remedy (delete and rebuild).
- The **version row** carries the encoded blob reference — an encoded `BlobRef`: content hash, length, and the ordered block list (one block in v1) — stored there explicitly by plan 2 (`docs/superpowers/plans/2026-10-03-s3-versioning-p2-versioned-store.md`), so a later chunking policy changes writers, not the row format; blocks themselves are files and have no rows of their own, because liveness is derived, not counted (see **Garbage collection**).
- The **version row** also carries the version's **ETag**, in the same wire form the `object_meta` row uses and copied from that row when the version is superseded — never recomputed from the content, because a multipart-composed `MD5-of-MD5s-N` ETag is not reproducible from the bytes and a rehash would re-stream the whole blob per version-addressed read; so a version-addressed `GET`/`HEAD` and a `ListObjectVersions` page serve the header from the row.

## Write paths

The supersede protocol is the crash-safety heart of this design and gets its own treatment in the plan; the shape to settle is the ordering that makes every interruption window recoverable:

1. The incoming content streams to the temp file as today (hashing ETag/checksum in the same pass).
2. The outgoing file's content is chunked and written into the block store — blocks are content-addressed and immutable, so a partial write is inert garbage, never a torn blob.
3. A commit that makes the outgoing version's row durable **before** the key path is overwritten; a crash after this point and before the rename leaves the old file at the key path plus a row describing the same content, which recovery either adopts or discards (the plan pins which).
4. The existing atomic rename publishes the new content; the existing transaction updates the `object_meta` row with the new version identity.
5. A crash anywhere before (4) leaves the previous state intact and the new content as temp residue, which today's startup sweep already reclaims.

The same protocol serves `PutObject`, `PostObject`, `CopyObject`'s destination, and `CompleteMultipartUpload`'s publish; `DELETE` without a version ID is the same protocol with an empty incoming body and a marker in place of the new version. Two paths skip the move entirely, because no previous version may be preserved: a suspended-bucket write replacing an existing null version (AWS overwrites it in place) and a write onto an object whose current version is already a delete marker (nothing to preserve). The supersede race above aborts step 2 rather than committing unknown bytes. Concurrency keeps today's guards: the fs bucket mutation lock (`crates/tinio-fs/src/backend/mod.rs:411-423`) around the commit, and the server's per-key lock (`crates/tinio-server/src/backend/locks.rs:18-26`) around conditional check-then-commit. Which of the two owns the supersede ordering, and whether a per-key version sequence needs its own guard, is a plan-level question.

## Read paths

- **Current version**: unchanged — the file stream with Range support.
- **By version ID**: the blob reader walks the block list, honoring Range across block boundaries; headers (`ETag`, checksum, `x-amz-version-id`, `x-amz-delete-marker`) come from the version row.
- **`ListObjectVersions`**: merges the current state (the walk or the meta row) with the version index, newest first per key, with prefix/delimiter/pagination semantics matching the existing listing code (`crates/tinio-fs/src/listing.rs`).
- **`ListObjects` / `ListObjectsV2`**: unchanged — current versions only, exactly as AWS defines them.
- **Read-only mode (FR-023 amended).** Decided with the operator on 2026-10-03: the root's `meta.redb` is opened **read-only** — redb 4.2 ships `ReadOnlyDatabase` for exactly this (`redb` `db.rs:427`, `open` at `:458`) — and becomes the run's **only** metadata source: objects, tags, ACLs, CORS and the version index all read from it, so history is served read-only rather than lost. The **scanner is disabled in this mode**: its job is to pre-warm ETags, listings already recompute missing/stale entries synchronously, and in read-only mode that recomputation is simply not written back. The relocated home state dir keeps tool state only (socket, state file, logs) — no second database. If the read-only open fails — no database, a corrupt one, a format version this build refuses, or a **read-write server holding the same root** (redb documents that a read-only open may not be concurrent with a read-write `Database`, `db.rs:390-391`) — the run **degrades** to today's shape: current versions serve from their files and every metadata read comes back empty, with a warning naming the reason. This supersedes FR-023's "the root's own `.tinio/` is not read" sentence; the corpus text and its scenarios move in the same change (see **Ownership**).

## Garbage collection and retention

- **Liveness is derived, not counted.** The live block set of a bucket is the union of the block lists of its version rows; there is no refcount table to keep transactional. This is sound because blocks are immutable and content-addressed: a block absent from every live set is unreachable by definition.
- **Sweep**: the existing sweep cadence (`crates/tinio-fs/src/sweep.rs`) and the startup repair (`fs-backend.md` §8.1) gain the block-store pass for the buckets that have one — the per-bucket subtree joins the classes `docs/tests.md` already documents, and `crates/tinio-fs/src/backend/tests.rs:791` (`state_dir_holds_only_redb_tmp_and_multipart`) is the test that names today's closed set of state-dir entries and must be extended.
- **Retention** — decided with the operator on 2026-10-03: three keys in the `[s3]` section, beside `temp_ttl_hours` and `multipart_expire_days` — `noncurrent_keep` (retain the newest N noncurrent versions; `0` = unlimited), `noncurrent_expire_days` (expire a noncurrent version D days after it stopped being current; `0` = never), and `block_grace_minutes` (the minimum age before an unreferenced block may be reclaimed; default 10, the Garage precedent, with a validation floor of 1 — a zero would silently disarm the grace). When both retention thresholds are set, whichever is met first expires the version, matching the two-condition shape of S3 Lifecycle's `NewerNoncurrentVersions` + `NoncurrentDays`. Delete markers count against the keep-N budget, as AWS treats them as versions. Expired versions are dropped exactly as an explicit version delete drops them.
- **The GC race**: a publish can add a reference after the live set was computed. The plan pins the guard (re-check under the bucket mutation lock, or a mark epoch), because a sweep that deletes a freshly referenced block is silent data loss.
- **Grace before reclamation.** Garage — the only prior implementation of shared-block reclamation in an S3-compatible server — frees a block only after its derived reference count reaches zero *and* a grace delay (ten minutes in its implementation), because a publish can still be in flight; it also ships repair tooling (`garage repair …`) for the drift that accumulates anyway. The engine's sweep therefore takes a **minimum age** as well as a live set — but the grace is **not** the race guard above and does not stand in for it: a dedup hit leaves the target block's timestamp untouched, so a publish that returns `Existing` can commit a row naming a block older than the grace, which a sweep holding a live set computed before that publish then deletes. The guard the previous bullet pins (the re-check under the bucket mutation lock, or a mark epoch) is the one that closes the race; the grace only narrows the window for a block whose *first* publish is in flight (`docs/superpowers/versioning-storage-prior-art-research.md` §6).
- **`doctor`**: gains block-store residue checks (block files referenced by no row, rows whose blocks are missing) and a verify pass over the block store, in the dry-run-aware shape the existing `Cleanup` implementation has (`crates/tinio-fs/src/cleanup.rs`).

## The block store: one contract, one engine, one implementation

The capability is layered so that a future backend does not re-invent it per transport:

- **The contract** — an abstract, async trait for immutable, content-addressed block storage, implemented by each backend over its own transport so the engine (and with it versioning, dedup and GC) is inherited rather than re-invented. Its exact surface — operations and signatures — is pinned by plan 1 (`docs/superpowers/plans/2026-10-03-s3-versioning-p1-block-engine.md`, Task 1-2 Interfaces); this document owns the model, not the signatures. It carries the properties the engine relies on rather than leaving them to each implementor: a block's name is its hash, so a partial or repeated write is inert; publish is crash-safe (a torn block is invisible, never served); the namespace is one bucket. Its home is `tinio-core::blob` — settled with the operator on 2026-10-03 — the workspace's backend-contract crate, the same place `Storage` lives and the same shape `data-model.md` already expects the planned `tinio-s3` / `tinio-webdav` backends to implement.
- **The engine** — `crates/tinio-blob`: the chunker, the streaming blob writer (chunk → hash → dedup → write only the missing blocks), the blob reader (ordered and range-capable), and the live-set sweep. It is generic over the contract, so every backend implementing the contract gets identical chunking, dedup and GC behavior; the version index it derives liveness from lives in `tinio-store` and is shared the same way.
- **The implementation** — the local filesystem block store: the first implementation of the contract, used by `tinio-fs` today, writing one file per block under the bucket's own subtree of the state dir. A remote implementation (WebDAV, FTP, S3 itself) is the reason the contract exists and is not built in this work.

**Why the seam.** Versioning is not a capability a WebDAV or FTP backend should have to invent per transport. With the contract/engine split, such a backend implements block I/O over its own transport and inherits the identical chunking, dedup, GC and version semantics — the equivalent capability this layering exists for. The **version state machine** itself is written, decided 2026-10-03, as a **module inside `tinio-fs`** behind a narrow interface that keeps fs paths and the mirror's file layout out of the policy code — the one rule every backend shares is "the current version is whatever that backend's object store holds". It does not get a crate of its own until a second backend exists to justify the seam; the constraint recorded now is that lifting it later is a move, not a rewrite.

- **Chunking — decided: one block per blob (the whole content), with the block abstraction kept.** The operator's ruling on 2026-10-03. In v1 a blob is a single content-addressed block, so dedup is a whole-content lookup and the block list holds exactly one entry. The prior art supports starting here rather than at CDC (`docs/superpowers/versioning-storage-prior-art-research.md` §3, §4, §6): no S3-compatible server delta-encodes versions — AWS states plainly that "each version of an object is the entire object; it is not just a diff from the previous version" — and the one S3-compatible server that deduplicates at all, Garage, does it with fixed-size blocks and no versioning on top, so this design is already ahead of every shipped peer. What the design commits to is the **seam**: the block list, the block-addressed layout and the live-set GC are built now, so splitting a blob into fixed-size (or content-defined) blocks later is an engine policy change — same file layout, same version rows, same GC — not a format migration. What v1 does not capture is dedup between near-copy supersedes (an edited file re-stores whole); the upgrade is cheap and waits for measurement rather than speculation. A second upgrade path is recorded beside it, decided with the operator on 2026-10-03: for objects uploaded through S3 multipart, the client's part boundaries are already recorded (`OBJECT_PARTS` rows), so those boundaries are themselves a chunking policy that needs no chunking algorithm at all; its limits are that it covers only multipart-uploaded content and that the boundaries are the client's, so they shift with the client's behavior. Neither route is taken in v1; both are recorded so the measurement decides.
- **Hash — decided: SHA-256.** Block names are internal to one bucket's store, so the choice carries no compatibility surface, and SHA-256 is already a workspace dependency. BLAKE3 (faster; used by Garage) stays the alternative if block hashing ever shows up in a profile; swapping it later is a store rebuild, which the `FORMAT_VERSION` ruling makes an acceptable remedy.
- **Block layout**: one file per block under the per-bucket store, published temp + rename; a block's file name is its hash, so dedup is a lookup and re-writing an existing block is a no-op.
- **Verification — decided: trust the store on the read path.** The write path always hashes what it stores; reads do not re-hash (with whole-blob v1 that would double the CPU of every `GET`), and integrity is checked by `doctor`'s verify pass and by an optional startup pass after an unclean shutdown.
- **Error surface**: one error type projecting into `tinio_core::storage::Error`'s existing I/O arm, so a consumer maps it once. That type has **no corruption arm today** — its only failure carrier is `Io` — so the corruption carrier this design wants does not exist yet, and plan 2 decides whether to add one or to carry corruption as `Io`.

## The reference implementation (`tinio-mem`)

`tinio-mem` is a real, selectable backend and the conformance oracle (`CONTEXT.md`, "Conformance harness"), so it implements the **same extended contract** — version states, version IDs, null versions, delete markers, `ListObjectVersions`, retention — rather than a stub. Its physical shape follows from its existing one:

- The current version's bytes stay where they are today, in the object row: mem has no filesystem, so the "current version is the file" rule degenerates to "the current version is the row", and an unversioned bucket's footprint is unchanged.
- A superseded version's content is stored in a **blob row keyed by content hash** — mem is content-addressed at whole-blob granularity, with no chunking and no block files. The block engine is an fs-side concern; the conformance suite asserts *semantics*, never layout, so the two backends stay free to differ physically while being provably identical in behavior.
- The move/materialize pair is a row operation in mem (no I/O), which makes mem the cheapest place to test the *state machine* — including the delete-marker, suspended and null-version rules — and the fs suites then test the same state machine against real files.
- What mem cannot test is the block engine itself: chunking, dedup, block GC and the crash windows are `tinio-blob`'s and `tinio-fs`'s own suites (see **Testing**). Retention legs that need a time trigger are driven directly rather than through mem, which has no sweep.
- Mem compiles the versioning code under the same cargo feature as `tinio-fs`, so a stripped build strips both backends' versioning together.

## Error surface

The S3 wire behavior this design settles:

- **`NoSuchVersion` (`404`)** for a version ID that names no existing version — including a version whose content an out-of-band edit invalidated.
- **Delete markers**: `404` + `x-amz-delete-marker: true` when a plain `GET`/`HEAD` lands on a marker as the current version; `405 Method Not Allowed` + `Last-Modified` + `x-amz-delete-marker: true` when a `GET`/`HEAD` addresses a marker by version ID — and **no `Allow` header**, decided 2026-10-03 on the implementation evidence below.
- **`InvalidArgument`** for a malformed `versionId`.
- **`NotImplemented`** for every version operation when the capability is absent — and, decided 2026-10-03, for **any request carrying `versionId`** in that state, never a silent fallback to the current version — and for a `MfaDelete=Enabled` request always.
- **`x-amz-version-id`** on the responses AWS carries it on (PUT/POST/complete-multipart, GET/HEAD, DELETE).

The exact table belongs to `contracts/s3-surface.md`; this design names the facts and the plan enumerates the rows.

## Feature gating and configuration

Three levels, one shared meaning, none of them a second implementation:

- **Compile time**: the cargo feature `versioning` (decided 2026-10-03), gating the new code in `tinio-blob`, `tinio-fs`, `tinio-mem` and `tinio-server`. **`tinio-core` is not gated**: its `version` module and `VersionOps` are inert types and one trait, and gating them would not compile — the ungated `object::Info` carries `version_id: Option<version::Id>` and `Storage` aggregates `VersionOps`. **The config keys are not gated either**: `tinio-config` owns the keys and parses `versioning` / `noncurrent_keep` / `noncurrent_expire_days` / `block_grace_minutes` in every build — an unknown key in a config is a startup error (FR-016), so a stripped build must still read a config that names them. The capability decorator's existing row syntax — `#[gated(versioning: "versioning")]` in the `tinio_s3_ops!` table (`crates/tinio-server/src/capability.rs:41-72`) — strips a gated operation together with its feature, so a stripped build answers `NotImplemented` through s3s's trait default rather than through a hand-written arm.
- **Run time**: `[s3] versioning` — a flattened key beside `multipart`, `copy_object`, `tagging` and `cors` (`crates/tinio-config/src/schema/s3.rs:144-146`) — **default on**, decided 2026-10-03. The other core-surface capabilities default on too; the real opt-in is the per-bucket state, which defaults to unversioned, so a server with the toggle on still changes nothing until a bucket enables versioning. The toggle exists to switch the whole surface off for a deployment (and refuses with the family's existing sentence, `NotImplemented "<Operation> is disabled"`).
- **Per bucket**: the S3 state itself. Only `PutBucketVersioning` can turn versioning on, and on an unversioned bucket every data-plane operation behaves exactly as today.

**A toggle switched off on a root that holds version data** — decided 2026-10-03: the server **starts**, every version operation is refused with `NotImplemented`, current versions keep serving, and startup logs a warning naming how many buckets hold version data (the number is cheap: one range scan of the bucket-versioning table). Refusing to start was rejected as making a config flip able to strand served data.

**A build without the feature reading such a root**: current versions serve (they are plain files), the additive tables are ignored, and any request carrying `versionId` is refused rather than answered from the current version — the fail-open hazard the error surface above closes. That contract is stated once here and tested in the plan.

## Risks

- **The mirror and versioning disagree about out-of-band edits.** The mirror wins by construction (the file is the current version), which means an out-of-band replacement silently invalidates the recorded current version ID. The degradation to `null` is the settled rule; it is stated, tested and documented — not closed.
- **Disk amplification is asymmetric.** Dedup applies to history only: N identical objects under different keys each cost a full file; only superseded content is deduplicated. A workload that overwrites one key repeatedly gains the most; a workload of unique objects gains nothing and pays the version-index rows.
- **GC is the data-loss surface.** A sweep that miscomputes liveness deletes reachable content irrecoverably. The live set is derived from committed rows only, the race guard and the minimum-age grace are mandatory, and `doctor` can verify residue.
- **Read-only mode now trusts the root's database.** A read-only run serves whatever that database holds — including data written by a different build — and redb's own rule (no read-only open concurrent with a read-write one) is the only guard against reading a live database; the degrade path is the remedy when the open fails. The amendment is also a behavior change to a documented mode, which is why **Ownership** and **Testing** name it.
- **The feature matrix can rot.** Three levels of enablement multiply the paths; the capability table (one row per gated operation) and the conformance legs are what hold it.
- **Cost on the overwrite path**: a supersede reads and re-hashes the outgoing file, so overwriting a large object costs an extra full read plus block writes. The alternative (streaming into the block store at write time) doubles storage for every object and was rejected — recorded here because it is the decision a future reader will question.
- **Whole-blob storage gives up near-copy dedup.** A superseded version differing from its successor by a few bytes is stored whole, so the saving real chunking would capture is not captured; the block seam exists so the upgrade is a policy change once measurement shows it pays (see **Chunking**).
- **The topology is unattested among S3 servers.** A materialized current version over a content-addressed history has no S3 prior art: Garage has the CAS half without versioning (and no materialized current at all), SeaweedFS has versioning without CAS, and MinIO keeps even the current version inside `xl.meta`. The nearest analogues are filesystem tools — Fossil (a mutable `/active` tree over the Venti CAS archive) and git/OSTree (a plain working tree over a CAS object store). Novelty is not a defect, but it means the suites are the only oracle for the *combined* behaviors (`docs/superpowers/versioning-storage-prior-art-research.md` §6).
- **MFA delete's refusal is our own contract.** AWS documents no failure mode for a server that cannot honour MFA delete, so the `NotImplemented` refusal is a deviation clients will meet only if they ask for MFA delete.

- **Protocol-layer readiness**: `s3s` 0.17 generates `get_bucket_versioning`, `put_bucket_versioning`, `list_object_versions` and the `version_id` DTO fields (verified against the vendored registry copy).
- **redb**: 4.2 ships `ReadOnlyDatabase` (`db.rs:427`; `open` at `:458`) and documents "Multiple processes may open a `ReadOnlyDatabase`, but it may not be opened concurrently with a `Database`" (`db.rs:390-391`) — the two facts the read-only-mode amendment rests on.
- **AWS fact-check (2026-10-03)**: the suspended-state, delete-marker, conditional-write, MFA-shape and ordering rules above were verified against `docs.aws.amazon.com` primary pages (user guide + API reference + the current S3 API Reference PDF). Two combinations AWS does not document are marked as such in the text: general-purpose `?versionId=null` resolution and conditional headers evaluated against a version-addressed read (the latter is treated as mechanical — the condition applies to the version the request addresses).
- **The delete-marker `405`'s exact shape (2026-10-03)**: AWS documents `405` + `Last-Modified` + `x-amz-delete-marker` and models no `Allow` member — botocore's `service-2.json`, the SDK-JS Smithy model and `aws/api-models-aws` all lack a `MethodNotAllowed` shape. MinIO writes no `Allow` header anywhere in its tree (`RELEASE.2025-10-15T17-29-55Z`, commit `9e49d5e7`); Ceph RGW, SeaweedFS and Garage answer `404 NoSuchKey` on this path rather than `405`; `ceph/s3-tests` asserts no such header; only LocalStack, an emulator, models one. This design therefore sends none — a client that needs the marker's identity reads `x-amz-delete-marker`.
