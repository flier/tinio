# Design: S3 conditional headers cleanup

**Date**: 2026-08-31
**Status**: approved — grilled 2026-08-31 (codebase/s3s/AWS fact-checked); review pass 2026-08-31 (precision fixes — If-Range match rule, 400 placement, copy-source position, response-metadata source; no structural change); review pass 2026-09-02 (code-review fixes — delete missing-key policy per the AWS model text → 204 for every conditional header; negative `if_match_size` → 400 `InvalidArgument` validated up front (state-independent); GET coherence re-check on a head/body snapshot race; CMU upload-existence-first ordering + 501 shape hoisted up front; abort lock scoped to conditional aborts; `any()` renamed `absent()`); review pass 2026-09-02 #2 (concurrency code review — the GET reconciliation gate widens to **etag OR mtime** and no-Range conditional GETs become a **single fetch + post-check**; the If-Range refetch is served-range-guarded, refetches re-validate, and a shrink mid-fetch is classified via the `InvalidRange` size; the **conditional-abort lock is removed** (storage-row serialization, parity with unconditional aborts); the specific-`If-None-Match` 501 is generalized to a shared `check_write_shape` gate over PutObject/CopyObject-destination/CMU; EntityTooSmall is enforced **authoritatively in the storage commit** (fs verify loop / mem write txn → `PartTooSmall`), the S3-layer pre-check staying as early validation of the lock-held listing; the three date comparison rules consolidate on one `whole_second_ordering` primitive)
**Scope**: tinio-server S3 interface — unify conditional-header handling (RFC 7232) and fill the missing support (DeleteObject, CompleteMultipartUpload, AbortMultipartUpload, If-Range); write-path both-header 400 rules; the GET read-path fix (head → condition check → stream). Companion spec: `2026-08-31-s3-tagging-ops-design.md` (object/bucket tagging, RenameObject, GetObjectAttributes) — RenameObject's conditions reuse the machinery this spec builds. Not touched: PostObject (delegation covers it), RestoreObject / SelectObjectContent / WriteGetObjectResponse (still NotImplemented), tinio-config schema.

## Goal

1. **One conditional machinery.** All conditional headers route through the shared evaluator in `backend/conditions.rs`; the ad-hoc special case (`objects.rs:62`), the hand-rolled CopyObject destination parse (`objects.rs:337`), and the per-op error mapping collapse into shared helpers.
2. **Every conditional surface the s3s 0.15 dto exposes is honored.** DeleteObject (`if_match`, `if_match_last_modified_time`, `if_match_size`), CompleteMultipartUpload (`if_match`, `if_none_match`), AbortMultipartUpload (`if_match_initiated_time`), plus `If-Range` on GET.
3. **Behavior is locked by tests.** Evaluator details in unit tests, HTTP behavior in the cucumber migration's `conditions.feature`.

## Non-goals

- **No PostObject work.** s3s's default `post_object` delegates to `put_object` (s3_trait.rs:4654-4659), carrying `if_match`/`if_none_match` through the conversion (dto/generated.rs:41967-41982) — conditions are already enforced via that delegation today.
- **No If-Range on HEAD.** HEAD has no body; `Range` is inapplicable. If-Range applies to GET only.
- **No tagging / RenameObject / GetObjectAttributes** — the companion spec `2026-08-31-s3-tagging-ops-design.md`.
- **No RestoreObject / SelectObjectContent / WriteGetObjectResponse** — RestoreObject is Glacier-tier restore semantics tinio has no tiering for; SelectObjectContent is a SQL-engine-scale feature; WriteGetObjectResponse is a data-plane write-back op. All stay `NotImplemented`.
- **No removal of existing Rust tests.** They stay until the cucumber migration (separate plan) reaches parity; new HTTP-level coverage lands as cucumber features from the start.

## Decisions (locked in brainstorming + grilling, 2026-08-31)

- **Conditional depth**: every s3s 0.15 dto field + If-Range (GET only); PostObject out.
- **Cleanup degree**: structural unification (special case, hand parses, error mapping) **and** the GET read-path fix (head → condition check → stream body; no body fetch when a precondition fails).
- **Evaluator shape — approach B**: keep the RFC 7232 4-header `ConditionalHeaders` evaluator exactly as is (it implements the §13.2.2 precedence and has unit-test backing); the new checks (DeleteObject trio, CMU, Abort) are small AND-composition checkers that share the parse helper and the error mapping; the missing-object policy is shared by the Put/Copy destination family (`check_missing`: `If-Match` → 412, everything else → pass — create-if-absent), while DeleteObject (missing → 204 under every conditional header, handled in the op — revised 2026-09-02) and CMU (404 `NoSuchKey` on a missing destination with `If-Match`) each keep their **own** policy — the three deliberately differ. No universal evaluator (approach A — the RFC precedence does not apply to the new checks) and no declarative condition builder (approach C — YAGNI).
- **Comparison precision**: `if_match_last_modified_time` / `if_match_initiated_time` compare at **second-precision equality** (both sides truncated), matching the Last-Modified wire format; `if_match_size` compares by **exact equality** (it is an `i64`, not a date). If-Range dates also compare at second precision, but with the RFC 9110 §13.1.5 **match rule**, not equality — a date matches when `last_modified <= header_date` (an equal or later date matches; a future date matches; only an older date fails). The two operators are different and must not be conflated.
- **GET fast path kept**: the head-first read-path fix applies only when a conditional header or If-Range is present; an unconditional GET keeps today's direct body fetch.
- **Write-path both-present rule**: PutObject/CopyObject destinations AND CompleteMultipartUpload reject `If-Match` + `If-None-Match` in the same request → 400 `InvalidRequest` (AWS conditional-writes semantics; AWS does not document the exact code — `InvalidRequest` is the commonly reported one). The violation is a **request-shape error** — validated before any work that costs I/O: PutObject checks it at the top of the op, **before `stage_body`** (a rejected request must not pay the body stream; PostObject inherits the check through the put delegation), CMU checks it **before the parts parse and the lock**. The read paths (GET/HEAD) keep today's RFC 9110 §13.2.2 behavior. The rule applies only to the destination protocol — the copy-source family (`copy_source_if_match` + `copy_source_if_none_match`, CopyObject and UploadPartCopy) keeps today's RFC evaluation order (If-Match first), **no 400** (AWS documents no such restriction for the copy-source headers; a position is stated here so implementers don't invent one). Cucumber asserts the exact `InvalidRequest` code.
- **CMU conditional facts (verified 2026-08-31; the non-`*` If-None-Match code re-checked against real-AWS reports and LocalStack modeling)**: `If-None-Match` accepts `*` only — a specific ETag value → 501 `NotImplemented` ("A header you provided implies functionality that is not implemented"), a rule the 2026-09-02 #2 review **generalized to every destination write op** via the shared `check_write_shape` gate (real AWS answers 501 on PutObject too — a specific value must never fall through to a live comparison or a silent overwrite); `If-Match` compares the **current object at the key** (missing → 404 `NoSuchKey`, mismatch → 412); the per-key critical section makes head-check + complete atomic, so AWS's `409 ConditionalRequestConflict` race cannot arise and needs no handling. The 5 MiB non-final-part rule (EntityTooSmall) is pre-checked on the lock-held listing snapshot **and** enforced authoritatively in the storage commit — the fs verify loop and the mem write txn re-read the current part state and answer `PartTooSmall` (review #2): a concurrent UploadPart overwriting a part after the S3-layer snapshot is caught at the commit, never composed silently.
- **DeleteObject missing-key policy (revised 2026-09-02, code review)**: a missing object answers 204 under **every** conditional header — the AWS model text shipped in s3s 0.15 (`DeleteObjectInput`, mirroring the AWS API reference) says for `If-Match`, `x-amz-if-match-last-modified-time`, and `x-amz-if-match-size` alike: "If the [validator] matches **or if the object doesn't exist**, the operation will return a 204". Delete is idempotent; the conditions gate an **existing** object only (mismatch → 412). No conditions → 204 unchanged. The earlier "If-Match present → 412" reading came from the design's 2026-08-31 AWS fact-check, which the in-repo model text contradicts. (Real AWS restricts the date/size headers to directory buckets; tinio honors them on the general-purpose model since s3s exposes them in the dto.)
- **No version compatibility (user-confirmed, 2026-08-31)**: the project is pre-release with no released data — behavior changes (the write-path 400 rule, conditional deletes, the head-first GET) land directly, with no compat shims and no migration paths.
- **New spec IDs**: `specs/001-s3-local-server` gains new FR/SC IDs for the conditional surface.
- **Cucumber features created by this plan**: `conditions.feature` lands in the existing `tinio-e2e` crate independently; the uncommitted BDD-migration plan absorbs it later.

## Design — shared machinery (`backend/conditions.rs`)

- **Move `parse_etag_condition_header`** from `objects.rs:33-46` into `conditions.rs` (it currently has one caller pair; after this change CopyObject destination, DeleteObject, and If-Range all use it). Keep its `InvalidArgument` on non-UTF8/parse failure.
- **`parse_if_range`** — parses `If-Range` into an enum `IfRange { Etag(dto::ETag), Date(dto::Timestamp) }`. Parse failure or `*` → `None` (the header is ignored, preserving today's behavior). RFC 9110 §13.1.5: wildcard is not a valid If-Range value.
- **`ConditionalHeaders::absent()`** — true iff all four headers are `None`; the destination fast-path (skip the head) is decided here, folding the `objects.rs:62` special case into the evaluator. (Renamed from `any()` on code review 2026-09-02 — the old name read as its opposite.)
- **`ConditionalHeaders::check_missing()`** — the missing-object policy of the destination protocol (Put/Copy): `If-Match` → 412, everything else → pass (create-if-absent). (No `write_path` parameter — `ConditionFailure::Match` maps to 412 on both paths; dropped on code review 2026-09-02. DeleteObject does NOT use it: its missing-object policy — 204 under every conditional header per the AWS model text — is handled in the op; CMU keeps its own 404 `NoSuchKey`.)
- **`to_whole_seconds`** — the second-precision truncation used by every conditional timestamp comparison.

## Design — filled operations

- **DeleteObject** (`objects.rs:217`): evaluate `if_match` (strong, as today, `*` matches any existing object) AND `if_match_last_modified_time` (second-precision equality with the object's `last_modified`) AND `if_match_size` (exact equality) — all provided conditions must pass, else 412. A negative `if_match_size` (the dto type is `i64`) is **malformed** — 400 `InvalidArgument`, validated **up front** before the head (request-shape, state-independent: a missing key never answers 204 to a malformed size; review fix 2026-09-02). The head-check + delete runs inside the per-key critical section — the lock `op_delete_object` already takes today (`objects.rs:226`), shared with puts, copy destinations, and CMU; the new part is the condition check, not the lock. A missing object skips the checker entirely (204 per the missing-key policy above).
- **CompleteMultipartUpload** (`multipart.rs:496`): the destination conditions evaluate against the **object currently at the key** (the one being replaced) — not the composed ETag of the completing upload. `if_match`: strong compare (or `*` = any existing object); missing destination → **404 `NoSuchKey`**; mismatch → 412. `if_none_match`: **`*` only** — a specific ETag value → 501 `NotImplemented`; missing destination → pass, existing → 412. **Request-shape rejections go up front** (before the parts parse and the lock — request shape, no state needed): both headers in one request → 400 `InvalidRequest` AND a specific `If-None-Match` → 501 (review fix 2026-09-02: the 501 is the same shape class and no longer waits for the parse + head). The head-check + complete runs inside the per-key critical section (the lock `op_complete_multipart_upload` already takes); the upload's own existence is validated FIRST inside the lock — a conditional retry of a completed/aborted upload answers `NoSuchUpload`, the same ordering as the abort op and the unconditional complete (review fix 2026-09-02).
- **AbortMultipartUpload** (`multipart.rs:736`): `if_match_initiated_time` compares (second-precision, via the shared `whole_second_ordering` equality) against the upload's Initiated timestamp → 412 on mismatch; a missing upload answers `NoSuchUpload` regardless. **No server lock, conditional or not** (review pass 2026-09-02 #2: the 2026-09-02 lock addition is removed — its 2026-09-02 justification said abort-vs-complete needed the per-key critical section, but the state an abort touches is `(bucket, upload_id)`-scoped and both backends drain it in ONE transaction with an in-txn existence + key match, exactly as the always-lock-free unconditional abort relied on; a complete landing between the fetch and the drain surfaces as `NoSuchUpload`, AWS-consistent, and the per-key lock CMU takes guards its own destination conditions, not the abort. Holding the key lock across the abort would also have serialized every same-key writer behind the fs backend's unbounded best-effort `remove_dir_all`). The storage state already exposes Initiated via `get_multipart_upload`; no storage change.
- **If-Range (GET)** (`objects.rs:139`): only evaluated when `Range` is present — an If-Range without a Range is ignored and the request takes the unconditional fast path (RFC 9110 §13.1.5). Strong ETag comparison (a weak `W/` tag never matches), or a date matched by the RFC 9110 §13.1.5 rule: a date matches when `last_modified <= header_date` (second precision, both sides truncated — an equal or later date matches, a future date matches, only an older date fails). An unparseable value or `*` is **ignored** (treated as absent, so the Range is served as if no If-Range were sent — preserving today's behavior; RFC 9110 §13.1.5: a wildcard is not a valid If-Range value). The RFC 7232 conditions are evaluated first — a failed `If-Match`/`If-None-Match` answers 412/304 and If-Range is never evaluated. Match → serve the 206 as today; mismatch → ignore Range and serve the full 200 (an unsatisfiable Range answers 416 only when If-Range matches or is absent). The decision happens in the read-path fix below, before the body fetch. Note: s3s 0.15 has no `if_range` dto field — the header is parsed from `req.headers`.
- **Write-path both-present rule**: PutObject and CopyObject destinations follow CMU — `If-Match` + `If-None-Match` together → 400 `InvalidRequest` (AWS conditional-writes semantics), and a specific (non-`*`) `If-None-Match` → 501 `NotImplemented` — one shared `check_write_shape` gate over all three destination ops, called up front before any staging/parts parse/lock (review #2). The copy-source family and the read paths (GET/HEAD) are exempt and keep the RFC 9110 evaluation.

## Design — read-path fix

- GET currently fetches the body, then checks conditions, then drops the body on failure (`objects.rs:149-164`, comment acknowledges it). Change to: head (`head_object`) → condition check → only on pass, stream the body with the Range decided by If-Range. HeadObject already checks against Info and is unaffected. **Fast path kept**: the head-first form applies only when a Range is present AND (a conditional header or an If-Range is present); a no-Range conditional GET takes a **single fetch + post-check** instead (review #2 — see below); an unconditional GET fetches the body directly as today, no extra metadata read.
- **Snapshot coherence (review fix 2026-09-02; upgraded by review #2)**: the head and the body fetch are two independent reads — no lock serializes them (unlike the conditional put, whose check and commit share the per-key write lock). The reconciliation gate now fires when the fetched snapshot differs from the head's by **ETag OR mtime** — a byte-identical re-PUT changes the mtime but not the content-MD5 ETag, and date conditions / date If-Ranges must re-evaluate on it. On the gate: the RFC 7232 conditions **re-evaluate against the fetched snapshot** (304/412 with the fetched validators). A full object is refetched only when the fetch actually **served a range** (`served_range` Some) and If-Range no longer matches the fetched snapshot — an already-fetched full body is never discarded — and the refetched snapshot itself passes the condition re-check before serving (bounded: at most one refetch). A ranged fetch that answers `InvalidRange{size}` while an If-Range was honored is classified by the size: equal to the head's → genuinely unsatisfiable → 416; different → the object shrank/was replaced → If-Range is stale → drop the Range, refetch the full object, re-evaluate. Response metadata always comes from the served snapshot, so a response always describes exactly one object. The no-Range conditional GET needs none of this — conditions evaluate on the single fetched snapshot, race-free by construction.
- **Cost profile** (the fix is not free on every backend): the memory backend's `get_object` copies the whole body up front — the head-first form saves that copy for failing conditional GETs over a Range; a no-Range conditional GET pays the copy even when 304 wins (review #2: accepted — it buys a single consistent snapshot and removes one storage read on the pass path; the fs backend streams lazily, so there the no-Range form costs nothing extra on failure and saves an open on the pass path). The If-Range-over-Range path keeps head + fetch: two reads on pass, one extra open on fs, as before.
