# Design: host-level confinement capability — detection, refusal and remedy

**Date**: 2026-10-01
**Status**: draft — grilled 2026-10-01 in six rounds; every decision below is the operator's. Three facts moved during the grilling — and a second grilling of the plan that followed it — and are folded into the text below. No code lands before a plan document exists.
**Scope**: `crates/tinio-sandbox-core` (the error variant, because the shared enum lives there), `crates/tinio-sandbox-windows` (the predicate, the classification, the message factory, and — behind the existing `testing` feature — the Low-integrity spawn device the scenario needs), `crates/tinio-sandbox` (the facade predicate), `crates/tinio-cli` (the early gate, the error variant, the `doctor` check), `crates/tinio-e2e` (two scenarios — the Low-integrity one and the seeded residue fixture **Risks** names), and the one `host_cannot` site whose own precondition is this fact (`crates/tinio-server/tests/support/windows_e2e_harness.rs` `:559`). **Not touched**: `backend_available()` and its build-level answer, the Linux and macOS backends, `tinio_util::testing::host_cannot`'s shape.
**Spec**: `specs/001-s3-local-server/contracts/cli.md` owns the CLI contract this design is enforced through — its `--sandbox` refusal rule and its `Errors (exit 1)` list. `specs/001-s3-local-server/contracts/doctor-report.schema.json` owns the report shape the `doctor` check must fit. This document owns the one new fact both refer to: the **host-level** capability answer, which had no owner before it.

## Background

Two answers already exist to "can this machine confine?", and neither is the answer an operator needs when a launch fails.

The first is `tinio_sandbox::backend_available()`: a facade-owned `pub const fn` answering whether a platform's confinement backend has landed **in this build**. It is a build-time fact, it is `true` on all three supported platforms, and it cannot see a token. It is the CLI's first refusal (`sandbox/plan.rs`, the sole reader) and keeps that place.

The second is the failure itself, and today it is a bare HRESULT. `CreateAppContainerProfile` failing at `crates/tinio-sandbox-windows/src/sid.rs` builds `io::Error::other("CreateAppContainerProfile: hr=0x{hr:08X}")`; the facade carries it up; `crates/tinio-cli/src/error.rs`'s `SandboxBroken` renders the detail **verbatim**, which is that variant's own stated design. The operator therefore reads `... CreateAppContainerProfile: hr=0x80070005` and is told neither what happened nor what to do.

**The condition is not a test artifact; it was measured against a user-visible path.** On 2026-10-01 this workspace root carried `Mandatory Label\Low Mandatory Level`: a binary built under it ran at Low integrity, could not create an AppContainer profile (`hr=0x80070005`) and could not write `D:\Temp`, while the same binary copied outside the tree passed. A Low-integrity process writing to a Medium object is denied by no-write-up policy; the profile's `Packages` directory and its `AppContainer\Storage` key are both such writes.

**Where the refusal lands.** `PackageSid::derive` runs inside `prepare_launch` (`backend/mod.rs` `:396`, called at `:229`), and `grant_whitelist` runs after it returns (`:230`, first ACE at `:453` or `:456`). **A host that cannot create the profile therefore already fails before the first ACE**, at the profile creation itself. What is *not* yet true is that the refusal is early in the run: by `:396` the CLI has already created the state directory and the served root (`commands/start/run.rs` `:195`, `:199`), opened the access log and bound the data listener and the control channel (`sandbox/confine.rs` `:225`–`:232`), and the crate has already swept stale profiles (`backend/mod.rs` `:367`), written the ACL salt file via `package_name` (`:385`) and taken the machine-wide profile mutex (`:394`). Those are the side effects an early refusal buys back, and they are the ones this design targets.

**The condition the operator reported is the broad one.** On the host above, the *first* error a user meets is `temp dir: PermissionDenied ... D:\Temp\.tmpXXXXXX`, raised by `create_dir_all` long before any confinement code runs. A capability answer that can only be reached inside `Backend::confine` would never be the sentence that user reads. That is why the gate is placed in the CLI as well as the library (see **The gate**).

**The CLI's own first write sits above the gate.** `resolve::server` (`commands/start/run.rs` `:119-123`) runs **above** `sandbox::plan` (`:147-155`), and on a root that holds no `.tinio.toml` yet, `discover::load_or_create` (`tinio-config/src/discover.rs` `:139-159`) does `create_dir_all` on the state directory and writes the config. On the host measured above — the one whose token cannot create an AppContainer profile — that same token cannot write a Medium state directory either, so the operator's first error is the resolution's bare `PermissionDenied` and the gate is never reached. **What holds is the library's guarantee** (its first persistent side effect is the sweep the gate precedes) and the CLI's guarantee on any root that already holds a config. The design claims no more: the operator accepted this limit in writing (plan-grilling round 2, Q12), and the plan records it in its Review Focus.

## Goal

One runtime answer, one operator sentence, one place that says it:

1. A host whose token cannot create an AppContainer profile is refused **before this crate's first persistent side effect** — before the stale-profile sweep, the salt file, the profile mutex, the profile itself and every ACE — and, in the CLI, before the writes the gate actually precedes (a first run's resolution above the gate may already have created the state directory).
2. The refusal names the cause and two actions the operator can take, and keeps the raw HRESULT for support.
3. The suites that must skip on such a host say what a user sees, without either side owning a second copy of the sentence.

## Non-goals

- `backend_available()` and its build-level answer. It stays the **first** refusal and keeps its owner; this design's answer is the second and sits after it.
- The other Windows preconditions — symlink and reparse points, junctions, socket reachability. Each keeps the place it already has, and the suites that skip on them are unaffected in substance.
- The Linux and macOS backends. The Linux jail applies in place; **macOS Seatbelt is itself an SBPL profile** (`crates/tinio-sandbox-macos/src/profile.rs`), so the platform needs no *AppContainer* profile and no predicate of this shape — the facade answers `Ok(())` there.
- `tinio_util::testing::host_cannot`'s shape. Its doc calls it the one arbitration of `ALLOW_SKIP` every suite shares, and this design changes only what its callers pass it.
- Any GitHub-style "fix the host" automation. The refusal reports; the operator acts.

**The `doctor` row is in scope.** `tinio doctor` gains the check below in this change; the work is scoped under **The doctor check**, and the report's *shape* keeps its owner.

## The predicate

New module `crates/tinio-sandbox-windows/src/capability.rs` and **one public entry point** — `can_confine()`, answering `Result<(), Error::HostCannotConfine>`. The probe's window (`Window`, `probe_window`) is `pub(crate)`, and the one caller outside the predicate that needs it is `testing::with_probe_profile(f)` — **in the crate's non-default `testing` module, behind that feature**, which is where `docs/tests.md` puts a device a `tests/` target must share. It runs `f` while the probe's own throwaway profile is alive and hands it that live `PackageSid`, so a caller that needs a real AppContainer SID — the Windows e2e harness's ACL precondition is the one that exists — takes it from the predicate's probe instead of deriving a second profile of its own. The crate therefore has one recipe for a throwaway profile, and the predicate's module keeps the one public entry point it is designed around rather than widening it by the window it already opened. The error type is the shared enum's variant (`tinio-sandbox-core`), not a private type, so the façade, the CLI and the launcher all name the same thing. The verdict an HRESULT gets is its own function, `classify(hr)`, because that is the seam the tests drive and the boundary below is stated in exactly one place.

**Host-level and process-scoped.** It asks whether *this process's token* can create an AppContainer profile. It is not asked about a root, a path or an access mode, so its answer is one per process rather than one per run.

**Cached, but only where caching is sound.** A token does not change under a running process, so a definitive verdict is computed once and held in a `OnceLock`: both `Ok` and `Err(E_ACCESSDENIED)` are definitive. Anything `classify` does not recognise is **not** a verdict: the call answers `Ok(())` and caches nothing, so a later call re-probes and the unrecognised failure surfaces at the real call site, where it is the platform error it is. This design refuses only what it can name, and a transient race must not become a permanent claim (see **Risks**).

**Probed, not guessed — and probed on a name of its own.** The probe creates a throwaway profile through the existing `PackageSid` and drops it, so create-then-delete is the lifetime that type already has and no new side-effect class is introduced. Two constraints fix the name:

- It must **not** be `package_name(root)`. That function derives a real root's exact profile name — a probe using it would take over the profile of a live real run and its `Drop` would then delete it — and it also reads or creates `%LOCALAPPDATA%\tinio\acl-salt` as a side effect the capability answer has no business having.
- It must sit under the `PACKAGE_PREFIX` `tinio.sandbox.` so that a probe profile left behind by a crash is swept.

The probe therefore uses the fixed constant `tinio.sandbox.capability-probe`: deterministic, at most one on the machine, sweep-eligible if orphaned, and impossible to confuse with a real root's `tinio.sandbox.<16 hex>` name — the sweep's filter is a bare prefix test on both of its listings (`sweep.rs` `:393-401`, `:475-478`), with no shape check, so a non-hex leaf is still a candidate.

**The probe holds `ProfileLock` across its create *and* its delete** (plan-grilling round 2, Q9), best-effort. Without it two probes of the fixed name interleave: the second takes the profile over on `ERROR_ALREADY_EXISTS`, the first's `Drop` deletes it, and the second's `Drop` then records a deletion of a profile it did not own — `DeleteAppContainerProfile` answers `S_OK` for an absent name, so that entry is an `info` about someone else's probe rather than a warning — while a third process can meet a transient `ERROR_PATH_NOT_FOUND` inside the same window. A lock that cannot be created does not block the answer, and the type's own `Drop` re-enters this process's `ProfileLock` safely (`sweep.rs` `:998-1001`). The probe's `Drop` stays the type's own — it frees the SID, takes `ProfileLock` and calls `DeleteAppContainerProfile` — because a second, lock-free delete path would be a new lifecycle to justify, and the lock it takes is the same one the launcher takes moments later in the same process.

**Classification is the part that must not be greedy.** Only `E_ACCESSDENIED` (`0x80070005`) is a capability answer. `ERROR_PATH_NOT_FOUND` (`0x80070003`) — which a concurrent creation of one name inside `userenv` produces, recorded in `backend/tests.rs` — and every other HRESULT are **not**, and keep today's path unchanged: they propagate as the platform error they are.

**The real call site is classified too, and is the floor.** `PackageSid::derive`'s own `E_ACCESSDENIED` (`sid.rs` `:1217`) is classified by the same `classify`. On a host this design did not anticipate, the failure an operator sees still carries the cause and the remedy rather than a bare HRESULT, whatever the preflight said.

## The message

One factory, two consumers. `capability.rs` also owns the sentence, as two parts rather than one string, because the CLI's error and `host_cannot`'s arguments need different halves:

- **cause** — the fact and its most likely explanation, with the HRESULT kept verbatim.
- **remedy** — the two actions: run in an ordinary user session, and check or clear the Low mandatory label on the tree the binary was built in.

The platform layer renders both and puts them **into the core variant's fields**; `tinio-sandbox-core` is shared with the other two platforms and knows nothing about AppContainer, so it carries the text rather than producing it. `can_confine()`'s error and the production error are the same value with the same two fields, so the CLI renders `{cause} — {remedy}` verbatim and the one test call site builds `host_cannot`'s `reason` argument from the rendered error. Neither side re-types the sentence, which is what makes "the suite says what the user sees" checkable rather than aspirational. (`host_cannot`'s third argument stays the site's own, because it is appended with no separator — `tinio-util/src/testing.rs` `:2946-2953`.)

**A step event says the same thing in the log.** When the verdict is negative the launcher emits `step="host cannot confine"` with the HRESULT, and the same text lands in the error the operator reads. The step name follows the existing `step="grant the ACLs"` / `step="sweep the stale profiles"` family and is the surface the suites assert.

## The gate

Two placements, one predicate, and the reason they differ is the side-effect boundary rather than defence in depth.

- **In the CLI, inside `refuse_unhonourable`.** `sandbox::plan` (`commands/start/run.rs` `:154`) resolves the request and owns the fail-closed half; a run that asked for confinement asks `can_confine()` through the facade there, before the state directory and served root are created (`:195`, `:199`) and before `sandbox::confine`. This placement turns the reported symptom — `PermissionDenied` on a temp directory — into a named cause and two actions without asking the same question in a second place. Its limit is the resolution above it, which can already have written: on a first run the filesystem may answer first.
- **In the library, at the head of `Backend::confine`** (`backend/mod.rs` `:228`), before `prepare_launch`. This is what protects every other embedder of `tinio-sandbox`, and it is what keeps the sweep, the salt file, the mutex and the profile from happening before the refusal.

A negative answer at either placement is fail-closed: exit 1, no ACE, no profile residue, no port bound, no store published by the sandbox path, no sweep, no salt file written — the shape `contracts/cli.md` already gives the build-level and platform-level refusals, which this one joins rather than replaces. (A CLI resolution above the gate can have created the state directory first.)

## Error surface

Four layers, one fact each; the plan pins the signatures.

| Layer | Change |
|---|---|
| `tinio-sandbox-core` | `Error` gains `HostCannotConfine`, carrying the rendered `cause` and `remedy` plus the raw HRESULT. It sits **beside** `Unsupported`, and the two name each other: `Unsupported` is the compile-time fact ("the platform cannot confine this process at all"), this is the run-time one ("the platform can, this token cannot"). |
| `tinio-sandbox-windows` | `capability.rs` owns the predicate, `classify` and the factory. `PackageSid::derive`'s existing `Error::Launch` path classifies `E_ACCESSDENIED` into the new variant. |
| `tinio-sandbox` | The facade exposes `can_confine()` for all three platforms, answering `Ok(())` on unix; it re-exports `tinio-sandbox-core`'s `Error` unchanged, so the variant needs no per-target arm. `backend_available()` is untouched and keeps its place. |
| `tinio-cli` | `crates/tinio-cli/src/error.rs` gains a variant at exit 1, beside `SandboxBroken` and `SandboxDenied`; `sandbox_err` maps the core variant onto it instead of letting it fall through to `Error::from`. **The variant carries the core error whole** rather than its own `cause` and `remedy` fields: the `{cause} — {remedy}` join is spelled once, in the core, rather than re-typed here and held equal by a lockstep test, and the raw HRESULT rides along in the variant instead of being dropped on the way through. |

`SandboxBroken` and `SandboxDenied` keep their owner (`docs/superpowers/plans/2026-09-25-sandbox-followups.md`, section 4) and are not restated here. The distinction this design adds sits beside theirs: `Broken` says the mechanism never applied, `Denied` says it applied and refused an operation, and this one says the mechanism could not be applied **on this host** — the answer whose remedy is the operator's, not the request's.

## The doctor check

`tinio doctor` gains one row, built as every other row is (`commands/doctor/checks.rs`, the list at `:396`):

- **Check name**: `host confinement`. It appears in the human report and as the `check` field of the JSON, whose shape `doctor-report.schema.json` pins and which therefore does not change.
- **Severity**: `warn`, matching the one existing host-capability row, `free space`, which likewise reads the host and answers `warn` on a root with nothing wrong with it. `warn` is not a softer `error` here: both non-`ok` arms exit `1`, so on a machine that cannot confine `tinio doctor` **fails** even when every other row is `ok`. That is the existing severity→exit rule rather than a new one, and this design has the contract text updated to name its first instance (plan Task 10).
- **Detail**: the factory's `cause` and `remedy`, so the doctor row and the launch refusal are the same sentence.

The `doctor` contract's own rule — a command asked to diagnose a root must leave that root exactly as it found it (`contracts/cli.md` `:45`) — is not broken: the probe creates and deletes a Windows profile and touches no root. What does need correcting is a comment claiming the writability probe is "the diagnosis's one temporary write" (`checks.rs` `:562`); after this change the probe is a second and self-cleaning one, and the comment says so.

## Testing

- **The classification, driven directly.** `classify(hr)` is unit-tested without a broken host: `0x80070005` is the capability, `0x80070003` is not. The negative is a regression guard, not a formality — a greedy predicate is the defect this design is most likely to ship.
- **The predicate's verdict and its cache.** The classification half is driven directly (above). The verdict itself has **no test hook, deliberately** (plan-grilling round 2, Q11): a `testing`-featured `override_probe` has no consumer — `tinio-cli` holds no dev-dependency on `tinio-sandbox-windows` at all, and a `OnceLock` verdict would make a forced refusal order-dependent inside a shared test binary. It is exercised where it is real, in the scenario below. The `testing` feature module (`lib.rs` `:95`) remains the seam for that suite's own devices, for the crate's own reason: `#[cfg(test)]` is invisible to `tests/`.
- **The gate's behavior.** A refusal exits 1, writes no ACE, leaves no profile, publishes no `state`, and leaves no salt file.
- **Same source, not same words — for the one site that shares the subject.** `host_can_confine` (`windows_e2e_harness.rs` `:559`) derives its reason from `can_confine()`, so the sentence a skipped Windows e2e leg prints and the sentence a refused `tinio start` prints cannot drift while both stay green. **The other six `host_cannot` sites keep their own text** (plan-grilling round 2, Q10) — `sandbox_e2e.rs` `:86`, `tinio-sandbox-linux/tests/jail.rs` `:67`, `sweep.rs` `:1098`, `backend/tests.rs` `:649`, `:1313`, `:1574` — because each speaks about its own precondition (a symlink privilege, a reachable address, a live peer), and their `remedy` argument is a verbatim suffix of the sentence, so this one would substitute an unrelated action for a specific one. The factory has two consumers: the CLI's error and this single test site.
- **The harness owns no second probe.** `windows_e2e_harness::host_can_confine` delegates the profile half to `can_confine()` and keeps the scratch-directory and `icacls` halves, which test a different thing. **The ACL half names the probe's own package SID**, lent by `testing::with_probe_profile` (§The predicate), and grants to it with `acl::grant_spec(sid.as_str(), Target::Directory, AccessMode::ReadWrite)` through `testing::icacls`. What it certifies is the **principal the launcher actually grants to** rather than an account that merely happens to be the runner's, and the harness derives no profile of its own for it. **What it does not certify is the `acl::Grants` writer**: the entry is written by `icacls.exe`, so a host that can write it with the tool but not through the crate's own DACL path passes this precondition and then fails the leg itself rather than skipping it. That is the fail-not-skip side of `docs/tests.md`'s rule rather than a gap in it, and the code comment beside the call carries the same fact for a reader of the harness.
- **Two end-to-end scenarios, in `doctor.feature`** — the Low-integrity one below, and the seeded residue fixture **Risks** names, which pins that the clear-before-create keeps answering `E_ACCESSDENIED` rather than taking a leftover probe profile over. They are two because they assert two different facts: the first that a real Low token is refused, the second that the refusal cannot be produced by residue. **The Low-integrity scenario.** A host that cannot confine is reproduced for real: a helper in `tinio-sandbox-windows`'s `testing` module starts `tinio.exe` with a **Low-integrity token**. The helper needs no elevation — measured 2026-10-01: `CreateRestrictedToken` + `SetTokenInformation(TokenIntegrityLevel)` + `CreateProcessAsUserW` spawns successfully as this user, and the child's integrity is proven by differential test (the parent writes the same file the child cannot). The scenario runs `tinio doctor <root>` as that child — the **text** report, because the existing row-reading step (`steps/doctor.rs` `:521-528`) parses `render_text`'s shape and pretty-printed JSON keeps one field per line — and asserts the `warn` `host confinement` row carrying the factory's cause and the verbatim HRESULT. **It is the predicate's behavioural proof; the gate's call site is pinned by the structural test instead** (plan Task 7), because no seam exists to force the facade's answer. **The library's half is enforced by a witness rather than read from source**: `prepare_launch` takes a `capability::Admission` — a witness whose field is private to `capability`, so `admit()` is the crate's only constructor — and a run whose gate moved below the crate's first side effect would not compile, with `backend/tests.rs` recording why no source-reading leg stands in its place. **The CLI's half keeps its source-reading test over `plan.rs`**, because its gate's position relative to the resolution above it is a call order no type in that crate can enforce. `doctor` is the command that can be run under such a token at all: a launch's resolution writes the state directory above the gate, so it would die of `PermissionDenied` before the gate could answer.
- `docs/tests.md`'s fail-not-skip rule is unchanged: a suite that cannot certify fails, and `TINIO_SANDBOX_ALLOW_SKIP` stays the only opt-out. The new scenario needs no opt-out — it forces its precondition rather than hoping for it.

## Risks

- **A false negative.** A host that fails for a cause other than `E_ACCESSDENIED` passes the gate and still fails later. It fails with the cause and the remedy — the real call site is classified too, the floor above — but the promise "refused early" does not hold for it. Accepted: the alternative is a greedy classification, whose false positive is worse, and the boundary is a tested fact.
- **A false positive remains possible in principle.** `E_ACCESSDENIED` from a cause that is not the token would be reported as "this host cannot confine". No such cause was observed. The message names the observed cause as the likely one rather than as a certainty, which is why it is written as a cause and two actions rather than as a verdict, and why an unrecognised HRESULT is never cached.
- **Probe residue.** A probe killed between its clear and its delete leaves `tinio.sandbox.capability-probe` behind. **The reap is not the answer**: it is the launcher's sweep, which only runs when a launcher prepares and is skipped while another `tinio` process is alive, so a `tinio doctor` run's probe never triggers it — which is why the operator chose to make the probe immune rather than accept the residue. It **clears the name before creating it**, and a refusal while clearing is the capability answer — the same sentence, classified by the same `classify` — so the create is asked to create rather than to take over. Permission precedes existence on this host, so a refused token gets `E_ACCESSDENIED` even with the name present and never reaches the takeover (Task 4 fix round 3, re-measured by the wave-E review: Low + residue `0x80070005`, Medium + residue `0x800700B7`): the clear hardens a hole this host cannot exhibit. **The observed false negative had a different, measured cause**: a low-integrity child's create answered an unrecognised transient `0x80070020` (`ERROR_SHARING_VIOLATION`, 1/3000–2/1500 while another process churned the name), which `classify` rejects, so `get_or_probe` answered `Ok`, cached nothing and the row read `ok host confinement`; the wave-E review ranked that cause first, a child not actually reduced to Low second, and excluded the residue takeover. The residual is stated, not closed: the lock serialises only the probes that take it, so another probe can create the name between the clear and the create. A seeded e2e scenario (`doctor reports a host that cannot confine with a leftover probe profile`) pins it — a state fixture with a regression role, not the reproduction of an observed defect. The probe cannot collide with a real run's profile name.
- **Probe cost.** One profile clear-create-delete per process that asks, cached thereafter. Paid on every run that requested `--sandbox`, including runs that then fail for another reason. Measured 2026-10-01 on this host by timing the shipped profile-API sequence directly — `DeleteAppContainerProfile` (the clear), `CreateAppContainerProfile`, the SID render, `DeleteAppContainerProfile` (the type's `Drop`) and `FreeSid` — over 10 repetitions: mean **15.1 ms**, range **12.5–18.2 ms**. That is the API calls alone, from a PowerShell `Add-Type` host: the probe's own `ProfileLock`, its tracing-dispatcher swap and the run's startup are outside it. Recorded here rather than asserted in CI, because a timing assertion on this path would fail on a loaded machine for reasons unrelated to the design.
- **The gate's position can rot.** Both placements are call sites, and a later edit that moves a write above the CLI gate, or the grant phase above the library gate, silently restores the state this design removes. The gates' tests are what hold them.
- **The doctor probe is a second temporary write.** It is self-cleaning and touches no root, but it is a real side effect under a command the contract describes as read-only in intent. If a future change makes the probe costlier or non-clean, `doctor` is where it will be noticed first.

## Evidence

Measured 2026-10-01 on this Windows host, while diagnosing `tinio-sandbox-windows`'s suite:

- A test binary built under a root carrying `Mandatory Label\Low Mandatory Level`: 76 failures, every one `PermissionDenied` on a `D:\Temp` temp dir, plus `CreateAppContainerProfile: hr=0x80070005`. The same binary copied outside the tree: 120 passed.
- `whoami /groups` inside the tree reported `Mandatory Label\Low Mandatory Level (S-1-16-4096)`; the tree's root carried the same label with `(OI)(CI)(NW)`.
- Removing the root's explicit label succeeded unelevated; the inherited labels beneath it did not, returning `ERROR_PRIVILEGE_NOT_HELD` — which is why the tree, and not the label, was rebuilt.
- `icacls <file> /setintegritylevel Low` on a copy under `%TEMP%` answers `Access is denied`: writing a mandatory label needs `SeSecurityPrivilege`, which this token does not hold. The label mechanism is therefore unavailable to a test harness, and the e2e scenario uses a token instead.
- `CreateRestrictedToken` + `SetTokenInformation`(`TokenIntegrityLevel`, `S-1-16-4096`) + `CreateProcessAsUserW` **succeeds unelevated** from this token (`spawned pid=36392`). The child's Low integrity was proven differentially: the parent writes `%TEMP%\lowlabel-probe\child.txt` successfully, the child's identical redirection produces no file, and a second child run writing a fresh file in the same directory produces none either — a Medium directory refusing a Low writer, which is the same no-write-up rule as the original incident.
- The profile lifecycle cost — one clear-create-delete per process that asks — is now measured: 2026-10-01 on this Windows host, the shipped profile-API sequence (`DeleteAppContainerProfile` clear, `CreateAppContainerProfile`, the SID render, `DeleteAppContainerProfile` drop, `FreeSid`) timed over 10 repetitions in a PowerShell `Add-Type` host gives mean **15.1 ms**, range **12.5–18.2 ms** (those API calls alone, not the run's startup). `docs/superpowers/plans/2026-09-25-sandbox-followups.md` records the older shape as "Not measured"; that record stands as that phase's, and this is the number this design pays for.
