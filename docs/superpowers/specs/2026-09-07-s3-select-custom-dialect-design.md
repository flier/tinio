# Design: custom sqlparser Dialect for tinio-select (no SQL rewriting)

**Date**: 2026-09-07
**Status**: implemented — all review waves complete (2026-09-10)
**Scope**: `crates/tinio-select/src/sql.rs` (parse + validate layer), a new `dialect.rs`, a new `path.rs` + `path/grammar/object_path.pest`, `crates/tinio-select/src/engine.rs` (sentinel matching takes the request-carried name; the `__s3_is_not_missing` arm is deleted), `Cargo.toml` workspace pins for `pest`/`pest_derive`/`delegate` (+ `uuid` v4 feature on tinio-select), and — for the path-segment matching alignment (user ruling 2026-09-08 Q13) — `json.rs` (and `engine.rs`'s select-side lookup) tests + doc, no behavior-code change expected (see Path-matching alignment). Not touched: `row.rs`, `record.rs`, `output.rs`, `events.rs`, `error.rs`, `tinio-server` (both the op and the error mapping), `tinio-e2e`. The public surface `sql::parse(&str) -> Result<QueryPlan, Error>` is unchanged; `QueryPlan` gains exactly one field, `pub missing: SentinelNames` (user ruling 2026-09-08: per-request uuid sentinel names — the single interface change, superseding the 2026-09-07 fixed-name/interface-unchanged ruling on this point); `FromClause`/`PathSeg`/`Projection` are unchanged.

## Background

Today `sql.rs` parses in three stages: `reject_reserved_functions` (byte scan), `preprocess_from` (byte scan + **text splice** — the FROM path's `S3Object[*].books[0]` text is substituted with the stand-in `S3Object`), and `rewrite_is_missing` (token scan + **text splice** — each `X IS [NOT] MISSING` is spliced into the sentinel call `__s3_is_missing(X)`). Both splices are the compatibility problem: quote/comment-aware byte scanners (`ScanState`, `word_at`, `from_clause_end`, `clause_has_join`, `function_paren`), a char-position map (`positions`) for the splice offsets, the chain-overlap rejection (a splice-panic guard on untrusted input), the reserved-name scan needed *because* the sentinel is spliced into user text, and the documented misparse cases (`SELECT from FROM ...` — the scanner cannot distinguish a column named `from`).

The rewrite exists only because sqlparser 0.62 cannot parse the two constructs natively:
- **`IS [NOT] MISSING`**: no `IsMissing` in `Expr` (only `IsNull`/`IsNotNull`/`IsTrue`/`IsFalse`/`IsUnknown`/`IsDistinctFrom`); `MISSING` is a `NoKeyword` word; the default `IS` parser fails at `parser/mod.rs:3991`.
- **`FROM S3Object[*].books[0]`**: no dialect hook anywhere in table-factor parsing; `[*]` is `LBracket Mul RBracket` and nothing in `parse_object_name` consumes a bracket. Verified 0.62.0 (`Parser::parse_sql` → `parse_statements` → `Parser::parse_statement` → `dialect.parse_statement` at `parser/mod.rs:589-596`).

The change is a pure **refactor to the same AST shapes**: the hand-parse path produces the same `Statement::Query` tree the rewrite+stock-parse produced, so `engine.rs`/`json.rs`/`row.rs` and every validator keep working. `IS MISSING` keeps an `Expr::Function` sentinel representation, but the sentinel name is no longer a fixed string (uuid ruling 2026-09-08): `parse()` mints one uuid v4 per request and the single function name is `__s3_is_missing_<uuid-simple>` — constructed in exactly one place, `SentinelNames::is_missing()`. `IS NOT MISSING` produces **no second name**: it is `Expr::UnaryOp{ op: Not }` around the same sentinel call — the engine's existing `UnaryOperator::Not` arm (Bool→!b, Null→Null) is exactly the old `__s3_is_not_missing` semantics, because the sentinel-call arm always returns Bool. The engine matches the name carried on `QueryPlan.missing` (its `is_sentinel_call` single-part-unquoted shape check and `sentinel_operand` stay). Because the name is minted per request, user text cannot collide with it — the R15 reserved-name scan (`reject_reserved_functions`/`SENTINEL_FUNCTIONS`) is **deleted outright**, not replaced (see Deletions and Error surface for the one behavior consequence).

## Goal

Replace both text splices with grammar-level parsing. Alignment target: AWS S3 Select (user ruling 2026-09-08: no old-behavior compatibility, no message preservation for its own sake — every accepted construct and every error is what the new grammar defines):
1. Custom `Dialect` override of `parse_statement` (signature in 0.62: `fn parse_statement(&self, parser: &mut Parser) -> Option<Result<Statement, ParserError>>`; `None` falls back to stock) that intercepts only statements containing a custom FROM factor.
2. Custom `Dialect` override of `parse_infix` (signature in 0.62: `fn parse_infix(&self, parser: &mut Parser, expr: &Expr, precedence: u8) -> Option<Result<Expr, ParserError>>`, `dialect/mod.rs:766`; consulted at `parser/mod.rs:3735` before the `IS` token is consumed) that handles `IS [NOT] MISSING`, producing the sentinel `Expr::Function` directly (name from the request's `SentinelNames`; `IS NOT MISSING` → `UnaryOp{Not}` wrapper).
3. The FROM-path grammar written in **pest** (per user directive 2026-09-07, modeled on jsonpath-rust's `src/parser/grammar/json_path_9535.pest` — `#[derive(Parser)]`, `#[grammar = "..."]`, silent `_` rules, `$` atomic pairing; jsonpath-rust is an external layout reference only, not a workspace dependency) — no hand-written path parser.
4. New dependency pins: `pest = "2.7"`, `pest_derive = "2.7"` in the workspace (the 2.7 caret resolves to 2.9.1 in Cargo.lock; the pest semantics this design relies on — `$` compound-atomic, `^".."` case-insensitive, no implicit WHITESPACE, prefix parse — are verified green against the resolved 2.9.1 via the path/grammar test corpus); `uuid` is already workspace-pinned — tinio-select enables the `v4` feature. `unsafe_code = "forbid"` per crate — pest/pest_derive emit no `unsafe` (verify at implementation).

## Non-goals

- No new SQL features. The accepted grammar is unchanged (no JOIN/subquery/GROUP BY/HAVING/ORDER BY/DISTINCT/UNION — still rejected; channels/messages are free-form now, except the custom path's JOIN / LIMIT BY / OFFSET rejections, which keep the old `Error::Unsupported` channel and message — see Error surface). One interface change only: `QueryPlan.missing` (ruling 2026-09-08); the `parse` signature and every other shape stay.
- No sqlparser fork/patch. `Expr` stays closed; the sentinel representation (a Function call, optionally Not-wrapped) stays.
- No behavior change for statements without a custom FROM path — they never reach the hand-parse path (the `parse_statement` hook returns `None` and stock parsing runs, as today). One documented widening per the 2026-09-08 no-old-compatibility ruling: the non-custom path's alias surface is stock's own (`AS <any keyword>`, `AS 'quoted'` accepted — the deleted preprocess rejected these; pinned by `non_custom_alias_surface_is_stock`). Same stance, second widening of that surface (implementation review 2026-09-10): parens around a PLAIN `S3Object` factor — `FROM (S3Object s)` — were a preprocess parse error and are now accepted, the stock parser unwrapping the parens via `supports_parens_around_table_factor` (delegated true; already pinned `ok` by the delegation-drift corpus). The boundary is exact: a plain (non-custom) factor's acceptance surface is stock's own; a custom path inside parens (`FROM (S3Object[*].a)`) stays refused by the skeleton.
- No change to error **codes** or HTTP mapping (`Parse`/`Unsupported` → 400 `S3QueryParsingError`).

## Known boundaries (AWS/MinIO research 2026-09-08)

The published grammar is thin — four segment forms (`.{{name}}`, `['{{name}}']`, `[{{index}}]`, `.*`/`[*]`), wildcard-first required for any path (`S3Object` alone ≡ `S3Object[*] AS S3Object`; `S3Object.{{path}}` invalid), wildcard ≥1 row / `MISSING` semantics, zero-based indexes, case-insensitive unquoted attribute matching + double-quote exact + ambiguity error — all documented on the [SELECT command](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-select-sql-reference-select.html) page. **Never documented by AWS** (and the service is closed to new customers, so unverifiable): escape sequences inside `['...']` (neither `''` nor `\`), identifier character classes, whitespace inside the path, and whether the case-sensitivity rules apply at all to `['name']` path segments. **MinIO explicitly does not evaluate `FROM S3Object[*].path`** ("JSON path expressions are not yet evaluated" — MinIO docs/select/README.md), so MinIO is no authority on this construct; AWS alone. Decisions on the undocumented cells (made with the user 2026-09-08): `['name']` content is raw up to the closing quote with no escapes; the path contains no whitespace; path-segment matching is case-insensitive with an ambiguity error (mirrors the documented attribute-access rule; see Path-matching alignment).

## Architecture

`sql::parse` mints a `SentinelNames` (one uuid v4), builds an `S3SelectDialect` per call and hands it to `Parser::parse_sql(&dialect, sql)`. The dialect **owns** its copy of the sql text — the 0.62 `Dialect` trait is `Debug + Any` (`dialect/mod.rs:204`), and `Any`'s `'static` bound means a dialect cannot hold a borrowed `&str`; the struct is `#[derive(Debug)]` and stores `String` (≤ 256 KiB, once per request). It also carries: the `SentinelNames`, the one-pass custom-factor candidate (`has_custom_path_candidate`, computed once in `new` — see the hook below), and a `RefCell<Option<Vec<PathSeg>>>` output slot the hook fills (`RefCell` is legal — no `Send`/`Sync` bound on `Dialect`). Token spans are converted to byte offsets by the monotonic `SpanCursor` (`SpanCursor::new`/`seek` in `path.rs`), built once per factor parse: it refuses backwards seeks and walks forward from its own state, so each seek walks only the gap since the previous one — O(statement) per factor parse, no map, no re-walk from byte 0, no allocation — a converter only, never a splice; verified: 0.62 `Span` carries only line/column, `tokenizer.rs:556-560`, no byte offsets, so the converter is unconditionally required (2026-09-10: the per-character map and the byte-0 re-walk before it are gone). The slot holds **segments only**: the alias is never captured a second time, it is read once from the AST factor by `validate_from`. A second custom statement would overwrite the slot, but the single-statement check rejects before the slot is ever read (pinned by a test).

```
parse(sql)                          (unchanged signature)
 ├─ MAX_EXPRESSION guard            (unchanged)
 ├─ missing = SentinelNames::mint() (uuid v4; the R15 reserved-name scan is gone —
 │                                   the name is unguessable, no guard needed)
 ├─ stmts = Parser::parse_sql(&S3SelectDialect, sql)
 │    ├─ parse_statement hook: unquoted SELECT keyword AND the input has an
 │    │     "S3Object" Word + LBracket/Period candidate (one tokenize in `new`, quote/comment-safe)?
 │    │     no  → None → stock parse (unchanged behavior for all non-custom queries)
 │    │     yes → custom SELECT skeleton (stock public parsers per clause; the stock
 │    │            validator then runs on the produced AST — the skeleton is a second,
 │    │            narrower acceptance gate in front of it, not the single error source)
 │    └─ parse_infix hook: IS [NOT] MISSING → sentinel Expr::Function named missing.is_missing()
 │                          (IS NOT MISSING → UnaryOp{Not} wrapper; both custom and stock paths)
 ├─ Query-shape checks + validators  (unchanged)
 └─ QueryPlan { from ← validate_from(select, dialect.take_segments()), missing, ... }
```

### `parse_statement` hook — the custom FROM factor

The hook is called before the statement's leading token is consumed, so declining is free (return `None`, stock re-dispatches from the same position). It then reads two gates: the first token is an unquoted `SELECT` keyword, and the input carries a custom-factor candidate (`has_custom_path_candidate`, computed once in `S3SelectDialect::new` — **one linear tokenize**, quote/comment-aware by construction, fail-open on a tokenizer error so `parse_sql` reports the real one; 2026-09-10 simplify replaced the per-statement `peek_nth_token` scan, which re-walked and re-cloned tokens per index and was O(N²) at the 256 KiB cap). The candidate looks for a `Token::Word` matching `S3Object` (unquoted, case-insensitive — the tokenizer is quote-aware, so no byte scanner) immediately followed, whitespace aside, by `LBracket` or `Period`. It is **whole-input, not per-statement**: multi-statement inputs are rejected by the single-statement check anyway, and a false positive (a pathless SELECT whose projection/WHERE mentions `S3Object.`) yields an equivalent AST — the skeleton parses those positions with the same stock `parse_projection`/`parse_expr` the rewrite path used, pinned by `false_positive_projection_trigger_keeps_stock_behavior`.

The skeleton (all sub-parsers are stock and `pub` in 0.62 — verified: `parse_projection` 4823, `parse_expr` 1366, `parse_query_body` 14569, `parse_optional_group_by` 12979, `parse_optional_order_by` 13036, `parse_keyword`/`peek_keyword`/`peek_nth_token`/`next_token`, all `pub`): `SELECT` → optional `DISTINCT` (consumed into `select.distinct`; validator rejects as today) → `parse_projection()` → `FROM` → **custom factor** → optional alias (**hand-rolled** peek/ident consume, mirroring the current `take_ident`+`clause_keyword` rules exactly: quoted alias fine, `AS` required, clause keywords rejected; stock `parse_optional_alias(&[Keyword])` is close but its `after_as` arm accepts *any* keyword — verified `parser/mod.rs:12953-12960`, `after_as ||` admits any `Word` — which would loosen the current `AS where` rejection; keep our own, which means `take_ident`'s alias logic and `CLAUSE_KEYWORDS` are **retained**, see Deletions) → `WHERE` (`parse_expr` — the `parse_infix` hook is live here) → `GROUP BY` (`parse_optional_group_by`; validator rejects) → `HAVING` (peek keyword + `parse_expr` into `select.having`; validator rejects "unsupported: HAVING") → `ORDER BY` (`parse_optional_order_by`; validator rejects) → `LIMIT` (hand-parse: `parse_keyword(LIMIT)` + `parse_expr`; an optional `BY <expr>[, <expr>]*` (stock public `parse_comma_separated`) and an optional `OFFSET <expr> [ROW|ROWS]` (stock public `parse_offset`) are parsed into `LimitClause::LimitOffset` and rejected by the validator's own `Unsupported("LIMIT BY")` / `Unsupported("OFFSET")` arms — one acceptance gate, no skeleton-side duplication (2026-09-10 simplify); the MySQL comma form is *not* parsed by the skeleton — a residual `,` fails closed as a trailing-token error on the custom path, while the stock path keeps today's `OffsetCommaLimit` → validator behavior) → set-op (peek `UNION`/`EXCEPT`/`INTERSECT`; consume the op and parse the right operand with `parse_query_body`, compose `SetExpr::SetOperation` with the custom body as left; the validator's existing "unsupported: X" arm runs unchanged) → a JOIN-family word right after the factor (`JOIN`/`LEFT`/`RIGHT`/`INNER`/`CROSS`/`FULL`/`NATURAL`/`ON`/`USING`) is rejected at the clause with the old `Unsupported("JOIN")` channel and message (the `unsupported` marker, 2026-09-10). `FROM (` (nested custom path inside a derived table) and other non-S3Object factor starts return the `"invalid FROM: expected S3Object"` message the old preprocess produced for those inputs, and a `WITH`-starting custom statement is refused as the same `SyntaxError`-family (`WITH` after a custom path is unpinned in the corpus; both old and new stay request-level 400).

The `FromClause` has **one birth path** (`validate_from(select, segments) -> Result<FromClause, Error>`, 2026-09-10 simplify): `parse()` calls `validate_from(select, dialect.take_segments().unwrap_or_default())`, so the segments come from the dialect's captured slot on the custom path and are empty otherwise, while the alias is read from the single validated AST factor — the same plain `S3Object` + alias shape both paths produce, one source, no cross-check (the old code's splice-text-vs-AST alias check was real; there is nothing left to check against once the alias is only ever read off the AST, and the factor's `S3Object` name/quote checks plus the JOIN/one-factor checks are what actually guard the clause).

### Path-matching alignment (user ruling 2026-09-08 Q13)

FROM path segments participate in the same case-sensitivity model the docs state for attribute access: unquoted `.name` matches case-insensitively and a case-folded duplicate key is an `AmbiguousFieldName` error; double-quoted attribute access is exact. The implemented rule (`json_lookup`, shared with the engine's select-side lookup) already has it: `NameStyle::Bare` = case-insensitive + ambiguity error, `NameStyle::Quoted` = exact. **Gap**: the traversal feeder always passes `NameStyle::Bare` — `['name']` segments are NOT routed as quoted, so `.name` and `['name']` behave identically today. Per AWS, `.{{name}}` and `['{{name}}']` are both "by name" forms and the docs never state a distinction — and since `['name']` content is a *name designator* (not an identifier), the design decision is: **both name forms are case-insensitive + ambiguity-error; the exact-match arm stays for quoted attribute access in SELECT/WHERE only** (where AWS documents double-quote exactness explicitly). So `json.rs` needs no behavior change — the gap is doc + added tests pinning `['name']` case-insensitivity and `json_lookup` quoted-vs-bare behavior (the existing `json_attribute_lookup_case_sensitivity` test covers the attribute side).

**The custom factor** (`FROM S3Object[*].books[0] [AS alias]`): `next_token` reads the `S3Object` word (unquoted only — a quoted `"S3Object"` stays stock-parsed and is then rejected by `validate_from`, which gains a `quote_style.is_none()` check to preserve the old rejection), then the dialect slices the original sql **from the `S3Object` token's start byte offset** and runs the pest `path` rule over that slice (a **prefix** parse, no `EOI` in the rule — jsonpath's `main = ${SOI ~ jp_query ~ EOI}` style is for full matches; here we need consumed-length, and the grammar re-matches the `^S3Object` root itself). `pest` does the grammar; the dialect only walks `next_token()` while a token's start byte is below the pest `as_span().end()` byte. Two checks then close the prefix-parse gap (review 2026-09-08):

- **(a) Boundary alignment.** The sqlparser Word token class is wider than the pest `name` class (`GenericDialect::is_identifier_part` accepts non-ASCII letters, `@`, `#`, `$` — `generic.rs:35-42`; pest `name` is ASCII-only), so pest can stop *inside* a Word token (`S3Object[*].foo#bar`, `S3Object[*].café`). Walking by "token start below pest end" would consume that whole token and leave nothing behind — a silent accept with a truncated segment name (`Name("foo")`), where the old byte parser rejected via leftover bytes. After the walk, the last consumed token's **end** byte must equal `as_span().end()`; a mismatch is rejected `"invalid FROM path"`. The check is seeded with the `S3Object` token's own span end, so the zero-segment case (`FROM S3Object s` reached via a false-positive trigger, where the walk consumes nothing) passes instead of erroring. (On accept paths pest always ends on a token boundary — `]`, a name char, or `*` — so this check never fires for valid input.)
- **(b) Refused continuation.** Because `path`'s segment group is optional, the pest prefix parse **never fails** (the slice always starts with `^S3Object`). A malformed path (`S3Object.books`, `[0x]`, `['it''s']`, `S3Object[0]`) therefore doesn't produce a pest error — it leaves a `.`/`[` token behind. If the next token after the walk is `Period` or `LBracket`, report `"invalid FROM path"` (the old message family) instead of a generic trailing-token syntax error.

The pest pairs map to `Vec<PathSeg>` (Name/Index/Wild — `usize` overflow from an index pair becomes `"invalid FROM path"`, as today); the pair text is never spliced, only read. The dialect builds the AST factor separately as the **plain** `TableFactor::Table { name: S3Object, alias }` — the exact stand-in the old rewrite produced — and records `FromClause { segments, alias }` into its captured slot.

pest grammar sketch (facts verified 2026-09-08 against pest 2.x docs + sqlparser 0.62.0 source; rulings 2026-09-08: no escapes inside `['name']` — raw up to closing quote; no whitespace inside the path — no `WHITESPACE` rule is declared, and `$` (compound atomic) suppresses implicit whitespace while keeping interior tokens; `@` would make interior rules *silent* — unusable for walking segment pairs; `^"S3Object"` is an ASCII case-insensitive string match; `Parser::parse(Rule, input)` matches a prefix — `EOI` is needed only for full-match, which is why jsonpath-rust's `main` uses `${SOI ~ jp_query ~ EOI}` while our dialect calls `parse(Rule::path, slice)` and reads `as_span().end()`):

```pest
main = ${ SOI ~ path ~ EOI }              // full-text entry (tests)
path = ${ "^S3Object" ~ (first_seg ~ seg*)? }
first_seg = { "[" ~ "*" ~ "]" }
seg = _{ dot_name | dot_wild | bracketed }
dot_name = { "." ~ name }
dot_wild = { "." ~ "*" }
wstar = { "*" }
bracketed = { "[" ~ (wstar | index | quoted) ~ "]" }
name = { (ASCII_ALPHANUMERIC | "_" | "$")+ }
index = { ASCII_DIGIT+ }
quoted = { "'" ~ (!"'" ~ ANY)* ~ "'" }
```

(`EOI` appears only in `main`; the dialect calls `parse(Rule::path, slice)` and reads `as_span().end()`.) The pair walker must recurse the container rules (`path`, `first_seg`, `bracketed`) **and merge** the recursion's segments into the output — `first_seg` yields `wstar`, `bracketed` yields `wstar`/`index`/`quoted`; dropping the recursion result silently drops segments. The current `parse_object_clause` byte parser, `ScanState`, `word_at`, `from_clause_end`, `clause_has_join`, `function_paren`, `is_ident_byte`/`is_ascii_ident_start`, `expect`, `take_ident`-for-path pieces are deleted. `take_ident`'s **alias** logic is **kept** as the skeleton's hand-rolled alias consumer (see the skeleton paragraph — stock `parse_optional_alias` cannot reproduce the `AS where` rejection), and `clause_keyword`/`CLAUSE_KEYWORDS` are **kept** with it.

### `parse_infix` hook — `IS [NOT] MISSING`

The hook gets the already-parsed operand with the parser positioned just *before* `IS` (the `IS` token is the peek; stock advances only after the hook returns — `parser/mod.rs:3735-3741`). Precedence is already gated by the caller: the Pratt loop checks `get_next_precedence()` (`IS` → `Precedence::Is`, `dialect/mod.rs:853`) and breaks *before* calling `parse_infix` when `IS` would not bind (`parser/mod.rs:1411-1424`), so the hook only fires where `IS` is a valid infix — no precedence handling of our own is needed. The hook looks ahead without consuming (peek): `IS` (keyword), optional `NOT`, then a non-keyword `Word` matching `missing` case-insensitively (`peek_nth_token` skips whitespace — `parser/mod.rs:4451`). The `NOT` test must compare **`w.keyword == Keyword::NOT`** — never `Token::make_keyword("NOT")` equality: `Word::value` preserves the user's casing, so an equality check would miss a lowercase `is not missing` that the old byte scan accepted. Pattern mismatch → `None` (stock handles `IS NULL`/`IS DISTINCT FROM`/etc. unchanged). Pattern match → consume the three tokens (`next_token` skips whitespace — `advance_token`'s loop, `parser/mod.rs:4528`), build `Expr::Function { name: self.missing.is_missing(), args: List([Unnamed(Expr(operand))]), single-part unquoted }`; for `IS NOT MISSING` wrap it in `Expr::UnaryOp{ op: Not }`. Directly chained `X IS [NOT] MISSING IS MISSING` is rejected: the operand is already a sentinel — either a bare `Function(sentinel-name)` or the hook-produced `UnaryOp{Not}(Function(sentinel-name))`; both shapes yield `Err("invalid IS MISSING expression")` (the `Not` wrapper is our own production, not a user `Nested`), so matching `Not` does not weaken the ruling; `is_sentinel_expr` also recurses through `Expr::Nested` — a parenthesized chained form `(X IS MISSING) IS MISSING` is our own production when nested (the uuid name is minted only by the hook), so it is rejected with `Err("invalid IS MISSING expression")` rather than silently wrapping; a `Nested` over a plain operand (`(s.a) IS MISSING`) stays accepted; depth is bounded by the parser's recursion guard. The old `OPERAND_BOUNDARY_KEYWORDS` walk-back disappears entirely. `s.from IS MISSING` — the compound identifier parses first; no keyword-boundary hack needed.

### Deletions

`preprocess_from`, `rewrite_is_missing`, `parse_object_clause`, `ScanState`, `find_from_keyword`, `from_clause_end`, `clause_has_join`, `word_at`, `function_paren`, `skip_whitespace`/`is_word`/`token_start`/`token_end` (rewrite-scoped), `OPERAND_BOUNDARY_KEYWORDS`, `is_ident_byte`/`is_ascii_ident_start`, `take_ident` (its alias logic is re-implemented inside the dialect's hand-rolled alias consumer) die with the rewrite machinery. The (line,col)→byte converter is **kept** unconditionally — as `path.rs`'s monotonic `SpanCursor` (`new`/`seek`), which walks forward from its own state and refuses backwards seeks (0.62 spans carry no byte offsets — see Architecture); it is used only to locate the pest slice, never to splice. `clause_keyword`/`CLAUSE_KEYWORDS` are **kept** (`pub(crate)`, used by the dialect's alias consumer). `reject_reserved_functions` and `SENTINEL_FUNCTIONS` are **deleted outright** (user ruling 2026-09-08, uuid sentinels): the R15 threat was a user-authored call silently adopting MISSING semantics by naming the sentinel — a per-request unguessable name removes the collision channel entirely, and no replacement guard is needed. Behavior consequence (recorded in Error surface): a user-authored fixed-name `__s3_is_missing(x)` now parses as an ordinary unknown function and is rejected by the engine during eval (in-stream error channel), no longer a request-level 400.

### Error surface (user ruling 2026-09-08: no old-behavior compatibility; AWS-aligned, honest errors)

The dialect's `Some(Err(ParserError))` results flow through the existing `parse_sql` map (`syntax error: {e}`), unless the dialect's `unsupported` marker is set — then `parse()` returns `Error::Unsupported(kind)` instead. The marker now carries **only the JOIN-family rejection** (the skeleton parses no joins); `LIMIT … BY` / `LIMIT … OFFSET` reach the validator's own `Unsupported` arms like every other clause (2026-09-10 simplify — the marker for those two was duplication of the validator). Structured, never sniffed from the message text. No message is preserved for its old text's sake — every message is what the new grammar actually rejects:
- `SELECT from FROM S3Object s` → **rejected** (corrected 2026-09-09 after implementation review: 0.62's stock grammar fires the *empty-projection* arm — `supports_empty_projections() && peek_keyword(FROM)` at `parser/mod.rs:14742-14747`, GenericDialect delegates it true — so `from` is consumed as the FROM keyword, the second `FROM` becomes the table name, and the trailing alias fails `parse_statements`' `expected_ref("end of statement")`). The honest outcome is a stock parse error (`"Expected: end of statement, found: s"`), not an accepted `Identifier("from")` projection — the prefix-parser identifier fallback never runs because the empty-projection arm short-circuits first. Pinned by a test asserting the rejection.
- `FROM other` → the stock parser's AST reaches `validate_from`; its messages are rephrased (not pinned to the old preprocessor text). e2e pins only status/code (`400 S3QueryParsingError`, the `Bad SQL is a request-level 400 S3QueryParsingError` scenario).
- Chained `X IS [NOT] MISSING IS MISSING` → `ParserError("invalid IS MISSING expression")` when the operand is directly a sentinel call (bare or our own `Not`-wrapped shape); the parenthesized `(X IS MISSING) IS MISSING` and `(X IS MISSING) IS NOT MISSING` are also rejected `invalid IS MISSING expression` (Q2a ruling extended: `is_sentinel_expr` recurses through `Expr::Nested` — a Nested containing the per-request uuid name can only be our own production, so no user query is affected; the reasoning supersedes the original no-recursion wording, which would have silently produced wrong data for these chains).
- User-authored `__s3_is_missing(...)` (the old fixed sentinel name) → parses as an ordinary unknown function; the engine rejects it during eval (in-stream error channel), no longer a request-level 400 (uuid ruling — the R15 scan is deleted; see Deletions).
- Path/grammar mismatches → the pest prefix parse never fails (the segment group is optional), so malformed paths are caught by the boundary-alignment and refused-continuation checks (see The custom factor) and reported in the `"invalid FROM path"` family; a leftover path token the skeleton cannot otherwise place surfaces as an honest stock trailing-token error. Old message strings are not preserved unless unchanged by nature.

The `dialect` — `S3SelectDialect` implements `Dialect` by delegating to an inner `GenericDialect`. The delegation must be **exhaustive**: GenericDialect overrides ~70 methods in 0.62.0 (`dialect/generic.rs:27-312+` — not a handful), and every override returning `true` where the trait default is `false` is grammar the stock path depends on: `supports_limit_comma` (`LIMIT 3,5`, generic.rs:140), `supports_limit_by` (:272), `supports_group_by_expr` (:56), `supports_empty_projections` (:184), `supports_parens_around_table_factor` (:124), `supports_select_wildcard_except` (:100), `supports_projection_trailing_commas` (:152), `supports_filter_during_aggregation` (:220), `supports_struct_literal` (:180), the identifier-char predicates (:27-42), and the rest of the file. Missing one silently drifts non-custom-query behavior — e.g. `SELECT * FROM S3Object LIMIT 3,5` never touches the hooks, so a missed `supports_limit_comma` delegation makes it stop parsing with no test obviously pointing at the cause. The 71 forwarders are generated by the `delegate` crate's `delegate!` macro from a single signature list (user directive 2026-09-10, superseding the earlier hand-written choice); the macro emits only the listed methods, so a method missing from the list silently falls back to the trait default — the list is re-audited against `dialect/generic.rs` on any sqlparser bump and pinned by the delegation-drift corpus.

## Testing

- Existing `sql.rs` unit corpus: behavior-identical constructs must keep passing (path shapes, `IS MISSING` forms, quote/comment safety, keyword-named fields, aggregates/limit/distinct/join/group-by/order/union/subquery rejections, `referenced_columns`, `projection_needs_alias`); assertions pinned to old scanner-misparse messages (`FROM other` case) are rewritten to the new honest messages with a comment (user ruling 2026-09-08: no old-behavior compatibility). Sentinel-name assertions always read the name from `plan.missing.is_missing()` — never hardcode; whole-`QueryPlan` equality is per-parse nondeterministic (uuid), so no test may compare two parses or a parse against a hand-built plan without masking `missing`.
- Changed expectations (corrected 2026-09-09): `SELECT from FROM S3Object s` is pinned as **rejected** with `"end of statement"` (the empty-projection arm — see Error surface), and the old `reject_reserved_sentinel_functions` test is replaced by one pinning that a fixed-name `__s3_is_missing(s.a)` call parses as an ordinary unknown function.
- New: pest grammar unit tests (accept/reject corpus mirroring the old path accept/reject set, incl. `usize` overflow, `S3Object.name` first-segment rule, `$` in names, non-ASCII rejection; **unterminated quote is a pest-unit-level case only** — end-to-end it dies in `parse_sql`'s upfront tokenization before any hook runs, so the end-to-end assertion is the tokenizer error, not a pest one); pair-walker tests that catch dropped-recursion bugs (`S3Object[*]` → `[Wild]`, `[0]`/`['n']`/mid-path `[*]` segments present); dialect tests for the boundary-alignment guard (`S3Object[*].foo#bar`, `S3Object[*].café` → rejected `"invalid FROM path"`, never truncated), the refused-continuation family (`S3Object.books`, `S3Object[0]`, `['it''s']` → `"invalid FROM path"`), `IS MISSING` in projection vs WHERE vs chained (incl. lowercase `is not missing`), `IS NOT MISSING` → `UnaryOp{Not}` shape; a delegation-drift corpus on the stock path exercising the GenericDialect-true surface (`LIMIT 3,5`, `LIMIT BY`, `supports_group_by_expr`, wildcard EXCEPT, parens around table factor); captured `FromClause` equality with the old segments for the traversal corpus; a multi-statement case pinning that the captured slot is never read after the single-statement rejection; a parity harness table (each previously-spliced case → same plan/error).

## Risks

- **sqlparser 0.62 private surface**: the hand skeleton relies on `pub` methods in the pinned version (`parse_projection`, `parse_expr`, `parse_optional_group_by`, `parse_optional_order_by`, `parse_query_body`, `parse_set_operator`/`parse_set_quantifier`, `peek_nth_token`, `next_token`, `parse_keyword`s) — all verified present in 0.62.0; a future version bump can shift them (they are the same class of API the current code already depends on — the pin stays 0.62).
- **Delegation completeness**: the GenericDialect delegation list is ~70 methods in 0.62.0 (see The dialect); a missed `supports_*` that returns `true` silently drifts stock-path grammar (e.g. `LIMIT 3,5`) with no hook involvement to blame. Mitigated by the delegation-drift corpus and by re-auditing `dialect/generic.rs` on every sqlparser bump — a bump can also *add* overrides, widening the list.
- **Sentinel uniqueness/equality fallout** (uuid ruling): the name carries 122 bits of uuid v4 entropy and is constructed at one point (`SentinelNames::is_missing`), never re-parsed from user text; user collision is untargetable (the name is minted after the query text arrives). The observable costs are accepted by the ruling: `QueryPlan: PartialEq` is per-parse nondeterministic (no whole-plan asserts), and a user-authored fixed-name `__s3_is_missing(...)` degrades from request-level 400 to an in-stream engine error.
- **pest whitespace semantics**: pest's implicit-whitespace rule only applies when `WHITESPACE` is defined; the grammar intentionally defines none (atomic `$`/`@` rules) so the zero-whitespace path semantics are preserved — covered by the accept/reject tests.
- **`unsafe_code = "forbid"`**: pest/pest_derive-generated code is `unsafe`-free (the pest ecosystem builds with strict lints); confirmed at implementation; if not, pest stays and the derive-holder module gets the one `#[allow]` scoped to the generated parser with a justification comment.
- **Skeleton-drift vs stock parser**: the hand path re-sequences select clauses; a mismatch surfaces as a behavior test failure (the corpus), not silently.
- **Token/pest span divergence**: the sqlparser tokenizer and the pest grammar lex the path region by different rules; the boundary-alignment + refused-continuation checks (The custom factor) are the guard, and the dialect tests pin the known divergence shapes (wider Word class, `''` inside `['...']`, tokenizer-fails-first cases like unterminated quotes).
- **pest `$` vs `@` semantics** (verified 2026-09-08): `@` makes interior rules silent — segment pairs would be invisible to the walker; `$` keeps them and suppresses implicit whitespace — the grammar uses `$`. Also verified: implicit whitespace only with a defined `WHITESPACE` rule (none defined here); `^".."` is ASCII case-insensitive; `parse(Rule, input)` matches a prefix (EOI needed only for full-match).
- **Error-surface churn**: tests pinned to old messages are rewritten (user ruling 2026-09-08) — the corpus update surface is larger than a pure-refactor would be, and e2e remains the external gate (status/code only).
