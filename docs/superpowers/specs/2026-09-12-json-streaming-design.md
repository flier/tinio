# JSON Streaming Reader Design: LINES / DOCUMENT Dual Handlers + PathSeg Compiled State Machine

- Date: 2026-09-12
- Status: Reviewed (brainstorming process, design confirmed section by section with the user; two rounds of grilling: deviations ④⑤⑥, LFS and test shape adjudicated)
- Scope: `crates/tinio-select/src/json.rs` refactor; `tinio-select/Cargo.toml` gains one already-pinned dependency; git LFS introduced for the first time (test fixtures) + CI checkout adjustment
- Language: English. Originally written in Chinese under an explicit user exemption; translated to English on 2026-09-15 at the user's request, which ends that exemption.

## Background and Problem

S3 Select JSON input has two framings (`InputSerialization.JSON.Type`): LINES (one JSON value per line) and DOCUMENT (the whole stream is one JSON document; when the root is an array, each element is a record). The current implementation, `json.rs`, is a single `Reader<R>` that dispatches by type inside `next()`:

- LINES (`read_line`): the whole line is read into a `Vec<u8>` (≤ 1 MB line-width cap), then `serde_json::from_slice` materialises it wholesale into one `Value`, which then goes through `apply` candidate-set expansion.
- DOCUMENT (`read_document`): the whole document is read into a `Vec<u8>` (the only line of defence is the whole-document ≤ 1 MB cap) → materialised wholesale → the `pending` queue expands every root element in one go. Three full allocations (bytes, `Value`, `pending`); a document > 1 MB errors outright (`document_input_record_cap`).

Goal: each of the two modes parses and processes in streaming fashion, so that at any moment only the current record is materialised, with a memory bound of one record (≤ 1 MB) independent of total input size; a large DOCUMENT is no longer loaded wholesale. The engine contract (`RecordReader` in `record.rs`: `next() -> Result<Option<Record>, Error>`, `Record::Json(Option<Value>)`) means a record must in the end be fully materialised — the point of streaming is to converge the memory bound onto one record, not onto zero.

Non-goals: streaming the CSV / Parquet readers; making the `RecordReader` pull contract asynchronous (the crate keeps synchronous pulling, `unsafe_code = "forbid"` unchanged); any change on the output side (event packaging); per-column cloning on the engine's select side.

## Overall Architecture

`json.rs` is split into a `json/` directory:

- `json/mod.rs` — module documentation (rewritten, including the deviation record of this design), `Type`, `Params`, the dispatch entry point `Reader` (`enum Handler { Lines, Document }`), the `pub(crate) use value::{json_lookup, to_value};` re-export (`engine.rs` still resolves via `crate::json::{to_value, json_lookup}`; call sites unchanged), shared test helpers and engine composition tests. (**Amended 2026-09-13**: the shared test helpers are split out into `json/testing.rs` (`#[cfg(test)]`) — the 20 migrated cases span the lines/document test modules and reference the same helper set; the engine composition tests stay in mod.rs.)
- `json/value.rs` — `to_value` and `json_lookup` moved in as-is (no behaviour change).
- `json/framing.rs` — the framing filters (`Read` adapters): `LineFraming`, `DocFraming`, `BudgetedRead`.
- `json/matcher.rs` — `CompiledPath` (the PathSeg compilation product) + the `StepSeed` visitor state machine.
- `json/lines.rs` — `pub struct Lines<R>`: the LINES handler driven by line framing.
- `json/document.rs` — `pub struct Document<R>`: the DOCUMENT handler driven by document framing.

Interfaces stay unchanged: the `json::Reader::new(reader, params, from)` signature is unchanged; `build_reader` in `events.rs`, the ScanRange tests in `record.rs`, and the parameter mapping in `tinio-server`'s `backend/select.rs` are all untouched; the `Record::Json(Option<Value>)` record model is unchanged. The old `apply`/`expand`/`read_document`/whole-line `parse` are deleted. `tinio-select/Cargo.toml` gains `serde.workspace = true` (the workspace already pins `serde = "1"`; `serde_json` pulled it in transitively anyway, so the transitive closure does not grow at all).

## Parsing Kernel

Everything goes through serde_json streaming deserialisation: `serde_json::Deserializer::from_reader` (serde_json's `StreamDeserializer` same-family mechanism) + per-value pulling. serde's `MapAccess`/`SeqAccess` pull callbacks are the event stream, driving the compiled `StepSeed` state machine directly:

- Unmatched subtrees are consumed by a **hand-written validating skip, `Skip`** — it takes `deserialize_any` (never `deserialize_ignored_any`: that consumes the value before any visitor runs) so that strings arrive as `&str`, are validated and then discarded; `visit_seq`/`visit_map` recurse into themselves, and keys pass through it too. Nothing is materialised; memory stays O(1). **Amended 2026-09-13**: the original plan was to use `serde::de::IgnoredAny` and claim that "serde fully validates the whole stream… no validation gap" — checking against the serde_json 1.0.151 source shows this does not hold: `IoRead::ignore_str` (`read.rs:348-366`) only validates escape shape and the digit count of `\uXXXX`, **does not validate surrogate pairs** (`ignore_escape` does not go through `parse_unicode_escape`) and **does not validate UTF-8** (the skip branch does not pass through `str::from_utf8`), so input such as `{"a":1,"b":"\uD800"}`, which `from_slice` rejects today, would be silently accepted. `Skip` fills this in point by point; validation coverage matches today's.
- Only subtrees hit at the final step are materialised into `serde_json::Value`; `arbitrary_precision` numbers keep the original token (the normalisation of `1e309` → `1e+309` is done by serde; `raw_number_passthrough_no_decimal_parse` semantics unchanged).
- Keys are decoded by serde via `next_key::<String>()` (`\uXXXX` escapes handled automatically); skip scopes use `next_key::<IgnoredAny>()` to avoid per-key allocation. **(Amended 2026-09-13, second round)** Skip scopes actually use `next_key_seed(Skip)` — likewise allocation-free, and the key content goes through `Skip` validation (point by point identical to today's `from_slice`); `IgnoredAny` is abandoned entirely (see the Amendment to the `Skip` item in this section).

Why not use `StreamDeserializer::into_iter` directly: it can only produce whole top-level values (a root array is returned as one whole value), and it cannot suspend in mid-value, so it cannot achieve "each pull = one record root". Hence a framing filter reshapes the byte stream (see the next section), and from_reader + `DeserializeSeed` pulls value by value.

Rejected alternatives: a hand-written boundary scanner + a resumable explicit-stack state machine (that scheme's resumable stack and element-level offsets hold up, but the scanner only judges boundaries, not scalars, so an illegal scalar in a skipped region would no longer be reported, conflicting with the ruling that "serde's full validation takes priority" — grilling Q2 therefore ruled to adopt only its element-level offsets, its tests and its delivery approach; its original draft was deleted on 2026-09-13 per user instruction and is not kept separately); serde `SeqAccess` + a worker thread + a channel (one thread per query, `R: Send + 'static` contagion, cross-thread error propagation, violating the crate's synchronous pull model).

## The PathSeg Compiled State Machine

Compilation: `CompiledPath::from_segments(segments: &[PathSeg])`. **(Amended 2026-09-13)** The original signature was `from_segments(segments: &[PathSeg], ty: Type)`; the root rule is already carried by framing (see the next item), the matcher never branches on `Type`, and that parameter was never used — it is removed, and the call site and the `Type` import go with it (review finding: Speculative Generality).

- The root rule (the implicit `S3Object[*]`, consistent with the status quo and independent of whether `[*]` is written explicitly) is carried by framing: in LINES each line is one root (empty input = zero roots, zero lines); in DOCUMENT an array root is per element, anything else is a single whole root, and an empty array `[]` → the handler supplements one MISSING (zero-hit rule).
- Step sequence: with a leading `Wild` dropped from the segment list, it compiles to `Vec<Step>`, `Step = Name(String) | Index(usize) | Wild`.

Execution: `StepSeed` holds `{ steps, depth, pending: &mut VecDeque<Option<Value>>, budget }` and implements `DeserializeSeed`; the visitor dispatches on `steps[depth]`:

- `visit_map` + `Name(n)`: the decoded key is compared with `eq_ignore_ascii_case`; on a hit, recurse `next_value_seed` with `depth+1`; a second case-folded hit within the same object → `Error::Ambiguous`. Values of unmatched keys are skipped with `IgnoredAny`.
- `visit_seq` + `Index(i)`: an ordinal count; only the i-th element recurses, the rest use `IgnoredAny`.
- `visit_seq`/`visit_map` + `Wild`: recurse per element / per member value; an empty container → zero hits.
- The container visit ends with a hit count of 0 → enqueue one `None` (MISSING short-circuit propagation, equivalent to the old `apply`'s `None → None`).
- A step applied to a scalar (`visit_bool`/`visit_i64`/`visit_u64`/`visit_f64`/`visit_str`/`visit_unit`) → zero hits → one `None`.
- `depth == steps.len()` → the current value is a hit: after arming the `BudgetedRead` budget, `next_value::<Value>()` / `Value::deserialize` materialises it into the queue.
- **(Amended 2026-09-13, Q9(a)) Three items in this section are outdated; the Amendments in §Framing Filters and deviations ①③ take precedence**: ① `StepSeed`'s fields are actually `{ steps, pending, failure }` — no `budget` (the cap is instead armed by the handler per root pull), no `depth` (dispatch is on `steps[0]`, recursion on a sliced sub-seed), and `failure` records `Error::Ambiguous`; ② the budget is no longer armed per value before a hit is materialised (per-value arming accumulates across hits and raises false positives); ③ unmatched subtrees always use the hand-written validating `Skip` (see the §Parsing Kernel Amendment), not `IgnoredAny`.

Two semantic pillars:

- Order equivalence: the output order is point-by-point identical to the old `apply`'s order-preserving expansion over candidates (lexicographic DFS); all existing traversal-order tests are kept.
- Streaming handling of ambiguity: the ambiguity determination is only complete when the object closes. **A final-step Name defers output** — the hit value is first materialised into a holding slot (one value ≤ 1 MB, bounded), the rest of the object is scanned, and on close it is enqueued only if there is no duplicate, otherwise `Ambiguous` is reported; hence the two pinned tests `traversal_case_insensitive_duplicates_are_ambiguous` and `traversal_bracket_name_duplicates_are_ambiguous` pass unchanged. A non-final-step Name (whose row count below is unbounded and cannot be buffered) errors as soon as a duplicate key is found in the stream, having possibly already produced some rows within that object — consistent with the existing contract for parse errors, that "data-dependent errors surface mid-stream" (see "Semantic Deviations").

## Framing Filters

Two `Read` adapters plus one quota wrapper make "each serde pull = one record root" and enforce the 1 MB cap mid-read:

- `LineFraming`: supplies only the content bytes of the current line at a time (excluding `\n`); when the line is exhausted it is EOF, and after a reset it supplies the next line — a line is no longer read into memory whole. Line width (content + terminator) is counted while supplying, and exceeding 1 MB errors immediately (`lines_input_record_cap` / `lines_input_record_cap_exact_span_allowed` semantics unchanged). Empty line → EOF at the first byte → serde reports "EOF while parsing a value" → `Format` (`empty_line_is_a_format_error` semantics unchanged).
- `DocFraming`: root-shape probing — if the first byte after skipping leading whitespace is `[` → array mode: top-level `[`/`]`/`,` are not supplied (swallowed), a virtual whitespace byte is injected at element boundaries (cleanly terminating number-like tokens), and top-level separators are validated (a non-`,`/`]` after an element errors; `[1,]` and `[1 2]` error; a non-whitespace after `]` errors) — each `StepSeed` pull parses exactly one element. Not `[` → single-value mode: the whole stream is passed through as-is, in one pull. String awareness (a `\` skips one byte) keeps the top-level determination correct; if the depth has not returned to zero at EOF → serde naturally reports "EOF while parsing". The filter accounts by its own bytes to give each element's first-byte offset (for the record offset of deviation ⑥).
- `BudgetedRead`: a 1 MB budget (a shared `Rc<Cell>` handle) is **charged per root pull** — the handler calls `reset()` once at the start of each pull (**Amended 2026-09-13**: this was originally the pair `arm()`/`disarm()`; `BudgetedRead` only lives inside the pull block, so the `armed` flag is always true and `disarm` has nothing to do — removed), and the accounting covers **every byte** supplied during that pull: hit values, skipped subtrees and separators alike. Reading past the budget immediately raises an io error and sets a flag; on seeing the flag the handler returns exactly `Error::Format("input record exceeds 1 MB")` (CAP_MESSAGE unchanged word for word). **The invariant: "one pull = one root ≤ 1 MB"** (in array mode one element, in single-value mode the whole document); unmatched subtrees no longer have an exemption gap. LINES has a line-width cap as well; both produce the same message. **(Amended 2026-09-13)** The original design was "arm before the matcher materialises a hit value" (charging per hit value): measured, this accumulates across hits — if the hit set contains several elements of 400 KB each, the second element is already misjudged as over the limit and reported as a cap error, even though its record is itself far below 1 MB; and unmatched subtrees are not armed at all, so a cap mid-framing cannot be charged either. After switching to arming per root pull, `document_input_record_cap_exact_allowed` (a single-value root of exactly 1 MB) passes right on the line at 1 048 576/1 048 576. **(Amended 2026-09-13, second round)** The "separators" above means bytes that **are supplied**, such as the injected virtual whitespace; top-level `[`/`]`/`,`, whitespace swallowed by `skip_ws` and LINES' `\n` are swallowed inside framing and do not go through `BudgetedRead` — they are constrained by framing's own span/offset accounting (which is exactly the path the LINES line-width cap takes).

## Handlers

- `Lines<R>`: holds one `Deserializer::from_reader(LineFraming)`; one `StepSeed` pull per line (line = one root), then a second pull to probe the end of the line: producing a second value or reporting a non-EOF error → trailing-garbage `Format` error (aligned with `from_slice`'s trailing behaviour); `err.is_eof()` → the line ended cleanly. `last_record_start` is accounted by the line start (`lines_last_record_start` unchanged).
- `Document<R>`: `Deserializer::from_reader(DocFraming)`; loop: the filter reports a next element → `StepSeed` pulls one element. `[]` → zero elements → supplement one `None` (start 0); empty input (zero bytes) → zero records; pure whitespace → `is_eof` on the first pull → `Format` (same as today); in single-value mode, a second pull after the root value probes for trailing data (`{} x`, `5 {}` → `Format`). `last_record_start()` = the first-byte offset of the current root element (a MISSING row takes the start of the element it was derived from; a single-value root = the root value's first byte) — deviation ⑥.

`pending` boundedness: LINES ≤ one line's hit set (line ≤ 1 MB); DOCUMENT array mode ≤ one element's hit set; DOCUMENT single-value mode = the whole document's hit set accumulating within one pull, and that pull is likewise charged against the 1 MB budget, so exceeding it is a cap error (see "Semantic Deviations" ③, **Amended 2026-09-13**).

## Error Handling

serde errors and filter io errors are uniformly mapped to `Error::Format(format!("json input: {e}"))` (`is_eof()` distinguishes a clean record end from a format error; no string matching is done); the cap is mapped, via the `BudgetedRead` flag, to the word-for-word unchanged `"input record exceeds 1 MB"`; the `Error::Ambiguous` path is unchanged; `json_lookup` on the engine side is untouched (the single implementation keeping the case rule consistent with the traversal side is still in place).

## Semantic Preservation and Deviations (user-confirmed)

Invariants: `[]` → exactly one MISSING; LINES empty input = zero lines; an empty document = zero records; a pure-whitespace document errors; trailing garbage at the end of a line/document errors (strictly probed before records are produced); an empty line errors; the LINES 1 MB line-width cap and line-start accounting; scalar serde semantics (including `1e+309`); no validation gap in skipped regions; byte-level duplicate keys are serde last-wins (grilling Q3 ruled against extending Ambiguous to them); apart from the filler input of the two tests listed in deviation ④, the entire existing test suite passes unchanged.

Confirmed deviations:

1. DOCUMENT total size unbanned — the 1 MB cap changes from "the whole document" to "**each root**" (in array mode each element, in single-value mode the whole document). An array document whose elements are each ≤ 1 MB can be streamed at any size; a single-object/scalar root > 1 MB still errors (the documents of the two existing cap tests are themselves single scalar records, so they pass unchanged). **(Amended 2026-09-13)** The wording changes from "each produced record" to "each root": the cap is charged per root pull, so an unmatched element, though it produces no record, is equally bound by the 1 MB limit (charging per hit would miss it).
2. Relaxed error timing for ambiguity on a non-final-step Name — a duplicate key found in the stream errors immediately, having possibly already produced some rows within that object; a final-step Name is still strict (output deferred until the object closes).
3. Single-value root hit set accumulates per document — a DOCUMENT with a single-object root + a deep wildcard accumulates all of that document's matching records in one pull; an array root (the mainstream large-document scenario) is unaffected and bounded per element. **(Amended 2026-09-13)** This case is **not unbounded**: that pull is likewise charged the 1 MB budget per root, so a document exceeding 1 MB overall returns `Error::Format("input record exceeds 1 MB")` rather than accumulating without limit. (Before 2026-09-13 this case was described as "this case is unbounded", which did not match the per-root-pull charging implementation; revised per Q15.)
4. Priority between the LINES cap and parse errors — parsing is entirely handed to serde_json, and under streaming it parses as it supplies: a line with illegal content may report a serde parse error before reaching the line-width cap; the cap is still enforced mid-way for well-formed lines (memory boundedness unchanged). The filler input of the two tests `lines_input_record_cap` and `lines_final_unterminated_line_over_cap` switches to a legal JSON shape; the assertions are unchanged (the cap message is word for word; the exactly 1 MB boundary is still pinned by the already-legal `lines_input_record_cap_exact_span_allowed`).
5. Streaming of DOCUMENT error timing — document-level format errors change from "all or nothing" (whole-document parsing, where any error zeroes every record) to per-element exposure: records before the failing element have been produced, and the client receives Records events first and the error event afterwards. LINES is already per-line streaming semantics today, so it is unchanged; in single-value mode, trailing garbage after the root goes through the "pull + probe" pairing and is still reported before any record is produced.
6. Real per-element offsets in DOCUMENT and ScanRange filtering (extension) — a record (including MISSING) reports the first-byte offset of the root element it was derived from (single-value root = the root value's first byte; empty-array zero-hit MISSING = 0), and `last_record_start` is no longer always 0 under DOCUMENT; the ScanRange window filters DOCUMENT by record start (AWS documentation restricts JSON ScanRange to LINES-only; recorded as an extension); `BytesProcessed` (the difference between adjacent starts) settles as the scan advances rather than all at once at EOF (in implementation the final value = `scanned − first element's start`, i.e. −1 for a `[...]` root: the first byte `[` belongs to no record; under the former whole-document accounting it was always equal to `scanned`); **(Amended 2026-09-13)** an EOF falling **inside** a value (a truncated element, a truncated single-value root) must be a `Format` error — `[]` versus "EOF mid-value" is distinguished by framing's "whether the top-level `]` has been consumed", otherwise `["abc` and `[{"a":` would be taken as a clean empty array; the `document_start_above_zero_yields_nothing` assertion is kept (its single-object root input starts at byte 0 anyway, and `start = 1` still discards), and the comment drops the byte-0 rationale; the 2026-09-04 byte-0 pin is replaced by a supersede annotation (see "Synchronised Updates").

## Test Plan

Migration: the LINES tests → `lines.rs`; the DOCUMENT tests → `document.rs`; the engine composition tests (the `run`/`run_err` helpers and the AWS examples) stay in `mod.rs`. Exception (deviation ④): the filler input of `lines_input_record_cap` and `lines_final_unterminated_line_over_cap` switches to a legal JSON shape (`{"x":"<…>"}`), with the assertions unchanged — beyond that, not a single line of any existing test is touched.

New:

- `document_array_larger_than_1mb_streams`: 4 × 400 KB elements (total > 1 MB) → four records, no error — the main pin for deviation ①.
- `document_element_over_cap_errors_after_prior_records`: one element > 1 MB → an in-stream `Error::Format("input record exceeds 1 MB")`, with records before the failing element already produced and later elements no longer produced (also pins deviation ⑤). **(Amended 2026-09-13, second round)** Originally named `document_element_over_cap_errors`; renamed to align with the plan implementation.
- Matcher matrix: a zero hit at each of the Name/Index/Wild steps → exactly one MISSING; MISSING short-circuit propagation; nested-wildcard DFS order; Index out of range; final-step Name defers output + ambiguity; non-final-step Name ambiguity errors in-stream; escaped key (`"R\u0075les"`) matching. **(Amended 2026-09-13)** Plus two cap-attribution tests: `element_barely_under_cap_is_accepted` (a record delivering exactly `MAX_RECORD` bytes must pass — arming per hit value would under-count the opening-quote byte and wrongly reject it) and `budget_is_charged_per_root_not_accumulated` (a document of four 400 KB elements totalling ~1.6 MB must not falsely report a cap on the 2nd element).
- Framing: `[1,]`, `[1 2]`, `[1] x`, end-of-line garbage, a pure-whitespace line, a pure-whitespace document → `Format` containing `json input`; EOF in an unclosed document → `Format`; scalar roots (`5`/`"x"`/`null`); nested array elements (`[[1],[2]]`).
- Row-order table-driven cases: wildcard fan-out interleaved with MISSING, nested wildcards, Index misses (enumerative reinforcement of `apply` order equivalence); CRLF line coverage (zero coverage today). **(Amended 2026-09-13)** Plus an indented-line case: `last_record_start` reports the first byte of the **line** (i.e. the start of the indentation), not the value's first byte.
- Deviation ⑥: a root array + a `ScanRange` window filtering by element start; record starts monotonically non-decreasing (including MISSING rows); empty-array MISSING start 0.
- CI large-document streaming test (`tests/stream_large.rs`): a gzip-compressed fixture in git LFS (`tests/fixtures/large/document.json.gz`, ~64 MB decompressed, a pretty-printed array of small objects), read through the production-identical `record::decompressed(Some(Compression::Gzip), …)` path, asserting row count, cap behaviour, completion and monotonic offsets — the test itself does not land the decompressed bytes. **(Amended 2026-09-13, second round, user-adjudicated)** Scale 400k elements/~64 MB → 100k elements/~16 MB: the four assertions do not depend on a larger size, and the CI per-byte parse cost drops to about 1/4.
- Memory-peak gate (`tests/stream_memory.rs`, one file, one `#[test]`): a counting `#[global_allocator]`, asserting a loose peak upper bound (~32 MB) while streaming the same fixture — a regression tripwire rather than a measurement; one file so that the multithreaded harness does not count other tests' allocations. **Amended 2026-09-13**: `[lints.rust] unsafe_code = "forbid"` (`crates/tinio-select/Cargo.toml:51`, **a per-crate setting**) covers every target of this crate (including `tests/`) and cannot be overridden by `allow`, so a counting `#[global_allocator]` cannot land; instead, an in-crate `#[cfg(test)]` `pending_high` high-water-mark pin, and `tests/stream_memory.rs` is dropped. **This pin counts bytes** (the serialised length of the `Value`s accumulated into the queue): by a count-based measure "one 1 MB value" and "5 000 values of a dozen-odd bytes" are the same number while their memory differs by three orders of magnitude, which has nothing to do with the memory promise it is meant to guard. The array-root assertion is at the one-element order of magnitude (`document_array_root_keeps_pending_bounded`); deviation ③ is instead pinned by `document_single_root_under_cap_yields_all_matches` (one pull produces every match, with the peak backstopped by the cap) and `document_single_root_over_cap_errors` (over 1 MB is a cap error). This pin is cross-platform, needs no unsafe and no fixture, and directly pins the design promise itself.
