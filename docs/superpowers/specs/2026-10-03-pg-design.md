# Design: the PostgreSQL persistence store (`tinio-store-pg`) and the pg backend (`tinio-pg`)

**Date**: 2026-10-03
**Status**: draft — operator review. Decisions taken with the operator on 2026-10-03 (rounds 19–39 of the metadata-store contract design's question set; each is tagged). §1–§2 are **adopted, not authored here**: they are the spike's verdict and shape fixes, taken verbatim from `docs/superpowers/pg-meta-spike-findings.md` when P3 starts. Round 38 is post-audit: an independent six-lane review found the store's content model could not keep the visibility and reclamation promises, and its findings are folded in (PG18–PG25).
**Scope**: the PostgreSQL implementation of the four persistence contracts (`tinio-store-pg`) and the backend built on it (`tinio-pg`) — schema and migrations, connection, TLS and pool policy, content storage, configuration and invocation, the read-only mode, ownership, cleanup, and the `@pg` test pass. Not touched: the persistence contracts themselves, the shared operation bodies (`tinio-ops`), and every other backend.

## Background

The metadata-store work line validates its four persistence contracts against PostgreSQL *before* anything depends on them: a workspace-excluded spike (`spike/pg-meta/`, P1's Task 2) implements the metadata contracts, `VersionMeta` and the whole `ObjectContent` surface over `postgres:18-alpine` and runs the conformance suite. That spike was written for one purpose — proving the contracts — and deliberately carries none of a crate's engineering: no library surface, no error type, no pool, no TLS, no migrations.

This document covers what comes after: P3 promotes the spike into `tinio-store-pg` and completes it, and P5 builds `tinio-pg` over the shared ops engine with configuration, TLS, read-only support, cleanup and a cucumber pass.

**Why this document is longer than its first draft**: the audit (round 38) showed that a chunked `bytea` store cannot keep the contracts' promises by accident. A row cannot "name" its chunks without a generation/base marker (an overwrite would let a reader serve a mixture of two objects' bytes); `BlockStore` requires a block's length and a comparable publication time, which the first schema did not carry, and a multi-statement publish needs a completeness rule or an interrupted publish is served forever as truncated content; a chunk row without an object row is not an object, so `scan` must be row-backed here; and the operational surfaces (a locks' liveness, a read-only role, a migration remedy that is not "delete the database") are part of the design, not deployment details.

## Goal

1. **`tinio-store-pg` is a real crate** implementing all four contracts with schema versioning and migrations, an error type projecting into `storage::Error`, TLS-capable pooled connections, and the conformance suite green from its own tests.
2. **`tinio-pg` is a servable backend** over `tinio-ops`: the `Storage`/`VersionOps`/`Cleanup` implementations, the `[storage] type`/`[storage.pg]` configuration, the synthetic root, the session read-only mode with a restricted role, the writable-ownership guard, doctor checks, and a serialized `@pg` cucumber pass in CI.
3. **PostgreSQL-specific behavior is stated, not implied**: ordering and encoding, read-only, content chunking and generations, connections and TLS, migrations and their remedy, cleanup, and the supported topologies.

## Non-goals

- **No ORM, and no compile-time-checked SQL.** `sqlx` with explicit runtime statements (`sqlx::query` + `.bind()`), never the `query!`/`query_as!` macros (PG26): **values are always bound parameters; table and column identifiers come only from the fixed schema** — a statement built by formatting is a defect, and `Cleanup`'s scan-shaped SQL is where one would appear. A macro form would make every `pg` build need a database or a committed offline cache, which PG8 forbids.
- **No multi-writer topology.** One writable instance owns a database (PG12).
- **No pg-specific persistence contract.** Where PostgreSQL cannot satisfy a rule, that is a scope finding (the contract changes, not the schema).
- **No multi-tenant or RLS design.** One database per served instance; the dsn carries credentials; no namespace prefix.
- **No `tinio-pg`-specific S3 semantics.** The operations come from `tinio-ops`; this backend supplies storage, hooks, configuration and lifecycle.

| PG6 | Read-only (FR-023) is a session-level read-only connection **and a role without `INSERT`/`UPDATE`/`DELETE` grants**: the entry guard answers `AccessDenied` first, and the privileges are the second guard that actually holds when a helper bypasses the entry | 26, 38 |

| PG9 | The pool is the driver's own pool (PG26), sized by `[storage.pg] pool` (default 8), with a connection timeout and a health check | 33 |
| PG10 | TLS uses the driver's rustls connector with the **system trust store** (PG26); the mode set is `disable`/`prefer`/`require` (**`verify-ca`/`verify-full` are not tokio-postgres modes**), `require` performs chain **and** hostname verification, and **an omitted `sslmode` is treated as `require`**, not as the client's `prefer` default: plaintext happens only with an explicit `sslmode=disable`, and the negotiated mode is logged and shown by `doctor` | 33, 34, 38 |
| PG11 | Migrations run **automatically at startup**, forward-only, each step in its own transaction, under an advisory lock held on a **dedicated out-of-pool connection** with its own key and a bounded wait; a failure refuses to start; a database **newer** than the binary is refused. The remedy is **not** the redb one: the bytes live only here, so it names the required binary/schema version and a dump/restore path — never "delete and rebuild". A read-only instance never migrates and refuses a mismatch; `doctor` reports the applied version and any pending migration **through a non-migrating inspection path** | 33, 38 |
| PG12 | **One writable instance per database**: `PgStore::hold_ownership()` opens a dedicated out-of-pool connection, takes a process-lifetime advisory lock under a named key, and **re-verifies it on a cadence** — the re-verify is also what keeps the connection's TCP path warm, because the driver exposes no keepalive knob (PG26) — losing it terminates the process (or drops it to read-only), because a silently released lock is exactly the two-writer corruption this rule exists to prevent. Read-only instances take no lock and coexist (≤1 writable + N read-only); `doctor` prints the owner | 34, 35, 38 |
| PG13 | A positional `DIR` (or a discovered `.tinio/` root) under `[storage] type = "pg"` is a **usage error** naming the remedy | 34 |
| PG14 | `PgBlocks` **chunks a block internally** (8 MiB rows, transparent to `BlockStore`), because the engine's v1 policy stores a whole blob as one block and a `bytea` field caps at 1 GB | 36 |
| PG15 | `pg` gates the crate's dependencies and code; **`pg-tests`** (non-default) gates the DB-backed tests; `pg` joins `crates/tinio`'s `full` set, so the released binary can serve this backend while the default workspace leg stays database-free | 36, 38 |
| PG16 | `pg` and `versioning` are orthogonal features of `tinio-pg` (`versioning` gates its own version module and the `VersionOps` twin; `tinio-store-pg`/`tinio-ops` carry no `versioning` feature at all) | 38 |
| PG17 | The `@pg` pass runs the backend-neutral scenarios plus `@pg`-tagged ones (fs-specific scenarios are tagged `@fs`), resets the database per scenario (truncate + re-migrate + construct), and is **serialized**; its exclusion is a fifth axis in the e2e default filter and `not @pg` joins the mem pass's list | 38 |
| PG18 | **Content carries a discriminator and a generation.** The rows are keyed by `(bucket, kind, key, seq)` with `kind ∈ {object, part}`, and the object's row records **which generation is live** (a base sequence or a generation id): an overwrite writes a new generation and the row's update is what makes it live, so a reader can never mix two generations' bytes and a partial publish is invisible. The **form** (a `base_seq` column, a generation id, or an in-place replace inside the row's transaction) is the spike's to pin against real PostgreSQL; the requirement is not | 38 |
| PG19 | **`blocks` carries `len` and `published`** (a comparable timestamp on the caller's clock): `BlockStore::list`/`Entry` require both and neither can be derived from the chunks alone. A publish is **complete or absent**: every chunk row is written with `ON CONFLICT DO UPDATE`, a repeated publish fills gaps rather than answering `Existing` on a partial block, and "some rows, not all" reads as not present | 38 |
| PG20 | Part chunks share the content relation with `kind = 'part'` and their own collision-proof key namespace (the spike pins the encoding); `scan` filters `kind = 'object'`, so a part can never be enumerated or opened as an object | 38 |
| PG21 | The **multipart completion's assembly** is stated per backend: pg's requirement is that it never rewrites the whole object if the layout can avoid it (a part-list indirection, or a copy under a new generation made live by the row's update), and that a partially assembled object is invisible; the spike pins the form | 38 |
| PG22 | A publish's **transaction boundary is bounded**: either the chunks commit in batches under an incompleteness marker (a partial object is unreadable until the row makes it live), or the backend declares a maximum body size. The spike measures and pins which; an unbounded single transaction (a 100 GiB PUT as 100 000 statements) is not acceptable | 38 |
| PG23 | **`scan` is row-backed for pg**: a chunk row without an object row is residue, not an object, so pg's `scan` enumerates keys that have a live row (a join, or the metadata plane as the source) — the opposite of fs's content-is-truth rule, and the reason the engine's listing heals rather than assumes | 38 |
| PG24 | The chunk columns are declared `STORAGE EXTERNAL`: object bytes are usually incompressible, and detoasting a value for a 4 KiB range read would decompress the whole chunk | 38 |
| PG25 | The credential check is **scoped** so it can hold alongside the mandated DB tests: tests read the dsn from `TINIO_PG_DSN`, and the only literal lives in `docker-compose.yml` — the command is `rg -n 'postgres://[^"]*:[^"]*@' crates --glob '!**/tests/**' --glob '!**/docker-compose.yml'` (P3 Task 5 Step 2 owns it) | 38 |
| PG26 | The driver is **`sqlx`** — it supersedes the driver *crate* choice rounds 33/34 pinned for PG9/PG10, whose **policies** stand: `sqlx::PgPool` is the pool, `PgConnectOptions` (with the `tls-rustls-ring-native-roots` feature — rustls over the system trust store) replaces `tokio-postgres-rustls` + `rustls-native-certs`, and statements are runtime `sqlx::query`/`.bind()`, never `query!` (the non-goals say why). Two mappings are the store's, not sqlx's defaults: an omitted or explicit `sslmode=require` becomes **verify-full** (chain *and* hostname), because sqlx's own `Require` stops at the chain and never checks the hostname, and the remaining modes map one-to-one. A migration step and a publish batch are each one `sqlx` transaction; both advisory locks stay on dedicated out-of-pool `PgConnection`s | 39 |

### §3 Schema and migrations

Tables (names, columns and types are the store's, not the contracts'):

| Table | Key | Carries |
|---|---|---|
| `buckets` | `name` | creation time, tags wire, owner wire, ACL wire, CORS wire |
| `object_meta` | `(bucket, key)` | etag, size, mtime, identity, tags, checksum, owner, ACL, the current version's id and sequence, and **the live content generation** (PG18) |
| `uploads` | `(bucket, upload_id)` | key, initiated-at, tags, owner, ACL, upload checksum |
| `parts` | `(bucket, upload_id, number)` | etag |
| `part_checksums` | `(bucket, upload_id, number)` | algorithm, base64 value |
| `upload_checksums` | `(bucket, upload_id)` | algorithm, checksum type |
| `object_parts` | `(bucket, key, number)` | size, algorithm, base64 value |
| `bucket_versioning` | `bucket` | the bucket's versioning state |
| `content` | `(bucket, kind, key, seq)` | 1 MiB chunk, `STORAGE EXTERNAL` (PG18, PG20, PG24) |
| `blocks` | `(hash, seq)` | 8 MiB chunk of a published blob, plus `len` and `published` on the block's first row (PG14, PG19) |
| `version_rows` / `version_index` | `(bucket, key, seq)` / `(bucket, key, id)` | the version tables `tinio-version` defines |
| `schema_version` | `id` | the applied schema version and its timestamp |

- Every key column is `text COLLATE "C"`; every `ORDER BY` repeats the collation; **the database encoding is verified to be UTF-8 at connect** (PG4).
- **Transactions**: one statement per point operation, one transaction per mutating contract method; a multi-row operation is never half applied; a publish's boundary is bounded (PG22).
- **Migrations** (PG11): numbered SQL files embedded in the binary (`migrations/0001_init.sql`, …), applied forward-only, each in its own transaction, under an advisory lock on a dedicated out-of-pool connection with its own key and a bounded wait. Newer → refused; older → migrated; the refusal names the binary/schema version and a dump/restore path, never a rebuild.
- **Concurrency**: row locks (`SELECT … FOR UPDATE`, `INSERT … ON CONFLICT`) and, for read-modify-writes, single `UPDATE … RETURNING` statements; never a transaction held across a non-database `await`.

### §4 Connection, pool, TLS, ownership and access modes

- **One connection per transaction**, from the driver's pool (PG9, PG26) sized by `[storage.pg] pool` (default 8), with a connection timeout and `test_before_acquire` as the health check.
- **Construction**: `PgStore::connect(dsn, pool, Access::{ReadWrite, ReadOnly})` — `ReadWrite` migrates, `ReadOnly` only verifies and refuses a mismatch — plus **`PgStore::inspect(dsn, pool, access)`**, a non-migrating path that reads `schema_version` (what `doctor` uses; a diagnosis must not mutate its subject — the mode only says how the inspecting session is opened, and comes back in the report) and `PgStore::migrate()` for an explicit run.
- **TLS** (PG10, PG26): the driver's rustls connector over the system trust store; `require` (chain + hostname verified), `disable`, and an explicit `prefer` only if the operator writes it; **a dsn with no `sslmode` is treated as `require`**; an unavailable TLS path is an error naming the mode, never a silent downgrade; the negotiated mode is logged and shown by `doctor`.
- **Ownership** (PG12): `PgStore::hold_ownership() -> OwnershipGuard` on a dedicated out-of-pool connection, a named advisory-lock key, and a periodic re-verify on that connection; loss of the lock logs and terminates the process (a reader-only downgrade is the fallback for an operator who prefers it, recorded in the plan). A second writable instance refuses to start with a message naming the owner; read-only instances take no lock and coexist.
- **Access modes**: `ReadWrite` and `ReadOnly` (PG6) — the read-only instance answers `AccessDenied` at the entry and relies on the restricted role underneath.
- Connection failures project to `storage::Error`'s I/O variant with the dsn redacted; errors and logs render host and database from the parsed config only (PG5).

### §5 Content storage

- **Chunking** (PG2, PG18): stage buffers one 1 MiB chunk; a publish writes the remaining chunks of a **new generation**, then updates the object's row so the new generation is live — a reader uses the row's generation, so a partial publish is invisible and a shrinking overwrite cannot serve residue. Staging is keyed (the persistence spec's D38), so chunks are inserted under the target key from the start.
- **Part chunks** live in the same relation under `kind = 'part'` with a collision-proof namespace (PG20); `scan` reads `kind = 'object'` only, and **pg's `scan` is row-backed** (PG23) so residue is not listed and a bucket holding only residue is empty.
- **Blocks** (PG14, PG19): a block's chunks are 8 MiB rows; `len` and `published` let `BlockStore::list`/`Entry` answer, the sweep's grace window work, and a re-publish fill gaps (`ON CONFLICT DO UPDATE`), so an interrupted publish can never be served as a truncated block.
- **Ranged reads** select the chunks their range touches and slice the first and last; the columns are `STORAGE EXTERNAL` (PG24).
- **The multipart completion** (PG21) follows the stated strategy (part-list indirection or copy-under-a-new-generation), with a partially assembled object invisible; the spike pins it.
- Content writes and the metadata row are separate transactions (they are separate contracts), so the failure mode is orphan chunks, never a row without bytes — and for pg an orphan is invisible to listings (PG23) and reclaimed by `Cleanup` (PG7).

### §6 The backend surface (`tinio-pg`, P5)

- **Configuration and invocation** (PG5, PG13): `[storage] type = "pg"` selects the backend; `[storage.pg] dsn` (a `Secret`) and `[storage.pg] pool`; `TINIO_PG_DSN` overrides the dsn; the keys parse in every build. There is no served root, so the run uses a **synthetic root** — `~/.tinio/pg/<hash of the dsn>/` (or `TINIO_STATE_DIR` when the operator sets it) — which is what makes the existing config discovery, state directory, control channel, state file and log paths work unchanged. A positional `DIR` is a usage error naming the remedy.
- **Read-only** (PG6): the connection is read-only (`default_transaction_read_only = on`) **and the role has no DML grants**; every mutating operation answers `AccessDenied` before touching the database; migrations never run; a schema mismatch refuses service; there is no served root and no relocation.
- **Ownership** (PG12): the writable instance holds the guarded lock; read-only instances do not.
- **Cleanup** (PG7): `repair` and `reclaim_meta_orphans` are SQL scans — orphan chunks, rows whose upload is gone, version rows past retention, blobs with no live reference (through `tinio_blob`'s `LiveSet` + sweep) — yielding the same `ActionStream` the fs backend yields.
- **Doctor**: connectivity through the pool, the applied schema version and any pending migration (through `PgStore::inspect`), the database encoding, the read-only flag and role, the ownership lock's holder, and a pool-health line.
- **Tests** (PG8, PG15–PG17): DB-backed tests behind `pg-tests`; the `@pg` pass serialized, resetting per scenario, with the `@pg` axis in the e2e default filter and `not @pg` in the mem pass's list; the CI job carries `postgres:18-alpine` and runs the store's suite, `assert_conformance` and the pass. The `>100 MiB` streaming leg lives here (it is the chunked-content risk's mitigation).

## Risks

| Risk | Mitigation |
|---|---|
| The promoted spike's shortcuts survive into a shipped store | §3 replaces its schema (generations, block metadata, migrations) and §4 its connection handling; P3 starts by re-deriving them from the findings |
| A generation/base marker is subtly wrong for a shrink-overwrite or an interrupted publish | PG18 states the requirement, the spike pins the form against real PostgreSQL, and the suite's overwrite/range leg (`write 3 MiB → overwrite with 1 MiB → range-read across the old boundary`) is the test |
| `bytea` chunking interacts badly with TOAST or large objects | Chunks are 1–8 MiB with `STORAGE EXTERNAL` (PG24); the 8 MiB suite leg, the `>100 MiB` leg and the `>1 GB` block leg are the coverage |
| A lock or session silently disappears | PG11's migration lock and PG12's ownership lock both live on dedicated out-of-pool connections, with liveness checks and a loud failure |
| Read-only is bypassed by a helper | PG6's two layers: the entry guard (the contract's answer) and the role's privileges (the database's refusal) |
| TLS misconfiguration degrades to plaintext | PG10: an omitted `sslmode` is `require`, the mode set is the client's real one, and the negotiated mode is reported |
| A migration remedy destroys data | PG11's remedy names the version and a dump/restore path; "delete and rebuild" is explicitly excluded because these tables hold the only copy |
| The CI PostgreSQL job slows every PR | DB tests stay behind `pg-tests` and in the dedicated job; `cargo test --workspace` never needs a database (PG8, PG15) |

## Verification

1. P3: the conformance suite green from `tinio-store-pg`'s own tests against `postgres:18-alpine`; a non-UTF8 database refused; a schema-version test that migrates an older database forward and refuses a newer one with the pg remedy; a served owner key in `doctor`.
2. P5: `assert_conformance` green on `tinio-pg`; the serialized `@pg` pass green in the CI job; `@fs`/`@mem` untouched.
3. `rg -n 'postgres://[^"]*:[^"]*@' crates --glob '!**/tests/**' --glob '!**/docker-compose.yml'` returns nothing (P3 Task 5 Step 2's scoped form); `doctor`/`status` output masks the dsn and names host/database only.
4. A read-only instance answers `AccessDenied` for every mutating operation, serves reads, never migrates, refuses a schema it does not match, and cannot write even when a helper bypasses the entry guard; a second writable instance refuses to start while a read-only one starts beside the writer.
5. `Cleanup`'s dry run on planted orphans reports them and `--fix` removes them; the blob sweep reports only unreferenced blocks; a listing never shows residue.
6. A 3 MiB object overwritten by a 1 MiB object serves only the new bytes for every range; a `>100 MiB` stream round-trips; a block larger than its chunk size reports `len`/`published` and survives an interrupted publish.
