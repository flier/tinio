# Design: the PostgreSQL persistence store (`tinio-store-pg`) and the pg backend (`tinio-pg`)

**Date**: 2026-10-03
**Status**: landed for the store half (P3, 2026-10-08): `crates/tinio-store-pg` carries the four contracts, the migrations, the pool and the ownership guard. `tinio-pg` (the backend surface, configuration, read-only role, cleanup, doctor and the `@pg` pass) is still P5. Decisions taken with the operator on 2026-10-03 (rounds 19–39 of the metadata-store contract design's question set; each is tagged). The first section below is **adopted, not authored here**: it is the spike's verdict and shape fixes, copied verbatim from `docs/superpowers/pg-meta-spike-findings.md` at P3 Task 1 Step 2 and marked as a record. Round 38 is post-audit: an independent six-lane review found the store's content model could not keep the visibility and reclamation promises, and its findings are folded in (PG18–PG25).
**Scope**: the PostgreSQL implementation of the four persistence contracts (`tinio-store-pg`) and the backend built on it (`tinio-pg`) — schema and migrations, connection, TLS and pool policy, content storage, configuration and invocation, the read-only mode, ownership, cleanup, and the `@pg` test pass. Not touched: the persistence contracts themselves, the shared operation bodies (`tinio-ops`), and every other backend.

## Background

The metadata-store work line validates its four persistence contracts against PostgreSQL *before* anything depends on them: a workspace-excluded spike (`spike/pg-meta/`, P1's Task 2) implements the metadata contracts, `VersionMeta` and the whole `ObjectContent` surface over `postgres:18-alpine` and runs the conformance suite. That spike was written for one purpose — proving the contracts — and deliberately carries none of a crate's engineering: no library surface, no error type, no pool, no TLS, no migrations.

This document covers what comes after: P3 promotes the spike into `tinio-store-pg` and completes it, and P5 builds `tinio-pg` over the shared ops engine with configuration, TLS, read-only support, cleanup and a cucumber pass.

**Why this document is longer than its first draft**: the audit (round 38) showed that a chunked `bytea` store cannot keep the contracts' promises by accident. A row cannot "name" its chunks without a generation/base marker (an overwrite would let a reader serve a mixture of two objects' bytes); `BlockStore` requires a block's length and a comparable publication time, which the first schema did not carry, and a multi-statement publish needs a completeness rule or an interrupted publish is served forever as truncated content; a chunk row without an object row is not an object, so `scan` must be row-backed here; and the operational surfaces (a locks' liveness, a read-only role, a migration remedy that is not "delete the database") are part of the design, not deployment details.

## Goal

1. **`tinio-store-pg` is a real crate** implementing all four contracts with schema versioning and migrations, an error type projecting into `storage::Error`, TLS-capable pooled connections, and the conformance suite green from its own tests.
2. **`tinio-pg` is a servable backend** over `tinio-ops`: the `Storage`/`VersionOps`/`Cleanup` implementations, the `[storage] type`/`[storage.pg]` configuration, the synthetic root, the session read-only mode with a restricted role, the writable-ownership guard, doctor checks, and a serialized `@pg` cucumber pass in CI.
3. **PostgreSQL-specific behavior is stated, not implied**: ordering and encoding, read-only, content chunking and generations, connections and TLS, migrations and their remedy, cleanup, and the supported topologies.

## Non-goals

- **No ORM, and no statement built by formatting.** `sqlx` is the driver and its macros carry the statements (PG26): **values are always bound parameters; table and column identifiers come only from the fixed schema** — a statement assembled from a value is a defect whatever its form, and `Cleanup`'s scan-shaped SQL is where one would appear. A short statement is written inline in `query!`/`query_as!`/`query_scalar!`; a longer one is a `.sql` file named by the file macros. Both are checked at compile time — against a live database, or against the committed `.sqlx` cache that a database-free build reads (PG8's rule is that no build needs a database, not that none may read a checked-in file).
- **No multi-writer topology.** One writable instance owns a database (PG12).
- **No pg-specific persistence contract.** Where PostgreSQL cannot satisfy a rule, that is a scope finding (the contract changes, not the schema).
- **No multi-tenant or RLS design.** One database per served instance; the dsn carries credentials; no namespace prefix.
- **No `tinio-pg`-specific S3 semantics.** The operations come from `tinio-ops`; this backend supplies storage, hooks, configuration and lifecycle.

| PG6 | Read-only (FR-023) is a session-level read-only connection **and a role without `INSERT`/`UPDATE`/`DELETE` grants**: the entry guard answers `AccessDenied` first, and the privileges are the second guard that actually holds when a helper bypasses the entry | 26, 38 |
| PG7 | `Cleanup` is fully implemented (SQL scans plus the blob sweep through `tinio_blob`'s `LiveSet`) | 26 |
| PG8 | The `@pg` cucumber pass runs in the CI job that carries the PostgreSQL service, **serialized** (one shared database, one scenario at a time); DB-backed tests are the crate's own `#[cfg(test)]` legs and skip when `TINIO_PG_DSN` is unset, so `cargo test --workspace` stays database-free | 20, 21, 38 |
| PG9 | The pool is the driver's own pool (PG26), sized by `[storage.pg] pool` (default 8), with a connection timeout and a health check | 33 |
| PG10 | TLS uses the driver's rustls connector with the **system trust store** (PG26); the mode set is `disable`/`prefer`/`require` (**`verify-ca`/`verify-full` are not tokio-postgres modes**), `require` performs chain **and** hostname verification, and **an omitted `sslmode` is treated as `require`**, not as the client's `prefer` default: plaintext happens only with an explicit `sslmode=disable`, and the negotiated mode is logged and shown by `doctor` | 33, 34, 38 |
| PG11 | Migrations run **automatically at startup**, forward-only, each step in its own transaction, under an advisory lock held on a **dedicated out-of-pool connection** with its own key and a bounded wait; a failure refuses to start; a database **newer** than the binary is refused. The remedy is **not** the redb one: the bytes live only here, so it names the required binary/schema version and a dump/restore path — never "delete and rebuild". A read-only instance never migrates and refuses a mismatch; `doctor` reports the applied version and any pending migration **through a non-migrating inspection path** | 33, 38 |
| PG12 | **One writable instance per database**: `PgStore::hold_ownership()` opens a dedicated out-of-pool connection, takes a process-lifetime advisory lock under a named key, and **re-verifies it on a cadence** — the re-verify is also what keeps the connection's TCP path warm, because the driver exposes no keepalive knob (PG26) — losing it terminates the process (or drops it to read-only), because a silently released lock is exactly the two-writer corruption this rule exists to prevent. Read-only instances take no lock and coexist (≤1 writable + N read-only); `doctor` prints the owner | 34, 35, 38 |
| PG13 | A positional `DIR` (or a discovered `.tinio/` root) under `[storage] type = "pg"` is a **usage error** naming the remedy | 34 |
| PG14 | `PgBlocks` **chunks a block internally** (8 MiB rows, transparent to `BlockStore`), because the engine's v1 policy stores a whole blob as one block and a `bytea` field caps at 1 GB | 36 |
| PG15 | `tinio-store-pg` carries no `pg` feature: it *is* the PostgreSQL implementation, and `pg` is the **consumer's** optional dependency on it (`crates/tinio` spells it `pg = ["dep:tinio-store-pg"]`), so a configuration that does not serve PostgreSQL does not reference the crate at all; **`pg-tests`** (non-default) gates the DB-backed tests; `pg` joins `crates/tinio`'s `full` set, so the released binary can serve this backend while the default workspace leg stays database-free | 36, 38 |
| PG16 | `pg` and `versioning` are orthogonal features of `tinio-pg` (`versioning` gates its own version module and the `VersionOps` twin; `tinio-store-pg`/`tinio-ops` carry no `versioning` feature at all) | 38 |
| PG17 | The `@pg` pass runs the backend-neutral scenarios plus `@pg`-tagged ones (fs-specific scenarios are tagged `@fs`), resets the database per scenario (truncate + re-migrate + construct), and is **serialized**; its exclusion is a fifth axis in the e2e default filter and `not @pg` joins the mem pass's list | 38 |
| PG18 | **Content carries a discriminator and a generation.** The rows are keyed by `(bucket, kind, key, seq)` with `kind ∈ {object, part}`, and the object's row records **which generation is live** (a base sequence or a generation id): an overwrite writes a new generation and the row's update is what makes it live, so a reader can never mix two generations' bytes and a partial publish is invisible. The **form** (a `base_seq` column, a generation id, or an in-place replace inside the row's transaction) is the spike's to pin against real PostgreSQL; the requirement is not | 38 |
| PG19 | **`blocks` carries `len` and `published`** (a comparable timestamp on the caller's clock): `BlockStore::list`/`Entry` require both and neither can be derived from the chunks alone. A publish is **complete or absent**: every chunk row is written with `ON CONFLICT DO UPDATE`, a repeated publish fills gaps rather than answering `Existing` on a partial block, and "some rows, not all" reads as not present | 38 |
| PG20 | Part chunks share the content relation with `kind = 'part'` and their own collision-proof key namespace (the spike pins the encoding); `scan` filters `kind = 'object'`, so a part can never be enumerated or opened as an object | 38 |
| PG21 | The **multipart completion's assembly** is stated per backend: pg's requirement is that it never rewrites the whole object if the layout can avoid it (a part-list indirection, or a copy under a new generation made live by the row's update), and that a partially assembled object is invisible; the spike pins the form | 38 |
| PG22 | A publish's **transaction boundary is bounded**: either the chunks commit in batches under an incompleteness marker (a partial object is unreadable until the row makes it live), or the backend declares a maximum body size. The spike measures and pins which; an unbounded single transaction (a 100 GiB PUT as 100 000 statements) is not acceptable | 38 |
| PG23 | **`scan` is row-backed for pg**: a chunk row without an object row is residue, not an object, so pg's `scan` enumerates keys that have a live row (a join, or the metadata plane as the source) — the opposite of fs's content-is-truth rule, and the reason the engine's listing heals rather than assumes | 38 |
| PG24 | The chunk columns are declared `STORAGE EXTERNAL`: object bytes are usually incompressible, and detoasting a value for a 4 KiB range read would decompress the whole chunk | 38 |
| PG25 | The credential check is **scoped** so it can hold alongside the mandated DB tests: tests read the dsn from `TINIO_PG_DSN`, and the only literal lives in `docker-compose.yml` — the command is `rg -n 'postgres://[^"]*:[^"]*@' crates --glob '!**/tests/**' --glob '!**/docker-compose.yml'` (P3 Task 5 Step 2 owns it) | 38 |
| PG26 | The driver is **`sqlx`** — it supersedes the driver *crate* choice rounds 33/34 pinned for PG9/PG10, whose **policies** stand: `sqlx::PgPool` is the pool, `PgConnectOptions` (with the `tls-rustls-ring-native-roots` feature — rustls over the system trust store) replaces `tokio-postgres-rustls` + `rustls-native-certs`, and the statements are `sqlx`'s macros (`query!`/`query_as!`/`query_scalar!` for a short inline statement, `query_file!`/`query_file_as!`/`query_file_scalar!` for a file) off the committed `.sqlx` cache, with the runtime `sqlx::query`/`.bind()` form kept for DDL and the templated test statements no macro can describe. Two mappings are the store's, not sqlx's defaults: an omitted or explicit `sslmode=require` becomes **verify-full** (chain *and* hostname), because sqlx's own `Require` stops at the chain and never checks the hostname, and the remaining modes map one-to-one. A migration step and a publish batch are each one `sqlx` transaction; both advisory locks stay on dedicated out-of-pool `PgConnection`s | 39 |

**2. The schema seed.**

`spike/pg-meta/schema.sql` is applied at connect (P3 derives its migrations from it). Fifteen relations:

| Table | Key | Carries |
|---|---|---|
| `buckets` | `name` | creation time, tags wire, owner wire, ACL wire, CORS wire |
| `object_meta` | `(bucket, key)` | etag, size, mtime, identity, tags, checksum, owner, ACL |
| `object_parts` | `(bucket, key, number)` | size, algorithm, base64 value (the retained part list) |
| `uploads` | `(bucket, upload_id)` | key, initiated-at, tags, owner, ACL |
| `parts` | `(bucket, upload_id, number)` | etag |
| `part_checksums` | `(bucket, upload_id, number)` | algorithm, value |
| `upload_checksums` | `(bucket, upload_id)` | algorithm, checksum kind |
| `bucket_versioning` | `bucket` | the bucket's versioning state |
| `version_rows` | `(bucket, key, seq)` | id wire, blob, size, etag, created, became-noncurrent, kind, tags, checksum, owner, ACL |
| `version_index` | `(bucket, key, id)` | the id-to-seq lookup (the point index read) |
| `current_slots` | `(bucket, key)` | the key's current version identity (nullable) and sequence (finding F3) |
| `content_heads` | `(bucket, kind, ckey)` | the generation counter, the live generation and its length (PG18) |
| `content` | `(bucket, kind, ckey, seq, chunk_no)` | a 1 MiB chunk, `STORAGE EXTERNAL` (PG18, PG20, PG24) |
| `blocks` | `(hash, seq)` | an 8 MiB block chunk plus `len` and `published` (PG14, PG19; P3's `PgBlocks` uses it) |
| `schema_version` | `id` | the applied schema version, its timestamp and note |

Every column an ordered read compares is `text COLLATE "C"`, and every ordered statement repeats the collation; discriminator and wire-only columns (`version_index.id`, `content.kind`, the tags/checksum/owner/acl wires) carry no collation because no ordered read touches them. The connect-time UTF-8 check is what makes `"C"` mean the contract's byte order (PG4, section 6).

Part numbers are `bigint` in all three part relations (the brief's pin; the store binds them as `i64`), and the gate's schema leg asserts that the three `number` columns' `data_type` is `bigint` rather than asserting the name alone.

`PgStore::connect` runs `RESET_SQL` before applying `schema.sql`: **it drops all 15 relations on every connect** (`DROP TABLE ... CASCADE`), so each connection starts from an empty schema - a second connect in the same process empties what the first one created. The blast radius is the point: the file is `CREATE TABLE IF NOT EXISTS`, so without the reset a database left by an earlier revision would silently keep an older column set and the gate would pass against yesterday's DDL - exactly the failure the `integer`->`bigint` correction would otherwise have hit.

**Spike-only, and gone at promotion**: the README promotes this directory into `crates/tinio-store-pg`, where the schema becomes migrations. `connect` must then migrate and never drop, and `RESET_SQL` must not be carried over.

The schema leg asserts **presence, not absence**: it fails when one of the 15 relations is missing, but it only prints the table list, so a stale *extra* table would be reported rather than refused. With `RESET_SQL` in place that cannot arise in the gate; P3's migration check should assert the absence of foreign relations if it wants the stricter property.

**3. The forms the pg design defers to this spike (PG18-PG23).**

**PG18 - the content discriminator and the live generation.**

**Pinned**: `content_heads(bucket, kind, ckey, next_seq, live_seq, live_len)` beside `content(bucket, kind, ckey, seq, chunk_no, chunk)`. `kind` is a `CHECK (kind IN ('object','part'))` discriminator in the primary key of both relations. A publish allocates a fresh generation (`INSERT ... ON CONFLICT DO UPDATE SET next_seq = content_heads.next_seq + 1 RETURNING next_seq`), writes that generation's chunks, then makes it live in one `UPDATE` guarded by `AND next_seq = $4`. A reader resolves `live_seq`, never `next_seq`, so an interrupted publish is invisible and a shrinking overwrite cannot serve residue.

**Finding F1**: the live-generation marker cannot live in `object_meta` the way the pg design's section 3 table sketches it ("the object's row records which generation is live"). The content contract is independent of the metadata plane: `assert_content_conformance` publishes bytes with no object row at all, and `scan`/`stat`/`open` must still answer. The marker therefore lives in the content relation (`content_heads`), and PG18's *requirement* holds exactly.

**PG19 - the block plane's `len`/`published` and publish completeness.**

**Pinned**: `blocks(hash text COLLATE "C", seq integer, chunk bytea, len bigint, published bigint)` with `chunk` `STORAGE EXTERNAL`. Every chunk row carries the block's declared `len` and the publish's comparable `published` stamp (the caller's clock), and a publish writes with `ON CONFLICT DO UPDATE` so a repeat fills gaps instead of answering "exists". A block is served only when the full chunk count for its declared `len` is present, so "some rows, not all" reads as absent.

**Finding F10 (scope)**: the spike pins the *form* but does not implement `BlockStore` - the D23 surface this task implements carries no block call, and `PgBlocks` is P3's (PG3, PG14). The columns are the seed; the list/grace-window behaviour is P3's to prove.

**PG20 - the collision-proof part namespace.**

**Pinned**: parts share the content relation with `kind = 'part'` and their own key space: `ckey = "p:" || hex(upload_id) || ":" || zero-padded-4-digit number` (the code's `format!("p:{hex}:{number:04}")`; no read depends on the padding) for parts, and `ckey = "o:" || object_key` for objects. The `kind` discriminator is in the primary key, so no part number can collide with an object key and no object key can collide with a part. `scan` filters `kind = 'object'` *and* `starts_with(ckey, 'o:' || prefix)`, so a part is never enumerated, listed or opened as an object.

**PG21 - the multipart completion's assembly.**

**Deferred to P3 - not pinned here, and not ambiguous.** No D23 call reaches completion, and review item 39 puts both the form and its leg on P3 (D43 keeps this spike to the D23 surface); pinning a form would mean inventing behaviour against a document the findings already supersede for P3.

What the spike *does* pin is the mechanism a completion must use: assemble under a **new generation** and flip the head, never rewrite a live generation in place. Both halves are implemented and green - `publish` inserts chunks under `next_seq + 1` and flips with one guarded `UPDATE`, and `copy` copies a generation's chunks and flips its own - so a partial assembly is invisible by construction. The two candidate shapes stay open and unranked for P3: (a) copy the retained parts' chunks into a fresh generation, or (b) a part-list indirection read at `open`/`stat` time.

**PG22 - the bounded publish transaction.**

**Pinned**: chunks commit in batches of `PUBLISH_BATCH_CHUNKS = 4` (4 MiB), one `INSERT ... SELECT ... FROM unnest($5::int[], $6::bytea[])` statement per batch, under the incompleteness marker (`live_seq` does not move until the final `UPDATE`). The statement count for a body of `n` chunks is `ceil(n / 4) + 2` (one allocate, the batches, one flip) - bounded and independent of the body size, and the body is never one unbounded transaction.

**Declared and reported**: the gate prints the plan for its 8 MiB leg - 8 chunk rows in 2 batch statements - and that leg really stages, publishes and byte-compares the chunks; the *plan* itself is a shared computation (the driver prints what `publish` computes), so this line is a declared form, not an independent measurement. A 100 GiB body would be 102 400 chunks in 25 600 batches, 25 602 statements in all (`ceil(n/4) + 2`), each a bounded transaction; the `>100 MiB` streaming leg is P5's (D43).

**PG23 - `scan` is row-backed.**

**Pinned**: `scan` enumerates `content_heads` rows with `live_seq IS NOT NULL` and `kind = 'object'`, ordered by `ckey COLLATE "C"` with `starts_with` as the prefix bound and `$3::text IS NULL OR ckey > $3` as the exclusive cursor. A chunk row without a live head is residue, not an object; a bucket holding only residue is empty. The "row" here is the **content head**, not `object_meta`: the content suite publishes without metadata rows, and the content plane must answer for what it published. PG23's requirement (residue is not listed) holds; its suggested source ("a join, or the metadata plane") is not available to the content contract alone.

**PG24 - `STORAGE EXTERNAL`.**

**Pinned**: `ALTER TABLE content ALTER COLUMN chunk SET STORAGE EXTERNAL` and the same for `blocks.chunk`. The gate's ranged read over an 8 MiB object (1 000 003..=3 500 000) reads only the chunks that window touches.

**4.1 The four suite defects the gate found.**

All four are evidence for the spike's value: none was visible to Task 1's unit-level review, because none is a compile error and the mem/fs suite runs do not reach every fixture.

1. **`remove_if_empty` called twice** (`crates/tinio-util/src/testing/metadata.rs`): the success leg removed the bucket, then called `remove_if_empty` a second time and unwrapped the result - but the leg's own assertion (and the trait doc) says a missing row is `NoSuchBucket`. Corrected to `BucketMeta::remove` for the second call.
2. **The owner fixture** (`metadata.rs` line ~88): `OwnerId::new("conf-owner").expect("a valid owner id")`. `OwnerId::new` admits exactly 64 lowercase hex digits (or the anonymous canonical id), so the value panics and every ACL leg aborts. This is a *contract-vs-suite* mismatch the gate found on its first run; Task 1 owns the fixture.
3. **The CORS fixture expects the unrepresentable** (`metadata.rs` ~714-736, reached once the owner fixture was fixed): the leg records `cors::Config::default()` and then requires `row().cors.is_some()`. A default configuration has no rules, its wire is the empty string, and `bucket_row::decode_cors` (`crates/tinio-core/src/meta/bucket.rs`:155) maps "empty, corrupt or a configuration with no rules" to `None`. **No store can satisfy this assertion** - it needs a rule-bearing config. Task 1's fixer replaced it with a one-rule config and a field-for-field round-trip assertion, which is stronger than the original `is_some`.
4. **The 8 MiB window is off by one** (`metadata.rs` ~651-663): the leg asks for `ByteRange::Inclusive(start, start + 4096)`, which `ByteRange::resolve` (`crates/tinio-core/src/storage/range.rs`:26, "the inclusive range A..=B") answers with 4097 bytes, then compares that against the 4096-byte slice `expected[start..start + 4096]`. The gate measured the two sides (4097 vs 4096 bytes, the extra trailing byte being the object's 69639th). This is the fourth fixture the spike's gate caught and Task 1's unit-level review could not: the earlier `Inclusive(1, 3)` leg passes only because its expectation is likewise 3 bytes.

All four were corrected by Task 1's fixer; the gate then ran **8/8 legs green, exit 0** (the output in 1.2). The store needed no change for any of them: three were fixtures that no backend could satisfy and one was my own suite leg's second `remove_if_empty` call. Task 1's round-3 contract edits - the restored delete-marker assertion and the now-explicit no-row rule for `current_slot` - also pass against this store unchanged, which is why the final run is green on the settled suite. **Superseded (corrected 2026-10-07)**: that first run predated the contract's `list_parts_page`, `BucketMeta::set_tags_or_create`, `BucketMeta::set_grants_or_create` and `UploadMeta::drain_upload_checked` additions and covered none of them (see the warning at the top), and the crate then did not compile as committed. | `VersionMeta::list_versions` | one `SELECT ... ORDER BY seq DESC` | newest first (sequence order, not time order) |

### Schema and migrations

Tables (names, columns and types are the store's, not the contracts'):

| Table | Key | Carries |

| `current_slots` | `(bucket, key)` | the key's current version id and sequence (F3: they cannot ride `object_meta`) and the restored marker's bit (`is_delete_marker`, the 2026-10-10 wave's `0002_current_slot_marker.sql`; see "What P3 landed" below) |
| `content_heads` | `(bucket, kind, ckey)` | the live generation and its length (F1: the marker lives here, not on `object_meta`) |
| `uploads` | `(bucket, upload_id)` | key, initiated-at, tags, owner, ACL, upload checksum |
| `parts` | `(bucket, upload_id, number)` | etag |
| `part_checksums` | `(bucket, upload_id, number)` | algorithm, base64 value |
| `upload_checksums` | `(bucket, upload_id)` | algorithm, checksum type |
| `object_parts` | `(bucket, key, number)` | size, algorithm, base64 value |
| `bucket_versioning` | `bucket` | the bucket's versioning state |
| `content` | `(bucket, kind, key, seq)` | 1 MiB chunk, `STORAGE EXTERNAL` (PG18, PG20, PG24) |
| `blocks` | `(hash, seq)` | 8 MiB chunk of a published blob, plus `len` and `published` on the block's first row (PG14, PG19) |
| `version_rows` / `version_index` | `(bucket, key, seq)` / `(bucket, key, id)` | the version tables `tinio-version` defines |
| `schema_version` | `id` | the applied schema version and its timestamp |

- Every key column is `text COLLATE "C"`; every `ORDER BY` repeats the collation; **the database encoding is verified to be UTF-8 at connect** (PG4).
- The database-backed leg that pins the ordering (`the_order_does_not_move_with_the_database_locale`) compares the cluster's default collation against a `BUILTIN_LOCALE 'C.UTF-8'` one; on this musl image both order bytes identically (F9), so the leg guards the pin's **presence** rather than its load-bearing effect — dropping `COLLATE "C"` would not turn it red. A discriminating leg would create the second scratch database with `LOCALE_PROVIDER icu`, whose `en-US-x-icu` order the spike measured to differ (`_,0,a,B` against `0,B,_,a`); recorded 2026-10-09 as the leg's known limit, with the same note on the test.
- **Transactions**: one statement per point operation, one transaction per mutating contract method; a multi-row operation is never half applied; a publish's boundary is bounded (PG22).
- **Migrations** (PG11): numbered SQL files under `sql/migrations/` (`{version}_{description}.sql`), embedded at compile time by `sqlx::migrate!` into the crate's migrator, applied forward-only, each in its own transaction, under an advisory lock on a dedicated out-of-pool connection with its own key and a bounded wait. Newer → refused; older → migrated; the refusal names the binary/schema version and a dump/restore path, never a rebuild.
- **Concurrency**: row locks (`SELECT … FOR UPDATE`, `INSERT … ON CONFLICT`) and, for read-modify-writes, single `UPDATE … RETURNING` statements; never a transaction held across a non-database `await`.

### Connection, pool, TLS, ownership and access modes

- **One connection per transaction**, from the driver's pool (PG9, PG26) sized by `[storage.pg] pool` (default 8), with a connection timeout and `test_before_acquire` as the health check.
- **Construction**: `PgStore::connect(dsn, pool, Access::{ReadWrite, ReadOnly})` — `ReadWrite` migrates, `ReadOnly` only verifies and refuses a mismatch — plus **`PgStore::inspect(dsn, pool, access)`**, a non-migrating path that reads `schema_version` (what `doctor` uses; a diagnosis must not mutate its subject — the mode only says how the inspecting session is opened, and comes back in the report) and `PgStore::migrate()` for an explicit run.
- **TLS** (PG10, PG26): the driver's rustls connector over the system trust store; `require` (chain + hostname verified), `disable`, and an explicit `prefer` only if the operator writes it; **a dsn with no `sslmode` is treated as `require`**; an unavailable TLS path is an error naming the mode, never a silent downgrade; the negotiated mode is logged and shown by `doctor`.
- **Ownership** (PG12): `PgStore::hold_ownership() -> OwnershipGuard` on a dedicated out-of-pool connection, a named advisory-lock key, and a periodic re-verify on that connection; loss of the lock logs and terminates the process (a reader-only downgrade is the fallback for an operator who prefers it, recorded in the plan). A second writable instance refuses to start with a message naming the owner; read-only instances take no lock and coexist.
- **Access modes**: `ReadWrite` and `ReadOnly` (PG6) — the read-only instance answers `AccessDenied` at the entry and relies on the restricted role underneath.
- Connection failures project to `storage::Error`'s I/O variant with the dsn redacted; errors and logs render host and database from the parsed config only (PG5).

### Content storage

- **Chunking** (PG2, PG18): stage buffers one 1 MiB chunk; a publish writes the remaining chunks of a **new generation**, then updates the object's row so the new generation is live — a reader uses the row's generation, so a partial publish is invisible and a shrinking overwrite cannot serve residue. Staging is keyed (the persistence spec's D38), so chunks are inserted under the target key from the start.
- **Part chunks** live in the same relation under `kind = 'part'` with a collision-proof namespace (PG20); `scan` reads `kind = 'object'` only, and **pg's `scan` is row-backed** (PG23) so residue is not listed and a bucket holding only residue is empty.
- **Blocks** (PG14, PG19): a block's chunks are 8 MiB rows; `len` and `published` let `BlockStore::list`/`Entry` answer, the sweep's grace window work, and a re-publish fill gaps (`ON CONFLICT DO UPDATE`), so an interrupted publish can never be served as a truncated block.
- **Ranged reads** select the chunks their range touches and slice the first and last; the columns are `STORAGE EXTERNAL` (PG24).
- **The multipart completion** (PG21) follows the stated strategy (part-list indirection or copy-under-a-new-generation), with a partially assembled object invisible; the spike pins it.
- Content writes and the metadata row are separate transactions (they are separate contracts), so the failure mode is orphan chunks, never a row without bytes — and for pg an orphan is invisible to listings (PG23) and reclaimed by `Cleanup` (PG7).

### The backend surface (`tinio-pg`, P5)

- **Configuration and invocation** (PG5, PG13): `[storage] type = "pg"` selects the backend; `[storage.pg] dsn` (a `Secret`) and `[storage.pg] pool`; `TINIO_PG_DSN` overrides the dsn; the keys parse in every build. There is no served root, so the run uses a **synthetic root** — `~/.tinio/pg/<hash of the dsn>/` (or `TINIO_STATE_DIR` when the operator sets it) — which is what makes the existing config discovery, state directory, control channel, state file and log paths work unchanged. A positional `DIR` is a usage error naming the remedy.
- **Read-only** (PG6): the connection is read-only (`default_transaction_read_only = on`) **and the role has no DML grants**; every mutating operation answers `AccessDenied` before touching the database; migrations never run; a schema mismatch refuses service; there is no served root and no relocation.
- **Ownership** (PG12): the writable instance holds the guarded lock; read-only instances do not.
- **Cleanup** (PG7): `repair` and `reclaim_meta_orphans` are SQL scans — orphan chunks, rows whose upload is gone, version rows past retention, blobs with no live reference (through `tinio_blob`'s `LiveSet` + sweep) — yielding the same `ActionStream` the fs backend yields.
- **Doctor**: connectivity through the pool, the applied schema version and any pending migration (through `PgStore::inspect`), the database encoding, the read-only flag and role, the ownership lock's holder, and a pool-health line.
- **Tests** (PG8, PG15–PG17): DB-backed tests are `#[cfg(test)]` legs that skip when `TINIO_PG_DSN` is unset; the `@pg` pass serialized, resetting per scenario, with the `@pg` axis in the e2e default filter and `not @pg` in the mem pass's list; the CI job carries `postgres:18-alpine` and runs the store's suite, `assert_conformance` and the pass. The `>100 MiB` streaming leg lives here (it is the chunked-content risk's mitigation).


### What P3 landed, and the five places it corrects this design

P3 promoted the spike into `crates/tinio-store-pg`. The design above is the one that binds the crate; these are the differences a reader of §3-§5 must know, each settled by the implementation and its suite rather than by preference.

- **The `content` key gained `chunk_no`.** §3 names `(bucket, kind, key, seq)`; the landed key is `(bucket, kind, key, seq, chunk_no)`, which is what makes two publishes of the same generation idempotent and a chunk replaceable in place (`ON CONFLICT ... DO UPDATE`). The visible ordering is still `chunk_no`, an integer, so no collation applies to it.
- **A block publish never rewrites a hash it finds.** §5 phrases the block rows as `ON CONFLICT DO UPDATE`; the crate uses `ON CONFLICT (hash, seq) DO NOTHING` per 8 MiB row, and `rows_affected == 0` answers `Published::Existing` with the staged bytes dropped. `DO UPDATE` would let a re-publish of an incomplete stream mix with the previous publish's rows and serve a spliced block, which PG19 forbids. Every row carries `len` and `published`, so one row answers `BlockStore::list`/`Entry` without a first-row special case.
- **A missing block projects to `io::ErrorKind::NotFound`.** `Error::NoSuchBlock` goes to `storage::Error::Io` with `NotFound` (`error.rs`), which is the contract `BlockStore::open` states; the generic `io::Error::other` arm would answer `Other` and break the contract. `blocks.rs`'s missing-block path returns `Error::NoSuchBlock` and relies on that projection; the two paths that read a *stored* block back — a chunk run shorter than the declared length, an address that will not parse — build their own `Error::Storage(storage::io(...))` with `UnexpectedEof` / `InvalidData`, which have no dedicated variant.
- **The DSN's SSL mode is a store policy, not the driver's default.** §4 says an omitted `sslmode` is `require`; sqlx 0.9 defaults to `Prefer` and offers no accessor for whether the operator wrote the mode, so `pool.rs` reads the dsn text and upgrades an omitted mode to the driver's `VerifyFull` (chain **and** hostname). An explicit `sslmode=prefer` is honoured. This is why the test dsn carries `?sslmode=disable` against the plaintext compose fixture, and why the suite has a leg (`a_require_dsn_never_downgrades_to_plaintext`) proving a `require` dsn against a plaintext server fails naming TLS rather than downgrading.
- **The slot carries the restored marker's bit (the 2026-10-10 wave, `docs/superpowers/specs/2026-10-10-version-slot-write-contract.md`).** §3's `current_slots(bucket, key, version_id, seq)` gains `is_delete_marker boolean NOT NULL DEFAULT false` (`sql/migrations/0002_current_slot_marker.sql`; `migrations.rs`'s `SCHEMA_VERSION` is **2**), because the new contract call `VersionMeta::restore_slot` consumes the version row the bit was derived from (the wave's spec §2.2 S7), so the bit must live in the slot's own record: `current_slot.sql` answers the left-joined row's `kind` when the row is present and `s.is_delete_marker` when it is not, and `advance_slot_upsert.sql` writes the column from the same row it always derived the bit from. Three statements are new (`restore_slot.sql`, the premise row read `FOR UPDATE`; `restore_slot_upsert.sql`; `restore_slot_stamp.sql`) and two are edited (`advance_slot_upsert.sql`, `current_slot.sql`). §5's "the only writer of a key's slot" and F3's "LEFT JOINs the version row for the delete-marker flag" describe the pre-wave shape: the slot now has two contract writers — `advance_slot` (forward-only; its guard is unchanged) and `restore_slot` (the backwards move to a real identity, the one move `advance_slot` refuses).

Two smaller records: the tests' scratch databases must carry a short name (bucket names are validated, so a bucket cannot be named after the scratch database), and DB-backed legs create their own scratch database per test, so `cargo test`'s parallelism is safe and a run leaves no state behind.
### The SQL layout: files, inline statements, and the offline cache

A statement lives in `crates/tinio-store-pg/sql/` -- one directory per Rust module that owns statements -- or, when it is short, inline at the call. The rule is the line: a statement that fits on one line (which `sqruff`'s 80-column format makes observable) may be spelled in the argument of `query!`, `query_as!` or `query_scalar!`; anything longer is a file named by `query_file!`, `query_file_as!` or `query_file_scalar!` (`sql/...`, resolved from `CARGO_MANIFEST_DIR`), or -- for DDL and the templated test statements no macro can describe -- loaded by a plain-literal `include_str!("../sql/...")`. A statement that more than one call site needs stays a file whatever its length, so one text has one home. A migration file is embedded by `sqlx::migrate!`'s directory literal (`sqlx::migrate!("./sql/migrations")`), which parses each version out of its name, and sqlx's own `_sqlx_migrations` bookkeeping is not used: PG11's runner records into `schema_version` because the schema, and the refusal a newer database gets, are the store's contract rather than the driver's. The file macros expand to `include_str!` internally, so an SQL edit is still a code change and no statement is loaded at run time.

The two rules are the crate's review checklist, not a test: the guard that scanned the sources and the `sql/` tree (encoding the text in a three-valued alphabet -- letters, one code clinging to its word, one separating words -- so that `#[derive(Debug, Clone, Copy)]` could not spell `clone copy`) was deleted by operator directive. Read `docs/style.md` §SQL when touching the crate: no statement spelled by Rust code outside a single-line inline macro, every `include_str!`/`query_file*!` argument a plain path literal, a `migrate!` directory a plain `sql/...` literal, and every `.sql` file named by some source.

The macros check every statement at compile time, so `sqlx`'s `macros` feature is on and the crate commits `.sqlx/` at the workspace root, generated with `cargo xtask sqlx update` against a migrated database. With no `DATABASE_URL` -- every ordinary `cargo check` and the CI leg -- the macros read that cache, so PG8's rule holds (no build needs a database) while a statement missing from the cache fails the build. Two consequences are accepted: an inline statement is not `sqruff`-linted, which is the other reason to keep one trivial; and an entry that goes stale against a changed schema is caught only by `cargo xtask sqlx check` beside a live database, the leg P5's CI PostgreSQL job owns.

A parameter is the contract's own type: `bucket::Name`, `object::Key`, `version::Id`, `acl::OwnerId` and `object::Tags` carry `sqlx::Type`/`Encode`/`Decode` under `tinio-core`'s optional `sqlx` feature, which this crate turns on for itself, so a statement binds the newtype itself rather than a `String` copy of it, and a row can be read as the newtype. The first four derive the traits; `object::Tags` and `version::State` implement the three by hand (`#[sqlx(transparent)]` cannot forward the map, and a unit-only enum's column stores the type's `Display` wire form), so a statement binds the newtype itself -- a macro argument through the wildcard cast the next paragraph records, a runtime `.bind` directly. The exception is an array parameter (`= ANY ($1)`): sqlx picks an array's element type through `PgHasArrayType`, which a transparent derive does not provide and which the contract crate will not carry, so those binds stay an owned `Vec<String>`; the same mapping refuses a borrowed element type, so `content.rs`'s `insert_chunks` and `blocks.rs`'s `publish` -- whose chunks are `Vec<&[u8]>` -- pass that one argument as `&chunks as _` / `&pieces as _` through `query_file!`, which skips the element check and still encodes `bytea[]`, rather than copying every chunk, and `migrations.rs`'s `VERSION_TABLE_SQL` stays a plain `include_str!` as DDL.

Three macro behaviours the migration pinned, recorded so the next module does not rediscover them: a statement with no result columns (every `INSERT`/`UPDATE`/`DELETE` without `RETURNING`) yields a query the macros let you `execute`, while a statement that returns columns yields a `Map` with `fetch_*` only, so a discarded `SELECT` result is read with `fetch_optional`; and `sqlx` reads a column's nullability from the **table the column comes from**, never from the statement: an expression column (`exists(...)`, `count(*)`, `coalesce(...)`, `max(...)`, a function call) is always nullable, a schema-nullable column stays nullable however the `WHERE` constrains it, and an outer join's right-side column is described by its origin table (whose `NOT NULL` says nothing about the join) even though the join nulls it. So a column that cannot be null takes the `AS "name!"` override rather than the Rust struct taking an `Option` that is never `None`, and a column the join *can* null takes `AS "name?"` so the macro decodes the `Option` the row really holds: without it, `parts LEFT JOIN part_checksums` described `c.algorithm` as `Text NOT NULL` and the read died on the first part with no checksum row. Third, a macro's argument check pins a parameter to the Rust type `sqlx` maps its Postgres type to (`sqlx-macros-core`'s `query/args.rs` builds the check): a `text` parameter wants `&str`, which a `Deref<Target = str>` newtype matches and a newtype over any other inner type (`Tags`) does not, so a macro call passes the derived wire string where the same statement's runtime form binds the newtype -- unless the argument is a wildcard cast (`tags as _`, `state as _`, `id as _`), which `args.rs` strips before binding and skips in the check, so those call sites bind the contract type itself and its own `Encode` writes the wire form.

## Risks

| Risk | Mitigation |
|---|---|
| The promoted spike's shortcuts survive into a shipped store | §3 replaces its schema (generations, block metadata, migrations) and §4 its connection handling; P3 starts by re-deriving them from the findings |
| A generation/base marker is subtly wrong for a shrink-overwrite or an interrupted publish | PG18 states the requirement, the spike pins the form against real PostgreSQL, and the suite's overwrite/range leg (`write 3 MiB → overwrite with 1 MiB → range-read across the old boundary`) is the test |
| `bytea` chunking interacts badly with TOAST or large objects | Chunks are 1–8 MiB with `STORAGE EXTERNAL` (PG24); the 8 MiB suite leg, the `>100 MiB` leg and the `>1 GB` block leg are the coverage |
| A lock or session silently disappears | PG11's migration lock and PG12's ownership lock both live on dedicated out-of-pool connections, with liveness checks and a loud failure |
| Read-only is bypassed by a helper | PG6's two layers: the entry guard (the contract's answer) and the role's privileges (the database's refusal) |
| TLS misconfiguration degrades to plaintext | PG10: an omitted `sslmode` is `require`, the mode set is the client's real one, and the negotiated mode is reported |
| A migration remedy destroys data | PG11's remedy names the version and a dump/restore path; "delete and rebuild" is explicitly excluded because these tables hold the only copy |
| The CI PostgreSQL job slows every PR | DB tests are `#[cfg(test)]` legs that skip without `TINIO_PG_DSN`, and the dedicated job carries the service; `cargo test --workspace` never needs a database (PG8, PG15) |

## Verification

1. P3: the conformance suite green from `tinio-store-pg`'s own tests against `postgres:18-alpine`; a non-UTF8 database refused; a schema-version test that migrates an older database forward and refuses a newer one with the pg remedy; a served owner key in `doctor`.
2. P5: `assert_conformance` green on `tinio-pg`; the serialized `@pg` pass green in the CI job; `@fs`/`@mem` untouched.
