Code citations are pinned: MinIO is pinned to commit `7aac2a2c5b7c882e68c1ce017d8256be2feea27f` (branch `master`, commit date 2026-02-12; the latest published release at fetch time was `RELEASE.2025-10-15T17-29-55Z`), so every MinIO file path below can be read at `https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/<path>`. ## 1. AWS S3 versioning semantics

### 1.1 The three bucket states

AWS documents exactly three bucket states — Unversioned (the default), Versioning-enabled, and Versioning-suspended ([Retaining multiple versions of objects with S3 Versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html)). Verbatim constraints from that page: "You enable and suspend versioning at the bucket level. After you version-enable a bucket, it can never return to an unversioned state. But you can *suspend* versioning on that bucket." and "The versioning state applies to all (never some) of the objects in that bucket."

Enabling is retroactive in effect but not in storage: "Objects that are stored in your bucket before you set the versioning state have a version ID of `null`. When you enable versioning, existing objects in your bucket do not change. What changes is how Amazon S3 handles the objects in future requests." ([Versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html)). New writes then get IDs — "After you enable versioning on a bucket, Amazon S3 automatically adds a unique version ID to every object stored (using `PUT`, `POST`, or `CopyObject`) in the bucket." ([Adding objects to versioning-enabled buckets](https://docs.aws.amazon.com/AmazonS3/latest/userguide/AddingObjectstoVersioningEnabledBuckets.html)).

### 1.2 What AWS actually documents about version IDs

The S3 User Guide says only that version IDs are *unique* and *server-generated*; it does not document a format, a length limit, or any ordering semantics for the ID string itself ([Versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html), [Adding objects to versioning-enabled buckets](https://docs.aws.amazon.com/AmazonS3/latest/userguide/AddingObjectstoVersioningEnabledBuckets.html)). The strongest first-party wording I could find for "opaque" is in AWS's Lightsail S3-compatible bucket docs, not the S3 User Guide: "Version IDs cannot be edited. They are Unicode, UTF-8 encoded, URL-ready, opaque strings that are no more than 1,024 bytes long." ([Enable and suspend object versioning in Lightsail](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-managing-bucket-object-versioning.html)). I checked the current S3 User Guide versioning page and its 2023 Wayback snapshot and neither contains the word "opaque" (`UNVERIFIED` as an S3-User-Guide statement; it is verifiably an AWS statement, and it matches the 1,024-byte ceiling in the S3 API model where version IDs appear as ordinary strings). AWS never documents version IDs as sortable, monotonic, or time-encoded — see 1.6 for what it does promise about ordering.

### 1.3 The `null` version

The `null` version is a real, addressable version, not the absence of one. It is the version that existed before versioning was enabled, and the version written while versioning is suspended ([Versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html)). It can be named explicitly in the API: "To delete a delete marker with a `NULL` version ID, you must pass the `NULL` as the version ID in the `DeleteObject` request." ([Working with delete markers](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ManagingDelMarkers.html)). Lifecycle rules can expire the current version and an `ExpiredObjectDeleteMarker` action can clean up a stale delete marker ([Working with delete markers](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ManagingDelMarkers.html)).

### 1.4 Delete markers

- "Only Amazon S3 can create a delete marker, and it does so whenever you send a `DeleteObject` request on an object in a versioning-enabled or suspended bucket. The object specified in the `DELETE` request is not actually deleted. Instead, the delete marker becomes the current version of the object. The object's key name (or key) becomes the key of the delete marker." ([Working with delete markers](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeleteMarker.html)).
- GET/HEAD without a `versionId`, when the current version is a delete marker: 404 (Not Found) plus `x-amz-delete-marker: true`.
- GET/HEAD *with* a `versionId` that names a delete marker: 405 (Method Not Allowed), `x-amz-delete-marker: true`, and `Last-Modified: timestamp` (the latter "only when using the `HeadObject` or `GetObject` API operations"). Verbatim: "When you get an object by specifying a `versionId` in your request, if the specified version is a delete marker, Amazon S3 responds with the following: A 405 (Method Not Allowed) error, A response header, `x-amz-delete-marker: true`, A response header, `Last-Modified: timestamp`" ([Working with delete markers](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeleteMarker.html)).
- The two response headers on `DeleteObject` distinguish the two cases: `x-amz-delete-marker` "Indicates whether the specified object version that was permanently deleted was (true) or was not (false) a delete marker before deletion", and `x-amz-version-id` "Returns the version ID of the delete marker created as a result of the DELETE operation" ([DeleteObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DeleteObject.html)).
- A plain `DELETE` while the current version is already a delete marker does not remove anything — it stacks another delete marker: "if the version that is a delete marker (without specifying the version ID of the delete marker), Amazon S3 does not delete the delete marker, but instead `PUTs` another delete marker." ([Working with delete markers](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ManagingDelMarkers.html)).
- A delete marker is invisible to `ListObjects` but visible to `ListObjectVersions`, where it appears as a `<DeleteMarker>` element with its own `VersionId` and `IsLatest` ([ListObjectVersions](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectVersions.html)).

### 1.5 Versioning-suspended write and delete rules

The suspended-state `DELETE` rules are documented in detail ([Deleting objects from versioning-suspended buckets](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjectsfromVersioningSuspendedBuckets.html)): "If versioning is suspended for a bucket, a `DELETE` request: Can only remove an object whose version ID is `null`. Doesn't remove anything if there isn't a null version of the object in the bucket. Inserts a delete marker into the bucket." And the consequence: "Since a delete marker doesn't contain any content, you'll lose the content for the `null` version when a delete marker replaces it." The delete marker inserted this way itself carries a `null` version ID. Explicit-version deletion still works: "Even in a versioning-suspended bucket, the bucket owner can permanently delete a specified version by including the version ID in the `DELETE` request."

The suspended-state PUT rule (a new write replaces the `null` version in place rather than adding a version) is stated by AWS in the API reference for `PutBucketVersioning` only as "**Suspended** — Disables versioning for the objects in the bucket." ([PutBucketVersioning](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutBucketVersioning.html)); the user-guide page that stated it more fully ("Adding objects to versioning-suspended buckets") returns HTTP 404 at the URL naming convention used by its sibling pages, and I could not locate its current replacement (`UNVERIFIED` for the exact wording of the PUT-side rule; the delete-side rule above is verified).

### 1.6 Listing order and pagination

The documented ordering guarantee is by *storage time*, not by ID string: "Amazon S3 returns object versions in the order in which they were stored, with the most recently stored returned first." ([Listing objects in a versioning-enabled bucket](https://docs.aws.amazon.com/AmazonS3/latest/userguide/list-obj-version-enabled-bucket.html)). Keys are ordered (list results are "returned in UTF-8 binary order" — [Listing keys using the REST API](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ListingKeysUsingAPIs.html)); versions of one key are ordered newest-first, and each entry carries `IsLatest`. Pagination is by `KeyMarker` plus `VersionIdMarker` ([ListObjectVersions](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectVersions.html)). Note that pagination therefore requires the server to be able to resume *within* a key's version list given an arbitrary version ID — a design constraint on the version-ID scheme (see 6.1).

### 1.7 What AWS documents about physical storage and billing

AWS is explicit that there is no delta coding between versions: "Normal Amazon S3 rates apply for every version of an object that is stored and transferred. Each version of an object is the entire object; it is not just a diff from the previous version. Thus, if you have three versions of an object stored, you are charged for three objects." ([Versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html); repeated verbatim on [How S3 Versioning works](https://docs.aws.amazon.com/AmazonS3/latest/userguide/versioning-workflows.html)). AWS publishes nothing about the internal layout or encoding of version IDs. The lifecycle interaction is documented: the `Expiration` action applies to the current version and (in a versioned bucket) results in a delete marker being added rather than a delete, while `NoncurrentVersionExpiration` "applies to noncurrent object versions, and Amazon S3 permanently removes these object versions. You cannot recover permanently removed objects." ([Deleting object versions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjectVersions.html)).

## 2. MinIO: physical layout

### 2.1 On-disk layout

The authoritative layout description is the comment block at the top of [`cmd/xl-storage-format-v2.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/xl-storage-format-v2.go):

```
// disk1/
// └── bucket
//     └── object
//         ├── a192c1d5-9bd5-41fd-9a90-ab10e165398d
//         │   └── part.1
//         ├── c06e0436-f813-447e-ae5e-f2564df9dfd4
//         │   └── part.1
//         ├── df433928-2dcf-47b1-a786-43efa0f6b424
//         │   └── part.1
//         ├── legacy
//         │   └── part.1
//         └── xl.meta
```

So: one directory per object at its key path, holding one `xl.meta` metadata file plus one UUID-named *data directory per version*, each containing `part.N` files (a `legacy` directory holds the pre-xl.meta-format data). Every version of the object lives under the *same* object directory — the key path names the object, and the version identity is carried inside `xl.meta` and in the per-version data-directory name. `xl.meta` is a msgpack-encoded `[]journal`: "The []journal contains all the different versions of the object. This array can have 3 kinds of objects: ``object``: If the object is uploaded the usual way: putobject, multipart-put, copyobject / ``delete``: This is the delete-marker / ``legacyObject``: This is the legacy object in xlV1 format, preserved until its overwritten. The most recently updated element in the array is considered the latest version." ([`cmd/xl-storage-format-v2.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/xl-storage-format-v2.go)).

Small objects are inlined into `xl.meta` itself rather than written to `part.1`: on read, `canInline := fi.ShardFileSize(fi.Parts[0].ActualSize) <= inlineBlock` with `if inlineBlock <= 0 { inlineBlock = 128 * humanize.KiByte }` ([`cmd/xl-storage.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/xl-storage.go)); the configured value is documented in the storage-class config as "InlineBlock indicates the size of the block which will be used to inline an erasure shard and written along with xl.meta on the drive, on a versioned bucket this value is automatically chosen to 1/8th of the this value" ([`internal/config/storageclass/storage-class.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/internal/config/storageclass/storage-class.go)). A per-version header flag records it (`xlFlagInlineData`), alongside `xlFlagUsesDataDir` and `xlFlagFreeVersion` ([`cmd/xl-storage-format-v2.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/xl-storage-format-v2.go)). `part.1` (through `part.N` for multipart) holds that drive's *erasure shard* of the version — MinIO never stores whole-object blobs on one disk.

### 2.2 Writing a version, retaining the previous one

A new version is first written to a temporary object under the reserved `.minio.sys` bucket (`tempErasureObj := pathJoin(uniqueID, fi.DataDir, partName)`, written via `minioMetaTmpBucket`), then committed under the final path with `renameData` → `RenameData` ([`cmd/erasure-object.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/erasure-object.go)). Both identity values are minted per PUT in `putObject`:

```go
fi.VersionID = opts.VersionID
if opts.Versioned && fi.VersionID == "" {
    fi.VersionID = mustGetUUID()
}
fi.DataDir = mustGetUUID()
```

([`cmd/erasure-object.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/erasure-object.go); `mustGetUUID` is `uuid.NewRandom().String()` in [`cmd/object-api-utils.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/object-api-utils.go).) The version ID is the S3-visible identity; the data directory is a *separate*, purely internal UUID. Nothing is overwritten: the previous version keeps its own data directory and its entry in the journal, and it becomes noncurrent.

### 2.3 MinIO's crash-consistency protocol for publishing a version

`RenameData` is documented as "rename source path to destination path atomically, metadata and data directory" ([`cmd/xl-storage.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/xl-storage.go)). Its commit sequence, in source order, is: read the current destination `xl.meta` into `dstBuf`; if there is an old data dir, preserve the pre-existing metadata as a backup inside that old data dir — "If we have oldDataDir then we must preserve current xl.meta as backup, in-case needing renames(). ... preserve current xl.meta inside the oldDataDir." writing `xl.meta.bkp`; then "Commit meta-file" via `renameAll(srcFilePath, dstFilePath, skipParent)`; and the inverse path exists as `opts.UndoWrite && opts.OldDataDir != ""` → `renameAll(.../xl.meta.bkp, .../xl.meta)`. The constants are `xlStorageFormatFile = "xl.meta"` and `xlStorageFormatFileBackup = "xl.meta.bkp"`. This is a concrete, published instance of "keep the old materialized copy until the new one is atomically published, and be able to roll back". The atomicity it leans on is the filesystem's: "If newpath already exists, it will be atomically replaced, so that there is no point at which another process attempting to access newpath will find it missing." ([rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html)).

### 2.4 Delete markers and free versions

A delete marker is a journal entry of type `delete` (`DeleteType`, with a `DeleteMarker` payload) rather than an object entry; `xlMetaV2Version.Valid()` requires `j.DeleteMarker != nil && j.DeleteMarker.ModTime > 0` ([`cmd/xl-storage-format-v2.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/xl-storage-format-v2.go)). `xlStorage.DeleteVersion` "deletes FileInfo metadata for path at `xl.meta`. forceDelMarker will force creating a new `xl.meta` to create a new delete marker", and if no `xl.meta` exists it will "Create a new xl.meta with a delete marker in it" ([`cmd/xl-storage.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/xl-storage.go)).

MinIO has a second, internal kind of tombstone it calls a **free version**: "In addition to these we have a special kind called free-version. This is represented using a delete-marker and MetaSys entries. It's used to track tiered content of a deleted/overwritten version. This version is visible _only_ to the scanner routine, for subsequent deletion. This kind of tracking is necessary since a version's tiered content is deleted asynchronously." ([`cmd/xl-storage-format-v2.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/xl-storage-format-v2.go)). It is created with a fresh ID (`fi.SetTierFreeVersionID(mustGetUUID())` in [`cmd/erasure-object.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/erasure-object.go)) and skipped during normal listing unless explicitly requested (`if header.FreeVersion() { nonFreeVersions-- ... }` in `ToFileInfo`), with a dedicated audit action `ILMFreeVersionDelete = "ilm:free-version-delete"` ([`cmd/data-scanner.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/data-scanner.go)). Free versions are also excluded from tier accounting: "Skip tier accounting if object version is a delete-marker or a free-version tracking deleted transitioned objects" ([`cmd/data-scanner.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/data-scanner.go)).

### 2.5 Version IDs: generation and ordering

- Generation: random v4 UUID, `mustGetUUID()` → `uuid.NewRandom().String()` ([`cmd/object-api-utils.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/object-api-utils.go)). MinIO's docs confirm the server-side-only rule: "MinIO AIStor does not support client-managed version ID allocation. All version ID generation is handled by the Object Store process." ([MinIO object versioning](https://min.io/docs/minio/linux/administration/object-management/object-versioning.html)).
- Ordering: version IDs are *not* used for ordering. The journal is kept sorted by `sortsBefore`, whose first key is `ModTime` descending — "Prefer newest modtime. if x.ModTime != o.ModTime { return x.ModTime > o.ModTime }" — and only falls back to type, signature, then `bytes.Compare(x.VersionID[:], o.VersionID[:])` as a consistency tiebreaker ([`cmd/xl-storage-format-v2.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/xl-storage-format-v2.go)). A random UUID is therefore fine for MinIO precisely because nothing sorts by it.
- `null`: `nullVersionID = "null"` (`cmd/xl-storage.go`); internally the null version is encoded as the *zero* UUID, and the string `"null"` is accepted and mapped at the API boundary — `if fi.VersionID == "" { fi.VersionID = nullVersionID }` and `if fi.VersionID != "" && fi.VersionID != nullVersionID { uv, err = uuid.Parse(fi.VersionID) }`, with `ToFileInfo` rendering the zero UUID back to an empty version string ([`cmd/xl-storage-format-v2.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/xl-storage-format-v2.go)). MinIO's docs agree: "For objects created while versioning is disabled or suspended, MinIO AIStor uses a `null` version ID. You can access or remove these objects by specifying `null` as the version ID as part of S3 operations." ([MinIO object versioning](https://min.io/docs/minio/linux/administration/object-management/object-versioning.html)).

### 2.6 Garbage collection of noncurrent versions

Three mechanisms, all asynchronous and scanner-driven:

1. **ILM noncurrent expiration.** The lifecycle config supports `NoncurrentVersionExpiration` and `NewerNoncurrentVersions`; the scanner turns matching events into a delete list: `case lifecycle.DeleteVersionAction: // noncurrent versions expiration` appends an `ObjectToDelete{ObjectV{ObjectName, VersionID}}` to `toDel` ([`cmd/data-scanner.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/data-scanner.go)); the config predicates `rule.NoncurrentVersionExpiration.NoncurrentDays > 0` and `.NewerNoncurrentVersions > 0` gate whether the rule is applied ([`internal/bucket/lifecycle/lifecycle.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/internal/bucket/lifecycle/lifecycle.go)). This is the `mc ilm rule add` surface, verified at the CLI reference: `--noncurrent-expire-days` (with a cross-reference "Use either the --noncurrent-expire-days flag or the --purge-all-object-versions-days flag to apply expiration behavior to noncurrent object versions"), `--noncurrent-expire-newer`, `--noncurrent-transition-days`, and for the current version `--expire-days` ("The number of days to retain an object after being created").
2. **Delete-marker expiry.** `ExpiredObjectDeleteMarker` is a first-class field of the lifecycle `Expiration` element (`type ExpireDeleteMarker struct { Boolean }` in [`internal/bucket/lifecycle/expiration.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/internal/bucket/lifecycle/expiration.go)); the CLI exposes it as `--expire-delete-marker`, "Specify this option to direct MinIO AIStor to remove delete markers for objects with no remaining object versions", which is mutually exclusive with `--expire-days` ([mc ilm rule add](https://min.io/docs/minio/linux/reference/minio-mc/mc-ilm-rule-add.html)). A separate `--purge-all-object-versions-days` / `--purge-all-object-versions-delete-marker` pair exists to drop every version of an object outright ([mc ilm rule add](https://min.io/docs/minio/linux/reference/minio-mc/mc-ilm-rule-add.html)).
3. **Free-version cleanup** for transitioned objects, as described in 2.4.

The whole thing runs on "a low-priority process that yields to higher-priority workloads, so that rule timing does not cause performance spikes. The scanner may therefore not detect an object as eligible for a configured transition or expiration lifecycle rule until *after* the lifecycle rule period has passed." ([MinIO object lifecycle management](https://min.io/docs/minio/linux/administration/object-management/object-lifecycle-management.html)). Deletion itself has no refcount: it is a per-version directory removal plus a journal rewrite, and `DeleteVersion` "returns to the caller which dataDir to delete, also indicates if this is the last version" — the *last* version's removal deletes the object path entirely ([`cmd/xl-storage-format-v2.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/xl-storage-format-v2.go)).

### 2.7 Does MinIO deduplicate or content-address object data? No.

Verified, not assumed: (a) data paths are `<bucket>/<object>/<DataDir UUID>/part.N`, with `DataDir` assigned from `mustGetUUID()` on every PUT ([`cmd/erasure-object.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/erasure-object.go)), so two identical uploads land in two different directories; (b) the recursive file listing of the pinned commit (1,566 paths, `"truncated": false`, via `https://api.github.com/repos/minio/minio/git/trees/7aac2a2c5b7c882e68c1ce017d8256be2feea27f?recursive=1`) contains zero paths matching `dedup|dedupe|chunk`; (c) MinIO's own erasure-coding documentation page contains no occurrence of "dedup" ([MinIO erasure coding](https://min.io/docs/minio/linux/operations/concepts/erasure-coding.html)). MinIO's only content-derived values are integrity checksums (bitrot), not addresses: e.g. `BitrotChecksumAlgo`, `DefaultBitrotAlgorithm`, and xxhash/jsoniter imports in [`cmd/xl-storage-format-v2.go`](https://github.com/minio/minio/blob/7aac2a2c5b7c882e68c1ce017d8256be2feea27f/cmd/xl-storage-format-v2.go). Identical bytes across versions or objects consume full space.

## 3. Other S3 implementations and object stores

| System | Where a version physically lives | Data dedup / chunking |
|---|---|---|
| Ceph RGW | one RADOS object per version, named `<bucket_marker>_:<version_id>_<key>`; the `null` version is deliberately stored under the plain `<bucket_marker>_<key>` | no dedup; striping via `rgw_max_chunk_size` (default 4 MiB) + manifest/tail objects |
| OpenStack Swift | versioned_writes: full archived copies named `<length><object_name>/<timestamp>` in an archive container (legacy), or a full copy in a hidden container plus a symlink (new mode) | no dedup; SLO segment sharing only when a client explicitly lists the same segment |
| Garage | content-addressed blocks + a `version` CRDT table keyed by version UUID | **yes — explicit, documented block-level dedup**, blocks by blake2 hash, default 1 MiB |
| SeaweedFS | `.versions/` sibling directory per object holding one file per version (`v_<32-hex>`) | no dedup; chunk manifests + filer `-maxMB` auto-chunking (default 4 MB) |
| Cloudflare R2 | n/a — object versioning is not supported | not applicable |
| Backblaze B2 | versioning is always on and implicit; every upload is a stored version identified by (fileName, fileId) | no dedup documented; large files assembled from parts (5 MB–5 GB each) |

### 3.1 Ceph RGW

- **Physical layout.** Every RGW data object is named `<bucket_marker>_<oid>`, where the marker is the bucket instance id: `prepend_bucket_marker()` does `oid = bucket.marker; oid.append("_"); oid.append(orig_oid)` ([rgw_rados.h @v19.2.2](https://github.com/ceph/ceph/blob/v19.2.2/src/rgw/driver/rados/rgw_rados.h#L71-L92); same body at [v17.2.7](https://github.com/ceph/ceph/blob/v17.2.7/src/rgw/rgw_rados.h#L69-L90)). Note the path move: `src/rgw/rgw_rados.{h,cc}` does not exist at v18+; the file is `src/rgw/driver/rados/rgw_rados.{h,cc}`.
- **The S3 version ID *is* the object's `instance` field**, and it is encoded into the physical RADOS name. Object identity is `rgw_obj { bucket, key }` with `rgw_obj_key {name, instance, ns}` ([rgw_common.h @v17.2.7](https://github.com/ceph/ceph/blob/v17.2.7/src/rgw/rgw_common.h#L1806)); a PUT with bucket versioning enabled and no `versionId` calls `gen_rand_obj_instance_name()` and returns the instance to the client as the version id ([rgw_op.cc @v17.2.7](https://github.com/ceph/ceph/blob/v17.2.7/src/rgw/rgw_op.cc#L3961-L3967)). The generator is a 32-character random alphanumeric with no underscores, "no underscore for instance name due to the way we encode the raw keys" ([rgw_rados.cc @v17.2.7](https://github.com/ceph/ceph/blob/v17.2.7/src/rgw/rgw_rados.cc#L7881-L7895)). `rgw_obj_key::get_oid()` returns the plain escaped name only when no encoding is needed; otherwise it returns `_<ns>[:<instance>]_<name>`, so a versioned namespace-less key becomes `_:<version_id>_<key>` ([rgw_obj_types.h @v21.3.0](https://github.com/ceph/ceph/blob/v21.3.0/src/rgw/rgw_obj_types.h); same body at [v17.2.7](https://github.com/ceph/ceph/blob/v17.2.7/src/rgw/rgw_common.h#L1338-L1420)). **Special case:** instance `"null"` and the empty instance are deliberately *not* encoded, so the `null` version lives under the plain `<bucket_marker>_<key>` name — the same code. Namespaces in use: `RGW_OBJ_NS_MULTIPART "multipart"` and `RGW_OBJ_NS_SHADOW "shadow"` ([rgw_rados.h @v17.2.7](https://github.com/ceph/ceph/blob/v17.2.7/src/rgw/rgw_rados.h#L66-L67)).
- **Per-version index record and current-version resolution.** Each version gets a `rgw_bucket_dir_entry` written with `key = obj.key.get_index_key()` (name + instance) plus size/etag/mtime/owner ([rgw_rados.cc @v17.2.7](https://github.com/ceph/ceph/blob/v17.2.7/src/rgw/rgw_rados.cc#L6475-L6497)); the index itself is one OMAPPED RADOS object per bucket shard, not a file ([rgw_rados.cc @v17.2.7](https://github.com/ceph/ceph/blob/v17.2.7/src/rgw/rgw_rados.cc#L2763)). Versioned buckets keep a logical-head record `RGWOLHInfo { rgw_obj target; bool removed; }` in the bucket index, managed by `set_olh`/`update_olh`/`clear_olh`/`repair_olh` — a delete records a marker via `removed` rather than removing the object ([rgw_rados.h @v17.2.7](https://github.com/ceph/ceph/blob/v17.2.7/src/rgw/rgw_rados.h#L97-L115)).
- **Correction to a common assumption:** I found no `_head`, `.__head`, or `.meta` literal in `rgw_rados.{h,cc}`, `rgw_common.h`, `rgw_op.cc`, or `rgw_multi.cc` at v17.2.7. "Head object" is a *role* in code (`get_obj_head_ref`, `remove_rgw_head_obj`), not a filename suffix, and the version id appears as the `:instance` form above. Any claim that Ceph's per-version artifacts use `.meta`/`_head` names is `UNVERIFIED` and unsupported by primary source.
- **Dedup: none.** RGW has no content addressing; each version is a distinct RADOS object derived from the instance-encoded oid. The full RGW option list at v19.2.2 contains zero matches for "dedup" ([rgw.yaml.in @v19.2.2](https://github.com/ceph/ceph/blob/v19.2.2/src/common/options/rgw.yaml.in)). This is a source-derived absence, not an explicit "we do not dedup" statement — mark as `UNVERIFIED`-as-documented.
- **Chunking/striping does exist, but it is not dedup.** `rgw_max_chunk_size` defaults to 4 MiB: "The chunk size is the size of RADOS I/O requests that RGW sends when accessing data objects ... This also defines the RGW head object size, as head operations need to be atomic ... up to this amount of payload data will be stored alongside metadata in the head object." ([rgw.yaml.in @v19.2.2](https://github.com/ceph/ceph/blob/v19.2.2/src/common/options/rgw.yaml.in); rendered [Ceph RGW config reference](https://docs.ceph.com/en/latest/radosgw/config-ref/)). Related defaults: `rgw_put_obj_max_window_size` 64 MiB, `rgw_max_put_size` 5 GiB. Multipart parts are separate objects and the head object carries the manifest in xattr `RGW_ATTR_MANIFEST` pointing at tail objects ([rgw_rados.cc @v17.2.7](https://github.com/ceph/ceph/blob/v17.2.7/src/rgw/rgw_rados.cc#L3194-L3200)).
- The user-facing state rules match AWS: "Enabled: All objects added to the bucket receive a unique version ID"; "Suspended: ... receive the version ID null" ([bucketops.rst @v19.2.2](https://github.com/ceph/ceph/blob/v19.2.2/doc/radosgw/s3/bucketops.rst), rendered [docs.ceph.com](https://docs.ceph.com/en/latest/radosgw/s3/bucketops/)).

### 3.2 OpenStack Swift versioned_writes

Swift has three modes — two legacy (`X-Versions-Location`, `X-History-Location`) and a newer "object versioning" mode (`X-Versions-Enabled: true`) — all implemented in the `versioned_writes` middleware ([middleware source, branch master](https://opendev.org/openstack/swift/src/branch/master/swift/common/middleware/versioned_writes/)).

- **Legacy layout: versions are ordinary full objects with a derived name in another container.** "These non-current versions are named as follows: `<length><object_name>/<timestamp>` Where length is the 3-character, zero-padded hexadecimal character length of the object name, `<object_name>` is the object name, and `<timestamp>` is the time when the object was initially created as a current version." ([Object Versioning API](https://docs.openstack.org/swift/latest/api/object_versioning.html); same in [legacy.py](https://opendev.org/openstack/swift/src/branch/master/swift/common/middleware/versioned_writes/legacy.py)). There is no separate versioning data structure — a version is a normal object at a computed name.
- **Delete semantics differ by header.** `X-Versions-Location` is a pop: a DELETE "only remove[s] the current version of the object. If any previous versions exist ... the most recent one is copied over the current version, and the copy in the archive container is deleted" — so "if you have 5 total versions ... you must delete the object 5 times". `X-History-Location` instead copies the current version to the archive container and writes a zero-byte delete marker whose content type is `application/x-deleted;swift_versions_deleted=1` ([legacy.py](https://opendev.org/openstack/swift/src/branch/master/swift/common/middleware/versioned_writes/legacy.py); [Object Versioning API](https://docs.openstack.org/swift/latest/api/object_versioning.html)).
- **New mode: hidden container plus symlink.** "the actual object is written to a hidden container and a symlink object is written to the parent container. Every object is assigned a version id ... `X-Object-Version-Id`"; a delete writes a zero-byte delete-marker *version* and deletes the symlink, and with versioning disabled the object gets a `null` version id ([object_versioning.py](https://opendev.org/openstack/swift/src/branch/master/swift/common/middleware/versioned_writes/object_versioning.py)). The hidden container is derived from the parent via `get_reserved_name('versions', container_name)`, and **the version id is a Swift `Timestamp` stored bit-inverted in the version object's name so that newest sorts first**: `build_versions_object_name(name, version_id) → reserved_name(name, ~Timestamp(version_id).internal)` (same file). Swift version ids are therefore timestamps, not UUIDs.
- **Large objects.** A large object is a manifest object holding a JSON list of segments (fid/etag/size) and marked `X-Static-Large-Object: True`; "Objects can be referenced by multiple manifests" ([slo.py](https://opendev.org/openstack/swift/src/branch/master/swift/common/middleware/slo.py)) — segment sharing happens only if the client explicitly lists the same segment object; there is no automatic dedup. The versioning middleware does a real copy (`COPY`) of each version.
- **No automatic pruning past a limit.** Contrary to a common assumption, neither mode deletes the oldest version past a prefix/count limit: `X-Versions-Location` removes exactly one version per explicit DELETE, and the new mode has no lifecycle or prune code. Expiry is done with ordinary object expiration (`X-Delete-At`/`X-Delete-After`) or manual deletes ([Object Expiration](https://docs.openstack.org/swift/latest/api/object-expiration.html)). Swift's S3-compatible API does claim versioning support ([S3 compatibility](https://docs.openstack.org/swift/latest/s3_compat.html)).

### 3.3 Garage — the closest prior art to a content-addressed version store

Garage is the most directly relevant system in this survey: it stores object bytes in content-addressed blocks, tracks versions by UUID, and garbage-collects blocks by reference count. Repo: primary at `git.deuxfleurs.fr/Deuxfleurs/garage`, GitHub mirror used for permalinks; all citations below are at tag **v2.4.1**, the latest release at fetch time.

- **Block layout is content-addressed on disk:** `<data_dir>/blocks/<hex(hash[0])>/<hex(hash[1])>/<hash>`, with the drive/partition chosen from hash bytes [2] and [3] over 1024 partitions (`HASH_DRIVE_BYTES = (2,3)`, `DRIVE_NPART = 1024`) ([src/block/layout.rs @v2.4.1](https://github.com/deuxfleurs-org/garage/blob/v2.4.1/src/block/layout.rs)).
- **Version metadata** lives in a `version` CRDT table keyed by the **version UUID as partition key** with an `EmptyKey` sort key, holding `Version { uuid, deleted, blocks: Map<VersionBlockKey{part_number, offset}, VersionBlock{hash: blake2, size}>, parts_etags, backlink }` ([src/model/s3/version_table.rs @v2.4.1](https://github.com/deuxfleurs-org/garage/blob/v2.4.1/src/model/s3/version_table.rs)). The object table stores, per object key, the list of `ObjectVersion {uuid, state, data}` ([src/model/s3/object_table.rs @v2.4.1](https://github.com/deuxfleurs-org/garage/blob/v2.4.1/src/model/s3/object_table.rs)).
- **Reference counting is explicit and first-class:** `block_refs` entries are `BlockRef { block: Hash (partition key), version: Uuid (sort key), deleted: crdt::Bool }` ([src/model/s3/block_ref_table.rs @v2.4.1](https://github.com/deuxfleurs-org/garage/blob/v2.4.1/src/model/s3/block_ref_table.rs)). **A block's reference count is therefore literally the number of version UUIDs referencing that hash** — dedup and refcounting fall out of the same table.
- **Dedup is documented, not incidental:** "All data stored in Garage is deduplicated, and optionally compressed using Zstd. Objects uploaded to Garage are chunked in blocks of constant sizes (see `block_size`), and the hashes of individual blocks are used to dispatch them to storage nodes and **to deduplicate them**." ([doc/book/reference-manual/features.md @v2.4.1](https://github.com/deuxfleurs-org/garage/blob/v2.4.1/doc/book/reference-manual/features.md); rendered [garagehq.deuxfleurs.fr](https://garagehq.deuxfleurs.fr/documentation/reference-manual/features/)). Block size defaults to 1 MiB (`default_block_size` → 1048576 in [src/util/config.rs @v2.4.1](https://github.com/deuxfleurs-org/garage/blob/v2.4.1/src/util/config.rs)). Identical blocks across versions or across objects exist once; multipart part data is chunked the same way and part etags are kept in `Version.parts_etags` (version_table.rs).
- **GC is refcount-based *with a safety delay*:** "Blocks in the data directory are reference-counted ... blocks never get deleted in a 10 minute interval following the time when the RC reaches zero" ([doc/book/design/internals.md @v2.4.1](https://github.com/deuxfleurs-org/garage/blob/v2.4.1/doc/book/design/internals.md)). Repair tooling is first-class: `garage repair scrub start/pause`, `garage repair blocks`, `garage block info|list-errors|retry-now|purge`, `garage repair versions`, `garage repair block-refs`, `garage repair block-rc` ([durability-repairs.md @v2.4.1](https://github.com/deuxfleurs-org/garage/blob/v2.4.1/doc/book/operations/durability-repairs.md)).
- **The UUID is generated per write but not exposed as S3 versioning:** `gen_uuid()` is called at write time and returned as `x-amz-version-id` (`hex::encode(res.version_uuid)`) even though Garage's S3 API does not support bucket versioning — `GetBucketVersioning` is a stub that "always returns 'versioning not enabled'" ([put.rs @v2.4.1](https://github.com/deuxfleurs-org/garage/blob/v2.4.1/src/api/s3/put.rs), [s3-compatibility.md @v2.4.1](https://github.com/deuxfleurs-org/garage/blob/v2.4.1/doc/book/reference-manual/s3-compatibility.md)). So Garage has exactly the internal machinery a versioned store needs (per-write UUID, content-addressed blocks, refcount table) without the S3 versioning surface — and, conversely, it shows that "overwrite an object" can be modelled as "tombstone the old version, write a new one, let the RC drain".

### 3.4 SeaweedFS

- **Volume storage.** Each volume is `<volumeId>.dat` plus a `<volumeId>.idx` needle map (id → offset, size) ([weed/storage/volume.go](https://github.com/seaweedfs/seaweedfs/blob/master/weed/storage/volume.go), [wiki: Data Structure for Large Files](https://github.com/seaweedfs/seaweedfs/wiki/Data-Structure-for-Large-Files)). A file id is `FileId { VolumeId, Key (NeedleId), Cookie }`, rendered as `<volumeId>,<needleId><cookie>` (e.g. `6,1b70e99bcd`) ([weed/storage/needle/file_id.go](https://github.com/seaweedfs/seaweedfs/blob/master/weed/storage/needle/file_id.go), [wiki: Large File Handling](https://github.com/seaweedfs/seaweedfs/wiki/Large-File-Handling)); the cookie is a "random number to mitigate brute force lookups" ([weed/storage/needle/needle.go](https://github.com/seaweedfs/seaweedfs/blob/master/weed/storage/needle/needle.go)). Needle framing: `CookieSize = 4`, `NeedleIdSize = 8`, `SizeSize = 4` → 16-byte header, 8-byte padding, plus a CRC32 checksum; v3 needles append the checksum and an 8-byte timestamp after the data ([weed/storage/types/needle_types.go](https://github.com/seaweedfs/seaweedfs/blob/master/weed/storage/types/needle_types.go), [needle_write_v3.go](https://github.com/seaweedfs/seaweedfs/blob/master/weed/storage/needle/needle_write_v3.go)).
- **S3 versioning is a `.versions` sibling directory per object.** The writer uses `versionsDir := bucketDir + "/" + cleanObject + s3_constants.VersionsFolder`, storing both versions and delete markers there ([weed/s3api/s3api_object_versioning.go](https://github.com/seaweedfs/seaweedfs/blob/master/weed/s3api/s3api_object_versioning.go)); the wiki documents the on-disk shape as `/buckets/my-bucket/example.txt` plus `example.txt.versions/v_<32-hex>` ([wiki: S3 Object Versioning](https://github.com/seaweedfs/seaweedfs/wiki/S3-Object-Versioning)). The `.versions` directory entry's extended attributes cache the latest-version pointers (`ExtLatestVersionIdKey`, `ExtLatestVersionFileNamesKey`, size/ETag/mtime/owner, `ExtLatestVersionIsDeleteMarker`, `ExtDeleteMarkerKey = "Seaweed-X-Amz-Delete-Marker"`) ([weed/s3api/s3_constants/extend_key.go](https://github.com/seaweedfs/seaweedfs/blob/master/weed/s3api/s3_constants/extend_key.go)), and a background reconciler heals stranded latest-version pointers ([s3api_versioning_reconciler.go](https://github.com/seaweedfs/seaweedfs/blob/master/weed/s3api/s3api_versioning_reconciler.go)).
- **Version IDs are sortable by construction — the clearest example of that design choice in this survey.** `weed/s3api/s3api_version_id.go` states: "New format uses inverted timestamps so newer versions sort first lexicographically. Old format used raw timestamps where older versions sorted first", computing `invertedTimestamp := math.MaxInt64 - now` and producing a 32-hex ID (16 hex of inverted nanosecond timestamp + 16 hex random); the file also says "Version IDs are opaque to clients but become filenames under `.versions`", and suspended versioning overwrites with version id `null` ([s3api_version_id.go](https://github.com/seaweedfs/seaweedfs/blob/master/weed/s3api/s3api_version_id.go), [wiki](https://github.com/seaweedfs/seaweedfs/wiki/S3-Object-Versioning)). So the ID is simultaneously opaque to clients *and* the on-disk filename *and* the listing sort key — three properties fused into one string.
- **Chunking, no dedup.** Large files use a JSON `ChunkManifest{Name, Mime, Size, Chunks:[{Fid, Offset, Size}]}` (uploaded with `cm=true`) as the entry point, and filer-side auto-chunking splits files larger than `-maxMB` (default **4 MB**) ([weed/operation/chunked_file.go](https://github.com/seaweedfs/seaweedfs/blob/master/weed/operation/chunked_file.go), [weed/command/filer.go](https://github.com/seaweedfs/seaweedfs/blob/master/weed/command/filer.go), [wiki: Large File Handling](https://github.com/seaweedfs/seaweedfs/wiki/Large-File-Handling)); manifests can nest and `ResolveChunkManifest` resolves recursively ([weed/filer/filechunk_manifest.go](https://github.com/seaweedfs/seaweedfs/blob/master/weed/filer/filechunk_manifest.go)). Needles are addressed by (volume, needle id, cookie), never by content hash, and greps for "dedup" in the filer/needle data paths return nothing (the one hit near the filer is a singleflight that deduplicates concurrent *remote-cache operations*, not data) — so no dedup, `UNVERIFIED`-as-documented.

### 3.5 Cloudflare R2 and Backblaze B2 (semantics only; neither publishes a layout)

- **Cloudflare R2: versioning is not supported.** The S3 API compatibility table marks both `GetBucketVersioning` and `PutBucketVersioning` as unsupported ([R2 S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/)); the docs index lists no versioning page ([r2/llms.txt](https://developers.cloudflare.com/r2/llms.txt)); the "Object lifecycles" page defines only expire/transition rules for live objects plus a default 7-day rule to expire multipart uploads — no noncurrent-version rules ([R2 object lifecycles](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)); the delete docs contain no version-id semantics ([R2 delete objects](https://developers.cloudflare.com/r2/objects/delete-objects/)); and the release notes record only a 2022 "dummy implementation" of `GetBucketVersioning` that mimics an empty AWS response ([R2 release notes](https://developers.cloudflare.com/r2/platform/release-notes/)). The closest retention feature is bucket locks, which prevent delete/overwrite for a period — retention, not history ([R2 bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/)). Third-party pages claiming R2 versioning works exist; primary Cloudflare docs contradict them.
- **Backblaze B2: versioning is always on and implicit.** `b2_upload_file` "Uploads one file and returns its unique file ID"; uploading another file with the same name creates another version with "the newest one first", and `b2_list_file_versions` lists all of them ([B2 File Versions](https://www.backblaze.com/docs/cloud-storage-file-versions)). A version is identified by (fileName, fileId), where `fileId` is "The unique identifier for this version of this file", used by `b2_get_file_info`, `b2_download_file_by_id`, and `b2_delete_file_version` ([b2_upload_file](https://www.backblaze.com/apidocs/b2-upload-file)). Downloading by name returns the most recent version. The listing's `action` field is `"upload" | "start" | "hide" | "folder"`, where `"start"` is an unfinished large file and `"hide"` is "a file version marking the file as hidden, so that it will not show up in `b2_list_file_names`" ([b2_list_file_versions](https://www.backblaze.com/apidocs/b2-list-file-versions)); `b2_hide_file` "Hides a file so that downloading by name will not find the file. Previous versions of the file are still stored" ([b2_hide_file](https://www.backblaze.com/apidocs/b2-hide-file)). Ordering is file name ascending, then upload date/time descending. Lifecycle rules are per `fileNamePrefix` and include `daysFromUploadingToHiding`, `daysFromHidingToDeleting`, and `daysFromStartingToCancelingUnfinishedLargeFiles` ([B2 lifecycle rules](https://www.backblaze.com/docs/cloud-storage-lifecycle-rules)). Large files (5 MB–10 TB) are assembled from 5 MB–5 GB parts, each with its own SHA-1: "When you call `b2_finish_large_file`, the parts are combined into one large file, but the number of bytes that are stored remains the same" ([B2 large files](https://www.backblaze.com/docs/cloud-storage-large-files)). No dedup is documented — every upload or copy is a separately stored version with its own fileId (`UNVERIFIED`-as-documented). The file-id shape is not documented as a format, but the official example `4_z4a48fe8875c6214145260818_f0000000000823564_d20150725_m091433_c001_v0000123_t0104` embeds the upload date and time in its `_d<yyyymmdd>_m<hhmmss>` segment ([b2_upload_file](https://www.backblaze.com/apidocs/b2-upload-file)).

### 3.6 What the S3-compatible field actually does

Three observations cut across the table. First, **no S3-compatible server in this survey stores version history as deltas**: Ceph, Swift, SeaweedFS, and B2 each store whole per-version copies; only Garage dedups, and it does so at the block layer, invisible to the S3 API (Garage also does not expose versioning at all). Second, **two version-ID idioms dominate**: random opaque IDs (MinIO's UUIDv4, Garage's UUID, Ceph's 32-char random alphanumeric) and **timestamp-derived sortable IDs** (Swift stores a bit-inverted `Timestamp` in the version object's name; SeaweedFS stores an inverted-nanosecond hex prefix; B2's fileId embeds the upload time) — with the sortable variants chosen precisely so that listing, on-disk naming, and age-based expiry can all share one string. Third, **per-object version state is usually carried outside the version data** — Ceph's bucket-index `dir_entry` + OLH record, SeaweedFS's `.versions` directory xattrs, Swift's container-level `X-Versions-Location` — which is how those systems answer "which version is current?" without scanning the version list.

### 4.2 Per-system notes

- **git.** Loose objects are zlib-deflated files named by the SHA-1 of `"<type> <len>\0" + content`, fanned out by first hex byte ([Git Internals — Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)). Packfiles store each object whole or as an `ofs-delta`/`ref-delta` against a base that may itself be deltified ([gitformat-pack — deltified representation](https://git-scm.com/docs/gitformat-pack#_deltified_representation)); delta selection is heuristic (sort by type/size/name, compare within `--window`, default 10; `--depth` default 50, max 4095) and not content-defined ([git-pack-objects](https://raw.githubusercontent.com/git/git/master/Documentation/git-pack-objects.adoc)). The v2 `.idx` is a 256-entry fan-out table + sorted OID table + CRC32 + offset table ([gitformat-pack — version 2 pack idx files](https://git-scm.com/docs/gitformat-pack#_version_2_pack_idx_files_support_packs_larger_than_4_gib_and)). Reclamation is reachability, not refcounting: `git prune` "runs `git fsck --unreachable` using all the refs available in refs/ ... and prunes all unpacked objects unreachable from any of these head objects" ([git-prune](https://raw.githubusercontent.com/git/git/master/Documentation/git-prune.adoc)), implemented as `mark_reachable_objects(...)` in [reachable.c](https://raw.githubusercontent.com/git/git/master/reachable.c). Crash safety is bought with time, not bookkeeping: "`--prune=now` ... increases the risk of corruption if another process is writing to the repository concurrently" ([git-gc](https://git-scm.com/docs/git-gc)); cruft packs keep unreachable objects with a side `.mtimes` file so per-object ages survive packing ([gitformat-pack — cruft packs](https://git-scm.com/docs/gitformat-pack#_cruft_packs)). The working tree is an ordinary plain-file materialization of HEAD; only `.git/objects` is content-addressed.
- **restic.** "The data from each file is split into variable length Blobs cut at offsets defined by a sliding window of 64 bytes. The implementation uses Rabin Fingerprints for implementing this Content Defined Chunking (CDC). An irreducible polynomial is selected at random and saved in the file `config` when a repository is initialized, so that watermark attacks are much harder." and "Files smaller than 512 KiB are not split, Blobs are of 512 KiB to 8 MiB in size. The implementation aims for 1 MiB Blob size on average." ([restic References — Backups and Deduplication](https://restic.readthedocs.io/en/stable/100_references.html#backups-and-deduplication)); source constants `windowSize = 64`, `MinSize = 512 * kiB`, `MaxSize = 8 * miB` in [restic/chunker](https://raw.githubusercontent.com/restic/chunker/master/chunker.go). The index is a JSON object listing packs and, per blob, `id/type/offset/length` ([restic References](https://restic.readthedocs.io/en/stable/100_references.html#index-id)). `forget` only removes snapshots — "the data that was referenced by files in this snapshot is still stored in the repository. To cleanup unreferenced data, the prune command must [be run]" — and `prune` works by "(1) All snapshots and directories within snapshots are scanned to determine which data is still in use ... (4) prune will actually perform the repack, modify the index according to the changes and delete the obsolete files" ([restic Removing backup snapshots](https://restic.readthedocs.io/en/stable/060_forget.html)). Prune refuses to run on an inconsistent view (`ErrIndexIncomplete = errors.Fatal("index is not complete")`, `ErrPacksMissing`, `ErrSizeNotMatching` in [internal/repository/prune.go](https://raw.githubusercontent.com/restic/restic/master/internal/repository/prune.go)); the finer crash-ordering guarantees are `UNVERIFIED`.
- **borgbackup.** "The buzhash chunker triggers (chunks) when the last HASH_MASK_BITS bits of the hash are zero, producing chunks with a target size of 2^HASH_MASK_BITS bytes"; "Buzhash is only used for cutting the chunks ... the buzhash value is not used as the deduplication criteria (we use a cryptographically strong hash/MAC over the chunk contents for this, the id_hash)" ([borg internals — The buzhash chunker](https://borgbackup.readthedocs.io/en/stable/internals/data-structures.html#the-buzhash-chunker)). Constants at tag 1.4.5: `CHUNK_MIN_EXP = 19` (512 KiB), `CHUNK_MAX_EXP = 23` (8 MiB), `HASH_WINDOW_SIZE = 0xfff`, `HASH_MASK_BITS = 21` ("Results in ~2 MiB chunks statistically"), `CHUNKER_PARAMS = (CH_BUZHASH, 19, 23, 21, 4095)`, `DEFAULT_MAX_SEGMENT_SIZE = 500 * 1024 * 1024` ([src/borg/constants.py @1.4.5](https://github.com/borgbackup/borg/blob/1.4.5/src/borg/constants.py)). The repo is a log-structured KV store: entries carry `TAG_PUT=0`, `TAG_DELETE=1`, `TAG_COMMIT=2`, and "A COMMIT is always the final log entry in a segment and marks all data from the beginning of the log until the segment ending with the COMMIT as committed and consistent. The segment number of a segment ending with a COMMIT is called the transaction ID"; on open, "if it is not [committed], then all segments after the last committed segment are deleted" ([src/borg/repository.py @1.4.5](https://github.com/borgbackup/borg/blob/1.4.5/src/borg/repository.py)). Space is reclaimed only by compaction, itself transacted: "Since writing a DELETE tag does not actually delete any data and thus does not free disk space any log-based data store will need a compaction strategy", and compaction "never modifies existing segments" ([borg internals — Compaction](https://borgbackup.readthedocs.io/en/stable/internals/data-structures.html#compaction)); `borg compact` has `--threshold` default 10% ([borg compact](https://borgbackup.readthedocs.io/en/stable/usage/compact.html)). Archival storage holds no plain files; `borg check` was not fetched, so any claim about what it verifies is `UNVERIFIED`.
- **casync.** Buzhash rolling hash over a 48-byte window: `#define CA_CHUNKER_WINDOW_SIZE 48`, cutting when `h(i) mod d(avg) == d(avg) - 1`, with the header noting the discriminator formula "only yields correct results as long as the minimal chunk size is picked as avg/4, and the maximum chunk size as avg*4" ([src/cachunker.h](https://github.com/systemd/casync/blob/main/src/cachunker.h)). No refcount or mark-and-sweep is documented in the fetched sources; reflink/seed re-materialization is commonly associated with casync but the string "reflink" did not appear in the fetched README (`UNVERIFIED`).
- **IPFS / UnixFS.** kubo's `ipfs add --chunker` help: "The default is a fixed block size of 256 * 1024 bytes, 'size-262144'. Alternatively, you can use the Buzhash or Rabin fingerprint chunker for content defined chunking by specifying buzhash or rabin-[min]-[avg]-[max]" and, importantly for stability, "Only the fixed-size chunker ('size-N') guarantees that the same data will always produce the same CID. The rabin and buzhash chunkers may change their internal parameters in a future release." ([core/commands/add.go](https://github.com/ipfs/kubo/blob/master/core/commands/add.go)). Crash-safety details of the sweep are `UNVERIFIED`.
- **Venti (Plan 9).** Blocks are SHA-1-addressed and write-once: "The data to be stored is split into fixed-size blocks and written to the server, producing a list of scores. The resulting list of scores is split into fixed-size pointer blocks (using only an integral number of scores per block) and written to the server ... Each file stored this way is summarized by a VtEntry structure recording the top-most score, the depth of the tree, the data block size, and the pointer block size." ([venti(6)](https://9p.io/magic/man2html/6/venti)). Block size is 8 KiB throughout the performance discussion ([Venti paper](https://9p.io/sys/doc/venti/venti.html)). The index is a disk-resident hash table of fixed-size buckets, one bucket per disk block, with overflow into adjacent buckets, and both index and bloom filter "can be rebuilt if lost or damaged" from the append-only log ([Venti paper §5](https://9p.io/sys/doc/venti/venti.html), [venti(8)](https://9p.io/magic/man2html/8/venti)). Reclamation is explicitly refused: "once it is decided that the data is worth keeping, the resources needed to store the data have been consumed and cannot be reclaimed. This eliminates the task of periodically 'cleaning up'..."; "data is never deleted from Venti and thus a stale handle will never be encountered" ([Venti paper](https://9p.io/sys/doc/venti/venti.html)). Fossil adds a mutable plain-file layer in front: "/active is the root of a conventional file system whose blocks are stored in a disk file ... The snapshots in /snapshot are ephemeral: eventually they are deleted to reclaim the disk space they occupy. Long-lasting snapshots stored on a Venti server are kept in /archive" ([fossil(4)](https://9p.io/magic/man2html/4/fossil)). The Fossil paper at `9p.io/sys/doc/fossil/fossil.html` returns HTTP 404 and has no Wayback snapshot, so findings here rest on the man pages and the Venti paper.

## 6. Cross-cutting lessons

### 6.1 Version-ID scheme trade-offs

- **What S3 requires of the ID.** Only: unique per bucket, server-generated, returned in `x-amz-version-id` on writes and in listings, nameable in `?versionId=`, and usable as a pagination cursor (`VersionIdMarker`) [AWS §1.2, §1.6]. AWS's own documented ordering guarantee is storage order, newest first — never ID order. AWS does not document the ID as sortable (and does not document a monotonic-timestamp encoding), but it does require the server to resume a per-key listing at an arbitrary version ID, which is much easier if the ID orders the same way the listing does.
- **UUIDv4 (MinIO).** Fine, and demonstrably sufficient: MinIO orders by `ModTime` in the journal and uses the ID only as a final tiebreaker in `sortsBefore` (MinIO §2.5). Cost: a v4 UUID is random, so any per-key ordering by ID requires a separate sort key (MinIO keeps `ModTime` in the header for exactly this); a GC that wants "delete noncurrent older than N days" must also carry a timestamp. Also note MinIO keeps *two* identities per version — a random `VersionID` (protocol-visible) and an independent random `DataDir` (internal) — so rotating or re-deriving one never disturbs the other.
- **Monotonic counter.** Requires persisted, crash-safe state per bucket or object and gives up on multi-writer concurrency without coordination; MinIO deliberately rejects client-managed allocation ("does not support client-managed version ID allocation"), which rules the client-side counter out for an S3-compatible surface.
- **Timestamp + random (e.g. ULID/UUIDv7-like).** Buys lexicographic ordering consistent with `ListObjectVersions` ordering, makes `VersionIdMarker` a plain range cursor, and makes noncurrent-age GC computable from the ID alone — at the cost of leaking creation time (harmless here) and still needing a random suffix for collision resistance within a millisecond. This is the only scheme among the three where "sort by ID" and "sort by time" are the same thing; MinIO shows that systems which do not need it simply keep a separate `ModTime` (see 2.5). Two shipping S3 servers do choose it: Swift stores a bit-inverted `Timestamp` in the version object's *name* (see 3.2), SeaweedFS stores an inverted-nanosecond hex prefix and says outright that the format changed to "inverted timestamps so newer versions sort first lexicographically" (see 3.4), and B2's fileId embeds the upload time (see 3.5). The price is that the ID becomes load-bearing for on-disk naming, listing order, and age-based expiry at once, so changing it later is a migration rather than a config change; a scheme that keeps ordering in a separate stored field (MinIO) can change the ID format freely.
- **Opaque is a promise you must keep.** If clients may cache version IDs across an upgrade, the ID encoding cannot be reinterpreted later. IPFS's chunker warning is the cautionary tale applied to IDs: "Only the fixed-size chunker ('size-N') guarantees that the same data will always produce the same CID. The rabin and buzhash chunkers may change their internal parameters in a future release." The same reasoning argues for keeping *any* ordering-implying ID scheme stable or treating ordering as a separate stored field.

### 6.2 Refcount vs mark-and-sweep for shared blocks

- **Exactly one system in this survey does what the proposed design needs, and it is the closest analogue available: Garage.** git, restic, and IPFS all reclaim by traversing roots (refs, snapshots, pins) and sweeping the unreachable set; borg reclaims by compacting a log, not by reading counts; casync documents no reclamation at all; Venti refuses reclamation by design. Garage instead keeps a `block_refs` table whose entries are `BlockRef { block: Hash, version: Uuid, deleted: Bool }` (see 3.3), so the reference count of a shared block *is* the set of version UUIDs pointing at it — and it deletes a block only after the count reaches zero, with an explicit safety delay: "blocks never get deleted in a 10 minute interval following the time when the RC reaches zero" ([Garage internals @v2.4.1](https://github.com/deuxfleurs-org/garage/blob/v2.4.1/doc/book/design/internals.md)). Two design details are worth copying: the count is derived from *rows in a table*, not an integer that must be incremented atomically with the reference, and the decrement path ends in a tombstone (`deleted: Bool`) rather than an immediate free. Garage also ships first-class repair tooling for the drift this model inevitably accumulates (`garage repair block-rc`, `garage repair block-refs`, `garage repair versions`, `garage repair scrub`, [durability-repairs.md @v2.4.1](https://github.com/deuxfleurs-org/garage/blob/v2.4.1/doc/book/operations/durability-repairs.md)).
- **Why not a plain integer refcount.** An integer refcount is a second piece of state that must be updated atomically with the reference that owns it; a crash between the two produces either a leak or (worse) a premature free that a later reader observes as corruption. Every system here that had a choice avoided the bare counter. The costs that refcounts *do* buy are O(1) deletion and no full-store scan — which matters for a system that deletes whole versions one at a time, as S3 does, provided the count is derived from durable per-reference rows rather than maintained as a scalar.
- **What makes mark-and-sweep safe.** git's answer is a time-based grace window: "Any object with modification time newer than the --prune date is kept, along with everything reachable from it", with the explicit warning that `--prune=now` "increases the risk of corruption if another process is writing to the repository concurrently" ([git-gc](https://git-scm.com/docs/git-gc)); cruft packs exist so that per-object mtimes survive packing ([gitformat-pack](https://git-scm.com/docs/gitformat-pack#_cruft_packs)). Restic's answer is to refuse to prune unless the index and all packs are mutually consistent ([prune.go](https://raw.githubusercontent.com/restic/restic/master/internal/repository/prune.go)). IPFS's answer is that only pinned roots protect blocks ([repo.go](https://github.com/ipfs/kubo/blob/master/core/commands/repo.go)). Note that Garage's 10-minute deletion delay is the *same* grace-window idea (a write in flight may be about to re-reference the block), applied to a refcount model rather than a sweep — the delay is what makes the count safe against a reader that has already resolved the version list but not yet written its reference.
- **Consequence for a shared-block versioning design.** A mark-and-sweep needs a complete, trustworthy enumeration of live roots (every object's version chain, every bucket, every in-flight upload) and a grace period that exceeds the longest possible write; a refcount needs a durable, transactional update on every reference add/remove, and a repair path (the analogue of `git fsck`) for the inevitable drift. The prior art's answer is neither pole but a specific mix: derive references from enumerable per-reference rows (Garage's `block_refs`), delete only on a zero count *and* after a grace delay, keep a tombstone that makes the state observable before the free, and ship a repair command that recomputes the true reachable set and reconciles — borg's compaction and restic's prune are both "recompute, then rewrite", and MinIO's free-version tombstones (see 2.4) are an explicit "this content is pending asynchronous deletion, do not account for it" marker, which is what a crash-safe cross-reference design looks like when the deletion cannot be done in one atomic step.

### 6.3 Crash-consistency protocols for "move the current version aside, then publish the new version"

- **Filesystem rename is the primitive everyone builds on.** "If newpath already exists, it will be atomically replaced, so that there is no point at which another process attempting to access newpath will find it missing." ([rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html)). But rename is only atomic for a *single* path; a version publish touches at least two (the data, and the metadata that makes it visible), so every system needs an ordering rule plus a recovery action.
- **MinIO: write-then-rename, with a rollback copy.** Stage under a temp bucket, `RenameData`, preserve the pre-existing `xl.meta` as `<oldDataDir>/xl.meta.bkp` before committing the new metadata, and roll back by renaming the backup into place (`UndoWrite`) (MinIO §2.3). Note the direction of the backup: the *old* metadata is preserved inside the *old* data directory, so the rollback path never needs the new version's data to be intact.
- **borg: append a commit record, and truncate on open.** All mutations are appended to a segmented log; a transaction is whatever follows the last `TAG_COMMIT`, and an uncommitted tail is deleted on the next open (borg §4.2). This is the log-structured alternative to rename: never overwrite, always append, and make the commit point a single record.
- **restic / git: publish the new root last, and never mutate the old one.** Restic writes new packs and a new index, then the snapshot that references them; prune then repacks and only afterwards deletes obsolete files, refusing to run when the index and packs disagree. Git publishes refs by rename and keeps unreachable objects for a grace period rather than deleting in the publish path.
- **The shape that applies here.** All four reduce to: (1) make the new content durable under a private name, (2) keep the old materialized copy intact and reachable until the new one is durable, (3) flip a single atomic commit point (rename of a metadata file, or a commit record), (4) have a recovery action for a crash before the commit point (delete the private copy / truncate the log tail / restore the backup), and (5) only then garbage-collect what the old version owned. MinIO's `xl.meta.bkp` is a working example of step 4 for a rename-based store; borg's "delete all segments after the last committed segment" is the same step for a log-based store. SeaweedFS shows the cost of a fifth variant worth avoiding if possible: when the commit point is a *separate, denormalized pointer* (the cached latest-version xattrs on its `.versions` directory entry) rather than the data itself, the system has to ship a background reconciler whose only job is to detect and heal a stranded pointer ([s3api_versioning_reconciler.go](https://github.com/seaweedfs/seaweedfs/blob/master/weed/s3api/s3api_versioning_reconciler.go)). Keeping the commit point and the data in one atomically-renamed artifact — as MinIO does with `xl.meta`, and as the proposed design's version record would — removes that class of drift entirely.

### 6.4 Does anyone keep the current version as a plain file while storing history content-addressed?

I found no S3-compatible server that does this, and no object store that does it in the way proposed (current version = plain file at the key path; superseded versions = content-addressed blocks). The two halves exist separately, and each system that has one is missing the other. Garage content-addresses all object data and dedups it, but exposes no S3 versioning, and its "current" version is simply the newest row in the version table — there is no materialized file at the key path to read ([Garage features @v2.4.1](https://github.com/deuxfleurs-org/garage/blob/v2.4.1/doc/book/reference-manual/features.md), see 3.3). SeaweedFS exposes full S3 versioning and materializes a `null`/current object as a real file at the key path, but stores each superseded version as a whole separate file in a `.versions/` directory with no content addressing at all ([SeaweedFS S3 versioning wiki](https://github.com/seaweedfs/seaweedfs/wiki/S3-Object-Versioning), see 3.4). MinIO keeps *every* version — including the current one — inside a single `xl.meta` journal plus per-version data directories, so nothing is materialized as "the object file" (see 2.1). Ceph RGW encodes the version id into the physical object name and keeps the current-version pointer in a bucket-index OLH record, again with no CAS (see 3.1). The closest published analogues outside S3 are *filesystem* tools, and they split into two shapes:

- **Materialized view over a CAS repository.** git: the working tree is plain files, `.git/objects` (+ packs) is content-addressed, and a checkout is a copy/hardlink of the tree. OSTree is explicit about the dedup benefit: "At its core is a git-like content-addressed object store with branches (or 'refs') to track meaningful filesystem trees within the store ... Each deployment is primarily composed of a set of hardlinks into the repository. This means each version is deduplicated; an upgrade process only costs disk space proportional to the new files" ([OSTree introduction](https://ostreedev.github.io/ostree/introduction/)). Note what these systems do *not* have: a mutable "current" object that is edited in place — the CAS side is append-only and the materialized side is disposable, which is the inverse of the S3 requirement that a superseded version must remain addressable by ID.
- **Mutable active tree plus an archival CAS behind it.** Fossil is the exact analogue of the proposed topology: "/active is the root of a conventional file system whose blocks are stored in a disk file ... Long-lasting snapshots stored on a Venti server are kept in /archive" ([fossil(4)](https://9p.io/magic/man2html/4/fossil)). The difference from S3 versioning is the trigger: Fossil snapshots on a schedule/CLI command into a *new* archive tree, whereas S3 must make every overwrite produce a new addressable version. Venti itself supplies the dedup half of the story and refuses the GC half (Venti §4.2).
- **One relevant negative result.** In every system surveyed, "the current version is the plain one" and "history is content-addressed" are implemented by making the *whole* store CAS-first and the plain file a derived artifact (git/OSTree), or by keeping two stores with a manual snapshot boundary (Fossil). None implements the per-object "demote the previous plain file into the CAS on overwrite" transition, which is the specific write path the proposed design needs; I have no prior-art citation for that transition, only for its two endpoints.
