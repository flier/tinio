**Direct answer.** AWS's Object Lock is a per-bucket opt-in that is irreversible: enabling it forces versioning on and forbids ever suspending versioning. Protection is per **object version**, never per key: a version carries a retention (GOVERNANCE or COMPLIANCE, with a fixed retain-until date) and/or a legal hold (ON/OFF, no expiry). A permanent delete (a request naming a `versionId`) of a protected version is `403 AccessDenied`; a simple delete is still allowed and writes a delete marker, which is not WORM-protected. COMPLIANCE cannot be shortened or removed by anyone; GOVERNANCE can be bypassed by a caller holding `s3:BypassGovernanceRetention` who also sends `x-amz-bypass-governance-retention: true`. A bucket may carry one default-retention rule; an explicit per-object retention overrides it. MinIO implements the same model with two recorded deviations that matter here — it refuses to enable Object Lock on an existing bucket (`InvalidBucketState`) and answers a protected delete with `400 InvalidRequest` — and RustFS implements it with a storage-level model separated from the wire DTO, fail-closed metadata, and the same effective-lock-at-multipart-create rule. tinio follows AWS's wire, not either deviation.

## 1. AWS API surface

### 1.1 The six operations

| Operation | Wire | Request body | Success |
|---|---|---|---|
| `GetObjectLockConfiguration` | `GET /{bucket}?object-lock` | none | `200` with `ObjectLockConfiguration` |
| `PutObjectLockConfiguration` | `PUT /{bucket}?object-lock` | `ObjectLockConfiguration` | `200`, empty body |
| `GetObjectRetention` | `GET /{bucket}/{key+}?retention&versionId=` | none | `200` with `Retention` |
| `PutObjectRetention` | `PUT /{bucket}/{key+}?retention&versionId=` | `Retention` | `200`, empty body |
| `GetObjectLegalHold` | `GET /{bucket}/{key+}?legal-hold&versionId=` | none | `200` with `LegalHold` |
| `PutObjectLegalHold` | `PUT /{bucket}/{key+}?legal-hold&versionId=` | `LegalHold` | `200`, empty body |

All six are generated by `s3s` 0.17 (`src/access/generated.rs:463-480`, `:802-819`; `src/s3_trait.rs:3889-3955`, `:7103-7154`), with the DTOs and XML codecs (`src/dto/generated.rs:21820-22051`, `:21891-21988`; `src/xml/generated.rs:107-112`, `:3784-3906`). The request headers `x-amz-bucket-object-lock-enabled`, `x-amz-bucket-object-lock-token`, `x-amz-bypass-governance-retention`, `x-amz-object-lock-mode`, `x-amz-object-lock-retain-until-date` and `x-amz-object-lock-legal-hold` are all defined (`src/header/generated.rs:68-74`, `:275-279`).

### 1.2 `ObjectLockConfiguration`

- Root `ObjectLockConfiguration`; optional `ObjectLockEnabled` (valid values: `Enabled`) and optional `Rule`. `Rule` carries one `DefaultRetention` (`src/dto/generated.rs:21820-22051`).
- `DefaultRetention`: `Mode` (`GOVERNANCE` | `COMPLIANCE`), and exactly one of `Days` or `Years`. "The `DefaultRetention` settings require both a mode and a period. The `DefaultRetention` period can be either `Days` or `Years` but you must select one. You cannot specify `Days` and `Years` at the same time." ([PutObjectLockConfiguration](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObjectLockConfiguration.html)) — direct.
- `PutObjectLockConfiguration`'s request syntax also carries `x-amz-bucket-object-lock-token`, `Content-MD5` and `x-amz-sdk-checksum-algorithm` (same page) — direct. The token is "a token to allow Object Lock to be enabled for an existing bucket" — direct; AWS Support issues it.
- `GetObjectLockConfiguration`'s response is the same shape; a bucket with no configuration answers `ObjectLockConfigurationNotFoundError` (**404**, confirmed on AWS's status-grouped error list; §7).

### 1.3 Per-version retention and legal hold

- `PutObjectRetention` request: `PUT /{Key+}?retention&versionId=` with `x-amz-bypass-governance-retention`, `Content-MD5` / `x-amz-sdk-checksum-algorithm`; body `Retention { Mode, RetainUntilDate }` (the current page also shows `EventHold` / `EventHoldDuration`, which `s3s` 0.17's DTO does **not** model) ([PutObjectRetention](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObjectRetention.html)) — direct.
- `GetObjectRetention` response: `Retention { Mode, RetainUntilDate }` only; `s3s` 0.17's DTO has no variable-retention fields (`src/dto/generated.rs:21983-21988`).
- `PutObjectLegalHold` request: `PUT /{Key+}?legal-hold&versionId=`; body `LegalHold { Status: ON | OFF }` ([PutObjectLegalHold](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObjectLegalHold.html)) — direct. `GetObjectLegalHold` answers `LegalHold { Status }`.
- Object writes carry the same three headers: `PutObject`, `CopyObject` and `CreateMultipartUpload` have `object_lock_legal_hold_status`, `object_lock_mode` and `object_lock_retain_until_date` on their DTOs (`src/dto/generated.rs:27205-27222`, `:3628-3642`, `:6191-6205`), and `s3s` parses them (`src/ops/generated/{put_object,copy_object,create_multipart_upload}.rs`). `PostObjectInput` carries the same three fields (`:23277-23294`), and `S3::post_object` maps the input into `PutObjectInput` (`src/s3_trait.rs:5069-5074`), so the form path reaches the same write handler. `CompleteMultipartUpload` has **no** lock fields (`src/dto/generated.rs:2481`), matching AWS's wire.
- `DeleteObject` and `DeleteObjects` carry `bypass_governance_retention` (`src/dto/generated.rs:8696-8702`, `:8946-8952`); `GetObject` / `HeadObject` echo the three lock headers (`src/dto/generated.rs` output fields; `src/ops/generated/get_object.rs:124-129`, `head_object.rs:119-120`).

### 1.4 Uploads and checksums

"The `Content-MD5` or `x-amz-sdk-checksum-algorithm` header is required for any request to upload an object with a retention period configured using Object Lock." ([Object Lock considerations — uploading](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-managing.html)) — direct. MinIO enforces it on `PutObjectRetention`/`PutObjectLegalHold` (`cmd/object-handlers.go:2934-2942`, `:2781-2784`); RustFS does not (§4.8).

## 2. AWS semantics

### 2.1 Modes

- **COMPLIANCE**: "a protected object version can't be overwritten or deleted by any user, including the root user in your AWS account. When an object is locked in compliance mode, its retention mode can't be changed, and its retention period can't be shortened." ([Locking objects with Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)) — direct. The only way to delete before the date is to delete the account — direct.
- **GOVERNANCE**: users cannot overwrite/delete/alter lock settings "unless they have special permissions"; to override or remove, "you must have the `s3:BypassGovernanceRetention` permission and must explicitly include `x-amz-bypass-governance-retention:true` as a request header" — direct.
- **Legal hold**: independent of retention; "remains in effect until removed"; "can be freely placed and removed by any user who has the `s3:PutObjectLegalHold` permission"; if retention expires the hold still protects; removing the hold does not shorten the retention — direct.
- **Bypass and legal hold**: "Bypassing governance mode doesn't affect an object version's legal hold status." ([Object Lock considerations — bypass](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-managing.html)) — direct.

### 2.2 Deletes and markers

- Permanent DELETE (with a version ID) of a protected version: "Amazon S3 returns an Access Denied (`403 Forbidden`) error" — direct.
- Simple DELETE (no version ID): "Amazon S3 returns a `200 OK` response and inserts a delete marker in the bucket, and that marker becomes the current version of the object with a new ID" — direct.
- "Delete markers are not WORM-protected, regardless of any retention period or legal hold in place on the underlying object." ([Managing delete markers with Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-managing.html)) — direct.

### 2.3 Default retention

- A bucket rule applies "by default to every new object placed in the specified bucket" ([PutObjectLockConfiguration](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObjectLockConfiguration.html)) — direct.
- "When you `PUT` an object version that has an explicit individual retention mode and period in a bucket, the object version's individual Object Lock settings override any bucket property retention settings." ([Configuring S3 Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-configure.html)) — direct.
- A default rule requires Object Lock already enabled — direct. The 100-year cap is stated in the bucket-policy context: "The maximum retention period is 100 years" — direct; MinIO and RustFS both enforce 36,500 days / 100 years (§3.6, §4.6).

### 2.4 Enablement and versioning

- "Before you lock any objects, you must enable S3 Versioning and Object Lock on a general purpose bucket." ([Configuring S3 Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-configure.html)) — direct.
- "After you enable Object Lock on a bucket, you can't disable Object Lock or suspend versioning for that bucket." — direct.
- "You can enable Object Lock for new or existing buckets." ([PutObjectLockConfiguration](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObjectLockConfiguration.html)) — direct; the existing-bucket path is the support-token path (§1.2).
- `CreateBucket` with `x-amz-bucket-object-lock-enabled: true` requires the `s3:PutBucketObjectLockConfiguration` and `s3:PutBucketVersioning` permissions ([CreateBucket](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CreateBucket.html)) — direct.

### 2.5 Lifecycle

- Lifecycle and Object Lock compose; a lifecycle action cannot delete a version under an active retention or legal hold (the lifecycle pages' rule; MinIO and RustFS both implement the skip, §3.7, §4.7). `UNVERIFIED` as a single AWS sentence; the behaviour is stated by both ports and is the only safe reading.

## 3. MinIO

### 3.1 Bucket configuration

- `BucketMetadata` carries `ObjectLockConfigXML`, `ObjectLockConfigUpdatedAt` and the parsed `objectLockConfig` (`cmd/bucket-metadata.go:68-109`), persisted in the per-bucket `.metadata.bin` (`:51`, `:196`, `:519`) under `.minio.sys/buckets/<bucket>/` (`cmd/object-api-utils.go:59`, `cmd/object-api-common.go:40`).
- `CreateBucket` with the lock header forces the versioning config on (`cmd/erasure-server-pool.go:886-895`); `x-amz-bucket-object-lock-enabled` accepts only case-insensitive `true`/`false`, else `ErrInvalidRequest` (`cmd/bucket-handlers.go:734-744`), and requires the object-lock-config and versioning permissions (`:764-780`).
- `PUT ?object-lock` (`cmd/bucket-handlers.go:1785-1856`): parses XML (4 KiB cap), accepts only `Enabled` (`internal/bucket/object/lock/lock.go:275-277`), and **refuses an existing bucket without a config** with `ErrObjectLockConfigurationNotAllowed` → `InvalidBucketState` 409, "Object Lock configuration cannot be enabled on existing buckets" (`cmd/bucket-handlers.go:1826-1834`, `cmd/api-errors.go:948-952`).
- `GET ?object-lock` returns the config or `ObjectLockConfigurationNotFoundError` 404 (`cmd/bucket-handlers.go:1858-1897`, `cmd/api-errors.go:2376-2377`).
- Suspending versioning is refused: `InvalidBucketState` 400, "An Object Lock configuration is present on this bucket, versioning cannot be suspended." (`cmd/bucket-versioning-handler.go:77-84`).

### 3.2 Per-version storage

- Lock state is **per-version user metadata**, not a field: `x-amz-object-lock-mode`, `x-amz-object-lock-retain-until-date`, `x-amz-object-lock-legal-hold`, plus internal LWW timestamps (`cmd/bucket-replication.go:75-78`; readers at `internal/bucket/object/lock/lock.go:473-513`).
- xl.meta splits `MetaUser` (user keys) from `MetaSys` (internal prefix) (`cmd/xl-storage-format-v2.go:1681-1694`, `:634-668`). A delete-marker version has only `MetaSys` and cannot carry retention (`:148-153`, `:468-496`); `PutObjectMetadata` rejects markers with `MethodNotAllowed` (`cmd/erasure-object.go:2209-2211`).

### 3.3 Write path

- `checkPutObjectLockAllowed` (`cmd/bucket-object-lock.go:245-340`) is the shared gate: no config/not enabled + lock headers → `ErrInvalidBucketObjectLockConfiguration`; an explicit existing version (only when a `versionId` is supplied) blocks on unexpired COMPLIANCE or legal hold; legal hold and retention require their permissions; with no explicit retention and a bucket default, the default applies `now + Validity` (`:322-338`).
- **Deviation**: the default is suppressed when a legal-hold header is present (`:333`, condition `!legalHoldRequested && retentionCfg.LockEnabled`). AWS treats the two as independent; the design rejects the suppression.
- `PutObject` (`cmd/object-handlers.go:2032-2048`), `CopyObject` (`:1583-1630`) and `NewMultipartUpload` (`cmd/object-multipart-handlers.go:163-179`) apply the gate. Copy explicitly strips the source's lock metadata (`:1584`).
- `CompleteMultipartUpload` rejects any lock or bypass header with `InvalidRequest` ("CompleteMultipartUpload spec does not use these headers") (`cmd/object-multipart-handlers.go:968-978`).
- A write with a retention requires `Content-MD5`/checksum (`cmd/object-handlers.go:2934-2942`, `:2781-2784`).

### 3.4 Delete path

- Simple DELETE creates a marker with no lock check (`cmd/object-handlers.go:2652-2666`; `cmd/erasure-object.go:1686-1706`).
- Version delete installs an `EvalRetentionBypassFn` (`cmd/object-api-interface.go:45-46`, `:138`) and calls `enforceRetentionBypassForDelete` (`cmd/erasure-object.go:2007-2011`, `cmd/bucket-object-lock.go:84-159`): legal hold first (`:99-102`), then COMPLIANCE (no bypass, `:107-123`), then GOVERNANCE (`:138-155`, requiring the header and the permission). A protected version returns `ObjectLocked` → `ErrObjectLocked` = **400 `InvalidRequest`**, "Object is WORM protected and cannot be overwritten" (`cmd/api-errors.go:1073-1077`, `:2326-2327`); a missing bypass permission is `AccessDenied` 403.
- Bulk delete pre-checks each entry that names a version and turns the refusal into a per-key `DeleteError` (`cmd/bucket-handlers.go:481-490`, `:535-540`, `:569-580`).
- Lifecycle's evaluator skips locked versions (`NoneAction`), and `DeleteAllVersions` / `DelMarkerExpiration` are refused on a lock-enabled bucket (`internal/bucket/lifecycle/evaluator.go:70-131`; `cmd/data-scanner.go:1164-1197`). Force-delete is refused on a lock bucket (`cmd/object-handlers.go:2614-2620`; `cmd/bucket-handlers.go:1698-1732`).

### 3.5 Retention modification

- `PutObjectRetention` (`cmd/object-handlers.go:2908-3013`): authenticated, no deferred authorization; `Content-MD5`/checksum required; bucket lock required; parses the body; `enforceRetentionBypassForPut` (`:2969-2972`) then writes or clears the mode/date (empty body clears both).
- The rule (`cmd/bucket-object-lock.go:167-233`): expired → unconstrained; GOVERNANCE without bypass → new mode must be GOVERNANCE and the date must not move earlier (`:194-204`); COMPLIANCE → mode must stay COMPLIANCE and the date must not move earlier, bypass deliberately passed `false` (`:209-221`); no existing retention → permission only (`:224-232`). A past date is rejected before the rule (`internal/bucket/object/lock/lock.go:403-405`).
- `GetObjectRetention` returns the stored mode/date or `ErrNoSuchObjectLockConfiguration`; MinIO maps that to **400** (`cmd/api-errors.go:1068-1072`) — an AWS deviation (see §6).

### 3.6 Defaults and limits

- `DefaultRetention` validation: mode GOVERNANCE/COMPLIANCE, exactly one of Days/Years, days `1..=36500`, years `1..=100` (`internal/bucket/object/lock/lock.go:187-228`, `:180-185`).
- `Config.ToRetention` computes `Validity` with `now.AddDate(...)` (`:283-307`); the default applies at write (`cmd/bucket-object-lock.go:322-338`).

### 3.7 Tests

- The lock package's unit matrix (`internal/bucket/object/lock/lock_test.go:88-610`): mode/legal-hold parsing, default-retention bounds, only-`Enabled`, past dates, header pairs, metadata filtering.
- Lifecycle's lock refusal (`internal/bucket/lifecycle/lifecycle_test.go:66-104`); the scanner's protected-version case (`cmd/data-scanner_test.go:179-183`, `:223-231`) and the lock-bucket `NoneAction` (`:313-407`).
- No HTTP-level tests for the six handlers in this revision (`cmd/bucket-handlers_test.go:680` is a plain `ObjectOptions{}` with a comment).

### 3.8 The `mc` command surface (the CLI's reference)

- `mc retention` has three subcommands, **not four**: `set`, `clear`, `info` — there is no `get` or `show` (`cmd/retention-main.go:24-38`).
  - `mc retention set [--bypass] [--default] [--recursive] [--rewind] [--versions] [--version-id] MODE VALIDITY TARGET` (`cmd/retention-set.go:59-93`). `MODE` is `governance`/`compliance` (upper-cased at `:102`); `VALIDITY` is only `Nd`/`Ny` (`cmd/retention-common.go:152-177`), never an absolute date; retain-until is `UTCNow() + validity` (`:112-125`). `--default` writes the bucket config and is mutually exclusive with the object-scoped flags (`cmd/retention-set.go:123-125`).
  - `mc retention info` (`cmd/retention-info.go:57-90`), `mc retention clear` (`cmd/retention-clear.go:53-88`; clear always passes `bypassGovernance=true`, `:118`).
- `mc legalhold` has the same three verbs (`cmd/legalhold-main.go:34-47`); **no positional ON/OFF**: `set` hard-codes `LegalHoldEnabled` (`cmd/legalhold-set.go:220`), `clear` hard-codes `LegalHoldDisabled` (`cmd/legalhold-clear.go:103`). Flags are `--recursive`, `--version-id`, `--rewind`, `--versions`.
- Enabling Object Lock at creation is `mc mb --with-lock` (`cmd/mb-main.go:30-48`, `:132`, `:148`); there is **no `mc object-lock` command** and no `mc admin` object-lock command. `mc retention set --default MODE VALIDITY ALIAS` enables locking on an existing bucket (docs since `RELEASE.2025-05-20T20-30-00Z`).
- `--json` is a global flag; the shapes are `{mode, until, urlpath, versionID, status, error}` for retention info, `{op, enabled, mode, validity}` for the bucket config, and `{legalhold, urlpath, key, versionID}` for legal hold (`cmd/retention-info.go:118-125`, `cmd/retention-common.go:83-90`, `cmd/legalhold-info.go:87-94`). `validity` in the bucket message is `30DAYS`/`3YEARS`, not `30d`.
- **Not exposed by `mc`**: absolute/date validity, event holds, `retention get`/`legalhold get`, bucket-level legal hold, `--bypass` on `retention clear` or on legal hold, and retention on delete markers (`cmd/retention-common.go:222-225`).
- tinio adopts the command names, `--default`, the `Nd`/`Ny` validity and the legal-hold `set`/`clear` semantics; it adds `tinio object-lock enable` for the no-default case `mc` cannot express without `mb --with-lock`, drops the alias layer, and omits `--recursive`/`--versions`/`--rewind` in v1 (OL24).

## 4. RustFS

### 4.1 Layers

- `s3s` DTOs in the serving crate; the storage model lives in `crates/ecstore/src/bucket/object_lock/` (`types.rs`, `objectlock.rs`, `objectlock_sys.rs`); the persisted bucket metadata owns the config DTO until the s3s ratchet migration (backlog #1842); the serving layer converts at its boundary (`crates/ecstore/src/bucket/object_lock/types.rs:15-21`).
- Per-version metadata lives in `MetaObject.meta_user` in xl.meta (`crates/filemeta/src/filemeta/version.rs:1456-1495`); the key literals are pinned as an on-disk format (`crates/filemeta/src/metadata_keys.rs:15-49`, `:51-257`).

### 4.2 Bucket configuration and fail-closed state

- `BucketMetadata` carries the raw XML, its timestamp, the parsed config and a sticky `lock_enabled` (`crates/ecstore/src/bucket/metadata.rs:434-506`). `object_locking()` is `lock_enabled || parsed.enabled` (`:626-628`); `object_lock_checks_required()` is true when the stored XML is unreadable, so a corrupt config cannot fail open (`:630-635`). Enabling sets `lock_enabled = true` and never clears it on empty data (`:1003-1015`).
- `ObjectLockConfigState::{Configured, ConfirmedAbsent, Fabricated}` and the authoritative reader (`crates/ecstore/src/bucket/metadata_sys.rs:139-179`): unreadable XML is an error; a legacy `lock_enabled` synthesizes `{Enabled, rule: None}`; absent is `ConfirmedAbsent`. Validation is exactly enabled + one default with mode + days `1..=36500` or years `1..=100` (`:235-258`).
- `GET ?object-lock` maps `ConfigNotFound` to `ObjectLockConfigurationNotFoundError` 404 (`rustfs/src/storage/ecfs.rs:1060-1104`).
- `PUT ?object-lock` (`rustfs/src/storage/ecfs.rs:1679-1784`): only `Enabled`; a rule must carry a valid default (`:445-507`); if no config exists yet, versioning must already be enabled, else `InvalidBucketState` "Object Lock configuration cannot be enabled on existing buckets" (`:1704-1713`); it then persists and auto-enables versioning (`:1724-1750`) — a two-commit sequence with a recorded gap (§4.8).
- `CreateBucket` force-enables versioning with the lock (`crates/ecstore/src/store/bucket.rs:992-1005`); the header requires the config and versioning permissions (`rustfs/src/storage/access.rs:2269-2281`). Versioning suspension is refused with `InvalidBucketState` (`rustfs/src/app/bucket_usecase.rs:880-911`).

### 4.3 Write path

- The shared builder requires mode and date together (`rustfs/src/app/object/shared.rs:815-852`; message "x-amz-object-lock-retain-until-date and x-amz-object-lock-mode must both be supplied"), requires the bucket enabled (`:840`), and converts to eval metadata.
- Copy removes inherited lock metadata then applies the destination's explicit/default lock (`rustfs/src/app/object/copy.rs:660-676`).
- `CreateMultipartUpload` resolves and stores the **effective** lock at create; a default is fixed at create, not completion (`rustfs/src/app/multipart_usecase.rs:1015-1033`; e2e `crates/e2e_test/src/object_lock/object_lock_test.rs:2073-2137`).
- `CompleteMultipartUpload` rejects lock/bypass headers (`rustfs/src/app/multipart_usecase.rs:290-293`, `:653-658`).
- An overwrite pre-check allows a new version but blocks legal hold and unexpired COMPLIANCE (`rustfs/src/app/object/shared.rs:858-906`), re-checked under the commit lock for explicit-version puts (`crates/ecstore/src/set_disk/ops/object.rs:4845-4869`).

### 4.4 Delete path

- The central gate is `check_object_lock_delete` (`crates/ecstore/src/set_disk/mod.rs:6466-6506`): skip meta buckets and marker creation; otherwise legal hold, COMPLIANCE, then GOVERNANCE + bypass (`crates/ecstore/src/bucket/object_lock/objectlock_sys.rs:286-306`). A block is `StorageError::PrefixAccessDenied` → S3 `AccessDenied` 403 (`rustfs/src/error.rs:789`), enriched with a reason on a single delete (`rustfs/src/app/object/delete.rs:1205-1215`).
- Simple DELETE creates a marker and skips the gate (`crates/ecstore/src/set_disk/mod.rs:6481-6483`); bulk delete checks each entry and reports per-key (`rustfs/src/app/object/delete.rs:488-507`, `:527-646`).
- Lifecycle skips locked versions and re-checks with a fresh config (`crates/lifecycle/src/evaluator.rs:92-127`, `crates/ecstore/src/bucket/lifecycle/bucket_lifecycle_ops.rs:3993-4040`).
- Force bucket delete is forbidden on a lock bucket (`crates/ecstore/src/store/bucket.rs:1472-1490`); a normal delete requires an empty bucket.

### 4.5 Retention modification

- `check_retention_for_modification` (`crates/ecstore/src/bucket/object_lock/objectlock_sys.rs:69-121`): an inactive retention is unconstrained; COMPLIANCE cannot be shortened/cleared/mode-changed even with bypass, extension is allowed; GOVERNANCE can extend freely and shorten/clear/mode-change only with bypass.
- `PutObjectRetention` gates early against the current object and re-checks inside the storage commit (`rustfs/src/storage/ecfs.rs:1826-1845`; `crates/ecstore/src/set_disk/mod.rs:6403-6420`). It writes the internal LWW timestamp (`rustfs/src/storage/ecfs_extend.rs:437-441`).
- The storage-level `RetentionMode::parse_exact` exists so a differently-spelled requested mode cannot normalize into a match (`crates/ecstore/src/bucket/object_lock/types.rs:53-64`).

### 4.6 Defaults and clock

- The default is applied at write: `now + Days`, or `add_years(now, Years)` with Feb-29 → Feb-28 (`rustfs/src/storage/ecfs_extend.rs:89-136`; `crates/ecstore/src/bucket/object_lock/objectlock_sys.rs:123-131`).
- The default is enforced even when the per-version keys are absent, by computing from `obj_info.mod_time` (`objectlock_sys.rs:350-366`); lifecycle has a parallel implementation (`crates/lifecycle/src/object_lock.rs:67-85`). An expired explicit retention does **not** fall back to the default (`crates/lifecycle/src/object_lock.rs:229-245`).
- Ranges: `1..=36,500` days, `1..=100` years, mutually exclusive (`rustfs/src/storage/ecfs.rs:445-507`).

### 4.7 Legal hold

- ON/OFF, independent, never bypassable; a malformed persisted status fails closed (`crates/ecstore/src/bucket/object_lock/objectlock_sys.rs:211-231`, `:291-297`, `:317-326`). `GetObjectLegalHold` defaults to OFF when the key is absent (`rustfs/src/storage/ecfs.rs:1035-1050`).

### 4.8 Recorded gaps and deviations

- **Content-MD5 is not enforced** for Object Lock requests; the MinIO-derived error constants are dead (`crates/ecstore/src/bucket/object_lock/objectlock.rs:20-28`).
- **`PutObjectRetention` accepts partial mode/date pairs**, persisting the missing half as empty; the delete gate then fails closed on the incomplete pair (`rustfs/src/storage/ecfs_extend.rs:409-436`; `crates/ecstore/src/bucket/object_lock/objectlock_sys.rs:338-348`).
- **`GetObjectRetention` never returns `NoSuchObjectLockConfiguration`**; an unlocked object gets an empty retention (`rustfs/src/storage/ecfs.rs:1139-1141`).
- **`GetObject` does not emit lock headers; `HeadObject` does** (`rustfs/src/app/object/head.rs:579-602`; no injection in `get.rs`).
- **Two-commit config update**: the lock config is written, then versioning separately (`rustfs/src/storage/ecfs.rs:1724-1750`).
- **Two parallel "is locked" implementations**: the ecstore helper is test-only, lifecycle has its own (`objectlock_sys.rs:210-231` vs `crates/lifecycle/src/object_lock.rs:21-44`).
- **Conservative lifecycle**: `DeleteAllVersions` is skipped whenever any lock config exists, even without a default rule (`crates/lifecycle/src/evaluator.rs:92-121`).

## 6. What the design adopts and rejects

- **Adopted from AWS**: the two modes and the exact bypass rule; legal-hold independence and its no-bypass rule; the marker rule; the 403 on a protected permanent delete; the default-overridden-by-explicit rule; the six wires and the checksum requirement.
- **Adopted from MinIO**: the effective-lock resolution at multipart create; the CompleteMultipartUpload header rejection; the lifecycle skip; the governance permission gate's shape.
- **Adopted from RustFS**: the storage-level model separated from the serving DTO; the enabled-bit-outlives-the-rule fail-closed shape; the malformed-metadata fail-closed rule; the Feb-29 fallback for `Years`; the default fixed at multipart create.
- **Rejected on evidence**: MinIO's creation-only enablement (AWS supports existing buckets, OL14); MinIO's 400 on a protected delete and on a missing per-object config (AWS's 403/404, OL17); MinIO's legal-hold suppression of the default (AWS independence, OL10); RustFS's partial retention pairs (OL10); RustFS's empty `GetObjectRetention` and `GetObject` header gap (OL17/OL18); RustFS's two-commit config update (OL13's one-step create; the update path writes one row); replication-specific bypasses (tinio has no replication). The edge-case pass added the marker choices (405 explicit / 404 `NoSuchKey` latest), the past-date `InvalidRequest` call (MinIO `MalformedXML`, RustFS `InvalidArgument`, AWS undocumented), the partial-pair rejection (MinIO rejects; RustFS accepts but fails closed on the delete), and the `mc` clear/set behaviours (OL9, OL17, OL24).

## 7. Confirmed statuses and remaining unknowns

The fact-check read AWS's current status-grouped error list (`https://docs.aws.amazon.com/AmazonS3/latest/userguide/ErrorCodeBilling.html`; the old `ErrorResponses.html` now redirects) and the AWS code-library examples for the three read operations:

- **`NoSuchObjectLockConfiguration` is 404 Not Found** — "The specified object does not have an ObjectLock configuration." AWS's `GetObjectRetention` and `GetObjectLegalHold` examples handle it; the API pages themselves have no Errors section.
- **`ObjectLockConfigurationNotFoundError` is 404 Not Found** — "The Object Lock configuration does not exist for this bucket." The `GetObjectLockConfiguration` example handles it.
- **`InvalidBucketState` is 409 Conflict** — "The request is not valid for the current state of the bucket." The API PDF lists it under 409. The exact code AWS returns for (a) enabling on a non-versioned bucket and (b) suspending versioning on a lock bucket is not documented; the design uses `InvalidBucketState` for both.
- **A legal-hold-only write receives the bucket default.** AWS states the default applies to every object version placed in the bucket, a legal hold is independent, and only an explicit individual mode **and period** overrides the default. No sentence pairs "legal hold only" with the default; the general rule is direct and the design follows it.
- **`GetObject` returns all three lock headers.** The response syntax lists `x-amz-object-lock-mode`, `x-amz-object-lock-retain-until-date` and `x-amz-object-lock-legal-hold`, and the userguide says both `HeadObject` and `GetObject` return them.
- **`CompleteMultipartUpload` has no lock or bypass headers**; only `CreateMultipartUpload` carries the lock headers. Confirmed by the absence from its request syntax.
- **The checksum requirement covers default retention.** The sentence is "any request to upload an object with a retention period configured using Object Lock"; there is no default-retention carve-out. A legal hold is not a retention, so the requirement does not attach to a legal-hold-only write that receives no default.
- **A past `RetainUntilDate`'s exact code is still `UNVERIFIED`.** No AWS page names a code for a well-formed past date. The design uses `400 InvalidRequest` as its documented call; MinIO and RustFS reject the date on every path.
