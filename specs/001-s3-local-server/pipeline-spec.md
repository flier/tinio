# Part 1 — Spec (Requirements Specification)

## 1. Background and Goals

After the redb migration (prerequisite spec, landed), the etag recomputation of list/scanner remains inline: entry-by-entry computation, entry-by-entry `set` (one write transaction per entry) — on the list side, `FsListing::list` paginates first over walked keys and only resolves the emitted page via `etag_for_file` + `buffer_unordered(ETAG_CONCURRENCY=16)` (listing.rs); on the scanner side, `reconcile_bucket` does entry-by-entry `ensure_etag` + `BATCH_SIZE=32` yield (scanner.rs). Under redb's single-writer model each commit = one write-lock acquisition + one fsync (`Durability::Immediate`); during a cold scan of a large bucket the write-transaction frequency = entry count N, and recomputation is serially coupled with DB writes on the request/scan path, with no way to throttle or observe them independently.

**Goals**:

1. Split ETag computation (file read + hashing, CPU/IO bound) and batched DB writes (the single-writer serialization point) into **two independent pipelines**, each with its own bounded queue, concurrency, backpressure, and metrics.
2. Reduce write transactions from N to ≈N/batch_size (amortizing fsync and lock contention).
3. Cold-path CPU/IO concurrency controllable and observable, with downgradable thread priority to avoid preempting request threads.
4. Write-lock contention cost observable (lock wait vs total transaction duration distribution), to validate the batching gains and find hotspots.

**Current state deliberately kept by the prerequisite spec** (this phase replaces it): inline recompute + `BATCH_SIZE=32` yield pacing. The hot path (meta hit) has zero write transactions and is unaffected by this phase.

### 1.1 Why not a simpler approach (review rationale)

Rejected alternative: **a semaphore-throttled `spawn_blocking` pool + inline batch-accumulated commit** (limit compute-side concurrency; DB writes accumulated by the producer and then committed directly via `set_batch`). It does capture the single benefit of "batched commit"; it was rejected because:

- **One layer of backpressure missing**: inline commit couples DB write-lock waiting directly into the producer (list request / scanner loop) — when the write lock is held by a long transaction (e.g. compact statistics, a large batch commit), all in-flight list requests block synchronously on `begin_write()`, with no independent throttling and no way to observe the backlog; a dedicated write pipeline confines "waiting for the write lock" to one worker, and producers only wait for bounded-queue slots.
- **One layer of observability missing**: the inline approach has no observable surface for queue depth / in-flight / busy workers, so it cannot answer "is CPU/IO controllable" (acceptance criterion 5).
- **No thread priority possible**: `spawn_blocking` threads are managed globally by tokio and cannot have their priority set; `priority = low` requires tasks to run on their own threads (see §3 thread priority).
- **Generality**: the pipeline contract (`pipeline::Task`/`Runner`) targets "any slow/high-IO operation" and "any batched persistence", not just etag (acceptance criterion 5's stub-task requirement); the inline approach would re-invent throttling for every new scenario.

Cost (explicitly accepted): the server process gains two independent tokio runtimes; tinio-fs's construction surface grows (required pipeline handles, §3 lifecycle); the contract spans three crates.

## 2. Scope

**In scope**: tinio-core pipeline contract + `pipeline::InlineRunner`; tinio-fs task implementations (`EtagComputeTask`/`MetaWriteBatchTask`, async tokio::fs IO) + `meta::Store::set_batch` + gated-load primitives (P2); tinio-server dual-pipeline runtime (independent runtimes + thread priority) + config + metrics; list/scanner integration; write-lock latency histogram; set_batch exploratory benchmark + full-pipeline benchmark.

**Out of scope**: single-entry write paths unchanged (put_object's `meta::Store::set`, multipart operations still call the store directly with short transactions — not via the pipeline); hot path unchanged; compact/cleanup mechanism unchanged (settled by the prerequisite spec).

## 3. Design

### 3.1 Layering

| Layer | Contents |
|---|---|
| tinio-core `pipeline.rs` (new contract, analogous to `Cleanup`) | **`Task` = custom Future** (`#[async_trait]`, the same mechanism as `Cleanup`): `kind()` + `async fn run(&mut self) -> Output` (`Output: Send + 'static`; `&mut self` because a `dyn Task` cannot be taken by value — a by-value `self` is uncallable on `Box<dyn Task>`, E0161; R6: must not panic). **`Runner` = executor** (`Runner<O = RunOutput>`): `enqueue` ≈ spawn, returns `Result<Completion<O>, Error>` — `Err` = not accepted (`Error::ShutDown`, Q3), `Ok` = **`Completion` ≈ JoinHandle**. The Runner creates `(Reply, Completion)` and calls `Reply::send(output)` after `run()`; the pipeline does not interpret the Ok payload. `Error::Dropped` is a unit variant answering a dropped task (panic or queued-drop). **Both pipelines reuse the same contract** |
| tinio-fs (task implementations) | `EtagComputeTask: pipeline::Task` (IO pipeline): **only missing/stale entries are enqueued** (P6: producer-side `entry_matches` gate; hits do not occupy a worker) → async tokio::fs open (nofollow via the blocking pool) → 64 KiB bounded streaming read + incremental MD5 (1 task = 1 worker thread occupied, Q4); **payload carries stored context `Option<database::StoredMeta>` and `follow_symlinks`**; the task reproduces `ensure_etag`'s composed-ETag preservation decision (P1) and opens the file with nofollow (R3); **`Output = Result<(key, etag, identity), tinio_fs::Error>`** (original error, unboxed). `MetaWriteBatchTask: pipeline::Task` (write pipeline): holds a `meta::Store` handle + a batch of entries (**including identity**) → single `set_batch` commit inside `run()`; **data-only, no in-task channel**; **`Output = Result<(), tinio_fs::Error>`**. Completion semantics live on the `Completion` returned by `enqueue`: list awaits, scanner drops (Q3b) |
| tinio-server (runtime) | **`Pipeline<O = RunOutput>`** (the `O: Outcome` bounds live on the impl blocks, not the struct; `Pipelines<IoResult, RemoveResult, DbResult>` owns three independent fields): bounded queue holding `(Box<dyn Task<Output = O>>, Reply<O>)`. **IO pipeline**: capacity 1024 + `[pipeline.io] workers` workers (ETag compute, `etag::Result`); **removal pipeline**: capacity 1024 + `[pipeline.remove] workers` workers (default 1 — delete-bucket tombstone `remove_dir_all`, `Result<(), tinio_fs::Error>`); **DB write pipeline**: capacity 1024 + `[pipeline.db] workers` workers (default 1 — redb single-writer; >1 does not raise write throughput); **one independent tokio runtime per pipeline** (multi_thread, `on_thread_start` sets thread priority); the worker wraps `run()` in `catch_unwind` (R6), logs via `Outcome::failure()` (visible even when the handle is dropped, R8), then `Reply::send`; each has `shutdown()` + `stats()`; constructed at startup and injected into `FsOptions` |

### 3.2 Data Flow (Cold List / Cold Scan)

```
list/scanner (producer, tinio-fs)
  ├─ walk files + **gated load** (new primitive, R1: batched point reads of in-page keys for list / full-bucket scan for scanner, 1 read transaction each) → **in-memory matches gate** (P6: `entry_matches` hits use the stored etag directly, **not enqueued**) → only missing/stale entries enter the IO pipeline (list paginates first over walked keys, **only the emitted page is enqueued**, P3)
  ├─▶ IO pipeline: EtagComputeTask (async tokio::fs IO, concurrency bounded by [pipeline.io] workers, Q4) → `enqueue` returns a Completion, results come back out of order
  ├─ streaming flush into batches (Q5): results accumulate into the current batch as they arrive; enqueue immediately when count ≥ meta_batch_size OR estimated bytes ≥ meta_batch_bytes
  └─▶ write pipeline: MetaWriteBatchTask (single set_batch commit) — list: await Completion final drain (Q2); scanner: drop Completion (enqueue-and-forget, Q3b)
```

- **Separation of duties**: the IO pipeline only does "file read + hash" (CPU/IO bound); the write pipeline only does "batched DB writes" (redb single-writer serialization; independent backpressure prevents the producer from piling up write tasks unboundedly). The two pipelines never block each other.
- **Single-entry direct writes bypass the pipeline**: put_object's `meta::Store::set` (current type name, formerly MetaStore) and multipart operations still call the store directly (short transactions, request path); the write pipeline only carries batched writes.
- **matches gate before enqueue (P6)**: `entry_matches` (size + mtime) is done in memory by the producer; matching entries use the stored etag directly and are **not enqueued** into the IO pipeline (no worker occupied). Tasks no longer reproduce the matches short-circuit.
- **Composed-ETag preservation semantics (P1)**: `ensure_etag`'s decision "touch keeps the composed form, replacement rehashes" (meta.rs; meta-redb-spec §5.5) is reproduced inside the compute task — the task only handles entries the producer has already judged missing/stale: stored is composed + same size + same file identity (fall back to the mtime jitter window when identity is unavailable) → return the original etag, and the write batch only refreshes mtime + identity; otherwise streaming rehash.
- **Task open safety (R3)**: the `EtagComputeTask` payload carries `follow_symlinks`; when false it opens with `open_nofollow_std` (synchronous, already available in fsutil.rs), preserving the symlink-rejection semantics of `FsOptions.follow_symlinks=false` — incidentally fixing the TOCTOU gap in the current `md5_of_file` path (tokio::fs::File::open, no nofollow); on Windows, file identity is taken from the already-open handle (avoiding a second open by path).
- **List pagination first (P3)**: paginate over walked keys first, and enqueue only the missing/stale entries of the emitted page (current invariant preserved: recompute limited to the page, `max_keys=1` costs only 1 meta read — listing.rs comment and tests); scanner enqueues the whole bucket.
- **Result ordering and counting**: list re-sorts by key at the end (current `objects.sort_by` behavior preserved); scanner's `ScanSummary` counts are accumulated by the producer from task results (missing/stale → recomputed).
- **Scanner pacing (R2)**: keep the current delay yield — after each enqueued batch (`BATCH_SIZE` redefined as "number of compute tasks enqueued per batch") do `yield_now + sleep(delay)` (the `[scanner] delay` scheduling contract is not removed); bounded-queue backpressure serves only as an upper-bound fallback.
- **Scanner systemic-failure breaker (R4)**: ≥100 consecutive failures in the same bucket (**excluding NotFound** — a single file disappearing is a normal skip; constant tunable) → abort that bucket's reconcile and propagate (the error); warn at the run layer, retry on the next scan round; single-entry failure skip + warn unchanged (Q10).
- **Required, no inline fallback**: `FsOptions.io_pipeline`/`db_pipeline` are **required** and typed by task `Output` (P4/P7): IO = `Arc<dyn pipeline::Runner<EtagResult>>`, DB = `Arc<dyn pipeline::Runner<Result<(), tinio_fs::Error>>>` (original errors not boxed into `RunOutput`) — pipeline users do not support inline computation; correctness depends on the pipeline existing. **Construction friction in offline/test scenarios is absorbed by `pipeline::InlineRunner`** (tinio-core reference implementation, blanket `Runner<O>`) (Q1 decision): doctor (CLI not yet implemented — commands are stubs; uses InlineRunner when it lands), benches, unit tests, doctests, and tinio-server dev contexts can all just pass `InlineRunner` without starting a runtime; `examples/serve.rs` is the one exception — it builds the real `Pipelines` runtime (the online context, serve.rs); the runtime implementation (real concurrent pipeline) lives in tinio-server.
- **Extensibility**: any slow/high-IO operation implements `pipeline::Task` into the IO pipeline; any batched persistence implements `pipeline::Task` into the write pipeline (e.g. future backends, object-copy verification).

### 3.3 Configuration (Two Pipeline Sections + `[storage.fs]` Additions)

- **`[pipeline.io]` and `[pipeline.db]`** are their own sections (tinio-config gains a `pipeline` config structure with `io`/`db` sub-structures; **absent section → defaults, presence-gated, Q8**), each with three keys: `workers` (io default **2**, 1..=64 — the task-5 full-pipeline benchmark knee, basis in task-5-report.md; db default **1**, 1..=4 — redb single-writer, 1-vs-2 verification cell +0.5%/+1.7%, task-5-report.md), `priority` (`normal`/`low`/`high`, default `normal`; mapping see §3.4 — low/high verified and pinned at implementation time: `Crossplatform(0)` → `THREAD_PRIORITY_IDLE`, `Crossplatform(99)` → `THREAD_PRIORITY_TIME_CRITICAL`, Q7), `capacity` (bounded queue capacity, default 1024, 1..=65536).
- **`[storage.fs]` gains two keys** (the sub-section is already established: `follow_symlinks` + `compact_threshold_percent`, landed in prerequisite-spec task 6): `meta_batch_size` (default **128** — the task-2.5 set_batch exploratory benchmark knee: the large-entry marginal gain per doubling falls below 2× at 128 in all three runs, basis in task-2.5-report.md; range 1..=4096, write-batch grouping, Q6), `meta_batch_bytes` (default 262144 = 256 KiB — confirmed by the task-2.5 calibration: it binds only for entries > 2048 B, impossible for legal keys, so it stays a memory bound + safety valve, task-2.5-report.md; range 1024..=16 MiB, write-batch byte cap; per-entry estimate ≈ 56B + key byte length, Q5); `[pipeline.io] workers` default **2** — the task-5 full-pipeline benchmark knee (1→2 +1.8–2.1×, 2→4 never gains and regresses on the short-key axis, 4→8 flat, basis in task-5-report.md); `[pipeline.db] workers` default **1** confirmed by the same benchmark (+0.5%/+1.7% vs 2 — no write-throughput gain, redb single-writer). No arbitrary/guessed values. **Default-value pattern consistent with the current state**: constants live in the tinio-core storage module (same pattern as `DEFAULT_FOLLOW_SYMLINKS`/`DEFAULT_COMPACT_THRESHOLD_PERCENT`); the config schema and `FsOptions` share them to prevent drift.
- contracts/config.md updated in sync (with each section's defaults and value ranges); auto-generated config does **not** emit the `[pipeline.*]` sections (Q8); the write side is plain `toml` — the `toml_edit` write path was dropped as unmotivated (F47, root pin removed).

### 3.4 Thread Priority (`thread-priority` Crate)

One independent tokio runtime per pipeline (`worker_threads = workers` + `thread_name("tinio-pipeline-io"/"tinio-pipeline-db")`); `Builder::on_thread_start` calls `ThreadPriority::set_for_current()` at thread start (tinio-server gains the workspace dependency `thread-priority` 3.1.1 — latest version as of 2026-06 verified, MIT, cross-platform mapping Windows `SetThreadPriority` / Unix `nice` etc., includes `ThreadPriority::Crossplatform(u8)`); `priority = low` avoids hashing/write batches preempting request threads. Tasks run on the pipeline's own threads (a prerequisite for priority to take effect — tokio's `on_thread_start` also applies to blocking-pool threads, but this design routes the task IO through tokio::fs (Q4): the file syscalls run on the tokio blocking pool, whose threads also apply the on_thread_start priority); the producer (server runtime) enqueues across runtimes via a tokio channel (channels are not bound to a runtime). Failure to set priority (permissions etc.) → warn log and continue degraded (best effort). `pipeline::InlineRunner` does not implement priority (same-thread execution, no thread to set).

**priority mapping (Q7 revision, replacing the original Q5 decision)**: `ThreadPriorityValue` range is **[0;100)** — the original decision `Crossplatform(255)` is **out of range and dropped**. The crate's Windows mapping is **banded, not a raw cast** (`TryFrom<ThreadPriority> for WinAPIThreadPriority` in thread-priority 3.1.1): `Crossplatform(0)` → `THREAD_PRIORITY_IDLE` (-15), 1..=19 → `Lowest` (-2), 20..=39 → `BelowNormal` (-1), 40..=59 → `Normal` (0), 60..=79 → `AboveNormal` (1), 80..=98 → `Highest` (2), `Crossplatform(99)` → `THREAD_PRIORITY_TIME_CRITICAL` (15) — verified at implementation time (probe below). Decision: `normal` = do not set; `low` = `Crossplatform(ThreadPriorityValue::MIN)` = **0** → `THREAD_PRIORITY_IDLE`; `high` = `Crossplatform(ThreadPriorityValue::MAX)` = **99** → `THREAD_PRIORITY_TIME_CRITICAL` (default `normal`; high only when explicitly enabled). Verification results and chosen values are recorded in this spec.

**Verified at implementation (2026-08-28, Windows probe `windows_thread_priority_mapping_probe` in tinio-server pipeline.rs, passing)**: `low` = `Crossplatform(ThreadPriorityValue::MIN)` = **0** → Windows reads back `THREAD_PRIORITY_IDLE`; `high` = `Crossplatform(ThreadPriorityValue::MAX)` = **99** → Windows reads back `THREAD_PRIORITY_TIME_CRITICAL`; midpoint 50 → `Normal`, confirming the small-to-low / large-to-high direction of the crate's banded mapping (not a raw `SetThreadPriority(priority as i32)` cast — the bands are listed above). `ThreadPriorityValue::try_from(100)` errors, confirming the [0;100) range. `set_for_current` failure degrades with a warn (`priority_set_failure_warns_and_degrades`).

### 3.5 Lifecycle

Both pipelines follow the server lifecycle (construct/shutdown); tasks exit naturally after `shutdown()`; scanner watch shutdown semantics unchanged — exit after in-flight batches complete. **Shutdown order (R5)**: server stops accepting new requests → **IO pipeline** shutdown → **DB write pipeline last** — in-flight list's already-enqueued batches can complete the final drain (Q2). **Tasks queued but not yet executing at shutdown are dropped** (executing ones finish naturally); after shutdown `enqueue` returns `Err(Error::ShutDown)` (Q3). When a task is dropped before send (panic or queued-drop), awaiting the `Completion` yields `Err(Error::Dropped)`.

### 3.6 Semantics Preserved (Invariants)

The `matches` gate (**done by the producer before enqueue, P6**), last-write-wins, and crash-lost-batch self-healing (uncommitted entries are recomputed next time — a batch lost in the queue is equivalent to uncommitted) are all unchanged. **New invariants (2026-08-25 re-review)**: composed-ETag touch-preservation semantics reproduced inside the task (P1); corrupt-entry self-healing — the gated load aligns row-by-row with `ObjectMetaTable::get` semantics (invalid etag field → treated as missing, recomputed and rewritten; `corrupt_entry_self_heals_on_recompute` test behavior preserved; invalid key field → skip that row), rather than the existing `walk()`/`for_bucket()` whole-corrupt-row `CorruptMeta` semantics (P2); a file disappearing between walk and hash (NotFound) keeps its current handling: list skips the entry, scanner skips (existing listing.rs/scanner.rs semantics). **Error semantics (Q10 decision)**: list — task failure → that entry Err → the whole list propagates (the error) (consistent with the current state); scanner — **upgraded to single-task failure skip + warn and continue** (behavior change: currently any entry failure aborts the whole bucket's reconcile with a run-layer warn; with the pipeline, single-failure cost approaches zero, so the scanner should continue and the next scan round self-heals); **systemic-failure breaker (R4)**: ≥100 consecutive failures in the same bucket (excluding NotFound) → abort the bucket and propagate (the error), preventing a whole-bucket failure from being drowned out by per-entry warns; task panic (R6) → the worker does not send, the `Completion` gets `Error::Dropped`, the producer treats it as a failure (list propagates (the error) / scanner counts toward the threshold). **Error messages preserve the original error (P7)**: `pipeline::Error::Dropped` is a unit variant (P7 simplification, 2026-08-29); task `Output` uses original types such as `tinio_fs::Error`, no `to_string()`, no type-erasing boxing.

### 3.7 Memory Trade-off

Whole-bucket meta loaded into memory + in-pool buffers (io_workers × 64 KiB) + dual-queue tasks (constant) — acceptable at local-server scale.

## 4. Write-Lock Latency Statistics and Pipeline Observability

**Motivation**: under the single-writer model the write lock is the serialization point; batched writes lower the contention frequency, but the contention cost must be **observable** — which writes wait on the lock and for how long — to validate the batching gains and find hotspots.

**Design**:

- tinio-fs built-in **fixed-bucket histogram** (atomic counters, no third-party dependency): the timing wrapper lands on `database::Handle`'s (formerly `DbHandle`) **closure-style write-transaction wrapper** (meta-redb-spec G2 settled: record wait before entry, total at closure end) — from wrapper entry to `begin_write()` returning ≈ **lock wait** (blocked on the single-writer lock; includes a small transaction-init overhead, approximate by definition), to commit/abort returning = **total write-transaction duration** (including fsync). Two histograms (wait / total). **Revised by the data-path review (2026-08-27, G3)**: `Handle::write` is async — the closure + commit run on the tokio blocking pool via `spawn_blocking`, and the wrapper captures `start` at entry **before** the hop, so wait spans entry → `begin_write()` **including the blocking-pool queue delay** (a queued write waits for a pool slot as well as the single-writer lock) and total spans entry → commit/abort return (handle.rs `timed_write`).
- Bucket bounds (microseconds): `<10, <100, <1k, <5k, <20k, <100k, >100k` (constants tunable); the snapshot contains per-bucket counts + count + sum/max, from which approximate p50/p90/p99 can be derived.
- `write_lock_stats() -> WriteLockSnapshot` read-only accessor; the tinio-server metrics layer converts it to a prometheus cumulative-bucket histogram (`_bucket{le=...}`) at scrape time, aligned with the existing "full-scan gauges 30s TTL read-only snapshot" pattern — tinio-fs does not take a prometheus dependency.
- **Pipeline observability (tinio-server runtime)**: the IO and write pipelines each have a `stats()` snapshot (queue depth / in-flight / busy workers); tinio-server /metrics outputs gauges — whether CPU/IO and DB writes are under control is directly observable.
- **Write-pipeline failure reporting (R8/R7)**: the Runner always `Reply::send(run()'s Output)`. If the `Output` is a failure `Result`, the worker **always warns** via `Outcome::failure()` — list awaits the `Completion` yet the log is still written; when scanner drops the handle, `send` returns `Err(value)` and the log has already been written (Q3b fallback). The write-pipeline worker tracks consecutive failures; ≥10 (constant tunable) → escalate to a strong warn ("likely systemic") — **without stopping consumption** (stopping would hang producer enqueue), reset on success. **Escalation fires once per streak** (anti-log-spam, confirmed at review 2026-08-29): the "≥10" reads as "at the 10th" — the strong warn fires when the streak crosses the threshold, per-failure warns continue past it, and a success resets the streak, re-arming the next escalation.
- All write transactions go through the `Handle::write` closure wrapper → full coverage (`meta::Store`/`bucket::Store`/`multipart::Store` all hold `Arc<database::Handle>`; no per-call-site instrumentation needed). **Out-of-scope exception (P5)**: `evaluate_compact`'s statistics transaction is the only direct `begin_write()` path (once per sweep round) — the timing helper is sunk into a `Handle`-private unified path shared by `write()` and `evaluate_compact`, so "full coverage" holds.
- The write-lock histogram is a **cheap atomic snapshot** (no full scan) and needs no 30s TTL cache — that TTL pattern belongs only to the storage-layer full-scan gauges (T075); /metrics reads and converts directly at scrape time.

## 5. Acceptance Criteria

**Acceptance run (2026-08-27)**: all criteria below verified — `cargo test --workspace` 576 passed / 0 failed, `cargo clippy --workspace --all-targets` exit 0 (only the pre-existing `tinio-util` warning), C1–C8 all PASS; the per-criterion test-name evidence is in `.superpowers/sdd/pipeline-spec/task-6-report.md` (referenced, not duplicated here).

1. After cold list/cold scan, entries are complete and correct (**composed-ETag preservation and corrupt-entry self-heal-on-recompute do not regress**, P1/P2); write transactions drop from N to ≈N/batch_size; the hot path (second list/scan) has zero write transactions and **zero IO tasks** (P6: matches hits are not enqueued); **list pagination-first preserved** (`max_keys=1` enqueues only the emitted page, 1 meta read, P3); scanner single-compute failure skip + warn continue (Q10), ≥100 consecutive failures in the same bucket abort and propagate (the error) (R4); a file swapped to a symlink between walk and hash → the task refuses to open it (nofollow, R3).
2. Both pipelines' bounded-queue backpressure works (when either pipeline is slow the producer blocks instead of piling up unboundedly).
3. Write-lock latency distribution observable: tinio-fs `write_lock_stats()` snapshot + tinio-server /metrics cumulative-bucket histogram (lock wait and total transaction duration), approximate p50/p90/p99 derivable from the buckets.
4. Config works: `[pipeline.io]`/`[pipeline.db]` `workers`/`priority`/`capacity`, `[storage.fs]` `meta_batch_size`/`meta_batch_bytes` take effect, out-of-range/invalid values error, absent sections use defaults (presence-gated, Q8); defaults (bases recorded in the task reports): `meta_batch_size` = **128** (task-2.5 set_batch benchmark knee, Q6), `meta_batch_bytes` = **262144** (task-2.5 calibration), `[pipeline.io] workers` = **2** (task-5 full-pipeline benchmark knee: 1→2 +1.8–2.1×, 2→4 regresses on short keys, 4→8 flat), `[pipeline.db] workers` = **1** (task-5 1-vs-2 verification: +0.5%/+1.7%, redb single-writer) — nothing arbitrary/guessed; default constants live in the tinio-core storage/pipeline modules (same `DEFAULT_*` pattern, shared by config and `FsOptions` to prevent drift).
5. CPU/IO controllability and generality: concurrent hash streams and file-handle count ≤ `[pipeline.io] workers` (bounded by the runner to [pipeline.io] workers — one task per worker — asserted by a concurrency test, Q4); write-pipeline parallelism ≤ `[pipeline.db] workers` with batched commits (write transactions ≈ N/batch); both pipelines' snapshots observable (tinio-server `stats()` + /metrics gauges); **generality — non-etag task types (stub tasks) can be enqueued and executed**.
6. `pipeline::InlineRunner` (tinio-core, Q1): doctor (cli)/bench/unit-test/dev contexts can construct `FsStorage` without starting a runtime; required-pipeline semantics unbroken (missing pipeline → compile-time type error, not runtime panic).
7. Shutdown semantics: after shutdown tasks exit naturally, queued tasks dropped, `enqueue` returns `Err(Error::ShutDown)` (Q3); shutdown order IO → DB (R5), in-flight list's already-enqueued batches can complete the drain.
8. Pipeline resilience (R6/R7/R8): task panic → strong warn + that worker stays alive and keeps processing later tasks, awaiting the `Completion` yields `Error::Dropped`; ≥10 consecutive write-pipeline batch failures → escalate to strong warn once per streak (consumption not stopped, reset on success); failures are still logged via `Outcome` when the `Completion` is dropped.

## 6. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Hashing load (CPU/IO) out of control | IO pipeline parallelism cap (`[pipeline.io] workers`) + bounded-queue backpressure + 64 KiB bounded buffers; write pipeline's independent backpressure prevents DB write pileup; both pipelines' snapshots observable |
| Thread-priority set failure / platform differences | Best effort: `set_for_current` failure warns and continues degraded; `normal` always available; mapping centralized in the `thread-priority` crate |
| Dual-runtime complexity | Per-pipeline runtime structure identical (same constructor parameterized); `InlineRunner` absorbs non-server scenarios, tests never touch runtimes |
| Crash losing a batch | Equivalent to uncommitted → next cold path recomputes and self-heals (semantic invariant §3.6) |
| Misconception that write-pipeline workers >1 helps | Config range allows 1..=4 (tuning headroom), default 1 verified by benchmark and recorded |
