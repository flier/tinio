# Contract: S3 Data-Plane Surface

**Branch**: `001-s3-local-server` | **Date**: 2026-08-21

The S3 protocol surface implemented by the backend over s3s (routing, XML, error codes, SigV4/SigV2 verification handled by the framework). All other operations of the S3 trait (99 total) return standard NotImplemented errors.

## Implemented operations (~30)

| Group | Operations |
|-------|-----------|
| Buckets | `CreateBucket` (FR-002, FR-012), `DeleteBucket` (only empty → else `BucketNotEmpty`), `HeadBucket`, `ListBuckets` (2025-03 pagination semantics: `continuation-token` / `max-buckets` / `prefix`; a `ContinuationToken` is returned when more buckets remain; CreationDate from the `BUCKETS` table of `meta.redb`), `GetBucketLocation` (returns `us-east-1`), `PutBucketTagging`/`GetBucketTagging`/`DeleteBucketTagging` (FR-030; replace-all put; missing bucket → `NoSuchBucket` on get/put, delete idempotent — 204), `PutBucketCors`/`GetBucketCors`/`DeleteBucketCors` (FR-033; see §Bucket CORS below) |
| Objects | `PutObject` (FR-003, ETag = content MD5), `GetObject` (FR-003; Range → seek + `206`/`Content-Range`; ETag; Content-Type inferred; If-Range FR-029), `HeadObject`, `DeleteObject` (conditional trio FR-027), `DeleteObjects` (batch), `CopyObject` (FR-015; server-side file copy, no client passthrough; source conditionals `x-amz-copy-source-if-*` and destination conditionals `x-amz-if-match`/`x-amz-if-none-match` → 412 on failure; destination both-present → 400 FR-027), `GetObjectAttributes` (FR-032; requested subset; retained-part pagination), `RenameObject` (FR-031; atomic same-bucket move — source + destination conditionals, destination overwrite), `GetObjectTagging`/`PutObjectTagging`/`DeleteObjectTagging` (FR-030; replace-all put, delete clears; missing object → `NoSuchKey` on get/put, delete idempotent — 204) |
| Listing | `ListObjects` (V1), `ListObjectsV2` (V2) — prefix filtering, delimiter grouping, pagination per S3 semantics (FR-004) |
| Multipart | `CreateMultipartUpload`, `UploadPart`, `UploadPartCopy`, `CompleteMultipartUpload` (composed ETag `MD5-of-MD5s-N`; conditional writes FR-028; non-final parts ≥ 5 MiB enforced authoritatively in the storage commit), `AbortMultipartUpload` (`If-Match-Initiated-Time` FR-028), `ListParts`, `ListMultipartUploads` (FR-014) |

## Behavior notes

- **ETag**: single uploads `"<md5hex>"`; multipart `"<md5hex>-N"`; served only when meta-store size/mtime matches, else recomputed streaming (FR-022). Listings include ETags — missing/stale entries are recomputed synchronously during the listing (one-time full-content pass over externally-added files, documented cost of SC-006).
- **Range**: framework parses the header; backend seeks and returns the correct range + `Content-Range`.
- **Content-Type**: inferred from extension (`mime_guess`, fallback `application/octet-stream`); user `x-amz-meta-*` accepted and dropped.
- **Checksums** (FR-026; `x-amz-checksum-*`): validated and echoed on multipart uploads and single-object PUTs behind `[s3] checksum = true` (default `false` = accepted and dropped, the v1 behavior); see [Multipart upload checksum validation design](../../../docs/superpowers/specs/2026-08-31-multipart-checksum-validation-design.md). Effective validation coverage (which request combinations are actually validated when the toggle is on):
  - `UploadPart` — at most one `x-amz-checksum-<algo>` value (header field or aws-chunked trailer; `Content-MD5` may coexist and is validated in the same pass); a mismatch answers `BadDigest` and the part is never stored. A part whose algorithm differs from the upload's create-time algorithm answers `InvalidRequest`.
  - `UploadPartCopy` — no client checksum value exists on the wire (AWS defines none); for create-algorithm uploads the server computes and persists the copied part's checksum and echoes it in `CopyPartResult`.
  - `CompleteMultipartUpload` — `CompletedPart` checksum entries are cross-checked against the stored values; the full-object value is validated pre-commit (`COMPOSITE` = the algorithm over the concatenated raw part digests; `FULL_OBJECT` = CRC linearization, CRC algorithms only) with algorithm/type/size consistency (`BadDigest` on value or type conflicts, `InvalidRequest` on algorithm/type/size shape violations).
  - `PutObject` with a client checksum value validates it through the staging tee (mismatch → `BadDigest`, nothing stored) and records the validated digest as the object's checksum (kind `FULL_OBJECT`); the PUT response echoes the value only when the request carried one (the UploadPart rule). `PostObject` rides the framework's put-object delegation. `CopyObject` carries the source's recorded checksum into the destination (value AND kind — the bytes are identical; AWS documents the automatic carry) and a client `x-amz-checksum-algorithm` on the copy stays accepted and dropped (known deviation: AWS recomputes the requested algorithm). No default CRC64NVME is auto-attached.
  - **Recorded checksum & echo** (2026-09-03, the tagging-plan amendment): the object row records the checksum at write time — algorithm wire, base64 value, and kind — and the read paths never compute or derive. `CompleteMultipartUpload` records the full-object value it derived pre-commit with the kind that produced it (`COMPOSITE` by default — the checksum-of-checksums over the concatenated raw part digests, uniform for every algorithm; `FULL_OBJECT` for the CRC linearization shape). `RenameObject` preserves the record (FR-031); an overwrite replaces it (a checksum-less write clears it). GET/HEAD echo the per-algorithm header plus `x-amz-checksum-type` whenever a checksum is recorded — unconditional, no `x-amz-checksum-mode` gating (AWS serves the echo only when the checksum was uploaded with the object); `GetObjectAttributes`' `Checksum` member reads the same record (FR-032). A toggle-off write records nothing (accept-and-drop, so nothing echoes).
  - Deviations: a Complete-time checksum value without a create-time algorithm is accepted but not validated (documented AWS behavior for CRC32/CRC32C/SHA-1/SHA-256; assumed for CRC64NVME); Complete validation is skipped (warn) when any listed part lacks a stored checksum; create-algorithm uploads' `UploadPartCopy` gives up the zero-copy fast path.
- **Error codes** (FR-005): `NoSuchBucket`, `NoSuchKey`, `InvalidBucketName`, `BucketAlreadyExists`, `BucketNotEmpty`, `InvalidAccessKeyId`/`SignatureDoesNotMatch` (framework), `NotImplemented` (disabled/unsupported ops), etc.
- **Traversal** (FR-006): keys containing `..`/absolute/control sequences rejected before any FS access.
- **Conditional requests** (FR-027/FR-028/FR-029; RFC 9110 §13.2.2 precedence): `If-Match` / `If-None-Match` / `If-Modified-Since` / `If-Unmodified-Since` honored on Get/Head (`If-None-Match` / `If-Modified-Since` failure → `304 Not Modified`; `If-Match` / `If-Unmodified-Since` failure → `412 Precondition Failed`); on the PUT write path only `If-Match` / `If-None-Match` are evaluated (any precondition failure → `412 Precondition Failed`) — `If-Modified-Since` / `If-Unmodified-Since` on PUT are not supported. The Copy source is evaluated per S3 semantics. Conditional checks reuse the meta-store ETag + filesystem mtime.
  - **Conditional deletes** (FR-027): DeleteObject evaluates `If-Match` (strong ETag; `*` matches any existing object), `x-amz-if-match-last-modified-time` (whole-second equality) and `x-amz-if-match-size` (exact size) — every provided header must pass, else `412`; the head-check + delete run in the per-key critical section. Missing-object policy (AWS model text): a missing object answers 204 under every conditional header — "if the [validator] matches or if the object doesn't exist, the operation will return a 204" — delete is idempotent and the conditions gate an existing object only; no conditions → 204 unchanged. A negative size is a request-shape error → 400 `InvalidArgument`, validated before the head (state-independent).
  - **Write-path shape gate** (FR-027, AWS conditional writes): PutObject, CopyObject's destination (`x-amz-if-match` / `x-amz-if-none-match`), RenameObject's destination (the same plain headers on the rename request), and CompleteMultipartUpload share one gate — `If-Match` + `If-None-Match` in one request → 400 `InvalidRequest`, and a specific (non-`*`) `If-None-Match` → 501 `NotImplemented` (AWS does not implement specific If-None-Match values on writes; a non-matching value must never fall through to a silent overwrite). Both are request-shape errors, validated before the body is staged / the parts parsed and the lock. The copy-source family (`x-amz-copy-source-if-*`, CopyObject and UploadPartCopy) and RenameObject's source family (`x-amz-rename-source-if-*`) are NOT subject to the gate — they keep the RFC 9110 §13.2.2 evaluation order (If-Match first, then If-None-Match), no 400 (AWS documents no such restriction for the copy-source family; the rename-source family follows it). Read paths (Get/Head) keep the RFC order (304/412).
  - **Conditional multipart writes** (FR-028): CompleteMultipartUpload conditions evaluate against the object currently at the key (the one being replaced), atomically under the write lock: `If-Match` mismatch → 412, missing destination → `404 NoSuchKey`; `If-None-Match` accepts `*` only — existing object → 412, missing → pass, a specific ETag value → 501 `NotImplemented`. Non-final listed parts must be ≥ 5 MiB: the S3 layer pre-checks its lock-held listing snapshot (`EntityTooSmall`), and the storage commit re-reads the current part state and enforces the rule authoritatively (`PartTooSmall` — a concurrent UploadPart overwriting a part after the snapshot is caught at the commit). AbortMultipartUpload honors `x-amz-if-match-initiated-time` (whole-second equality with the upload's Initiated timestamp → else 412; a missing upload answers `NoSuchUpload` regardless); no server lock — conditional and unconditional aborts alike rely on the storage's one-transaction drain (in-txn existence + key match; a complete landing between the check and the drain surfaces as `NoSuchUpload`).
  - **If-Range on GET** (FR-029): evaluated only when a `Range` is present (an If-Range without a Range is ignored). A strong-ETag match or an HTTP-date match (`last_modified` ≤ header date at whole-second precision) serves the Range (206); a **mismatching** validator drops the Range (the full 200 is served; an unsatisfiable Range answers 416 only when the If-Range matches or is absent). A wildcard or an unparseable value is not a valid If-Range — the header is ignored, so the Range is served as if absent (bare unquoted tokens included: s3s's S3-compat ETag parse tolerates them, the If-Range parser does not). The RFC 7232 conditions are evaluated first. Read-path snapshot policy (revised 2026-09-02 #2/#3): every request without RFC 7232 conditions is a **single fetch** whose snapshot the validators evaluate on, race-free by construction — a no-Range conditional GET is a fetch + post-check (a failed precondition answers 304/412 with that snapshot's validators), and a pure If-Range request fetches the Range against one snapshot and evaluates the If-Range on it, refetching the full object when the validator is stale (the served bytes are discarded; a stale validator pays a wasted range read, no more). Only a Range request carrying RFC 7232 conditions reads a head first (a precondition 304/412 must answer before a 416, and the head gates the fetch shape); the response metadata always comes from the body fetch's own snapshot. When a write lands between the head and the fetch — detected by ETag **or mtime** difference (a byte-identical rewrite changes only the mtime) — the conditions re-evaluate against the fetched snapshot; a full object is refetched only when the fetch actually served a range and the If-Range no longer matches (never discarding an already-fetched full body), the refetch re-validates, and a ranged fetch answering `InvalidRange` drops the Range for the full object when the If-Range is stale or its reported size differs from the head's (the object shrank) — the head-first flow classifies against the head it holds, the head-less pure-If-Range flow against a head taken lazily on the error path — and answers 416 otherwise (validator current and size unchanged). Unconditional GETs keep the direct fetch.
- **Object tagging** (FR-030): object tags are stored metadata — both backends persist the object row's canonical wire string (sorted `k=v&k2=v2`, RFC 3986-encoded), and `Info.tags` is always populated: head/get/listing carry it, and GetObjectTagging plus the `x-amz-tagging-count` echo read the same field (no dedicated tag fetch on the read paths). The `?tagging` surface: `GetObjectTagging` returns the stored set — a tag-less object answers the empty `<TagSet>` — and a missing object answers 404 `NoSuchKey`; `PutObjectTagging` replaces the whole set (replace-all, never a merge; missing object → 404 `NoSuchKey`); `DeleteObjectTagging` clears the set (204; idempotent on a missing object, like the object delete). None of the three touches the object body or its remaining metadata, and none takes the per-key lock — tag writes are last-writer-wins against concurrent object and tag writes (AWS gives no atomicity guarantee; deliberate). **Validation** is shared by every surface through the core `Tags` type: keys 1..=128 and values 0..=256 UTF-16 units; charset = Unicode letters, numbers, and spaces plus `+ - = . _ : / @` (the S3 Control regex); duplicate keys rejected; count caps are per surface — ≤ 10 tags for an object, ≤ 50 for a bucket; every violation answers `InvalidTag` (400), on the XML `TagSet` and the header alike. **Write paths**: the `x-amz-tagging` header (URL-encoded `k=v&k2=v2`, RFC 3986-strict decode — `+` stays literal, `%20` is space) is real on `PutObject`, on `CopyObject` under REPLACE, and on `CreateMultipartUpload` (stored in the upload state, applied at completion); a malformed value answers `InvalidTag` before the body is staged / the parts parsed (request-shape — the failed put never creates the object). `x-amz-tagging-directive` is CopyObject-only: COPY (the default) carries the source's set into the destination — a copy never invents tags — and REPLACE records the request's parsed set (empty when the header is absent); the directive never rewrites the source's own tags. `x-amz-tagging-count` rides GET (the dto field) and HEAD (hand-set response header — the s3s head output models no field) whenever the object carries tags, and is omitted for a tag-less object. **Capability toggle** (FR-021): the six tagging operations (this trio plus the bucket trio below) gate on the `tagging` capability (`[s3] tagging`, default on) — off ⇒ every one answers `NotImplemented`, the write headers (`x-amz-tagging`, `x-amz-tagging-directive`) are accepted and dropped unvalidated (a malformed value passes), and the count echo is suppressed.
- **Bucket tagging** (FR-030): `PutBucketTagging` / `GetBucketTagging` / `DeleteBucketTagging` store the bucket's set in the bucket row (same canonical wire string; replace-all put; the 50-tag cap → `InvalidTag`). A missing bucket answers 404 `NoSuchBucket` on get and put — only the delete is idempotent on the bucket's existence (204, for a missing and a tag-less bucket alike). No per-bucket lock (last-writer-wins, as on the object surface). The trio is pinned by the conformance harness (both backends), the server unit suite, and `tagging.feature` (round trip + off-mode, alongside the object trio).
- **Bucket CORS** (FR-033; design `docs/superpowers/specs/2026-09-05-s3-cors-design.md`, close of gap-analysis Tier A#2): `GetBucketCors`/`PutBucketCors`/`DeleteBucketCors` store the bucket's CORS configuration in the bucket row (canonical order-preserving wire string, an additive BUCKETS element; a zero-rule set is normalized to the `''` wire). The `''` wire = no configuration — `get` answers 404 `NoSuchCORSConfiguration` `"The CORS configuration does not exist"`, `delete` is idempotent on a no-config existing bucket (204), and `put` replaces the WHOLE set (replace-all, never a merge; rule order preserved — the wire codec never sorts or dedupes); a missing bucket answers 404 `NoSuchBucket` on all three (the bucket-existence check is the storage's, not a config-level one). No per-bucket lock — last-writer-wins, as on the tagging surface. **Put validation** (400 `InvalidRequest`): ≥1 rule — an XML body with zero `CORSRule` elements never reaches the handler: s3s's deserializer answers 400 `MalformedXML` at the shape gate (the handler's `InvalidRequest` for an empty rule list is unit-pinned only); ≤100 rules; rule ID ≤255 chars; every rule has ≥1 `AllowedMethod` AND ≥1 `AllowedOrigin` (the dto lists can come back EMPTY from an XML body with zero such elements); `AllowedMethod` ∈ the five AWS values (accepted case-insensitively, stored uppercased); ≤1 `*` per allowed-origin/header pattern; no `,` in any list item or rule ID; no C0 (<0x20)/DEL (0x7f) control bytes; `MaxAgeSeconds` ≥ 0; decoded config ≤ 64 KB (bounds the per-Origin-request scan amplification). **Content-MD5** is required, AWS three-state: missing → 400 `InvalidRequest` `"Missing required header for this request: Content-MD5"` (message verbatim); malformed (not 16-byte base64) → 400 `InvalidDigest`; digest EQUALITY against the XML body is not verified — s3s's deserializer consumes the body, so AWS's `BadDigest` path is unreachable (recorded deviation, shared with the ACL plan; `x-amz-checksum-*` does not substitute). **Preflight** (the anonymous browser OPTIONS) is answered by a custom route on s3s 0.15's `S3Route` seam, matched before op dispatch; a true preflight = OPTIONS with `Origin` AND `Access-Control-Request-Method` (a bare OPTIONS probe is NOT a preflight — falls through to s3s's 501 `"Unknown operation"`, the pre-feature behavior), the route's `check_access` is overridden (browsers cannot sign preflights; the bucket's config is the only authorization), and the bucket is resolved path-style. Allowed: 200 with an empty body (`Content-Length: 0`), `Access-Control-Allow-Origin` = the requested origin — or the literal `*` when the matched rule's origin is the bare `*`, in which case `Access-Control-Allow-Credentials` is OMITTED (`*`+`true` is spec-illegal; concrete rules echo the origin with `Credentials: true`) — `Access-Control-Allow-Methods` = the matched RULE's full method list, comma-joined (pinned — not the requested method), `Access-Control-Allow-Headers` = the request's own names, rule-filtered and echoed verbatim (case/spelling kept; omitted when the request sent none), `Access-Control-Expose-Headers`/`Access-Control-Max-Age` when the rule sets them, and `Vary: Origin, Access-Control-Request-Headers, Access-Control-Request-Method` APPENDED (merge, never replace). Denied: 403 `AccessDenied` (recorded deviation — AWS sends `AccessForbidden`, s3s 0.15's enum has no such code) with AWS's message text verbatim — no configuration (or a well-formed but MISSING bucket: the same message, `"CORS is not enabled for this bucket."`, closes the existence oracle — a probe cannot distinguish) and rule mismatch (`"CORSResponse: This CORS request is not allowed. This is usually because the evalution of Origin, request method / Access-Control-Request-Method or Access-Control-Request-Headers are not whitelisted by the resource's CORS spec."` — the "evalution" typo is AWS's own, kept); denials carry NO `Access-Control-*` headers and no `Vary`; a SYNTACTICALLY invalid bucket name (bad chars, too long) is answered by s3s itself with 400 `InvalidBucketName`/`InvalidURI` BEFORE the route matches, so the never-reveal 403 is scoped to well-formed names. **Decoration of actual responses**: a non-preflight request carrying a matching `Origin` gets the `Access-Control-*` set on its response — on `Ok` responses only, and s3s encodes op errors as Ok bodies, so 4xx/5xx XML answers are decorated too (matches AWS) — selected by AWS first-match semantics: the FIRST rule whose origin matches wins and the method is validated WITHIN that rule (no fall-through to a later rule); the set is `Access-Control-Allow-Origin` (origin or bare-`*` split as on preflight), `Access-Control-Allow-Methods` (the rule's list), `Access-Control-Expose-Headers` (when set), `Access-Control-Allow-Credentials` (concrete rules only), the `Vary` trio appended — and NO `Access-Control-Allow-Headers` (AWS sends it on preflight only). Every header value derived from request or config data is built FALLIBLY: a value `HeaderValue` rejects is skipped, never a panic (combined with the put-layer control-byte rejection, two layers against header-value injection). **Gating** (double, FR-021): the `cors` cargo feature (default on, in `default`) strips the three ops, the route, and the decorator entirely — the ops answer s3s's own 501 defaults (`"… is not implemented yet"`) and OPTIONS falls through to s3s's 501; the `[s3] cors` capability (default true) keeps the code but answers 501 `NotImplemented "{name} is disabled"` per op and leaves the route unregistered (a browser OPTIONS falls through to s3s's 501 too — never an `Access-Control-*` answer). Pinned by the conformance harness (both backends), the server unit + data-plane suites, `cors.feature`, and the boto3-journey CORS legs.
- **RenameObject** (FR-031; the AWS directory-bucket move, honored on the general-purpose model): wire shape `PUT /{bucket}/{destination}?renameObject` — not a query-disambiguated POST — with the source in the `x-amz-rename-source` header: a key of the request's own bucket, bare or with the single leading slash of the documented form (stripped before the degenerate-key comparison; a bucket-prefixed source is not a legal key here). The response echoes the moved object's ETag as a response header (the s3s 0.15 output model is empty). The move is atomic: bytes, ETag, tags, recorded checksum, and any retained `OBJECT_PARTS` rows migrate with the record (fs: one metadata transaction — a rename is not a fresh object). An existing destination with no destination conditions is **overwritten** (AWS implies it — overwriting is prevented only by adding `If-None-Match`); source == destination answers 412 `PreconditionFailed` (the degenerate-key check fires before any head; the only AWS-stated failure mode); a missing source answers 404 `NoSuchKey` under any source condition (AWS is silent on the code — tinio's choice). Source conditions — `x-amz-rename-source-if-match` / `x-amz-rename-source-if-none-match`, malformed → 400 (the etag-parse rule) — evaluate against the source head with the RFC 9110 §13.2.2 order, write-path answers (a failing precondition → 412, never 304); destination conditions ride the plain `If-Match` / `If-None-Match` headers through the shared destination policy (FR-027): on an existing destination the set evaluates (failure → 412; `If-None-Match: *` against an existing destination → 412), on an absent one the shared missing-object policy runs (`If-Match` against nothing → 412, `If-None-Match` passes and the rename proceeds to a 200). Both keys run their per-key critical sections, acquired in sorted order (deadlock-free; the overwrite serializes against same-key writers). Gated under the `copy` capability (compile-time feature and runtime toggle, FR-021) — off ⇒ `NotImplemented`. An in-flight multipart upload created for the source key keeps its recorded key — completing it after the move recreates the source; accepted as a last-writer-wins race, no extra coordination.
- **GetObjectAttributes** (FR-032): `GET /{key}?attributes` returns the requested subset of ETag / ObjectSize / StorageClass / Checksum / ObjectParts of one object; the `x-amz-object-attributes` header selects the set and its entries are comma-joinable (the SDK wire form — each entry splits on commas). A missing object answers 404 `NoSuchKey`. No conditions, no capability gate (the op echoes stored metadata; nothing is recorded while the `checksum` toggle is off, so there is nothing to echo then either). StorageClass is always STANDARD (tinio has no tiers). The Checksum member echoes the recorded object checksum — per-algorithm member plus `ChecksumType` from the recorded kind, no read-path computation (FR-026). ObjectParts answers only when the object's current generation was multipart-completed — a non-multipart object omits the container (AWS) — and paginates the retained assembly parts with the multipart listings' page-size policy: `x-amz-max-parts` (default 1000; < 1 → `InvalidArgument`, the `allow_zero_page_size` hatch) and `x-amz-part-number-marker` (exclusive). The page carries `IsTruncated`, `NextPartNumberMarker` (only when truncated), the applied `MaxParts`, `PartNumberMarker`, per-part number / size / recorded per-part checksum, and the total rides `<PartsCount>` (all parts, not the page). **Parts retention** (the `OBJECT_PARTS` rows — part number, size, algorithm, checksum value): a multipart completion persists the assembled list in the same transaction as the object; an overwrite (plain put or re-completion) and a delete (single or batch) remove the key's rows in the same transaction; a rename migrates the rows with the record (FR-031); a copy never inherits them (the destination is a fresh single-part object). In-flight upload `PARTS` state is untouched — only completed objects retain rows.
- **Folder markers**: keys ending in `/` are not objects. PUT `dir/` creates the directory (idempotent); GET/HEAD on `dir/` return `NoSuchKey`; DELETE `dir/` always returns `204` (idempotent, mirroring AWS DeleteObject marker semantics) and removes the directory only when it is empty — a non-empty directory is left in place.
- **Key charset**: universal rules (all backends): traversal, absolute paths, control characters → rejected. Platform charset restrictions follow the backend: the filesystem backend rejects keys that cannot exist on the host OS (e.g. Windows-invalid characters on Windows); other platforms allow them.
- **Symlinks**: rejected by default (`[storage.fs] follow_symlinks = false`) — access resolving through a symlink is refused and symlink entries are excluded from listings (a link inside a bucket cannot escape the storage root). Opt-in `true` follows links, which may point outside the root (user-owned directory, documented).
- **Capability toggles** (FR-021): runtime `[s3]` section disables groups → `NotImplemented` (`multipart`, `copy_object`, `list_objects_v1`, `list_objects_v2`, `delete_objects`, `tagging` — the last added 2026-09-03, default on, off ⇒ the six tagging operations answer `NotImplemented`, FR-030; `cors` — added 2026-09-05, default on, off ⇒ the three bucket CORS operations answer `NotImplemented` `"{name} is disabled"` and the preflight route is not registered, FR-033); compile-time default-on features (`multipart`, `copy`, `list-v1`, `list-v2`, `cors`) strip the code entirely — stripped groups return `NotImplemented` and their `[s3]` keys are silently ignored.
- **Listing page size**: every listing page size < 1 (`max-buckets`, `max-keys`, `max-parts`, `max-uploads`) answers `InvalidArgument`, and `max-buckets` above the AWS-documented 10,000 is rejected too (never a silent clamp). `[s3] max_buckets` (default 10,000; 0 = unlimited) clamps ListBuckets page sizes — including the no-parameter default; `[s3] max_keys` (default 0 = unlimited) clamps ListObjects page sizes; multipart listings are uncapped. The `[s3] allow_zero_page_size = true` escape hatch restores the legacy empty page (negatives clamped to 0) on the pre-existing `max-keys` / `max-parts` / `max-uploads` surfaces; ListBuckets stays strict. V1/V2/ListParts/ListMultipartUploads responses echo the effective (clamped) page size.
- **SigV2**: disabled by default (`[s3] sig_v2 = false`); enable only for legacy clients — aws cli v2 and rclone always use SigV4.
- **DeleteBucket is 204-before-gone** (F07): the name is unpublished (renamed under `.tinio/deleting/`) before the request answers `204 No Content`; the tree is purged asynchronously on the removal lane. A bucket recreated under the same name is live again immediately — it may briefly coexist with the background purge of the old tree. Removal failures surface as an error log plus the scanner summary's `removal_failures`; a graceful shutdown awaits the lane with a bounded timeout, and any interrupted walk is reclaimed at the next startup repair or scanner pass.
- **Read-only mode** (FR-023): all mutating operations (`CreateBucket`, `DeleteBucket`, `PutObject`, `DeleteObject(s)`, `CopyObject`, all multipart ops) return `AccessDenied`; read operations behave identically.
- **Addressing style**: path-style addressing is the supported/tested mode (s3s serves `/<bucket>/<key>`); virtual-hosted addressing is not configured in v1. Interop tests verify aws cli v2 and rclone work against `127.0.0.1` endpoints without client-side addressing overrides.
- **Listing pollution**: reserved `.tinio/` never appears in `ListBuckets`; root-level files are not buckets (only directories). `.tinio` is a reserved path segment at ANY depth (FR-020): keys containing it are rejected on write (`AccessDenied`), return `NoSuchKey` on read, and are skipped in listings — a nested root's state is never served by an outer server.
- **Out-of-band changes** (FR-013, SC-006): files placed/modified on disk are served immediately; Last-Modified always from FS mtime.
